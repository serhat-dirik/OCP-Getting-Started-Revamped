== Lose the data, then save it · 10 min

Parasol's claims database loses every claim to a routine Pod restart, then survives the same restart once one line of its definition changes.

[IMPORTANT]
.Prep — run before the session
====
This demo runs from the module's *entry* state, where the claims database still writes to an ephemeral volume. Stage it a few minutes ahead, so the application and its database have finished their first boot:

[source,sh,role=execute]
----
ws prep storage-stateful
----

It inspects the project first and offers to clear anything left from an earlier run; answer its prompt. Do not stage the finished lab state: the data loss in step 1 is what the first half of the demo shows, and it only happens on the ephemeral entry state.

Every step runs in the *Terminal* tab as `{user}`, in the `{user}-dev` project. Nothing here needs the web console, so enlarge the terminal font beforehand if the output goes to a shared screen.

NOTE: After every restart, the block waits until the claims application answers its readiness check through its Route before it reads or writes, so no request reaches a Pod that is already gone. The application checks each pooled database connection before using it, which is why step 3 needs no application restart; that it keeps working is the result being shown.

CAUTION: Deleting the *persistent* database Pod in step 3 takes around 30 seconds, because a ReadWriteOnce volume has to detach from one node before it attaches to another; the ephemeral Pod in step 1 comes back in about 15. Neither is a hang. After a rehearsal, run `ws prep storage-stateful` again and accept the wipe — the demo has to start with an ephemeral database and no PersistentVolumeClaim.

=== Brief

image::storage-stateful/storage-stateful-01-storage-chain.svg["The storage abstraction chain in two rows. Inside your namespace, a Pod running your database mounts a PersistentVolumeClaim — what you ask for. That claim is bound to the cluster-scoped row, where a PersistentVolume — what the platform gives you — is created from a StorageClass, the recipe the platform follows, which carves real disk from the cluster's storage backend."]

*Storage that dies with the Pod*

A container's filesystem is part of its Pod. That is correct for a stateless application and fatal for a database: the first time the Pod is rescheduled, upgraded, or simply dies, everything written inside it goes with it. Nothing raises an alarm, because nothing is broken — the platform did exactly what a Pod means.

*The storage abstraction chain*

OpenShift separates the request from the disk. An application asks for storage with a PersistentVolumeClaim in its own namespace; a StorageClass — the platform team's recipe for one kind of storage — provisions a matching PersistentVolume on demand and binds it to the claim. Developers write claims. Nobody files a storage ticket, and nobody picks an array.

*StatefulSet vs Deployment*

A Deployment treats its Pods as interchangeable, which is why a database deployed that way can lose its data to a restart. Software whose identity matters runs as a StatefulSet instead: each Pod keeps its ordinal name and its own claim across restarts. In production an Operator wraps those primitives into a database that also replicates, fails over, and takes backups.

*In this demo*

. Three claims created in Parasol's claims database, and lost to a routine Pod restart
. The ephemeral volume replaced by a PersistentVolumeClaim, in one command
. The same restart repeated, with the claims still there
. The claim traced back to the volume and the class that provisioned it

=== 1 · Three claims, and a restart that loses them — 4 min

Create three claims through the claims application's own API, then delete the database Pod — the same thing a node drain, an upgrade, or a crash does — and read the claims back.

image::storage-stateful/storage-stateful-02-sts-vs-deployment.svg["Two workload shapes side by side. A Deployment whose Pods carry generated names, pod-a1b2 and pod-c3d4, sharing one load-balanced Service; and a StatefulSet whose Pods pg-sts-0 and pg-sts-1 each keep a stable name, own their own volume — data-pg-sts-0 and data-pg-sts-1 — and answer to their own DNS name from a headless Service."]

*Why it matters*

The database runs as a Deployment, so its Pod is interchangeable: the replacement carries the same specification and none of the previous Pod's disk. Its data volume is an `emptyDir` — part of the Pod. A StatefulSet is the right shape for a datastore because identity and volume stay together, but a StatefulSet on an ephemeral volume would lose the data just as completely. The volume is what decides.

[source,sh,role=execute,subs="attributes+"]
----
CLAIMS=$(oc -n {user}-dev get route parasol-claims -o jsonpath='{.spec.host}')
for c in '{"claimant":"Nadia Rahman","type":"auto","amount":3200}' \
         '{"claimant":"Owen Fletcher","type":"home","amount":18750}' \
         '{"claimant":"Priya Das","type":"life","amount":50000}'; do
  curl -s -X POST "http://$CLAIMS/api/claims" -H 'Content-Type: application/json' -d "$c" -o /dev/null -w 'created %\{http_code}\n'
done
curl -s -D - -o /dev/null "http://$CLAIMS/api/claims" | grep -i x-total-count
----

Three claims, in a real PostgreSQL running on the cluster. Now restart the database Pod:

[source,sh,role=execute,subs="attributes+"]
----
CLAIMS=$(oc -n {user}-dev get route parasol-claims -o jsonpath='{.spec.host}')
oc -n {user}-dev delete pod -l app=claims-db
oc -n {user}-dev rollout status deploy/claims-db
oc -n {user}-dev rollout restart deploy/parasol-claims && oc -n {user}-dev rollout status deploy/parasol-claims
for i in $(seq 1 30); do curl -sf -o /dev/null "http://$CLAIMS/q/health/ready" && break; sleep 2; done
curl -s -D - -o /dev/null "http://$CLAIMS/api/claims" | grep -i x-total-count
----

*What just happened*

Zero claims. The application had to be restarted before it could answer at all, because the `claim` table itself was created inside that volume the first time it connected — the whole database went, not only the rows. Ephemeral or persistent is a property of the volume, not of the database.

=== 2 · One volume definition changes — 3 min

Swap the ephemeral volume for a PersistentVolumeClaim in a single command, then create three claims again. The application, the database image, and everything else about the deployment stay as they were.

image::storage-stateful/storage-stateful-01-pvc-bound.png["The claims-db-data PersistentVolumeClaim in the console: a Bound badge beside the name, a donut reading 2 GiB available, and a summary column giving Status Bound, Requested capacity 2 GiB, Capacity 2 GiB, Used 45.69 MiB — the database's actual footprint — Access modes ReadWriteOnce, Volume mode Filesystem, and the StorageClass that provisioned it, ocs-external-storagecluster-ceph-rbd."]

*Why it matters*

`--claim-size=2Gi` is the entire storage request. The cluster's default StorageClass provisions a real volume for it on demand, binds it once the Pod is scheduled, and mounts it at the database's data directory. No ticket, no array, no disk created in advance.

[source,sh,role=execute,subs="attributes+"]
----
CLAIMS=$(oc -n {user}-dev get route parasol-claims -o jsonpath='{.spec.host}')
oc -n {user}-dev set volume deploy/claims-db --add --overwrite --name data \
  -t pvc --claim-name=claims-db-data --claim-size=2Gi --mount-path=/var/lib/pgsql/data
oc -n {user}-dev rollout status deploy/claims-db
oc -n {user}-dev rollout restart deploy/parasol-claims && oc -n {user}-dev rollout status deploy/parasol-claims
for i in $(seq 1 30); do curl -sf -o /dev/null "http://$CLAIMS/q/health/ready" && break; sleep 2; done
for c in '{"claimant":"Persistent Pat","type":"auto","amount":4100}' \
         '{"claimant":"Durable Dana","type":"home","amount":22500}' \
         '{"claimant":"Lasting Lee","type":"life","amount":65000}'; do
  curl -s -X POST "http://$CLAIMS/api/claims" -H 'Content-Type: application/json' -d "$c" -o /dev/null; done
curl -s -D - -o /dev/null "http://$CLAIMS/api/claims" | grep -i x-total-count
----

*What just happened*

The claim was `Pending` for a moment — the default class waits for the first consumer, so the volume is created where the Pod lands — then `Bound`, and the database came back writing to it instead of to the Pod.

=== 3 · The same restart, the opposite outcome — 2 min

Delete the database Pod again, exactly as in step 1, and read the claims straight back. The application is not restarted this time.

image::storage-stateful/storage-stateful-04-what-you-built.svg["What the change amounts to: an emptyDir volume, marked as data that dies with the Pod, replaced through oc set volume --overwrite by the Bound claim claims-db-data on a PersistentVolume from the default StorageClass. Beside it, the StatefulSet form of the same idea — pg-sts-0 and pg-sts-1, a per-Pod claim each, stable identity over headless DNS, a partitioned update, and an init-container migration."]

*Why it matters*

The same Pod restart, the opposite outcome, and no recovery procedure in between: the data was never in the Pod. The application did not have to be told anything, because both its schema and its rows were on the volume, waiting for the new Pod to mount them.

[source,sh,role=execute,subs="attributes+"]
----
CLAIMS=$(oc -n {user}-dev get route parasol-claims -o jsonpath='{.spec.host}')
oc -n {user}-dev delete pod -l app=claims-db
oc -n {user}-dev rollout status deploy/claims-db
for i in $(seq 1 30); do curl -sf -o /dev/null "http://$CLAIMS/q/health/ready" && break; sleep 2; done
curl -s -D - -o /dev/null "http://$CLAIMS/api/claims" | grep -i x-total-count
----

*What just happened*

Three claims, through the restart that emptied the database two steps ago. The only difference between the two outcomes is what the `data` volume is.

=== 4 · Where the disk came from — 1 min

Follow the chain in the terminal: the claim in the project, the PersistentVolume bound to it, and the StorageClass that created it.

image::storage-stateful/storage-stateful-02-storageclass.png["The StorageClass detail page for ocs-external-storagecluster-ceph-rbd: the left column gives the name, annotations, and the provisioner openshift-storage.rbd.csi.ceph.com; the right column gives Reclaim policy Delete, Default class True, and Volume binding mode WaitForFirstConsumer."]

*Why it matters*

Nobody filed a storage request. The platform team publishes the classes — which backend, which access modes, whether volumes can grow, what happens when the claim is deleted — and application teams claim against them. That contract is what makes storage a platform service rather than a project.

[source,sh,role=execute,subs="attributes+"]
----
oc -n {user}-dev get pvc claims-db-data
PV=$(oc -n {user}-dev get pvc claims-db-data -o jsonpath='{.spec.volumeName}')
oc get pv "$PV" -o custom-columns='NAME:.metadata.name,CAPACITY:.spec.capacity.storage,RECLAIM:.spec.persistentVolumeReclaimPolicy,DRIVER:.spec.csi.driver'
oc get storageclass
----

*What just happened*

A claim, a real volume created on demand behind it, and the class that did the work — dynamic provisioning, end to end.

== Frequently asked questions

*My PVC says `Pending` and nothing is happening — is it broken?*::
Almost always no: the default class uses `WaitForFirstConsumer`, so it deliberately waits to provision the volume until a Pod that mounts the claim is scheduled, and the disk then lands near that Pod. `oc describe pvc <name>` shows the event. A claim with no consuming Pod sits `Pending` by design.

*Why did killing the database Pod return an error rather than an empty list?*::
Because the schema — the `claim` table itself — was created inside the ephemeral volume the first time the application connected, and it died with the Pod. The application is configured to reuse an existing schema rather than wipe and recreate one on boot, so against a brand-new empty database it fails instead of quietly rebuilding the table. The whole database was in ephemeral storage, not just the rows.

*Two replicas of PostgreSQL — is that a highly available database?*::
No. A StatefulSet gives each Pod a stable identity and its own volume; it does not replicate data between them, so two replicas are two independent PostgreSQL instances with separate storage. Replication, failover, and backups are the job of a database Operator or a managed service. The StatefulSet is the plumbing underneath one, not a database strategy by itself.

*If the workload is deleted, does the data go with it?*::
No, and that surprises people in both directions. Deleting a StatefulSet leaves the claims from its `volumeClaimTemplate` bound and still holding data, so a workload can be deleted and recreated without loss — and orphaned claims quietly accumulate cost when nobody cleans them up. Deleting the claim is what releases the volume, and on a class whose reclaim policy is `Delete`, the storage goes too.

.Why no StorageClass says "ReadWriteMany"
[%collapsible]
====
Your list may include more classes besides these two, and a different storage backend will name and shape its classes differently — some offer no RWX-capable class at all. Read your own `oc get sc` output above rather than assuming these exact names; the commands below use this cluster's names.

A StorageClass object has no field that says "this supports ReadWriteMany".
Run `oc get sc <name> -o yaml` on any class here and you'll see the provisioner, reclaim policy, binding mode and expansion flag — never a list of access modes.
Whether RWX works is a property of the *provisioner* underneath the class (a file-backed CSI driver such as CephFS, NFS, EFS, Azure Files or Filestore — or not), so the only reliable way to know is to read the provisioner name yourself or ask your platform team.
====

Guess a candidate from provisioner names (this only sets a shell variable):

[source,sh,role=execute,subs="attributes+"]
----
RWX_CLASS=$(oc get sc -o jsonpath='{range .items[*]}{.metadata.name} {.provisioner}{"\n"}\{end}' \
  | grep -Ei 'cephfs|efs|azure-?file|filestore|nfs|glusterfs|manila' | awk '{print $1}' | head -1)
echo "candidate RWX-capable class: ${RWX_CLASS:-<none found by name>}"
----

.A naming guess, not an API guarantee
[%collapsible]
====
That `grep` only pattern-matches common file-storage provisioner names — it can miss a real RWX class with an unusual name, or, rarely, match one whose driver doesn't actually support it.
Confirm with your platform team or storage vendor's docs before relying on this outside a lab.
On *this* cluster it lands on `ocs-external-storagecluster-cephfs` (the CephFS provisioner) — that is this cluster's worked example, not a name to expect elsewhere.
If your own cluster genuinely has no RWX-capable class — common on cloud block-only storage — that is a normal, supported answer: skip the probe below, and keep the lesson — RWX is provisioner-dependent, and you find out by asking, not by reading the StorageClass object.
====

Prove the candidate with a throwaway RWX claim; with no candidate, this is a deliberate no-op:

[source,sh,role=execute,subs="attributes+"]
----
if [ -n "${RWX_CLASS?is unset - run the candidate-class block above again}" ]; then
  oc -n {user}-dev create -f - <<EOF
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: rwx-probe
spec:
  accessModes: [ReadWriteMany]
  storageClassName: $RWX_CLASS
  resources:
    requests:
      storage: 1Gi
EOF
  sleep 5
  oc -n {user}-dev get pvc rwx-probe -o custom-columns='NAME:.metadata.name,STATUS:.status.phase,MODE:.spec.accessModes[0]'
  oc -n {user}-dev delete pvc rwx-probe
else
  echo "No RWX-capable class detected by name on this cluster — skipping the probe."
  echo "Lesson: access modes are a property of the provisioner, not something the StorageClass API advertises; you would ask your platform team which class, if any, supports ReadWriteMany."
fi
----

*What just happened:* a candidate's probe binds as `ReadWriteMany`, then is deleted; with none, the message is the lesson: RWX detection comes from outside the StorageClass object.

.Why access modes depend on your cluster
[%collapsible]

Access modes are a property of the storage backend, not something every cluster offers equally.

== 7. Stage a partitioned update
⏱ *~5 min* · roll the update to one member first, verify, then finish

Parasol wants every database change proven on one member before it reaches the other: a canary, built into the StatefulSet.

*You'll end with:* `pg-sts-1` on a new revision while `pg-sts-0` waits on the old one, then both updated.

[mermaid]
....
include::example$diagrams/storage-stateful/09-partitioned-update.mmd[]
....

Set `rollingUpdate.partition` to `1`, so only Pods with ordinal *≥ 1* (`pg-sts-1`) take the next change:

[source,sh,role=execute,subs="attributes+"]
----
oc -n {user}-dev patch statefulset pg-sts --type=merge \
  -p '{"spec":{"updateStrategy":{"type":"RollingUpdate","rollingUpdate":{"partition":1}}}}'
----

Change the Pod template; a marker environment variable stands in for "a new image tag":

[source,sh,role=execute,subs="attributes+"]
----
oc -n {user}-dev set env statefulset/pg-sts ROLLOUT=canary
oc -n {user}-dev rollout status statefulset/pg-sts
----

Check which Pods changed:

[source,sh,role=execute,subs="attributes+"]
----
oc -n {user}-dev get pods -l app=pg-sts -L controller-revision-hash
r0=$(oc -n {user}-dev get pod pg-sts-0 -o jsonpath='{.spec.containers[0].env[?(@.name=="ROLLOUT")].value}')
r1=$(oc -n {user}-dev get pod pg-sts-1 -o jsonpath='{.spec.containers[0].env[?(@.name=="ROLLOUT")].value}')
echo "pg-sts-0 ROLLOUT: ${r0:-(unset)}"
echo "pg-sts-1 ROLLOUT: ${r1:-(unset)}"
----

.Expected output
[source,texinfo]
----
NAME       READY   STATUS    AGE   CONTROLLER-REVISION-HASH
pg-sts-0   1/1     Running   79s   pg-sts-bdfb69cdb          <- unchanged (ordinal 0 < partition 1)
pg-sts-1   1/1     Running   17s   pg-sts-5f58d47b5d         <- rolled to the new revision
pg-sts-0 ROLLOUT: (unset)
pg-sts-1 ROLLOUT: canary
----

*What just happened:* only `pg-sts-1` took the change; `pg-sts-0`, below the partition, stayed on the old revision.
A bad image would hit one member, and reverting the change rolls it back.

Satisfied? Finish by dropping the partition to `0`:

[source,sh,role=execute,subs="attributes+"]
----

  -p '{"spec":{"updateStrategy":{"rollingUpdate":{"partition":0}}}}'

----

Now `pg-sts-0` rolls too, and both Pods are on the new revision.

== Challenge (optional)
⏱ *~10 min* · no hand-holding

You have the mechanics.
Try these on your own:

* *Scale the StatefulSet to 3* with `oc scale statefulset/pg-sts --replicas=3`, then back to 2. What happens to `data-pg-sts-2`?
* *Feel the reclaim policy:* `oc delete statefulset pg-sts`, then `oc get pvc -l app=pg-sts`; then run the exercise 6 block again.
* *Break a mount path:* point the claims database's `data` volume at `/var/lib/postgresql/data` (the community PostgreSQL image's path) with exercise 3's `oc set volume ... --overwrite --name data` and a different `--mount-path`; then put it back.

.What you should see
[%collapsible]
====
* *Scale to 3:* `pg-sts-2` and `data-pg-sts-2` appear, and `data-pg-sts-2` *survives* the scale-down to 2 (StatefulSet PVCs are never auto-deleted).
* *Reclaim policy:* after deleting the StatefulSet, the PVCs are still there.
That leaked storage is exactly why `ws reset {module-id}` purges PVCs explicitly.
Run the exercise 6 block again and `pg-sts-0` and `pg-sts-1` come back on the very same PVCs, with the `schema_history` row from exercise 8 still in `pg-sts-0`.
* *Mount path:* the PVC stays `Bound`, yet the claims API fails: the database initialized an *empty* data directory on the container's own filesystem, and your volume sits unused.
Put the path back, and your claims return without an app restart; they never left the volume.
The troubleshooting page shows how to spot this.
====

When you are done, run `ws verify {module-id}` in the Terminal; every check passes once the StatefulSet is back at two replicas and the database is on its proper path.
Or run `ws prep {module-id} --yes` to return to a fresh (ephemeral) claims app and start over.
