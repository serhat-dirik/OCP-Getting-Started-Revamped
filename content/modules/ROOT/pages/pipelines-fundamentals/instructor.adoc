This module has one dominant pacing fact: *the first pipeline run is long* — Maven downloads the dependency tree twice, once for the test and once inside the image build.
Plan the room around the first run: start exercise 1, then send attendees into exercise 2 (the task library) while it builds — the module is *designed* so the reading fills the wait.

[WARNING]
.The "later runs are half the time" advice was wrong until 2026-08-07 — re-measure before you quote a number
====
Every timing on this page below the first run was measured on a pipeline that *had no cache at all*.
The `maven-jdk21` Task kept Maven's local repository inside the TaskRun container, so it died with the Pod and every run re-downloaded everything.
The proof is two *consecutive* runs measured 2026-08-06 whose `unit-test` took *11m20s* and *11m33s* — near-identical, because nothing was ever warming.
The same session measured a full green run at *20m49s* and a red run at *12m08s*, against the *2m47s* this guide claims for a red run below.

A persistent `maven-cache` workspace landed 2026-08-07 (a per-user PVC, bound by every run in the module).
It changes the numbers in your favour, and *nobody has timed a cached run yet* — so no figure for one appears on this page.
Time your own dry run and treat the table below as the uncached ceiling until it is replaced.
====
The single most memorable beat is exercise 3: a one-line change turns the pipeline red at the test and the build never runs.

== Timing

Attendee hands-on: *~40 min* (add ~12–15 min of concept up front).
*Budget ~60–70 min of wall clock*, and schedule the module on that, not on the 40.

The gap is not slack — it is the pipeline, and it is measured, not estimated. Exercise 1's run alone
was *20m49s*, exercise 3's red run *12m08s* and its green re-run *~10m*: **~43 min in three runs**,
before exercise 4 starts. A room asked to sit through that with a "40 min" label on the door will
read the module as broken when it is merely slow. The `maven-cache` workspace (2026-08-07) removes
one of each green run's two Maven downloads, so these numbers are the *ceiling* — plan to the ceiling
and finish early.

[cols="1,4,1,2",options="header"]
|===
| # | Exercise group | Attendee time | Measured core — *uncached*, see the warning above

| 1 | Run the build-test-deploy pipeline from the console | ~10 min | started from *Actions → Start*, `Succeeded` in *~13 min* on 4.21.22 (unit-test 5m34s, build-image 6m56s, image-report 10s), and *20m49s* on the 2026-08-06 cluster — then `deploy` rolls out the app *and creates its edge Route*; image within the 500 MB budget
| 2 | Explore the company task library | ~10 min | read-only (`oc get`/`jsonpath`) — seconds; done *during* the exercise-1 build
| 3 | Break the build (failing test) | ~10 min | RED run fails at unit-test (build/report/deploy SKIPPED) — *2m47s* on 4.21.22 but *12m08s* on the 2026-08-06 cluster; GREEN re-run *7m0s* on 4.21.22, *10m10s* on 4.22.5 (2026-07-26) — no 2026-08-06 green re-run was timed
| 4 | Pipelines-as-Code (git push) | ~10 min | webhook setup ~5 min; the PaC-fired run is just another run of the same pipeline, and appears *within ~5 s* of the push

[NOTE]
.How this timing was measured — and what it is worth
====
The *Measured core* column is real, and it is *two* clusters: OCP 4.21.22 / OpenShift Pipelines 1.22.4 (2026-07-10, `user2`, started from the console *Actions → Start* form against the 2&nbsp;Gi `-cicd` namespace default with no `taskRunSpecs`) and the 2026-08-06 re-measurement.
Where they disagree, both numbers are printed. The spread *is* the finding: with nothing cached, a run's length is a property of how fast that cluster can pull from Maven Central, and it moved a red run from 2m47s to 12m08s.

* *First run (exercise 1)* — Maven downloads its dependency tree *twice*: once in `unit-test`, once inside the image build's `Containerfile`.
That is nearly the whole cost; the actual work (compile, image assembly, deploy + Route) is well under a minute of it.
* *Later runs* — the `maven-cache` workspace (new, 2026-08-07) means `unit-test` reuses what the previous run downloaded.
The image build still runs its own `mvn` inside the `Containerfile` and does *not* see that cache, so a green run does not become short — it loses one of its two downloads.
*No cached run has been timed.*
* *A failing test fails fast in Task terms, not in wall-clock terms* — the RED break-fix run *fails at `unit-test`* and the three downstream Tasks (`build-image`, `image-report`, `deploy`) are *Skipped*, so it costs one Maven download rather than two.
Uncached, that was still 12m08s on the 2026-08-06 cluster.
* *PaC latency* — a pushed run appears *within a few seconds*; its duration is just a normal run.
====

== Pre-flight checklist

Run these *before the session* (as cluster admin unless noted).

. *A sample user's entry state materializes and verifies.*
+
[source,sh,role=execute]
----
ws start pipelines-fundamentals --user user1
ws verify pipelines-fundamentals --user user1 --entry-only
----
+
Expect the `✅ all N checks passed` banner with no ❌: the `user1-cicd` namespace + entry marker, `claims-db` ready, the `parasol-claims-build-test-deploy` Pipeline, the `maven-cache` claim, the Gitea fork, its Ex3 break-fix target, its seeded `.tekton/pull-request.yaml`, and the curated `parasol-tasks` library reachable.
// The count deliberately reads N, not a literal. It was written as "8" and had already drifted
// (the script asserts more than that today, and gained the maven-cache check on 2026-08-07); a
// number here rots on every added check and tells the reader to distrust a correct green run.

. *The curated library exists and its Tasks are readable.*
+
[source,sh,role=execute]
----
oc get tasks.tekton.dev -n ogsr-parasol-tasks
----
+
Expect `image-size-report` and `maven-jdk21` among them (the library has grown — sibling modules seed their own curated Tasks, so the list is longer than two; fully qualify `tasks.tekton.dev` so a full-catalog cluster's migration-toolkit `tasks` resource can't shadow the Tekton one).
If the namespace is missing, the workshop-config Argo app has not synced — re-sync it (the library is workshop-layer, not per-user).

. *The `maven` gap the lab teaches is real on this cluster.*
+
[source,sh,role=execute]
----
oc get tasks.tekton.dev maven -n openshift-pipelines -o jsonpath='shipped maven build image: {.spec.steps[1].image}{"\n"}'
----
+
Expect a `…/ubi9/openjdk-17…` image.
Exercise 2's whole point is that this build step is Java 17 and cannot build the Java 21 app. Current Pipelines ships a `JAVA_VERSION` param on the `maven` Task (default 11), but it does *not* repoint this pinned image — so the gap holds; the lab reframes the motivation as a guaranteed Java 21 runtime, not a missing knob. If a future operator makes `JAVA_VERSION` actually swap the build image to a Java 21 runner, revisit the framing.

. *The Pipelines-as-Code controller is up and reachable at the predictable URL.*
+
[source,sh,role=execute]
----
oc get pods -n openshift-pipelines | grep pipelines-as-code-controller
echo "webhook target: https://pipelines-as-code-controller-openshift-pipelines.$(oc get ingresses.config cluster -o jsonpath='{.spec.domain}')"
----
+
Expect the controller Pod `Running`.
Attendees *cannot* read the route themselves (it is in `openshift-pipelines`), so the lab has them build the URL from `{cluster_domain}` — confirm that host resolves.

. *The build namespace is sized for the console Start form.*
+
[source,sh,role=execute]
----
oc get limitrange workshop-limits -n user1-cicd -o jsonpath='cicd default mem limit: {.spec.limits[0].default.memory}{"\n"}'
----
+
Expect `2Gi`.
This raised default is what lets attendees start the pipeline from the console *Actions → Start* form — which cannot set per-task memory — without an OOMKill, so no PipelineRun carries `taskRunSpecs`.
If it reads `1Gi`, the `gitops/workshop-config` `per-user-limits` change has not synced; re-sync the workshop-config Argo app before the session, or the Start-form runs OOM at `unit-test`.

. *The per-user Maven cache claim exists.*
+
[source,sh,role=execute]
----
oc get pvc maven-cache -n user1-cicd
----
+
Expect the claim to exist. `Pending` is correct and healthy before anyone runs a pipeline — the default StorageClass binds on first use.
`NotFound` means the entry app has not synced the new template; re-run `ws start pipelines-fundamentals --user user1`.
Every PipelineRun in this module attaches this claim *by name*, so without it a run's Task Pod sits `Pending` instead of building.
+
[WARNING]
.Order of operations on a cluster that has not been updated yet
=====
The `maven-cache` workspace is declared on the *library* Task `maven-jdk21` (shipped by the `workshop-config` Argo app) and mapped by the *per-user* Pipeline (shipped by the entry app).
Sync `workshop-config` *first*.
If a per-user entry state maps the workspace while the library still serves the old Task, the run fails with `workspace binding "maven-cache" does not match any declared workspace` — it does not fall back to uncached.
Confirm the library is current before the room:
[source,sh,role=execute]
----
oc get tasks.tekton.dev maven-jdk21 -n ogsr-parasol-tasks \
  -o jsonpath='library task workspaces: {.spec.workspaces[*].name}{"\n"}'
----
Expect `source maven-cache`.
=====

. *Pre-warm the Maven cache (recommended — and it now actually works).*
Run one full pipeline on a sample user before the room.
This fills that user's `maven-cache` claim, so their `unit-test` no longer downloads the dependency tree.
+
[source,sh,role=execute]
----
ws solve pipelines-fundamentals --user user1     # runs the real pipeline to completion; BLOCKS by design
----
+
[IMPORTANT]
.Pre-warming is *per user*, not per node
=====
The cache is a PersistentVolumeClaim in `{user}-cicd`.
Solving `user1` warms `user1` and nobody else — the old advice ("pre-warm the nodes and the first-run pain largely disappears") was wrong twice over: there was no cache to warm at all, and the thing that would have needed warming is per-user, not per-node.
To warm a whole room you have to solve every user, which costs one full pipeline run each — decide whether that is worth the cluster time, or accept that every attendee's *first* run is the slow one and use exercise 2 to fill the wait, which is what the module is designed for.
=====
+
[IMPORTANT]
.`ws solve pipelines-fundamentals` blocks for the length of a whole pipeline run — that is correct, not a hang
=====
`ws solve` runs the actual build-test-deploy pipeline and *waits for it to finish* before returning (the engine gates on the Argo sync operation, sized by the module's `waitSeconds: 1200`).
*Measured 2026-07-10:* `7m45s` end-to-end (the solve Job's own pipeline ran 7m15s), and it was *truthful on return* — the `parasol-claims` deploy was `1/1`, pod Running, `0` restarts against `claims-db`.
That was an *uncached* run, like every solve measured so far; the 2026-08-06 cluster took *20m49s* for the same pipeline.
Budget for the worst of those until someone times a solve against a warm `maven-cache`.
It prints "demo-ready" *only when the app is truly up*; earlier engine versions printed ready ~7 min early, and that was fixed for this module.
Do not Ctrl-C it thinking it stalled.
=====

. *`ws smoke` passes for a sample attendee — the only pre-flight check that runs as the attendee, in the real cockpit terminal.*
+
[source,sh,role=execute]
----
ws smoke pipelines-fundamentals user1
----
+
Every module declares `smokeCommands` in `ws-meta.yaml`; unlike the checks above (run from an admin context), `ws smoke` execs into the attendee's own Showroom terminal as `user1` and proves the representative commands work under their real identity, PATH, and namespace isolation — not just that the objects exist.

[NOTE]
.What "done" looks like
====
You do not need a separate rubric for when the room is ready to move on: each exercise in the lab ends on its own ✔ *Verify:* line, which is the per-exercise move-on signal — when an attendee's output matches it, that exercise is done. For a whole-module self-check, attendees can run `ws verify pipelines-fundamentals` themselves at any point in the Showroom terminal; it is the same script pre-flight step 1 above runs for you (with `--entry-only`).

== Demo-mode notes

Beyond the Say/Show/Do arc in the demo flavor:

* *Pre-solve, and pre-wire the webhook, before the room.*
Run `ws solve pipelines-fundamentals --user {user}` early (it blocks for a full pipeline run) so a finished, healthy `parasol-claims` is your opening visual — and, since 2026-08-07, so *your own* `maven-cache` claim is filled before you present.
The demo's live beats (3–4) are a *PaC push*, so you also need the webhook set up on your fork *before* you present — do lab exercise 4's setup (create the Gitea token, the `gitea-pac-secret`, and the webhook) ahead of time.
Rehearse the one-line test edit once.
* *Talk through the build, never at it.*
A run is minutes long even with the cache filled — the image build does its own `mvn package` inside the `Containerfile` and cannot see the cache, and nobody has timed that shape yet.
Start the push, then narrate the task-library story (the Java 17 vs 21 gap) while it builds — do not watch a progress bar.
* *The red-then-green is the whole demo.*
Beat 3 (push a broken test → pipeline goes red at `unit-test`, build never runs) and beat 4 (revert → push → green → deployed) are the payoff.
The line that lands: "a failing test *stopped* the deploy — the pipeline refused to ship the bug."
* *Have a fallback.*
If a live push is slow or a webhook hiccups, show the pre-solved run's `tkn pipelinerun describe --last` (the five Tasks + the `image-within-budget` result) and narrate from there.

== Top questions attendees ask

*1. "Why did my first run take 12 minutes when the demo said pipelines are fast?"*::
Almost all of it is Maven downloading the dependency tree — *twice*, once for the test Task and once inside the image build.
On a cold node that is ~9–11 minutes of the ~13; the second run on the same node is ~7 because the artifacts are cached.
In a real setup you would add a persistent Maven cache (a shared workspace or a mirror) to pay that cost once.
It is not the pipeline machinery that is slow — it is a first-time dependency download, and it is the honest cost of building from source.

*2. "Why curate a `maven-jdk21` Task when OpenShift ships a `maven` Task?"*::
Because the shipped one cannot build this app.
Its build step is pinned to a Java 17 runner image; the `JAVA_VERSION` param it now exposes (default 11) does not repoint that image, so a Java 21 app still fails with `release version 21 not supported`.
Rather than every team patch their own copy, the platform team publishes one correct Task into a shared library and everyone references it by cluster resolver.
That single, concrete gap *is* the argument for an organization library — fix it once, everyone inherits the fix.

*3. "Where did `ClusterTask` go? My old pipeline used them."*::
`ClusterTask` was removed from OpenShift Pipelines; this cluster runs {pipelines_version}, so it does not exist.
The *cluster resolver* replaces it — `taskRef: {resolver: cluster, params: [name, namespace, kind]}` — and it is better: Tasks live in ordinary namespaces with ordinary RBAC, and you reference the exact one you want.
Any tutorial telling you to create a `ClusterTask` is out of date.

*4. "The failing test stopped the whole pipeline — is that configurable?"*::
Yes, and stopping is the default and usually what you want: `build-image` has `runAfter: unit-test`, so a failed test means the build (and everything after) is *skipped*.
That is the gate — a broken change cannot become a deployed image.
If you ever want a Task to run *despite* an earlier failure (say, always publish a test report), Tekton has `finally` tasks for exactly that; the default dependency chain is a hard gate on purpose.

*5. "Is deploying straight from the pipeline how we go to production?"*::
No — and the lab says so.
Here the pipeline deploys into its own `-cicd` namespace to keep the module self-contained.
In practice the pipeline's job ends at *building and publishing a trustworthy image*; promoting that image across dev/stage/prod is GitOps' job (a later module), where Argo CD reconciles the image into each environment from Git.
Pushing an image straight from CI into prod is the anti-pattern GitOps exists to replace.

== Watchouts

* *Two Maven downloads per run — the cache removes ONE of them.*
`unit-test` (`mvn test`) and `build-image` (the `mvn package` inside the `Containerfile`) each resolve dependencies.
The `maven-cache` workspace covers `unit-test` only: `build-image` runs Maven inside a buildah build, which has no access to a Tekton workspace, so it re-downloads on every run no matter what.
Expect the module's floor to be "one Maven download", not "no Maven download" — and re-measure rather than quoting a number for it.
Pre-warm with a `ws solve` on the user you will demo as; it warms that user only.
Never let the room sit watching the first build — that is what exercise 2 is for.
* *`ws reset` purges PipelineRuns.*
`ws reset pipelines-fundamentals` deletes `pipelineruns.tekton.dev` (and the deployed app) as well as the usual workloads — a plain `oc delete all` does *not* touch Tekton CRs, so the reset was extended for this module.
Attendees who reset start with a clean run list; that is intended.
* *The break-fix claim number is dynamic — never quote a fixed one.*
The failing test's message reads "claim `CLM-XXXX` was Approved while still Unassigned"; the number is *assigned at test time* from the test database's claim-number sequence, which the sibling tests in the same class also draw from, so it differs run to run.
On the measured run it was `CLM-1032`; on the next it will not be.
The lab says "your claim number" — keep it that way.
* *The PaC webhook is per-fork, and one-time.*
Each attendee wires a webhook on *their own* fork; there is no shared webhook.
If PaC does not fire, check three things in order: the webhook exists and is *active* in Gitea (Settings → Webhooks → *Recent Deliveries* shows the POST and its response), the `gitea-pac-secret` Secret exists with both keys (`token`, `webhook-secret`), and the webhook's secret *matches* the Secret's `webhook-secret`.
* *The `Repository` CR must keep its `git_provider` — and the `.tekton` uses a cluster resolver.*
Two things the entry state now ships (both were on-cluster failures during the build): the `Repository` carries `git_provider` (a bare `url` makes PaC reject the webhook with "failed to find git_provider details"), and `.tekton/pull-request.yaml` resolves the Pipeline with `resolver: cluster` (a name-only `pipelineRef` fails with "cannot find referenced pipeline").
If you hand-edit the `Repository` and drop `git_provider`, PaC breaks — re-apply the entry state.
* *Memory: the build namespace is sized, not the PipelineRun.*
The `{user}-cicd` namespace default container limit is raised to 2&nbsp;Gi (`gitops/workshop-config/templates/per-user-limits.yaml`) — that is what lets attendees start the pipeline from the console *Actions → Start* form (which cannot set per-task memory) without an OOMKill, so *no PipelineRun carries `taskRunSpecs` any more*.
If a build dies mid-`mvn` with `OOMKilled`, the cause is a run that *lowered* a Task's memory, or a run in a namespace that is not build-sized.
* *The pipeline creates the Route — attendees never `oc expose`.*
The `deploy` step now creates the Service and an edge-terminated Route itself, so exercise 1 has attendees *read* the Route and call the app, not create it.
If a Route is missing after a green run, the `deploy` step did not reach its `oc create route edge` line — read that step's logs.
* *Break-fix depends on the fork carrying the test.*
The break-fix test (`approvingAClaimRequiresAnAssignedAdjuster`) must be present in the attendee's fork of `parasol-claims`.
It is in the monorepo's `apps/parasol-claims`; confirm the shared `parasol/parasol-claims` seed repo (which forks are taken from) carries it before an event — `curl -s <gitea>/parasol/parasol-claims/raw/branch/main/src/test/java/com/parasol/claims/ClaimResourceTest.java | grep -c '@Test'` should report `14`.

== Provenance

Pipelines Fundamentals is built fresh on OpenShift Pipelines 1.22.4 (`tekton.dev/v1`, Pipelines-as-Code) and performed end-to-end on OpenShift 4.21.22.
The console-first rework was *re-grounded on `user2`*: a plain run with no `taskRunSpecs` (the console *Actions → Start* path) OOMKilled at `unit-test` under the old 1&nbsp;Gi namespace default, then `Succeeded` through `build-image` and `image-report` under the 2&nbsp;Gi `-cicd` default now shipped in `per-user-limits.yaml` — unit-test 5m34s, build-image 6m56s, image-report 10s, `image-within-budget: true`.
The `deploy` step creates the app's Service and edge Route itself (no hand `oc expose`), mirroring the Application Security Testing capstone.
The break-fix (`Parasol rule violated`, downstream Tasks Skipped) and the PaC git-push flow are the same pipeline as the original grounding.
