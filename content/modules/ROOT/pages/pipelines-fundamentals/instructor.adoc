// Internal delivery runbook. First built on OCP 4.21.22 / OpenShift Pipelines 1.22.4 (2026-07-10);
// the Timing section was re-measured end to end on 2026-11-12 (see the comment there).

This module's pacing is set by four pipeline runs, each about *2–4 minutes*.
Maven resolves the dependency tree twice per run, once for the test and once inside the image build, and since 2026-11-12 both resolve from the in-cluster Maven mirror (`ogsr-maven-mirror`, warmed at install), so the cluster's internet egress no longer sets the run length: on cluster-5vqxc a full run went from *4m02s* to *3m32s* (`unit-test` Maven 95 s → 83 s, the `Containerfile` Maven 49 s → 36 s). The rest is Quarkus compile and the test suite, which a mirror cannot shorten.
Attendees who finish reading early can start exercise 2 (the task library) while exercise 1's run builds.

[WARNING]
.There is no "later runs are half the time" — settled by measurement 2026-08-08
====
Every run of this pipeline is uncached, and that is now a decision rather than an omission.
Do not tell a room that the second run will be quick.

The reasoning that suggested otherwise: two *consecutive* runs measured 2026-08-06 timed `unit-test` at *11m20s* and *11m33s* — near-identical, which was read as "nothing is warming".
A persistent `maven-cache` workspace was added 2026-08-07 to fix it.
It failed twice over, and both are measured on OCP 4.22.8 / OpenShift Pipelines 1.23.1:

* *It could not run.* Binding both `shared-workspace` and `maven-cache` gives `unit-test` two PVC-backed workspaces, and Tekton's Affinity Assistant permits one in its default `coschedule=workspaces` mode. Every run failed in about *27 seconds* with `TaskRunValidationFailed` / `[User error] more than one PersistentVolumeClaim is bound` — before a step started, so with no logs to read.
* *It was not worth the workaround.* With the cluster's Affinity Assistant switched to `coschedule=pipelineruns` (which lifts the cap), three real runs on 2026-08-08 gave *cold cache 13m26s*, *warm cache 11m10s*, *no cache 11m18s*. A warm cache saved eight seconds; the cold run — the one an attendee actually pays, since the claim starts empty — cost two minutes more than no cache at all.

The workspace, its PVC and its binder Job were removed on 2026-08-08.
The dependency download was never the expensive part: Quarkus compile and a 30-test suite are.
Every figure below is therefore the shipped shape. Before the mirror, runs spread from 10 to 21 minutes across clusters, and that spread was egress speed, not caching.
====
The single most memorable beat is exercise 3: a one-line change turns the pipeline red at the test and the build never runs.

[NOTE]
.What the time goes into
====
* *Every run* resolves Maven dependencies *twice*: once in `unit-test`, once inside the image build's `Containerfile`. Both come from the in-cluster mirror, so compile and the 33-test suite are most of a run.
* *Later runs cost the same as the first.* This was tested rather than assumed: with a genuinely warm Maven repository the same pipeline finished in *11m10s* against *11m18s* with none (2026-08-08, before the mirror).
* *A failing test fails fast in Task terms*: the RED run stops at `unit-test` and the three downstream Tasks are *Skipped*, so it costs one Maven resolution rather than two.
* *PaC latency*: a pushed run appears *within a few seconds*; its duration is just a normal run.
====

== Pre-flight checklist

Run these *before the session* (as cluster admin unless noted).

. *A sample user's entry state materializes and verifies.*
+
[source,sh,role=execute]
----
adm start pipelines-fundamentals --user user1
ws verify pipelines-fundamentals --user user1 --entry-only
----
+
Expect the `✅ all N checks passed` banner with no ❌: the `user1-cicd` namespace + entry marker, `claims-db` ready, the `parasol-claims-build-test-deploy` Pipeline, *every task of that Pipeline admissible*, the Gitea fork, its Ex3 break-fix target, its seeded `.tekton/pull-request.yaml`, and the curated `ogsr-parasol-tasks` library reachable.
The admissibility check is the one worth knowing about: it reads the Pipeline's workspace bindings against this cluster's Affinity Assistant mode and fails if any task would be rejected at run time.
It exists because for one day in August 2026 every check on this list passed over a Pipeline that could not run at all.
// The count deliberately reads N, not a literal. It was written as "8" and had already drifted;
// a number here rots on every added check and tells the reader to distrust a correct green run.

. *The curated library exists and its Tasks are readable.*
+
[source,sh,role=execute]
----
oc get tasks.tekton.dev -n ogsr-parasol-tasks
----
+
Expect `image-size-report` and `maven-jdk21` among them (the library has grown — sibling modules seed their own curated Tasks, so the list is longer than two; fully qualify `tasks.tekton.dev` so a full-catalog cluster's migration-toolkit `tasks` resource can't shadow the Tekton one).
If the namespace is missing, the workshop-config Argo app has not synced — re-sync it (the library is workshop-layer, not per-user).

. *The `maven` gap the lab teaches is real on this cluster.*
+
[source,sh,role=execute]
----
oc get tasks.tekton.dev maven -n openshift-pipelines -o jsonpath='shipped maven build image: {.spec.steps[1].image}{"\n"}'
----
+
Expect a `…/ubi9/openjdk-17…` image.
Exercise 2's whole point is that this build step is Java 17 and cannot build the Java 21 app. Current Pipelines ships a `JAVA_VERSION` param on the `maven` Task (default 11), but it does *not* repoint this pinned image — so the gap holds; the lab reframes the motivation as a guaranteed Java 21 runtime, not a missing knob. If a future operator makes `JAVA_VERSION` actually swap the build image to a Java 21 runner, revisit the framing.

. *The Pipelines-as-Code controller is up and reachable at the predictable URL.*
+
[source,sh,role=execute]
----
oc get pods -n openshift-pipelines | grep pipelines-as-code-controller
echo "webhook target: https://pipelines-as-code-controller-openshift-pipelines.$(oc get ingresses.config cluster -o jsonpath='{.spec.domain}')"
----
+
Expect the controller Pod `Running`.
Attendees *cannot* read the route themselves (it is in `openshift-pipelines`), so the lab has them build the URL from `{cluster_domain}` — confirm that host resolves.

. *The build namespace is sized for the console Start form.*
+
[source,sh,role=execute]
----
oc get limitrange workshop-limits -n user1-cicd -o jsonpath='cicd default mem limit: {.spec.limits[0].default.memory}{"\n"}'
----
+
Expect `2Gi`.
This raised default is what lets attendees start the pipeline from the console *Actions → Start* form — which cannot set per-task memory — without an OOMKill, so no PipelineRun carries `taskRunSpecs`.
If it reads `1Gi`, the `gitops/workshop-config` `per-user-limits` change has not synced; re-sync the workshop-config Argo app before the session, or the Start-form runs OOM at `unit-test`.

. *The Pipeline this cluster will actually admit.*
+
[source,sh,role=execute]
----
oc get tektonconfigs.operator.tekton.dev config \
  -o jsonpath='affinity assistant mode: {.spec.pipeline.coschedule}{"\n"}'
----
+
Expect `workspaces` (the operator default) or an empty value, which means the same thing.
In that mode a TaskRun may mount exactly *one* PVC-backed workspace, and this module's Pipeline is built for it — `shared-workspace` and nothing else.
`ws verify --entry-only` grades this pairing for you; run the command above only when you want to see the cluster's own answer.
+
[NOTE]
.Why an instructor is told about a scheduling flag at all
=====
Because a mismatch here does not look like a scheduling problem.
For one day in August 2026 this module shipped a second PVC-backed workspace (a persistent Maven cache), and every run of the pipeline died at `unit-test` in 27 seconds with `[User error] more than one PersistentVolumeClaim is bound` — no step started, so no logs, and in the room it reads as a broken cluster.
If you ever see that message, the Pipeline is asking for two PVCs somewhere. This prints each task and the workspaces it binds, so the offending one names itself:
[source,sh,role=execute]
----
oc get pipelines.tekton.dev parasol-claims-build-test-deploy -n user1-cicd \
  -o jsonpath='{range .spec.tasks[*]}{.name}: {range .workspaces[*]}{.workspace} {end}{"\n"}{end}'
----
=====

. *There is nothing to pre-warm — do not plan a warm-up round.*
The old advice here was to run one pipeline first so later runs would be quick.
It is wrong, and it was tested: with a fully warm Maven repository the pipeline finished in *11m10s* against *11m18s* with none (2026-08-08, three runs, one namespace).
Every attendee's every run costs the same, and exercise 2 is designed to fill the wait.
+
`adm solve pipelines-fundamentals --user user1` is still worth running before the room — not to warm anything, but so a finished, healthy `parasol-claims` is your opening visual:
+
[source,sh,role=execute]
----
adm solve pipelines-fundamentals --user user1     # runs the real pipeline to completion; BLOCKS by design
----
+
[IMPORTANT]
.`adm solve pipelines-fundamentals` blocks for the length of a whole pipeline run — that is correct, not a hang
=====
`adm solve` runs the actual build-test-deploy pipeline and *waits for it to finish* before returning (the engine gates on the Argo sync operation, sized by the module's `waitSeconds: 1200`).
*Measured 2026-11-12:* `5m16s` end-to-end on cluster-5vqxc (the solve pipeline itself ran about 3m30s), and it was *truthful on return*: the `parasol-claims` deploy was `1/1`.
Before the in-cluster Maven mirror the same solve took 7m45s to 20m49s depending on the cluster; if it takes that long again, check the mirror (`oc get pods -n ogsr-maven-mirror`).
It prints "demo-ready" *only when the app is truly up*; earlier engine versions printed ready ~7 min early, and that was fixed for this module.
Do not Ctrl-C it thinking it stalled.
=====

. *`adm smoke` passes for a sample attendee — the only pre-flight check that runs as the attendee, in the real cockpit terminal.*
+
[source,sh,role=execute]
----
adm smoke pipelines-fundamentals user1
----
+
Every module declares `smokeCommands` in `ws-meta.yaml`; unlike the checks above (run from an admin context), `adm smoke` execs into the attendee's own Showroom terminal as `user1` and proves the representative commands work under their real identity, PATH, and namespace isolation — not just that the objects exist.

[NOTE]
.What "done" looks like
====
You do not need a separate rubric for when the room is ready to move on: each exercise in the lab ends on its own ✔ *Verify:* line, which is the per-exercise move-on signal — when an attendee's output matches it, that exercise is done. For a whole-module self-check, attendees can run `ws verify pipelines-fundamentals` themselves at any point in the Showroom terminal; it is the same script pre-flight step 1 above runs for you (with `--entry-only`).

== Demo-mode notes

Beyond the Say/Show/Do arc in the demo flavor:

* *Pre-solve, and pre-wire the webhook, before the room.*
Run `adm solve pipelines-fundamentals --user {user}` early (it blocks for a full pipeline run) so a finished, healthy `parasol-claims` is your opening visual before you present.
The demo's live beats (3–4) are a *PaC push*, so you also need the webhook set up on your fork *before* you present — do lab exercise 4's setup (create the Gitea token, the `gitea-pac-secret`, and the webhook) ahead of time.
Rehearse the one-line test edit once.
* *Talk through the build, never at it.*
A run takes about 4 minutes (a push-fired run measured *3m32s* on 2026-11-12), most of it compile and tests.
Start the push, then narrate the task-library story (the Java 17 vs 21 gap) while it builds — do not watch a progress bar.
* *The red-then-green is the whole demo.*
Beat 3 (push a broken test → pipeline goes red at `unit-test`, build never runs) and beat 4 (revert → push → green → deployed) are the payoff.
The line that lands: "a failing test *stopped* the deploy — the pipeline refused to ship the bug."
* *Have a fallback.*
If a live push is slow or a webhook hiccups, show the pre-solved run's `tkn pipelinerun describe --last` (the five Tasks + the `image-within-budget` result) and narrate from there.

== Top questions attendees ask

*1. "Why does a run take four minutes when the demo said pipelines are fast?"*::
Maven resolves the dependency tree twice, once for the test Task and once inside the image build, and Quarkus compiles and tests the app.
The downloads come from the platform team's in-cluster Maven mirror (the `MAVEN_MIRROR_URL` param on `unit-test`, the `BUILD_ARGS` on `build-image`), so what remains is compile and test time.
The pipeline machinery adds seconds; the rest is the honest cost of building from source and proving it with tests.

*2. "Why curate a `maven-jdk21` Task when OpenShift ships a `maven` Task?"*::
Because the shipped one cannot build this app.
Its build step is pinned to a Java 17 runner image; the `JAVA_VERSION` param it now exposes (default 11) does not repoint that image, so a Java 21 app still fails with `release version 21 not supported`.
Rather than every team patch their own copy, the platform team publishes one correct Task into a shared library and everyone references it by cluster resolver.
That single, concrete gap *is* the argument for an organization library — fix it once, everyone inherits the fix.

*3. "Where did `ClusterTask` go? My old pipeline used them."*::
`ClusterTask` was removed from OpenShift Pipelines, so it does not exist on this cluster.
The *cluster resolver* replaces it — `taskRef: {resolver: cluster, params: [name, namespace, kind]}` — and it is better: Tasks live in ordinary namespaces with ordinary RBAC, and you reference the exact one you want.
Any tutorial telling you to create a `ClusterTask` is out of date.

*4. "The failing test stopped the whole pipeline — is that configurable?"*::
Yes, and stopping is the default and usually what you want: `build-image` has `runAfter: unit-test`, so a failed test means the build (and everything after) is *skipped*.
That is the gate — a broken change cannot become a deployed image.
If you ever want a Task to run *despite* an earlier failure (say, always publish a test report), Tekton has `finally` tasks for exactly that; the default dependency chain is a hard gate on purpose.

*5. "Is deploying straight from the pipeline how we go to production?"*::
No — and the lab says so.
Here the pipeline deploys into its own `-cicd` namespace to keep the module self-contained.
In practice the pipeline's job ends at *building and publishing a trustworthy image*; promoting that image across dev/stage/prod is GitOps' job (a later module), where Argo CD reconciles the image into each environment from Git.
Pushing an image straight from CI into prod is the anti-pattern GitOps exists to replace.

== Watchouts

* *Two Maven resolutions per run, both from the mirror.*
`unit-test` (`mvn test`) and `build-image` (the `mvn package` inside the `Containerfile`) each resolve dependencies, on every run; since 2026-11-12 both resolve them from the in-cluster mirror (`MAVEN_MIRROR_URL`, a param on `unit-test` and a build arg on `build-image`).
If runs suddenly take 10 minutes or more again, the mirror is the first suspect: `oc get pods -n ogsr-maven-mirror`.
* *`ws reset` purges PipelineRuns.*
`ws reset pipelines-fundamentals` deletes `pipelineruns.tekton.dev` (and the deployed app) as well as the usual workloads — a plain `oc delete all` does *not* touch Tekton CRs, so the reset was extended for this module.
Attendees who reset start with a clean run list; that is intended.
* *The break-fix claim number is dynamic — never quote a fixed one.*
The failing test's message reads "the API refused to approve claim `CLM-XXXX` while its adjuster was Unassigned … answered 409"; the number is *assigned at test time* by the service from the claim-number sequence, which the sibling tests in the same class also draw from, so it differs run to run.
On the measured run it was `CLM-2000`; on the next it will not be.
The lab says "your claim number" — keep it that way.
* *The PaC webhook is per-fork, and it outlives a reset.*
Each attendee wires a webhook on *their own* fork; there is no shared webhook.
`ws reset` and `ws prep --yes` never touch the fork's Gitea settings, so an attendee who repeats exercise 4 meets their old `pac` token (Gitea refuses the name) and their old webhook (every push delivered twice). The lab's *Doing this exercise a second time?* collapsible tells them to delete both first.
If PaC does not fire, check three things in order: the webhook exists and is *active* in Gitea (Settings → Webhooks → *Recent Deliveries* shows the POST and its response), the `gitea-pac-secret` Secret exists with both keys (`token`, `webhook-secret`), and the webhook's secret *matches* the Secret's `webhook-secret`.
* *The `Repository` CR must keep its `git_provider` — and the `.tekton` uses a cluster resolver.*
Two things the entry state now ships (both were on-cluster failures during the build): the `Repository` carries `git_provider` (a bare `url` makes PaC reject the webhook with "failed to find git_provider details"), and `.tekton/pull-request.yaml` resolves the Pipeline with `resolver: cluster` (a name-only `pipelineRef` fails with "cannot find referenced pipeline").
If you hand-edit the `Repository` and drop `git_provider`, PaC breaks — re-apply the entry state.
* *Memory: the build namespace is sized, not the PipelineRun.*
The `{user}-cicd` namespace default container limit is raised to 2&nbsp;Gi (`gitops/workshop-config/templates/per-user-limits.yaml`) — that is what lets attendees start the pipeline from the console *Actions → Start* form (which cannot set per-task memory) without an OOMKill, so *no PipelineRun carries `taskRunSpecs` any more*.
If a build dies mid-`mvn` with `OOMKilled`, the cause is a run that *lowered* a Task's memory, or a run in a namespace that is not build-sized.
* *The pipeline creates the Route — attendees never `oc expose`.*
The `deploy` step now creates the Service and an edge-terminated Route itself, so exercise 1 has attendees *read* the Route and call the app, not create it.
If a Route is missing after a green run, the `deploy` step did not reach its `oc create route edge` line — read that step's logs.
* *Break-fix depends on the fork carrying the test.*
The break-fix test (`approvingAClaimRequiresAnAssignedAdjuster`) must be present in the attendee's fork of `parasol-claims`.
It is in the monorepo's `apps/parasol-claims`; confirm the shared `parasol/parasol-claims` seed repo (which forks are taken from) carries it before an event — `curl -s <gitea>/parasol/parasol-claims/raw/branch/main/src/test/java/com/parasol/claims/ClaimResourceTest.java | grep -c approvingAClaimRequiresAnAssignedAdjuster` should report `1` (measured 2026-11-12; a count of `@Test` lines is not a stable check, it grows with the suite).

== Provenance

Pipelines Fundamentals is built fresh on OpenShift Pipelines 1.22.4 (`tekton.dev/v1`, Pipelines-as-Code) and performed end-to-end on OpenShift 4.21.22.
The console-first rework was *re-grounded on `user2`*: a plain run with no `taskRunSpecs` (the console *Actions → Start* path) OOMKilled at `unit-test` under the old 1&nbsp;Gi namespace default, then `Succeeded` through `build-image` and `image-report` under the 2&nbsp;Gi `-cicd` default now shipped in `per-user-limits.yaml` — unit-test 5m34s, build-image 6m56s, image-report 10s, `image-within-budget: true`.
The `deploy` step creates the app's Service and edge Route itself (no hand `oc expose`), mirroring the Application Security Testing capstone.
The break-fix (`Parasol rule violated`, downstream Tasks Skipped) and the PaC git-push flow are the same pipeline as the original grounding.
