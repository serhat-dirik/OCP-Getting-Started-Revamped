[.lead]
Parasol's claims service builds and ships by hand today — and every engineer does it a little differently.

You built and deployed `parasol-claims` in earlier work with single commands you typed yourself.
That is fine for one person learning the platform, but it does not scale to a team: there is no shared record of *how* the app is built and tested, no gate that a broken change has to pass, and no way to make "the build" happen the same way every time.
In this module you turn that manual sequence into a *pipeline* — a versioned, repeatable build-test-deploy that any Git push can run — and you start the *company task library* that keeps every Parasol team's pipeline consistent.

== What you'll learn

* Where a pipeline fits: *continuous integration*, *continuous delivery*, and *continuous deployment*, and which part this module builds.
* The *anatomy of a pipeline* — Steps, Tasks, and a Pipeline on the definition side; a PipelineRun, its TaskRuns, and their Pods on the run side — and the three inputs/outputs that make Tasks reusable: *parameters*, *workspaces*, and *results*.
* The three *reuse layers* — shipped catalog Tasks, a curated *organization library*, and your app's own Pipeline — and how the *cluster resolver* wires them together.
* *Why platform teams curate a task library*, shown by one concrete Task: `maven-jdk21`, which fixes the build container and Maven settings every Parasol Java service builds with.
* That *how a pipeline runs is a set of deliberate choices* — who owns it, what triggers it (every push versus a nightly schedule), and where its definition lives — and you wire one of them, *Pipelines-as-Code*, where a Git push builds the pushed commit.
* That *pipelines produce data, not just artifacts*: a Task can emit results (here, an image's size and whether it fits a budget) that surface at the run level.

== Where a pipeline fits: CI and CD

A pipeline automates the path a change takes from a commit to a running application.
Each stretch of that path has a name:

Continuous integration (CI):: Every change is built, tested, checked for security issues, and released as an image, automatically, soon after it is pushed.
A broken change is caught within minutes, while its author still has the context.
Continuous delivery:: The same change carries on to a staging environment and its acceptance tests, then stops.
The release is always ready for production; a person approves the last step.
Continuous deployment:: The same path with no manual step: a change that passes every check reaches production on its own.

Both of the last two are abbreviated *CD*, which is why "CI/CD" can mean either.

== Anatomy of a pipeline

A pipeline is not magic; it is a handful of plain Kubernetes objects, and once you see the shapes the rest follows.
They come in two halves: a *definition* that says what to run, and a *run* that does it.

The definition:

Step:: One command or script, run in a container image the Step names.
Task:: An ordered list of Steps that does one reusable job — clone a repository, run a Maven build, build an image, roll out a Deployment.
A Task declares *what it needs* and *what it produces*, so it can be reused across many pipelines without editing.
Pipeline:: An *ordered graph of Tasks*: "clone, then test, then build, then report, then deploy."
The Pipeline itself runs nothing — it is the recipe.

The run:

PipelineRun:: *One execution* of a Pipeline.
This is where the Pipeline meets reality: you hand it parameter values and a workspace, and it runs the Tasks.
Run the same Pipeline ten times and you get ten PipelineRuns.
TaskRun:: *One execution* of one Task.
A PipelineRun creates one TaskRun for each Task in the Pipeline.

// GROUNDING (2026-11-15): the two Step names are maven-jdk21's (pipelines/tasks/maven-jdk21.yaml);
// `container step-mvn-goals has failed` is tkn's own line, captured live in lab exercise 3 on
// 2026-11-12 (see the provenance comment there). The per-run PVC is the lab's volumeClaimTemplate
// binding; only fetch-source, unit-test and build-image map shared-workspace in pipeline.yaml.
Each TaskRun runs as *one Pod*, and each Step runs as *one container* in that Pod, named `step-` plus the Step's name.
The `unit-test` Task has two Steps, so its Pod has two containers: `step-generate-settings` and `step-mvn-goals`.
That is why a failing test is reported as `container step-mvn-goals has failed`.

The reason a Task is reusable — rather than a copy-pasted shell script — is three typed connection points:

Parameters:: Typed *inputs* to a Task or Pipeline (the Git URL, the image tag, a size budget).
The same Task builds *any* repository because the repository is a parameter, not a hardcoded value.
Workspaces:: *Shared storage* attached at run time — in this lab, a new PersistentVolumeClaim for each run.
Every Task runs in its own Pod, so files do not pass from one Task to the next on their own: a workspace is how they do.
The claims Pipeline clones the source into a workspace, and the test and build Tasks read that *same* checkout.
Results:: Small typed *outputs* a Task publishes (a computed image size, a "within budget" verdict, a Git commit SHA).
Results let a Task report a *fact* — and let later Tasks, or a human reading the run, act on it.

This is the whole vocabulary.
The claims Pipeline you run in the lab, `parasol-claims-build-test-deploy`, is exactly this: five Tasks in order, three of them sharing one workspace, driven by four parameters, publishing two results.

== Three reuse layers, wired by the cluster resolver

The best Tekton Task is one you *did not write*.
A build-test-deploy pipeline is mostly generic work — clone, build, roll out — that thousands of teams have already solved.
OpenShift Pipelines organizes that reuse into three layers, and your app's Pipeline pulls from all three:

[cols="2,4,2,2",options="header"]
|===
| Layer | What it is | Lives in | Maintained by

| ① *Catalog Tasks*
| Around forty ready Tasks shipped with the product: `git-clone`, `buildah`, `openshift-client`, and more
| `openshift-pipelines`
| The product; you reference them, you never maintain them

| ② *The organization library*
| The Tasks your organization standardizes on, published once so every team's pipeline references the *same* blessed version
| A shared namespace (here, `ogsr-parasol-tasks`)
| Your platform team

| ③ *Your app Pipeline*
| Composes layers ① and ② into the specific build your app needs: the one thing that is genuinely yours
| Your own namespace
| Your app team
|===

The wiring between layers is the *cluster resolver*.
Instead of copying a Task's YAML into your Pipeline, you write a reference — "the Task named `git-clone`, in the `openshift-pipelines` namespace" — and Tekton *resolves* it at run time:

[source,yaml]
----
taskRef:
  resolver: cluster        # <-- fetch a Task that already lives on this cluster
  params:
    - {name: kind, value: task}
    - {name: name, value: maven-jdk21}
    - {name: namespace, value: ogsr-parasol-tasks}
----

When a run starts, that reference becomes a running step:

[NOTE]
.The cluster resolver is the modern replacement for `ClusterTask`
====
Older Tekton had a `ClusterTask` kind — a Task installed cluster-wide.
It has since been *removed* from OpenShift Pipelines, so `ClusterTask` does not exist here.
The *cluster resolver* is its supported successor: reference any Task in any namespace you can read, by name.
If you find a tutorial that tells you to create a `ClusterTask`, it is out of date — use a resolver reference like the one above.
====

== Why a platform team curates a library: one way to build Java

The middle layer — the curated organization library — is the one people question: "if OpenShift already ships a catalog of Tasks, why maintain our own?"

The two layers answer different questions.
The catalog answers *how to do a job* — clone a repository, build an image, run Maven, roll out a Deployment — for any organization.
The library answers *how this company does it*.
The claims Pipeline uses both: three of its steps come straight from the catalog, and its Maven step comes from Parasol's library.

The Maven step is where Parasol has made its own decisions.
Its platform team has settled how every Java service builds: in one build container — Red Hat's UBI 9 OpenJDK 21 image with Maven 3.9, pinned *by digest* so two runs never compile against two different JDK builds — with a Maven settings file generated on every run to use the platform team's in-cluster repository mirror, and with the same default goals.
A general-purpose Task cannot carry one company's choices, so the platform team wrote them down once, as `maven-jdk21`, and published it into the `ogsr-parasol-tasks` library.

What that buys, compared with every team assembling its own Maven setup:

* *One reviewed definition.* "How we build Java here" is a versioned file in Git, reviewed like code, instead of a dozen slightly different copies.
* *Every team runs the same build.* Each pipeline references the Task by cluster resolver, so every Java build at Parasol runs on the same image with the same settings.
* *Upgrades happen in one place.* A patched builder image or a different mirror is one change to the library, and every pipeline that references it picks the change up on its next run; adopting a newer Java release is one new library Task that teams move to by changing a single reference.

[TIP]
.This is the whole argument for an organization library
====
A curated library is not bureaucracy — it is the fix for "every team works out the same build setup and configures it a slightly different way."
The catalog provides the general-purpose building blocks (`git-clone`, `buildah`, `openshift-client`); the library adds what is specific to your company.
The lab has you read both `maven-jdk21` and the flagship `image-size-report` Task from the `ogsr-parasol-tasks` namespace — the curated library you *use* is the same kind you will *contribute to* on a platform team.
====

== Pipelines-as-Code is one pattern, not the only way

Running a Pipeline by hand — the way you start the first run in the lab — proves it works, but someone has to remember to run it.
*Pipelines-as-Code* (PaC) is one answer: the pipeline definition lives in a `.tekton/` directory *inside the application's own Git repository*, versioned and reviewed with the code, and a *webhook* is only the trigger that tells the PaC controller a push arrived.
You wire both halves in the lab: the webhook, with a `Repository` custom resource that tells PaC which namespace to run in, and then a small pipeline you write and change in Git.

But PaC is a *choice*, and on a production platform it is often not the only one — or even one a single team gets to make alone.
Three questions decide how a pipeline actually runs, and each has more than one defensible answer:

Who owns it, and how far does it reach?::
A dev team usually owns its *CI* — build, test, and package the image.
Whether that same pipeline may *deploy* is an org-policy question, not a technical one: promotion into shared *stage* and *production* environments is frequently *not* permitted to dev teams — a separate platform or DevOps team owns that path.
So a dev pipeline often stops at "publish a trustworthy image" and hands off, while a platform team's pipeline carries it the rest of the way.
"CI only" versus "all the way to production" is a boundary someone drew on purpose.

What triggers it — every push, or a schedule?::
Firing on *every push* (what PaC does) gives the fastest feedback, but it is also the most expensive: a full build per commit spends compute a busy team may not want to.
Many teams trigger deliberately instead — a *nightly* build, a run before a release, or a run on a tag.
A scheduled nightly build is just a Kubernetes `CronJob` that starts the same Pipeline:
+
[source,yaml]
----
apiVersion: batch/v1
kind: CronJob
metadata:
  name: parasol-claims-nightly
spec:
  schedule: "0 20 * * *"          # 20:00 every day — not on every commit
  jobTemplate:
    # … container spec omitted
    command: ["oc", "create", "-f", "/runs/pipelinerun.yaml"]
----
+
Same Pipeline, a different *trigger*.

Where does the definition live?::
PaC keeps the pipeline *with the app*, in the app's own repo — a good fit when the team that writes the app also owns its CI.
But a platform or DevOps team running delivery for *many* applications often keeps its pipelines in a *separate* repository, versioned and reviewed on its own, pointed at each app.
Pipeline-in-the-app and pipeline-in-a-separate-repo are both normal; which fits depends on *who owns the pipeline*.

[NOTE]
.Not every pipeline is build-test-deploy
====
The pipeline you run here builds, tests, and ships an image — but that is not the only job pipelines do.
Plenty exist only to *tag a release and package artifacts*: cut a version, tag the commit, publish the built artifacts to a registry, with no deploy at all.
"Pipeline" means "an automated, repeatable sequence" — delivery is the most common one, not the only one.
====

The lab wires the *dev-owned, push-triggered, in-the-app-repo* corner of that space (the green path above), because it is the most hands-on way to feel a pipeline fire on its own: the `.tekton/` file is reviewed, diffed, and rolled back like any other code, and every push is built the same way with no one pressing a button.
Recognize it for what it is — one sensible default among several, chosen on purpose, not the one true way to run a pipeline.

== Pipelines produce data, not just artifacts

A pipeline's obvious output is an artifact — a container image.
But a Task can also publish *results*: small, typed facts about what it did.
Parasol's curated `image-size-report` Task inspects the freshly built image, computes its pull size, and compares it against a budget — then publishes three results (`image-size-bytes`, `image-size-mb`, `within-budget`).
The Pipeline surfaces two of them at the *run* level, so `tkn pipelinerun describe` shows something like this for the claims image (the exact size will differ on your run):

[source,texinfo]
----
📝 Results

 NAME                   VALUE
 image-size-mb          391
 image-within-budget    true
----

That is a small idea with large consequences: once a pipeline emits *data*, later steps can *branch* on it (fail a build whose image blew its budget, block a deploy on a failed scan), and humans can *audit* it.
The next module builds heavily on this — signing, attestation, and vulnerability gates are all "a Task produced a fact, and a later step enforced it."

== How this shows up in real orgs

* *"How is this service built?" has one answer, and it is in Git.*
Before a pipeline, the real build lives in someone's shell history and a wiki page that is six months stale.
After, the build-test-deploy is a reviewed file in the repository — the honest, current answer to "how do we ship this?"
* *The platform team's leverage is the library.*
The single most valuable thing a platform team ships here is not a pipeline — it is the curated Task library every pipeline reuses.
Fix a Task once (a CVE in a builder image, a new required scan) and every team inherits it.
`maven-jdk21` is a small, concrete example of that leverage: Parasol's Java build, defined once.
* *A failing test that stops the build is a feature, not a nuisance.*
The moment tests run *in the pipeline*, a broken change cannot become a deployed image — the pipeline refuses to build past a red test.
Teams that put this gate in place stop shipping the class of bug their tests already catch.
* *Push-to-build is the on-ramp to everything that follows.*
Once a Git push reliably builds, tests, and reports, you have the hook that supply-chain gates (next module) and GitOps promotion (later) attach to.
Pipelines are where "we have some automation" becomes "we have a delivery process."

[NOTE]
.Where the pipeline deploys — and where it will deploy later
====
In this module the pipeline deploys the built image into your own `{user}-cicd` namespace, right next to the pipeline, so the module stays self-contained.
That keeps the focus on *pipeline mechanics*.
Deploying straight from a build into a namespace is fine for a CI sandbox and deliberately *not* how you promote to staging or production — in later modules the pipeline hands the image off to GitOps, which reconciles it into each environment.
Notice here that the pipeline *can* deploy; the question of *where it should* is the GitOps modules' story.
====
