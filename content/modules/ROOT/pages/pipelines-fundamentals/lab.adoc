== Demo arc — Push to green, and the test that stops a bad build (13 min)

[NOTE]
.Before you present
====
Three prep steps, all *before the room*:

. Run `ws solve pipelines-fundamentals --user {user}`.
It runs the build-test-deploy pipeline to completion and leaves `parasol-claims` deployed and healthy — your destination to show.
*This blocks for ~8–10 minutes by design* (it waits for the real build), so do it early; it is truthful when it returns.
. *Wire the Pipelines-as-Code webhook on your fork.* Beats 3–4 are a live push, and without this they do nothing at all.
It is lab exercise 4's setup done ahead of time.
In Gitea: avatar → *Settings* → *Applications* → *Manage Access Tokens* → name a token `pac`, scope *write:repository*, *Generate Token*, and copy it.
Then store it alongside a webhook secret you invent:
+
[source,sh,role=execute,subs="attributes"]
----
NS={user}-cicd
read -rsp "paste your Gitea token, then press Enter: " GITEA_TOKEN; echo
----
+
[source,sh,role=execute,subs="attributes"]
----
WEBHOOK_SECRET="parasol-$(openssl rand -hex 6)"
echo "webhook secret — paste this into the Gitea form: $WEBHOOK_SECRET"
echo "target URL     — https://pipelines-as-code-controller-openshift-pipelines.{cluster_domain}"
oc delete secret gitea-pac-secret -n $NS --ignore-not-found=true
oc create secret generic gitea-pac-secret -n $NS \
  --from-literal=token="$GITEA_TOKEN" \
  --from-literal=webhook-secret="$WEBHOOK_SECRET"
----
+
Then, in your fork: *Settings* → *Webhooks* → *Add Webhook* → *Gitea*, with *Target URL* and *Secret* set to the two values just printed, *HTTP Method* `POST`, *POST Content Type* `application/json`, *Trigger On* *Push Events*, and *Active* checked.
. *Prove the webhook fires — before the room, not on stage.* Make one throwaway commit in your fork (edit `README.md` in the Gitea UI), then:
+
[source,sh,role=execute]
----
oc get repository parasol-claims -n $NS \
  -o jsonpath='provider={.spec.git_provider.type}  reads-secret={.spec.git_provider.secret.name}{"\n"}'
oc get pipelinerun -n $NS --sort-by=.metadata.creationTimestamp --no-headers \
  -o custom-columns='RUN:.metadata.name,SUCCEEDED:.status.conditions[?(@.type=="Succeeded")].status' | tail -1
----
+
*If the second line names a `parasol-claims-pull-request-…` run*, the webhook is live and beats 3–4 run exactly as written.
*If it still names the solve run*, nothing fired: read Gitea *Settings → Webhooks → Recent Deliveries* for the POST and its response code, confirm the `webhook-secret` you stored matches what you pasted into the form, and confirm the first line printed `provider=gitea` — a `Repository` that has lost `git_provider` makes Pipelines-as-Code reject the push outright.
If you cannot clear it in the time you have, present beats 3–4 from "If the webhook stays silent" below.
Do not walk in hoping.

Have your fork open at {gitea_url}/{user}/parasol-claims[{user}/parasol-claims^] and a terminal with `NS={user}-cicd` set.
The money moment is beat 3: a push turns the pipeline *red*, then beat 4 turns it *green* — rehearse the file edit once so it lands.

NS={user}-cicd

[source,sh,role=execute]
----

+
"Clone, test, build, *report*, deploy — and read the right-hand column: three of those Tasks come from the catalog OpenShift ships, two from our own library. Not one of them is code this team wrote.
The report step is the one our platform team wrote — read the number off the screen: it measured the image against a 500 MB budget and published that as a *result*. Pipelines produce data, not just images."

=== Beat 2 — Why a platform team curates its own Tasks

[demo-block]
[TIME 3m]
Say:: "Why does a platform team curate its own Tasks when OpenShift ships forty? Because the shipped Maven Task is pinned to Java 17 — and this app is Java 21. It literally cannot build it."
Show:: The Terminal — the shipped Task's image, then the curated one.
Do::
+
[source,sh,role=execute]
----
oc get tasks.tekton.dev maven -n openshift-pipelines -o jsonpath='shipped maven runs on: {.spec.steps[1].image}{"\n"}'
oc get tasks.tekton.dev maven-jdk21 -n ogsr-parasol-tasks -o jsonpath='our maven-jdk21 runs on: {.spec.steps[0].image}{"\n"}'
----
+
"Java 17 versus Java 21 — and the shipped task's `JAVA_VERSION` knob doesn't repoint that pinned Java 17 image, so it still can't build a 21 app. So we curated *one* correct Task into a shared library, and every team's pipeline references it. That library is the platform team's leverage."

=== Beat 3 — A push that should not ship, and does not

[demo-block]
[TIME 3m]
Say:: "Now watch the pipeline earn its keep. I'll push a one-line change that tries to approve a claim with no adjuster assigned — something the claims service itself refuses to do."
Show:: The Gitea web UI — edit `ClaimResourceTest.java`, flip the toggle to `false`, commit.
Then the Terminal: a one-line status check proves the push started a run, and later four grepped lines carry the verdict.
Do:: In Gitea, edit `src/test/java/com/parasol/claims/ClaimResourceTest.java`, change `assignAdjusterBeforeApproval = true` to `false`, and *Commit Changes* to `main`.
Then show that the *push* — not you — started a run:
+
[source,sh,role=execute]
----
oc get pipelinerun -n $NS --sort-by=.metadata.creationTimestamp --no-headers \
  -o custom-columns='RUN:.metadata.name,SUCCEEDED:.status.conditions[?(@.type=="Succeeded")].status' | tail -1
----
+
"A run called `parasol-claims-pull-request-…`, four seconds after the commit. Nobody pressed a button."
+
That one line is your progress bar: `SUCCEEDED` reads `Unknown` while the run works, then `False` here and `True` in beat 4.
*Never follow the log on a projector* — this run is minutes of Maven download and none of it is worth showing.
Re-run the line above between sentences while you narrate the task-library story from beat 2, and when it turns `False`, read only the verdict:
+
[source,sh,role=execute]
----
oc get taskrun -n $NS -l tekton.dev/pipelineTask=unit-test --sort-by=.metadata.creationTimestamp \
  -o name | tail -1 | cut -d/ -f2 | xargs -I{} tkn taskrun logs -n $NS {} | grep -iE "AssertionFailedError|Tests run:|FAILURE"
tkn pipelinerun describe --last -n $NS | sed -n '/Skipped Tasks/,$p'
----
+
"It's *red* at `unit-test`: the API answered *409* — 'cannot be Approved while its adjuster is Unassigned.' That's the service enforcing a business rule, and the test catching it. And look at the second output — `build-image`, `image-report` and `deploy` are *skipped*. The build never ran. A failing test *stopped* the deploy."

This first run is the slow one, and it resolves Maven's dependency tree *twice*: once in `unit-test`, and once more inside the image build, which runs its own `mvn` in the `Containerfile` and shares nothing with the Task before it.

All four are real — how fast the dependencies arrive is a property of the cluster you are on, not of anything you can set here.

== 2. Explore the company task library
⏱ *~10 min* · the three reuse layers, and why Parasol curates its own Tasks

You just saw the Pipeline reference five Tasks by cluster resolver.
This exercise looks at the two *curated* ones — and the concrete reason they exist.

[NOTE]
.Why this exercise stays in the terminal
====
The curated Tasks live in shared namespaces (`ogsr-parasol-tasks` and `openshift-pipelines`) that you can *read* but not *select* as a project in the console — so the console's *Pipelines → Tasks* view cannot scope to them for you.
Reading a Task's inner fields (its image, its parameters) is also exactly what `oc get … -o jsonpath` does best, so this one is CLI-only.
====

Start by browsing Parasol's shared library.
You have read access to it (the platform team granted it), so you can list and read the Tasks any pipeline reuses:

.Expected output (an extract — the shared library grows as teams curate their own Tasks; the two this pipeline uses:)

The shared library holds several curated Tasks — teams add their own over time — and two of them fill gaps in *this* pipeline.
Now the *why*.
The Pipeline's `unit-test` step runs Maven — and OpenShift Pipelines *ships* a `maven` Task, so the obvious choice is to use that shipped one.
Look at what it actually runs:

[source,sh,role=execute]
----

oc get tasks.tekton.dev maven -n openshift-pipelines -o jsonpath='  {.spec.steps[1].image}{"\n"}'
echo "shipped maven task, parameters:"
oc get tasks.tekton.dev maven -n openshift-pipelines -o jsonpath='  {range .spec.params[*]}{.name}{"  "}{end}{"\n"}'
----

.Expected output (parameter names vary by Pipelines version — the load-bearing fact is the build-step *image*)
[source,texinfo]
----

  registry.redhat.io/ubi9/openjdk-17@sha256:...
shipped maven task, parameters:

----

The shipped `maven` Task *advertises* a `JAVA_VERSION` parameter (its description even lists `8, 11, 17, 21`) — so it looks like you could just ask for 21.
But read the *build-step image*: it is pinned to *Java 17* (`ubi9/openjdk-17`), and `JAVA_VERSION` does not repoint it — the parameter is a promise the pinned image can't keep.
`parasol-claims` is a *Java 21* application, so the shipped Task still cannot build it: Maven runs on JDK 17 and fails with `release version 21 not supported`, whatever you set `JAVA_VERSION` to.
That is the gap the curated library fills — not a missing *knob*, but a guaranteed *runtime*.
Read Parasol's answer:

[source,sh,role=execute]
----
echo "curated maven-jdk21, build step image:"
oc get tasks.tekton.dev maven-jdk21 -n ogsr-parasol-tasks -o jsonpath='  {.spec.steps[0].image}{"\n"}'
----

.Expected output
[source,texinfo]
----
curated maven-jdk21, build step image:
  registry.access.redhat.com/ubi9/openjdk-21:latest
----

A *Java 21* runner image — the guaranteed runtime the shipped Task's `JAVA_VERSION` knob could not actually deliver.
Rather than paste a patched Maven Task into every Java 21 pipeline, the platform team curated `maven-jdk21` *once*, and every pipeline references it by cluster resolver.
That is the entire argument for an organization library, in one concrete gap.

Now read the other curated Task — the one that produced the `image-size-mb` result you saw in exercise 1:

The *cluster resolver* you have been reading — `resolver: cluster` with `name` and `namespace` — is its supported replacement, and it is strictly better: Tasks live in a normal namespace with normal RBAC, and you reference the exact one you want.

== 3. Break the build: a failing test stops the pipeline
⏱ *~10 min of your hands, but budget ~20 — it is two more full pipeline runs* · edit a test in your fork, watch the pipeline refuse the bad change, then fix it

A pipeline that tests but ships anyway is theater.
The value is that a *failing test stops the build* — a broken change never becomes a deployed image.
You will prove that by breaking a real rule, in *your own fork*.

The rule is Parasol's: *a claim cannot be Approved while its adjuster is still Unassigned* — somebody has to own a claim before the company agrees to pay it.
`parasol-claims` *enforces* it in the service: `ClaimResource.updateStatus()` answers a `PUT {"status":"Approved"}` against an unowned claim with *409 Conflict*, never 200.
(409 rather than 400 is deliberate — the request body is perfectly valid, it is the *claim* that is not in a state that allows the change.)

A unit test drives that rule from the outside, and it is green as shipped: it opens a claim *with* an adjuster, approves it, and the service accepts.
You will flip a one-line toggle so the test opens the claim with *no* adjuster instead — the service then refuses the approval, the test fails on the 409, the pipeline goes red, and you revert.

In your *Gitea tab* ({gitea_url}/{user}/parasol-claims[{user}/parasol-claims^]):

. Open `src/test/java/com/parasol/claims/ClaimResourceTest.java`.
. Click the *pencil* (Edit) icon.
. Use your browser's find (kbd:[Ctrl+F] / kbd:[Cmd+F]) for `assignAdjusterBeforeApproval` — it is a single declaration, currently around line 527:
+
[source,java]
----
final boolean assignAdjusterBeforeApproval = true;
----
. Change `true` to `false`.
. Scroll down and *Commit Changes* directly to the `main` branch (commit message e.g. "break: approve without an adjuster").

⏱ *~10 min* · wire a webhook so the pipeline fires on every push — no `oc create`

Two pieces remain: create that Secret, and create the webhook that feeds it.

*First*, give PaC a Gitea token (to read your repo and report status) and a *webhook secret* (a shared string that lets PaC trust the incoming push).
Create the token in Gitea, then store both in the `gitea-pac-secret` the `Repository` already expects:

. In Gitea, click your avatar (top right) → *Settings* → *Applications*.
. Under *Manage Access Tokens*, name a token `pac`, and under *Select scopes* choose *write:repository*.
Click *Generate Token* and *copy the value* (Gitea shows it once).
. Store the token plus a webhook secret you generate into the Secret.
Run this block first — it ends at a prompt and waits; paste the token you just copied and press *Enter*.
It is read silently, so nothing appears as you paste:
// DO NOT merge this block with the one below it. An interactive `read` must be the LAST
// line of a click-to-run block: content/supplemental-ui/js/click-to-run.js sends the whole
// block to the terminal in a SINGLE write (commandText() takes the block's entire
// textContent; sendToTerminal() posts it as one `execute` message), so any line after the
// `read` sits in the tty input queue and is swallowed as the token. Measured on bash 3.2
// and bash 5.1: `read` captured the next line verbatim, and on 5.1 every remaining line of
// the block was discarded as well — merged, this stored WEBHOOK_SECRET="parasol-..." as
// the Gitea token and never created the Secret at all. Verified 2026-07-29.
+
[source,sh,role=execute]
----
read -rsp "paste your Gitea token, then press Enter: " GITEA_TOKEN; echo
----
+
Now generate the webhook secret and create the Secret from both values:
+
[source,sh,role=execute]
----
WEBHOOK_SECRET="parasol-$(openssl rand -hex 6)"
echo "your webhook secret is: $WEBHOOK_SECRET"
echo "  ^ copy it — you paste it into the Gitea webhook form next"
# `ws start` does NOT clear a leftover Secret from a prior pass on this same cluster (only
# `ws reset`/`ws prep` do) — clear it first, safe even on a first run (no-op if absent):
oc delete secret gitea-pac-secret -n $NS --ignore-not-found=true
oc create secret generic gitea-pac-secret -n $NS \
  --from-literal=token="$GITEA_TOKEN" \
  --from-literal=webhook-secret="$WEBHOOK_SECRET"
----

*Second*, create the webhook in Gitea that POSTs to the PaC controller.
The controller is reachable at a predictable address built from your cluster domain — print it:

[source,sh,role=execute,subs="attributes"]
----
echo "https://pipelines-as-code-controller-openshift-pipelines.{cluster_domain}"
----

In your fork's Gitea page:

. *Settings* → *Webhooks* → *Add Webhook* → *Gitea*.
. *Target URL*: the URL printed above.
. *HTTP Method*: `POST`; *POST Content Type*: `application/json`.
. *Secret*: the `$WEBHOOK_SECRET` value printed earlier.
. *Trigger On*: *Push Events* (leave the default branch filter).
. *Active*: checked. Click *Add Webhook*.

== Challenge (optional)
⏱ *no hand-holding*

You have the mechanics.
Try these on your own:

* *Tighten the budget.*
Re-run the pipeline with `-p max-size-mb=300` (add a `params` entry, or `tkn pipeline start ... -p max-size-mb=300`) and read the `image-report` step: the image is in the high 300s of MB, so `within-budget` flips to `false`.
Notice the run still *succeeds* — the report *flags*, it does not *fail* the build.
How would you make it a hard gate?
* *Read a Task's full body.*
`oc get tasks.tekton.dev image-size-report -n ogsr-parasol-tasks -o yaml` — find where it writes its three results (the `$(results.<name>.path)` files).
That is how any Task publishes data.
* *Trigger on a pull request.*
Open a PR in Gitea against `main` instead of pushing to it, and watch PaC run the pipeline for the PR — the same `.tekton/` file handles both (`on-event: [push, pull_request]`).
* *Find the run in the console.*
Open *Pipelines → PipelineRuns* in the {ocp_console_url}[OpenShift console^], select your latest run, and read the graph — the same five Tasks, visualized.

When you are done, run `ws verify {module-id}` — or `ws prep {module-id} --yes` to wipe `{user}-cicd` back to the entry state (the pipeline and `claims-db`, your fork intact) and start fresh.
