== Exercise 1 shows *two* pods, and `oc logs --previous` errors

Symptom:: After the exercise-1 break, `oc get pods -l app=parasol-claims` shows *two* pods — one `1/1 Running` and one `0/1` whose `STATUS` flips between `Running`, `Error`, and `CrashLoopBackOff` — and a plain `oc logs -l app=parasol-claims --previous` errors with `previous terminated container "…" not found`.
Cause:: The readiness probe you add first *gates* the rolling update: the new pod cannot reach the database, never passes readiness, and is held at `0/1`, while the old, healthy pod keeps serving.
So there are two pods, and `oc logs -l …` matches *both* — but the healthy old pod has no previous (crashed) container, which is exactly what triggers the error.
The `STATUS` column oscillates because the broken container keeps booting, failing, and restarting; the honest signal is the `READY` column staying `0/1`.
Fix:: Read the *newest* (broken) pod by name instead of by label, with no `--tail` (see the lab page's own note on why a fixed tail silently truncates the payoff line on some runs):
+
[source,sh,role=execute]
----
BAD=$(oc get pods -l app=parasol-claims --sort-by=.metadata.creationTimestamp -o jsonpath='{.items[-1:].metadata.name}')
oc logs "$BAD" --previous | grep -A2 -iE 'Failed to start|UnknownHost'
----
+
The last `Caused by:` is the real cause (here, `UnknownHostException: wrong-db-host`).
Remove the bad override to recover: `oc set env deploy/parasol-claims QUARKUS_DATASOURCE_JDBC_URL-` (then `oc rollout status deploy/parasol-claims`).

== `oc logs --previous` fails with `unable to retrieve container logs for cri-o://…`

Symptom:: Even with the pod targeted by *name* (not by label), `oc logs "$BAD" --previous` sometimes fails outright with `unable to retrieve container logs for cri-o://…` instead of printing the crash trace — including on a run with only one restart, following the lab's steps at normal pacing.
Cause:: `--previous` asks cri-o for the *immediately preceding* terminated container instance. A `CrashLoopBackOff` container restarts on its own schedule, and cri-o rotates/garbage-collects old container log files independently of anything you do — by the time the command runs, the instance `--previous` points at may already be gone. This is a real race against container-log retention, not a flaky cluster or a mistake in the command; it reproduced in 2 of 3 measured attempts during the module's cold-start smoke (2026-07-31), so treat it as expected, not exceptional.
Fix:: The lab's own command already carries the fix — a fallback to the *current* container's logs, which is still crash-looping on the identical cause:
+
[source,sh,role=execute]
----
BAD=$(oc get pods -l app=parasol-claims --sort-by=.metadata.creationTimestamp -o jsonpath='{.items[-1:].metadata.name}')
oc logs "$BAD" --previous 2>/dev/null | grep -A2 -iE 'Failed to start|UnknownHost' \
  || oc logs "$BAD" | grep -A2 -iE 'Failed to start|UnknownHost'
----
+
If you typed the bare `--previous` version by hand and hit the error, just re-run without `--previous` — the current container shows the same `UnknownHostException`.

== I removed an environment variable and the app broke

Symptom:: After `oc set env deploy/parasol-claims SOMEVAR-`, the app fails to connect to the database.
Cause:: Once you wire a ConfigMap or Secret with `oc set env --from`, each key becomes an environment variable *sourced from* that object.
Removing it with `SOMEVAR-` deletes the sourced variable too — the app loses that setting and falls back to a default that does not point at your database.
Fix:: Re-inject the source; it is idempotent:
+
[source,sh,role=execute]
----
oc set env deploy/parasol-claims --from=configmap/claims-config
oc set env deploy/parasol-claims --from=secret/claims-creds
----
+
Only remove a variable with `NAME-` when you intend the app to stop having it.
To *change* a value, edit the ConfigMap/Secret instead.

== The Route returns `503`, or a cut-off HTML page, right after a config change

Symptom:: `curl` to the claims Route returns `503` — or, piped through `head -c 80`, prints the start of an HTML page (`<html> <head> <meta name="viewport" …`) — for a few seconds after an `oc set env`/`oc set probe` command, even after `oc rollout status` printed `successfully rolled out`.
Cause:: Each of those commands triggers a rolling update.
`rollout status` returns as soon as the new pod is Ready, while the old one is still shutting down, and the OpenShift router refreshes its list of backend pods only every few seconds.
A request sent in that window can still be routed to the old pod's address, hang, and come back as the router's `503` "Application is not available" page.
Measured at the exercise-2 checkpoint by the 2026-11-12 smoke.
Fix:: Wait until only the new pod is left, give the router ten seconds, and let `curl` retry instead of printing the error page — the lab's own blocks do exactly this:
+
[source,sh,role=execute]
----
oc rollout status deploy/parasol-claims
for i in $(seq 1 45); do [ "$(oc get pods -l app=parasol-claims -o name | wc -l)" -eq 1 ] && break; sleep 2; done
sleep 10
curl -sf --retry 30 --retry-all-errors --retry-delay 2 -o /dev/null -w '%{http_code}\n' \
  "http://$(oc get route parasol-claims -o jsonpath='{.spec.host}')/api/claims"
----
+
A persistent `503` (not transient) means the pod never becomes Ready — check `oc get pods` and the readiness probe path.

== `oc create configmap ... already exists`

Symptom:: Re-running exercise 2's `oc create configmap claims-config …` (or the `claims-creds` Secret) fails with `configmaps "claims-config" already exists`.
Cause:: `oc create` is not idempotent — it refuses to overwrite an object that already exists. You hit this by running the create step twice in one sitting. A `ws reset {module-id}` is *not* the cause: reset purges the namespace's user ConfigMaps and Secrets (everything except the platform's own `*-dockercfg`/`*-token`/CA objects and the module's entry marker), so after a reset `claims-config`/`claims-creds` are gone and the create succeeds cleanly.
Fix:: Delete the object first and re-create — or make the step idempotent with `apply`:
+
[source,sh,role=execute,subs="attributes+"]
----
oc delete configmap claims-config --ignore-not-found -n {user}-dev
oc delete secret claims-creds --ignore-not-found -n {user}-dev
----
+
Or overwrite in place: `oc create configmap claims-config … --dry-run=client -o yaml | oc apply -f -`.

== The mounted config file has no effect

Symptom:: You mounted a properties file but its settings (e.g. `access-log`) do not take effect.
Cause:: Either `QUARKUS_CONFIG_LOCATIONS` does not point at the mounted path, or an environment variable is overriding the same property (env vars outrank file config in Quarkus).
Fix:: Confirm the file is present and the env var points at it:
+
[source,sh,role=execute]
----
oc exec deploy/parasol-claims -- cat /mnt/claims-config/application.properties
oc set env deploy/parasol-claims --list | grep QUARKUS_CONFIG_LOCATIONS
----
+
The path in `QUARKUS_CONFIG_LOCATIONS` must be the exact mounted file (or its directory).
Remember that a property also set via an environment variable will win over the file.

== `git clone` of my config fork fails

Symptom:: In exercise 4, `git clone {gitea_url}/{user}/claims-config` fails, though `oc` commands work.
Cause:: The fork is a *public* repo, so clone needs no credentials — a failure is almost always network (proxy/TLS interception) rather than auth, or the fork job has not finished.
Fix:: Confirm the Git server is reachable and the fork exists:
+
[source,sh,role=execute,subs="attributes+"]
----
curl -sI {gitea_url}/{user}/claims-config | head -1
----
+
A `200`/`301` means the repo is there — retry the clone.
If it is missing, the fork job has not run; ask your instructor to run `adm reset {module-id} --user {user}`.

== The three-environment digest comparison shows a mismatch, not three identical values

Symptom:: In exercise 4's final promotion check, one namespace's `digest=` differs from the other two, even though `dev`/`stage`/`prod` all run the same `overlays/*` referencing the identical `parasol-claims:1.0` tag.
Cause:: This is the mutable-tag trap, not a broken promotion — and it is called out in the lab's own note right after this comparison. The overlays name the image by *tag*, and `imagePullPolicy: IfNotPresent` means a node that already cached an earlier build of `:1.0` (from a previous run of this module, or an image rebuild that landed after that node last pulled) keeps serving its cached bytes instead of pulling what the tag currently points to. Only the pod scheduled onto that stale-cache node shows the odd digest.
Fix:: Delete the pod in the odd namespace so a fresh pull lands, then re-compare:
+
[source,sh,role=execute,subs="attributes+"]
----
# substitute whichever namespace showed the odd digest above, e.g. {user}-stage or {user}-prod
NS={user}-stage
oc delete pod -l app=parasol-claims -n "$NS"
oc -n "$NS" rollout status deploy/parasol-claims
oc -n "$NS" get pod -l app=parasol-claims -o jsonpath='{.items[0].status.containerStatuses[0].imageID}' | sed 's#.*@##' | cut -c1-16
----
+
All three digests should now match. This is exactly why a real promotion pipeline references images by *digest* (`@sha256:…`), never by a mutable tag — the fix done properly is in the trusted-supply-chain module.

== Exercise 4's stage-vs-prod log count comes out backwards (prod noisier than stage)

Symptom:: Comparing `oc logs -l app=parasol-claims --tail=100 | grep -c 'io.quarkus'` between stage (`INFO`) and prod (`WARN`) shows prod with *more* matching lines, not fewer — the opposite of what the log-level setting should produce.
Cause:: Two compounding effects, both structural, not flaky: (1) `oc logs -l …` reads *every* pod the selector matches, and prod runs 3 replicas to stage's 2, so the comparison was never apples-to-apples; (2) every replica of a promoted environment runs Hibernate's `drop-and-create` schema import against the *same* shared ephemeral Postgres on startup (the seed reloads every boot, by design — see `apps/parasol-claims/src/main/resources/application.properties`), so replicas that lose that race throw `duplicate key value violates unique constraint "claim_event_pkey"` at `WARN`, and that exception's stack frames run through `io.quarkus.hibernate.orm.runtime.*` classes — so they still match a blanket `io.quarkus` grep even though they are not the `INFO` startup chatter the exercise means to measure. More replicas means more of that noise, which is why prod (more replicas, higher threshold) can out-count stage.
Fix:: This is fixed in the current lab page — it now reads a single named pod per environment and filters on the log-*level* field (`INFO  \[io\.quarkus`) instead of the bare package-name substring, so a database-seeding race (which throws `WARN`/`ERROR`, a different level) cannot swamp the count. If you are looking at an older capture that still shows the inverted numbers, re-run the corrected command from the current lab page.
