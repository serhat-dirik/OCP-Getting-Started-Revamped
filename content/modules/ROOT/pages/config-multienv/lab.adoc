== Up, but not ready — and the same image in three environments · 12 min

A pod that is running yet cannot serve is held out of rotation until it recovers, and the identical image digest then runs in dev, stage and prod with only its configuration changing.

[IMPORTANT]
.Prep — run before the session
====
This demo starts from the finished lab state. Stage it before the session:

[source,sh,role=execute]
----
adm solve config-multienv
----

It leaves the claims service fully configured in `{user}-dev` and promoted to `{user}-stage` (2 replicas) and `{user}-prod` (3 replicas), and takes a few minutes to return.

Staging brings stage and prod up through Argo CD, and each of them boots a PostgreSQL of its own, so a command that has returned is not the same as three serving environments. Step 4 prints one line per environment and has nothing to show for an empty one, so confirm all three first:

[source,sh,role=execute,subs="attributes+"]
----
for ns in {user}-dev {user}-stage {user}-prod; do
  printf "%-16s ready=%s\n" "$ns" \
    "$(oc -n $ns get deploy parasol-claims -o jsonpath='{.status.readyReplicas}' 2>/dev/null)"
done
----

Expect `1`, `2` and `3`; if a line comes back empty, that environment is not serving yet — wait a minute and run the check again, and if it is still empty run the staging command above again rather than applying an overlay by hand, which is the attendee exercise and costs several minutes.

Have a terminal signed in as `{user}` and the web console on *Topology* in `{user}-dev`. Pod names and image digests were captured from a live run and will differ here.

CAUTION: Three different image digests in step 4 are not a broken promotion. The shared `parasol-claims:1.0` tag was rebuilt after some nodes had already cached the older image, and `imagePullPolicy: IfNotPresent` let an earlier-scheduled pod keep the cached bytes — which is itself the argument for promoting by digest rather than by tag. Delete the odd pod out, then re-run the comparison:

[source,sh,role=execute,subs="attributes+"]
----
ODD={user}-stage        # the namespace whose digest differed; change it if it was another one
oc -n $ODD delete pod -l app=parasol-claims
oc -n $ODD rollout status deploy/parasol-claims
----

=== Brief

image::config-multienv/config-multienv-01-config-sources.svg["Four places to put settings — inline environment variables, a ConfigMap for non-secret configuration, a Secret for credentials, and a mounted file — with an arrow from each into a single box for the parasol-claims image, which is built once and reads its configuration at startup."]

*Why externalize configuration at all*

A container image is meant to be immutable and portable: build it once, run it anywhere. Bake one environment's specifics into it — a database hostname, a password, a log level — and that promise is gone. "Promote to production" now means "rebuild", and the artifact that passed staging is not the artifact that ships.

The fix is old and simple: the image carries the behavior, the environment supplies the settings. OpenShift offers four places to put them — inline environment variables, a ConfigMap, a Secret, and a file mounted from either — in increasing order of how carefully each is handled.

*Running is not the same as ready*

A pod can be up and still unable to serve: loading, waiting on a dependency, or wedged. The platform cannot tell unless the application says so, and it says so through three probes. Startup holds the other two off while the application boots. Liveness restarts a container that has wedged. Readiness answers "can I take traffic right now" — and a pod that answers no is removed from the Service's endpoints, so requests are held rather than sent somewhere they would fail.

*Promotion: same image, different config*

Put the two together and promotion becomes almost boring, which is the goal. Because the image is immutable and every environment-specific setting is external, moving to production is not a rebuild — it is applying a different set of values to the same bytes. Kustomize describes one base and the per-environment overlays that change only what should differ.

*In this demo*

. The claims service in dev — settings in a ConfigMap, credentials in a Secret, three probes declared
. Readiness deliberately broken: the container runs, no pod is ever ready, and the Route returns 503
. The probe restored, and the pod put straight back into rotation
. The identical image digest in dev, stage and prod, with only replica counts and configuration differing
. The whole discipline on one screen

=== 1 · Configured from outside, and healthy — 2 min

Parasol runs the exact same claims image in dev, stage and production, and the only thing that differs between them is configuration. In `{user}-dev` that service is already running with its settings in a ConfigMap, its credentials in a Secret, and three probes declared on the Deployment.

image::config-multienv/config-multienv-02-configmap-secret.png["The claims-config ConfigMap detail page in the web console, scrolled to its Data section: five keys with their values in plain readable text — APP_ENV dev, POSTGRESQL_DATABASE parasol, POSTGRESQL_HOST claims-db, POSTGRESQL_PORT 5432 and QUARKUS_LOG_LEVEL INFO."]

*Why it matters*

The image holds no environment's details, so the same bytes can run in every environment — and a setting can be changed, reviewed and rolled back on its own, without a rebuild and without editing the application.

*On screen* — web console → *Topology* in `{user}-dev`: `parasol-claims` and `claims-db`, both running. Then, from the terminal, the probes the Deployment declares:

[source,sh,role=execute,subs="attributes+"]
----
oc -n {user}-dev get deploy parasol-claims \
  -o jsonpath='{.spec.template.spec.containers[0].startupProbe.httpGet.path} {.spec.template.spec.containers[0].readinessProbe.httpGet.path} {.spec.template.spec.containers[0].livenessProbe.httpGet.path}{"\n"}'
----

*What just happened*

Three paths, one per probe: started, ready, live. Readiness is the one the next step breaks.

=== 2 · Break readiness and the Route returns 503 — 4 min

Point the readiness probe at a URL that does not exist and roll the whole Deployment onto it, so the single remaining pod is one whose container is running perfectly well and can never answer yes to the platform's question.

image::config-multienv/config-multienv-03-readiness-503.png["The Pods list for the dev project, two rows: claims-db Running with Ready 1/1, and directly below it parasol-claims also Running with zero restarts but Ready 0/1 — a container that started fine and never passes its readiness probe."]

*Why it matters*

This is the failure the platform is built to contain. The container is up and the process is fine; what fails is the platform's question — can you serve? No ready pod means no endpoints, so the Route returns 503 rather than sending a request into a pod that would break it. The column that tells the story is READY, not STATUS.

[source,sh,role=execute,subs="attributes+"]
----
oc -n {user}-dev set probe deploy/parasol-claims --readiness --get-url=http://:8080/q/health/typo
# scale to 0 then 1 so the only pod uses the broken readiness check
oc -n {user}-dev scale deploy/parasol-claims --replicas=0
# wait for the old pod to actually go, so exactly one pod is left and it is the broken-probe one
for i in $(seq 1 20); do [ "$(oc -n {user}-dev get pods -l app=parasol-claims --no-headers 2>/dev/null | wc -l | tr -d ' ')" = 0 ] && break; sleep 2; done
oc -n {user}-dev scale deploy/parasol-claims --replicas=1
# then sample the new pod instead of sleeping blind: it reaches Running in ~20-30s and then HOLDS at
# 0/1, because readiness never passes. The loop stops the moment the container reports started.
for i in $(seq 1 12); do
  oc -n {user}-dev get pods -l app=parasol-claims --no-headers
  oc -n {user}-dev get pods -l app=parasol-claims -o jsonpath='{.items[0].status.containerStatuses[0].started}' | grep -q true && break
  sleep 3
done
oc -n {user}-dev get endpoints parasol-claims
CLAIMS=$(oc -n {user}-dev get route parasol-claims -o jsonpath='{.spec.host}')
curl -s -o /dev/null -w "Route: %\{http_code}\n" http://$CLAIMS/api/claims
----

*What just happened*

No ready pod, so the Service has no endpoints, so the Route answers 503. The platform is holding the request rather than delivering it to a pod that cannot serve it — with no load balancer touched and no pod removed from a pool by hand.

=== 3 · Restore the probe and the pod returns to rotation — 2 min

Point readiness back at the endpoint that exists. The same gate that drained the pod puts it back into rotation the moment it answers, and the Route recovers within seconds.

image::config-multienv/config-multienv-02-readiness-gate.svg["The readiness gate: a Route and Service above two pods. A solid traffic arrow reaches the pod whose readiness is passing, shown in green and in the Service endpoints; a dashed no-endpoint arrow stops short of the pod whose readiness is failing, shown in red, removed from endpoints with traffic held and the Route returning 503."]

*Why it matters*

Drain, hold, recover is one continuous decision the platform makes from the application's own answer. Nothing was reconfigured, nobody edited a pool, and no user reached the broken pod in between.

[source,sh,role=execute,subs="attributes+"]
----
oc -n {user}-dev set probe deploy/parasol-claims --readiness --get-url=http://:8080/q/health/ready
oc -n {user}-dev rollout status deploy/parasol-claims
# re-derive the host rather than reusing $CLAIMS: a fresh terminal would leave it
# empty, and `curl http:///api/claims` prints "Route: 000" — which reads exactly like a failed fix
CLAIMS=$(oc -n {user}-dev get route parasol-claims -o jsonpath='{.spec.host}')
curl -s -o /dev/null -w "Route: %\{http_code}\n" http://$CLAIMS/api/claims
----

*What just happened*

`Route: 200`. The pod re-entered the endpoints as soon as readiness passed, and the recovery needed no more action than the failure did.

=== 4 · One image, three environments, configuration only — 3 min

The other half of the story: the same image already runs in `{user}-stage` and `{user}-prod`, promoted by a Kustomize overlay per environment. Compare the three side by side — the digest, the replica count, and the environment's own configuration.

image::config-multienv/config-multienv-03-promotion-overlays.svg["One Kustomize base holding the claims app, its config and the parasol-claims:1.0 image, branching into three overlays — dev at 1 replica with APP_ENV dev and log INFO, stage at 2 replicas with APP_ENV stage and log INFO, prod at 3 replicas with APP_ENV prod and log WARN — each applied into its own namespace."]

*Why it matters*

The digest is the same in all three environments: the exact bytes that passed testing are the bytes in production. What differs is declared configuration, so promotion means applying values rather than rebuilding — and "it worked in staging" stops being a mystery, because the gap between the environments is something you can read in a diff.

[source,sh,role=execute,subs="attributes+"]
----
for ns in {user}-dev {user}-stage {user}-prod; do
  printf "%-16s replicas=%s  APP_ENV=%s  image=%s\n" "$ns" \
    "$(oc -n $ns get deploy parasol-claims -o jsonpath='{.status.readyReplicas}')" \
    "$(oc -n $ns get cm claims-config -o jsonpath='{.data.APP_ENV}')" \
    "$(oc -n $ns get pod -l app=parasol-claims -o jsonpath='{.items[0].status.containerStatuses[0].imageID}' | sed 's#.*@##' | cut -c1-19)"
done
----

=== 5 · The whole discipline on one screen — 1 min

Configuration in a ConfigMap, credentials in a Secret, health in three probes, and one image everywhere — four ordinary platform objects that together remove a whole class of production incident.

image::config-multienv/config-multienv-05-what-you-built.svg["What the module assembles: the parasol-claims:1.0 image, one image and one digest, feeding a configured and probed dev environment alongside the claims-config ConfigMap and claims-creds Secret, with oc apply -k of the stage and prod overlays promoting the same image onward to stage at 2 replicas with log INFO and prod at 3 replicas with log WARN."]

*Why it matters*

None of this is exotic and none of it is a product to buy. It is the default shape of an application on OpenShift, which is why the discipline holds under pressure instead of being the first thing dropped.

*On screen* — web console → *Topology* in `{user}-prod`: three healthy replicas of the same image the demo started from.

== Frequently asked questions

*Is a Secret encrypted?*::
No. A Secret's values are base64-encoded, which is trivially reversible — anyone who can read the Secret reads the plaintext. What a Secret buys is separate access control, so people can deploy without being able to read the database password, and one place to rotate a credential.

*Then where should the real source of truth for secrets live?*::
In a dedicated manager — HashiCorp Vault, or a cloud secrets service — synced into the cluster on demand. On OpenShift the External Secrets Operator does that: a small `ExternalSecret` object references the external manager, and the operator produces an ordinary Kubernetes Secret that the application consumes unchanged, so nothing in the workload has to know the difference.

*Why did the Route not return 503 the moment the probe broke?*::
Because a probe change triggers a rolling update, and the rollout is itself gated by readiness: the new pod never becomes ready, so it is held out of the Service while the old, healthy pod keeps serving. That is the platform protecting users from a bad change. A 503 appears only when there is no ready pod at all — which is why the demo scales to zero and back to one, so the only pod is the one with the broken probe.

*All three environments run the same tag — how do you know it is the same bytes?*::
The comparison reads the image digest from each running pod, not the tag. A tag is a mutable pointer and can be rebuilt underneath you; the digest is the content. That is also why supply-chain practice promotes by digest, and why a digest mismatch across environments is worth investigating rather than glossing over.

*Why does each environment get its own database?*::
So the environments are genuinely independent — promoting to production must not touch stage's data. Each overlay stands up its own PostgreSQL, seeded identically. They are ephemeral here on purpose; persistent storage is the next module.

.Why a probe first?

.The override, and life without a probe
[%collapsible]
====
`QUARKUS_DATASOURCE_JDBC_URL` is the environment-variable form of the app's datasource URL, and it *overrides* the correct value the image ships with.
Because this is a rolling update — the same strategy you met in *Platform Orientation & First App* — the platform brings up a *new* pod alongside the old one and holds off retiring the old one until the new pod passes readiness.
It never will.

The `STATUS` column oscillates — `Running`, `Error`, `CrashLoopBackOff` — as the container boots, fails, and is restarted on a back-off timer; `READY` stays `0/1` because the pod never once passes its readiness check.

Without the probe, the platform would have swapped straight to the broken pod, which would have reported a reassuring `1/1 Running` for the better part of a minute before it finally started crash-looping — the failure would have been invisible exactly when you needed to see it.
====

Now *read the logs* of the newest pod's *previous* container, where the crash usually is:

// No --tail here, deliberately. It used to be --tail=40, which cut the payoff line out of its own
// expected output: on a measured run the crash log was 129 lines with "Failed to start application"
// at line 65, so the last 40 lines began well past it and the attendee saw only the trailing
// UnknownHostException. Widening the window is not the fix — the log's length depends on JVM startup
// verbosity and varies run to run, so ANY fixed number is a guess that silently truncates on the runs
// where it matters. grep already bounds what reaches the terminal, so searching the whole log costs
// nothing and always finds the cause. (Found by the config-multienv smoke, 2026-07-31.)
//
// The --previous | grep fallback below is a second fix from the same smoke: `oc logs --previous`
// against a fast-restarting CrashLoopBackOff container failed outright with "unable to retrieve
// container logs for cri-o://..." in 2 of 3 measured attempts, including once at literal lab pacing
// with only 1 restart — cri-o had already rotated the log the "previous" flag pointed at away by the
// time the command ran. This is a real race against container-log retention, not a one-off. Because
// grep against an empty/failed `oc logs` output exits non-zero (no lines matched), the `||` below
// reliably falls back to the CURRENT container's logs — which, since the pod is still crash-looping
// on the same root cause, show the identical UnknownHostException even when "previous" is gone.
[source,sh,role=execute]
----
BAD=$(oc get pods -l app=parasol-claims --sort-by=.metadata.creationTimestamp -o jsonpath='{.items[-1:].metadata.name}')
oc logs "$BAD" --previous 2>/dev/null | grep -A2 -iE 'Failed to start|UnknownHost' \
  || { echo "(previous container log already rotated away by cri-o — reading the current one, which is still crash-looping on the same cause)"; oc logs "$BAD" | grep -A2 -iE 'Failed to start|UnknownHost'; }
----

.Why `--previous`, and the `||` fallback
[%collapsible]
====
By the time you look, the container has often already been restarted onto a fresh attempt, so the crash sits in the *previous* container's log.
Targeting the newest pod also avoids the healthy old pod, which has no previous container to read.
If cri-o has already rotated that previous log away, the command falls back to the current container's log, which is still crash-looping on the same cause.
====

=== Mount config as a file (the other way to deliver it)

Config can also arrive as a *mounted file*: put a properties file in a ConfigMap, mount it, and point Quarkus at it.

[source,sh,role=execute]
----
# a ConfigMap whose single key is a whole application.properties file
oc create configmap claims-file-config \
  --from-literal=application.properties=$'# delivered as a MOUNTED FILE\nquarkus.http.access-log.enabled=true\n'

# mount it read-only at /mnt/claims-config
oc set volume deploy/parasol-claims --add --name=file-config --type=configmap \
  --configmap-name=claims-file-config --mount-path=/mnt/claims-config --read-only=true

# point Quarkus at the mounted file (the documented quarkus.config.locations pattern)
oc set env deploy/parasol-claims QUARKUS_CONFIG_LOCATIONS=/mnt/claims-config/application.properties
oc rollout status deploy/parasol-claims
for i in $(seq 1 45); do [ "$(oc get pods -l app=parasol-claims -o name | wc -l)" -eq 1 ] && break; sleep 2; done
sleep 10
----

The file turns on HTTP access logging (`quarkus.http.access-log.enabled=true`), which nothing else sets.
Make two requests and look for access-log lines:

[source,sh,role=execute]

CLAIMS=$(oc get route parasol-claims -o jsonpath='{.spec.host}')
for i in 1 2; do curl -sf --retry 30 --retry-all-errors --retry-delay 2 -o /dev/null "http://$CLAIMS/api/claims"; done
oc logs -l app=parasol-claims --tail=20 | grep access-log
----

.Env vs mounted file — when to use which
[cols="1,2,2",options="header"]
|===
| | Environment variables | Mounted file

| Best for
| A handful of discrete values
| A large or structured config file

| To change a value
| Edit the Deployment
| Update the ConfigMap or Secret; the file changes in place

| Secrets
| In the process environment, so in crash dumps and some logs
| Kept *out* of the process environment
|===

Both are first-class: choose by size and rotation, not correctness.

.Work *with* the guardrails, not against them
[%collapsible]
====
The LimitRange and ResourceQuota are not there to frustrate you — they keep one team's workload from starving another's on a shared cluster.
The right instinct when you hit a quota is to *right-size your requests* (do you really need 4 cores?), not to demand the quota be raised.
Requests are a reservation; asking for more than you use wastes the whole namespace's headroom.

You are meeting these guardrails from the inside, as the tenant.
Authoring them from the outside — writing the ResourceQuota and LimitRange, and the RBAC that decides who may read or change them — is *Multi-Tenancy & Workload Security*, a separate module in this workshop.

The log level differs at runtime too: stage runs at `INFO`, prod at `WARN`.
Count the `INFO` lines of a *single* pod in each:

// Grounded by the config-multienv smoke, 2026-07-31 (2 passes, both reproduced): the original version
// of this check compared `oc logs -l app=parasol-claims` (the WHOLE label selector — every replica's
// log concatenated) and counted the literal substring `io.quarkus`. On a live cluster that inverted:
// stage measured 16, prod measured 28. Two compounding causes, both structural, not flaky: (1) prod
// runs 3 replicas to stage's 2, and a selector-based `oc logs` fans out to every matching pod, so the
// comparison was already unfair before log level entered into it; (2) all replicas of a promoted
// environment race to run Hibernate's drop-and-create schema import against the SAME shared ephemeral
// Postgres on startup (see apps/parasol-claims/src/main/resources/application.properties — the seed
// reloads on every boot, by design, so labs get reproducible claim numbers), so every replica that
// loses that race throws `relation "claim_event" does not exist` — a DDL-visibility race where one
// replica's schema-create has not yet committed when another replica's import runs — a WARN, not an
// INFO — whose stack frames run through io.quarkus.hibernate.orm.runtime.* classes and so still match
// a blanket `io.quarkus` grep. More replicas means more of that spam, not less, which is why prod
// (3 replicas, WARN threshold) out-counted stage (2 replicas, INFO threshold) instead of the other way
// around. The fix below addresses both causes rather than papering over one: read a SINGLE named pod
// per environment (removes the replica-count multiplier), and filter on the log-LEVEL field itself
// rather than a package-name substring (removes the WARN-storm confound, since QUARKUS_LOG_LEVEL
// governs level, not which package logged the line). Re-measured live on a promoted environment,
// 2026-07-31: the corrected command read stage=3, prod=0 on 4 of 4 runs, confirming the lesson holds.
// Those exact counts are a build-banner artefact — they drift with the Quarkus version — so the
// checkpoint below states the shape of the comparison, not the numbers.
[source,sh,role=execute,subs="attributes+"]
----
STAGE_POD=$(oc -n {user}-stage get pod -l app=parasol-claims -o jsonpath='{.items[0].metadata.name}')
PROD_POD=$(oc -n {user}-prod  get pod -l app=parasol-claims -o jsonpath='{.items[0].metadata.name}')
echo "stage (INFO):"; oc -n {user}-stage logs "$STAGE_POD" | grep -c 'INFO  \[io\.quarkus'
echo "prod  (WARN):"; oc -n {user}-prod  logs "$PROD_POD"  | grep -c 'INFO  \[io\.quarkus'
----

Expect stage *well above zero* and prod at *zero, or close to it*; the shape is the lesson, not the number.

.Why one pod, and why match on the log level
[%collapsible]
====
A promoted environment can run more than one replica, and a selector-based `oc logs` reads every matching pod, which multiplies noise instead of isolating the one setting your two overlays actually change.
And instead of matching the literal string `io.quarkus` — which also matches inside a `WARN`/`ERROR` stack trace whose frames simply happen to run through Quarkus-internal classes — the command filters on the log *level* field itself, since that is the one thing `QUARKUS_LOG_LEVEL` controls.

Every `INFO`-level line in this app's own framework chatter is tagged with the literal category `io.quarkus` — the startup banner, the feature list, the access log — so this count is gated purely by whichever threshold `QUARKUS_LOG_LEVEL` set, on exactly one pod.
It cannot be swamped by a database-seeding race between replicas, because that race throws `WARN`/`ERROR`, a different level entirely.
(If the pod you picked happens to be one that lost the seeding race, you may still see the occasional stray `WARN`/`ERROR` line elsewhere in its log — that will not affect this count, because this grep only ever matches `INFO`-level lines.)
====

== 7. [OPTIONAL] Real secret management with External Secrets
⏱ *~5 min* · read / instructor-led — no hands-on on this cluster

A Kubernetes Secret is base64, not encryption, and it lives in the cluster; sooner or later Parasol's auditors ask where the production password *really* lives.

*You'll end with:* the pattern that keeps a credential's source of truth outside the cluster, with no change to the app.

[mermaid]
....
include::example$diagrams/config-multienv/12-external-secrets.mmd[]
....

Beyond a workshop, a credential's *source of truth* belongs in a secrets manager such as HashiCorp Vault, synced in by the *External Secrets Operator* (ESO), never copied by hand.
An `ExternalSecret` names the external key, and ESO produces an ordinary Secret your app consumes *unchanged*:

[source,yaml]
----
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: claims-creds
spec:
  refreshInterval: 1h
  secretStoreRef:              # points at a configured Vault / cloud store
    name: parasol-vault
    kind: SecretStore
  target:
    name: claims-creds         # the Secret the operator will create — same name your app uses
  data:
    - secretKey: POSTGRESQL_PASSWORD
      remoteRef:
        key: parasol/claims-db
        property: password
----

[IMPORTANT]
.This is a platform add-on, not installed here
====
A platform team installs ESO cluster-wide and wires it to the secrets manager; it is *not* on this cluster, so there are no hands-on steps (see your instructor's demo if one is scheduled).
Where the Secret comes from becomes a platform concern, not an application one.
====
