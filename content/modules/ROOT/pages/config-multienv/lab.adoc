In this lab you take the claims service from a fragile, hardcoded configuration to a properly externalized one, and then promote it across three environments.
You break the app with a bad setting and read the failure, move its configuration into a ConfigMap, move its credentials into a Secret, add health probes and watch a readiness gate hold traffic, set resource requests and bump into the namespace quota, and finally promote the *same image* to stage and prod with per-environment config.
Everything happens in your own namespaces — `{user}-dev`, `{user}-stage`, `{user}-prod` — so nothing you do can affect another attendee.

[TIP]
.Two ways to do most steps
====
Most steps below are offered two ways.
Use the *Console* tab for the graphical workflow in the {ocp_console_url}[OpenShift web console^] (sign in as `{user}`), or the *CLI* tab for `oc` in the *Terminal* tab beside these instructions — the two paths create the same objects.
Pick a path once: the tabs stay in sync across the page.
A few steps are CLI-only — promoting with Kustomize, delivering config as a mounted file, and reading a crash-looping pod's _previous_ logs — and say so where they appear.
The console click-paths follow the OpenShift web console; if a label reads slightly differently on your cluster, the `oc` command beside it is the source of truth.
====

== Demo arc — The readiness gate and one image in three environments (10–12 min)

[NOTE]
.Before you present
====
Run `adm solve config-multienv --user {user}` a few minutes ahead so the end state is up: the claims app fully configured in `{user}-dev`, and promoted to `{user}-stage` (2 replicas) and `{user}-prod` (3 replicas).
Have a terminal logged in as `{user}` and the web console *Topology* for `{user}-dev` open.
The command outputs below were captured from a live run; your pod names and image digests will differ.

*Check all three environments before you promise beat 4.* `adm solve` stands stage and prod up through
Argo, and each of them boots a Postgres of its own — so "the command returned" is not the same as
"the environment is up". Beat 4 prints one line per environment and has nothing to say if a line is
empty. Run this while you still have time to fix it:

[source,sh,role=execute,subs="attributes"]
----
for ns in {user}-dev {user}-stage {user}-prod; do
  printf "%-16s ready=%s\n" "$ns" \
    "$(oc -n $ns get deploy parasol-claims -o jsonpath='{.status.readyReplicas}' 2>/dev/null)"
done
----

*If it prints `1`, `2` and `3`*, beat 4 runs exactly as scripted.
*If a line comes back empty*, that environment is not serving yet — re-run the check a minute later,
and if it is still empty, run `adm solve config-multienv --user {user}` again and wait for all three.

terminal: that is the attendee's exercise, it costs minutes of dead air on stage, and the arc is

[demo-block]

Do:: Show the app is healthy and note the three probes it carries:

oc -n {user}-dev get deploy parasol-claims \
  -o jsonpath='{.spec.template.spec.containers[0].startupProbe.httpGet.path} {.spec.template.spec.containers[0].readinessProbe.httpGet.path} {.spec.template.spec.containers[0].livenessProbe.httpGet.path}{"\n"}'
----
+
"Three probes: started, ready, live. Watch what readiness does."

=== Beat 2 — Break readiness and the Route returns 503

[demo-block]
[TIME 4m]
Say:: "I'll break the readiness check — point it at a URL that doesn't exist — and roll it out. This is the failure the platform is built to contain."
Show:: The terminal, then the Topology node going out of rotation, then the Route returning 503.
Do:: Break readiness, roll the whole deployment onto the broken probe, and hit the Route.
The sampler in the middle is your talk track — while it prints, say: "the container is *up*; the
process is fine. What is failing is the platform's *question* — can you serve? Watch the READY
column, not STATUS."
+
[source,sh,role=execute,subs="attributes"]
----
oc -n {user}-dev set probe deploy/parasol-claims --readiness --get-url=http://:8080/q/health/typo
# scale to 0 then 1 so the only pod uses the broken readiness check
oc -n {user}-dev scale deploy/parasol-claims --replicas=0
# wait for the old pod to actually go, so exactly one pod is left and it is the broken-probe one
for i in $(seq 1 20); do [ "$(oc -n {user}-dev get pods -l app=parasol-claims --no-headers 2>/dev/null | wc -l | tr -d ' ')" = 0 ] && break; sleep 2; done
oc -n {user}-dev scale deploy/parasol-claims --replicas=1
# then sample the new pod instead of sleeping blind: it reaches Running in ~20-30s and then HOLDS at
# 0/1, because readiness never passes. The loop stops the moment the container reports started.
for i in $(seq 1 12); do
  oc -n {user}-dev get pods -l app=parasol-claims --no-headers
  oc -n {user}-dev get pods -l app=parasol-claims -o jsonpath='{.items[0].status.containerStatuses[0].started}' | grep -q true && break
  sleep 3
done
oc -n {user}-dev get endpoints parasol-claims
CLAIMS=$(oc -n {user}-dev get route parasol-claims -o jsonpath='{.spec.host}')
curl -s -o /dev/null -w "Route: %\{http_code}\n" http://$CLAIMS/api/claims
----
+
"No ready pods means no endpoints, and the Route returns 503. The platform is *holding* the request, not sending it to a broken pod. That's readiness doing its job."

=== Beat 3 — Fix it and the pod returns to rotation

[demo-block]
[TIME 2m]
Say:: "Now I fix it, and the platform puts the pod straight back into rotation."
Show:: The Route returning 200 again within seconds.
Do:: Restore the readiness path:
+
[source,sh,role=execute,subs="attributes"]
----
oc -n {user}-dev set probe deploy/parasol-claims --readiness --get-url=http://:8080/q/health/ready
oc -n {user}-dev rollout status deploy/parasol-claims
# re-derive the host rather than reusing $CLAIMS: a fresh terminal between beats would leave it
# empty, and `curl http:///api/claims` prints "Route: 000" — which reads exactly like a failed fix
CLAIMS=$(oc -n {user}-dev get route parasol-claims -o jsonpath='{.spec.host}')
curl -s -o /dev/null -w "Route: %\{http_code}\n" http://$CLAIMS/api/claims
----
+
"Green again. That whole cycle — drain, hold, recover — happened without anyone touching the load balancer."

=== Beat 4 — One image, three environments, config only

[demo-block]
[TIME 3m]
Say:: "Here's the other half: the same image, promoted across three environments with only configuration changing."
Show:: The terminal comparing dev, stage, and prod.
Do:: Show the identical image digest and the different per-environment config:
+
[source,sh,role=execute,subs="attributes"]
----
for ns in {user}-dev {user}-stage {user}-prod; do
  printf "%-16s replicas=%s  APP_ENV=%s  image=%s\n" "$ns" \
    "$(oc -n $ns get deploy parasol-claims -o jsonpath='{.status.readyReplicas}')" \
    "$(oc -n $ns get cm claims-config -o jsonpath='{.data.APP_ENV}')" \
    "$(oc -n $ns get pod -l app=parasol-claims -o jsonpath='{.items[0].status.containerStatuses[0].imageID}' | sed 's#.*@##' | cut -c1-19)"
done
----
+
"Same image digest in all three — the exact bytes we tested. Different replica counts and config per environment. Promotion here means applying config, not rebuilding."

[NOTE]
.If the three digests do not match
====
This is the one way beat 4 fails, and it fails on the exact sentence you just said out loud.
A differing digest is *not* a broken promotion — it is the *mutable-tag trap*: the shared
`parasol-claims:1.0` tag was rebuilt after some nodes had already cached the older image, and
`imagePullPolicy: IfNotPresent` let an earlier-scheduled pod keep the cached bytes.
Delete the odd pod out and the fresh pull converges the digests:

[source,sh,role=execute,subs="attributes"]
----
ODD={user}-stage        # the namespace whose digest differed; change it if it was another one
oc -n $ODD delete pod -l app=parasol-claims
oc -n $ODD rollout status deploy/parasol-claims
----

Then re-run the comparison block above.
Do not skip past it in silence — say the quiet part instead: "that is a *tag* being mutable, and it
is precisely why the supply-chain answer is to promote by *digest*, not by tag." The trap makes a
better ending than the clean run did.
====

== 1. Break the app with a bad setting — and read the failure
⏱ *~5 min* · the first deliberate break: a bad setting fails loudly and safely

Your claims service is running in `{user}-dev`, but it is configured the *naive* way: every setting, including the database password, is hardcoded inline in the Deployment.
See for yourself:

[source,sh,role=execute,subs="attributes"]
----
oc project {user}-dev
oc set env deploy/parasol-claims --list
----

.Expected output
[source,texinfo]
----
# deployments/parasol-claims, container parasol-claims
POSTGRESQL_HOST=claims-db
POSTGRESQL_PORT=5432
POSTGRESQL_DATABASE=parasol
POSTGRESQL_USER=parasol
POSTGRESQL_PASSWORD=parasol
----

Everything — including `POSTGRESQL_PASSWORD` — is sitting in plain text in the Deployment.
We will fix that.
But first, feel *why* configuration matters: change one setting to a bad value and watch what the platform does about it.

To *see* a bad setting the moment it lands, first give the platform a way to judge the app's health.
Add a *readiness probe* — the platform's "can this pod serve traffic *right now*?" check — pointed at the health endpoint the claims service already exposes.
Without one, the platform counts a container as ready the instant its process starts, even while it is seconds from crashing; with one, a pod that cannot serve is held out of rotation.
(You add the full set of probes — startup and liveness too — in exercise 4; this one readiness check is what makes the next failure visible.)

// Verified live OCP 4.22.5, 2026-07-28 as user1: at this module's entry state parasol-claims carries
// no probes at all (all three are gated behind `.Values.solve` in
// gitops/entry-states/config-multienv/templates/parasol-claims.yaml), so Actions offers "Add Health
// Checks" here — CLI 'oc set probe --readiness' beside it is authoritative.
[tabs]
====
Console::
+
--
. Go to *Workloads* → *Deployments* → `parasol-claims` → *Actions* → *Add Health Checks*.
. Add a *Readiness* probe — an *HTTP GET* on port `8080`, path `/q/health/ready` — and click *Save*.
--
CLI::
+
--
[source,sh,role=execute]
----
oc set probe deploy/parasol-claims --readiness \
  --get-url=http://:8080/q/health/ready --period-seconds=10 --failure-threshold=3
oc rollout status deploy/parasol-claims
----
--
====

The app is still healthy — one pod, `1/1` ready.
Now break it: point the datasource at a database host that does not exist.

// Verified live OCP 4.22.5, 2026-07-28 as user1: the Environment tab carries a "Single values (env)"
// section (Name/Value rows, "Add more" and "Add from ConfigMap or Secret") above a second section,
// "All values from existing ConfigMaps or Secrets (envFrom)" — CLI 'oc set env' beside it is authoritative.
[tabs]
====
Console::
+
--
. Go to *Workloads* → *Deployments* → `parasol-claims`, and open the *Environment* tab.
. Under *Single values (env)*, add a variable: name `QUARKUS_DATASOURCE_JDBC_URL`, value `jdbc:postgresql://wrong-db-host:5432/parasol`.
. Click *Save*.
The Deployment rolls out a new pod that picks up the bad datasource URL.
--
CLI::
+
--
[source,sh,role=execute]
----
oc set env deploy/parasol-claims \
  QUARKUS_DATASOURCE_JDBC_URL=jdbc:postgresql://wrong-db-host:5432/parasol
----
--
====

`QUARKUS_DATASOURCE_JDBC_URL` is the environment-variable form of the app's datasource URL, and it *overrides* the correct value the image ships with.
Because this is a rolling update — the same strategy you met in *Platform Orientation & First App* — the platform brings up a *new* pod alongside the old one and holds off retiring the old one until the new pod passes readiness.
It never will.
Look right away:

[source,sh,role=execute]
----
oc get pods -l app=parasol-claims
----

.Expected output (the broken pod is held at `0/1`; the old one still serves)
[source,texinfo]
----
NAME                              READY   STATUS             RESTARTS      AGE
parasol-claims-6764c459d6-dgmsm   1/1     Running            0             11m
parasol-claims-7874794948-pw8lr   0/1     CrashLoopBackOff   3 (19s ago)   2m20s
----

The new pod is `0/1` — *NotReady* — almost immediately: it cannot reach the database, so its readiness check never passes and the platform refuses to put it into service.
The old, healthy pod keeps running and keeps serving.
That is the readiness gate doing its job: a broken new version is *held back*, not shipped.
(Without the probe you just added, the platform would have swapped straight to the broken pod, which would have reported a reassuring `1/1 Running` for the better part of a minute before it finally started crash-looping — the failure would have been invisible exactly when you needed to see it.)

[NOTE]
.Watch the READY column, not STATUS
====
The `STATUS` column oscillates — `Running`, `Error`, `CrashLoopBackOff` — as the container boots, fails, and is restarted on a back-off timer.
Ignore it.
The honest signal is the `READY` column: it stays `0/1` the whole time, because the pod never once passes its readiness check.
====

The rollout is now stuck on that unready pod — confirm it, without waiting forever:

[source,sh,role=execute]
----
oc rollout status deploy/parasol-claims --timeout=15s
----

.Expected output
[source,texinfo]
----
Waiting for deployment "parasol-claims" rollout to finish: 1 old replicas are pending termination...
error: timed out waiting for the condition
----

And because the old pod is still in the Service, your users are unaffected — the Route keeps answering:

[source,sh,role=execute]
----
curl -s -o /dev/null -w "Route: %{http_code}\n" "http://$(oc get route parasol-claims -o jsonpath='{.spec.host}')/api/claims"
----

.Expected output
[source,texinfo]
----
Route: 200
----

Now do the thing this whole module is about: *read the logs.*
The broken pod is the *newest* one, so grab its name; then ask for its *previous* container's logs — that is usually where the crash is, because by the time you look, the container has often already been restarted onto a fresh attempt (targeting the newest pod also avoids the healthy old pod, which has no previous container to read):

// No --tail here, deliberately. It used to be --tail=40, which cut the payoff line out of its own
// expected output: on a measured run the crash log was 129 lines with "Failed to start application"
// at line 65, so the last 40 lines began well past it and the attendee saw only the trailing
// UnknownHostException. Widening the window is not the fix — the log's length depends on JVM startup
// verbosity and varies run to run, so ANY fixed number is a guess that silently truncates on the runs
// where it matters. grep already bounds what reaches the terminal, so searching the whole log costs
// nothing and always finds the cause. (Found by the config-multienv smoke, 2026-07-31.)
//
// The --previous | grep fallback below is a second fix from the same smoke: `oc logs --previous`
// against a fast-restarting CrashLoopBackOff container failed outright with "unable to retrieve
// container logs for cri-o://..." in 2 of 3 measured attempts, including once at literal lab pacing
// with only 1 restart — cri-o had already rotated the log the "previous" flag pointed at away by the
// time the command ran. This is a real race against container-log retention, not a one-off. Because
// grep against an empty/failed `oc logs` output exits non-zero (no lines matched), the `||` below
// reliably falls back to the CURRENT container's logs — which, since the pod is still crash-looping
// on the same root cause, show the identical UnknownHostException even when "previous" is gone.
[source,sh,role=execute]
----
BAD=$(oc get pods -l app=parasol-claims --sort-by=.metadata.creationTimestamp -o jsonpath='{.items[-1:].metadata.name}')
oc logs "$BAD" --previous 2>/dev/null | grep -A2 -iE 'Failed to start|UnknownHost' \
  || { echo "(previous container log already rotated away by cri-o — reading the current one, which is still crash-looping on the same cause)"; oc logs "$BAD" | grep -A2 -iE 'Failed to start|UnknownHost'; }
----

.Expected output
[source,texinfo]
----
ERROR [io.quarkus.runtime.Application] (main) Failed to start application: java.lang.RuntimeException: Failed to start quarkus
Caused by: org.hibernate.exception.JDBCConnectionException: Unable to open JDBC Connection for DDL execution [The connection attempt failed.]
Caused by: org.postgresql.util.PSQLException: The connection attempt failed.
Caused by: java.net.UnknownHostException: wrong-db-host
----

The root cause is right there at the bottom: `UnknownHostException: wrong-db-host`.
The app cannot resolve the database host you gave it.
The lesson is not the fix — it is the *habit*: when a pod will not start, the logs almost always tell you why in plain language, and the last `Caused by` is usually the real culprit.

== 2. Fix it the right way: move config into a ConfigMap
⏱ *~5 min* · externalize non-secret configuration

The quick fix is to remove the bad override:

[source,sh,role=execute]
----
oc set env deploy/parasol-claims QUARKUS_DATASOURCE_JDBC_URL-
oc rollout status deploy/parasol-claims
----

(The trailing `-` on a variable name *removes* it.)
Now the new pod can reach the database, passes its readiness check, and the rollout finally completes — the old pod steps aside.
But you have just proved the deeper problem: configuration is scattered inline in the Deployment, where it is easy to fat-finger and hard to manage.
Externalize it.
Create a *ConfigMap* — a named object that holds *non-secret* configuration — for the environment name, host, port, database name, and log level:

== 3. Move credentials into a Secret — and mount config as a file
⏱ *~7 min* · secret hygiene, and env vs mounted files

Look again at the last output: `POSTGRESQL_PASSWORD=parasol` is still sitting in plain text in the Deployment.
Anyone who can read the Deployment can read the password.
Move the credentials into a *Secret*, which is stored and access-controlled separately:

=== Mount config as a file (the other way to deliver it)

Environment variables are perfect for a handful of values, but they have downsides: they are visible in the process environment (and thus in crash dumps and some logs), and changing one means changing the Deployment.
The alternative is to deliver configuration as a *mounted file*.
Try it: put a small properties file in a ConfigMap and mount it into the container, then tell Quarkus to read it.

[source,sh,role=execute]
----
# a ConfigMap whose single key is a whole application.properties file
oc create configmap claims-file-config \
  --from-literal=application.properties=$'# delivered as a MOUNTED FILE\nquarkus.http.access-log.enabled=true\n'

# mount it read-only at /mnt/claims-config
oc set volume deploy/parasol-claims --add --name=file-config --type=configmap \
  --configmap-name=claims-file-config --mount-path=/mnt/claims-config --read-only=true

# point Quarkus at the mounted file (the documented quarkus.config.locations pattern)
oc set env deploy/parasol-claims QUARKUS_CONFIG_LOCATIONS=/mnt/claims-config/application.properties
oc rollout status deploy/parasol-claims
----

The property you put in that file — `quarkus.http.access-log.enabled=true` — turns on HTTP access logging, which nothing else sets.
So if you now see access-log lines, the mounted file was read.
Make a couple of requests and look:

[source,sh,role=execute,subs="attributes"]
----
CLAIMS=$(oc get route parasol-claims -o jsonpath='{.spec.host}')
curl -s -o /dev/null "http://$CLAIMS/api/claims"; curl -s -o /dev/null "http://$CLAIMS/api/claims"
oc logs -l app=parasol-claims --tail=20 | grep access-log
----

.Expected output
[source,texinfo]
----
... INFO  [io.quarkus.http.access-log] (executor-thread-1) 10.233.2.2 - - [09/Jul/2026:09:38:39 +0000] "GET /api/claims HTTP/1.1" 200 4798
----

That proves the mounted file was loaded.
For this app a few environment variables are simpler, so revert the mount and keep the env-based config for the rest of the lab:

[source,sh,role=execute]
----

----

(Leave the `claims-file-config` ConfigMap itself in place — unreferenced, it does no harm, and `ws reset` cleans it up.)

[NOTE]
.Env vs mounted file — when to use which
====
Reach for *environment variables* for a handful of discrete values.
Reach for a *mounted file* when you have a large or structured config (a whole properties/YAML file), when you want to rotate a value *without* editing the Deployment (update the ConfigMap/Secret and the file changes in place), or when you want to keep secrets *out* of the process environment.
Both are first-class; the choice is about size and rotation, not correctness.
====

// Grounded by the config-multienv smoke, 2026-07-31 (2 passes, both reproduced): the original version
// of this check compared `oc logs -l app=parasol-claims` (the WHOLE label selector — every replica's
// log concatenated) and counted the literal substring `io.quarkus`. On a live cluster that inverted:
// stage measured 16, prod measured 28. Two compounding causes, both structural, not flaky: (1) prod
// runs 3 replicas to stage's 2, and a selector-based `oc logs` fans out to every matching pod, so the
// comparison was already unfair before log level entered into it; (2) all replicas of a promoted
// environment race to run Hibernate's drop-and-create schema import against the SAME shared ephemeral
// Postgres on startup (see apps/parasol-claims/src/main/resources/application.properties — the seed
// reloads on every boot, by design, so labs get reproducible claim numbers), so every replica that
// loses that race throws `relation "claim_event" does not exist` — a DDL-visibility race where one
// replica's schema-create has not yet committed when another replica's import runs — a WARN, not an
// INFO — whose stack frames run through io.quarkus.hibernate.orm.runtime.* classes and so still match
// a blanket `io.quarkus` grep. More replicas means more of that spam, not less, which is why prod
// (3 replicas, WARN threshold) out-counted stage (2 replicas, INFO threshold) instead of the other way
// around. The fix below addresses both causes rather than papering over one: read a SINGLE named pod
// per environment (removes the replica-count multiplier), and filter on the log-LEVEL field itself
// rather than a package-name substring (removes the WARN-storm confound, since QUARKUS_LOG_LEVEL
// governs level, not which package logged the line). Re-measured live on a promoted environment,
// 2026-07-31: the corrected command read stage=3, prod=0 on 4 of 4 runs, confirming the lesson holds.
// Those exact counts are a build-banner artefact — they drift with the Quarkus version — so the
// checkpoint below states the shape of the comparison, not the numbers.
Compare a *single* pod in each environment, not the whole label selector — a promoted environment can run more than one replica, and a selector-based `oc logs` reads every matching pod, which multiplies noise instead of isolating the one setting your two overlays actually change.
And instead of matching the literal string `io.quarkus` — which also matches inside a `WARN`/`ERROR` stack trace whose frames simply happen to run through Quarkus-internal classes — filter on the log *level* field itself, since that is the one thing `QUARKUS_LOG_LEVEL` controls:

----
STAGE_POD=$(oc -n {user}-stage get pod -l app=parasol-claims -o jsonpath='{.items[0].metadata.name}')
PROD_POD=$(oc -n {user}-prod  get pod -l app=parasol-claims -o jsonpath='{.items[0].metadata.name}')
echo "stage (INFO):"; oc -n {user}-stage logs "$STAGE_POD" | grep -c 'INFO  \[io\.quarkus'
echo "prod  (WARN):"; oc -n {user}-prod  logs "$PROD_POD"  | grep -c 'INFO  \[io\.quarkus'
----

Every `INFO`-level line in this app's own framework chatter is tagged with the literal category `io.quarkus` — the startup banner, the feature list, the access log — so this count is now gated purely by whichever threshold `QUARKUS_LOG_LEVEL` set, on exactly one pod.
It cannot be swamped by a database-seeding race between replicas, because that race throws `WARN`/`ERROR`, a different level entirely, and by reading one pod instead of the whole selector you are no longer comparing three replicas' worth of noise against two.
Expect stage's count to be *comfortably greater than zero* (its `INFO` threshold lets its own startup chatter through) and prod's to be *zero, or very close to it* (its `WARN` threshold suppresses that same chatter) — the shape of the comparison is the lesson, not a specific number.
(If the pod you picked happens to be one that lost the seeding race, you may still see the occasional stray `WARN`/`ERROR` line elsewhere in its log — that will not affect this count, because this grep only ever matches `INFO`-level lines.)

== 7. [OPTIONAL] Real secret management with External Secrets
⏱ *~5 min* · read / instructor-led — no hands-on on this cluster

You saw it plainly: a Kubernetes Secret is base64, not encryption, and it lives in the cluster.
For anything beyond a workshop, the *source of truth* for a credential belongs in a dedicated secrets manager — HashiCorp Vault, or a cloud provider's secrets service — and should be *synced* into the cluster on demand, never copied by hand.

On OpenShift the tool for that is the *External Secrets Operator* (ESO).
You write a small `ExternalSecret` object that names a key in the external manager; the operator fetches it and produces an ordinary Kubernetes Secret that your app consumes *unchanged* — the app never knows the difference.
A minimal `ExternalSecret` looks like this:

[source,yaml]
----
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: claims-creds
spec:
  refreshInterval: 1h
  secretStoreRef:              # points at a configured Vault / cloud store
    name: parasol-vault
    kind: SecretStore
  target:
    name: claims-creds         # the Secret the operator will create — same name your app uses
  data:
    - secretKey: POSTGRESQL_PASSWORD
      remoteRef:
        key: parasol/claims-db
        property: password
----

[IMPORTANT]
.This is a platform add-on, not installed here
====
The External Secrets Operator is a cluster-wide operator that a platform team installs and wires to your secrets manager.
It is *not* installed on this workshop cluster, so there are no hands-on steps — treat this as the pattern to reach for in a real environment, and see your instructor's demo if one is scheduled.
The key idea to carry forward: your app keeps consuming a normal Secret; *where that Secret comes from* becomes a platform concern, not an application one.
====
