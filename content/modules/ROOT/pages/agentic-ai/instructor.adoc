== Timing (measured)

Total hands-on: *~97 min* (5 + 13 + 11 + 13 + 18 + 13 + 10 + 7 + 7). With the concept read, the
`[ADD-ON]` pointer and the wrap-up, budget *~2 h 10 min* for the module end to end. *That is longer
than one standard slot — read "Time-boxed delivery" below before you plan the session.*

[cols="3,1,4",options="header"]
|===
| Segment | Time | Notes

| Concept (agent anatomy, MCP, RAG, grounding, injection, the stack map) | ~20 min | ≤15-min core read; slides carry it, the `[ADD-ON]` stack map is discussion
| 1. Meet the running agent | ~5 min | `GET /agent/info` + readiness; no token spent
| 2. Engineer the grounding | ~13 min | The module's *write*-beat and its money moment: read the weak system prompt the agent shipped with, rewrite `cm/parasol-agent-grounding`, roll the agent onto it, re-ask
| 3. MCP tools are your APIs | ~11 min | Three claims tools + reading the tool schemas in the pod log
| 4. Ground answers with RAG | ~13 min | RAG citation, the assertion-versus-receipt distinction, `get_policy` on the cited document, a two-tool answer, the honest "not found"
| 5. Ship your own MCP tool server | ~18 min | *Longest, and gated on a cluster build (4–9 min, overlapped with the reading).* Read `PolicyTools.java`, build it in the attendee's own project, `oc new-app`, register with one env var, hand the agent back
| 6. Prompt injection | ~13 min | Make the agent state a figure no tool returned, watch the same payload fail differently by position, then build the non-model control
| 7. Score the grounding | ~10 min | A five-question set scored on two axes, run against the weak draft and the attendee's own prompt (2/5 → 5/5). *Temporarily reverts their work — see the watchout*
| 8. Observe the agent | ~7 min | Per-answer tokens/tool-calls + the GenAI Prometheus metrics and all three latency series
| 9. AI apps are apps | ~7 min | Deployment shape + the rollout-restart self-heal of the tool wiring
| The next platform layer (pointer) | ~1 min | `[ADD-ON]` — cut from a 5-minute recap to a pointer; the material is on the concept page and in the wrap-up
| Wrap-up + org mapping | ~10 min | Discussion + when-not-to-use
|===

Each `/agent/ask` call returns in *1–4 seconds* live at temperature 0; with the exception of exercise 5's build, the exercise times are dominated by reading and discussion, not the calls.

== Time-boxed delivery — what to drop, in order

This module now carries more hands-on time than a single 90-minute slot holds. Do not improvise the
cut on the day; decide it in advance, because two of the exercises leave state behind.

*The core path is exercises 1, 2, 3, 4, 6, 8, 9 — ~69 min hands-on*, and it is self-contained: it
still delivers the write-beat, the grounding payoff, the receipt distinction, the security beat and
the closing thesis.

Drop in this order:

. *Exercise 5 (−18 min)* — the largest single reclaim, and the only exercise with an environmental
dependency you cannot fix on stage (an in-cluster build cloning the Gitea mirror). If you drop it,
still spend two minutes on its *Anatomy of an MCP tool* reading with the room — the `@Tool`
annotation, and the fact that the description string is the only thing the model ever reads about
the method — because that is the idea the exercise exists to land.
. *Exercise 7 (−10 min)* — nothing downstream depends on it, and its artifact (`/tmp/eval-set.psv`
plus the thirty-line runner) is the one piece of this module attendees can genuinely take home and
run cold. Assigning it as homework loses less than dropping any other beat. *If you keep it, do not
let the room break in the middle of it* — see the watchout.
. *Exercise 9's second rollout (−3 min)* — by then the attendee has restarted this Deployment three
or four times. Keep the Deployment-shape half; skip the rollout-restart self-heal or narrate it.

Two further trims are *proposed but not applied* — they delete shipped material, so they need the
content owner rather than an instructor:

* *Exercise 3's pod-log block (−4 min)* — exercise 5 now reads the same log far more thoroughly, with
the full `search_policies` schema and a line-by-line Java-to-JSON table. If exercise 5 stays, the
exercise 3 block is a preview of it. (It carries a grounded screenshot, which is why this is a
content-owner call.)
* *The Challenge list* — three of its five items are now covered by exercises 4, 7 and 8. Trimming it
to *find the minimum viable grounding* and *design the guardrail* costs nothing, since it is optional
time, and stops it reading as a recap.

== How to know the room can move on

Two instruments tell you this without guessing, and neither is the clock. Each exercise ends on a `[.checkpoint]` block with a *✔ Verify:* line in the lab — that is the move-on signal, written for attendees to confirm before continuing. For the whole module, `ws verify agentic-ai --user <u>` is the same self-check the attendee can run any time; a room reporting all checks green is actually done, not just out of time.

== Pre-flight checklist

Run these from an admin context *before* the session. Each shows the expected output (domains shown as placeholders); the pod and `/agent/info` blocks are captures, the `ws verify` check lists are the checks the verify script runs.

*1. The environment materializes.* A fresh cluster (or a user who has never run this module) needs the entry state built before any check below will go green:

[source,sh,role=execute]
----
ws start agentic-ai --user user2
----

This is the same path `ws prep agentic-ai` runs — attendees trigger it themselves from the top of the *concept* page. `ws prep agentic-ai` waits up to *7 minutes* for the entry state to converge (the module's `waitSeconds: 420` sync window); it normally returns well inside that — the measured `ws reset` figure in the lifecycle table above (~90 s to converge) is the realistic one to expect, and the ceiling is a timeout, not a duration. Deliver the concept at its normal pace and it converges under you.

*2. The agent world is healthy.* Three pods Running and the MaaS copy hook Completed:

[source,sh,role=execute]
----
oc get pods -n user2-ai
----

[source,texinfo]
----
NAME                            READY   STATUS      RESTARTS   AGE
claims-db-...                   1/1     Running     0          ...
maas-copy-agentic-ai-user2-...         0/1     Completed   0          ...
parasol-agent-...               1/1     Running     0          ...
policy-docs-...                 1/1     Running     0          ...
----

*3. The agent answers and reports its wiring* (this is the URL attendees use; `/agent/info` spends no token):

[source,sh,role=execute]
----
curl -ksS "https://parasol-agent-user2-ai.apps.<cluster-domain>/agent/info"
# -> {"model":"<your MaaS model>","claimsDbMcpUrl":"http://claims-db:8080/mcp/sse",
#     "policyDocsMcpUrl":"http://policy-docs:8080/mcp/sse",
#      "groundingPromptSource":"config (parasol.agent.grounding-prompt)","groundingPrompt":"..."}
----

The same endpoint reports the *grounding* — `groundingPromptSource` and the live `groundingPrompt` — which is what exercise 2 is built on and what tells you, at a glance, whether a namespace is still at the entry state. It spends no token, so use it freely during the session.

*4. Each attendee's entry state is clean.* For a sample user:

[source,sh,role=execute]
----
ws verify agentic-ai --user user2 --entry-only
----

.The check list `ws verify … --entry-only` runs (from `tools/verify/agentic-ai.sh`)
[source,texinfo]
----
✅ namespace user2-ai exists
✅ entry marker ws-entry-agentic-ai present
✅ MaaS config carries the resolved model (configmap maas-config)
✅ MCP server claims-db deployed + ready
✅ MCP server policy-docs deployed + ready
✅ parasol-agent deployed + Ready (both MCP clients OK)
✅ grounding ConfigMap parasol-agent-grounding present
▶ agent model (maas-config): <your MaaS model> · credential source: <where the key came from>
✅ maas-credentials Secret staged
✅ staged GENAI_API_KEY is a plausible API key (present, not a JWT)
✅ MaaS endpoint accepted the staged credential (live probe at entry-state materialization)
✅ grounding is still the weak entry draft (attendee has not engineered it yet)
▶ entry state: the agent world is deployed and Ready above — no model call made, no token spent
✅ all 11 checks passed
----

The last check is the one to understand before you teach. The entry state ships a *deliberately weak* system prompt in `cm/parasol-agent-grounding` — one that never mentions tools — because rewriting it is exercise 2. If that check is red, this world has already been worked on (or solved): `ws reset agentic-ai --user <u>` puts the weak draft back. A user handed a world whose prompt is already strong never sees the module's money moment.

*5. The end state grades the attendee's own work* — and it is *token-free*, so it holds even if the MaaS key is having a bad morning. Run the full verify against a user who has not done the lab yet:

[source,sh,role=execute]
----
ws verify agentic-ai --user user2
# -> ❌ grounding prompt directs the model at its tools (your edit to cm/parasol-agent-grounding)
#    ❌ the running agent is still serving the OLD grounding — your ConfigMap edit has not reached the pod
#    -> ❌ 2 of 12 checks failed
----

*Those two reds are the module working, not a broken environment* — they are exactly what exercise 2 asks the attendee to turn green, and they are the negation of the entry check above. To see the green state for yourself, `ws solve agentic-ai --user user2` writes the strengthened prompt and rolls the agent onto it, and the same verify then reports `all 12 checks passed`. Put the world back with `ws prep agentic-ai --yes` before anyone sits down: a solved namespace hands the next attendee a finished lab.

[NOTE]
.The MaaS key is short-lived — plan for it
====
The agent's key is resolved and staged at materialization time — the workshop's own MaaS credential first, an adopted platform credential only as a fallback and only if it proves out against the endpoint — and workshop MaaS keys expire (they are provisioned per-event).
If `/agent/ask` starts returning `502` with `"authFailure": true`, the key expired: re-run `ws prep agentic-ai --yes` for the affected user (or ask the platform team to refresh the source key, then `ws reset agentic-ai --user <u>`).
*No graded check calls the model any more* — entry and end are both token-free — so a key that expired after the namespace was materialized leaves every check green and surfaces only in live `/agent/ask` and in the ⚠ corroboration line the full verify prints. Re-materialize after it expires and the credential checks go red instead, which is the honest signal. Either way, confirm a fresh key the morning of the session: verify no longer needs one, but every asking beat in the lab does.
====

*6. The per-cluster model is sourced on-cluster.* Confirm the model this cluster's key is scoped to:

[source,sh,role=execute]
----
oc get cm maas-config -n user2-ai -o jsonpath='{.data.model}{"\n"}'
# -> the model your cluster's MaaS key is scoped to (e.g. the cluster-specific model)
----

[NOTE]
.The model is converged per cluster — and why exercise 2 lands on any of them
====
The entry state *sources the model and endpoint from the credential it stages* at sync time, falling back to the chart default when those keys are absent — so one chart renders the right model on a cluster whose MaaS key is scoped to a *different* one, without a code change.

This is exactly why the module's write-beat is the *system prompt* and not a phrasing trick. Different models behave differently at temperature 0: asked the imperative question at the top of exercise 2 — the one that already says _"use your tools"_ — some print the tool call as *text* and never touch the data, while a more capable one calls the tool unaided. *Neither outcome changes what the attendee does next, or what is graded.* They read the prompt their agent shipped with, find that it never mentions tools, write one that does, and roll the pod onto it. If your model happened to ground it anyway, say so and use it — _"it worked despite what we had told it, not because of it"_ — then read the shipped prompt aloud and ask whether anyone would ship that to production. The lesson survives the model lottery because the artifact does.
====

*7. Exercise 5 can actually build.* This is the one exercise that depends on cluster facts beyond the agent, and all four are cheap to check. Run them the morning of the session:

oc auth can-i create builds.build.openshift.io/docker --as=user2 \

----

[source,texinfo]

NAME                         CREATED AT
limitrange/workshop-limits   ...
NAME                           REQUEST                                                          LIMIT                                             AGE
resourcequota/workshop-quota   ... requests.cpu: 450m/4, requests.memory: 768Mi/8Gi ...          limits.memory: 1792Mi/16Gi                        ...

Four things that check, and what a red one means:

* *The mirror is readable and current.* `git ls-remote` succeeding anonymously is what the in-cluster build's clone needs. Compare the SHA to origin's `main`; a stale mirror builds stale source. `ws git-refresh` re-syncs it.
* *The mirror's certificate is publicly trusted.* On this build cluster the Gitea route serves a wildcard from a public authority, so the build's clone trusts it with no extra wiring. *On a cluster whose ingress uses a self-signed certificate this is the step that breaks*, and it breaks inside the build pod where an attendee will not think to look — see the troubleshooting page.
* *An attendee may create a Docker-strategy build in their own project.* `can-i` is evidence and not proof (it cannot see admission webhooks), so if you have never run this module on this cluster, do exercise 5 once yourself as a real attendee identity before the session.
* *There is room for the build.* `{user}-ai` carries `limitrange/workshop-limits` with a *1Gi default memory limit* — which is exactly why the lab's `BuildConfig` states its own `resources:` rather than inheriting it, and why you should not let anyone "simplify" that block away. The quota shows a namespace using 450m/768Mi of 4 CPU / 8Gi, so the build pod (500m/1Gi requested) plus one more small JVM service fits with room.

== Demo-mode notes (beyond Say/Show/Do)

* *Confirm a live key first.* The whole demo is live model calls, and verify no longer needs one — so a green run does not prove the model will answer you. Run `ws verify agentic-ai --user {user}` a few minutes ahead and read the *credential* lines and the corroboration line at the bottom: a red credential check or a ⚠ corroboration means refresh the key before you present, not on stage.
* *Keep `jq` handy.* The `toolCalls` array is the star of the demo; pipe every call through `jq` so the audience sees *which* tool ran, not a wall of JSON.
* *Rehearse beat 1 — it is the money moment.* Ask the claim question, then `curl` `/agent/info` and read the shipped grounding *aloud* ("be helpful, be brief" — not one word about the six tools it is holding), patch the ConfigMap, `oc rollout restart`, and ask the *same* question again. Stage the strengthened prompt in `/tmp/grounding-prompt.yaml` beforehand (the lab's demo notes carry the file) so the beat is not a typing exercise, and rehearse it once: if your model grounds the first ask anyway, the line is "it worked despite what we told it," and the prompt you read aloud still lands the point.
* *Do not run `ws solve` before presenting.* Solve writes the strengthened prompt for you and rolls the agent — it takes beat 1 away. `ws prep agentic-ai --yes` is what you want, including between run-throughs: it puts the weak draft back.
* *Have Topology open in a second tab.* The closing line — "it's just a Deployment with a Route and probes" — needs the three-pod Topology on screen to land.
* *Guardrails are concept here.* The spec's demo arc mentions a guardrail block; on this cluster guardrails are the `[ADD-ON]` layer and are *not deployed*. Narrate them as "the next layer" — do not promise a live PII block you cannot show.

== Top 12 questions attendees ask

. *"Why did it print `[get_claim(...)]` instead of answering?"* +
The model *decided to describe* the tool call rather than *make* it — an ungrounded answer. The honest answer to "why" is that *nobody had told it to use its tools*: the system prompt the entry state ships describes a tone and never mentions the six tools the agent is holding. That is the whole of exercise 2 — rewrite `cm/parasol-agent-grounding` so it says there are tools and which question needs which, roll the Deployment, ask the same question again. Phrasing a question imperatively also nudges a model into calling a tool, but treat it as a probe rather than something to build on: it depends on every user and every integration remembering to say it, while the system prompt applies to every request. The lesson: *grounding is engineered*, and the thing you engineer is a piece of configuration.

. *"I fixed the prompt like the lab said — why doesn't it work when I just ask normally?"* +
Because the *wording* of a strengthened prompt is itself a variable, and the lab's printed sample happens to sit on the wrong side of it. Measured on `{maas_model}`, five runs per cell: the weak draft never grounds, plain or imperative; the printed sample grounds the imperative question and types the call out for the plain one; and a *rewording of those same instructions* grounds both. Same model, same question, same temperature — only the sentences differ. So the honest answer is not "phrasing is a second lever you still need", it is *"nobody can tell by reading, including us — that is why the lab ships a prompt with a measured weakness and invites you to beat it."* Point them at the optional block in exercise 2, which flips it in about three minutes. +
*Two things not to say.* Do not tell them their prompt is wrong — it may well be better than the printed one. And do not tell them the plain question is a coin flip; it is deterministic per prompt, and *which* way it lands is the unpredictable part.

. *"I wrote my own prompt and the plain question grounds — is the lab wrong?"* +
No, and this is the best outcome in the room — say so. They found the third row of the table for themselves. `ws verify` grades the *property* (does the prompt point the model at its tools), never the wording, so their prompt passes 12/12 exactly as the sample does. Use it: ask them to read their prompt and the printed sample aloud and have the room guess which one grounds a plain question. Nobody gets it reliably, which is the whole lesson — a system prompt is tested, not reviewed.

. *"Where does the agent keep the MaaS key, and is it safe?"* +
In a Secret (`maas-credentials`), injected as the `GENAI_API_KEY` environment value — the attendee never sees it, and `curl`-ing the agent never exposes it (the agent calls the model server-side). Endpoint and model are non-secret and live in the `maas-config` ConfigMap.

. *"Is this Llama Stack? Where's the vector database?"* +
No — the graded path is *Quarkus LangChain4j* calling the model directly, with *deterministic* keyword RAG. Llama Stack (a shared agent runtime) and a vector database (Milvus/pgvector) are the `[ADD-ON]` production layer, taught as concept. They slot in behind the same contracts the agent already uses.

. *"Can I see the trace for a request in Tempo?"* +
Not on this cluster — the OpenTelemetry *exporter is off* (there's no trace backend here), so spans stay in-process (you can see their ids as exemplars on the metrics). Turning on `QUARKUS_OTEL_SDK_DISABLED=false` plus an OTLP endpoint sends them to Tempo — that's the Observability tie, applied unchanged.

. *"All thirty attendees hit the same model endpoint — will it hold?"* +
Yes, at temperature 0 with short questions the calls are 1–4 s and cheap. The `inputTokens` are large because tool schemas travel with each request; that's the real cost signal to watch on the `gen_ai_client_token_usage_total` metric. Per-key quotas are an `[ADD-ON]` MaaS governance feature.

. *"Did we just hack the cluster?"* (exercise 6) +
No, and it is worth saying clearly because the room will be uneasy. Nothing in `claims-db`, the MCP server, or OpenShift was touched or compromised: `get_claim` ran against `CLM-1004` in *all nine* measured runs and returned the true record every time. The failure is entirely in what the model *said* about data it was correctly given. Point at the `toolCalls` line — nine clean lookups — and then at the answer. That gap is the lesson: an audit of tool calls would have shown nothing wrong.

. *"Wouldn't a better system prompt fix the injection?"* +
The prompt in force *already forbids it*. Have them re-read their own exercise-2 text (`curl -ksS $AGENT/agent/info | jq -r .groundingPrompt`) — it contains a hard constraint against fabricating claim data — and then look at the seven runs in nine that fabricated claim data. A sentence in the system prompt is a *request*, not a control. Then walk the list of controls that do work, and note that not one of them is a prompt.

. *"Does <some other model> resist this?"* +
Unknown, and unknowable without measuring — say exactly that. It may be better on the payload that landed here and *worse* on the one that did not; injection resistance is not a spec-sheet number and it is not inheritable from a vendor. The consequence for their org is the useful part: if a change of model can change your security posture, your security posture was never in the model.

. *"Can I leave the agent pointed at my own MCP server?"* (exercise 5) +
Not at the end of the exercise, and the reason is the readiness coupling they just proved: the agent's readiness probe pings whatever is registered, so an agent wired to *their* Deployment goes NotReady the moment their Deployment does — and `ws verify` would then red on "parasol-agent deployed + Ready" for a reason that has nothing to do with their work. The hand-back is a required step for that reason, not tidiness. Their `policy-docs-mine` keeps running and they can re-point at it whenever they like by re-running the same one-line `oc set env`, which is itself the lesson: registration is configuration in both directions.

. *"My question set scores 4/5 with my own prompt, but `ws verify` says 12/12 — which one is wrong?"* +
Neither, and this is the best question in exercise 7. `ws verify` grades a *property* — does this prompt point the model at its tools — and it must stay green for any correct prompt they write, so it cannot tell them whether their prompt *works*. The question set can, because it asks for facts the model could only get by calling something. A green grader and a 4/5 score together mean they have found the exact gap the beat exists for, on their own wording, before a customer did. Ask them which row failed and what they would change.

== Watchouts

* *Expired MaaS key.* The single most likely failure. Symptom: `/agent/ask` returns `502 authFailure`. It is *not* a lab bug — the key is short-lived. `ws prep agentic-ai --yes` re-copies a fresh key. Note that *no* check calls the model any more, entry or end, so a green `ws verify` is not evidence the key still works — the ⚠ corroboration line at the bottom of a full run is.
* *Model-dependent grounding — never hang the exercise on it.* The imperative question at the top of exercise 2 (_"Use your tools to look up claim CLM-1001 and report its status."_) prints the tool call as text on `{maas_model}` — measured, not a coin-toss — but a more eager model may ground the weak prompt unaided. Either way what is graded is the *ConfigMap the attendee wrote and the pod serving it*, not whether the model elected a tool call, so the exercise is unchanged. Do not promise the room that the first ask will fail; promise them the prompt is not good enough, and let them read it.
* *An attendee whose own prompt grounds the plain question.* Expected, correct, and the most valuable thing that can happen in exercise 2 — not a fluke and not a mis-grade. The wording of a strengthened prompt decides whether a plain question grounds, the lab's printed sample sits on the losing side of that (measured 5/5 each way on `{maas_model}`), and an attendee who writes their own is as likely to beat it as to match it. `ws verify` grades the property, not the sentences, so both pass 12/12. Run the optional block in exercise 2 with the room rather than explaining it away.
* *An edited ConfigMap that never reached the pod.* The prompt arrives as an environment variable, and an environment variable cannot change under a running pod — so an attendee who patches `cm/parasol-agent-grounding` and skips `oc rollout restart deploy/parasol-agent` still has an agent running the weak draft. This is the module's most common stuck point, it is deliberately part of the exercise, and both the lab and `ws verify` name it out loud ("the running agent is still serving the OLD grounding"). The one-line diagnosis is `curl -ksS $AGENT/agent/info | jq -r .groundingPrompt`.
* *`toolCalls[].result` is `null`.* This is expected — the agent records the tool *name and arguments* (the visibility that matters); the result is folded into the answer. Attendees sometimes read `null` as "the tool failed." The *answer* is the proof the tool ran.
* *ImagePullBackOff on a fresh cluster.* The three images are pulled from the shared `ogsr-parasol-images` registry; on a cold cluster the first pull can be slow. The pods become Ready once pulled — `ws reset` waits for it. If it never clears, the shared images aren't loaded — a provisioning gap, not a lab error.
* *The entry app should show "Synced/Healthy."* An older chart left `maas-config` permanently OutOfSync after the MaaS copy hook patched it; that was fixed upstream (the chart no longer renders values into that ConfigMap, so there's nothing left to diverge from). If you see OutOfSync on this entry app now, treat it as a real drift signal — do not wave it off as the old cosmetic case.
* *The agent is not Ready (`/q/health/ready` is DOWN).* Pre-flight step 2 above is exactly this check — the agent's readiness probe pings both MCP servers, so a Ready agent has already proven its tool wiring. If either `claims-db` or `policy-docs` is not `1/1`, the agent stays deliberately not-Ready rather than take traffic it can't serve; fix the tool server first (describe the pod, or `ws reset agentic-ai --user <u>` to re-materialize) and the agent's readiness flips to `UP` on its own.
* *Exercise 7 leaves the module temporarily red — do not let the room break in the middle of it.* Scoring the baseline means putting the *weak* draft back and rolling the agent onto it, so for those two or three minutes `ws verify agentic-ai` correctly reports the *entry* state and the attendee's work is not in force. The lab says so in place, and the very next step restores their own prompt from a snapshot they took. If the room breaks mid-exercise, send them back to the restore step first; an attendee who leaves for coffee at the baseline table and comes back to a red verify will believe they broke something.
* *Exercise 6 is meaningless against the weak entry draft.* The whole beat depends on the agent actually calling tools, which it does not do until exercise 2 is done and rolled out. If an attendee's first injection block returns a typed-out `[get_claim(...)]` with an empty `toolCalls`, they skipped or half-finished exercise 2 — check `/agent/info`, not the payload.
* *Exercise 6's outcome is not stable, and that instability is the content.* Measured on `{maas_model}`: 7 runs in 9 opened with the fabricated figure, 2 broke off into a typed-out tool call and never answered, 0 answered correctly. Both are failures and the checkpoint accepts either. *Never promise the room a specific sentence*, and if an attendee gets a clean answer, have them send it again rather than treating it as a pass.
* *Exercise 5's hand-back is a required step, not tidiness.* An attendee who registers `policy-docs-mine` and stops there has an agent whose readiness now depends on their own Deployment. It works — until it does not, and then `ws verify` reds on "parasol-agent deployed + Ready" for a reason that has nothing to do with their work. The optional break-and-fix in that exercise sits *after* the hand-back and restores the shipped URL on purpose, so no path through the exercise ends anywhere but the graded end state. If someone is red on that check, `curl -ksS $AGENT/agent/info | jq -r .policyDocsMcpUrl` is the one-line diagnosis.
* *`langchain4j_aiservices_timed_seconds_max` reading `0.0` is not a broken metric.* It is a *rolling window*, so an agent idle for a couple of minutes reports `0.0` while `_count` still shows every call it ever served (observed four times on the live agent). Tell them to ask a question and read the metric straight after. The mean — `_sum / _count` — has no such window and is the number to quote.
* *`ws smoke` fails only on "cockpit clone HEAD matches the mirror."* If `ws smoke agentic-ai <u>` reports 11/12 with only the freshness check failing, the attendee's cockpit pod is serving a Git clone from before the latest content push — a stale cockpit, not a module defect. `ws git-refresh --restart-terminals --user <u>` re-clones it to the mirror HEAD; every other check (identity, isolation, `ws prep`/`verify`, the `oc auth can-i` smoke command) passes independently of this one.

== Provenance

Agentic AI on OpenShift is a *net-new* module — no content ported from stale material. Everything it teaches was *performed* against the live `parasol-agent` in a `{user}-ai` namespace on the build cluster (OpenShift 4.21.22), driving the model `{maas_model}` over the shared MaaS endpoint: the agent's tool calls (`get_claim` against the `claims-db` MCP server, and the `policy-docs` MCP reads), the grounded-fact checkpoints, and the deliberate temperature-0 break-and-fix. Expected-output blocks show *representative* JSON — the model value is genericized to `<maas-model>` (model-agnostic), and namespace/domain are placeholders (yours are `{user}-ai` / `{cluster_domain}`); what the checkpoints verify is the grounded facts and the `toolCalls`, not byte-exact model prose.

*Exercises 5, 6 and 7 are newer still (2026-08-07), and their provenance differs — read this before you teach them.*

* *Exercise 6 (prompt injection) is fully measured.* Every output block in it was captured against the live agent in a `{user}-ai` namespace at temperature 0, with the strengthened grounding in force: 9 runs of the unframed payload (7 fabricated the figure, 2 degraded, 0 correct), 5 of the record-framed payload (2 correct, 3 degraded, 0 fabricated), and 5 of the id-shaped payload (5 correct "not found", with the payload confirmed present in the model's message list as a `role: tool` entry). Nothing in that exercise is composed.
* *Exercise 7 (scoring) is fully measured*, as an A/B/A on one agent with the question set and model held constant and only the ConfigMap moving: sample prompt 5/5 → weak draft 2/5 → reworded prompt 5/5 → sample 5/5, with the namespace restored to the state it was found in and re-scored to prove the restore. The two tables on the page are that runner's own stdout.
* *Exercise 5 (ship your own MCP tool server) is the exception, and it is flagged in place.* The Java, the captured tool schema, the `role: tool` message and the startup banner are all real — read from the source at a known commit and captured from a live agent and a live `policy-docs` pod — and the 6 m 00 s build figure is `status.duration` on the identical source and `Containerfile` built on this cluster. But the attendee's *own* build, deploy, registration, hand-back and the optional break-and-fix were **not** performed: the lane that wrote it and the lane that spliced it were both read-only on the cluster. Those seven commands carry verify-on-cluster markers in the page source and *must* be performed before this exercise is taught cold. Nothing in the prose is presented as a capture that is not one — where a shape is predicted rather than measured, it says so.
* *The exercise-4 `get_policy` step was performed* (3 runs, identical): on `{maas_model}` the model chooses `get_policy` rather than `search_policies`, passes `{"policyId": "POL-AUTO-01"}`, and *relays the document in its own words* rather than pasting it. The lab's captured block and its "the model relayed it" sentence are that measurement.
* *The latency series in exercise 8 were measured on the live agent*, including the finding that `langchain4j_aiservices_timed_seconds_max` is a rolling window that reads `0.0` on an idle agent — observed four times, and corroborated by `_max` equalling the `_sum` delta exactly when one call sat in the window.

Exercise 2's *grounding* beat is newer than the original run and is scoped honestly: the agent's system prompt was moved out of the image into `cm/parasol-agent-grounding`, the entry state now ships a deliberately weak first draft, and the graded outcome became the prompt the attendee writes plus the pod serving it — both read without spending a token. What these pages claim is scoped to what was measured: on `{maas_model}`, the weak entry draft never grounds — plain or imperative — the lab's *printed sample* grounds only when the question is imperative too, and a *rewording of that sample's own instructions* grounds both phrasings. The third of those was measured on 2026-08-07 as an A/B/A on a single agent (plain question throughout, only the system prompt moving: sample → reworded → sample, 5/5 identical per cell), and it falsified an earlier version of this page that stated the second finding as a property of strengthened prompts in general. The lab's authoring note records both measurements and why the sample stays the printed one. A more capable model remains free to ground the weak draft unaided, which would not change what the attendee does next.
