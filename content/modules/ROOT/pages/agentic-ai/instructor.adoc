== Timing (measured)

Total hands-on: *~54 min* (5 + 13 + 11 + 11 + 7 + 7). Exercise timings are from a live run driving the
agent — except exercise 2, re-budgeted when grounding became the module's write-beat (see the note
below); the `ws` lifecycle numbers are measured on the workshop cluster against the `{maas_model}` MaaS endpoint.

[cols="3,1,4",options="header"]
|===
| Segment | Time | Notes

| Concept (agent anatomy, MCP, RAG, grounding, the stack map) | ~20 min | ≤15-min core read; slides carry it, the `[ADD-ON]` stack map is discussion
| 1. Meet the running agent | ~5 min | `GET /agent/info` + readiness; no token spent
| 2. Engineer the grounding | ~13 min | The module's *write*-beat and its money moment: read the weak system prompt the agent shipped with, rewrite `cm/parasol-agent-grounding`, roll the agent onto it, re-ask
| 3. MCP tools are your APIs | ~11 min | Three claims tools + reading the tool schemas in the pod log
| 4. Ground answers with RAG | ~11 min | RAG citation, a two-tool answer, and the honest "not found"
| 5. Observe the agent | ~7 min | Per-answer tokens/tool-calls + the GenAI Prometheus metrics
| 6. AI apps are apps | ~7 min | Deployment shape + the rollout-restart self-heal of the tool wiring
| The next platform layer (reading) | ~5 min | `[ADD-ON]` — guardrails, Llama Stack, vector DB; no hands-on
| Wrap-up + org mapping | ~10 min | Discussion + when-not-to-use
|===

Each `/agent/ask` call returns in *1–4 seconds* live at temperature 0; the exercise times are dominated by reading and discussion, not the calls.

== How to know the room can move on

Two instruments tell you this without guessing, and neither is the clock. Each exercise ends on a `[.checkpoint]` block with a *✔ Verify:* line in the lab — that is the move-on signal, written for attendees to confirm before continuing. For the whole module, `ws verify agentic-ai --user <u>` is the same self-check the attendee can run any time; a room reporting all checks green is actually done, not just out of time.

== Pre-flight checklist

Run these from an admin context *before* the session. Each shows the expected output (domains shown as placeholders); the pod and `/agent/info` blocks are captures, the `ws verify` check lists are the checks the verify script runs.

*1. The environment materializes.* A fresh cluster (or a user who has never run this module) needs the entry state built before any check below will go green:

[source,sh,role=execute]
----
ws start agentic-ai --user user2
----

This is the same path `ws prep agentic-ai` runs — attendees trigger it themselves from the top of the *concept* page. `ws prep agentic-ai` waits up to *7 minutes* for the entry state to converge (the module's `waitSeconds: 420` sync window); it normally returns well inside that — the measured `ws reset` figure in the lifecycle table above (~90 s to converge) is the realistic one to expect, and the ceiling is a timeout, not a duration. Deliver the concept at its normal pace and it converges under you.

*2. The agent world is healthy.* Three pods Running and the MaaS copy hook Completed:

[source,sh,role=execute]
----
oc get pods -n user2-ai
----

[source,texinfo]
----
NAME                            READY   STATUS      RESTARTS   AGE
claims-db-...                   1/1     Running     0          ...
maas-copy-agentic-ai-user2-...         0/1     Completed   0          ...
parasol-agent-...               1/1     Running     0          ...
policy-docs-...                 1/1     Running     0          ...
----

*3. The agent answers and reports its wiring* (this is the URL attendees use; `/agent/info` spends no token):

[source,sh,role=execute]
----
curl -ksS "https://parasol-agent-user2-ai.apps.<cluster-domain>/agent/info"
# -> {"model":"<your MaaS model>","claimsDbMcpUrl":"http://claims-db:8080/mcp/sse",
#     "policyDocsMcpUrl":"http://policy-docs:8080/mcp/sse",
#      "groundingPromptSource":"config (parasol.agent.grounding-prompt)","groundingPrompt":"..."}
----

The same endpoint reports the *grounding* — `groundingPromptSource` and the live `groundingPrompt` — which is what exercise 2 is built on and what tells you, at a glance, whether a namespace is still at the entry state. It spends no token, so use it freely during the session.

*4. Each attendee's entry state is clean.* For a sample user:

[source,sh,role=execute]
----
ws verify agentic-ai --user user2 --entry-only
----

.The check list `ws verify … --entry-only` runs (from `tools/verify/agentic-ai.sh`)
[source,texinfo]
----
✅ namespace user2-ai exists
✅ entry marker ws-entry-agentic-ai present
✅ MaaS config carries the resolved model (configmap maas-config)
✅ MCP server claims-db deployed + ready
✅ MCP server policy-docs deployed + ready
✅ parasol-agent deployed + Ready (both MCP clients OK)
✅ grounding ConfigMap parasol-agent-grounding present
▶ agent model (maas-config): <your MaaS model> · credential source: <where the key came from>
✅ maas-credentials Secret staged
✅ staged GENAI_API_KEY is a plausible API key (present, not a JWT)
✅ MaaS endpoint accepted the staged credential (live probe at entry-state materialization)
✅ grounding is still the weak entry draft (attendee has not engineered it yet)
▶ entry state: the agent world is deployed and Ready above — no model call made, no token spent
✅ all 11 checks passed
----

The last check is the one to understand before you teach. The entry state ships a *deliberately weak* system prompt in `cm/parasol-agent-grounding` — one that never mentions tools — because rewriting it is exercise 2. If that check is red, this world has already been worked on (or solved): `ws reset agentic-ai --user <u>` puts the weak draft back. A user handed a world whose prompt is already strong never sees the module's money moment.

*5. The end state grades the attendee's own work* — and it is *token-free*, so it holds even if the MaaS key is having a bad morning. Run the full verify against a user who has not done the lab yet:

[source,sh,role=execute]
----
ws verify agentic-ai --user user2
# -> ❌ grounding prompt directs the model at its tools (your edit to cm/parasol-agent-grounding)
#    ❌ the running agent is still serving the OLD grounding — your ConfigMap edit has not reached the pod
#    -> ❌ 2 of 12 checks failed
----

*Those two reds are the module working, not a broken environment* — they are exactly what exercise 2 asks the attendee to turn green, and they are the negation of the entry check above. To see the green state for yourself, `ws solve agentic-ai --user user2` writes the strengthened prompt and rolls the agent onto it, and the same verify then reports `all 12 checks passed`. Put the world back with `ws prep agentic-ai --yes` before anyone sits down: a solved namespace hands the next attendee a finished lab.

[NOTE]
.The MaaS key is short-lived — plan for it
====
The agent's key is resolved and staged at materialization time — the workshop's own MaaS credential first, an adopted platform credential only as a fallback and only if it proves out against the endpoint — and workshop MaaS keys expire (they are provisioned per-event).
If `/agent/ask` starts returning `502` with `"authFailure": true`, the key expired: re-run `ws prep agentic-ai --yes` for the affected user (or ask the platform team to refresh the source key, then `ws reset agentic-ai --user <u>`).
*No graded check calls the model any more* — entry and end are both token-free — so a key that expired after the namespace was materialized leaves every check green and surfaces only in live `/agent/ask` and in the ⚠ corroboration line the full verify prints. Re-materialize after it expires and the credential checks go red instead, which is the honest signal. Either way, confirm a fresh key the morning of the session: verify no longer needs one, but every asking beat in the lab does.
====

*6. The per-cluster model is sourced on-cluster.* Confirm the model this cluster's key is scoped to:

[source,sh,role=execute]
----
oc get cm maas-config -n user2-ai -o jsonpath='{.data.model}{"\n"}'
# -> the model your cluster's MaaS key is scoped to (e.g. the cluster-specific model)
----

[NOTE]
.The model is converged per cluster — and why exercise 2 lands on any of them
====
The entry state *sources the model and endpoint from the credential it stages* at sync time, falling back to the chart default when those keys are absent — so one chart renders the right model on a cluster whose MaaS key is scoped to a *different* one, without a code change.

This is exactly why the module's write-beat is the *system prompt* and not a phrasing trick. Different models behave differently at temperature 0: asked the plain question in exercise 2, some print the tool call as *text* and never touch the data, while a more capable one calls the tool unaided. *Neither outcome changes what the attendee does next, or what is graded.* They read the prompt their agent shipped with, find that it never mentions tools, write one that does, and roll the pod onto it. If your model happened to ground the plain question anyway, say so and use it — _"it worked despite what we had told it, not because of it"_ — then read the shipped prompt aloud and ask whether anyone would ship that to production. The lesson survives the model lottery because the artifact does.
====

== Demo-mode notes (beyond Say/Show/Do)

* *Confirm a live key first.* The whole demo is live model calls, and verify no longer needs one — so a green run does not prove the model will answer you. Run `ws verify agentic-ai --user {user}` a few minutes ahead and read the *credential* lines and the corroboration line at the bottom: a red credential check or a ⚠ corroboration means refresh the key before you present, not on stage.
* *Keep `jq` handy.* The `toolCalls` array is the star of the demo; pipe every call through `jq` so the audience sees *which* tool ran, not a wall of JSON.
* *Rehearse beat 1 — it is the money moment.* Ask the claim question, then `curl` `/agent/info` and read the shipped grounding *aloud* ("be helpful, be brief" — not one word about the four tools it is holding), patch the ConfigMap, `oc rollout restart`, and ask the *same* question again. Stage the strengthened prompt in `/tmp/grounding-prompt.yaml` beforehand (the lab's demo notes carry the file) so the beat is not a typing exercise, and rehearse it once: if your model grounds the first ask anyway, the line is "it worked despite what we told it," and the prompt you read aloud still lands the point.
* *Do not run `ws solve` before presenting.* Solve writes the strengthened prompt for you and rolls the agent — it takes beat 1 away. `ws prep agentic-ai --yes` is what you want, including between run-throughs: it puts the weak draft back.
* *Have Topology open in a second tab.* The closing line — "it's just a Deployment with a Route and probes" — needs the three-pod Topology on screen to land.
* *Guardrails are concept here.* The spec's demo arc mentions a guardrail block; on this cluster guardrails are the `[ADD-ON]` layer and are *not deployed*. Narrate them as "the next layer" — do not promise a live PII block you cannot show.

== Top 5 questions attendees ask

. *"Why did it print `[get_claim(...)]` instead of answering?"* +
The model *decided to describe* the tool call rather than *make* it — an ungrounded answer. The honest answer to "why" is that *nobody had told it to use its tools*: the system prompt the entry state ships describes a tone and never mentions the four tools the agent is holding. That is the whole of exercise 2 — rewrite `cm/parasol-agent-grounding` so it says there are tools and which question needs which, roll the Deployment, ask the same question again. Phrasing a question imperatively also nudges a model into calling a tool, but it is the weaker lever: it depends on every user and every integration remembering to say it, while the system prompt applies to every request. The lesson: *grounding is engineered*, and the thing you engineer is a piece of configuration.

. *"Where does the agent keep the MaaS key, and is it safe?"* +
In a Secret (`maas-credentials`), injected as the `GENAI_API_KEY` environment value — the attendee never sees it, and `curl`-ing the agent never exposes it (the agent calls the model server-side). Endpoint and model are non-secret and live in the `maas-config` ConfigMap.

. *"Is this Llama Stack? Where's the vector database?"* +
No — the graded path is *Quarkus LangChain4j* calling the model directly, with *deterministic* keyword RAG. Llama Stack (a shared agent runtime) and a vector database (Milvus/pgvector) are the `[ADD-ON]` production layer, taught as concept. They slot in behind the same contracts the agent already uses.

. *"Can I see the trace for a request in Tempo?"* +
Not on this cluster — the OpenTelemetry *exporter is off* (there's no trace backend here), so spans stay in-process (you can see their ids as exemplars on the metrics). Turning on `QUARKUS_OTEL_SDK_DISABLED=false` plus an OTLP endpoint sends them to Tempo — that's the Observability tie, applied unchanged.

. *"All thirty attendees hit the same model endpoint — will it hold?"* +
Yes, at temperature 0 with short questions the calls are 1–4 s and cheap. The `inputTokens` are large because tool schemas travel with each request; that's the real cost signal to watch on the `gen_ai_client_token_usage_total` metric. Per-key quotas are an `[ADD-ON]` MaaS governance feature.

== Watchouts

* *Expired MaaS key.* The single most likely failure. Symptom: `/agent/ask` returns `502 authFailure`. It is *not* a lab bug — the key is short-lived. `ws prep agentic-ai --yes` re-copies a fresh key. Note that *no* check calls the model any more, entry or end, so a green `ws verify` is not evidence the key still works — the ⚠ corroboration line at the bottom of a full run is.
* *Model-dependent grounding — never hang the exercise on it.* The plain question at the top of exercise 2 prints the tool call as text on one model and grounds unaided on another. The lab is written so *both* outcomes lead to the same place, and what is graded is the *ConfigMap the attendee wrote and the pod serving it* — not whether the model elected a tool call. Do not promise the room that the first ask will fail; promise them the prompt is not good enough, and let them read it.
* *An edited ConfigMap that never reached the pod.* The prompt arrives as an environment variable, and an environment variable cannot change under a running pod — so an attendee who patches `cm/parasol-agent-grounding` and skips `oc rollout restart deploy/parasol-agent` still has an agent running the weak draft. This is the module's most common stuck point, it is deliberately part of the exercise, and both the lab and `ws verify` name it out loud ("the running agent is still serving the OLD grounding"). The one-line diagnosis is `curl -ksS $AGENT/agent/info | jq -r .groundingPrompt`.
* *`toolCalls[].result` is `null`.* This is expected — the agent records the tool *name and arguments* (the visibility that matters); the result is folded into the answer. Attendees sometimes read `null` as "the tool failed." The *answer* is the proof the tool ran.
* *ImagePullBackOff on a fresh cluster.* The three images are pulled from the shared `ogsr-parasol-images` registry; on a cold cluster the first pull can be slow. The pods become Ready once pulled — `ws reset` waits for it. If it never clears, the shared images aren't loaded — a provisioning gap, not a lab error.
* *The entry app should show "Synced/Healthy."* An older chart left `maas-config` permanently OutOfSync after the MaaS copy hook patched it; that was fixed upstream (the chart no longer renders values into that ConfigMap, so there's nothing left to diverge from). If you see OutOfSync on this entry app now, treat it as a real drift signal — do not wave it off as the old cosmetic case.
* *The agent is not Ready (`/q/health/ready` is DOWN).* Pre-flight step 2 above is exactly this check — the agent's readiness probe pings both MCP servers, so a Ready agent has already proven its tool wiring. If either `claims-db` or `policy-docs` is not `1/1`, the agent stays deliberately not-Ready rather than take traffic it can't serve; fix the tool server first (describe the pod, or `ws reset agentic-ai --user <u>` to re-materialize) and the agent's readiness flips to `UP` on its own.
* *`ws smoke` fails only on "cockpit clone HEAD matches the mirror."* If `ws smoke agentic-ai <u>` reports 11/12 with only the freshness check failing, the attendee's cockpit pod is serving a Git clone from before the latest content push — a stale cockpit, not a module defect. `ws git-refresh --restart-terminals --user <u>` re-clones it to the mirror HEAD; every other check (identity, isolation, `ws prep`/`verify`, the `oc auth can-i` smoke command) passes independently of this one.

== Provenance

Agentic AI on OpenShift is a *net-new* module — no content ported from stale material. Everything it teaches was *performed* against the live `parasol-agent` in a `{user}-ai` namespace on the build cluster (OpenShift 4.21.22), driving the model `{maas_model}` over the shared MaaS endpoint: the agent's tool calls (`get_claim` against the `claims-db` MCP server, and the `policy-docs` MCP reads), the grounded-fact checkpoints, and the deliberate temperature-0 break-and-fix. Expected-output blocks show *representative* JSON — the model value is genericized to `<maas-model>` (model-agnostic), and namespace/domain are placeholders (yours are `{user}-ai` / `{cluster_domain}`); what the checkpoints verify is the grounded facts and the `toolCalls`, not byte-exact model prose.

Exercise 2's *grounding* beat is newer than that run and is scoped honestly: the agent's system prompt was moved out of the image into `cm/parasol-agent-grounding`, the entry state now ships a deliberately weak first draft, and the graded outcome became the prompt the attendee writes plus the pod serving it — both read without spending a token. What is deliberately *not* claimed anywhere on these pages is that the weak draft fails on any particular model; that has not been measured, the lab documents both outcomes on the same plain question, and neither one changes what the attendee does.
