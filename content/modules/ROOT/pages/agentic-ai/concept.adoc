Parasol's support staff keep asking the same two questions all day: _"what's the status of this claim?"_ and _"what does our policy say about this?"_
A large language model on its own can talk fluently about insurance and be *confidently wrong* about *your* claims — it has never seen claim `CLM-1004`, and it will happily invent a plausible answer.
This module builds the honest version: an *agent* that answers those questions by *calling your systems as tools* and *grounding* itself in your policy documents — and ships on OpenShift with the exact same probes, metrics, and delivery path as every other Parasol service, because *an AI app is just an app*.

== What you'll learn

* The *anatomy of an agent* — model plus instructions plus *tools* plus memory — and why the tools, not the model, are where the real answers come from.
* Why *MCP tools are your APIs*: the *Model Context Protocol* (MCP) lets a model call your claims database and your policy search as ordinary services, so the agent reads *live* data instead of hallucinating it. In the lab you *build one* — the same tool server, compiled from source in your own project and registered with one environment variable.
* *Retrieval-Augmented Generation* (RAG) *honestly* — how grounding an answer in retrieved policy passages works, when it helps, and how it fails. Including the part most demos skip: a *citation is an assertion* the model made, and a *tool call is the receipt*.
* That *grounding is engineered, not guaranteed* — the model *decides* whether to call a tool, and the instruction that sways that decision is a *system prompt you write*, shipped as ordinary configuration. In the lab you write it.
* That *everything the agent reads is input* — free text from a claim can carry an instruction, and *prompt injection* is what decides whether an agent goes near a real claims queue. You make it happen, and then build the control that catches it, which is not a prompt.
* How you would *know if it got worse* — a fixed question set, scored on whether a tool ran and whether the grounded facts came back, small enough to write in a lab and to run in a pipeline.
* Where *guardrails*, a *Llama Stack* agent runtime, and a production *vector database* fit — the `[ADD-ON]` platform layer above the graded path — and *when* to reach for each.
* The thesis that ties the whole week together: *the same platform disciplines apply* — health, config, metrics, tracing, and the golden path are identical for an AI app.

== Why not just ask the model?

The tempting move is to send the question straight to a model: _"What is the status of claim CLM-1004?"_
It fails for reasons that are *structural*, not cosmetic — and each one is why an *agent* exists:

* *The model has never seen your data.* Claim `CLM-1004` lives in Parasol's claims system, not in the model's training set. Asked directly, the model *guesses* — it produces a fluent, plausible, *wrong* status. This is *hallucination*, and for a claim, a policy, or a payout it is worse than useless.
* *Your data changes; the model is frozen.* Even if a claim were somehow in the training data, it was `Submitted` last week and `Approved` today. A model is a snapshot; your systems are live. Answers about live state must come from *live systems*.
* *"Just paste it into the prompt" does not scale.* You could stuff all thirty claims and eight policies into every prompt, but real Parasol has millions of claims and thousands of documents. You cannot prompt-stuff a database. You need the model to *fetch* the few relevant facts *on demand*.

An agent solves all three the same way: it *calls tools*. The model does the language; your systems provide the *facts*.

== The anatomy of an agent

An "agent" is not magic and not a model. It is four parts working together:

* *Model* — the reasoning engine. On this workshop it is `{maas_model}`, served over an OpenAI-compatible *Models-as-a-Service* (MaaS) endpoint. The agent is *model-agnostic*: the same code runs against any served model; only an environment value changes.
* *Instructions* — the *system prompt* that sets the agent's job and its rules: _use your tools instead of guessing, never invent claim details, cite the policy id you relied on._ This is where you encode *behaviour*, and it is ordinary text you can read and change — on Parasol's agent it lives in a ConfigMap rather than in the image, which is what makes it yours to engineer.
* *Tools* — the functions the model may call. For Parasol these are the two *MCP servers*: `claims-db` (look up a claim, list by status, fetch history) and `policy-docs` (search the policy corpus). The tools are the whole point: they are how the agent touches *your* world.
* *Memory* — where the multi-step tool conversation is held. Parasol's agent uses a *fresh, per-request* memory: it remembers within a single answer (question → tool call → tool result → answer) but shares nothing between requests, so no earlier conversation can steer a later one. Pair that with *temperature 0*, which makes the model take the highest-probability token at each step rather than sampling — that *minimizes* randomness, and it is worth doing, but it does not *guarantee* determinism. Identical requests to one model at temperature 0 have been measured on this workshop returning the same substance in different packaging, and an agent under adversarial input can fail two different ways minutes apart. Pin what you can, then *measure* rather than assume.

== MCP tools are your APIs

The single most important idea in this module: *the tools an agent calls are just your services, behind a small standard adapter.*

*MCP* — the Model Context Protocol — is that standard. An MCP *server* advertises a set of *tools* (a name, the arguments, and what it returns); an MCP *client* (here, the agent) discovers them and lets the model call them. Parasol wraps its claims data and its policy search as two MCP servers, and the agent connects to both over HTTP:

Three things follow, and they are why MCP matters to a platform team:

* *A tool is a contract, not a model concern.* `get_claim(claimNumber)` returns one grounded sentence about a real claim. The model does not know or care whether that comes from H2, PostgreSQL, or a mainframe behind three hops — it calls the tool and gets a fact. *You* own the tool; the model just uses it.
* *Tools are ordinary services on the platform.* `claims-db` and `policy-docs` are plain OpenShift Deployments with Services, health probes, and metrics — *exactly* like any Parasol microservice. "Give the agent a new capability" means "deploy another service and register it as a tool," not "retrain a model."
* *One protocol, any client.* In AI-Assisted Development on OpenShift (a separate module), a *coding assistant* speaks this same MCP protocol to a *different* tool server — one that exposes Kubernetes operations instead of claims data. That portability is what MCP buys: write a tool server once, and *any* agent that speaks MCP can call it — the contract is the protocol, not the client.

== RAG, honestly

`policy-docs` is a *RAG* tool. *Retrieval-Augmented Generation* means: before the model answers, *retrieve* the few relevant documents and let the model *generate* its answer *from those passages* — not from its memory.

When a staffer asks about the auto deductible, the agent calls `search_policies("auto collision deductible")`, gets back the `POL-AUTO-01` passage, and answers from it — for example: _"500 USD per incident, as stated in policy POL-AUTO-01."_ The exact wording is the model's.

Be precise about what that citation is worth, because it is the single easiest thing to get wrong about RAG. A citation is *the model's own claim* about where it looked, produced by the same machinery as the rest of the sentence — a model can emit a perfectly well-formed policy id straight out of its weights, and a hallucination that cites its source is still a hallucination. The *evidence* is the agent's record that the tool ran: which tool, with what arguments, reported alongside the answer. A citation is an assertion; a tool call is a receipt. In the lab you check both, and then open the cited document and read the figure in it.

Be honest about what RAG does and does not do:

* *It helps when the answer is written down somewhere* and the query can find it. Policy terms, deductibles, documentation requirements, service levels — RAG shines.
* *It fails when retrieval fails.* If the search misses the right passage, the model answers from a *worse* context, or from its own memory again — grounding is only as good as the retrieval. Garbage retrieval, confident garbage answer.
* *It is not a database query.* RAG finds *relevant text*; it does not compute _"the average payout for denied home claims."_ That is what the `claims-db` *structured* tools are for. A good agent uses RAG for prose and structured tools for facts — and Parasol's agent *combines* them (below).

[NOTE]
.Deterministic retrieval now; a vector database later `[ADD-ON]`
====
Parasol's `policy-docs` uses a small, *deterministic keyword* retriever over eight fixed documents — no embeddings, no vector database, no GPU — so the lab's grounding is reproducible and runs anywhere.
Production RAG replaces that retriever with a *vector database* (Milvus or PostgreSQL/pgvector) holding *embeddings* of thousands of documents, for semantic search at scale. That is a real and important upgrade — and it slots in *behind the same `search_policies` tool contract*, so the agent does not change. Keeping the app-layer retriever simple here is deliberate; the vector database is the `[ADD-ON]` platform layer, covered below and in the wrap-up.
====

== Grounding is engineered, not guaranteed

Here is the part most demos hide: *the model decides whether to call a tool*, and that decision is not always the one you want. Handing an agent six perfectly good tools does not make it use them. What sways it is the *instruction it is carrying* — its *system prompt* — and that is not a property of the model. It is a piece of text somebody wrote.

On Parasol's agent that text is not compiled into the image. It arrives as *configuration*: a ConfigMap (`parasol-agent-grounding`) in your `{user}-ai` namespace, fed to the container as an environment variable, exactly like a connection string. Which means you can read what your agent was told, decide it is not good enough, and *change it* — and the difference is the difference between these two:

[cols="1,3",options="header"]
|===
| What the agent has been told | What that produces

| _"You are the Parasol Insurance claims assistant. Answer questions from Parasol staff about claims and policies as helpfully as you can. Keep answers short and professional."_ — a first draft about *manners* | Nothing here says the agent *has* tools, when to reach for one, or that it must not invent an answer it could not look up. On `{maas_model}` it prints the tool call as *text* — `[get_claim(claimNumber=CLM-1001)]`, `toolCalls` empty, your data never touched — and that holds for both phrasings the lab measures, plain and imperative. (A more capable model might call the tool unaided; that would say more about the model than about this prompt.)
| _"You have tools. USE THEM instead of guessing… call the claims tools… call `search_policies` and cite the policy id… Never invent claim details or policy terms."_ — an instruction about *grounding* | The tool *executes*. `toolCalls` names `get_claim`, the answer carries the real seeded record (_"...is UnderReview"_), coverage answers arrive with a policy citation, and an unknown claim comes back _"not found"_ instead of invented — because the prompt asked for that too.
|===

The lesson is not "the model is broken." It is that *grounding is something you engineer*, and the thing you engineer is an *artifact you can point at*: a ConfigMap, an environment variable, a rollout. In the lab you read the first draft above out of your own namespace, replace it, restart the Deployment so the new pod picks it up — an environment variable cannot change under a running process — and ask the same question again.

Phrasing the *question* imperatively (_"use your tools to look up claim CLM-1001…"_) also pushes a model toward calling a tool, and it is tempting to file that as a second lever you can pull. Keep it as a debugging aid instead: it is *per-question*, so it depends on every user, every caller and every integration remembering to say it, and none of them will. The system prompt applies to *every* request whether the asker knows about tools or not.

The harder truth, and the one the lab measures, is that the *wording of the system prompt itself* is a variable. Two prompts carrying the same instructions and differing only in their sentences can behave in opposite ways — same model, same question, one calls the tool and one types it out — and nothing you can read in either text tells you which is which. So a system prompt is not an artifact you review for correctness; it is one you *test*, against the worst phrasing your callers will produce, on the model you will actually serve. Pin everything else while you do — *temperature 0*, *seeded data*, *deterministic tools* — so the only variable left is the one you meant to change.

== Guardrails are a platform concern `[ADD-ON]`

An agent that reads live claims can also *leak* them, or be *steered* into answering something it should not.

That second one has a name — *prompt injection* — and it is worth understanding before you meet it. Everything the model receives is one flat list of text: your system prompt, the user's question, and whatever your tools returned. A claim's free-text description is text. A timeline note somebody typed is text. Nothing in that list carries a trust level, so an instruction sitting in a claim record reads exactly like an instruction sitting in your system prompt, and the model may follow it. The lab makes that happen on the live agent — and the useful finding is what *does not* fix it: a rule in the system prompt forbidding it, which the agent will cheerfully break. The controls that work are ordinary engineering, outside the model: validate the answer against what the tools returned, design tools whose output gives prose nowhere to hide, keep every tool read-only until a human is in the loop — and put the detector in the platform.

You do not want that protection scattered through every agent's code — you want it as a *platform layer* the request passes through, the same way a service mesh handles TLS or a gateway handles rate limits.

On Red Hat OpenShift AI that layer is the *TrustyAI FMS Guardrails Orchestrator* (generally available). Its lightweight, GPU-free option is a *regex-detector sidecar*: a `GuardrailsOrchestrator` with `enableBuiltInDetectors` scans inputs and outputs for patterns like Social Security numbers, credit-card numbers, and emails, and *blocks* or *masks* the message before it reaches — or leaves — the model.

* *Input guardrail:* a staffer pastes a claimant's Social Security number into a question → the detector blocks it before the model ever sees the *personally identifiable information* (PII).
* *Output guardrail:* the model is about to emit something off-limits → the detector filters it on the way out.

Guardrails are *not deployed on this cluster* — they are the `[ADD-ON]` layer. The point for now is *where the responsibility lives*: a policy the platform enforces, not code every team re-invents. Reach for it the moment an agent touches regulated data.

== Where your claim data goes

For a regulated insurer this is usually the *first* question, and it deserves a precise answer rather than a comforting one: when the agent answers about `CLM-1004`, what travels, and how far?

On this workshop the agent, both MCP tool servers, and the claims data itself are *in your cluster*, in `{user}-ai`. The *model* is not. It is served over a *Models-as-a-Service* endpoint *outside* the cluster — the one recorded in your namespace's `maas-config` ConfigMap — and the agent calls it server-side holding a short-lived key from a Secret, so the key never leaves the pod and you never handle it. What *does* leave is the *conversation*: your system prompt, the question, and *everything your tools returned*. When `get_claim` fetches Tom Becker's denied home claim, that record goes into the model's message list and travels with the request. That is not a hidden detail — it is the mechanism the lab's injection exercise puts under a microscope: your tool returned a string, the string went into the message list, and the model read it exactly the way it reads your grounding prompt.

Two things follow, and both are decisions somebody has to own:

* *What leaves is what your tools return.* The tool contract is the boundary, and it is yours to draw: `get_claim` hands back one grounded sentence about a claim, and a tool written for convenience would hand back the whole row — free-text notes, claimant details and all. Design the return value around the answer you need, and the data-protection question narrows to something a review can actually settle.
* *If the answer has to be "nothing leaves", move the model, not the agent.* In-cluster serving on Red Hat OpenShift AI (KServe/vLLM) puts the model on your own nodes, and the application does not change: same OpenAI-compatible contract, a different endpoint and model id in the same configuration. The trade is real and worth saying out loud — you take on a GPU you pay for whether it is busy or not, a model to keep patched, and the capacity planning for both, in exchange for a boundary your auditor can draw around your own cluster.

So the closing line an insurer wants — _"your claims data never leaves our cluster"_ — is not true of the graded path you are about to run, and it is *one layer up*, not one architecture away. Say both halves. What makes it credible is that the agent is indifferent to which half you pick.

== The Red Hat AI stack — what runs where

The graded path you build is deliberately the *simplest thing that teaches the ideas*. It helps to see it against the full stack, so you know what the `[ADD-ON]` layers add and when to adopt them:

[cols="2,2,3",options="header"]
|===
| Layer | This workshop (graded) | The `[ADD-ON]` production layer

| *Model serving* | *Models-as-a-Service* — a shared, OpenAI-compatible endpoint serving `{maas_model}`, off-cluster, GPU-free for you | In-cluster serving on Red Hat OpenShift AI (KServe/vLLM) when you must host the model yourself
| *Agent runtime* | *Quarkus LangChain4j*, calling the model directly — the reproducible, GA-grade spine | *Llama Stack* (Technology Preview) as a shared agent runtime with the Responses API — a product surface for agents, MCP registries, and RAG
| *Retrieval (RAG)* | Deterministic keyword search over 8 docs, in-memory | A *vector database* (Milvus / pgvector) of embeddings for semantic search at scale
| *Guardrails* | — (concept) | *TrustyAI FMS Guardrails Orchestrator* (GA) — regex-detector sidecar for PII/safety
| *Observability* | Health, Prometheus metrics, per-answer token + tool-call reporting | The same, plus OpenTelemetry traces to *Tempo* (ties Observability, a separate module)
|===

The whole right-hand column is *additive*: each piece slots in behind an interface the agent already uses, so you adopt them when the need is real — not on day one. That restraint *is* the engineering.

== What an answer costs

_"What does this cost us at five hundred adjusters?"_ is a fair question, and the answer that survives contact with a procurement team is the *shape* of the bill rather than a price per token — that price is vendor-specific, date-specific, and different in kind if you serve the model yourself, where you stop paying per token and start paying for a GPU whether it is busy or not.

The shape is *requests × tokens per request*, and the second term is where agents surprise people. Every question carries *all six tool definitions* — name, description, argument schema — because that is how the model knows what it may call, so most of what you send is the *inventory*, not the question. The lab measures exactly this on `{maas_model}`: one `get_claim` lookup answered with *2,333 input tokens against 39 output*, and the metrics snapshot on the same page reads *36,010 input against 884 output* across the calls that agent had served. Input outweighs output by roughly forty to sixty times in those two readings. Your figures will differ by model and by prompt; the *ratio*, and the reason for it, will not.

* *The cost signal is a metric you already scrape.* Every `/agent/ask` answer reports its own `tokenUsage`, and `gen_ai_client_token_usage_total` — split by token type and by model — is on the agent's `/q/metrics` from the first request. It is a Prometheus series like any other, on the dashboards you already run: no AI-specific cost tooling, which is this module's thesis turning up in the finance conversation.
* *Every tool you add is billed on every question, including the ones that use none.* Six schemas ride along whether the question needs them or not, so thirty tools means paying for thirty, every time — and making the model's choice harder while you do it. Split agents by job rather than growing one.
* *The cheapest request is the one that never reaches the model.* If you already know the caller wants the status of `CLM-1004`, call the tool directly — a model in the loop is tokens, latency and nondeterminism, and it should be something you buy on purpose. On the latency half of the same question, the lab's fifteen measured calls average *1.43 seconds* an answer.

Measurement is not a control, and the platform has one: *Models-as-a-Service* issues *per-key* quotas and rate limits `[ADD-ON]`, so a runaway integration meets a limit rather than an invoice. Measure your own input tokens per answer, multiply by the questions one adjuster actually asks in a day, and you have a number you can defend — at five adjusters or five hundred.

== Same platform disciplines apply

Step back and notice what the agent *is*: a Quarkus Deployment with a Service, an edge Route, a readiness probe (which pings both MCP servers, so a *Ready* agent has *proven* its tool wiring), a liveness probe, Prometheus metrics, and a container image pulled from the shared registry — *identical in shape to every other Parasol service you have deployed this week*.

That is the thesis. An AI app is *not* a special snowflake that needs a parallel platform. It needs config in a ConfigMap, a key in a Secret, and health probes that gate traffic (Config, Secrets & Multi-Environment), metrics and traces (Observability, Health & Scale), and delivery through Source-to-Image, pipelines, and GitOps (Ways to Build & Deliver Apps, Pipelines Fundamentals, and GitOps Fundamentals) — *the golden path you already know*. The model is new; the *disciplines* are not.

== How this shows up in real orgs

* *"Our chatbot confidently gave a customer the wrong claim status."* A model without tools *hallucinates* live data. The fix is *grounding*, and it has two halves that are both engineering: give the agent a tool onto the system of record, and *tell it, in its system prompt, to use that tool and to cite what it used*. Giving it the tool and hoping is the half that fails quietly. If it can't point at a source, don't trust it.
* *"Every team is building its own AI integration to the same backend."* MCP is the antidote: wrap the backend as *one* MCP server and every agent — and every coding assistant — calls the *same* tool. Tools are shared platform capability, not per-app glue.
* *"How do we stop an agent leaking PII?"* Not in each agent's code. A *guardrail* layer the platform enforces (regex detectors today, richer models later) blocks it once, for everyone. Security that depends on every developer remembering is security you don't have.
* *"Is this a whole new platform to run?"* No — and be suspicious of anyone who says it is. The agent is a Deployment with a Route and probes; it rides your existing pipelines and GitOps. *AI apps are apps.* The new part is the model endpoint and the tools, and both are just services.
* *"Can we make the demo reproducible?"* Only with discipline: *temperature 0*, *seeded data*, and *deterministic tools*. A live agent at temperature 0.7 over a production database is a great way to be surprised on stage. Pin the variables you can.
