== The agent answers with `[get_claim(...)]` and an empty `toolCalls`

*Symptom:* You ask a claim question and the `answer` is literally `[get_claim(claimNumber=CLM-1001)]` (or similar), and `toolCalls` is `[]`.

*Cause:* This is the *expected* behaviour before the fix, not a fault: the model *described* the tool call as text instead of *executing* it — an ungrounded answer, and on `{maas_model}` the entry state's weak prompt produces exactly this every time, for both phrasings the lab measures. The reason is almost always the *instruction the agent is carrying*: either its system prompt never told it that it has tools, or you have already fixed that and the running pod is not serving your fix yet.

*Fix:* Start from what the agent is actually running. `GET /agent/info` reports its own grounding and spends no token:

[source,sh,role=execute,subs="attributes"]
----
curl -ksS "https://parasol-agent-{user}-ai.{cluster_domain}/agent/info" \
  | jq -r '.groundingPromptSource, "---", .groundingPrompt'
----

Then read the ConfigMap it is fed from:

[source,sh,role=execute,subs="attributes"]
----
oc get cm parasol-agent-grounding -n {user}-ai -o jsonpath='{.data.grounding-prompt}'
echo
----

Those two outputs separate the two failures:

* *Both show a prompt that never mentions tools.* You are still at the entry state. That prompt is deliberately weak — it describes a *tone* and says nothing about the six tools the agent holds — and rewriting it *is* exercise 2. Write one that says there are tools, says which kind of question needs which, and forbids inventing what a tool did not return; then patch it into `cm/parasol-agent-grounding`.
* *The ConfigMap shows your new prompt but `/agent/info` still shows the old one.* Your edit reached the *cluster* and never reached the *process*. The prompt arrives as the `PARASOL_AGENT_GROUNDING_PROMPT` environment variable, and an environment variable cannot change under a running pod. Roll the Deployment:
+
[source,sh,role=execute,subs="attributes"]
----
oc rollout restart deploy/parasol-agent -n {user}-ai
oc rollout status deploy/parasol-agent -n {user}-ai --timeout=180s
----
+
Then re-read `/agent/info`, polling for a few seconds rather than asking once: the Route needs a moment longer to serve the *new* pod than the Deployment needs to call itself rolled out. `ws verify agentic-ai` grades this outcome separately and names it — _"the running agent is still serving the OLD grounding — your ConfigMap edit has not reached the pod."_

[NOTE]
.Phrasing the question is a probe, not the fix
====
Asking *imperatively* (_"Use your tools to look up claim CLM-1001 and report its status."_) also pushes a model toward calling a tool, and it is a good way to prove the wiring works while you debug. It is not the remedy, because it is *per-question*: it depends on every user, every caller and every integration remembering to say it, and none of them will. The system prompt applies to *every* request. Fix the prompt; keep the phrasing as a probe.

The honest edge, and the one that trips people here: whether the *plain* question grounds depends on *how your strengthened prompt is worded*, not only on whether it mentions tools. Against the lab's printed sample it comes back typed out on `{maas_model}`, five runs out of five; against a rewording of those same instructions it calls the tool, five out of five. Both outcomes are deterministic, and neither is predictable from reading the text. So if your plain question types the call out, that is not proof your prompt is broken — and if it grounds, that is not proof it is right. The only conclusion available is the one you measure.
====

== `POST /agent/ask` returns `502` with `"authFailure": true`

*Symptom:* Every question returns HTTP `502` and a body like `{"error":"model authentication failed - check the MaaS key ...","authFailure":true,...}`.

*Cause:* The model server rejected the agent's key with a `401`, and the agent *degrades gracefully* to a clean `502` instead of a stack trace. Three different key problems produce the same `502`, and the model server's own message tells them apart. Read it in the agent log:

[source,sh,role=execute,subs="attributes"]
----
oc logs deploy/parasol-agent -n {user}-ai --tail=200 \
  | grep -i "Agent model call failed" | tail -1 \
  | sed -E -e 's#Received=[^,]*#Received=<redacted>#g' \
           -e 's#(sk-|eyJ)[A-Za-z0-9._~+/=-]{8,}#\1<redacted>#g'
----

The agent *already* redacts this line before it writes it, so the `sed` is a second pair of hands, not the only one — it re-applies the same two rules to whatever the log actually contains. Both work by naming the thing: the gateway's `Received=` field by name, and `sk-…`/JWT-shaped tokens by shape. Neither is a length limit, and that is deliberate — see the warning below.

[cols="1,2"]
|===
| What the message says | What it means

| `Expired`, or nothing more specific
| The key has *expired* — workshop MaaS keys are short-lived, provisioned per event. The common case.

| `Virtual Key expected. Received=…, expected to start with 'sk-'`
| The key is the *wrong kind*: something that is not a MaaS virtual key was copied into the Secret. Seen when the platform's source credential belongs to a different model provider entirely.

| `key not allowed to access model. This key can only access models=[…]`
| The key is fine but *model-scoped* to a different model than `GENAI_MODEL`. Workshop MaaS keys grant one model; the key and the `maas-config` `model` value must name the same one.
|===

[WARNING]
.Why this redacts instead of truncating
====
An earlier version of this page trimmed the log line with `cut -c1-200` instead. Measured against the real line, the echoed key started at character *201* — the truncation cleared it by *ten characters*. That is not a control, it is a coincidence: one reword upstream and the same command prints a bearer token into your terminal.

If you write a diagnostic that displays output which might carry a credential, redact the credential *by name or by shape*. Never rely on a character count falling short of it — and never rely on the credential staying in the field you expect, which is why the shape rule above is there alongside the field rule.
====

*Fix:* `ws prep agentic-ai --yes` re-resolves the key and re-converges the model/endpoint into your namespace — that clears the expired case. The other two are *platform-side*: the source credential is wrong or scoped to another model, so tell your instructor rather than editing the Secret yourself.

*You should not normally reach this page for a wrong-kind key.* The entry state now validates the credential before staging it: it prefers the workshop's own MaaS credential over any credential belonging to a platform assistant on the cluster, rejects anything that is structurally not an API key, and spends one token proving the rest against the endpoint. Its verdict is recorded where you can read it:

[source,sh,role=execute,subs="attributes"]
----
oc get cm maas-config -n {user}-ai \
  -o jsonpath='{.data.aiPathAvailable}{"  "}{.data.aiPathReason}{"  "}{.data.credentialSource}{"\n"}'
----

`true` means the endpoint accepted the key when your namespace was materialized. `false` names the reason (`credential-is-a-jwt-not-an-api-key`, `credential-rejected-by-endpoint`, `no-maas-credential`) and `ws prep` will have printed the same reason. `unverified` means the cluster could not reach the endpoint at that moment, so the key was staged unproven — a `502` after that is expected and is an environment problem, not a key problem. `ws verify agentic-ai` reports the same three states as ✅ / ❌ / ⚠.

== `POST /agent/ask` returns `400` "question is required"

*Symptom:* The call returns HTTP `400` and `{"error":"question is required",...}`.

*Cause:* The request body had no `question`, or it was blank/whitespace. The agent validates input before spending a token.

*Fix:* Send a non-empty question: `-d '{"question":"Use your tools to look up claim CLM-1001 and report its status."}'`. Check your quoting — a shell that ate the JSON braces sends an empty body.

== The `toolCalls` show `"result": null` — did the tool fail?

*Symptom:* A grounded answer is correct, but each entry in `toolCalls` has `"result": null`.

*Cause:* This is *expected*, not a failure. The agent reports *which* tool the model chose and with *what* arguments — the visibility that matters. The tool's return value is folded straight into the model's context to produce the answer, so it is not duplicated in the report.

*Fix:* Nothing to fix. The *answer* is your proof the tool ran: a grounded fact (e.g. `CLM-1001` is `UnderReview`) is something the model could not have invented. To see the raw tool result, read the agent pod log (exercise 3).

== The agent is not Ready (`/q/health/ready` is DOWN)

*Symptom:* `oc get deploy parasol-agent` shows `0/1`; `GET /q/health/ready` reports `status: DOWN`, or the Route returns "Application is not available."

*Cause:* The agent's readiness probe *pings both MCP servers*, so a Ready agent has proven its tool wiring. If either `claims-db` or `policy-docs` is not up, the agent stays *not Ready* on purpose — it will not take traffic it cannot serve.

*Fix:* Check the tool servers: `oc get pods -n {user}-ai`. If `claims-db` or `policy-docs` is not `1/1`, that is the real problem — describe it (`oc describe pod ...`) or `ws reset agentic-ai --user <u>` to re-materialize. Once both MCP servers are `OK`, the agent's readiness flips to `UP` on its own.

== There are no traces in Tempo

*Symptom:* You expected the model call and tool calls to appear as spans in a tracing backend, but nothing shows up.

*Cause:* On this cluster the agent's OpenTelemetry *exporter is disabled* (`QUARKUS_OTEL_SDK_DISABLED=true`) — there is no trace backend wired here, so the spans stay in-process. You can still see their ids as *exemplars* attached to the Prometheus metrics.

*Fix:* This is expected on the workshop cluster — tracing is the `[ADD-ON]` observability tie to Observability (a separate module). To send traces, set `QUARKUS_OTEL_SDK_DISABLED=false` and `OTEL_EXPORTER_OTLP_ENDPOINT` to a collector, and each answer becomes a distributed trace. The *metrics* (`/q/metrics`) and the per-answer `toolCalls`/`tokenUsage` are the live observability here.

== The injection "worked" — the agent answered correctly

*Symptom:* Exercise 6's first block returns the true record (`Denied`, `8400.00 USD`) instead of the fabricated settlement, or the record-framed block answers correctly.

*Cause:* Expected. The outcome is *not stable*, and that instability is the finding the exercise is built on. Measured on `{maas_model}` at temperature 0: the first block fabricated the figure in 7 runs out of 9 and broke off mid-answer in the other 2 — never answering correctly — while the record-framed block answered correctly in 2 runs out of 5. A correct answer is a draw from the same distribution, not a fault.

*Fix:* Send the block again — the checkpoint expects you to. If it answers correctly *every* time across about five runs, check which model is actually in force (`curl -ksS "$AGENT/agent/info" | jq -r .model`): a different model draws the line somewhere else, which is the exercise's own point rather than a broken lab.

== Exercise 6: `toolCalls` is empty and the answer contains `[get_claim(...)]`

*Symptom:* The injection blocks return the tool call typed out as text, with `toolCalls: []`, so there is nothing to compare against.

*Cause:* The *weak entry grounding* is still in force, or the exercise-2 rollout has not finished. The injection beat needs an agent that actually calls tools; against the entry draft it never does, and the whole exercise collapses.

*Fix:* `oc rollout status deploy/parasol-agent -n $NS`, then `curl -ksS "$AGENT/agent/info" | jq -r .groundingPrompt` — if that prints the three-line "Keep answers short and professional" draft, go back and finish exercise 2.

== The `grep` over the pod log returns nothing

*Symptom:* `oc logs deploy/parasol-agent ... | grep -A2 '"role" : "tool"'` (exercise 6) or the `search_policies` schema grep (exercise 5) prints nothing at all.

*Cause:* The `--tail` window no longer reaches a model request. The agent logs every request, so a busy or long-running pod pushes the block you want past the tail — and a pod that has just been rolled has not served one yet.

*Fix:* Ask the agent a question *first*, then run the `grep` — in that order. If it still prints nothing, raise `--tail` (`--tail=800`, `--tail=2000`). A pod restarted since your last question has an empty request log by definition.

== `langchain4j_aiservices_timed_seconds_max` is `0.0`

*Symptom:* `/q/metrics` reports a healthy `_count` and `_sum` for the timer, but `_max` is `0.0` — on an agent that has demonstrably served requests.

*Cause:* Not a broken metric. `_max` is a *rolling window* maximum, not an all-time high: it reports the slowest call *recently*, and decays to zero when the agent has been idle. Observed four times on the live agent — for example `_count 5.0`, `_sum 8.757`, `_max 0.0` while idle, then `_count 6.0`, `_sum 9.991`, `_max 1.2335` immediately after one question, the `_max` being exactly the `_sum` delta because that call was the only one in the window.

*Fix:* Ask the agent something, then read `/q/metrics` straight away. For a number that does not decay, use the mean: `_sum / _count`. A `0.0` there means *nothing recent*, never *nothing slow*.

== Exercise 5: the build fails cloning the repository

*Symptom:* `oc logs build/policy-docs-mine-1 -n {user}-ai` ends in a `git clone` failure — a TLS/certificate error, or a host that cannot be resolved.

*Cause:* The `BuildConfig` clones the workshop's *in-cluster* Gitea mirror over HTTPS. Two things can break that: the mirror being unreachable, or — the one that surprises people — an ingress certificate the build pod does not trust. The build pod trusts the cluster's normal certificate authority bundle; on a cluster whose ingress serves a *self-signed* certificate the clone fails inside the build, where nobody thinks to look.

*Fix:* First confirm the mirror answers at all: `curl -sI {gitea_url}` from your terminal. If that is fine and the build still fails on the certificate, this is a cluster-provisioning property rather than a lab error — tell your instructor, who can point `spec.source` at a certificate authority reference. Note that `oc` succeeding from your terminal proves nothing about the build pod: they trust different things.

== Exercise 5: `oc new-app` created a Service on the wrong port

*Symptom:* Registration appears to work but `/q/health/ready` reports `policy-docs: DOWN`, or the agent's rollout never completes after `oc set env`.

*Cause:* The registration URL is `http://policy-docs-mine:8080/mcp/sse`, and `oc new-app` derives the Service port from the image's `EXPOSE`. If the derived port is not `8080`, the agent dials a port nothing is listening on and its readiness probe — which pings its MCP servers — correctly refuses to pass.

*Fix:* `oc get svc policy-docs-mine -n {user}-ai -o jsonpath='{.spec.ports[0].port}'` should print `8080`. If it does not, use the port it did derive in the `oc set env` URL. Either way you can always get back to a working agent with the hand-back command: `oc set env deploy/parasol-agent POLICY_DOCS_MCP_URL=http://policy-docs:8080/mcp/sse -n {user}-ai`.

== Exercise 7: the runner scores `0/5` and every row says `FAIL`

*Symptom:* `AGENT="$AGENT" bash /tmp/eval-run.sh` prints five `FAIL` rows with `GROUNDED NO` and an empty `-> answered:` line, and `SCORE: 0/5` — even though the agent answers fine when you `curl` it by hand.

*Cause:* The script cannot reach the agent. Either `$AGENT` did not make it into the script, or the endpoint is not answering. `AGENT=` is set as a plain shell variable at the top of the lab, and `bash <script>` starts a *child* shell that does not inherit one — which is why the lab runs it with the `AGENT="$AGENT"` prefix. Drop the prefix and the script sees an empty host.

*Fix:* Re-run it exactly as printed, with the prefix. If it still scores `0/5`, check the endpoint itself — `echo "$AGENT"` should print your Route, and `curl -ksS "$AGENT/agent/info"` should answer. A `502` there is the expired-MaaS-key case above, not a scoring problem.

== Exercise 7: `ws verify` went red in the middle of the exercise

*Symptom:* Part-way through scoring the baseline, `ws verify agentic-ai` reports the *entry* state and the grounding checks are red.

*Cause:* Correct, and temporary. Scoring a baseline means putting the *weak* draft back and rolling the agent onto it, so for those few minutes the agent genuinely is at the entry state. Nothing is broken.

*Fix:* Finish the exercise — the next step restores your own prompt from the `/tmp/grounding-mine.txt` snapshot you took, and verify goes green again. If you lost the snapshot, re-apply the prompt from exercise 2's *Write a grounding that works* step and roll the agent.

== A pod is `ImagePullBackOff`

*Symptom:* `parasol-agent`, `claims-db`, or `policy-docs` won't start; events show `ImagePullBackOff`.

*Cause:* The image isn't present in the shared internal registry (`ogsr-parasol-images`) yet, or the per-user pull permission hasn't propagated. The three images are built once into `ogsr-parasol-images` and pulled cross-namespace.

*Fix:* On a freshly provisioned cluster this usually clears once the images finish loading — `ws reset agentic-ai --user <u>` waits for readiness. If it never clears, the shared images aren't loaded: that is an environment provisioning gap, not a lab error — tell your instructor.

== `ws smoke` fails only on "cockpit clone HEAD matches the mirror"

*Symptom:* `ws smoke agentic-ai <u>` reports 11/12, failing only the freshness check ("pod serves ..., mirror ...").

*Cause:* The attendee's cockpit pod holds a Git clone from *before* the latest content push — a stale cockpit, not a module defect.

*Fix:* `ws git-refresh --restart-terminals --user <u>` re-clones the cockpit to the mirror HEAD; wait for the pod to come back, then re-run `ws smoke` for 12/12. Every other check — identity, isolation, `ws prep`/`verify`, the `oc auth can-i` smoke command — passes independently of this one.
