== What you built

You took a fluent-but-blind model and turned it into an agent Parasol's staff can *trust*: one that reads *live* claims, *grounds* its answers in the policy corpus with citations, admits when it doesn't know — and ships on OpenShift exactly like every other service.

* You *met* a running agent (`parasol-agent`) whose readiness probe pings both MCP tool servers, so a *Ready* agent had already proven its wiring — no token spent.
* You *engineered the grounding* — the exercise the module is really about. You read the system prompt your agent shipped with, found that it described a *tone* and never mentioned the six tools it was holding, wrote one that names them and forbids inventing what a tool did not return, patched it into `cm/parasol-agent-grounding`, and rolled the Deployment so the running pod picked it up. Same model, same question, same tools: the only thing that changed was what the agent had been *told* — and you measured that *how* it is told matters as much as *what*.
* You watched *MCP tools are your APIs*: the agent called `get_claim`, `list_claims_by_status`, and `get_claim_history` on your claims service, and `search_policies` on your policy corpus — reporting exactly which tools it used.
* You *grounded with RAG and citations* (`POL-AUTO-01`, `POL-CLAIM-01`), *combined* a claim fact with a policy rule in one answer, got an honest _"not found"_ for a claim that doesn't exist — and learned to tell an *assertion* from a *receipt*: the citation is the model's claim about where it looked, the `toolCalls` entry is your record that it looked, and `get_policy` let you open the document and read the figure yourself.
* You *shipped a tool server of your own* — read `search_policies` in the source, built it from the in-cluster repository, ran it in your project, and registered it with the agent by changing *one environment variable*. Same question, same `500 USD` cited to `POL-AUTO-01`, different server. Then you handed the agent back, because registration is configuration in both directions.
* You *broke it on purpose with prompt injection* — made the agent report a settlement no tool ever returned, watched the *same payload* fail differently from a different position, found your own system prompt's rule against fabricating data being ignored, and built the control that actually catches it: a comparison of the answer against what the tools returned, with no model in it.
* You *scored the grounding* — a five-question set with the grounded facts each answer must contain, graded on two axes (did a tool run, are the facts there), run against the weak draft and against your own prompt. 2/5 to 5/5, attributable to one ConfigMap.
* You *observed* the agent — per-answer tokens and tool calls, Prometheus GenAI metrics, mean seconds per answer from `_sum / _count` — and confirmed it is a plain Deployment with a Route and probes that *self-heals* its tool wiring on restart.

== Map it to your org

Discuss with the person next to you:

. *Pick one system you own that a support person asks about all day.* What would its `get_claim` be — the one tool that returns a grounded fact? Wrapping it as an MCP tool is a smaller job than most teams fear; what is stopping you?
. *Where would an ungrounded answer hurt you most?* You turned an agent from ungrounded to grounded by rewriting one ConfigMap — which means someone can turn it back just as easily. In your world, where would that text live, who *reviews* a change to it, and does it go through the same pipeline as code? And what is the *review gate* on the answers — do you require a *citation* on every AI answer, and would you ship an agent that couldn't produce one? Then the harder one: when somebody rewords that text next quarter — same instructions, tidier sentences — what would tell you that grounding had stopped working, before a customer does?
. *Who owns the guardrail?* If an agent in your org touched a Social Security number or account data, is the protection a *platform layer* everyone inherits, or code each team re-writes (and sometimes forgets)? What would it take to make it the former?
. *Find the free text in your own system.* You watched an instruction sitting in ordinary text get followed as if it were policy. In the system you picked in question 1, which fields can a *customer* put words into, and which of those would reach a model? Then the uncomfortable one: what would you compare an answer *against* to catch it — what does your `get_claim` return that a checker could hold the answer to, and would you have to change the tool to make that possible?
. *Who signs off the number?* You scored a prompt 2/5 and then 5/5 with five questions in a file. Who in your org would own that file, what score would you refuse to ship below, and where would the run live — a pipeline stage, a pre-merge gate, or a person's laptop? A suite nobody runs on a schedule is a suite that reports the state of last quarter.

== When NOT to use this

Honesty keeps this credible — an agent is not always the answer:

* *Don't use an agent when a plain API call will do.* If you *know* the user wants the status of claim `CLM-1004`, call `get_claim` directly — you don't need a model to decide that. Agents earn their cost when the *question is open-ended* and the right tool isn't known in advance. A model in the loop is latency, tokens, and nondeterminism you should add *deliberately*.
* *Don't RAG what fits in the prompt.* Retrieval is machinery. If the whole policy is three sentences, put it in the system prompt and skip the vector database. RAG is for corpora too big to prompt, not for looking clever.
* *Don't ship an ungrounded agent for anything that matters.* If it can't cite a source or call a tool, it is *guessing*. For a claim, a policy, a payout, or anything touching money or regulation, an ungrounded answer is a liability, not a feature.
* *Don't ship a system prompt you have not tested.* You measured this: two prompts carrying the *same* instructions and differing only in their sentences behaved in opposite ways on the same model, for the same question. A prompt is not an artifact you can review for correctness — treat it like code with no compiler and no type checker, and put it under test against the phrasing your callers will actually use.
* *Don't put an agent on regulated data without guardrails.* PII and safety filtering is not a "later" for an agent that reads real customer records. If the `[ADD-ON]` guardrail layer isn't there yet, keep the agent off regulated data until it is.
* *Don't give an agent a write tool because the read tools went well.* Every tool in this module is read-only, which is the only reason the worst thing injection could buy an attacker was a wrong sentence. The same seven-runs-in-nine against an `approve_claim` tool is money leaving the company. A tool that changes something needs a human in the loop, or an authorization the model cannot reach.
* *Don't demo at temperature 0.7 over live data.* Pin what you can — *temperature 0*, *seeded data*, *deterministic tools* — and be clear about what that buys: temperature 0 makes the model take the most-likely token instead of sampling, which *minimizes* randomness without *guaranteeing* determinism. You measured both halves of that in this workshop: a fixed question set repeating cell for cell, and the same injection payload producing two different failures minutes apart. A "creative" agent over a production database is how you get surprised in front of a customer; a pinned one is how you get *fewer* surprises, not none.

== The next platform layer `[ADD-ON]`

You built the *graded* spine — a Quarkus LangChain4j agent, MCP tools, deterministic RAG — deliberately the simplest thing that teaches the ideas. Three `[ADD-ON]` layers (a separate subscription, and in places a GPU) turn it into production, each slotting in *behind an interface the agent already uses*:

* *Guardrails* — the *TrustyAI FMS Guardrails Orchestrator* (generally available) runs a *regex-detector sidecar* that blocks or masks PII (Social Security numbers, credit cards, emails) and unsafe content as a *platform policy*, so no agent re-implements it. Adopt it the moment an agent touches regulated data.
* *A Llama Stack runtime* — Red Hat OpenShift AI ships *Llama Stack* (Technology Preview) as a shared agent runtime with the Responses API, MCP registries, and RAG providers. Adopt it when you want a *product surface* for agents rather than hand-wiring each service.
* *A vector database* — Milvus or PostgreSQL/pgvector holding document *embeddings* for semantic search at scale, behind the same `search_policies` contract. Adopt it when your corpus outgrows a handful of documents.

The engineering is knowing these exist and reaching for them *when the need is real* — not building all of it on day one.

== The bigger arc — modernize, then infuse AI

This module pairs with Application Modernization (a separate module): there you *modernized* Parasol's legacy claims service onto the platform; here you *infused it with AI* by putting an agent in front of the same claims data. And AI-Assisted Development on OpenShift (a separate module) proves the "MCP tools are your APIs" thesis from the other side: there a *coding assistant* speaks the very same MCP protocol to a *different* tool server — one exposing Kubernetes operations instead of claims data. Write a tool server once, and any agent that speaks MCP can call it.
