== Demo arc — The bad release that rolled itself back (12 min)

[NOTE]
.Before you present
====
Two prep steps, both *before the room*:

. Run `ws solve gitops-at-scale --user {user}`.
It creates the ApplicationSet-equivalent end state — the claims app GitOps-managed in `{user}-dev`/`{user}-stage` *and* running in `{user}-prod` as a canary *Rollout* (with the wave-ordered migration hook) — then *blocks ~4–6 minutes by design* while everything goes Healthy.
Do it early; it is truthful when it returns.
. Sign in to the student Argo CD UI ({student_argo_url}) as `{user}` and open the `claims-prod-{user}` application — its card (3 apps green, prod Healthy as a Rollout) is your opening visual.
The Argo CD *Rollout view* is not available on this cluster (its UI extension is enabled but does not render — see the exercise 3 note in the workshop flavor); the polling loops below are the canary's dashboard here, so have a large terminal window ready too.

Have a terminal with `PROD={user}-prod` set.
The money moment is beat 3: a bad release that the analysis gate *aborts* on its own, stable never leaving production.
====

[demo-block]
[TIME 3m]
Say:: "Parasol runs a dozen services across three environments. Nobody hand-writes thirty-six Argo CD Applications — one ApplicationSet generates them. And production doesn't take a new build all at once; it takes it as a canary that has to prove itself."
Show:: The Argo CD UI: the three `claims-{dev,stage,prod}-{user}` applications, all green (prod's card reads Healthy — the Rollout view that would normally show its 4 stable pods is not available on this cluster); then the terminal command below, which states the same fact directly.
Do:: In the terminal, show that production really is a progressive-delivery Rollout, not a plain Deployment:
+
[source,sh,role=execute,subs="attributes"]
----
PROD={user}-prod
oc get rollout parasol-claims -n $PROD \
  -o jsonpath='prod is a {.kind}, strategy {.spec.strategy.canary.steps[*].setWeight}%, phase {.status.phase}{"\n"}'
----
+
"One object generated all three environments; prod is the one that runs progressive delivery."

[demo-block]
[TIME 4m]
Say:: "Let's ship a new build of the claims service to production — version 1.1 — the GitOps way: I edit Git, and the canary takes over."
Show:: The Gitea editor on `rollouts/claims-rollout.yaml`, bumping the image tag `1.0` → `1.1` and committing; then the terminal, where the polling loop below is the canary's dashboard on this cluster.
Do:: After committing in Gitea, click *Refresh* on `claims-prod-{user}`, then narrate the steps as the terminal polls them (the Argo CD *Rollout view* that would normally animate this does not render here — the loop's `step N/5` / `canary-pods:X/4` / `analysis:` columns are the visual):
+
[source,sh,role=execute]
----
CANARY_STARTED=""
for i in $(seq 1 20); do
  oc get rollout parasol-claims -n $PROD \
    -o jsonpath='{.spec.template.spec.containers[0].image}' | grep -q ':1.1' \
    && { CANARY_STARTED=yes; break; }
  sleep 6
done
if [ -z "$CANARY_STARTED" ]; then
  echo "  ✗ the canary has not started — Argo has not synced the commit yet; press Refresh and re-run"
else
  for i in $(seq 1 24); do
    S=$(oc get rollout parasol-claims -n $PROD -o jsonpath='{.status.currentStepIndex}')
    P=$(oc get rollout parasol-claims -n $PROD -o jsonpath='{.status.phase}')
    A=$(oc get analysisrun -n $PROD --sort-by=.metadata.creationTimestamp -o jsonpath='{.items[-1:].status.phase}')
    echo "  $(date +%T)  step $S/5   $P   analysis:${A:-none}"
    [ "$P" = "Healthy" ] && [ "$S" = "5" ] && { echo "  ✔ promoted to 100%"; break; }
    sleep 7
  done
fi
----
+
"25% to the canary, a pause, 50%, then an *analysis* Job probes the new pods — it passes — and only now does 1.1 take 100%. The new version earned its traffic."

[demo-block]
[TIME 4m]
Say:: "Now the beat that matters. I ship another release — but this time the canary's analysis will fail, the way it would if the new build spiked errors. Watch production *not* break."
Show:: The terminal setting the analysis verdict to fail, the Gitea commit of the next build, then the terminal watch loop printing `Degraded` as the abort happens and the health-check curl proving stable never stopped serving.
Do:: Force the analysis to fail, then ship:
+
[source,sh,role=execute]
----
oc patch configmap gitops-at-scale-canary-control -n $PROD --type merge -p '{"data":{"verdict":"fail"}}'
----
+
Then in Gitea bump `rollouts/claims-rollout.yaml` image `1.1` → `1.0` (a stand-in for "the next build"), commit, *Refresh* `claims-prod-{user}`, and watch:
+
[source,sh,role=execute]
----
for i in $(seq 1 20); do
  P=$(oc get rollout parasol-claims -n $PROD -o jsonpath='{.status.phase}')
  A=$(oc get analysisrun -n $PROD --sort-by=.metadata.creationTimestamp -o jsonpath='{.items[-1:].status.phase}')
  echo "  $(date +%T)  $P   analysis:${A:-none}"
  [ "$P" = "Degraded" ] && break
  sleep 7
done
oc get route parasol-claims -n $PROD -o jsonpath='{.spec.host}' \
  | xargs -I{} curl -ks -o /dev/null -w "users still served: %{http_code}\n" http://{}/q/health/ready
----
+
"The analysis failed at 50%, the Rollout *aborted*, and it rolled back to the stable version on its own — production answered `200` the entire time. No human, no incident, no bad build in front of users."

[demo-block]
[TIME 1m]
Say:: "And here's the receipt — the analysis run that made the call."
Show:: The failed `AnalysisRun` and its message.
Do::
+
[source,sh,role=execute]

oc get analysisrun -n $PROD --sort-by=.metadata.creationTimestamp \

----
+
"``Failed`` — the metric breached its threshold, so the rollout was aborted. Read like an incident review, except the rollback already happened."

The CLI you just downloaded talks to the *same Argo CD API* as the UI, and that API enforces your tenancy: your token maps to `proj-{user}`, so you can create and manage only *your* project's objects.

That `PermissionDenied` is the tenancy boundary doing its job — the same boundary that lets *one* shared Argo CD instance safely serve a whole room.

== 5. Blue-green: the other strategy
⏱ *~5 min* · know the second shape of a safe rollout, and when to pick it

Canary is one progressive-delivery strategy; *blue-green* is the other, and the same Argo Rollouts controller serves it.
Where a canary shifts traffic *gradually* (25% → 50% → 100%) and gates on analysis mid-rollout, blue-green runs *two full versions side by side* — the live one (*blue*, behind an *active* service) and the new one (*green*, behind a *preview* service) — and cuts over *all at once* when you *promote*, with a *manual gate* in between.

[cols="1,2,2",options="header"]
|===
| | Canary (what you did) | Blue-green

| Traffic shift | Gradual, analysis-gated | Instant cutover on promotion
| Extra capacity | A small canary slice | A full second copy
| Reach for it when | You want to limit blast radius and can measure health mid-rollout | You want a clean instant switch after a full pre-flight on a preview URL
|===

== Challenge (optional)
⏱ *no hand-holding*

You have the whole progressive-delivery loop.
Try these on your own:

* *Add a fourth environment to the ApplicationSet.*
In your fork's `applicationset.yaml`, add a `qa` element (`env: qa`, `path: overlays/stage` to reuse an overlay) — then reason about what has to be true for a new Application to appear (hint: your `proj-{user}` allows only `{user}-dev/stage/prod` destinations, so a `{user}-qa` would be *refused* by the AppProject — a tenancy boundary, not a bug).
* *Read the analysis you cannot see in the UI.*
Re-run a failing canary and `oc logs` the analysis Job's pod (`oc get pods -n {user}-prod -l job-name`) — the probe prints exactly why it failed.
* *Stand up a blue-green Rollout.*
Deploy a second, throwaway Rollout using the `blueGreen` strategy (`activeService` + `previewService` + `autoPromotionEnabled: false`), push a new image, and watch the *preview* service point at the new version while *active* stays on the old — inspect both with `oc get rollout <name> -n {user}-prod -o jsonpath='{.status.blueGreen}'`.
Two things surprise almost everyone here, and both look like success.
First, `oc set image` cannot touch a Rollout at all (`no kind "Rollout" is registered for version "argoproj.io/v1alpha1"` — that verb only knows the built-in workload kinds), so ship the new version by editing your manifest and re-applying it.
Second, the paused Rollout is *not* held by `spec.paused`; that field is never set.
It is held by a *pause condition the controller wrote into `status`* — `phase: Paused`, `message: BlueGreenPause`, `pauseConditions: [{"reason":"BlueGreenPause", …}]` — with `status.blueGreen.activeSelector` still on the blue pod-hash while `previewSelector` has already moved to the green one.
Promoting means clearing that condition — normally a *Promote* button in a Rollouts UI, or the Argo Rollouts CLI plugin's `promote` command.
That plugin is not installed in this terminal (`oc plugin list` finds none), so signal the promotion on the object yourself — on the *status subresource*:
+
[source,sh,subs="attributes+"]
----
oc patch rollout <name> -n {user}-prod --subresource status \
  --type merge -p '{"status":{"pauseConditions":null}}'
----
+
*Active* cuts over to the green pod-hash within a second, `status.stableRS` becomes the green ReplicaSet, and blue scales to zero about 30 seconds later — the blue-green scale-down delay, which is why the old version is still there to fall back to for a moment.
Leave `--subresource status` off and the API server silently drops the status half of your patch: `oc` prints `patched (no change)` and the Rollout stays paused — the same false success `oc patch … -p '{"spec":{"paused":false}}'` hands you.
(A `'{"status":{"promoteFull":true}}'` patch on the same subresource promotes it too — the controller acts on that flag and clears it again.)
(The Rollouts controller serves blue-green with no extra infrastructure — same pod-ratio-free cutover you read about above.)
* *Break the ordering on purpose.*
Reason about what would happen if the migration hook were wave `3` instead of `1` — would the app come up before the schema was ready?

When you are done, run `ws verify {module-id}` to confirm production is a healthy Rollout.

[NOTE]
.Clean up when you are done
====
`ws prep {module-id} --yes` returns everything to a clean entry state: it purges your namespaces, restores your fork, and *removes the ApplicationSet before the Applications it generated* — so nothing gets re-created behind the reset, whatever order things are torn down in.
If you would rather remove just the ApplicationSet yourself, `~/argocd appset delete claims-{user}` deletes it and prunes its three Applications in one step.
====
