=== Brief

image::gitops-at-scale/gitops-at-scale-01-appset.svg["Two ways to run many environments: on the left, one hand-written Argo CD Application per environment, repeated again for every new service; on the right, a single ApplicationSet whose generator lists dev, stage and prod and stamps all three out of one Application template."]

*One Application per environment does not scale*

A dozen services across three environments is thirty-six Argo CD Applications — each a near-copy of another, differing in a repository path and a target namespace, and each one a thing a person has to create, keep consistent, and not forget.

An ApplicationSet removes that work. The Application is described once as a template, and a generator supplies the parameter sets to stamp it out: a list of environments, the folders in a repository, or the registered clusters. Change the template and every generated Application changes; add an environment and one line of input adds its Application. Environments that differ in kind are still one object — dev and stage are plain Deployments, production is a progressive-delivery Rollout, and each generated Application simply points at the folder that describes it.

*Shipping to production is still a bet*

GitOps gets a new version's manifests into an environment. It does not answer the question that makes release nights tense: is this version healthy under real conditions? Replacing every production pod at once bets the environment on the answer being yes.

Progressive delivery refuses that bet. A small slice of production runs the new version first, an automated analysis step judges it on evidence, and the slice widens only when that evidence arrives. When the analysis fails, the rollout aborts and the stable version — which never stopped serving — takes all the traffic back. Argo Rollouts is the controller that does this, and on this platform it shifts traffic by pod ratio, so no service mesh or traffic router has to be installed first.

*In this demo*

. Three environments generated from one ApplicationSet, with production running as a canary Rollout
. A new version shipped by editing Git, taking traffic in slices as its analysis passes
. A release whose analysis fails, aborted on its own with production never leaving the stable version
. The analysis record that made the call, read the way an incident review is read

=== 1 · One ApplicationSet, and production is a canary — 3 min

Parasol's claims service runs in three environments, and nobody authored an Argo CD Application for any of them — one ApplicationSet generated all three. Production is the one that differs: it runs as a Rollout rather than a Deployment.

image::gitops-at-scale/gitops-at-scale-05-what-you-built.svg["What the ApplicationSet ties together: the claims-config repository with its overlay and rollouts folders feeding a list-generator ApplicationSet, which generates claims-dev and claims-stage as Deployments and claims-prod as a Rollout, whose canary and analysis gate either promotes to 100 percent or aborts and rolls back to stable."]

*Why it matters*

"Onboard a new service" stops meaning "author more Applications by hand". The platform team owns one template, a line of generator input adds an environment, and the standards apply by construction rather than by review.

*On screen* — the student Argo CD: `claims-dev-{user}`, `claims-stage-{user}` and `claims-prod-{user}`, all three green. Then confirm from the terminal that production really is a progressive-delivery Rollout:

[source,sh,role=execute,subs="attributes"]
----
PROD={user}-prod
oc get rollout parasol-claims -n $PROD \
  -o jsonpath='prod is a {.kind}, strategy {.spec.strategy.canary.steps[*].setWeight}%, phase {.status.phase}{"\n"}'
----

*What just happened*

One object generated all three environments. The environment that had to differ differs by pointing at another folder, not by becoming another thing to manage.

=== 2 · Ship a new version: edit Git, the canary takes over — 4 min

Shipping version 1.1 of the claims service to production is a commit in the configuration repository. Argo CD syncs it, and the Rollout takes it from there — one slice of production at a time.

image::gitops-at-scale/gitops-at-scale-04-canary-progressing.png["A terminal polling loop following the production Rollout: successive timestamped lines move from step 0 of 5 Progressing with one canary pod of four, through a Paused step and analysis Running at step 3 of 5, to step 5 of 5 Healthy with analysis Successful and a closing line reading promoted to 100 percent."]

*Why it matters*

The new version earns its traffic. A quarter of production runs it while three quarters stay on the proven version, an analysis Job probes the canary's real readiness endpoint, and only that evidence widens the slice — so a release is measured rather than hoped for.

*On screen* — in Gitea, open `rollouts/claims-rollout.yaml` in `{user}/claims-config`, change the image tag from `1.0` to `1.1`, and commit. Then choose *Refresh* on `claims-prod-{user}` in Argo CD and follow the canary from the terminal, where the loop's `step N/5` and `analysis:` columns stand in for the Rollout view:

[source,sh,role=execute]
----
CANARY_STARTED=""
for i in $(seq 1 20); do
  oc get rollout parasol-claims -n $PROD \
    -o jsonpath='{.spec.template.spec.containers[0].image}' | grep -q ':1.1' \
    && { CANARY_STARTED=yes; break; }
  sleep 6
done
if [ -z "$CANARY_STARTED" ]; then
  echo "  ✗ the canary has not started — Argo has not synced the commit yet; press Refresh and re-run"
else
  for i in $(seq 1 24); do
    S=$(oc get rollout parasol-claims -n $PROD -o jsonpath='{.status.currentStepIndex}')
    P=$(oc get rollout parasol-claims -n $PROD -o jsonpath='{.status.phase}')
    A=$(oc get analysisrun -n $PROD --sort-by=.metadata.creationTimestamp -o jsonpath='{.items[-1:].status.phase}')
    echo "  $(date +%T)  step $S/5   $P   analysis:${A:-none}"
    [ "$P" = "Healthy" ] && [ "$S" = "5" ] && { echo "  ✔ promoted to 100%"; break; }
    sleep 7
  done
fi
----

*What just happened*

25% to the canary, a pause, 50%, then the analysis Job probed the new pods. It passed, and only then did 1.1 take 100%.

=== 3 · The analysis fails, and production does not — 4 min

The next release is the one that should never reach users. With the analysis verdict set to fail — the signal a build that spiked errors would produce — production accepts the new version as a canary and then refuses it.

image::gitops-at-scale/gitops-at-scale-05-canary-aborted.png["The same polling loop ending in rollout Degraded with analysis Failed and the line canary aborted, analysis failed; below it the Rollout's status message reads RolloutAborted, metric canary-health assessed Failed, and a curl against the production route answers prod health through the abort 200."]

*Why it matters*

Rollback stops being a person noticing, deciding and acting under pressure. The gate decides on evidence in the middle of the rollout, the stable pods never stop serving, and the outage that begins with "the deploy looked fine" does not begin.

Set the analysis verdict, so the failure lands at a known moment:

[source,sh,role=execute]
----
oc patch configmap gitops-at-scale-canary-control -n $PROD --type merge -p '{"data":{"verdict":"fail"}}'
----

*On screen* — in Gitea, change the same image tag from `1.1` back to `1.0`, standing in for the next build, commit, and *Refresh* `claims-prod-{user}`. Then watch the canary and the production route together:

[source,sh,role=execute]
----
for i in $(seq 1 20); do
  P=$(oc get rollout parasol-claims -n $PROD -o jsonpath='{.status.phase}')
  A=$(oc get analysisrun -n $PROD --sort-by=.metadata.creationTimestamp -o jsonpath='{.items[-1:].status.phase}')
  echo "  $(date +%T)  $P   analysis:${A:-none}"
  [ "$P" = "Degraded" ] && break
  sleep 7
done
oc get route parasol-claims -n $PROD -o jsonpath='{.spec.host}' \
  | xargs -I{} curl -ks -o /dev/null -w "users still served: %{http_code}\n" http://{}/q/health/ready
----

*What just happened*

The analysis failed at 50%, the Rollout aborted and returned to the stable version on its own, and the route answered `200` the whole time. No human acted, and no bad build reached a user.

=== 4 · The record of the decision — 1 min

Every abort leaves a record in the cluster: the AnalysisRun that judged the canary, the metric that failed, and the threshold it breached.

image::gitops-at-scale/gitops-at-scale-03-canary-analysis.svg["The canary sequence as a flow: a new version pushed via Git goes to 25 percent, pauses, widens to 50 percent, and reaches an analysis gate whose pass branch promotes to 100 percent and whose fail branch aborts and rolls back to stable."]

*Why it matters*

The decision is an object, not a story told afterwards. It reads like an incident review with the remediation already done — and it is the same evidence a release review or an auditor asks for.

[source,sh,role=execute]
----
oc get analysisrun -n $PROD --sort-by=.metadata.creationTimestamp \
  -o jsonpath='{.items[-1:].metadata.name}: {.items[-1:].status.phase} — {.items[-1:].status.message}{"\n"}'
----

== Frequently asked questions

*Is the canary really sending a quarter of the requests to the new version?*::
Roughly, and by pod ratio rather than by counting requests: at `setWeight: 25` with four replicas the controller runs one canary pod beside three stable ones, and the single Service load-balances across all four. Exact request percentages, header-based routing or mirroring need a traffic router — an OpenShift Route plugin or a service mesh — which this platform deliberately does not require, so progressive delivery works here with nothing extra installed.

*The canary aborted — why did production not go down?*::
A Rollout keeps the stable ReplicaSet running the whole time and only scales the canary up to the current weight. An abort scales the canary back to zero, and the stable pods — which never stopped serving — carry all the traffic again. "Rolled back" here means the new version was never promoted, not that anything was torn down and redeployed.

*Was that failure real, or forced?*::
The verdict is deterministic on purpose, so the abort lands at the same moment every time. The analysis behind it is real: the same Job probes the canary's live readiness endpoint, so a build that never becomes ready, or whose database wiring is wrong, fails the gate on its own merits.

*Canary or blue-green?*::
Canary when you want to limit the blast radius and can measure health during the rollout — a bad build fails at 50% rather than at 100% — at the cost of one extra slice of capacity. Blue-green when you want a clean instant cutover after a full pre-flight on a preview URL, and can afford two complete versions during the switch. Argo Rollouts serves both strategies.

*How is the ApplicationSet created — Argo CD has no screen for one?*::
With the Argo CD CLI, or by applying the object itself; Argo CD 3.4 has no create or read screen for ApplicationSets. That suits GitOps rather than hindering it: the ApplicationSet is a manifest in a repository like everything else, and it is normally delivered by GitOps too instead of being created by hand.

*One object describes the whole fleet* — and `dev`/`stage`/`prod` legitimately differ (prod is a Rollout), yet still come from this single ApplicationSet.

== 3. A canary rollout with automated analysis

Production runs claims `1.0` today.

Because prod is a *Rollout*, a new image is delivered as a *canary*: a small slice first, a pause, a wider slice, an *automated analysis* check, and only then 100%.

== 4. Break and fix: the analysis that saves production

A canary is only worth the toil if it *stops* a bad release.
So ship one.
You cannot reliably break a real image inside a timed lab, so production carries a deterministic *analysis control knob* — a ConfigMap in your prod namespace whose value the analysis Job honors.
Set it to `fail`, and the next canary's analysis reports a failure *exactly as if the new build had spiked errors under real traffic*.

First clear the knob (the regression is "resolved" — set `verdict` back to `pass`, with the command below or the same *Workloads* → *ConfigMaps* → `gitops-at-scale-canary-control` edit you used above):

[source,sh,role=execute]
----
oc patch configmap gitops-at-scale-canary-control -n $PROD --type merge -p '{"data":{"verdict":"pass"}}'
----

.Expected output
[source,texinfo]
----
configmap/gitops-at-scale-canary-control patched
----

Then revert the bad change: in the *Gitea* tab change the image tag back to `parasol-claims:1.1` and *Commit Changes* to `main` (message e.g. "Revert bad release; restore 1.1"), then open `claims-prod-{user}` in the {student_argo_url}[student Argo CD UI^] and press *Refresh* so Argo re-reads the revert.
If exercise 3 completed, you are reverting to the version that is *already* the stable one, so the Rollout clears the abort and returns to `Healthy` — no new canary, because production is already running `1.1`.
(If your exercise-3 canary never actually ran, this revert *starts* one instead — that is expected: in that case `1.1` is a genuinely new version for prod, and it earns its way in like any other.)

Now watch the recovery.
The proof is a *pair* of observations, not `Healthy` alone — a Rollout that never aborted is also `Healthy`.
An `AnalysisRun` that reached *Failed* must *exist* (the abort really happened) *and* the Rollout must be `Healthy` again.
The loop below lists *every* analysis this namespace has run, so it reads the same whether your revert started a fresh canary or not — a later `Successful` run does not erase the abort you are recovering from:

// capture note (2026-07-29): the gate changed from "the NEWEST AnalysisRun is Failed" to "a Failed
// AnalysisRun EXISTS". The old form printed a misleading "nothing to recover" in exactly the case the
// paragraph above blesses — a revert that starts a fresh (Successful) canary because exercise 3 never
// ran. The sample below is the SAME live run as before, re-rendered in the new form: the exercise-3
// canary (Successful) then the exercise-4 abort (Failed), oldest-first.

[source,sh,role=execute]
----
# Clearing the abort can take up to ~90s; if the loop ends still Degraded, press Refresh again + re-run.
RECOVERED=""
for i in $(seq 1 22); do
  P=$(oc get rollout parasol-claims -n $PROD -o jsonpath='{.status.phase}')
  PHASES=$(oc get analysisrun -n $PROD --sort-by=.metadata.creationTimestamp -o jsonpath='{.items[*].status.phase}' 2>/dev/null)
  ABORTS=$(printf '%s\n' "$PHASES" | tr ' ' '\n' | grep -cx Failed || true)
  echo "  $(date +%T)  rollout: $P   analyses so far: ${PHASES:-none}"
  [ "$P" = "Healthy" ] && [ "$ABORTS" -gt 0 ] \
    && { RECOVERED=yes; echo "  ✔ recovered — production Healthy again after the aborted release"; break; }
  sleep 7
done
if [ -z "$RECOVERED" ]; then
  if [ "$P" = "Degraded" ]; then
    echo "  ✗ still Degraded — Argo may not have re-read your revert yet; press Refresh and re-run this block."
  else
    echo "  ✗ nothing to recover: the Rollout is ${P:-unknown} and no AnalysisRun ever reached Failed —"
    echo "    the abort never happened (did your bad-build commit sync?). Re-run this exercise from the knob step."
  fi
fi
----

  08:50:14  rollout: Degraded   analyses so far: Successful Failed
  08:50:22  rollout: Healthy   analyses so far: Successful Failed
  ✔ recovered — production Healthy again after the aborted release
----

== 5. Blue-green: the other strategy
⏱ *~5 min* · know the second shape of a safe rollout, and when to pick it

Canary is one progressive-delivery strategy; *blue-green* is the other, and the same Argo Rollouts controller serves it.
Where a canary shifts traffic *gradually* (25% → 50% → 100%) and gates on analysis mid-rollout, blue-green runs *two full versions side by side* — the live one (*blue*, behind an *active* service) and the new one (*green*, behind a *preview* service) — and cuts over *all at once* when you *promote*, with a *manual gate* in between.

[cols="1,2,2",options="header"]
|===
| | Canary (what you did) | Blue-green

| Traffic shift | Gradual, analysis-gated | Instant cutover on promotion
| Extra capacity | A small canary slice | A full second copy
| Reach for it when | You want to limit blast radius and can measure health mid-rollout | You want a clean instant switch after a full pre-flight on a preview URL
|===

You do not have to choose blindly: the decision guide is in the wrap-up, and the Challenge below lets you stand up a blue-green Rollout yourself if you want to see the preview-then-promote cut live.

[.checkpoint]
****
✔ *Verify (understanding):* you can state, in one sentence each, when you would reach for a *canary* versus a *blue-green* rollout — and why request-level traffic percentages here would need a *traffic router* (Route plugin or mesh) rather than the pod-ratio splitting the canary used.
****

⏱ *no hand-holding*

You have the whole progressive-delivery loop.

* *Add a fourth environment to the ApplicationSet.*

* *Read the analysis you cannot see in the UI.*
Re-run a failing canary and `oc logs` the analysis Job's pod (`oc get pods -n {user}-prod -l job-name`) — the probe prints exactly why it failed.
* *Stand up a blue-green Rollout.*
Deploy a second, throwaway Rollout using the `blueGreen` strategy (`activeService` + `previewService` + `autoPromotionEnabled: false`), push a new image, and watch the *preview* service point at the new version while *active* stays on the old — inspect both with `oc get rollout <name> -n {user}-prod -o jsonpath='{.status.blueGreen}'`.
Two things surprise almost everyone here, and both look like success.
First, `oc set image` cannot touch a Rollout at all (`no kind "Rollout" is registered for version "argoproj.io/v1alpha1"` — that verb only knows the built-in workload kinds), so ship the new version by editing your manifest and re-applying it.
Second, the paused Rollout is *not* held by `spec.paused`; that field is never set.
It is held by a *pause condition the controller wrote into `status`* — `phase: Paused`, `message: BlueGreenPause`, `pauseConditions: [{"reason":"BlueGreenPause", …}]` — with `status.blueGreen.activeSelector` still on the blue pod-hash while `previewSelector` has already moved to the green one.
Promoting means clearing that condition — normally a *Promote* button in a Rollouts UI, or the Argo Rollouts CLI plugin's `promote` command.
That plugin is not installed in this terminal (`oc plugin list` finds none), so signal the promotion on the object yourself — on the *status subresource*:
+
[source,sh,subs="attributes+"]
----
oc patch rollout <name> -n {user}-prod --subresource status \
  --type merge -p '{"status":{"pauseConditions":null}}'
----
+
*Active* cuts over to the green pod-hash within a second, `status.stableRS` becomes the green ReplicaSet, and blue scales to zero about 30 seconds later — the blue-green scale-down delay, which is why the old version is still there to fall back to for a moment.
Leave `--subresource status` off and the API server silently drops the status half of your patch: `oc` prints `patched (no change)` and the Rollout stays paused — the same false success `oc patch … -p '{"spec":{"paused":false}}'` hands you.
(A `'{"status":{"promoteFull":true}}'` patch on the same subresource promotes it too — the controller acts on that flag and clears it again.)
(The Rollouts controller serves blue-green with no extra infrastructure — same pod-ratio-free cutover you read about above.)
* *Break the ordering on purpose.*
Reason about what would happen if the migration hook were wave `3` instead of `1` — would the app come up before the schema was ready?
