== The release that refuses to ship broken · 10 min

Parasol's notifications service becomes a versioned chart that installs in one command, refuses a broken upgrade without taking the service down, and rolls back in one more — the same packaging model every operator on this cluster arrived through.

[IMPORTANT]
.Prep — run before the session
====
This demo runs from the module's entry state rather than the finished lab. Stage it from the cockpit terminal:

[source,sh,role=execute]
----
ws prep packaging-distributing
----

That leaves the seeded fork, a prebuilt notifications image and its marker in place, with nothing installed — installing it is what the demo does.

Then build the chart the demo installs, so the session starts from a chart that is ready to go:

// `rm -rf` is what makes a second run behave like the first: `ws prep` cleans the namespace but
// never touches ~/parasol-notifications, and `helm create` overwrites only its own scaffold files.
[source,sh,role=execute,subs="attributes+"]
----
cd ~ && NS={user}-dev
rm -rf parasol-notifications
helm create parasol-notifications
cd parasol-notifications
# The chart ships the 1.0 notifications app — record that in Chart.yaml's appVersion
# (so `helm history` reads 1.0, not the placeholder `helm create` stamps in).
sed -i 's/^appVersion:.*/appVersion: "1.0"/' Chart.yaml
cat > values.yaml <<EOF
replicaCount: 1

image:
  # The prebuilt notifications image seeded into your namespace as an ImageStream tag.
  repository: image-registry.openshift-image-registry.svc:5000/$NS/parasol-notifications
  pullPolicy: IfNotPresent
  tag: "1.0"

imagePullSecrets: []
nameOverride: ""
fullnameOverride: ""
serviceAccount: {create: true, automount: true, annotations: {}, name: ""}
podAnnotations: {}
podLabels: {}
podSecurityContext: {}
securityContext: {}

service:
  type: ClusterIP
  port: 8080          # the service listens on 8080; containerPort follows this value

route:
  enabled: true       # publish an OpenShift edge Route (replaces the stock Ingress)

site: "$NS"           # origin-site marker the service echoes on GET /

resources:
  requests: {cpu: 50m, memory: 64Mi}
  limits: {cpu: 200m, memory: 128Mi}

livenessProbe:
  httpGet: {path: /health, port: http}
readinessProbe:
  httpGet: {path: /health, port: http}

autoscaling: {enabled: false, minReplicas: 1, maxReplicas: 100, targetCPUUtilizationPercentage: 80}
nodeSelector: {}
tolerations: []
affinity: {}
EOF
echo "values.yaml written"
cat > templates/deployment.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "parasol-notifications.fullname" . }}
  labels:
    {{- include "parasol-notifications.labels" . | nindent 4 }}
spec:
  {{- if not .Values.autoscaling.enabled }}
  replicas: {{ .Values.replicaCount }}
  {{- end }}
  selector:
    matchLabels:
      {{- include "parasol-notifications.selectorLabels" . | nindent 6 }}
  template:
    metadata:
      labels:
        {{- include "parasol-notifications.labels" . | nindent 8 }}
    spec:
      serviceAccountName: {{ include "parasol-notifications.serviceAccountName" . }}
      containers:
        - name: {{ .Chart.Name }}
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag | default .Chart.AppVersion }}"
          imagePullPolicy: {{ .Values.image.pullPolicy }}
          env:
            - name: SITE
              value: {{ .Values.site | quote }}
          ports:
            - name: http
              containerPort: {{ .Values.service.port }}
              protocol: TCP
          {{- with .Values.livenessProbe }}
          livenessProbe:
            {{- toYaml . | nindent 12 }}
          {{- end }}
          {{- with .Values.readinessProbe }}
          readinessProbe:
            {{- toYaml . | nindent 12 }}
          {{- end }}
          {{- with .Values.resources }}
          resources:
            {{- toYaml . | nindent 12 }}
          {{- end }}
EOF
echo "deployment.yaml updated (SITE env + values-driven probes)"
rm -f templates/ingress.yaml
cat > templates/route.yaml <<'EOF'
{{- if .Values.route.enabled }}
apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: {{ include "parasol-notifications.fullname" . }}
  labels:
    {{- include "parasol-notifications.labels" . | nindent 4 }}
spec:
  to:
    kind: Service
    name: {{ include "parasol-notifications.fullname" . }}
  port:
    targetPort: http
  tls:
    termination: edge
    insecureEdgeTerminationPolicy: Allow
{{- end }}
EOF
echo "ingress.yaml removed, route.yaml added"
cat > templates/NOTES.txt <<'EOF'
Thanks for installing {{ .Chart.Name }} (release {{ .Release.Name }}).
Reach the notifications service in your browser:

  oc get route {{ include "parasol-notifications.fullname" . }} -n {{ .Release.Namespace }} -o jsonpath='{"https://"}{.spec.host}{"\n"}'
EOF
echo "NOTES.txt replaced (Route-aware; no stale ingress refs)"
cd ..
helm lint parasol-notifications
----

The values point the chart at the prebuilt image in your namespace, publish an edge Route in place of the stock Ingress, and probe `/health`. The scaffolded `NOTES.txt` has to go with that Ingress — it still reads `.Values.ingress.*`, and every render fails while it does. `1 chart(s) linted, 0 chart(s) failed` means the chart is ready to install.

CAUTION: `ws prep packaging-distributing` returns the world to that entry state between runs. If a run left a failed release behind, run `helm uninstall parasol-notifications -n {user}-dev` first, then both blocks above again.

=== Brief

image::packaging-distributing/packaging-distributing-01-spectrum.svg["The packaging spectrum, left to right: raw manifests applied by hand, an OpenShift Template, Kustomize overlays and patches, a Helm chart with values and an OCI artifact, and an operator with a custom resource and controller — under an arrow showing that the day-2 responsibility encoded in the package increases along the way."]

*A running application is not a shippable one*

When Parasol's platform team hands the notifications service to a dozen internal teams, the question is not whether it runs. It is how each of those teams installs it, and what happens when version two ships.

Hand them a folder of YAML and every team edits it differently, nobody can say which version is in production, and an upgrade is a diff nobody reviews. A product's user experience is its install and upgrade, not only its runtime — and packaging is where operability gets encoded once, so every consumer inherits it.

*The spectrum, ordered by day-2 cost*

There is no single right way to package an application; there is a spectrum, and the axis that orders it is how much day-2 responsibility the package takes off a human. Raw manifests take none. An OpenShift Template parameterizes a one-shot create but never upgrades what it created. Kustomize renders overlays declaratively, with no release history and no rollback command. Helm adds versioned releases — upgrade, rollback, hooks and tests — acting when you run it, then stopping. An operator runs forever and reconciles continuously, at the highest authoring and lifetime cost.

Most applications are happiest in the middle: a chart is plenty. An operator earns its cost only when the continuous reconcile is the value.

=== 2 · An upgrade that fails without an outage — 4 min

The next release carries an ordinary configuration mistake: probes pointing at `/healthz`, a path this service does not serve. Helm holds the release open until the new pod is ready, it never becomes ready, and the upgrade fails — while the pods from revision 1 keep answering throughout.

[mermaid]
....
include::example$diagrams/packaging-distributing/06-failed-upgrade-rollback.mmd[]
....

*Why it matters*

A package that refuses to promote a release whose pods never became ready is a package that keeps a bad configuration away from customers. Recovery is not a change ticket either: the previous revision is still recorded, so going back is one command rather than a reconstruction.

// The 90-second wait is DELIBERATE and must not be shortened away. Both implementations of the
// service serve /health and nothing else (apps/parasol-notifications/node/server.js:71,
// apps/parasol-notifications/python/app.py:59), so /healthz 404s, the probe can never pass, and
// `--wait` holds the release open for the full timeout before reporting UPGRADE FAILED. Exercise 4
// of this page runs the identical command.
[source,sh,role=execute,subs="attributes+"]
----
cd ~ && NS={user}-dev
helm upgrade parasol-notifications ./parasol-notifications -n $NS \
  --set replicaCount=2 \
  --set 'livenessProbe.httpGet.path=/healthz' \
  --set 'readinessProbe.httpGet.path=/healthz' --wait --timeout=90s
----

`--wait` holds that release open for the full ninety seconds before Helm gives up, and the wait is the evidence. In a second terminal:

[source,sh,role=execute,subs="attributes+"]
----
oc get pods -n {user}-dev -l app.kubernetes.io/instance=parasol-notifications
curl -sk "https://$(oc get route parasol-notifications -n {user}-dev -o jsonpath='{.spec.host}')/health"; echo
----

One new pod sits at `0/1` beside the old ones at `1/1`, and the service answers `UP` in the middle of the failed upgrade. The first terminal then ends in `UPGRADE FAILED: context deadline exceeded` — the new pod never passed its probe, so Helm never promoted it. Now return to the last good revision:

[source,sh,role=execute,subs="attributes+"]
----
NS={user}-dev
helm rollback parasol-notifications -n $NS
helm history parasol-notifications -n $NS | tail -3
----

*What just happened*

`helm history` records the failed revision and the rollback beside it, so both the mistake and the recovery are auditable facts. Nothing was deleted, and the service never stopped answering.

=== 3 · The bundle behind a real operator — 3 min

Helm is one end of the spectrum and an operator is the other. Every operator on this cluster was installed through the same chain, so it can be read live — here, the Pipelines operator that runs the builds.

image::packaging-distributing/packaging-distributing-02-olm-anatomy.svg["The OLM install chain in two stages: what you choose — a CatalogSource catalog index image, the operator's PackageManifest with its channels, and a Subscription naming one channel — feeding what OLM takes over: an InstallPlan approved automatically or manually, a ClusterServiceVersion carrying the owned CRDs, controller Deployment and RBAC, and the operator Pod that reconciles the custom resources."]

*Why it matters*

Clicking *Install* on a catalog tile is not magic. A Subscription names a package and an upgrade channel, OLM resolves it into an InstallPlan, and that plan installs a ClusterServiceVersion declaring the custom resources the operator owns and the controller Deployment that reconciles them. The vocabulary is the same whether you are reading someone's operator or shipping your own.

[source,sh,role=execute]
----
oc get subscriptions.operators.coreos.com -n openshift-operators openshift-pipelines-operator-rh
CSV=$(oc get subscriptions.operators.coreos.com -n openshift-operators openshift-pipelines-operator-rh -o jsonpath='{.status.installedCSV}')
oc get csv "$CSV" -n openshift-operators -o jsonpath='owned CRDs: {range .spec.customresourcedefinitions.owned[*]}{.kind}{" "}{end}{"\n"}'
----

*What just happened*

A Subscription picked a channel, OLM installed a CSV, and that CSV owns the printed custom resource definitions and runs a controller that reconciles them forever. That reconcile loop is the whole cost of an operator, and it is worth paying only when the reconcile is the value. For a service like notifications, the chart from step 1 is the right answer.

== Frequently asked questions

*Why package with Helm at all — why not just apply the YAML?*::
Three things this demo showed: a versioned release with an auditable history, an upgrade and rollback lifecycle that recovered a broken release in one command, and tests and hooks every consumer inherits. Applying YAML over the top of the last deploy has no revision to go back to and no record of what changed.

*Why did the failed upgrade sit there for ninety seconds?*::
That is `--wait --timeout=90s` doing its job. Helm holds the release open until the new pods report ready; the bad probe path never passes, so it waits out the window and then fails the upgrade rather than promoting it. A shorter timeout fails faster — the length of the wait is a choice, the refusal is not.

*Where does this fit with GitOps and Kustomize?*::
They compose. Kustomize is bases and overlays with no release semantics — no history, no rollback command — while a chart is a versioned artifact with both. GitOps renders either one from Git, so the usual shape is a chart for the application and Git as the promotion gate between environments.

*How would other teams get the chart?*::
`helm package` produces a versioned archive, and a chart pushes to any OCI registry — including this cluster's integrated one, where a repository maps to `<namespace>/<name>`, so the chart lands beside the app image and is told apart by its version tag. Shipping to customers adds certification on top: chart-verifier for a chart, Preflight and Partner Connect for an operator bundle.

*Should we write an operator for our service?*::
Almost always no. An operator earns its cost when continuous reconcile is the value — repairing drift the moment it happens, orchestrating a stateful upgrade, failing over, or managing many instances from one spec. If day-2 is "occasionally upgrade with new values", a chart already does that, and an operator would be a reconcile loop with nothing to reconcile plus a controller to build, certify and maintain for the life of the product.

.Why an edge Route, not an Ingress or a plain Route
[%collapsible]
====
An Ingress is generic Kubernetes; on OpenShift a browser-facing app wants a *Route*.
A plain HTTP Route (or `oc expose`) gets HSTS-upgraded by the router and can dead-end in the browser; an *edge* Route with `insecureEdgeTerminationPolicy: Allow` terminates TLS at the router and serves both schemes.
This is the workshop-wide rule for any browser-facing app — the chart bakes it in so every install gets it right.
====

.Why one replica: the store lives inside each pod
[%collapsible]
====
Exercise 4 left this release at *two* replicas, and the notifications service is a demo notifier, not a durable queue (its README says so): it keeps its store *in memory, inside each pod*.
With two pods behind one Service, a POST lands on *one* of them and the very next GET can be answered by the *other*, which never saw the write.

[mermaid]
....
include::example$diagrams/packaging-distributing/12-per-pod-store.mmd[]
....

The test you just wrote asserts a *write-then-read-back round-trip*, a property this app only has at *one* replica.
So the upgrade passes `--set replicaCount=1` explicitly, and `--wait` holds it open until the scale-down has actually finished, so the hook and the test both see a single pod.

// SEV1 fix (smoke 2026-07-31, user1/cluster2): the smoke measured TWO Ready replicas serving the
// Service at `helm test` time on the literal path, and `helm test` failed 2/2 (the round-trip read
// hit the pod that never saw the POST). The cause is now settled: `helm rollback` (exercise 4) restores
// the TARGET revision's own recorded user-supplied values, and revision 2 was recorded with
// `replicaCount=2` — that is where the 2 replicas come back from, NOT from this `helm upgrade`
// inheriting a stale `--set`. That was the original (wrong) diagnosis and it had it backwards: a plain
// upgrade without `--reuse-values` DISCARDS the previous user-supplied values and re-reads values.yaml,
// which would have given 1. Rollback restoring a recorded override and upgrade discarding one are
// different mechanisms, and only the first explains the measurement. `--set replicaCount=1`
// is therefore explicit, so this step no longer depends on which revision's values happen to be
// recorded; `--wait` closes the scale-down race; the readback line makes the state the test depends on
// visible on the page. The per-pod store is a real property of apps/parasol-notifications (in-memory
// list, resets on restart) and is now taught rather than silently relied on.
[source,sh,role=execute]

# --set replicaCount=1: exercise 4 left this release at 2 replicas, and this app's store is per-pod.
# --wait: hold until the scale-down has finished, so the hook and the test see exactly one pod.
helm upgrade parasol-notifications ./parasol-notifications -n $NS \
  --set replicaCount=1 --wait --timeout=180s >/dev/null && echo "upgraded"
oc get deploy parasol-notifications -n $NS -o jsonpath='{.status.readyReplicas}{"/"}{.spec.replicas}{" ready\n"}'
# the post-upgrade hook Job seeds CLM-0000 around the time the upgrade returns — retry until it lands
SEEDED=""
for i in $(seq 1 15); do
  if curl -sk "https://$ROUTE/api/notifications" | grep -o 'CLM-0000'; then SEEDED=yes; break; fi
  sleep 2
done
if [ -z "$ROUTE" ]; then
  echo "ROUTE is empty — run the first block of this exercise again, then this one"
elif [ -z "$SEEDED" ]; then
  echo "CLM-0000 never appeared — the seed hook Job likely failed; read its logs: oc logs job/parasol-notifications-seed -n $NS"
fi

.Why the replica count mattered — and what it tells you about testing a packaged app
[%collapsible]
====
That scale-back was not a workshop quirk; it was the app being honest about itself.
A `helm test` asserts what the release *guarantees*, and this release guarantees "write it, then read it back" only while a single pod holds the store.
Two rules fall out of that, and they are worth more than the test:

* *If the app must scale, its state cannot live in the pod.* Move the store to a database or a shared cache and the same test passes at any replica count — the test never needed fixing; the *app* did.
* *If you cannot move the state, say so in the chart.* A single-replica constraint belongs in `values.yaml` comments and the chart's README, not in the author's head — otherwise the next consumer sets `replicaCount=3` and the limitation surfaces as a support ticket instead of a red test.

Making the test pass by retrying the read until it happens to land on the pod that holds the write would be the *wrong* fix: a flaky test that hides a real property of the workload is worse than no test.
====

[source,sh,role=execute]
----
oc whoami -t | helm registry login $REG -u $(oc whoami) --password-stdin --ca-file /tmp/service-ca.crt
----

.Expected output
[source,texinfo]
----
Login Succeeded
----

.Why a chart can go to an image registry, and why a token and a CA file
[%collapsible]
====
Modern Helm speaks *OCI*, the same artifact format as container images, so a chart can live in any OCI registry, including the cluster's *internal registry*.
That registry is an in-cluster Service (`$REG`) whose certificate is signed by the cluster's *service CA*, so you log in with your OpenShift token and trust that CA, the bundle saved to `/tmp/service-ca.crt`.
====

*Push the chart* into your namespace, where it lands as a tag:

[source,sh,role=execute]
----
helm push parasol-notifications-0.1.0.tgz oci://$REG/$NS --ca-file /tmp/service-ca.crt
----

.Expected output (pushed as an OCI artifact; note the sha256 digest)
[source,texinfo,subs="attributes+"]
----
Pushed: image-registry.openshift-image-registry.svc:5000/{user}-dev/parasol-notifications:0.1.0
Digest: sha256:ab9cc8033b1bf5be306912262264ea43626b49c37ba2f6e48b5e75b8c637204a
----

*What just happened:* the chart is tag *`0.1.0`* of the `parasol-notifications` repository, beside the app image's tag `1.0`.

.The integrated registry uses `<namespace>/<name>` — no deeper paths
[%collapsible]
====
On a general-purpose OCI registry (Quay, Harbor) you would push charts under a tidy prefix like `oci://registry/{user}-dev/charts`.
The OpenShift *integrated* registry maps repositories to ImageStreams — exactly `<namespace>/<name>` — so a deeper `.../charts/parasol-notifications` path is *rejected* (a `401` from the registry's token endpoint).
Push to `oci://<registry>/<your-namespace>` and let the chart's own name and version tag keep it distinct from the app image.
====

*Prove the round-trip:* pull the chart back and compare digests.

[source,sh,role=execute]
----
mkdir -p /tmp/pulled && cd /tmp/pulled
helm pull oci://$REG/$NS/parasol-notifications --version 0.1.0 --ca-file /tmp/service-ca.crt
cd - >/dev/null
----

.Expected output (the same sha256 digest — a verified round-trip)
[source,texinfo,subs="attributes+"]
----
Pulled: image-registry.openshift-image-registry.svc:5000/{user}-dev/parasol-notifications:0.1.0
Digest: sha256:ab9cc8033b1bf5be306912262264ea43626b49c37ba2f6e48b5e75b8c637204a
----

*What just happened:* the digests match: the registry holds exactly what you packaged. (Yours differ from the `ab9cc8…` sample, as a content hash should; only *your* two must match.)
Anyone with pull access can now `helm install oci://$REG/$NS/parasol-notifications --version 0.1.0`, no chart directory needed.

.Three things that vary by cluster, and what each one teaches
[%collapsible]
====
// version-anchor-ok: the releases ARE the lesson here — the paragraph teaches that the catalog index tag tracks the cluster's OpenShift minor, which cannot be said without naming two of them. They are illustrative examples, not a claim about the reader's cluster.
The index image tag *tracks your cluster's OpenShift minor* — `v4.22` on a 4.22 cluster, `v4.21` on a
4.21 one. That is the point of the line: the catalog you install from is versioned to the platform,
so an operator bundle is one that was tested against *your* OpenShift.

The *number* of InstallPlans depends on how long the cluster has lived. A freshly installed operator
shows *one*. On a cluster where the `latest` channel with `Automatic` approval has already upgraded
the operator, you will see *several* — OLM keeps the superseded plans beside the current one.

The *`CSVS` column can name several operators at once* — and this is the third trap of the exercise.
OLM approves a whole *resolution* in one InstallPlan: the operator you asked for plus everything it
pulled in with it. So `clusterServiceVersionNames` is an *array*, and yours is not necessarily first —
above, Pipelines is the *third* entry. That is why the command asks for `[*]` (every entry, comma-joined)
and not `[0]`: reading only the first name is the same *bare-index* mistake as trusting a bare
`subscription` name, and on a cluster whose baseline operators were approved together it would print
*nothing at all*. Keeping `NAME` in the `grep` means a no-match shows up as a header with no rows —
visible, not silent. Either way, the newest plan's CSV list *contains* the `installed CSV` you read a
moment ago.
====

== 8. Where OLM is going, and map your product onto the spectrum
⏱ *~5 min* · the direction of travel, then a decision with a straight face

Chart or operator for the notifications service? First, where operator packaging is heading.

*You'll end with:* OLM v1 proven live here, and the notifications service placed on the spectrum.

Exercise 7 was *classic OLM*. Its successor, *OLM v1*, is generally available and *running here*:

[source,sh,role=execute]

[cols="1,2,2",options="header"]
|===
| | Classic OLM (exercise 7) | OLM v1

| Objects | `Subscription` → `CSV` | `ClusterCatalog` + `ClusterExtension`
| Permissions | OLM grants what the bundle's CSV declares | A ServiceAccount and RBAC you supply
| Status | Drives OperatorHub today | The *direction*
|===

.How many catalogs to expect, and where they show in the console
[%collapsible]
====
How many catalogs you see depends on how the cluster was provisioned: clusters provisioned without the Red Hat Marketplace catalog (common on RHDP/bare-metal) show three; clusters with it show a fourth, `openshift-redhat-marketplace`.
`oc get clusterextension` may also list operators someone already installed the new way.
The current web console doesn't surface either object; reading `oc get clustercatalog` returning `Serving` entries is enough to know OLM v1 is real and coming.
====

*Now the decision, made honestly.* For a service you own, place it:

[cols="1,3,3",options="header"]
|===
| Package | Day-2 it covers | Reach for it when…

| Raw manifests | none — you own every change | it's a throwaway or a one-off
| Kustomize | environment overlays, GitOps diffs | Git is your control plane and there's no release lifecycle
| *Helm* | install / upgrade / rollback / test / hooks | you want *versioned releases* with an undo — *most apps*
| Operator | *continuous reconcile* — repair, stateful upgrade, failover | the *reconcile itself is the value*, not just install/upgrade
|===

[NOTE]
.The honest line: when *not* to write an operator
====
If your day-2 is "occasionally `helm upgrade` with new values," a *chart already does that*; an operator adds a reconcile loop with nothing to reconcile, and a controller to build, certify and keep alive.
Write one when it must *continuously* act: repair drift, orchestrate a stateful upgrade, fail over, or manage many instances from one spec.
The notifications service wants *Helm*, and saying so out loud is the senior move.
====
