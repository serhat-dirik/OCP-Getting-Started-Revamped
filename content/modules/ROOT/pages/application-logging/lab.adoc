== From an unreadable log to one query · 16 min

A claims service whose log no program can read becomes one that answers, in a single query, what happened to one customer's request across all three replicas.

[IMPORTANT]
.Prep — run before the session
====
This demo starts from the finished lab state. Stage it before the session:

[source,sh,role=execute]
----
adm solve application-logging
----

It leaves the claims service in `{user}-dev` running three replicas that emit structured JSON, with its logging configuration in the `claims-logging` ConfigMap, and takes a few minutes to roll out.

Confirm both halves of that state from the cockpit terminal once the staging returns:

[source,sh,role=execute,subs="attributes"]
----
oc -n {user}-dev get deploy parasol-claims -o jsonpath='ready={.status.readyReplicas}{"\n"}'
oc -n {user}-dev logs deploy/parasol-claims --tail=1 | jq -r '.loggerName'
----

The first line prints `ready=3` and the second a logger name. A `jq` parse error on the second means structured logging is off and the staging did not take: run the staging command again and wait for the rollout, rather than switching JSON on by hand — step 1 needs that setting already in place.

Sign the cockpit terminal in as `{user}`. A second screen showing the web console's *Logs* tab for one claims pod is worth having: the contrast between what that view can do and what a field query can do is the whole demo.

NOTE: Do not add `--prefix` to any `oc logs` command here. The staged service emits JSON, and `--prefix` glues a `[pod/…]` tag onto every record, which breaks `jq` and fills the screen with unreadable JSON. The `jq -r '[.hostName, .message] | @tsv'` form in step 1 stays readable and still names the pod.

CAUTION: Steps 1 and 4 send their own traffic rather than reading whatever is already in the log, and the count matters. An id taken from the existing log with `tail -1` is usually one the service generated for a single stray call and matches exactly one record. Nine requests landed on all three replicas in 3 of 3 measured trials; four landed on one pod.

NOTE: The captured comparison in step 2 is captured on purpose — turning the root level up live costs a rollout of about 30 seconds. If there is time for it, `oc set env deploy/parasol-claims QUARKUS_LOG_LEVEL=DEBUG` and back is the live version; rehearse it first. Step 3 needs no cluster at all, so it still works if the network does not.
====

=== Brief

[mermaid]
....
include::example$diagrams/application-logging/01-log-line-journey.mmd[]
....

*stdout is the interface*

A container's log is not a file. It is a stream, and the contract is one line long: write to standard output, and the platform takes it from there. CRI-O captures what the process writes, the kubelet stores it under `/var/log/pods/` and rotates it, and both `oc logs` and the console's *Logs* tab read that — on any cluster, with nothing installed and nothing configured.

Writing to a file inside the container instead fails three ways at once: the file is deleted with the pod, nothing collects it, and nothing rotates it, so a chatty service quietly fills the node's disk.

*A log line is data, not a sentence*

That free baseline stops at one pod at a time, and where it stops is not a platform limit — it is a decision made in the application. A line of prose can be read by a person and by nothing else. "Show me every WARN" becomes `grep WARN`, which also matches the word inside a message, and "which replica served this request" has no answer at all.

Structured records change both, and the switch is configuration rather than code: named fields to compare, the pod name carried in the record, and a correlation id put into the logging context so every line one request produced shares a value. OpenShift collects, rotates and serves whatever the application emits. Whether that is queryable is decided upstream of the platform, which is also why an aggregation tier is only worth its cost when the applications feeding it are disciplined.

*In this demo*

. Nine claim submissions spread across three replicas, and the two questions the resulting log cannot answer
. The log level as a dial rather than a rebuild, and the difference between turning up your own code and turning up everything underneath it
. A credential written into a log by an access log nobody thought about, and why shortening the line is not a fix
. One customer's request found across all three replicas with a single query

=== 1 · A log a human can read and nothing else can — 6 min

Nine claim submissions go through the Route and land across all three replicas. The log that comes back names the pod that wrote each line and still cannot say which line belonged to one caller — because every record in it is a sentence rather than data.

[mermaid]
....
include::example$diagrams/application-logging/02-correlate-across-replicas.mmd[]
....

*Why it matters*

An adjuster calls the service desk: a claim she approved twenty minutes ago still shows as submitted. The service runs three replicas, so her request was served by one of them, and nothing in the log says which one, or what else happened while it was being handled. That is not a missing product; it is a property of what the application chose to write.

Send the traffic, then project every replica's log down to the pod and the message:

[source,sh,role=execute,subs="attributes"]
----
CLAIMS=$(oc -n {user}-dev get route parasol-claims -o jsonpath='{.spec.host}')
for i in $(seq 1 9); do
  curl -s -o /dev/null -X POST -H 'Content-Type: application/json' \
    -d "{\"claimant\":\"Broker portal $i\",\"type\":\"home\",\"amount\":5$i.00}" \
    "http://$CLAIMS/api/claims"
done
oc -n {user}-dev logs -l app=parasol-claims --tail=-1 \
  | jq -R 'fromjson? // empty' \
  | jq -r 'select(.loggerName=="com.parasol.claims.ClaimResource" and .level=="INFO")
           | [.hostName, .message] | @tsv'
----

Which pod wrote each line is on the screen. Which line was hers is not, and neither is anything else that happened while her one request was in flight.

The reason is the shape of the line. Ask a program to read one that was written as prose:

[source,sh,role=execute]
----
echo '2026-08-22 19:00:14,318 INFO  [com.parasol.claims.ClaimResource] (executor-thread-1) claim CLM-1031 created type=auto amount=1850.00' | jq .
----

A parse error, and it is the honest state of most production logs. Here is the same event out of the running service, with one setting changed:

[source,sh,role=execute,subs="attributes"]
----
oc -n {user}-dev logs deploy/parasol-claims --tail=1 | jq .
----

*What just happened*

Named fields. `level` is a value to compare rather than a word to hope does not appear in a message, and `hostName` is the pod, so the record knows where it came from. Nothing was rebuilt and no new image was published: the JSON formatter is a configuration setting on the same running service.

=== 2 · One dial for your code, another for every layer beneath it — 4 min

The level is a runtime setting rather than a build-time one, and it is set per logger category. Turning up the application's own category and turning up the root level are different decisions, with a measurably different bill.

[mermaid]
....
include::example$diagrams/application-logging/05-level-dial-scope.mmd[]
....

*Why it matters*

"Give us more detail in production" is answered with "which detail". The category dial reaches your code. The root dial also reaches the HTTP layer, the bean container, the config system and the ORM — and the ORM at DEBUG prints every SQL statement it runs, with the query text and the bound parameters. That is a disclosure change as much as a volume change.

Start with who is writing to this log right now:

[source,sh,role=execute,subs="attributes"]
----
oc -n {user}-dev logs -l app=parasol-claims --tail=-1 \
  | jq -R 'fromjson? // empty' | jq -r '.loggerName' | sort | uniq -c | sort -rn
----

A short list, with the application's own logger at the top of it. The `io.quarkus` row is the boot banner, still in the buffer because `--tail=-1` reads the whole stream; everything below it is this application. The same command on the same service with the *root* level turned up instead is captured rather than run live, because it costs a rollout:

[source,sh,role=execute]
----
cat <<'EOF'
  98 io.quarkus.micrometer.runtime.binder.vertx.VertxHttpServerMetrics
  66 org.hibernate.SQL
  39 io.quarkus.arc.runtime.BeanContainerImpl
  30 jakarta.json.spi.JsonProvider
  18 io.smallrye.config
EOF
----

*What just happened*

Measured twice on this exact service: four identical requests cost *four* records with `com.parasol` turned up, and *ninety to a hundred and ten* with the root level turned up. The second line of the captured output is the part people miss — `org.hibernate.SQL` at DEBUG is every statement the ORM ran, written down. A bigger bill and a different set of things retained.

=== 3 · Truncation is not redaction — 3 min

A partner integration puts its API key in the query string, and an HTTP access log writes the full request line. Two obvious fixes are applied to the same captured line: one of them is arithmetic, the other names the field.

[mermaid]
....
include::example$diagrams/application-logging/06-truncation-versus-redaction.mmd[]
....

*Why it matters*

A credential in a log is an incident rather than a bug. Once it is written it is in a store, in a backup and possibly in a third-party index, and the remediation is a credential rotation rather than a code fix. Nothing on the cluster is touched here — the line lives in a shell variable:

[source,sh,role=execute,subs="attributes"]
----
ACCESS='10.235.0.2 - - [22/Aug/2026:19:17:32 +0000] "GET /api/claims?api_key=PARASOL-PARTNER-EXAMPLE-4f9a2c7b HTTP/1.1" 200 4798'
echo "$ACCESS" | cut -c1-60
echo "$ACCESS" | cut -c1-72
echo "$ACCESS" | sed -E 's/(api_key=)[^ &"]*/\1<redacted>/'
----

*What just happened*

Sixty characters looks safe. It is safe by nine characters, and nobody chose nine — the client IP happened to be ten characters long. One longer hostname, one different pod IP, one reworded message, and the same command prints part of the key. The third line is a redaction of the thing: it names the field, so the length stops mattering. The key in the example is synthetic and authenticates nothing.

=== 4 · One request, three pods, one query — 3 min

The adjuster's action is several calls behind one click. Each of them carries the same request id, that id is a field on every record they produce, and one query returns her whole story.

[mermaid]
....
include::example$diagrams/application-logging/04-what-you-built.mmd[]
....

*Why it matters*

Nothing in this query is a product. It is a filter, a level, a field and an id, all decided in application code — the half of a logging strategy that cannot be bought, and the half that decides whether a log aggregation tier is worth what it costs.

[source,sh,role=execute,subs="attributes"]
----
RID="parasol-adjuster-$(date +%s)"
CLAIMS=$(oc -n {user}-dev get route parasol-claims -o jsonpath='{.spec.host}')
for i in $(seq 1 9); do curl -s -o /dev/null -H "X-Request-Id: $RID" "http://$CLAIMS/api/claims"; done
curl -s -o /dev/null -H "X-Request-Id: $RID" -X POST -H 'Content-Type: application/json' \
  -d '{"claimant":"Dana Whitfield","type":"auto","amount":1850.00}' "http://$CLAIMS/api/claims"
oc -n {user}-dev logs -l app=parasol-claims --tail=-1 \
  | jq -r --arg rid "$RID" 'select(.mdc.requestId==$rid) | [.hostName,.level,.message] | @tsv'
----

*What just happened*

Ten records, three distinct pod names, one id: nine DEBUG lines for the reads and one INFO line for the state change. Together they are one request's entire history across every pod that touched it — the question step 1 could not answer, answered by a single query.

== Frequently asked questions

*Why does this demo not stand up a log aggregation stack?*::
Because the half that cannot be bought is this one, and because building the tier teaches the platform team's job rather than the application team's. Concretely, a LokiStack is six to eight pods and needs object storage — an S3-compatible bucket or an OpenShift Data Foundation tier — which is a dependency not every cluster has. The pieces are all Red Hat operators and worth naming: `cluster-logging` owns the ClusterLogForwarder that decides what is collected and where it goes, `loki-operator` runs the store with one tenant per namespace, and `cluster-observability-operator` supplies the console's query view. Every one of them sits downstream of what the application emits, and a collector cannot name a field nobody wrote.

*Is a request id just a trace id under another name?*::
Where distributed tracing is already in place, the trace id is the right value to put into the logging context, and no second identifier should be invented. But the two answer different questions — a trace says where the time went across services, a log says what exactly happened here — with different retention and different costs, and a sampled trace may not have kept the one request you care about. This mechanism is also what you use where there is no tracing at all, which is most brownfield estates.

*Can a leaked credential be handled by shortening the line?*::
No, and step 3 is the arithmetic. A character count is a coincidence you are relying on: it holds until a hostname gets longer, a client IP changes or a message is reworded. Redact by field name, by credential shape, or do not print the value at all — and treat "does this change log anything caller-supplied?" as a review question, because a leak is invisible at review time right up until the message changes.

*We changed the ConfigMap and nothing happened. Why?*::
A ConfigMap consumed as environment variables is read when the container starts, so changing the object does not reach a running process; `oc rollout restart` is the missing step. Mounted as a file, the content does update in place, which is one of the honest reasons to prefer a mounted file.

*What does structured logging cost?*::
More bytes per record, and a log that is harder to skim in a terminal. For any service whose logs will ever be collected, that trade is not close: the fields are what a collector, a store and a query language filter and group on, while free text arrives as one opaque string per line that every consumer has to write a parser for — and write again the day someone reorders the message.

=== Break it: a bad logging setting takes the app down

Log configuration is configuration, and configuration can be wrong.
Set an invalid level and watch what the platform does:

[source,sh,role=execute]
----
oc set env deploy/parasol-claims QUARKUS_LOG_LEVEL=VERBOSE
oc rollout status deploy/parasol-claims --timeout=90s
oc get pods -l app=parasol-claims
----

.Expected output (sample — the timeout is the point)
[source,texinfo]
----
deployment.apps/parasol-claims updated
Waiting for deployment "parasol-claims" rollout to finish: 1 old replicas are pending termination...
error: timed out waiting for the condition

NAME                              READY   STATUS    RESTARTS      AGE
parasol-claims-855cc98d4b-9x6hj   0/1     Error     3 (59s ago)   92s
parasol-claims-d9bb4f78f-9jdx8    1/1     Running   0             4m5s
----

Two pods, and the app is still answering.
That is not the break failing — it is the rolling update being *gated* by the readiness probe, so the old healthy pod keeps serving while the new one cannot start.
(If your deployment carries no readiness probe you will see one pod instead, and it will be the broken one. Either way, the pod you want is the newest.)

Read *why* it is failing.
This is the one question `oc logs` cannot answer without a flag, because the container you care about is already gone:

[source,sh,role=execute]
----
BAD=$(oc get pods -l app=parasol-claims --sort-by=.metadata.creationTimestamp -o name | tail -1)
echo "newest pod: $BAD"
oc logs $BAD --previous --tail=3
echo
echo "--- and the current container, failing the same way ---"
oc logs $BAD --tail=3
----

// Verified live on cluster-m24jn (OCP 4.22.8), 2026-08-22, twice: `--previous` came back with the
// rotation message on both runs, and there is NO blank line before the "---" banner — the oc
// message ends WITHOUT a newline, so the bare `echo` in the block supplies that one newline and
// nothing more. Leave the `echo` in: without it the banner glues onto the cri-o id (CC-3).
.Expected output (sample — `--previous` may or may not have content; see below)
[source,texinfo]
----
newest pod: pod/parasol-claims-65d7cb6dbb-6kgjz
unable to retrieve container logs for cri-o://341f587e3586d898cc7b127366724091cba4d5b7e542db28...
--- and the current container, failing the same way ---
	Maximum pool size: undefined/unknown
Configuration validation failed:
	java.lang.IllegalArgumentException: SRCFG00039: The config property quarkus.log.level with the config value "VERBOSE" threw an Exception whilst being converted Unknown level "VERBOSE"
----

There is the cause, in one line: `Unknown level "VERBOSE"`.
`--previous` reads the *previous generation* of the container in that pod, which is exactly what you want after a crash — but the container runtime rotates old container logs on its own schedule, so it often has nothing left to give you.
That is why the block reads the current container too: a pod in `CrashLoopBackOff` is failing the same way every time, so the live log says the same thing.

[IMPORTANT]
.`oc logs --previous` fails quietly
====
When the previous container's log has already been rotated away, `oc logs --previous` prints `unable to retrieve container logs for cri-o://…` *and exits 0* — measured on this cluster.
So a `cmd --previous || fallback` never runs its fallback.
Always run the two reads as two commands, the way the block above does.
====

Now fix it and confirm the app is whole:

[source,sh,role=execute]
----
oc set env deploy/parasol-claims QUARKUS_LOG_LEVEL-
oc rollout status deploy/parasol-claims --timeout=120s
oc get pods -l app=parasol-claims
----

The rollout returns almost instantly, because removing the variable restores the *previous* pod template — the healthy pod that never went away is already correct.

[NOTE]
.Three things in that output are worth a second look
====
`--prefix` tags each line with the pod that wrote it, and `--tail=-1` is not optional — with a *label selector*, `oc logs` shows only the last *10 lines per pod* unless you ask for everything (`oc logs --help` says so, and you will measure it in exercise 5).

The lines are grouped *by pod*, not ordered by time: `oc logs -l` concatenates one stream per pod. Two lines next to each other did not necessarily happen next to each other.

You may also see a claim number repeat across pods. Each new replica re-creates the schema and reloads the 30 seed claims at boot, against the same ephemeral database — so the numbering restarts. It is the shared throwaway database being shared, not a bug, and it does not affect anything you do with logs here.

== 2. Make it structured — a log line is data, not a sentence
⏱ *~7 min* · free text → JSON, and the first question free text cannot answer

Try to make a program read the log you have:

[source,sh,role=execute]
----
oc logs deploy/parasol-claims --tail=1 | jq .
----

.Expected output
[source,texinfo]
----
jq: parse error: Invalid numeric literal at line 1, column 11
----

That is the honest state of most production logs: a human can read them and nothing else can.
Fix it with one setting.

== 4. Never log a secret — and never call truncation a fix
⏱ *~8 min* · the deliberate leak, the arithmetic that "protects" it, and the real fix

Parasol's broker portal calls the claims API as a partner integration, and — as an enormous number of real integrations do — it puts its API key in the *query string*.
Nobody at Parasol logs that key. They do not have to.

Turn on the HTTP access log, which is a completely reasonable thing to do while investigating a routing problem:

[source,sh,role=execute]
----
oc set env deploy/parasol-claims QUARKUS_HTTP_ACCESS_LOG_ENABLED=true
oc rollout status deploy/parasol-claims --timeout=300s
----

Now make the call the broker portal makes:

[source,sh,role=execute]
----
CLAIMS=$(oc get route parasol-claims -o jsonpath='{.spec.host}')
curl -s -o /dev/null "http://$CLAIMS/api/claims?api_key=PARASOL-PARTNER-EXAMPLE-4f9a2c7b"
oc logs deploy/parasol-claims \
  | jq -r 'select(.loggerName=="io.quarkus.http.access-log") | .message' | tail -3
----

// Verified live on cluster-m24jn, 2026-08-22. The key is a synthetic partner key invented for this
// lab (note EXAMPLE in the middle) — it authenticates nothing anywhere, which is what lets the page
// print it. Never substitute a real-looking token here.
.Expected output (sample — the key is the point)
[source,texinfo]
----
10.234.0.2 - - [22/Aug/2026:19:17:30 +0000] "GET /q/health/ready HTTP/1.1" 200 220
10.235.0.2 - - [22/Aug/2026:19:17:32 +0000] "GET /api/claims?api_key=PARASOL-PARTNER-EXAMPLE-4f9a2c7b HTTP/1.1" 200 4798
----

There it is, in your log, in plain text, written by a component nobody thought of as handling secrets.
The access log's default pattern records the full request line, and the full request line contains the query string.

Two other things are worth noticing in those two lines.
The first line is the *kubelet's readiness probe* — turning on an access log means paying to record a health check every few seconds, per pod, forever.
And the key was written the moment the request arrived: no code of yours ran, no `log.info` was called.

=== The fix that is not a fix

The instinct, when you find this, is to show less of the line.
Run all three of these and compare:

[source,sh,role=execute]
----
ACCESS=$(oc logs deploy/parasol-claims \
  | jq -r 'select(.loggerName=="io.quarkus.http.access-log") | .message' | grep api_key | tail -1)
echo "$ACCESS" | cut -c1-60
echo "$ACCESS" | cut -c1-72
echo "$ACCESS" | sed -E 's/(api_key=)[^ &"]*/\1<redacted>/'
----

.Expected output (sample — from a run where the client IP was ten characters long)
[source,texinfo]
----
10.235.0.2 - - [22/Aug/2026:19:17:32 +0000] "GET /api/claims
10.235.0.2 - - [22/Aug/2026:19:17:32 +0000] "GET /api/claims?api_key=PAR
10.235.0.2 - - [22/Aug/2026:19:17:32 +0000] "GET /api/claims?api_key=<redacted> HTTP/1.1" 200 4798
----

Sixty characters looked safe.
On that run the key value started at character *70*, so sixty cleared it by *nine characters* — and nobody chose nine.
The client IP happened to be ten characters long; a router pod with a longer address, a different date format, or one more character in the path, and the same command prints part of the key.
Seventy-two, which looks just as arbitrary and just as safe, prints three characters of it.

This is not a hypothetical.
This repository ships `tools/lint/credential-redaction-guard.py` because a diagnostic here printed a model-gateway error through `cut -c1-200` and the credential in that message began at character *201* — safe by ten characters, by arithmetic, not by design.
The same sweep found the identical shape already live one module over, with the credential at character 75.

The third line is what a redaction looks like: it names *the field* and replaces its value, so the length of anything stops mattering.
Note what it is not, though — it is a fix applied while *reading*. The credential is still in the log.

=== The real fix, and the part you cannot undo

A credential does not belong in a URL.
URLs are logged by servers, proxies, routers and browsers, they end up in referrer headers and in bookmarks, and none of that is under your control.
Move it to a header, which the default access-log pattern does not record, and make the same call:

[source,sh,role=execute]
----
curl -s -o /dev/null -H 'Authorization: Bearer PARASOL-PARTNER-EXAMPLE-4f9a2c7b' \
  "http://$CLAIMS/api/claims"
oc logs deploy/parasol-claims \
  | jq -r 'select(.loggerName=="io.quarkus.http.access-log") | .message' | grep -v health | tail -1
echo -n "records still containing the key: "
oc logs deploy/parasol-claims \
  | jq -r 'select(.loggerName=="io.quarkus.http.access-log") | .message' | grep -c 'PARASOL-PARTNER'
----

.Expected output (sample)
[source,texinfo]
----
10.233.2.2 - - [22/Aug/2026:19:17:49 +0000] "GET /api/claims HTTP/1.1" 200 4798
records still containing the key: 1
----

The new request logged the path and nothing else.
The count is still `1`, and that is the most important line on this page: *the leak that already happened is still there.*
A log is append-only. Once a credential is written it is in the node's file, in whatever collected it, in a backup, and possibly in a third-party index — so the remediation is not a code fix, it is a *credential rotation*. The code fix only stops the next one.

[WARNING]
.The access-log pattern is a security surface
====
`quarkus.http.access-log.pattern` accepts `%\{i,HeaderName}`, which logs a *request header*.
Add `%\{i,Authorization}` to "help with debugging" and you have put every bearer token through the door you just closed — measured on this cluster, that pattern writes `hdr=Bearer PARASOL-PARTNER-EXAMPLE-4f9a2c7b` into the access log, in full.
Treat the pattern the way you would treat a log statement, because that is exactly what it is.
====

Turn the access log back off — you switched it on to investigate something, and leaving it on is both the bill from exercise 3 and the risk from this one:

[source,sh,role=execute]
----
oc set env deploy/parasol-claims QUARKUS_HTTP_ACCESS_LOG_ENABLED-
oc rollout status deploy/parasol-claims --timeout=300s
----

[.checkpoint]
****
✔ *Verify:* you found the key in an `io.quarkus.http.access-log` record, you saw `cut -c1-72` print part of it, the header-borne call logged a request line with no key in it, and `oc set env deploy/parasol-claims --list | grep -c ACCESS_LOG` now returns `0`.

With a *label selector*, `oc logs` defaults to the last *10 lines per pod*; without a selector it shows everything.
A correlation query that quietly reads 10 lines per pod will quietly find nothing.

The second is that the id came from the *caller*, and a caller can put anything in a header — including a newline, which forges a second, entirely fictional log record.
The claims service neutralizes it before it reaches the logging context; you can read the helper in `apps/parasol-claims/src/main/java/com/parasol/claims/LogSafe.java` and the test that pins it in `RequestIdFilterTest`.
The rule is the same one as exercise 4: transform *the thing*, at the boundary, before it can do anything.

== 6. Take it home: when logs must outlive the pod
⏱ *~3 min* · reading only — nothing to run

Everything you did in this lab works on any OpenShift cluster with nothing installed, and it stops at the same two edges: `oc logs` reads *one pod at a time*, and the node *rotates* what it keeps.
Delete the pod and its log goes with it.

The tier that removes those edges is a platform team's build, not a developer's, and it has three named pieces — `cluster-logging` (which owns the *ClusterLogForwarder*: what is collected, from where, filtered how, sent where), `loki-operator` (which runs the *LokiStack* that stores it, with one tenant per namespace), and `cluster-observability-operator` (which puts the query surface in the web console).
The concept page for this module describes what each one does and why this workshop does not stand one up: a LokiStack is six to eight pods and needs object storage.

The thing to take away is the direction of the dependency.
Every one of those components is *downstream* of the decisions you just made.
A collector cannot give a field a name that the application never emitted, a store cannot index a level the application never set, and no retention policy can un-write a credential.
The expensive tier is worth its cost exactly to the degree that what feeds it is disciplined — and that half is done in application code, by you, before any of it is installed.
