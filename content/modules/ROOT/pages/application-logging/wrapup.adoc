== What you built

You took the claims service from a log that only a human could read to one that answers questions.
You read the free baseline and found its edge — `oc logs` shows one pod at a time and the node rotates what it keeps — then killed the app with an invalid log level and recovered the reason from a container that no longer existed.
You turned free text into one JSON object per record and asked it things `grep` cannot answer, moved the level dial into a ConfigMap and turned *your* category up without turning the framework up with it, measured what the blunt version costs and saw it put database queries in the log, leaked a partner's API key through an access log and proved that truncating the line was arithmetic rather than safety, and finally followed one user action across three replicas with a single query.

The one idea under all of it: *a log line is data a machine reads, and what is in it was decided by your application.*
No collector can name a field you never emitted, no store can index a level you never set, and no retention policy can un-write a credential.

== Map to your org

Take these back to how your teams work today:

. *Pick one service and ask what its log could answer.*
Not "does it log" — every service logs. Ask: could you find every record for one customer's request, across every replica, without knowing which pod served it?
Could you count errors by type without a regular expression?
If the answer to both is no, that service's log is a diary, not an instrument — and the fix is a week of work in the application, not a purchase.
. *Find out who has turned DEBUG on in production, and when they last turned it off.*
You measured the cost: the same four requests, four records against about a hundred.
For a real service of yours, what is the standing level, who can change it, and does changing it require a deployment?
Then ask the harder half: when the level goes up, *what starts being written down* — query text, headers, payloads — and who agreed to retain that?
. *Trace where a credential could enter your logs, and assume one already has.*
Query strings, access-log patterns, exception messages that echo a request, a `toString()` on a config object.
For each one, is the control a *redaction of the thing*, or a character count someone chose once?
And a fire drill worth running: if a token appeared in your logs this morning, who would know, how would they find every copy, and how long would rotating it take?

== When *not* to do it this way

Everything here can be over-applied, and a logging discipline that nobody follows is worse than a simple one that everybody does.

* *Structured logging is not free, and it is not always the point.*
JSON is more bytes per record and it is genuinely harder to read in a terminal at three in the morning.
For a batch job that runs nightly, prints twenty lines and is read by exactly one person, plain text is the right answer.
The trade turns the moment anything *collects* the log — because then the consumer is a machine, and a machine needs fields.
* *A correlation id you do not propagate is theatre.*
This lab put an id on one service's records. In a real call chain it has to be *passed on* — into the outgoing HTTP call, the message header, the job record — or you have a beautifully labelled log for the first hop and nothing after it.
If you are not going to plumb it through, be honest that you have bought a per-service id, not a trace. And note the neighbouring tool: distributed tracing (a separate module) exists precisely for the cross-service version of this question, and a trace id is usually the right thing to put in the MDC rather than inventing a second identifier.
* *Do not log your way to a metric.*
Counting log lines to answer "how many claims per minute" is expensive and slow: you are paying storage and query time for a number a counter would give you for free.
If the question is *how many* or *how fast*, it is a metric. Logs answer *what exactly happened, to this one thing*.
* *Centralized aggregation is a real bill, and the tier is not the point.*
A LokiStack is six to eight pods and object storage, and somebody has to run it, size it, and set retention.
For a small estate the free baseline plus disciplined application logs is genuinely enough — and if the applications are *not* disciplined, buying the tier just means paying to store a haystack.
Add the tier when a question you actually need answered spans more than one pod's lifetime; not before.
* *And be honest about retention as a liability.*
Everything you keep is something you may have to produce, secure, and explain.
"Keep everything forever" is not caution, it is an unpriced risk.

== Go deeper

* *Observability, Health & Scale* — the two signals this module hands off to and from: metrics for *how many and how fast*, traces for *where the time went across services* (a separate module).
* *Config, Secrets & Multi-Environment* — the ConfigMap you put your log level in, and the promotion pattern that lets stage run at DEBUG while production runs at INFO (a separate module).

* Red Hat documentation: the OpenShift *Logging* guide (`ClusterLogForwarder`, `LokiStack`, per-tenant access), and the *Quarkus* logging reference for categories, handlers, JSON output and the MDC.
