Now build the *neutral agent* — the client that talks to the model and to the MCP server running in your namespace. Create a small `ask-agent` helper once; you'll reuse it for every question:

[source,sh,role=execute]
----
cat > ask-agent <<'EOF'
#!/usr/bin/env bash
# ask-agent [--allow-writes] "<prompt>"  — run the neutral mcp-agent-cli as a one-shot pod and
# print its tool-call trace + answer. The client holds NO kubeconfig: it reaches the model over
# MaaS and the cluster ONLY through the MCP server (which runs as the scoped mcp-agent SA).
set -euo pipefail
NS="${NS:-$(oc project -q)}"
RO=true; [[ "${1:-}" == "--allow-writes" ]] && { RO=false; shift; }
PROMPT="$*"; POD="ask-agent-$RANDOM"
ARGS=$(jq -cn --arg w "$([[ $RO == false ]] && echo --allow-writes || true)" --arg p "$PROMPT" \
  'if $w=="" then [$p] else [$w,$p] end')
jq -n --arg pod "$POD" --arg img "$AGENT_CLI_IMAGE" --argjson args "$ARGS" --arg ro "$RO" \
  '{apiVersion:"v1",kind:"Pod",metadata:{name:$pod,labels:{app:"mcp-agent-cli-run"}},
    spec:{restartPolicy:"Never",activeDeadlineSeconds:240,containers:[{name:"cli",image:$img,imagePullPolicy:"Always",args:$args,
    envFrom:[{configMapRef:{name:"maas-config-env"}},{secretRef:{name:"maas-credentials"}}],
    env:[{name:"MCP_SERVER_URL",value:"http://kubernetes-mcp-server:8080/sse"},{name:"MCP_READ_ONLY",value:$ro}],
    resources:{requests:{cpu:"100m",memory:"384Mi"},limits:{cpu:"1",memory:"768Mi"}}}]}}' \
  | oc apply -f - >/dev/null
echo "· agent pod $POD running (the model round-trip can take up to a minute)…"
# fail fast on a pull-dead pod instead of waiting out the full timeout
for _ in $(seq 1 12); do
  ph=$(oc get pod "$POD" -n "$NS" -o jsonpath='{.status.phase}' 2>/dev/null || true)
  [[ "$ph" == Running || "$ph" == Succeeded || "$ph" == Failed ]] && break
  wr=$(oc get pod "$POD" -n "$NS" -o jsonpath='{.status.containerStatuses[0].state.waiting.reason}' 2>/dev/null || true)
  if [[ "$wr" == ImagePullBackOff || "$wr" == ErrImagePull ]]; then
    echo "✗ agent image could not be pulled ($wr) — check that AGENT_CLI_IMAGE is reachable: $AGENT_CLI_IMAGE"
    oc delete pod "$POD" -n "$NS" >/dev/null 2>&1 || true
    exit 1
  fi
  sleep 2
done
oc wait --for=jsonpath='{.status.phase}'=Succeeded pod/"$POD" -n "$NS" --timeout=180s >/dev/null 2>&1 \
  || oc wait --for=jsonpath='{.status.phase}'=Failed pod/"$POD" -n "$NS" --timeout=3s >/dev/null 2>&1 || true
echo "────────────────────────────────────────────────────────────────────"
oc logs "$POD" -n "$NS"; echo "────────────────────────────────────────────────────────────────────"
oc delete pod "$POD" -n "$NS" >/dev/null 2>&1 || true
EOF
chmod +x ask-agent
export PATH="$PWD:$PATH"
echo "ask-agent ready"
----

You don't need to read every line. The wiring is the lesson, and it's in the `spec`: the agent pod gets the *model* endpoint and key (`envFrom` the `maas-config-env` ConfigMap and the `maas-credentials` Secret) and the *MCP server* address (`MCP_SERVER_URL`) — *and nothing else*. No kubeconfig, no cluster token it uses. Its only route to the cluster is asking the MCP server, which acts as `mcp-agent`.

[NOTE]
.If an "ask" fails fast instead of thinking for a minute
====
A genuine model round-trip takes up to ~a minute, and `ask-agent` waits up to ~3 minutes for the one-shot pod to finish. But if the agent *image can't be pulled*, the helper's pre-check catches the `ImagePullBackOff` in the first few seconds and *fails fast* — `agent image could not be pulled` — rather than leaving you staring at a 3-minute hang. If you see that, the problem is image/registry access, not the model: check `echo $AGENT_CLI_IMAGE` and `oc get pod -l app=mcp-agent-cli-run -n $NS`.
====

== 2. Diagnose the broken deployment — read-only
⏱ *~7 min* · watch the agent call the cluster, then verify its claims yourself

Ask the agent why the claims service is broken. Phrase it the way you'd brief a junior engineer — *tell it what to inspect*, and it will call the read tools in order:

[source,sh,role=execute]
----
ask-agent "Inspect namespace $NS to find out why the parasol-claims pod is Running but not Ready. List the pods in that namespace, get the parasol-claims deployment, and read the recent events. Then explain the root cause in one or two sentences, quoting the readinessProbe path."
----

The sample namespace in the captured output below is `user3-dev`; *yours* is `{user}-dev` — read the *shape*, not the exact name.

.Shape of the output — the header, mode line and tool names are fixed; the results depend on what your cluster returns, and the answer is the model's own prose
[source,texinfo]
----
mcp-agent-cli
  model:     <your cluster's configured model>
  mcp server: http://kubernetes-mcp-server:8080/sse  (1 wired)
  mode:      READ-ONLY (mutating tools hidden from the model)

TOOL-CALL TRACE (3 calls)
  [1] pods_list_in_namespace
      args:   {"namespace": "user3-dev"}
      result:
        ... parasol-claims-665b7fcfc8-...   0/1   Running ...
  [2] resources_get
      args:   {"apiVersion": "apps/v1", "kind": "Deployment", "name": "parasol-claims", "namespace": "user3-dev"}
      result: {... "readinessProbe":{"httpGet":{"path":"/q/health/reddy","port":8080} ...}
  [3] events_list
      args:   {"namespace": "user3-dev"}
      result: <recent events — see the note below on what this call does and does not return>

read-only: no mutating tools were offered by the server.

ANSWER
  <the model's own words, built from what those three calls returned — on a grounded run it
   names the readinessProbe path /q/health/reddy and the failing status code>
----

Two things just happened, and both matter:

* *The agent called the cluster, it did not guess.* The `TOOL-CALL TRACE` is the receipt — three read tools, with the exact arguments and the exact results. The answer is built from what those calls returned, not from the model's imagination.
* *It ran with eyes only.* `mode: READ-ONLY` and `no mutating tools were offered by the server` — the MCP server, started `--read-only`, advertised only read tools, so there was nothing to write with even if the model wanted to.

[NOTE]
.`events_list` may not hand the agent the 404 — and that changes nothing about the diagnosis
====
The probe failure is an event on the *Pod*, not on the Deployment, and it is one line among everything else the namespace has emitted recently. Depending on what the model asks for and how much of the result it keeps, the `404` may or may not appear in that third call's result — and the model may reach the same conclusion from `resources_get` alone, since the wrong path is right there in the deployment spec.
Do not treat "the 404 was in the agent's trace" as the thing that proves the diagnosis. The thing that proves it is *your own* check, next — which reads the event off the pod where it actually lives.
====

[NOTE]
.Grounding is engineered, not guaranteed
====
You *told* the agent what to inspect — "list the pods, get the deployment, read the events." That imperative phrasing is deliberate: models decide *whether* to call a tool, and a terse question like "why is parasol-claims broken?" can make some models *print a tool call as text* and answer from memory instead of actually calling it (you'd see `TOOL-CALL TRACE (0 calls)` and a bracketed tool name in the answer).
That is not the model being broken — it is a reminder that *grounding is something you engineer*, through clear phrasing, the system prompt, and (in production) tool-forcing settings. When an agent gives a grounded answer, someone made it ground. Try the terse version in the challenge and watch the difference.

== 3. Grant a scoped write, and let the agent fix it
⏱ *~9 min* · give it hands — the smallest hands that do the job

Diagnosing is safe; *fixing* means *writing*, and writing is a decision *you* make. You'll grant `mcp-agent` a *narrow* write, enable the write path, watch the client's read-only seatbelt, then let the agent loose on the one bad field — and *review what it actually did to the cluster*, which is the half of this exercise that matters most.

First, the human grant: a small `deployer` Role that can `patch`/`update` *deployments* — in *this* namespace, and nothing else. Not `edit` (which can touch secrets), not cluster-wide.

[source,sh,role=execute,subs="attributes"]
----
oc apply -f - <<EOF
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: mcp-agent-deployer
  namespace: {user}-dev
rules:
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list", "watch", "update", "patch"]   # no secrets, no scale, no delete
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: mcp-agent-deployer
  namespace: {user}-dev
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: mcp-agent-deployer
subjects:
  - kind: ServiceAccount
    name: mcp-agent
    namespace: {user}-dev
EOF
----

// deployment, update the probe path, apply, confirm"), one cluster's served model returned
// TOOL-CALL TRACE (0 calls) on 2 of 2 attempts — it printed resources_get(...) /

//   - "use your tools — do not print tool calls as text" targets the 0-calls mode, and is the weaker

//   - "keep every other field, including the container image, exactly as it was returned" targets the

The phrasing is doing two jobs, and both are the *grounding is engineered* idea from exercise 2, applied to a *write*: *use your tools — do not print tool calls as text* pushes the model to actually call the mutating tool rather than describe it, and *keeping every other field, including the container image, exactly as it was returned to you* pushes it to edit the manifest it read rather than hand-author a replacement. Neither is a guarantee. On some models the write is the least reliable call in the whole loop — the reads fire every time and the write never does, no matter how the ask is worded — which is exactly what the three landings below are about.

That is the entire reason the scoped write is narrow: the blast radius of a confident mistake is one deployment in one namespace.

== 4. The forbidden test — watch RBAC deny the agent
⏱ *~5 min* · the whole module in one denial

The agent can now read and patch *your* namespace. Point it at *someone else's* and watch the platform stop it.
The *server* still offers every tool (you removed `--read-only` in exercise 3), but this ask runs the client in its default *read-only* mode again — no `--allow-writes` — so the client hides the six mutating tools and you'll see its `hid 6 mutating tools` line in the output. None of that decides what happens next: for the *read* calls the agent is about to make, the only thing standing between it and a neighbour's namespace is *RBAC on `mcp-agent`*.

// NEIGHBOUR must never be the reader's OWN namespace. user1 is a normal attendee slot, so a
// hardcoded `user1-dev` made this exercise silently INVERT for whoever holds it: the
// "forbidden" call would read their own namespace and succeed, killing the module's climax.
//
// 2026-08-12 — the FIRST fix for that was `[ "{user}" = "user1" ]`, and it was dead code.
// {user} is a BUILD-TIME Antora attribute; the identity that decides whether the probe is
// self-directed is the RUNTIME login, and nothing makes those agree. The demos cockpit
// renders {user} as the deliberate non-identity `your-user`
// (gitops/workshop-config/templates/showroom-demos.yaml), so the comparison was ALWAYS false
// and the branch could never be taken — a presenter logged in as user1 got `user1-dev`, their
// OWN namespace, and the beat demonstrated ACCESS where it means to demonstrate DENIAL.
// Proven by impersonation on cluster-m24jn: user1 listing user1-dev succeeds, user2-dev is
// Forbidden. `oc whoami` is the only source that knows who is actually logged in, so the test
// is now made there. Do NOT reintroduce a comparison against {user}, and note the block
// deliberately carries NO subs="attributes" — that is what keeps a build-time identity out.
The first line asks *the cluster* who you are, then picks a namespace that is therefore *never yours*: everyone probes `user1-dev`, except whoever is logged in as `user1`, who probes `user2-dev` instead. That matters — pointed at your own namespace the agent would succeed, and the whole point of the exercise is watching it be refused.

[source,sh,role=execute]
----
ME=$(oc whoami)
NEIGHBOUR=user1-dev
if [ "$NEIGHBOUR" = "${ME}-dev" ]; then NEIGHBOUR=user2-dev; fi
echo "logged in as ${ME} - probing ${NEIGHBOUR}, which is not yours"
ask-agent "Find out what is running in the neighbouring namespace $NEIGHBOUR. List the pods in namespace $NEIGHBOUR, and also read the recent events in namespace $NEIGHBOUR. Then report what you found."
----

The sample namespace in the captured output below is `user3-dev`; *yours* is `{user}-dev` — read the *shape*, not the exact name. The namespace it is *refused* on is whatever `$NEIGHBOUR` resolved to for you.

* *The API server said no.* `pods is forbidden: User "system:serviceaccount:user3-dev:mcp-agent" cannot list resource "pods" ... in the namespace "user1-dev"`. `mcp-agent` has a `view` RoleBinding in *your* namespace and *nowhere else*, so a read of `user1-dev` is a `403` — enforced by the platform, underneath the agent.

=== Beat 2 — A scoped write, and the agent fixes the probe

// The --allow-writes prompt in this beat is the twin of exercise 3's and must stay identical to it.
// Why it names its tools — and the fact that it is UNMEASURED as a fire-rate fix — is recorded once,
// in the GROUNDING comment above the exercise-3 prompt. Presenter fallback: the recovery NOTE below.
// Do NOT put a // comment between a `+` continuation and its block: measured 2026-08-05, it ends the
// list item and the block silently detaches from the Do:: entry.
[demo-block]
[TIME 4m]
Say:: "Diagnosing is safe. *Fixing* means writing. So I grant the agent's identity a *scoped* write — patch deployments, in *this* namespace, nothing else — and let it fix the one bad field."
Show:: The `deployer` Role + binding applied; the agent's write attempt; *then the cluster's own answer* — pod state, probe path, image — and the `managedFields` naming who wrote.
// The namespace comes from $NS — set by SHARED SETUP A from `oc whoami` — and the block below
// deliberately carries NO subs="attributes". `{user}-dev` there rendered `your-user-dev` on the
// demos cockpit (that ConfigMap's non-identity placeholder), so the apply died on a namespace
// that does not exist, mid-beat, in front of the room. Same reason as beat 3's neighbour probe.
// The heredoc is UNQUOTED (`<<EOF`, not `<<'EOF'`) so $NS actually expands — quoting it back
// would ship `namespace: $NS` to the API server.
// These lines sit ABOVE the Do:: rather than between its `+` and its block, which is the trap the
// header of this file warns about and this very beat used to demonstrate — see the fix commit.
Do:: Grant the narrow write, enable the write path, and let the agent fix it:
+
[source,sh,role=execute]
----
oc apply -f - <<EOF
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: {name: mcp-agent-deployer, namespace: $NS}
rules:
  - {apiGroups: ["apps"], resources: ["deployments"], verbs: ["get","list","watch","update","patch"]}
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: {name: mcp-agent-deployer, namespace: $NS}
roleRef: {apiGroup: rbac.authorization.k8s.io, kind: Role, name: mcp-agent-deployer}
subjects: [{kind: ServiceAccount, name: mcp-agent, namespace: $NS}]
EOF
----

[source,sh,role=execute]
----
oc patch deploy kubernetes-mcp-server -n $NS --type=json \
  -p '[{"op":"replace","path":"/spec/template/spec/containers/0/args","value":["--port","8080","--toolsets","core,config"]}]'
oc rollout status deploy/kubernetes-mcp-server -n $NS --timeout=90s
ask-agent --allow-writes "Use your tools — do not print tool calls as text. In namespace $NS: first call resources_get for the parasol-claims Deployment. Then call resources_create_or_update with that exact manifest and one single change — readinessProbe.httpGet.path from /q/health/reddy to /q/health/ready — keeping every other field, including the container image, exactly as it was returned to you. Then confirm what you changed."
oc get pods -n $NS -l app=parasol-claims
oc get deploy parasol-claims -n $NS -o jsonpath='probe path: {.spec.template.spec.containers[0].readinessProbe.httpGet.path}{"\n"}image:      {.spec.template.spec.containers[0].image}{"\n"}'
----
"It could only touch that deployment because I granted the write. Now the part people skip: *I do not take its word for it* — I read the cluster. If it's green, great. If it narrated instead of acting, I approve its proposed patch and apply it myself. And if it *acted and got it wrong* — a placeholder in the image field while its answer says 'done' — that is the most useful thing that can happen in this room, because it's exactly why the grant is one verb on one resource in one namespace."

=== Beat 3 — RBAC denies the neighbouring namespace

[demo-block]
[TIME 4m]

// The neighbour MUST be derived at RUNTIME from `oc whoami`, never compared against
// the build-time {user} attribute. See the identical block in exercise 4 for the
// measurement that forced this — a page attribute cannot know who is logged in.
// Above the Do::, not between its `+` and its block — see the header note on that trap.
Do:: Point the agent at a namespace it was never granted. The first line asks *the cluster* who you are and picks a namespace that is therefore never yours:
+
[source,sh,role=execute]
----
ME=$(oc whoami)
NEIGHBOUR=user1-dev
if [ "$NEIGHBOUR" = "${ME}-dev" ]; then NEIGHBOUR=user2-dev; fi
echo "logged in as ${ME} - probing ${NEIGHBOUR}, which is not yours"
ask-agent "Find out what is running in the neighbouring namespace $NEIGHBOUR. List the pods in namespace $NEIGHBOUR, and also read the recent events in namespace $NEIGHBOUR. Then report what you found."
----
"It *tried* — the trace shows the call — and the API server returned `is forbidden`. Not because the agent's software chose to behave, but because `mcp-agent` has no `view` in that namespace. *RBAC is the boundary.* Your agent is a junior engineer with root, unless you stop it — so you scope it with RBAC, not trust."

[NOTE]
.Reset between runs
====
`ws prep ai-assisted-development --yes` returns the world to the entry state: the broken `parasol-claims` (probe `/q/health/reddy`, `0/1`), the MCP server back to `--read-only`, and `mcp-agent` back to `view`-only (your `deployer` grant removed).
It resolves the attendee from `oc whoami`, so it touches the namespace you have been presenting from and no other — `--user {user}` is deliberately NOT written here, because on the demos cockpit `{user}` renders `your-user` and the command dies naming a user that does not exist.
`ws prep` resets the *cluster*, not your *shell*: `$NS`, `$AGENT_CLI_IMAGE` and `ask-agent` survive it in the terminal you created them in. A *new* terminal tab has none of them, and `ask-agent: command not found` is what that looks like — re-run the three blocks under *Set up your terminal first* rather than re-prepping a namespace that is already fine.
