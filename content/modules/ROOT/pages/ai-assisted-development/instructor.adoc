This module has two movements, and the join is the whole point.
The *read-only movement* (exercises 1-2) is *the agent as a diagnostician* — it calls the cluster, you watch the tool-call trace, and you *verify its claims yourself*. Nothing it does can break anything, because the ServiceAccount it acts through can only read.
The *governed-write movement* (exercises 3-4) is *the agent as an operator under control* — you grant a *scoped* write and it fixes the fault, then you ask it to overstep and *RBAC denies it*. Exercise 4 is the climax the whole module builds to: the denial is enforced by the platform, underneath the agent, not by the agent's own settings.

The single most valuable thing you can reinforce is the *boundary claim*: the security guarantee is *RBAC on the ServiceAccount*, and the agent's read-only flag is defense in depth. Attendees arrive thinking "read-only mode = safe"; the module's job is to move them to "the identity's RBAC = safe, the flag is a bonus."

== Timing

Total hands-on: *~31 min* (add ~15 min of concept up front — the MCP+ServiceAccount boundary and the two-phase RBAC diagrams).

[cols="1,4,1,3",options="header"]
|===
| # | Exercise group | Attendee time | Measured core

| 1 | Meet the MCP server + connect the agent | ~5 min | reading the scoped SA/RBAC + building the `ask-agent` helper; all `oc` reads *instant*
| 2 | Diagnose read-only | ~7 min | one `ask-agent` run — the *model round-trip is the wait* (~20-40 s); reading the trace + `oc` verification is the rest
| 3 | Scoped write + fix + *review* + audit | ~9 min | the RBAC grant + server flip are *instant*/~15 s rollout; the fix `ask-agent` run ~30-60 s; +1 min for the review step and, when needed, the recovery (all `oc` reads *instant*, one further ~15 s rollout); reading the audit trail
| 4 | The forbidden test | ~5 min | one `ask-agent` run (~20-40 s) + the `oc auth can-i --as` matrix (*instant*); the denial is the payoff
| 5 | In-IDE preview | ~5 min | reading only — optional, no checkpoint
|===

[NOTE]
.How this timing was measured
====
On the build cluster (OpenShift 4.21.22, Kubernetes 1.34) on 2026-07-15, every exercise was performed in a `user3-dev` namespace with the neutral `mcp-agent-cli` against the cluster's served model.
The mechanics are *instant*: `oc get`/`auth can-i`/`apply` return in well under a second, and the agent's container image is pull-through-cached (pull ~0.2 s), so each `ask-agent` pod starts immediately.
*The only real wait is the model round-trip.* A read-only diagnosis (three tool calls) took roughly 20-40 s end to end; the fix and the forbidden test are similar. Budget each `ask-agent` call at up to a minute and tell attendees so they don't think it hung.
The dominant *attendee* time is reading — the tool-call trace, the `managedFields` audit, and the `is forbidden` denial — not waiting on commands.
Exercise 3 gained a *review* step on 2026-07-31 (read the cluster, not the answer) plus a recovery block. Its commands are `oc` reads (instant) and at most one further rollout, measured at the same ~15 s as the server flip on the same cluster — hence ~8 → ~9 min, not a new measurement of the agent path.
====

== How to know the room can move on

Two instruments tell you this without guessing, and neither is the clock. Each exercise ends on a `[.checkpoint]` block with a *✔ Verify:* line in the lab — that is the move-on signal, written for attendees to confirm before continuing. For the whole module, `ws verify ai-assisted-development --user <u>` is the same self-check the attendee can run any time; a room reporting all checks green is actually done, not just out of time.

== Pre-flight checklist

Run these *before the session* (as cluster-admin, `KUBECONFIG` on the workshop cluster). The sample user below is `user3`.

`ws prep ai-assisted-development` waits up to *6 minutes* for the entry state to converge (the module's `waitSeconds: 360` sync window). It normally returns well inside that — the ceiling is a timeout, not a duration. Attendees start it themselves from the top of the *concept* page, so deliver the concept at its normal pace and it converges under you.

. *A sample user's entry state materializes and verifies.*
+
[source,sh,role=execute]
----
adm start ai-assisted-development --user user3
ws verify ai-assisted-development --user user3 --entry-only
----
+
Expect the `ws-entry-ai-assisted-development` marker in `user3-dev`; `kubernetes-mcp-server` *1/1*, started `--read-only`, running as the `mcp-agent` ServiceAccount; `parasol-claims` *0/1* with `readinessProbe.httpGet.path=/q/health/reddy`; `mcp-agent` bound *only* to `view` in `user3-dev`; and the `parasol-ai-assist` DevWorkspace `started: false`.

. *The MaaS key is present and valid — the agent needs a model.* *This is the module's one hard runtime dependency (it is why AI-Assisted Development is `[ADD-ON]`).*
+
[source,sh,role=execute]
----
oc get secret maas-credentials -n user3-dev -o jsonpath='has GENAI_API_KEY: {.data.GENAI_API_KEY}{"\n"}' | sed 's/:.*/: (present)/'
oc get cm maas-config -n user3-dev -o jsonpath='model={.data.model}  endpoint={.data.endpoint}{"\n"}'
----
+
Expect a non-empty key and the cluster's model/endpoint. If the key is empty or expired, every `ask-agent` run ends in `error: model authentication failed - check the MaaS key (GENAI_API_KEY); it may be expired.` — re-source the key before the session (the entry-state hook copies it from the platform Lightspeed secret).

. *The neutral CLI image exists in the shared registry.*
+
[source,sh,role=execute]
----
oc get istag mcp-agent-cli:1.0 -n ogsr-parasol-images -o jsonpath='{.image.dockerImageReference}{"\n"}'
----
+
Expect a `…/ogsr-parasol-images/mcp-agent-cli@sha256:…` digest. If it's missing, the app build hasn't published it; `ask-agent` will `ImagePullBackOff`.

. *Know your cluster's served model — and that tool-calling reliability varies by model.*
+
[source,sh,role=execute]
----
adm smoke ai-assisted-development --user user3     # runs a read-only ask-agent diagnosis in the live cockpit
----
+
The module is *model-agnostic*, but models differ both in whether they *execute* a write at all and in whether the manifest they write is *correct* (see Watchouts). Run exercise 3 end to end on *your* cluster's model before the session and check the cluster afterwards, not the agent's answer — budget the same *~9 min* the lab's own exercise-3 chip states, because this is the module's graded exercise itself, not a quick check:
+
[source,sh,role=execute]
----
oc get pods -n user3-dev -l app=parasol-claims
oc get deploy parasol-claims -n user3-dev -o jsonpath='probe: {.spec.template.spec.containers[0].readinessProbe.httpGet.path}{"\n"}image: {.spec.template.spec.containers[0].image}{"\n"}'
----
+
Expect `1/1 Running`, probe `/q/health/ready`, and an `image-registry.openshift-image-registry.svc:5000/…/parasol-claims:…` reference. A `STATUS` of `InvalidImageName` with a placeholder in the `image` line is the *third landing* — the agent wrote, wrongly, and said it succeeded.
+
[source,sh,role=execute]
----
ws prep ai-assisted-development --user user3 --yes     # resets after the dry run; ceiling 6 min (waitSeconds: 360)
----
+
[IMPORTANT]
.The dry run above is a full lab exercise (~9 min), and the reset that follows it has its own 6-minute ceiling
=====
Two separate clocks are hiding in this pre-flight step. Exercise 3 itself — the one you just ran end to end — is the module's *graded* exercise, timed at *~9 min* in the lab's own chip, not a quick smoke check. The `ws prep … --yes` reset that follows it then waits up to *6 minutes* for the entry state to re-converge (`waitSeconds: 360`); it normally returns well inside that, and the ceiling is a timeout, not a duration. Know which landing to expect on the day (see Watchouts) before you run either.
=====

. *`mcp-agent` is scoped to ONE namespace — the forbidden test depends on it.*
+
[source,sh,role=execute]
----
oc auth can-i get pods -n user1-dev --as=system:serviceaccount:user3-dev:mcp-agent   # expect: no
----
+
Expect *`no`*. If a prior module or a stray `ClusterRoleBinding` gave `mcp-agent` broader reach, exercise 4's denial won't fire — the whole climax depends on the binding being namespaced.

== Demo-mode notes

Beyond the Say/Show/Do arc in the demo flavor:

* *Run the demo from the entry state, not `adm solve`.*
The story is *diagnosing and fixing* a broken app. `adm solve ai-assisted-development` renders the finished end state (`parasol-claims` already `1/1`) — use it to *show the destination* or pre-stage, never as the demo's start.
* *Pre-warm the model.* The first `ask-agent` call of the day can be slower (cold model, key fetch). Run one throwaway diagnosis a minute before you present so the live one is snappy.
* *Land the denial beat.* Exercise 4 is the whole demo. Read the `is forbidden` line out loud, then the identity in it — `system:serviceaccount:user3-dev:mcp-agent` — and say "it *tried*; the platform said no." Follow with the `oc auth can-i --as` matrix so they see it's the API server, not the agent's manners.
* *Whatever the agent does with the write, use it — but read the cluster on screen first.* If it narrates the `resources_create_or_update` call instead of running it, say "it proposed the exact right patch; now *I* review and apply it." If it writes something wrong and reports success, that is the stronger beat — show the `InvalidImageName` pod and the placeholder in the image field next to the answer claiming victory, then the `managedFields` line naming `kubernetes-mcp-server` as the writer, then recover in seconds with the block staged in your buffer. Either way the line is the same: *the answer is a claim; the cluster is the fact.* Keep the recovery block ready before you start so a wrong write costs you fifteen seconds, not the demo.

== Top questions attendees ask

*1. "Everyone's exercise 3 came out differently — mine narrated, hers broke the app, his just worked. Which is right?"*::
All three, and the lab says so. Models *decide* whether to emit a tool call through the function-calling channel or just describe it in prose (smaller models, and large structured arguments like a whole deployment manifest, push some of them to narrate); and a model that *does* write may hand-author a *replacement* manifest and fill fields it did not reason about with template text — which is how a placeholder lands in the image and the app goes `InvalidImageName` while the answer reports success. The lab's recovery block lands the fix from any of the three. Reinforce the framing rather than smoothing the difference away: *the room just proved that "the agent says it worked" is not evidence*, and the reason the damage stopped at one deployment is the grant was one verb, one resource, one namespace. If you have time, put both a narrating and an acting outcome on screen side by side — it is the best version of this module you will ever deliver.

*2. "Why not just give the assistant a kubeconfig or `cluster-admin` so it always works?"*::
Because then the agent's power is *your* power, and a model that can be wrong or prompt-injected now has it. The entire module is the alternative: a dedicated ServiceAccount, read-only by default, a namespaced write granted per task. The online recipes that grant `cluster-reader` cluster-wide are teaching a *convenience*, not a *posture* — on a shared, multi-team cluster that convenience is an incident waiting to happen.

*3. "Isn't the `--read-only` flag enough to keep it safe?"*::
It's a seatbelt, not the boundary. A sibling MCP server's read-only mode filtered the *list* of tools but not their *execution* (CVE-2026-46519), so it was bypassable. The durable guarantee is RBAC on the ServiceAccount, enforced by the API server *underneath* the agent — which is why exercise 4's cross-namespace read is a `403` even with writes fully enabled. Set the flag *and* scope the identity.

*4. "The cross-namespace test returned data instead of being denied — what went wrong?"*::
`mcp-agent` has more than the intended `view`-in-one-namespace binding. Check `oc auth can-i get pods -n <neighbour> --as=system:serviceaccount:<user>-dev:mcp-agent` (pre-flight #5) — it must be `no`. A stray `ClusterRoleBinding`, or a neighbour namespace that granted `mcp-agent` access, breaks the denial. The forbidden test only works because the binding is namespaced and scoped to the attendee's own namespace.

*5. "Which model is this, and will my cluster's model behave the same?"*::
The module is *model-agnostic* — it runs against whatever model your cluster serves over Models-as-a-Service (surface it with `oc get cm maas-config`). The *security* behavior (RBAC denials, the audit trail, read-only) is identical on every model. What varies is *tool-calling reliability* — how consistently the model executes calls versus narrating them. Do a dry run on your cluster's model (pre-flight #4) so you know whether exercise 3's fix executes directly or uses the reviewed-and-apply fallback.

== Watchouts

* *Exercise 3's write lands three different ways depending on the model — this is the module's top delivery variable.*
(1) *Correct write*: `resources_create_or_update` executes, `parasol-claims` goes `1/1`. (2) *No write*: the agent narrates the call as text, zero executed calls, the correct manifest printed in the answer — observed on the 2026-07-15 build cluster's model, which diagnoses reliably (small-argument read calls) but narrates the large write. (3) *Wrong write*: it executes, but hand-authors a *replacement* Deployment carrying a placeholder in the image field (`image: <image>`), leaving `InvalidImageName` while the answer reports success — reproduced twice independently on 2026-07-31, on two clusters with two attendees; `managedFields` recorded `kubernetes-mcp-server op=Apply` both times, so the write was genuine and attributable.
+
Do *not* tell the room which one to expect, and do not present any of them as the failure case: the page is written to hold for all three, and dry-running your own cluster (pre-flight #4) is how *you* know which is likely. Landing 3 is the best teaching moment in the module — an agent that acts wrongly and reports success is exactly why the write grant is one verb on one resource in one namespace, and exactly why the lab makes reading cluster state a required step rather than a suggestion. The recovery block in exercise 3 restores the image from the entry marker's `seedImage` and re-applies the probe fix; it is a no-op on landing 1, so attendees can run it regardless. Note that the *older* fallback — patching the probe alone — repairs landing 3 not at all.
* *The in-IDE Dev Spaces beat is an optional preview.*
The `parasol-ai-assist` DevWorkspace resolves its `che-code` editor through the in-cluster Dev Spaces dashboard editor API (the earlier bare-plugin-id `registryUrl` failure is fixed). This is the settled, permanent design (design call #40, closed) — not a stopgap: it is Eclipse Che's own documented way to inject an editor into a DevWorkspace authored via the Kubernetes API, it needs no external registry (in-cluster Service DNS only), and it survives Dev Spaces operator upgrades because it's a maintained product integration surface rather than a guessed-at internal path. A custom controller-namespace "editor definition" ConfigMap was considered and rejected — that mechanism is for non-bundled editors, and `che-code` already ships bundled. Exercise 5 stays an optional in-IDE *preview* — the full security lesson is already exercised from the terminal (exercises 1-4), so a workspace that is slow to open on first launch costs nothing gradeable. A graded in-IDE checkpoint remains a planned enhancement (separate backlog item, not part of #40).
* *The read-only note changes wording after you flip the server — that's correct.*
While the server is `--read-only` (entry state), the client filter reports `no mutating tools were offered by the server` (the server never advertised them). Only *after* exercise 3 flips the server off `--read-only` does the client report `hid 6 mutating tools`. Both are right; the client filter only has something to hide once the server offers writes. Don't let attendees think the filter is broken at entry.
* *MaaS key expiry and quota under an agentic loop.*
Each `ask-agent` run re-sends the full tool schema and may take several model turns; the per-user MaaS key is short-lived. If a run ends in `model authentication failed`, the key expired — re-source it (pre-flight #2). The `MCP_MAX_STEPS` cap (default 10) bounds runaway loops.
* *A pushed fix advances the deployment revision counter across a fix/reset cycle.*
Cosmetic only — `parasol-claims` may show revision 2/3 after a fix or a re-run. The *spec* (the bad probe at entry, the good probe after the fix) is what matters; `ws prep ai-assisted-development --yes` fully re-materializes.

== Provenance

AI-Assisted Development is a net-new module (spec: "fresh; MCP + kubernetes-mcp-server + Lightspeed docs; ties Multi-Tenancy & Workload Security for the RBAC spine").
It is marked `[ADD-ON]` for one reason: the agent needs a model, reached over Models-as-a-Service — a hosted-model dependency no core `[OCP]` module may require. Everything *else* it teaches (MCP, ServiceAccounts, RBAC, the internal registry, Dev Spaces) is core OpenShift.

The lab was performed in a `user3-dev` namespace on OpenShift 4.21.22 on 2026-07-15 with the neutral `mcp-agent-cli` against the cluster's served model (model-agnostic; live infra scrubbed): the read-only diagnosis is a real three-tool-call trace (`pods_list_in_namespace` → `resources_get` → `events_list`) that named the wrong probe path `/q/health/reddy`, confirmed against the live `Readiness probe failed` event on the pod (the `statuscode:` in that message *varies* — 503 measured on this module's own entry state, 502 and 404 also seen — so neither the lab nor this record pins one, and it is not a checkpoint); the scoped `deployer` grant made `oc auth can-i patch deployments --as=…:mcp-agent` flip to `yes` while `get secrets` stayed `no`; with the server flipped off `--read-only` the client filter hid *6* mutating tools; the fix was applied through the `mcp-agent` identity's `resources_create_or_update` (server-side Apply, recorded in `managedFields` as `manager: kubernetes-mcp-server`), taking `parasol-claims` to `1/1`; and the forbidden test is a real two-tool-call trace against `user1-dev`, both returning `pods is forbidden` / `events is forbidden` for `system:serviceaccount:user3-dev:mcp-agent`, with the agent reporting the denial. The MCP server image is digest-pinned to `kubernetes-mcp-server` 0.0.65 — pre-1.0, daily-churn software; the running image carries no version label at all (`oc image info` on the pinned digest, 2026-07-31, returns only the UBI base labels plus `org.opencontainers.image.revision`), so the *digest* is the only identity available on-cluster and the lab compares against that rather than a version string. Re-verify every flag and tool name against the release you are actually running before reusing this trace as ground truth. The `--read-only` bypass cited is CVE-2026-46519 (a different, sibling project — not the server used here).

Exercise 3's *outcome* is not part of that provenance and must not be treated as fixed. On 2026-07-31, on two different clusters and two different attendees, the same `--allow-writes` ask produced a *real* `resources_create_or_update` (`managedFields`: `kubernetes-mcp-server` `op=Apply`) that hand-authored a replacement Deployment with a literal `image: <image>` placeholder — `InvalidImageName`, `1/1` unreachable — while the agent's own answer reported success. The page now covers correct-write, no-write and wrong-write without pinning any of them to a model, and the entry marker records `seedImage` (entry chart 0.1.8) so the recovery restores the image from cluster state instead of a retyped literal.
