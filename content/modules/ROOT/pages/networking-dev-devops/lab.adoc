=== Brief

image::networking-dev-devops/networking-dev-devops-01-traffic-directions.svg["Two directions of traffic: a browser outside the cluster reaching a namespace north-south, labelled what you expose — Route or Gateway API; and inside that namespace the web tier calling the api tier calling the database east-west, labelled who may talk to whom — NetworkPolicy or UserDefinedNetwork."]

*Two directions of traffic*

Every conversation on a cluster runs in one of two directions. *North-south* crosses the cluster boundary — a browser reaching a front end — and is controlled by choosing what to expose. *East-west* is traffic between pods inside the cluster — the front end calling the API, the API querying the database — and is controlled by policy.

This demo is entirely east-west, because that is where the default is uncomfortable.

*The default is wide open*

Inside the cluster, every pod can open a connection to every other pod, in any namespace, on any port. For a three-tier application that means the database will accept a connection from the front end, from a debugging pod, from anything that happens to share the namespace. Security here is not something to switch on; it is something to add.

*Two ways to add it*

*NetworkPolicy* is the workhorse: a default-deny baseline so nothing may talk, then precise allows for the flows the application genuinely needs. It is per pod and per port, expressed as labels and enforced in the data plane — no sidecar, no appliance. The allows are also the documentation, which is what makes the result auditable.

A *UserDefinedNetwork* is the stronger, simpler answer when isolation is a property of a whole namespace. The namespace gets its own Layer 2 segment, so its pods are isolated from every other namespace natively, with no policy to write and none to get wrong.

*In this demo*

. A flat namespace, where a pod unrelated to the application opens the claims database
. One default-deny policy — and the application breaking with it, DNS included
. The flows the application needs re-opened, explicitly and only those
. The database answering the API, and refusing the same pod as before
. A partner namespace already isolated by its own network, with no policy written

=== 1 · The flat network — 2 min

Parasol's claims application runs in one namespace as three tiers — `parasol-web`, `parasol-claims` and `claims-db`. Alongside them sits `demo-client`, a pod with nothing to do with the application, which opens a connection straight to the database.

image::networking-dev-devops/networking-dev-devops-01-services-clusterip.png["The project's Services list in the web console: claims-db, parasol-claims and parasol-web, each showing one internal cluster address and port — 5432 or 8080 — with no external address anywhere on the page, which is what ClusterIP means."]

*Why it matters*

"Can the database be reached from anywhere it shouldn't be?" is the question a security review asks, and on a flat namespace the honest answer is "yes — from everything." Nothing here is misconfigured; this is what a namespace looks like before anyone decides who may talk to whom.

[source,sh,role=execute,subs="attributes"]
----
NS={user}-dev; PARTNER={user}-partner
oc get svc -n $NS
echo -n "demo-client -> claims-db:5432 : "; oc exec deploy/demo-client -n $NS -- timeout 5 bash -c '</dev/tcp/claims-db/5432 && echo OPEN'
----

*What just happened*

Three ClusterIP Services, reachable in-cluster and invisible from outside — and one unrelated pod holding an open TCP connection to Postgres. On a fresh namespace, every pod can reach every other pod, on every port.

=== 2 · Default-deny, and the application goes down with it — 3 min

One policy closes the namespace: an empty pod selector with both Ingress and Egress listed. Nothing may talk — and that includes the application itself.

image::networking-dev-devops/networking-dev-devops-03-networkpolicy-yaml.png["The default-deny-all NetworkPolicy on its YAML tab in the web console: podSelector is an empty pair of braces, which matches every pod in the project rather than none, and policyTypes lists both Ingress and Egress — the two lines that turn an empty selector into a deny."]

*Why it matters*

A default-deny baseline is the only starting point that is honest about what a namespace allows, and the breakage that follows is the lesson rather than a fault. `parasol-claims` falls to `0/1` because its readiness probe checks a database it can no longer reach; the pod does not crash, it is simply marked NotReady. The same policy also blocks DNS, which is why a first default-deny so often gets blamed on the application.

[source,sh,role=execute,subs="attributes"]
----
NS={user}-dev; PARTNER={user}-partner
oc apply -n $NS -f - <<'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: default-deny-all}
spec: {podSelector: {}, policyTypes: [Ingress, Egress]}
EOF
for i in $(seq 1 24); do oc get pods -n $NS -l app=parasol-claims -o jsonpath='{.items[*].status.containerStatuses[0].ready}' | grep -q false && break; sleep 3; done
oc get pods -n $NS -l app=parasol-claims
MSG=$(oc logs -n $NS deploy/parasol-claims --tail=20 2>/dev/null | grep -o 'health down.*Acquisition timeout' | tail -1)
echo "${MSG:-step failed: no DB health-down line in the logs yet — check the pod exists and is Running (oc get pods -n $NS -l app=parasol-claims), then re-run}"
----

*What just happened*

The last line is the application's own log: the database health check timed out. Nothing was deployed, scaled or edited — one policy took the namespace from wide open to silent.

=== 3 · Re-open only what the application needs — 3 min

Three policies restore exactly two flows: DNS resolution for every pod, and the API's connection to the database. Nothing else comes back.

image::networking-dev-devops/networking-dev-devops-05-network-policy-layers.svg["Three layers of east-west control in increasing strength: NetworkPolicy with a default-deny baseline plus precise per-pod, per-port allows; a UserDefinedNetwork giving a namespace its own isolated network with no policy to write; and a service mesh adding mutual-TLS identity and layer-7 policy."]

*Why it matters*

This is least privilege applied to the network, and it is written down. Each allow names a source, a destination and a port, so the policy set answers "what may talk to what?" without anyone inspecting the cluster.

The DNS allow is the one everybody gets wrong the first time. It has to name the CoreDNS pods' own ports — `dns` and `dns-tcp`, which are `5353` — because the rule is evaluated against the destination pod, not against the Service's port 53.

[source,sh,role=execute,subs="attributes"]
----
NS={user}-dev; PARTNER={user}-partner
oc apply -n $NS -f - <<'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: allow-dns-egress}
spec:
  podSelector: {}
  policyTypes: [Egress]
  egress: [{to: [{namespaceSelector: {matchLabels: {kubernetes.io/metadata.name: openshift-dns}}}], ports: [{protocol: UDP, port: dns}, {protocol: TCP, port: dns-tcp}]}]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: allow-db-from-claims}
spec:
  podSelector: {matchLabels: {app: claims-db}}
  policyTypes: [Ingress]
  ingress: [{from: [{podSelector: {matchLabels: {app: parasol-claims}}}], ports: [{protocol: TCP, port: 5432}]}]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: allow-claims-to-db-egress}
spec:
  podSelector: {matchLabels: {app: parasol-claims}}
  policyTypes: [Egress]
  egress: [{to: [{podSelector: {matchLabels: {app: claims-db}}}], ports: [{protocol: TCP, port: 5432}]}]
EOF
oc rollout status deploy/parasol-claims -n $NS --timeout=40s
----

*What just happened*

The API is back to `1/1`. It reaches the database because a rule says it may — not because nothing was stopping it.

*What just happened*

The connection is dropped because no rule lets it through: `demo-client` was given no egress allow, and the database admits ingress only from `parasol-claims`. Both point the same way, which is the correct mental model — under default-deny, traffic needs a reason to exist.

=== 5 · A namespace isolated with no policy at all — 2 min

Parasol's partner namespace was created with its own primary network. It holds no NetworkPolicy, and even with the front end opened to every source, its workload cannot reach it.

image::networking-dev-devops/networking-dev-devops-03-platform-accretion.svg["The Parasol platform so far shown in grey — the application delivered by GitOps, and tenancy with workload security — with this module's layer highlighted above it: Service and Route for north-south traffic, NetworkPolicy for east-west, and UserDefinedNetwork."]

*Why it matters*

Where isolation is a property of the whole namespace, a UserDefinedNetwork gives it natively: there is no policy to write, and none to get wrong. The trade-off is a hard rule — a primary UDN must exist before the namespace's first pod, so it is a platform decision at namespace-creation time rather than something to retrofit. NetworkPolicy remains the answer wherever the flows are selective.

The front end sits behind the default-deny from step 2, so a blocked connection alone would prove nothing. The block opens `parasol-web` port 8080 to every source, probes it from this terminal and from the partner workload, and then removes that opening again.

[source,sh,role=execute,subs="attributes"]
----
NS={user}-dev; PARTNER={user}-partner
oc get networkpolicy -n $PARTNER
oc exec deploy/partner-workload -n $PARTNER -- ip -brief addr show ovn-udn1
oc apply -n $NS -f - <<'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: allow-web-from-anywhere}
spec: {podSelector: {matchLabels: {app: parasol-web}}, policyTypes: [Ingress], ingress: [{ports: [{protocol: TCP, port: 8080}]}]}
EOF
sleep 3
echo -n "this terminal    -> parasol-web.$NS.svc:8080 : "; timeout 5 bash -c "</dev/tcp/parasol-web.$NS.svc.cluster.local/8080" 2>/dev/null && echo OPEN || echo "BLOCKED (exit $?)"
echo -n "partner-workload -> parasol-web.$NS.svc:8080 : "
OUT=$(oc exec deploy/partner-workload -n $PARTNER -- timeout 5 bash -c "</dev/tcp/parasol-web.$NS.svc.cluster.local/8080 && echo OPEN" 2>&1); rc=$?
case "$rc:$OUT" in
  0:*OPEN*) echo "OPEN — NOT isolated (unexpected here)" ;;
  124:*|*"No route to host"*|*"Network is unreachable"*) echo "BLOCKED (own network — no path to the app)" ;;
  *) echo "step failed (exit $rc): $OUT" ;;
esac
oc delete networkpolicy allow-web-from-anywhere -n $NS
----

*What just happened*

With `parasol-web` open to every source, this terminal, a pod in another namespace on the cluster network, connected. The partner workload did not: it sits on `ovn-udn1`, a separate Layer 2 segment at `10.20.0.0/16`, with no route to the application namespace. No policy stopped it; its network did. The database answers only the API, and the partner workload is on its own network — none of it a firewall appliance.

== Frequently asked questions

*We applied default-deny and an application went 0/1 without anyone touching it — why?*::
That is the policy working. A default-deny denies egress as well as ingress, so the application can no longer open its connection to its database; its readiness probe checks that database, the check fails, and the pod is marked NotReady. It does not crash — the status stays `Running`. Adding the two allows for that hop brings it straight back to `1/1`.

*Our DNS allow uses `port: 53` and DNS is still broken. Why?*::
Because OVN-Kubernetes evaluates an egress port against the *destination pod*, and the CoreDNS pods listen on `5353` — the `dns-default` Service is what maps 53 to 5353. A rule for `port: 53` never matches the pod, so DNS stays denied. Name the CoreDNS pods' own ports, `dns` and `dns-tcp`, which is what OpenShift's own operators do. It is the most common self-inflicted "my policy is correct but nothing works."

*The partner workload still has an `eth0` on the cluster network — is it really isolated?*::
Yes. A pod on a primary UDN keeps a cluster-network `eth0` for node-level infrastructure such as kubelet health checks, but its default route leaves through `ovn-udn1` on the UDN's own segment. OVN-Kubernetes enforces the isolation regardless of that extra interface: with the front end open to every source, a pod on the cluster network connects and the partner workload still times out, even though it can resolve DNS through the shared cluster service.

*Why would a `type=LoadBalancer` Service sit at `<pending>`?*::
Because no provider answered — it means "nothing handed out an address," not "failed." A LoadBalancer Service needs a cloud load balancer or an add-on such as MetalLB on bare metal. Where there is none, the external IP never arrives, and the fix is either a Route, which needs no provider, or installing a provider if an L4 external IP is genuinely required.

*Can you show the Gateway API end to end?*::
Yes, even without a LoadBalancer provider. By default the OpenShift Gateway API implementation fronts each Gateway with a LoadBalancer Service, which stays `<pending>` for the same reason as above. Annotate the Gateway `networking.istio.io/service-type: ClusterIP` and publish its Service with a Route, and GatewayClass → Gateway → HTTPRoute runs end to end — the workshop lab does exactly that. Where a provider exists, drop both and the Gateway gets an external address of its own.

*Two different certificates, from two different authorities, on one request.*

[NOTE]
.Why you never supplied a destination CA certificate
====
A re-encrypt Route usually expects a `destinationCACertificate` so the router can verify the backend.
You omitted it, and it still worked — deliberately.
The Route API's own documentation for that field says that when it is not specified, the router may supply its own destination CA and validate using the short service name `service.namespace.svc`, "which allows infrastructure generated certificates to automatically verify."
A service serving certificate is exactly such an infrastructure-generated certificate, and its subject is exactly that short name — which you just read at hop 2.
Supply a `destinationCACertificate` when the backend's certificate comes from *your own* CA instead.
====

== 4. Re-open only what the app needs, then prove the isolation
⏱ *~10 min* · DNS (the gotcha), the db-from-api and api-from-web allows, and the payoff

Now add back *only* the flows the app genuinely needs — least privilege, for the network.

*First, DNS* — the thing default-deny broke that surprises everyone.
Re-open egress to the cluster DNS service.
The subtlety: name the CoreDNS pods' *named ports* `dns`/`dns-tcp`, *not* port `53`.
OpenShift's DNS Service listens on `53` but forwards to CoreDNS pods on port `5353`, and a NetworkPolicy is evaluated against the *destination pod's* port — so a rule for `53` silently fails to admit DNS:

[source,sh,role=execute,subs="attributes"]
----
NS={user}-dev; PARTNER={user}-partner
oc apply -n $NS -f - <<'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns-egress
spec:
  podSelector: {}
  policyTypes:
    - Egress
  egress:
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: openshift-dns
      ports:
        - protocol: UDP
          port: dns          # CoreDNS pod port (5353), NOT the Service's 53
        - protocol: TCP
          port: dns-tcp
EOF
sleep 4
echo -n "demo-client DNS lookup of claims-db: "; oc exec deploy/demo-client -n $NS -- timeout 6 bash -c 'getent hosts claims-db >/dev/null && echo RESOLVED' 2>/dev/null; rc=$?
[ $rc -eq 124 ] && echo "still blocked (lookup timed out — re-check the policy's named ports)" || { [ $rc -ne 0 ] && echo "step failed (exit $rc) — check the demo-client pod exists"; }
----

.Expected output
[source,texinfo]
----
demo-client DNS lookup of claims-db: RESOLVED
----

[NOTE]
.Why named ports, not port 53
====
Try the "obvious" version with `port: 53` and DNS *stays broken* — verified live on this cluster.
OVN-Kubernetes matches the egress port against the pod behind the Service (after the Service's `53 → 5353` translation), so the rule must name the pod's port.
The named ports `dns`/`dns-tcp` track the CoreDNS container regardless of the number and are exactly what OpenShift's own platform operators use.
This is the single most common reason a "correct-looking" DNS allow does nothing.
====

== 5. Native isolation with a UserDefinedNetwork
⏱ *~7 min* · a partner namespace isolated with zero policy — proven with your own policies opened up

Sometimes you want a whole namespace isolated and you want it *for free* — no policy to write or maintain.
That is a *UserDefinedNetwork*.

Your `{user}-partner` namespace was created with a *Layer 2 Primary UDN*: it has its *own* pod network, so its workloads are isolated from `{user}-dev` *natively*.

[NOTE]
.NetworkPolicy or UDN — which to reach for
====
Reach for a *UserDefinedNetwork* when isolation is a property of the *whole namespace* (a partner, a regulated tenant, a "this never talks to anything else" workload) and you want it native and maintenance-free.
Reach for *NetworkPolicy* when you need *selective* flows — "the database from the API, the API from the web, and nothing else" — within a namespace or across namespaces.
The catch that makes UDN a platform-team decision: a Primary UDN must exist *before* the namespace's first pod (you cannot convert a populated namespace), which is exactly why `{user}-partner` was built this way for you.
====

The Route you built in exercise 2 is the workhorse today.
The *Gateway API* is where portable, multi-tenant ingress is heading, and it is GA on OpenShift.
It splits exposure across three objects with three owners: a *GatewayClass* (the platform's implementation), a *Gateway* (a listener), and *HTTPRoutes* (the routing rules an app team attaches).
