This module has two beats that land, and they bracket the hands-on.
It *opens* on the flat network — a `demo-client` pod that has nothing to do with the app opening a connection straight to the database (exercise 1) — and it *closes* on the reveal that the same pod is now *blocked* while the API still gets through (exercise 4), followed by a partner namespace isolated *natively* by a UserDefinedNetwork with zero policy (exercise 5).
Exercise 6 then reuses the lockdown: attendees build their own Gateway, and it answers `503` until they open the flows its Envoy proxy needs.
Everything between is the mechanics — Services/endpoints, the exposure tree, default-deny-then-allow — that makes those beats legible.
Optimize the room for exercise 4 (let the "same database, two answers" land) and exercise 5 (let "no policy at all" land).

The single most common confusion is *a DNS egress allow written with `port: 53` that does nothing* — OVN-Kubernetes matches the port against the CoreDNS *pod* (5353), so the rule must use the named ports.
Pre-empt it (see Watchouts); the lab teaches the named-port form directly and explains why.

On the build cluster (OCP 4.21.22, OVN-Kubernetes) on 2026-07-13, every exercise was performed as `user1` and timed.

The re-encrypt beat closing exercise 2 was added later and measured the same way on 2026-07-25: *46 s* of command time end to end, of which *26 s* is the one `parasol-web` rollout after the certificate is mounted.

Exercise 6 became hands-on on 2026-11-12 and was measured as `user8` on OCP 4.22.22: *~38 s* of command time, plus the Envoy proxy's recovery after the policy fix — *5 s* when the policies went in at once, *6–9 s* after a 40 s reading pause, *~60 s* after it had spent two minutes in restart backoff.

== Exercise 6 — what the room will see

* *`PROGRAMMED True` is not "serving".* The Gateway reports `Programmed` as soon as its Service has an address. Under exercise 3's `default-deny-all` its Envoy proxy cannot reach `istiod` (`openshift-ingress`, port 15012), so it never goes Ready and the `parasol-gw` Route returns `503`. That is the planned break; let it land before the fix — "the Gateway is pods in *your* namespace, so *your* policy applies to it."
* *The annotation is the bare-metal answer.* Without `networking.istio.io/service-type: ClusterIP` the implementation asks for a `LoadBalancer` Service, which stays `<pending>` here (`AddressNotAssigned`). It must be a `metadata` annotation — the same key under `spec.infrastructure.annotations` was not honored for the Service type on the build cluster.
* *The lab's Gateway runs one small proxy, by opting in.* The `openshift-default` class default is two Envoy proxies (HorizontalPodAutoscaler `minReplicas: 2`), each limited to 2 CPU / 1Gi — 4 CPU of the namespace's 8 `limits.cpu`. The lab's Gateway sets `spec.infrastructure.parametersRef` to the workshop's `ogsr-gateway-proxy` ConfigMap, which every attendee namespace carries: one proxy at 50m/128Mi requests, 500m/512Mi limits. Measured with the whole lab applied: `limits.cpu` 2.2 of 8. An attendee who drops the `parametersRef` still gets a working Gateway, just two full-size proxies.

== Demo-mode notes

Beyond the Say/Show/Do arc in the demo flavor:

* *Run the demo from the entry state, not `adm solve`.*
The whole story is *building* the controls from a flat network. `adm solve networking-dev-devops` renders the finished end state (policies, Routes and the exercise-6 Gateway in place) — use it to *show the destination* or pre-stage, never as the demo's start.
* *Let the break breathe (beat 2).*
After `default-deny`, pause on `parasol-claims` at `0/1` and the DB health-`DOWN` log line. This is the moment that makes "the network is a control plane" concrete — the app didn't crash, the *network* stopped it.
* *Land the payoff line (beat 4).*

== Top questions attendees ask

*1. "My DNS allow uses `port: 53` — why is DNS still broken?"*::
Because OVN-Kubernetes evaluates a NetworkPolicy egress port against the *destination pod*, and the CoreDNS pods listen on *5353*, not 53 (the `dns-default` Service maps `53 → 5353`).
A rule for `port: 53` never matches the pod, so DNS stays denied.
Use the CoreDNS pods' *named ports* `dns` / `dns-tcp` (what OpenShift's own operators do) or the number `5353`.
This was verified live on the build cluster — `53` fails, `dns`/`dns-tcp` works — and it is the single most common self-inflicted "my policy is correct but nothing works."

*2. "Why is my `type=LoadBalancer` Service stuck at `<pending>`? Is the cluster broken?"*::
No — `<pending>` means *no provider answered*, not "failed."
A LoadBalancer Service needs something to hand out external IPs: a cloud load balancer, or an add-on such as MetalLB on bare metal.
This workshop cluster is bare metal with no such provider, so the external IP never arrives.
The fix is a *Route* (which needs no provider) or, if you truly need an L4 external IP, install a provider.

*3. "Why re-encrypt instead of just passthrough? Both encrypt the last hop."*::
Because passthrough costs you the router.
With passthrough the router never decrypts, so it can only see SNI — it cannot route on a URL path, cannot split traffic by path, and cannot add or rewrite HTTP headers (the Route API notes passthrough is incompatible with header actions).
It also pushes certificate management into the application: the pod must hold a certificate the *outside world* trusts, which means real public certificates distributed to workloads.
Re-encrypt keeps the router doing HTTP-layer work *and* encrypts the last hop, and the pod's certificate only ever has to be trusted *inside* the cluster.
Passthrough is the right answer when the backend must terminate TLS itself — client-certificate authentication, or a non-HTTP protocol.

*4. "We never gave the Route a destination CA certificate. Why does it verify the backend?"*::
Because the backend's certificate is *infrastructure-generated*.
The Route API's documentation for `destinationCACertificate` states that when the field is not specified, the router may provide its own destination CA and perform hostname validation using the short service name `service.namespace.svc` — which is exactly the subject the service CA operator issues (`CN=parasol-web.{user}-dev.svc`, which attendees read at hop 2).
So a service serving certificate verifies automatically, with nothing configured.
You *do* need `destinationCACertificate` when the backend presents a certificate from your own CA rather than the cluster's.
Verified live on the build cluster: the reencrypt Route was created with `spec.tls` containing only `{"termination":"reencrypt"}` and was `Admitted=True` and serving.

*5. "I applied default-deny and `parasol-claims` went `0/1` — I didn't touch it. Why?"*::
That is the policy working.
`default-deny-all` denies *egress* too, so `parasol-claims` can no longer open its connection to `claims-db:5432`; its readiness probe checks the database, the check fails, and the pod is marked NotReady (it does *not* crash — status stays `Running`).
Its log shows `Database connections health check … DOWN … Acquisition timeout`.
Add the `parasol-claims → claims-db` egress allow (and the matching db ingress allow) and it returns to `1/1`. This is the intended "app breaks, now write the allows" beat.

*6. "The partner workload still has an `eth0` on the cluster network — is it really isolated?"*::
Yes.
A Primary UDN pod keeps a cluster-network `eth0` for node-level infrastructure (kubelet health checks and the like), but its *default route* leaves through `ovn-udn1` on the UDN's `10.20.0.0/16` segment — that is its primary network.
OVN-Kubernetes enforces the isolation regardless of the extra interface: the pod cannot reach workload pods in other namespaces (verified — the connection to `parasol-web` times out), even though it can still resolve DNS via the shared cluster service.
The presence of `eth0` is an implementation detail, not a leak.

*7. "Why does my Gateway need a Route in front of it? Isn't the Gateway the ingress?"*::
On a cluster with a load-balancer provider, it is: the implementation gives each Gateway a `LoadBalancer` Service and the Gateway gets its own external address.
This cluster has no provider, so that Service would sit `<pending>` exactly like question 2, and the Gateway would report `AddressNotAssigned`.
The lab asks for a `ClusterIP` Service instead (the `networking.istio.io/service-type` annotation) and publishes it through the cluster's router with an edge Route.
The three-object model — GatewayClass → Gateway → HTTPRoute — is identical either way; only how the Gateway's address reaches the outside world changes.

== Watchouts

* *The DNS named-port trap (see question 1).*
Attendees who "fix" DNS with `port: 53` will see it stay broken and blame the cluster. The lab teaches `dns`/`dns-tcp` directly with a NOTE explaining why; if someone is stuck, check their `allow-dns-egress` ports first.
* *default-deny breaks DNS and the app — that's the lesson, not a bug.*
Both are expected in exercise 3. Don't let a confused attendee "fix" it by deleting default-deny; the point is to re-open flows deliberately in exercise 4.
* *The Route needs a router-ingress allow under default-deny.*
`allow-web-from-router` (namespaceSelector `policy-group.network.openshift.io/ingress: ""`) is what lets the ingress router reach `parasol-web` once default-deny is on. Without it, the Route returns an error even though the Service is fine — a subtle one to debug if an attendee skips it.
* *The `demo-client` block is over-determined — frame it honestly.*
Under the end state, `demo-client` is blocked both because default-deny denies its egress (it got no allow) *and* because the `claims-db` ingress admits only `parasol-claims`. Present it as "no rule lets it through," not "the db ingress policy alone stops it" — both point the same way, and that is the correct mental model.
* *The re-encrypt beat's real failure mode is a Route pointed at the plaintext port.*
If an attendee creates the reencrypt Route against `--port=http` (8080) instead of `--port=https` (8443), the router tries to open TLS to a plaintext listener and the Route returns *503* with the router's "Application is not available" page — not a TLS error, which is what makes it confusing. Confirmed live. Check `spec.port.targetPort` first; it is `https` when correct.
* *The pod must be serving TLS before the Route will work, and `1/1 Ready` does not prove it.*
The readiness probe checks the plaintext port, so `parasol-web` goes `1/1` whether or not the TLS listener came up. The lab has attendees grep the startup line for `Listening on: … and https://0.0.0.0:8443` for exactly this reason — if someone's re-encrypt Route 503s, check that line before anything else.
* *The two `oc set` commands trigger two rollouts.*
`oc set volume` and `oc set env` each patch the Deployment, so the second supersedes the first mid-roll; `oc rollout status` after both is what settles it (measured 26 s). An attendee who runs `oc rollout status` between them will see it complete twice and may think something is wrong.
* *LoadBalancer `<pending>` and Gateway `Programmed=False` are the same root cause.*
Bare metal, no LB provider. A Gateway showing `AddressNotAssigned` is missing the `networking.istio.io/service-type: ClusterIP` annotation (or carries it under `spec.infrastructure` instead of `metadata`) — `oc annotate` fixes it in place in about 2 s.
* *The Gateway `503` is the planned break, not a fault.*
Under default-deny the Envoy proxy restarts on a failing startup probe until `allow-gateway` lets it reach `istiod`. If an attendee's proxy stays `0/1` *after* the fix, check that policy's `podSelector` label (`gateway.networking.k8s.io/gateway-name`) matches their Gateway's name.
* *The `EndpointSlice` deprecation warning on `oc get endpoints` is cosmetic.*
`oc get endpoints` prints `v1 Endpoints is deprecated … use discovery.k8s.io/v1 EndpointSlice`. It is the clearest view for teaching Service→endpoints; the warning is informational and harmless.
