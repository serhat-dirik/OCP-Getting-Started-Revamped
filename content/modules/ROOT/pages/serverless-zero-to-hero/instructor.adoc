This module has one spine and it builds: *a service that holds zero pods → wake it and feel the cold start → autoscale it on concurrency → split traffic across revisions → build a function from source on the cluster → wake it on an event*.
The beat that lands hardest is the *cold start* (exercise 2): a real first request of *10–30 seconds*, then a tenth of a second warm. It makes the whole scale-to-zero tradeoff concrete, and the deliberate `-m5` break-and-fix turns it into a lesson instead of a surprise.
The beat to frame most carefully is the *eventing taste* (exercise 6): the delivery is *real* and the service *wakes from zero*, but it returns an honest `405` — the app serves `/` (a `GET` is `200`) but has no *POST* CloudEvents handler, and *processing* is the next module. Do not let it read as a failure.

The single most useful thing to internalize before delivering: *the entry state ships the `ksvc` already deployed and scaled to zero.* Exercise 1 is *observe*, not *deploy from scratch* — the teaching starts from a running (idle) service, which is the honest serverless picture.

== Timing

Total core (exercises 1–6): *~43 min*, plus ~15 min of concept up front. The command latencies are small; the real clock is the *waits* — the ~10–30 s cold start, the ~60–90 s scale-to-zero settle, the ~20–40 s revision rollouts, and the ~2 min on-cluster function build.

[cols="1,4,1,2",options="header"]
|===
| # | Exercise group | Attendee time | Measured core

| 1 | Observe your deployed ksvc | ~5 min | all reads, instant; time is spent *orienting* on the Configuration/Route/Revision model
| 2 | Scale to zero and back (cold start) | ~6 min | cold start *15.27 s*; warm *0.106 s*; the scale-to-zero wait *~60–90 s*; the `-m5` trap is instant
| 3 | Autoscale + tune concurrency | ~8 min | revision rollout *~20–40 s*; a scale-to-zero settle *~60–90 s*; the burst climbs *0→3 in ~10 s*
| 4 | Split traffic between revisions | ~8 min | split + rollback instant; the two direct curls + the 50-request batch instant
| 5 | Build and deploy a Function (`kn func deploy --remote`) | ~8 min | measured 2026-11-12, four runs: build+deploy *1 min 57 s – 2 min 30 s* end to end (Maven *39 s – 72 s* via the warm in-cluster mirror); the scale-to-zero wait *~100 s*; function cold start *2.3–2.8 s*, warm under *0.1 s*
| 6 | Eventing taste (source→broker→trigger) | ~8 min | broker/trigger/pingsource Ready in *seconds*; the delivery `405` instant
|===

[NOTE]
.How this timing was measured
====
On the build cluster (OCP 4.21.22, Kubernetes 1.34) on 2026-07-13, every exercise was performed against the live OpenShift Serverless 1.37.1 control plane in `user6-dev` and timed.
The `kn`/`oc` commands are fast: creating or re-weighting a `ksvc` is a sub-second command; a new revision reaches Ready in *~20–40 s* (schedule + JVM boot + probe pass). The genuine time-sinks are the *scale-from-zero cold start* (*15.27 s* measured — a JVM boot, not a hang) and the *scale-to-zero settle* (*~60–90 s* of no traffic, the Knative default stable window plus grace period). Budget for those waits and for *reading* — the revision model, the split, the eventing 405 — not for command latency.
====

== How to know the room can move on

Two instruments tell you this without guessing, and neither is the clock. == Instructor demo — the 10-minute arc (demo flavor)

The demo flavor renders a three-beat Say/Show/Do arc: *wake from zero + cold start* (3 min), *sudden burst + autoscale to the ceiling and back to zero* (3 min), *80/20 revision split + one-line rollback* (4 min).

* *Run it from the entry state, not `adm solve`.* The story is *building* the split live. `adm solve serverless-zero-to-hero --user user4` renders the finished end state (a second revision, the 80/20 split, the eventing wiring, and the `premium-calculator` function, deployed from the image the install built, so no build runs); use it to *pre-stage* or to show the destination, never as the demo's start.
* *Put `oc get pods -w` on screen.* The visual for beats 1–2 is *pods appearing and vanishing*. A second pane running `oc get pods -n $NS -l serving.knative.dev/service=parasol-claims -w` next to the terminal is the whole show.
* *Land the cold start (beat 1).* Say "watch the clock" while the first `curl` hangs for *10–30 seconds* and returns `200`, then run the warm one for the tenth-of-a-second contrast. Promise the *range*, never a single number — this cluster has produced 15.27 s, 18.81 s and 26.51 s on the same service — then read out whatever the screen shows. That wait *is* the tradeoff — don't hide it, sell it.
* *The rollback is the closer (beat 3).* "One line, a hundred percent back to stable — because the old revision never went away." Then re-weight to 80/20 to show it's a dial, not a door.

== Demo-mode notes

* *Pre-warm nothing; pre-settle everything.* Let the service reach *zero* pods before beat 1 (about a minute of no traffic) so the cold start actually fires. If you've been poking it, wait for the pod to disappear first.
* *Create v2 off-screen for the split beat.* The demo's split assumes a second revision exists. `adm start` does NOT clear a leftover `parasol-claims-v2` from a prior pass on this same cluster (only `ws reset`/`ws prep` do) — run `oc delete revision parasol-claims-v2 -n $NS --ignore-not-found=true` first, then `kn service update parasol-claims -n $NS --revision-name parasol-claims-v2 --concurrency-limit 2 --scale-max 3 --no-wait` so both revisions are present.
* *Drive traffic from inside the cluster.* Every load command is `oc exec deploy/demo-client -- … curl …`. The `demo-client` is CPU-capped (200 m), so use `containerConcurrency: 2` (as the lab does) to make the autoscale to the `max-scale` ceiling *deterministic* — a soft target may not visibly climb from the constrained client.
* *Be honest about the eventing 405.* If you show the eventing closer, say "the delivery is real and the service woke from zero — the `405` is because the app serves `/` but has no *POST* event handler yet, which is the next module." Never add a handler to force a `200`.

== Top questions attendees ask

*1. "My first request is slow — or it timed out. Is something broken?"*::
No — that's the *cold start*, and it's the point of the exercise. A scaled-to-zero service holds no pods; the first request waits (*~10–30 s* for this JVM service — measured five times here at 11.80 s, 12.79 s, 15.27 s, 18.81 s and 26.51 s) while Knative schedules a pod, boots the JVM, and hands the request through the activator. Every warm request after is ~0.1 s. If a client *times out* (the deliberate `-m5` trap), the fix is a realistic client timeout or a `min-scale: 1` warm floor — the latter gives up scale-to-*zero* to remove the cold start from the critical path. This is a tuning decision per service, not a defect.

*2. "Why is a pod still running when there's no traffic — or why did it take so long to scale to zero?"*::
Two Knative defaults add up: the *stable window* (~60 s the autoscaler averages over) plus the *scale-to-zero grace period* (~30 s), so a service settles to zero roughly a minute or a minute-and-a-half after the *last* request. In the eventing exercise, the `PingSource` fires *every minute*, so the service may never fully rest — that's expected (the events keep waking it). To see a clean scale-to-zero, stop all traffic (and, if needed, the PingSource) and wait.

*3. "The eventing delivery returned `405` — did the wiring fail?"*::
No — the wiring *worked*. The `PingSource` emitted, the `Broker` received, the `Trigger` delivered to the `ksvc`, and the service *woke from zero* to receive it. The `405` is because the claims-processor has *no CloudEvents handler* — the app serves `/` (a `GET` is `200`), but a `POST` to it is *Method Not Allowed*. The taste proves *source → broker → trigger → scale-up*; *processing* the event (parsing the CloudEvent, branching, replying) is the *Eventing Deep-Dive* module, which starts from this exact end state. Don't add a fake handler to force a `200`.

*4. "Where's the Route? Can I `oc create route edge` for the service like the other modules?"*::
No — for a `ksvc` that's wrong, and it will fight the operator. The Serverless operator *auto-creates* an edge-terminated OpenShift Route (backed by the Kourier ingress) in the `knative-serving-ingress` namespace, and publishes the address on the service as `status.url`. Attendees can't read that ingress namespace (cross-namespace), which is *why* the lab uses `ksvc.status.url` everywhere — it's the attendee-readable proof the Route exists. This is the documented exception to the project's standing "browser Routes must be ``oc create route edge``" rule.

*5. "Why does it scale on concurrency and not CPU? What's KPA vs HPA?"*::
Knative's default is the *Knative Pod Autoscaler* (KPA), which scales on *concurrency* (in-flight requests) and — uniquely — can scale *to zero*. The *Horizontal Pod Autoscaler* (HPA) scales a normal Deployment on *CPU or memory* and has a floor of at least one pod. You *can* attach an HPA to a Knative revision (for CPU-based scaling), but the KPA is the default and the only path to scale-to-zero, which is the whole reason to use Serverless. Concurrency is usually the better signal for a request-driven service anyway — it tracks *offered load* directly, not its CPU side effect.

*6. "The function build takes minutes — why not build it in my terminal?"*::
The terminal has no container engine, and on most enterprise desktops building and pushing images locally is exactly what is locked down. `kn func deploy --remote` uploads the source into the attendee's own namespace and runs the build there as an OpenShift Pipelines pipeline (scaffold → S2I build and push → deploy), as the `pipeline` ServiceAccount. Measured here: about *2 minutes* end to end, of which Maven is about 40 s through the in-cluster mirror. The build runs once; every call after it is an ordinary `ksvc`, and the function's cold start (*~2.5 s*) is a fraction of the claims service's because it is one small handler.

== Watchouts

* *[FRAGILITY] Entry ksvc re-sync + the immutable-revision webhook.*
The entry `ksvc` pins its revision name (`parasol-claims-v1`) and omits `readinessProbe.successThreshold`. Knative defaults the stored value to `1`; a *patch*-style re-apply sends `0`, and because the revision name is unchanged, the validation webhook rejects it (`Saw the following changes without a name change … successThreshold`) — a `ws reset`/`ws prep` Argo sync can then hang retrying. Purge-then-recreate avoids it, which is the normal path, but flag it to the platform team. *Permanent fix:* add `readinessProbe.successThreshold: 1` to `gitops/entry-states/serverless-zero-to-hero/templates/parasol-claims-ksvc.yaml`, or drop the pinned revision name.
* *[FRAGILITY, root-caused 2026-07-31] `adm start` on an already-resident module purges nothing.* `gc_conflicts` in `tools/ws/ws` only calls `purge_ns` when EVICTING a *different* conflicting module — re-running `adm start <module> --user <u>` on the SAME module that is already resident is a pure no-op purge-wise (verified live: the Configuration object's UID was unchanged, an attendee-minted `parasol-claims-v2` survived byte-for-byte). Any fixed-name, immutable-on-recreate object an attendee mints during the lab (`parasol-claims-v1-warm`, `-v1-cold`, `-v2`) therefore outlives a bare `adm start` re-entry; if a *later* pass mints the same name with even slightly different content (a rebuilt image, a changed concurrency setting), Knative's admission webhook rejects it and the exercise hard-fails with no recovery in the lab text. `ws reset`/`ws prep` DO purge correctly (Knative Revision cascade-deletes cleanly via `oc delete services.serving.knative.dev`) — the gap is only that `adm start` never invokes it for a same-module re-run. *Content-level fix applied here:* each `kn service update --revision-name` step in the lab now clears any same-named leftover first (`oc delete revision <name> --ignore-not-found=true`). *Open platform question* (not decided here — it changes the contract of `adm start` for all ~28 modules and would silently wipe attendee work with no confirmation prompt, unlike `ws prep`): should `adm start` always purge-then-recreate, even for a same-module re-run?
* *Cold-start expectation — set it up front.*
The JVM cold start is a *range*, not a number: *~10–30 s* (five runs on this cluster — 11.80 s, 12.79 s, 15.27 s, 18.81 s and 26.51 s). Attendees who don't expect it read it as a hang — and an instructor who promises "about fifteen seconds" makes a 26-second start look like the failure, which is the same defect from the other side. The lab measures it and includes the `-m5` break-and-fix on purpose; reinforce that it's honest and tunable (`min-scale`, native builds). Don't let anyone "fix" it by assuming the cluster is broken. Note the lab's recovery step and the troubleshooting entry both use `-m 60` for this reason — a `-m 30` clears the slowest measured start by only 3.5 s, so it can time out and *demonstrate* the fault it exists to cure.
* *Per-user eventing footprint.*
The lab's `PingSource` fires *every minute* (`* * * * +++*+++`) so the delivery is observable in the session; the `adm solve` reference uses *every five minutes* (`+++*+++/5`). Across a full cohort that's a per-minute event per user waking a `ksvc` — light, but it multiplies. If the cluster is busy, prefer `+++*+++/5` or have attendees delete the `PingSource` after the beat.
* *Autoscale visibility depends on the load client.*
The `demo-client` is CPU-capped (200 m), so it can only offer modest concurrency. The lab uses a *hard* `containerConcurrency: 2` so the scale-up to `max-scale` is *deterministic*; a *soft* target may plateau at 1–2 pods from this client. If you demo a soft target, say so — the mechanism is the same, the visible curve is gentler.
* *max-scale ceiling times the cohort.*
Each attendee's `ksvc` can burst to its `max-scale` (3–5). Across many users bursting at once that's real scheduler and quota pressure; the per-user quota is sized for it, but watch a busy cluster during the autoscale beat.
* *[QUOTA] The function build is the heaviest moment in `{user}-dev` — measured, it fits.*
Containers without their own limits get the LimitRange default of *1500m* CPU, so the build pod holds *3* CPU of limits (two steps) and the function pod *1.8* (app 1500m + `queue-proxy`, capped at 300m by the platform), against a `limits.cpu` quota of *8*. The Tekton affinity assistant holds 50m. Measured peaks: *3.75* CPU in the shipped order, *6.35* CPU when the function was redeployed with exercise 6's every-minute `PingSource` waking `parasol-claims` — no `FailedCreate` either way. Before the `queue-proxy` cap (1500m per pod) the second case failed with `exceeded quota`; if that cap is ever lost, exercise 5 must stay ahead of exercise 6, which is why it sits there.
* *[FIRST BUILD] A cold Maven mirror makes the build ~6 minutes.*
The install's `maven-mirror-warm` Job resolves the `kn func` Quarkus template's dependencies (measured 3 min 47 s on 2026-11-12), so the first attendee already builds warm. Measured without it: *6 min 14 s* through a cold mirror; straight from Maven Central the build task alone ran *3 min 01 s* (Maven 2 min 17 s). If the room reports six-minute builds, check `oc get jobs -n ogsr-maven-mirror -l app.kubernetes.io/name=maven-mirror-warm` completed.
* *A terminal reconnect drops the shell shortcuts — the first block of each exercise restores them.*
A page reload, or `adm git-refresh --restart-terminals`, gives the attendee a fresh shell without `$NS`, `$URL` or `$FURL`. Exercises 2 to 6 each open with a block that re-reads them from the cluster, and the lab says so near the top. Every request that uses them fails loudly when they are empty — `bash: URL: is empty - run the first block of this exercise again` — instead of printing a misleading `HTTP 000`; send the attendee back to the exercise's first block.
* *Don't tune the shared autoscaler ConfigMap.*
`config-autoscaler` in `knative-serving` is cluster-wide. All attendee tuning is *per-`ksvc`* (annotations + `containerConcurrency`); never point an attendee at the shared ConfigMap.
