== My scheduled-import stream isn't in my project

Symptom:: You ran `oc import-image {user}-dev/ext-ubi …` and the stream is nowhere in `{user}-dev` — or it landed in a different project.
Cause:: `oc import-image` does *not* parse a `namespace/name` positional prefix the way `oc tag` does. It creates the stream in your *current* project (whatever `oc project` shows) and treats the argument as a bare name — so the `{user}-dev/` prefix is ignored.
Fix:: Look in your current project — that is where the stream went — then import it again with `-n $NS` and a *bare* stream name:
+
[source,sh,role=execute]
----
oc get is ext-ubi -n "$(oc project -q)"
oc import-image ext-ubi -n $NS --from=registry.access.redhat.com/ubi9/ubi:latest --scheduled --confirm | head -3
----
+
If the first command lists `ext-ubi` in a project other than `{user}-dev`, delete that stray copy with `oc delete is ext-ubi -n "$(oc project -q)"`. On the build cluster, running the command from the `default` project created `ext-ubi` in `default`; with `-n user3-dev` it landed correctly. `oc tag` *does* take `namespace/name` — the two commands differ here, which is the trap.

== An import fails with "name unknown: Repo not found"

Symptom:: `oc import-image` returns `error: Import failed (InternalError): … name unknown: Repo not found` and `error: imported completed with errors`.
Cause:: The `--from` reference points at a repository the registry doesn't have — a typo in the path, a wrong tag, or a repo that needs credentials you didn't supply.
Fix:: Read the import status (it names the cause), then import the *correct* reference:
+
[source,sh,role=execute]
----
oc get is <stream> -n $NS -o jsonpath='{range .status.tags[*].conditions[*]}{.message}{"\n"}{end}'
oc delete is <stream> -n $NS          # remove the broken stream
oc import-image ext-ubi -n $NS --from=registry.access.redhat.com/ubi9/ubi:latest --confirm | grep -i imported
----
+
The import *status* is always the first thing to read — it distinguishes a bad repo (`Repo not found`) from a private repo needing a pull secret from a registry the *policy* blocks (exercise 6).

== `oc tag` fails: "not currently pointing to an image"

Symptom:: `oc tag $NS/parasol-claims:9.9 $NS/parasol-claims:prod` errors with `"…:9.9" is not currently pointing to an image, cannot use it as the source of a tag`.
Cause:: The *source* tag doesn't exist (or hasn't resolved to a digest yet). You can only promote *from* a tag that already points at a real image.
Fix:: List the tags that actually exist, and promote from one of those:
+
[source,sh,role=execute]
----
oc get is parasol-claims -n $NS -o jsonpath='available tags: {.spec.tags[*].name}{"\n"}'
oc tag $NS/parasol-claims:1.0 $NS/parasol-claims:prod
----
+
Nothing is created when the source is missing — the command guards you, so just re-run with a real source tag.

== The pull-secret Deployment is `ImagePullBackOff` — "authentication required"

Symptom:: `oc rollout status` on `parasol-registry-demo` ends in `error: timed out waiting for the condition`, the pod sits in `ImagePullBackOff`, and the kubelet event reads `authentication required` for an `image-registry.openshift-image-registry.svc:5000/...` image. Confusingly, the *next* exercise pulls an image from the same internal registry without any trouble.
Cause:: The pod template names a pull secret *and* pulls from the **internal** registry. The ServiceAccount admission plugin injects the SA's `imagePullSecrets` **only when the pod's own list is empty** — so naming one secret *replaces* the injected set rather than adding to it, and the `default-dockercfg-…` credential that authenticates to the internal registry is silently dropped. The secret you named is for `registry.parasol.example.com`, which is fictional, so the pod ends up with no usable credential for the image it is actually pulling. The next exercise's pull works because it names no pull secret, so injection happens normally. This is namespace-independent: pointing at your *own* namespace's ImageStream fails identically.
Fix:: Pull an image that needs no credential (the lab uses a public Red Hat base image), or name *both* secrets — yours and the SA's `default-dockercfg-…` — on the pod template. Confirm which credentials the admitted pod actually got:
+
[source,sh,role=execute]
----
oc get pods -n $NS -l app=parasol-registry-demo -o jsonpath='{range .items[*]}{.metadata.name}{": "}{.spec.imagePullSecrets[*].name}{"\n"}{end}'
----
+
If that prints only your secret and no `default-dockercfg-…`, you are looking at this exact cause.

== The pull-secret Deployment stays Ready but never uses the private registry

Symptom:: The `parasol-registry-demo` Deployment is `Running`, but you expected it to *pull* from `registry.parasol.example.com` and it clearly didn't.
Cause:: This is *by design*. The sample pull secret's host (`registry.parasol.example.com`) is an *inert placeholder* that doesn't resolve — there is no real private registry behind it. The Deployment runs a *public* Red Hat base image (which needs no credential at all) so the pod is genuinely `Ready`; the `imagePullSecrets` reference is the artifact being wired, not a live external pull.
Fix:: Nothing to fix — confirm the reference is present (that's the graded outcome); on a *real* private registry the same wiring performs a real pull:
+
[source,sh,role=execute]
----
oc get deploy parasol-registry-demo -n $NS -o jsonpath='imagePullSecrets={.spec.template.spec.imagePullSecrets[*].name}{"\n"}'
----
+
For a real registry, create the secret with genuine credentials (`oc create secret docker-registry … --docker-server=<real-host>`) and point the container `image` at that host — the `imagePullSecrets` / `oc secrets link` mechanics are identical.

== My promoted `prod` tag shows `referencePolicy: Source`, not `Local`

Symptom:: The seed `1.0` tag has `referencePolicy: Local`, but after `oc tag …:1.0 …:prod` the new `prod` tag reads `referencePolicy: Source`.
Cause:: `oc tag` defaults to `--reference-policy=source`. That's *not* a problem for the promotion — `prod` still resolves to the *same immutable digest* as `1.0` (promotion by digest is intact). `referencePolicy` only affects *where* a workload pulls the bits from (the internal registry pull-through for `Local`, the recorded source for `Source`).
Fix:: If you want the promoted tag to *also* pull through the internal registry, tag with `--reference-policy=local` (or enable local name lookup on the stream):
+
[source,sh,role=execute]
----
oc tag $NS/parasol-claims:1.0 $NS/parasol-claims:prod --reference-policy=local
oc get is parasol-claims -n $NS -o jsonpath='{range .status.tags[*]}{.tag}={.items[0].dockerImageReference}{"\n"}{end}'
----
+
Either way, `prod` and `1.0` share the same `sha256` — the promotion is honest; `referencePolicy` is a pull-source detail, not the identity.

== An import is refused: `registry "registry-1.docker.io:443" not allowed by whitelist`

Symptom:: `oc import-image … --from=docker.io/…` prints `The ImageStreamImport "…" is invalid: … importing images from registry "registry-1.docker.io:443" is forbidden: … not allowed by whitelist: …` followed by the allowed registries, and no ImageStream exists afterwards. `registry-1.docker.io` is Docker Hub's real host.
Cause:: Working as designed (exercise 6). The cluster's `Image` config sets `allowedRegistriesForImport`, and admission refuses any import from a registry that is not on the list — for every user, cluster-admin included. It is a validation error (HTTP `422`), not a permissions problem, so no role you could be granted changes it.
Fix:: Import the same kind of image from a registry on the list. Read the list, then use an approved source:
+
[source,sh,role=execute]
----
oc get image.config.openshift.io cluster -o jsonpath='{range .spec.allowedRegistriesForImport[*]}{.domainName}{"\n"}{end}'
oc import-image nginx -n $NS --from=registry.access.redhat.com/ubi9/nginx-124:latest --confirm | head -1
----
+
On a real team, a registry that genuinely needs to be on the list is a request to the platform team — the list is one cluster-wide field they own.

== My `docker.io` import was accepted — and the approved one now fails

Symptom:: In exercise 6, `oc import-image nginx … --from=docker.io/library/nginx:latest` printed `imagestream.image.openshift.io/nginx imported`, and the Red Hat import that follows fails with `error: the tag "latest" points to "docker.io/library/nginx:latest" - use the 'tag' command if you want to change the source to "registry.access.redhat.com/ubi9/nginx-124:latest"`.
Cause:: This cluster has no import allowlist: `allowedRegistriesForImport` was never set, so every registry is allowed. The workshop installer sets it; if it is missing, that is a platform gap, not your mistake. The second error is a side effect: `oc import-image` will not silently re-point an existing tag at a different source.
Fix:: Tell your instructor the allowlist is missing. Then delete the stream and import from the approved registry, so the rest of the module matches:
+
[source,sh,role=execute]
----
oc get image.config.openshift.io cluster -o jsonpath='allowed: {.spec.allowedRegistriesForImport[*].domainName}{"\n"}'
oc delete is nginx -n $NS
oc import-image nginx -n $NS --from=registry.access.redhat.com/ubi9/nginx-124:latest --confirm | head -1
----
+
An empty `allowed:` line confirms the cause. Both behaviours were reproduced on a build cluster where the allowlist had not been applied yet.

== The governance reads are "Forbidden" (exercises 6–7)

Symptom:: `oc get image.config.openshift.io/cluster` (or the samples/ConsoleSample/pruner/catalogsource reads) returns `Error … "…" is forbidden`.
Cause:: The read-only `platform-observer` role isn't granting those resources — the Registry, Images & Catalog Governance extension (image config, samples, pruner, catalog sources, ConsoleSample) didn't land on this cluster, or your user isn't in the `workshop-attendees` group bound to it.
Fix:: This is a *platform* gap, not something to fix in your namespace — confirm the grant and tell your instructor if it's missing:
+
[source,sh,role=execute]
----
oc get clusterrole platform-observer -o jsonpath='{range .rules[*]}{.apiGroups}:{.resources}{"\n"}{end}' | grep -iE 'image|sample|catalog|console'
----
+
Expect rules covering `config.openshift.io` `images`, `imageregistry.operator.openshift.io` `imagepruners`/`configs`, `samples.operator.openshift.io` `configs`, `console.openshift.io` `consolesamples`, and `operators.coreos.com` `catalogsources`. If they're absent, the workshop-config `platform-observer` extension needs to be applied (an instructor/platform action).

== The quickstart pod crash-loops: `UnknownHostException: parasol-db`

Symptom:: After exercise 5, the `claims-quickstart` pod shows `Error` or `CrashLoopBackOff` and its `RESTARTS` count climbs, or `oc rollout status` times out. Its log ends in `Caused by: java.net.UnknownHostException: parasol-db`.
Cause:: The claims image connects to a PostgreSQL Service named `parasol-db` at startup unless it is told to run without a database. Your project has no such Service, so the service cannot start. The lab's Template sets the two `QUARKUS_*_ACTIVE=false` variables to run it database-free; a Template written without them, or with a typo in either, deploys a pod that crashes. Without a readiness probe, `rollout status` can even report success first, because the container is up for a few seconds before it fails.
Fix:: Read the reason from the crashed container, then add the two variables. `oc set env` rolls out a new pod that stays up:
+
[source,sh,role=execute]
----
oc logs deploy/claims-quickstart -n $NS --previous | grep -m1 UnknownHost
oc set env deploy/claims-quickstart -n $NS QUARKUS_DATASOURCE_ACTIVE=false QUARKUS_HIBERNATE_ORM_ACTIVE=false
oc rollout status deploy/claims-quickstart -n $NS --timeout=120s
oc get pods -n $NS -l app=claims-quickstart
----
+
Expect `1/1 Running` with `0` restarts on the new pod. Then add the same two `env` entries to your Template file and `oc apply` it again, so the next instance starts correctly.

== My namespaced Template doesn't appear in the Software Catalog

Symptom:: You applied the `parasol-claims-quickstart` Template but don't see it under *Ecosystem → Software Catalog → Template*.
Cause:: Either you're looking at a *different* project in the console (a namespaced Template only shows in *its own* project's catalog), or the console list needs a refresh.
Fix:: Confirm the Template is in *your* project via the CLI (the source of truth), then check the console is scoped to the same project:
+
[source,sh,role=execute]
----
oc get templates -n $NS
----
+
If `oc get templates -n $NS` lists it, it *is* registered — switch the console's project selector to `{user}-dev` and filter the Software Catalog to *Template*. It will never appear in another project's catalog; that namespacing is the whole point.

== I can't `podman push` to the internal registry

Symptom:: `podman login` / `podman push` to the internal registry fails to connect from your laptop.
Cause:: Most workshop and locked-down clusters' internal registry has *no external route* (`defaultRoute` is off) — it's an in-cluster Service reachable only from inside the cluster.
Fix:: Use the API-based image flows this module teaches — `oc tag`, `oc import-image`, in-cluster builds — which need no route:
+
[source,sh,role=execute]
----
oc get route -n openshift-image-registry           # check whether a route exists
oc get image.config.openshift.io/cluster -o jsonpath='internal: {.status.internalRegistryHostname}{"\n"}'
----
+
Direct `podman push` needs `defaultRoute: true` on the registry config (a platform decision that adds an external surface). The route-free posture is intentional for shared and locked-down clusters.
