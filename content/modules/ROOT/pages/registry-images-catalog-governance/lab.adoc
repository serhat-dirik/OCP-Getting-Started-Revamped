== The platform team decides what runs and what is offered · 10 min

Parasol's tested image is promoted to production by immutable digest, an unapproved registry is refused at admission, a base image is set to re-pull itself, and one team gets a catalog entry nobody else sees.

[IMPORTANT]
.Prep — run before the session
====
Stage the module from the cockpit terminal:

[source,sh,role=execute]
----
ws prep registry-images-catalog-governance
----

This demo runs from the *entry* state — only the seeded `parasol-claims:1.0` ImageStream in `{user}-dev` and the sample pull secret, nothing promoted and nothing imported — so there is no finished state to stage. The same command returns the world to that state between runs.

Step 2 relies on the import allowlist the workshop installer sets on the cluster. Confirm it is in place:

[source,sh,role=execute]

oc get image.config.openshift.io/cluster -o jsonpath='allowed: {.spec.allowedRegistriesForImport[*].domainName}{"\n"}'

=== Brief

image::registry-images-catalog-governance/registry-images-catalog-governance-01-two-supply-chains.svg["Two supply chains meeting at one developer. Along the top, external registries — registry.redhat.io, quay.io, docker.io — pass through the platform's governance controls (allowed registries for import, registry sources, IDMS/ITMS mirrors) into the cluster's internal registry on port 5000 with its volume and nightly pruner, then into an ImageStream that records an immutable digest, can re-import on a schedule, and can serve the bits locally, and finally into the running workload. Along the bottom, the catalog supply — OperatorHub sources, the samples operator, ConsoleSample, namespaced Templates and devfiles — feeds the Software Catalog the same developer picks from."]

*Two supply chains on one page*

Every image question a platform team gets is one of two supply chains that meet at the developer. The *image supply* decides which bits run. The *catalog supply* decides what a developer can pick from in the first place.

A container tag is a moving target: whoever pushes `parasol-claims:prod` next changes what that name means. An *ImageStream* is OpenShift's answer — a stable in-cluster name that records the immutable `sha256` digest behind each tag, can re-import an external image on a schedule, and can serve the bits from the internal registry as a pull-through cache.

*The trust boundary: where images may come from*

Signing answers "is this image trusted?" — a different axis, covered in the supply-chain module. This one answers "may images come from that registry at all?", and it is set cluster-wide. `allowedRegistriesForImport` answers it at admission: instant, no node change, and no exemption for anyone. `registrySources` and IDMS/ITMS mirroring answer it at the container runtime on every node — how a disconnected cluster runs, and why those two re-render and roll the whole node pool. Most failures of this kind are policy never set, not policy defeated.

The catalog is curated with the same kind of lever: OperatorHub sources, the samples operator and `ConsoleSample` are cluster-wide, while a `Template` in a project is the one entry a team can publish for itself.

*In this demo*

. The tested claims image promoted to production by immutable digest, with `prod` and `1.0` proven to be the same bits
. An unapproved `docker.io` import refused by the cluster's allowed-registries policy, and the same need met from an approved registry
. A base image marked for scheduled re-import, so it stays current with nobody watching it
. A catalog entry published into one project, and offered in that project alone

=== 1 · Promote by digest, not by tag — 3 min

Parasol tested build `1.0` and wants it in production. Promote it without a rebuild and without re-pushing a tag anyone could swap: pin production to the exact bits that were tested, then prove that is what happened.

image::registry-images-catalog-governance/registry-images-catalog-governance-02-imagestream-two-tags.png["The parasol-claims ImageStream detail page after the promote: Image count has gone from 1 to 2, and the Tags table now carries two rows — parasol-claims:1.0 and parasol-claims:prod. Read across to the Identifier column: both resolve to the same sha256:ca759845... digest. The promote created a second NAME for one image, not a second copy of it."]

*Why it matters*

"Is the image in production the one we tested?" is either provable or a matter of trust. A digest is content-addressed — it can never point at different bits — so promotion becomes a pointer move that can be audited, rather than a rebuild that has to be believed.

[source,sh,role=execute,subs="attributes+"]
----
NS={user}-dev
oc get istag parasol-claims:1.0 -n $NS -o jsonpath='1.0 -> {.image.metadata.name}{"\n"}'
oc tag $NS/parasol-claims:1.0 $NS/parasol-claims:prod
oc get is parasol-claims -n $NS -o jsonpath='{range .status.tags[*]}{.tag}{" -> "}{.items[0].dockerImageReference}{"\n"}\{end}'
----

*What just happened*

Both tags print the same `sha256`. `prod` is a second *name* for one image, not a second copy of it — an ImageStream promotion is a pointer to immutable content.

=== 2 · The floor: where images may come from — 3 min

The platform team set this cluster's floor before anyone signed in: images are imported only from registries Parasol trusts. Read that list, watch an unapproved `docker.io` import be turned away, then meet the same need from an approved registry.

[mermaid]
....

*Why it matters*

Without this list, `oc import-image docker.io/anything` succeeds. One field on the cluster `Image` config is the difference between "anywhere" and "only what we trust", and it takes effect at admission — instantly, with no node change and no exemption, cluster-admin included.

[source,sh,role=execute,subs="attributes+"]
----
NS={user}-dev
oc get image.config.openshift.io/cluster -o jsonpath='{range .spec.allowedRegistriesForImport[*]}{.domainName}{"\n"}\{end}'
oc import-image nginx -n $NS --from=docker.io/library/nginx:latest --confirm
----

The import is refused and no image arrives. `oc` answers with one long validation error that names Docker Hub by its real host, `registry-1.docker.io:443`, and then lists the registries that are allowed. Nothing rebooted and no pool rolled — admission simply declined the request.

The same need, met from a registry on the list — a Red Hat-built nginx:

[source,sh,role=execute,subs="attributes+"]
----
NS={user}-dev
oc import-image nginx -n $NS --from=registry.access.redhat.com/ubi9/nginx-124:latest --confirm | head -1
----

*What just happened*

The same stream name was refused from `docker.io` and accepted from `registry.access.redhat.com`, by one field nobody in this project can change. That is why it is the control a platform team sets on day one — and why the heavier node-level controls, `registrySources` and IDMS/ITMS mirroring, are planned maintenance work rather than something switched on in a session.

=== 3 · A base image that re-pulls itself — 2 min

Base images drift: upstream patches a CVE and the tag moves. Marking a tag *scheduled* hands that re-check to the platform instead of to a person.

image::registry-images-catalog-governance/registry-images-catalog-governance-01-imagestream-detail.png["The parasol-claims ImageStream detail page in this project: Image count 1, an Image repository of image-registry.openshift-image-registry.svc:5000 followed by the project and stream name, and a Tags table with a single row. That row is the anatomy every imported tag has — the tag name, the mutable reference it was imported From, and the immutable sha256 digest it currently resolves to in the Identifier column."]

*Why it matters*

A tag row holds both halves of the problem: the moving reference an image came from, and the fixed digest it resolves to today. A scheduled tag makes the platform re-resolve that reference on its own, so staying current stops being a standing task — and because each import is recorded as a digest, "when did this base image change?" stays answerable.

[source,sh,role=execute,subs="attributes+"]
----
NS={user}-dev
oc import-image ext-ubi -n $NS --from=registry.access.redhat.com/ubi9/ubi:latest --scheduled --confirm | head -3
oc get is ext-ubi -n $NS -o jsonpath='{range .spec.tags[*]}{.name}{" scheduled="}{.importPolicy.scheduled}{"\n"}\{end}'
----

*What just happened*

`scheduled=true`. OpenShift re-checks the source registry periodically and pulls the new digest when the upstream tag moves, with nobody watching it.

=== 4 · A catalog entry for one team only — 2 min

The last lever is the catalog itself. Publish a one-click Parasol starter into this team's project, where it appears in their Software Catalog and in nobody else's.

image::registry-images-catalog-governance/registry-images-catalog-governance-03-developer-catalog-template.png["The Software Catalog narrowed to Templates — the breadcrumb reads Software Catalog then Templates — with the keyword box filtered to Parasol and 2 items returned: a Parasol Claims Quickstart tile (Provided by Parasol Insurance, described as a one-click Parasol claims service) and a Parasol PostgreSQL (ephemeral) tile. Both are badged Templates, but they come from different places: the Quickstart Template lives in this project, so only this project's catalog shows it, while the PostgreSQL Template lives in the cluster-wide openshift namespace, which every project's catalog shows."]

*Why it matters*

Curating the catalog centrally takes cluster-admin — the samples operator, OperatorHub sources, `ConsoleSample`. A `Template` in a project takes none of that: a team publishes its own blessed starting point without a ticket, and without changing what any other team sees.

[source,sh,role=execute,subs="attributes+"]
----
NS={user}-dev
oc apply -n $NS -f - <<'EOF'
apiVersion: template.openshift.io/v1
kind: Template
metadata:
  name: parasol-claims-quickstart
  annotations:
    openshift.io/display-name: "Parasol Claims Quickstart"
    description: A one-click Parasol claims service for this project's catalog.
    tags: "parasol,claims,quickstart"
parameters:
  - {name: APP_NAME, value: claims-quickstart, required: true}
objects:
  - apiVersion: apps/v1
    kind: Deployment
    metadata: {name: "$\{APP_NAME}", labels: {app: "$\{APP_NAME}"}}
    spec:
      replicas: 1
      selector: {matchLabels: {app: "$\{APP_NAME}"}}
      template:
        metadata: {labels: {app: "$\{APP_NAME}"}}
        spec:
          containers:
            - name: claims
              image: image-registry.openshift-image-registry.svc:5000/ogsr-parasol-images/parasol-claims:1.0
              env:   # no database in this starter: the service runs, its claims API stays off
                - {name: QUARKUS_DATASOURCE_ACTIVE, value: "false"}
                - {name: QUARKUS_HIBERNATE_ORM_ACTIVE, value: "false"}
              securityContext:
                runAsNonRoot: true
                allowPrivilegeEscalation: false
                capabilities: {drop: [ALL]}
                seccompProfile: {type: RuntimeDefault}
EOF
oc get templates -n $NS
----

*On screen* — the web console → *Software Catalog* in `{user}-dev`, filtered to *Templates*: *Parasol Claims Quickstart* is listed, and it is listed nowhere else. One Template, one namespace — self-service with no cluster-admin, and the platform team still decides what is offered everywhere else.

== Frequently asked questions

*Why use an ImageStream at all — why not reference the image directly?*::
Three reasons, all of them on screen in this demo. It pins a moving tag to an immutable digest, so `prod` is provably the bits that were tested. It can re-import on a schedule, so a base image stays current on its own. And with `referencePolicy: Local` it acts as a pull-through cache — workloads pull from the internal registry rather than the source, which is faster and survives the source being briefly unreachable. A bare image reference gives you none of the three: the tag can move silently, nothing re-imports, and every pod pulls from the source.

*The allowed-registries control is cluster-wide — how do you change it safely?*::
`allowedRegistriesForImport` is admission-level and instant: no node reboot, no pool roll, and it reverts as fast as it applies. It governs every user's imports, so it is set before people arrive — this cluster's installer set it — and changed afterwards in an announced window like any other cluster policy. The list must name every registry the cluster already imports from, including the release images and the stock samples, or their scheduled re-imports start failing. The heavier controls are the ones to plan around — `registrySources` and IDMS/ITMS mirroring re-render `/etc/containers/registries.conf` on every node and roll the pool, so they are maintenance work, never a live toggle.

*Can we push to the internal registry from outside the cluster?*::
Not on this cluster: the registry has no external route, so it is reachable only from inside, and everything runs through the API — `oc tag`, `oc import-image`, in-cluster builds. A default route can be enabled, but it adds an internet-facing surface with TLS and pull-secret handling to own. Route-free is the usual posture for shared and locked-down clusters. Where an organization needs a shared multi-cluster registry with scanning, geo-replication and fine-grained access control, that is Red Hat Quay rather than the integrated registry.

*Could we offer that Template to everyone rather than to one project?*::
Yes, and it is a different object. A namespaced `Template` is the lever a team owns; a cluster-scoped `ConsoleSample` puts an entry in every project's catalog, and that is a platform-team change. Removing stock entries is the same story in reverse: individual samples are dropped with `skippedImagestreams` and `skippedTemplates`, never by setting the samples operator to `Removed`, which deletes all of them.

[%collapsible]

== 4. Pull from a private registry with a pull secret

Public images need no credentials; for a *private* registry, the workload presents a *pull secret* when it pulls.

[mermaid]

....

Inspect the sample in your namespace (safe to decode: a non-secret teaching sample):

.Expected output (a dockerconfigjson: a host, a username, an auth token)
[source,texinfo]
----

{"auths":{"registry.parasol.example.com":{"username":"parasol-puller","password":"parasol","auth":"cGFyYXNvbC1wdWxsZXI6cGFyYXNvbA==","email":"puller@parasol.example.com"}}}
----

.This is an *inert* sample — the host doesn't resolve
[%collapsible]
====
`registry.parasol.example.com` is a placeholder that doesn't exist, and the credential is a teaching sample, not a real secret.
So you can't perform a real *pull* from it — but you *can* learn the two mechanics that wire a pull secret to a workload, which is the transferable skill.
On a real private registry (or Red Hat Quay) you'd create this secret with `oc create secret docker-registry` using genuine credentials, and the *same* two mechanics apply unchanged.
====

*Mechanic A: link it to a ServiceAccount*, so every pod it runs can authenticate:

[source,sh,role=execute]
----
oc secrets link default parasol-registry-creds --for=pull -n $NS
oc get sa default -n $NS -o jsonpath='default SA pull secrets: {.imagePullSecrets[*].name}{"\n"}'
----

.Expected output (the secret is now on the ServiceAccount)
[source,texinfo]
----
default SA pull secrets: default-dockercfg-... parasol-registry-creds
----

*Mechanic B: name it on the pod template* (`spec.template.spec.imagePullSecrets`), the GitOps-clean form.
The workload runs a *public* Red Hat image, so it is genuinely `Ready`.

[IMPORTANT]
.Naming a pull secret *replaces* the ServiceAccount's — it does not add to it
====
Name one secret on the pod template and *nothing* from the ServiceAccount is injected, not even the `default-dockercfg-…` secret for the **internal** registry.
Pulling from both? Name *both* secrets on the pod template, or use mechanic A and name none.
====

.Why naming one secret drops the others
[%collapsible]
====
This is the trap that makes mechanic B different from mechanic A, and it is worth more than the mechanic itself.

The ServiceAccount admission plugin injects the SA's `imagePullSecrets` into a pod *only when the pod's own list is empty*.
The moment you name one secret on the pod template, that list is no longer empty and nothing is injected.

So a pod template that names `parasol-registry-creds` and pulls from `image-registry.openshift-image-registry.svc:5000` fails with `authentication required`, even though the pull worked a moment earlier without the line and the SA is correctly linked.
That is why the workload below deliberately pulls a *public* image: the only credential it needs is none.
On a real private registry the same rule applies.
====

[%collapsible]
====
Two heavier controls answer the same question at the container runtime: `registrySources` (which registries *any* pod or build may pull from) and *ImageDigestMirrorSet* / *ImageTagMirrorSet* (redirect pulls to a mirror — how a disconnected cluster runs).
Changing either re-renders `/etc/containers/registries.conf` on *every* node and rolls the whole pool, rescheduling every tenant's pods.
That is planned maintenance, not a workshop step, so they stay on the concept page.
====

Two more cluster-wide controls, read-only for you.

First, *retention*: the nightly pruner that reclaims registry storage:

[source,sh,role=execute]
----
oc get imagepruner/cluster -o jsonpath='keepTagRevisions={.spec.keepTagRevisions} suspend={.spec.suspend}{"\n"}'
oc get cronjob image-pruner -n openshift-image-registry
----

.Expected output (a daily pruner keeping the last 3 revisions — your ages will differ)
[source,texinfo]
----
keepTagRevisions=3 suspend=false
NAME           SCHEDULE    TIMEZONE   SUSPEND   ACTIVE   LAST SCHEDULE   AGE
image-pruner   0 0 * * *   <none>     False     0        17h             45h
----

*What just happened:* `0 0 * * *` is midnight daily, keeping the last 3 tag revisions and anything younger than an hour.
On a multi-day event an *unreferenced* image can be pruned overnight, so keep what you use *referenced* by a running workload.
