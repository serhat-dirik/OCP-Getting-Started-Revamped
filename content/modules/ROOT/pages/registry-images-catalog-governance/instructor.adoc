This module has two beats that land, and they bracket the hands-on.
The *promotion by digest* is exercise 2 — `prod` and `1.0` resolving to the *identical* `sha256` — which makes "an ImageStream pins a tag to immutable content" concrete and provable, not abstract.
The *import refusal* is exercise 6 — each attendee's own `docker.io` import refused at admission by the allowlist the install set, then the same need met from an approved Red Hat registry.
Everything between is the image lifecycle — scheduled imports, pull secrets, a namespaced Template — that makes those two beats legible; exercise 7 closes with a view-only read of retention and the catalog supply.

The single most common confusion is *"my scheduled-import stream isn't in my project."*
It's the exercise-3 gotcha: `oc import-image {user}-dev/ext-ubi` doesn't parse the `namespace/` prefix (unlike `oc tag`) — it creates the stream in the user's *current* project. The lab flags this in an IMPORTANT block and uses `-n $NS`; pre-empt it only if someone strays from the written command.

[source,texinfo]
----

* spec.tags[latest].from.name: Forbidden: registry "docker.io" not allowed by whitelist: "image-registry.openshift-image-registry.svc:5000", "registry.redhat.io:443", "registry.access.redhat.com:443"

Three things to get right, because the screen invites the wrong reading:

* *It is an `Invalid` response — HTTP `422`, a validation error — not a `403`.* The word `Forbidden` is on screen, but as the *per-field cause reason*, not as the HTTP status. No role an attendee could be granted changes it.
* *There are two causes for one import*, the same message on `spec` and again on `status`. A multi-line wall of red is the correct result, not a second failure.
* *There is no exemption.* The capture was taken as `kubeadmin`, and the import was refused exactly as it is for an attendee.

If an attendee's `docker.io` import is *accepted*, the allowlist is missing on this cluster — the lab tells them to say so, delete `nginx` and continue. Fix it for the room by applying the install's allowlist (pre-flight item 6), never by hand-editing a different list: the list must name every registry the cluster imports from (`registry.redhat.io`, `registry.access.redhat.com`, `quay.io`, and the internal registry), or the stock samples and OpenShift's own release image streams stop re-importing.

=== Mirroring — a talk track, not a step

`registrySources.allowedRegistries` (pull/push enforcement on every node) and an *ImageDigestMirrorSet (IDMS)* / *ImageTagMirrorSet (ITMS)* are how an air-gapped cluster runs — every image reference is mirror-served. If the room asks what one looks like:

[source,yaml]
----
apiVersion: config.openshift.io/v1
kind: ImageDigestMirrorSet
metadata:
  name: parasol-mirror
spec:
  imageDigestMirrors:
    - source: registry.redhat.io/ubi9
      mirrors:
        - mirror.internal.parasol.example.com/ubi9
----

Talk track: applying `registrySources` or an IDMS/ITMS makes the Machine Config Operator re-render every node and roll the pool — minutes of disruption that reschedules every tenant's pods, so it is never run during a workshop. IDMS mirrors *by digest*, ITMS *by tag*. The older `ImageContentSourcePolicy` did this before OpenShift 4.13 and is *deprecated* — convert it with `oc adm migrate icsp`.

=== Catalog curation — what attendees read, and what they own

Exercise 7 is view-only: the samples operator (`Managed`, both skip lists empty), cluster ``ConsoleSample``s (none) and the OperatorHub catalog sources.
Talk track: `skippedImagestreams` / `skippedTemplates` remove *one* sample from the catalog; `managementState: Removed` deletes *all* of them and breaks every module that uses the catalog. A `ConsoleSample` is how the platform publishes a blessed cluster-wide starter — the cluster-scoped sibling of the namespaced Template attendees published in exercise 5, which is the catalog lever they own.

== Demo-mode notes

Beyond the Say/Show/Do arc in the demo flavor:

* *Run the demo from the entry state, not `adm solve`.*
The story is *building* the governed supply chain from the seeded stream. `adm solve registry-images-catalog-governance` renders the finished end state (promoted tag, scheduled import, Template, pull-secret Deployment, the approved `nginx` import) — use it to *show the destination* or pre-stage, never as the demo's start.
* *Land the digest-equality line (beat 1).*
"Same `sha256` on both — production runs the image we tested, and I can prove it." Say it while the two identical digest lines are on screen. That equality *is* the point of an ImageStream promotion.
* *The allowed-registries beat (beat 2) changes nothing.*
The install already set the allowlist, so the demo only reads it and runs two imports into the presenter's own project — nothing to announce, nothing to revert. Confirm the list in Prep; if it is empty, the refusal will not happen.
* *Keep the Template beat namespaced.*
"One Template, one namespace" is the contrast with the cluster-wide samples operator. If asked "could I do this for everyone?" — yes, that's a `ConsoleSample` (cluster-scoped), a platform-team change rather than a namespaced Template.

== Top questions attendees ask

*1. "Why use an ImageStream at all — why not just reference the image directly?"*::
Three reasons you can point at from the lab: it *pins a moving tag to an immutable digest* (so `prod` is provably the bits you tested — you saw `prod` and `1.0` share a `sha256`), it can *re-import on a schedule* (the `ext-ubi` stream stays current on its own), and `referencePolicy: Local` makes it a *pull-through cache* (workloads pull from the internal registry, not the source). A bare image reference gives you none of those — the tag can silently move, nothing re-imports, and every pod pulls from the source.

*2. "My scheduled-import stream isn't in my project — where did it go?"*::
`oc import-image` does *not* read a `namespace/name` positional prefix the way `oc tag` does. `oc import-image {user}-dev/ext-ubi …` creates the stream in your *current* project (whatever `oc project` shows), not `{user}-dev`. Always pass `-n $NS` with a *bare* stream name. On the build cluster, running it from the `default` project created `ext-ubi` in `default`; with `-n user3-dev` it landed correctly. This is exercise 3's IMPORTANT block.

*3. "Can I push to the internal registry from my laptop with `podman push`?"*::
Not on this cluster — the registry has *no external route* (`defaultRoute` is off), so it's reachable only in-cluster. Everything runs through the API: `oc tag`, `oc import-image`, in-cluster builds. Enabling `defaultRoute` is possible but adds an internet-facing surface and TLS/pull-secret handling — a deliberate platform decision, not a default. The route-free posture is the common one for shared and locked-down clusters.

*4. "The pull-secret step didn't actually pull from the private registry — is it broken?"*::
No — the sample host (`registry.parasol.example.com`) is an *inert placeholder* that doesn't resolve, so a real external pull can't happen. The lab teaches the *mechanics* — linking a secret to a ServiceAccount `--for=pull` and naming it in a pod's `imagePullSecrets` — which are identical for a *real* private registry (or Quay). The Deployment runs a *public* Red Hat base image so the pod is genuinely `Ready` — naming a pull secret on the pod replaces the ServiceAccount's internal-registry credential, so an internal image would fail; the pull-secret reference is the artifact being wired, not a live external pull. That honesty is deliberate — the transferable skill is the wiring.

*5. "Why can't I import from Docker Hub — can you allow it for me?"*::
No, and that is the lesson. `allowedRegistriesForImport` is one cluster-wide list the install set before the session; it refuses imports from any other registry for *everyone*, cluster-admin included, and changing it would change it for every attendee. It is a validation error (`422`), not a permission, so no role grant helps either. The answer a platform team gives is the one exercise 6 shows: find the image on an approved registry (Red Hat builds nginx), or make the case for adding a registry to the list. *Never* reach for `registrySources` or IDMS/ITMS to answer this — those re-render every node and roll the pool.

== Watchouts

* *`oc import-image` uses the current project, not a `namespace/` prefix.*
The single most common stumble (question 2). The lab uses `-n $NS`; if a user's stream vanishes, check `oc get is ext-ubi -n default` (or wherever their `oc project` points). Harmless, but confusing — pre-empt it if you see it.
* *Never mutate a cluster singleton during the session.*
`allowedRegistriesForImport`, `registrySources`, IDMS/ITMS, the samples `Config`, `ConsoleSample` — all singletons. The allowlist is set once, by the install; nothing in this module asks you to change any of them live.
* *The allowlist must name every registry the cluster imports from.*
On the workshop cluster that is `registry.redhat.io` and `registry.access.redhat.com` (the stock samples, the `java-21` builder, the lab's `ext-ubi` and `nginx` imports), `quay.io` (OpenShift's own release image streams in `openshift`, all scheduled — dropping it breaks their re-import and can block an upgrade) and the internal registry. Leave `docker.io` off: exercise 6 depends on it being refused.
* *`managementState: Removed` on the samples operator is a foot-gun.*
It deletes *all* of the roughly 60 image streams and 50-odd templates — the catalog the Build & Deliver and other modules depend on. The disable-a-sample demo MUST use `skippedImagestreams`/`skippedTemplates`. Never `Removed` on a shared cluster.
* *The nightly pruner can delete unreferenced images mid-event.*
`ImagePruner/cluster` runs daily at midnight, keeping 3 tag revisions and sparing images younger than an hour. On a multi-day event, entry-state images that aren't referenced by a running workload can vanish overnight. Mitigation is an ops decision: keep them referenced, raise `keepTagRevisions`, or suspend the pruner for the event.
* *Registry storage is one RWO PVC.*
Thirty users' multi-day image churn lands on a single volume with a `Recreate` (one-pod) registry. A full registry blocks *every* push and build cluster-wide. Monitor fill on long events; size the PVC accordingly at bootstrap.
