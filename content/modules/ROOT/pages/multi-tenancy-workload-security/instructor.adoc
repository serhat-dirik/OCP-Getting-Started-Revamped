This module has two beats that land, and they bracket the session.
It *opens* on workload security — attendees scale a root-demanding Deployment and watch *restricted-v2* reject it live (exercise 1) — and it *closes* on the reveal that the platform governed *them* exactly the way they just governed the payments team (exercise 6).
Everything between is RBAC and quota vocabulary that makes those two beats legible.
Optimize the room for exercise 1 (let them read the rejection and find the UID range) and exercise 6 (let the "the platform did this to you" click).

The single most common confusion is *`oc auth can-i --as=<user>` returning the "wrong" answer* for group-granted access — impersonation does not carry group memberships.
Pre-empt it (see Watchouts); the lab sidesteps it by verifying the *ServiceAccounts* (whose grants are direct), not the user's group grants.

== Timing

Total hands-on: *~43 min* (add ~15 min of concept up front, ~5 min buffer).

`ws prep multi-tenancy-workload-security` waits up to *5 minutes* for the entry state to converge (the engine default sync window; this module declares no longer budget in `ws-meta.yaml`). It normally returns well inside that — the ceiling is a timeout, not a duration. Attendees start it themselves from the top of the *concept* page, so deliver the concept at its normal pace and it converges under you.

== Pre-flight checklist

Run these *before the session* (as cluster-admin, `KUBECONFIG` on the workshop cluster).

. *A sample user's entry state materializes and verifies.*
+
[source,sh,role=execute]
----
adm start multi-tenancy-workload-security --user user1
ws verify multi-tenancy-workload-security --user user1 --entry-only
----
+
Expect `✅ all 12 checks passed` when run as admin.
The checks cover the namespace, the entry marker, the three seeded ServiceAccounts (`payments-ci`, `payments-ops`, `root-demander`), the standing quota, the `root-demander` Deployment at *0 replicas*, that no NetworkPolicy isolates `user1-dev` yet, and (impersonation-guarded) that the teammates are still *ungoverned*.

. *The root-demander workload is seeded correctly (root-demanding, scaled to 0).*
+
[source,sh,role=execute]
----
oc get deploy root-demander -n user1-dev -o jsonpath='replicas={.spec.replicas} runAsUser={.spec.template.spec.containers[0].securityContext.runAsUser}{"\n"}'
----
+
Expect `replicas=0 runAsUser=0`.
If `runAsUser` is empty or replicas is 1, the world isn't at entry — `ws reset multi-tenancy-workload-security --user user1`.

. *restricted-v2 is the default SCC and the namespace has its UID range.*
+
[source,sh,role=execute]
----
oc get scc restricted-v2 -o jsonpath='runAsUser={.runAsUser.type}{"\n"}'
oc get ns user1-dev -o jsonpath='uid-range={.metadata.annotations.openshift\.io/sa\.scc\.uid-range}{"\n"}'
----
+
Expect `runAsUser=MustRunAsRange` and a range like `1000960000/10000` — the numbers the exercise-1 rejection will name (they differ per namespace; that's fine, the lab reads them live).

. *The standing quota and limits are present (attendees read, not create, these).*
+
[source,sh,role=execute]
----
oc get resourcequota workshop-quota -n user1-dev
oc get limitrange workshop-limits -n user1-dev
----
+
Expect both present.
They are *workshop-layer* objects (never chart-owned) — if missing, the workshop-config layer didn't sync; re-run `bootstrap/install.sh`.

. *`adm smoke` passes for a sample attendee — the only pre-flight check that runs as the attendee, in the real cockpit terminal.*
+
[source,sh,role=execute]
----
adm smoke multi-tenancy-workload-security user1
----
+
Every module declares `smokeCommands` in `ws-meta.yaml`; unlike the checks above (run from an admin context), `adm smoke` execs into the attendee's own Showroom terminal as `user1` and proves the representative commands work under their real identity, PATH, and namespace isolation — not just that the objects exist.

. *Exercise 7's install-time settings are in place.*
+
Exercise 7 has attendees *feel* cluster-wide settings, so the workshop install must have applied them before the session:
+
[source,sh,role=execute]
----
oc get clusterrolebinding self-provisioners -o jsonpath='subjects=[{.subjects[*].name}] autoupdate={.metadata.annotations.rbac\.authorization\.kubernetes\.io/autoupdate}{"\n"}'
oc get project.config.openshift.io cluster -o jsonpath='template={.spec.projectRequestTemplate.name}{"\n"}'
oc get template project-request -n openshift-config -o name
echo -n "attendee can request a project? "; oc auth can-i create projectrequests --as=user1 \
  --as-group=workshop-attendees --as-group=system:authenticated --as-group=system:authenticated:oauth 2>/dev/null
echo -n "attendee can read the template? "; oc auth can-i get templates/project-request -n openshift-config --as=user1 \
  --as-group=workshop-attendees --as-group=system:authenticated --as-group=system:authenticated:oauth
----
+
Expect `subjects=[] autoupdate=false`, `template=project-request`, `template.template.openshift.io/project-request`, then `no` and `yes`.
Include `system:authenticated:oauth` in the impersonation: it is the group the default self-provisioning grant names, so leaving it out makes `can-i` say `no` on a cluster where real logins still get `yes`.
If the first line still reads `subjects=[system:authenticated:oauth]`, attendees *will* create projects in exercise 7 — raise it with whoever ran the install rather than patching it mid-session.

== Exercise 7: what the install set, and what to say

Exercise 7 used to be an instructor demo that changed cluster singletons live.
It is now attendee work, because the cluster is dedicated to the workshop and the install sets the cluster-wide levers before anyone signs in:

* the `self-provisioners` ClusterRoleBinding emptied and pinned with `rbac.authorization.kubernetes.io/autoupdate=false` (without the pin, the cluster restores the default grant on its own);
* a `project-request` Template in `openshift-config` (the default Project and `admin` RoleBinding, plus `deny-by-default`, four narrow allows, and a count-only `starter-quota`), named in `project.config.openshift.io/cluster`;
* read access for `workshop-attendees` to `projects` and `oauths` (through `platform-observer`) and to the one template.

You change nothing during the session.
Attendees are refused `oc new-project`, read the policy, then apply the template's first two NetworkPolicies to `{user}-dev` and probe it from `{user}-prod`.

*Talk track for the template.* Point at the four allows: a bare default-deny would also cut off the router, monitoring, and the Dev Spaces gateway, so a real template pairs the deny with the few sources the platform itself needs.
The quota is count-only on purpose: a `requests.*` quota would refuse every Pod that declares no requests, and this template has no LimitRange to fill them in.

*Talk track for the identity providers.* Read out whatever the attendees' `oc get oauth cluster` returned rather than a fixed list — it is a property of the cluster.
`workshop-users` is the htpasswd provider the workshop appends; it is the one attendees sign in with.
On this build cluster the other is `rhbk`, Red Hat build of Keycloak: one identity system serving both app SSO and cluster login.
The OAuth CR is a merge-hazard singleton — its `identityProviders` list is replaced as a whole — which is why the workshop appends its provider imperatively instead of letting GitOps own the list.

== Demo-mode notes

Beyond the Say/Show/Do arc in the demo flavor:

* *Run the demo from the entry state, not `adm solve`.*
The whole story is *building* the sandbox from ungoverned nothing.
`adm solve multi-tenancy-workload-security` renders the finished end state (teammates governed, workload fixed and running) — use it to *show the destination* or to pre-stage a screenshot, never as the demo's start.
* *Let the rejection breathe.*
In beat 4, after `oc scale`, pause on the `restricted-v2 … runAsUser: Invalid value: 0` line.
This is the moment SAs remember — "no admission controller I installed; this is how OpenShift ships." Don't rush to the fix.
* *Land the least-privilege line.*
The sentence that makes security-minded attendees lean in: "same team, two service accounts — one can read the payment secrets, one is completely blind to them, and the difference is one custom Role."
* *A plain reset now clears your hand-made bindings too.*
`ws prep multi-tenancy-workload-security --user {user} --yes` removes the `edit`/`deployer` bindings and the `deployer` Role you granted during the demo, so the "ungoverned" opening lands clean on a second run.

== Top questions attendees ask

*1. "Why can't my namespace `admin` apply a ResourceQuota or grant an SCC? Isn't it admin?"*::
Because RBAC forbids *privilege escalation*: you cannot grant (or grant yourself) a permission you don't already hold.
The built-in `admin` role deliberately omits `resourcequotas`/`limitranges` write and has *no* SCC rule, so a namespace admin can't lift their own quota or smuggle their workload to root.
"admin" means "admin *of this namespace's contents and RBAC*," not "admin of the cluster's guardrails."
That scoping is exactly what makes the sandbox safe to hand a team.

*2. "This image runs as root fine on Docker/other clusters — why does OpenShift reject it?"*::
OpenShift's default `restricted-v2` SCC assigns every workload a non-root UID from the namespace's range and refuses `runAsUser: 0`.
It's a security default, not a bug: most software doesn't need root, and the container just needs to tolerate an arbitrary UID (numeric non-root user, group-writable paths).
Two fixes: *fix the image* (drop the root demand — almost always right), or, when a workload genuinely needs a fixed/elevated UID, a *scoped* SCC grant to that one ServiceAccount (`oc adm policy add-scc-to-user nonroot-v2 -z <sa>`).
Never blanket-grant `anyuid`.

*3. "``who-can get secrets`` returns over a hundred subjects — is the cluster misconfigured?"*::
No — that's normal and healthy.
Platform controllers, operators, the kubelet, and every namespace's `builder`/`deployer`/`default` ServiceAccounts legitimately need Secret access somewhere.
The number (101 on the build cluster) is why the lesson is *always filter*: `who-can … | grep <team>` for the subjects you actually govern.
An audit that dumps a hundred rows is one nobody runs; a filtered `who-can` alias is the deliverable.

*4. "I ran `oc auth can-i list nodes --as=user1` and it said `no`, but user1 CAN list nodes. Which is right?"*::
Both — it's an *impersonation* gotcha.
`--as=<user>` impersonates the *user identity only*; it does *not* add the groups that user belongs to.
User1's node access comes from the `workshop-attendees` *group* binding (`platform-observer`), so it's invisible to `--as=user1` alone.
Add the groups (`--as-group=workshop-attendees …`) to evaluate group-granted access, or test as a real login.
This is why the lab verifies the *ServiceAccounts* (direct bindings, which impersonation reflects correctly) and inspects the user's own access by reading the *bindings*, not by impersonating.

*5. "Why can't I create my own project? Every other cluster lets me."*::
Because the platform team turned self-provisioning off: nothing grants your login `create projectrequests`, so `oc new-project` is refused.
On a fresh OpenShift cluster that grant goes to every OAuth-authenticated user.
Removing it, and stamping the projects the platform does create from a template, is how "anyone can make a wide-open namespace" becomes "every namespace is born governed."
The trade is a request process for new namespaces, which is why most platform teams automate it (a portal form, a GitOps pull request) rather than leave it to tickets.

*6. "Should each team get its own namespace, or its own cluster?"*::
Default to *namespace-per-team*: RBAC + quota + NetworkPolicy isolate teams cheaply and densely on a shared cluster, and it's what the whole workshop runs on.
Step up only for a *real* boundary — hard regulatory separation or a contractually capped blast radius — and even then, *Hosted Control Planes* (a per-tenant API server sharing worker capacity) is usually the right rung before a full cluster-per-team.
Isolation is a cost multiplier; buy only what a specific requirement forces you to.

== Watchouts

* *Impersonation doesn't carry group memberships.*
`oc auth can-i --as=<user>` reflects direct user bindings but *not* group-granted access (platform-observer, self-provisioning).
Add `--as-group=…` or test with a real login.
Attendees who verify their own group access with plain `--as` will see false "no"s — steer them to reading the *bindings* (as the lab does).
* *Exercise 7 needs the install's settings.*
If an attendee's `oc new-project` *succeeds*, self-provisioning is still on: have them `oc delete project <name>` and run pre-flight step 6.
Do not fix it mid-session — emptying the binding is the install's job, and `oc adm policy remove-cluster-role-from-group` leaves a stray parallel binding behind when it is later undone.
* *No other module creates projects.*
Every attendee namespace is created by Argo CD as a `Namespace` object, which never goes through the project request template, so the template does not touch them.
Dev Spaces can create `{user}-devspaces` itself when a module has not pre-created it (its ServiceAccount holds `create projectrequests`); a namespace made that way is stamped from the template, which is why the template carries `allow-from-openshift-devspaces`.
* *Exercise 7's NetworkPolicies stay in `{user}-dev` until a reset.*
`ws prep`/`ws reset` purge every NetworkPolicy in `{user}-dev`, and every other module that shares that namespace preps with the same purge, so the next module starts open.
* *`ws reset` now purges attendee-authored RoleBindings too.*
This is the first module where attendees *create* RBAC as the core exercise; the `ws reset` namespace purge clears workloads/Secrets *and* the `edit`/`deployer` bindings and `deployer` Role declared in this module's `ws-meta.yaml` (`purgeRbac`).
The impersonation-guarded entry check "teammates are ungoverned" confirms this on every run.
* *Never print a bound token.*
The lab mints tokens and decodes only their *claims*; the token itself is a live credential — don't echo it, don't paste it into chat.
* *The UID range differs per namespace.*
`restricted-v2` draws from each project's `openshift.io/sa.scc.uid-range` annotation, so the exact numbers in the exercise-1 rejection differ per attendee — the lab reads them live rather than hardcoding, and so should you when helping.
