This module has two beats that land, and they bracket the hands-on.
The *break-and-fix* is exercise 4 — the batch pod stuck `Pending` on an untolerated taint, then *snapping* onto the batch node the instant the toleration is added — which makes the single most important distinction concrete: *a selector attracts, a taint repels, a toleration only permits*.
The *proof* is exercise 5 — attendees *diagnose* why a rollout drops requests (a value planted in the database reverts to its seed after one pod restart, because every boot reseeds the *shared* `claims-db`), fix it at the source (`schema-management=none`), then watch `maxUnavailable: 0` hold available replicas flat at 3 through a live rollout and a PodDisruptionBudget *refuse* an eviction rather than breach its floor.
Everything between is the mechanics — requests/QoS, anti-affinity, topology spread — that make those beats legible.

The single most common confusion is *"I set a nodeSelector for the pool and my pod won't schedule."*
It's the exercise-4 lesson: the pool node is tainted, and a selector doesn't carry permission.
The lab teaches the break directly (add the selector alone, read the `Pending`), so pre-empt it only if someone skips ahead.

== Instructor demo — taint a pool, and drain through a PDB (exercise 6)

Both operations are *cluster-wide* — they affect every tenant on a shared cluster — so keep them instructor-performed.
*Do the drain on a disposable or clearly-safe node only*; on a shared workshop cluster a real `oc adm drain` evicts other users' pods.

=== Create a pool (how the batch pool was made)

[source,sh,role=execute]
----
oc label node <a-worker> workshop.redhat.com/pool=batch
oc adm taint node <a-worker> workshop.redhat.com/pool=batch:NoSchedule
oc get nodes -l workshop.redhat.com/pool=batch
----

Talk track: the label is the *attractor* (a `nodeSelector` target), the taint is the *repeller* (`NoSchedule` keeps untolerated pods off). Together they make a dedicated pool. The label evicts nothing; `NoSchedule` only blocks *new* untolerated pods. This is exactly the pair a platform team applies — often via a MachineSet's `spec.template.spec.metadata.labels` and a machine-config — to build GPU/batch/licensed pools.

=== Drain a node through the PodDisruptionBudget

With a claims pod on `<node>` and the exercise-5 PDB (`minAvailable: 1`) in place:

[source,sh,role=execute]
----
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data --pod-selector app=parasol-claims
----

Talk track: the drain *evicts* the claims pod (the budget allows one — `ALLOWED DISRUPTIONS: 2`), and it reschedules on a *distinct* node because the anti-affinity still holds. If you first exhaust the budget (`oc patch pdb parasol-claims --type=merge -p '{"spec":{"minAvailable":3}}'`), the same drain *waits*, printing:

[source,texinfo]
----
error when evicting pods/"parasol-claims-..." -n "user2-dev" (will retry after 5s):
Cannot evict pod as it would violate the pod's disruption budget.
----

That message — captured directly from the eviction API on the build cluster — is the whole point of a PDB: a voluntary disruption blocks rather than breaches. Restore `minAvailable: 1` afterwards.

== Demo-mode notes

Beyond the Say/Show/Do arc in the demo flavor:

* *Run the demo from the entry state, not `ws solve`.*
The whole story is *building* the controls from default scheduling. `ws solve deployment-targets-scheduling` renders the finished end state (spread + pinned + PDB) — use it to *show the destination* or pre-stage, never as the demo's start.
* *Let the `Pending` breathe (beat 1).*
After the `nodeSelector`-only patch, pause on `statement-batch` at `Pending` and read the `FailedScheduling` event aloud. "Untolerated taint" is the line that makes "a selector attracts, a toleration permits" land. Then the toleration snaps it into place — that contrast is the beat.
* *Land the capacity line (beat 3) — but check the roll landed first.*
"``available=3/3`` the whole way through." Say it while the sample loop scrolls `available=3/3` repeatedly. That's the visible proof `maxUnavailable: 0` never dropped the floor.
Glance at `oc rollout status` before you say it, though: the same flat number appears when the roll is *wedged* and the old pods are simply still serving. Never claim the win off the sampler alone.
* *You can claim zero now — and should.*
If asked "so it's *zero* dropped?" the honest answer is *no — a couple, and the reason is worth more than the number*. Measured 2026-07-29 on five confirmed-completed rolls, all at three replicas: the default roll at the entry state dropped *4* of ~292; with `schema-management=none` applied, *1* and *3* of ~285 (*3* and *4* with the reseed still on and only the strategy hardened). An older `dropped=15` capture from a previous cluster generation is no longer quoted anywhere — the counts are timing-sensitive and a magnitude nobody can reproduce is worse than none. The bulk of the drops came from a boot-time reseed of the shared database and `schema-management=none` removes that cause entirely; what remains is the ordinary cost of retiring a pod — endpoint removal propagates asynchronously, so a request can still reach a pod that is already shutting down, even though the app drains `SIGTERM` gracefully (`quarkus.shutdown.timeout`). Reaching a true zero needs a `preStop` hook that keeps the pod serving while it is de-registered; name that as the next technique rather than claiming this one already got there.

== Top questions attendees ask

*1. "My pod is `Pending` — how do I find out why?"*::
Read the `FailedScheduling` event: `oc get events -n <ns> --field-selector reason=FailedScheduling`.
It names the reason *node by node* — `untolerated taint(s)`, `didn't match Pod's node affinity/selector`, `didn't match pod anti-affinity rules`, `Insufficient cpu/memory`.
On the 6-node build cluster the anti-affinity case read `0/6 nodes are available: 1 node(s) had untolerated taint(s), 5 node(s) didn't match pod anti-affinity rules` — one tainted batch node plus every other node already holding a claims pod. On a differently-sized cluster both totals track its node count (the `0/N` is all nodes; the anti-affinity count is the non-batch nodes) — the lab derives them live, so don't read `6`/`5` as fixed.
That one line answers almost every "why won't it schedule," and it's always the first thing to read.

*2. "I added a `nodeSelector` for the pool and my pod won't schedule."*::
The pool node is *tainted*, and a `nodeSelector` doesn't carry permission.
A selector *attracts* (sends the pod at the node); a *toleration* *permits* (lets it past the taint). You need *both* — the selector to choose the node and the toleration to be allowed on it.
This is exercise 4's break-and-fix: `nodeSelector` alone → `Pending` with "untolerated taint"; add the matching toleration → it schedules.
A toleration *without* a selector is the opposite mistake — the pod is *allowed* on the tainted node but just as likely lands anywhere else.

*3. "Why did my rollout drop requests even with `maxUnavailable: 0`?"*::
Because `maxUnavailable: 0` only guarantees *capacity* — the count of *ready* pods never dips (verified: 18/18 samples at `3/3`) — and the drops here are a *data-plane* disruption at pod *startup*, not a connection-plane one at shutdown.
The `parasol-claims` image boots with Hibernate `drop-and-create`, so every new pod reseeds the *shared* `claims-db`, wiping tables out from under the pods still serving.
The deterministic tell is in the lab: a value written to `CLM-1001` reverts to its seed (`UnderReview`) after a single pod restart.
The fix is `schema-management=none` (seed the DB once at deploy instead), after which a re-measured probe falls to single digits (4 and 3 out of ~270, measured 2026-07-29). Shutdown-side tuning (`preStop`, `terminationGracePeriodSeconds`, `quarkus.shutdown.timeout`) never addressed *this* fault — the damage is done by a pod *arriving*, not leaving; it is what you would reach for next to close the residual few.

*4. "The node drain is hanging and won't evict anything."*::
Two possibilities, both PDB-related.
Either the budget is *exhausted* and the drain is *correctly waiting* (evicting more would breach `minAvailable`) — that's the feature working; the other node(s) will free up.
Or someone set `minAvailable` *equal to* the replica count, which leaves *zero* eviction room and *deadlocks* the drain forever.
Check `oc get pdb -n <ns>`: `ALLOWED DISRUPTIONS: 0` with `minAvailable == replicas` is the deadlock; lower `minAvailable` below the replica count.

*5. "The anti-affinity rollout is really slow — is it stuck?"*::
No — required `podAntiAffinity` makes a rolling update *sequential*.
With `maxSurge: 1`, each new pod must find a node with no other claims pod, so it waits for an old pod to vacate before the next replica rolls.
It's deliberate, not stuck (watch `oc rollout status` progress one replica at a time).
The one real trap: if replicas *equal* the number of eligible (non-batch) nodes, the surge pod has *nowhere* to go and the roll wedges — keep replicas below the eligible-node count (on this 6-node cluster that's the 5 non-batch nodes, so ≤4; on another cluster it's that cluster's non-batch count) so there's always a free node to surge onto.

== Watchouts

* *Required anti-affinity + rolling update = sequential, and can wedge.*
The roll is slow by design (see question 5). It *wedges* only if replicas == eligible nodes (the surge pod can't place). The lab scales to *one past the eligible-node count* (`ELIGIBLE+1`, computed live — 6 on this 6-node cluster) *deliberately* to show the `Pending`, then back to 3; don't leave a user scaled to the eligible count with `maxUnavailable: 0` or their next roll can't surge.
* *Use a `--type=strategic` patch for container-level edits.*
`--type=merge` replaces the whole `containers` list and fails with `spec.containers[0].image: Required value`. The lab flags this in an IMPORTANT block; if a user hits it raising the CPU limit (the resources step), that's the cause — the `oc set resources`/`oc set env` helpers sidestep it.
* *The exercise-5 CPU limit is `1` because the namespace quota says so — don't let an attendee "improve" it.*
In `{user}-dev`, `workshop-quota` caps `limits.cpu` at *6* and the namespace's other four workloads already hold *1300m*. Three claims replicas plus the `maxSurge: 1` pod fit at `limits.cpu: 1` (*5300m*) and do *not* at `2` (*7300m*) — at `2` the new ReplicaSet reports `ReplicaFailure`/`FailedCreate` with `exceeded quota: workshop-quota` and the roll never starts.
The trap is that `maxUnavailable: 0` keeps the old pods serving, so the lab's capacity sampler still prints `available=3/3` for the whole window and it *looks like the lesson worked*. The lab now follows the sampler with an `oc rollout status`; if someone reports "it says 3/3 but nothing happened", this is it.
Raising the quota is the wrong fix — it is a shared workshop-wide object and every other module's resource lesson leans on it.
* *You can promise "0 after" — the cause is deterministic.*
The fault is a boot-time reseed of the shared DB (every pod boot runs `drop-and-create`), which is why a planted value reverts to its seed *every* time — a deterministic signature, not noise. Once `schema-management=none` removes the reseed, the re-measured tight probe comes down — measured 2026-07-29 on confirmed-completed rolls: *1* and *3* out of ~285 with the fix applied, against *4* of ~292 at the entry state (*3* and *4* with the reseed still on and only the strategy hardened). Frame the win as *both* capacity held flat (`maxUnavailable: 0`) *and* the reseed removed (`schema-management=none`) — "before: a burst of drops; after: a handful."
*Do not promise zero.* `maxUnavailable: 0` guarantees capacity, not that every in-flight request lands: endpoint removal propagates asynchronously, so a request can still reach a pod that is already shutting down. If an attendee asks how to reach a true zero, the answer is a `preStop` hook plus graceful shutdown — a different technique, and a good pointer for the wrap-up. The *shape* (before ≫ after, after in single digits) is what's deterministic; the exact digits are not.
* *The `master` role label shows on screen — say "control plane".*
`oc get ds … nodeSelector` prints `node-role.kubernetes.io/master` for the control-plane-only agent. It's the legacy role label Kubernetes still sets; refer to those nodes as *control plane* in prose, and don't try to rename the label.
* *Exercise 4's `Pending` moment needs a TAINTED batch pool — not just a labeled one.*
Bootstrap only applies the `NoSchedule` taint at a 3-worker floor (see the pre-flight IMPORTANT box
above). Below the floor the node is labeled but not tainted, and the `nodeSelector`-only patch in
exercise 4 schedules immediately instead of going `Pending` — the lab's own precondition check tells
the attendee this live, so don't treat a "no Pending pod" report as something broken. `ws verify`
agrees: it reports the taint check as `➖` not-applicable and still ends green, so an attendee showing
you that banner has a *complete* run, not a half-graded one.
* *The batch pool is one node shared by all users.*
Each `statement-batch` is tiny (50m/64Mi), so ~30 users' batch pods fit comfortably. If a user scales `statement-batch` up hard, it could crowd the node — the `{user}-dev` quota keeps it bounded. Don't add a second dedicated pool per user; it's shared substrate by design.
* *This module is the catalogue's node-headroom canary.*
It is the only module that asks the scheduler for *four distinct placements at once* (three anti-affinity-spread replicas plus a surge pod). Every other module's workloads will happily pile onto one node. If the cluster is tight, this module is where you find out — see the pre-flight headroom check.
* *Never run a real `oc adm drain` on the shared cluster hands-on.*
It evicts *every* tenant's pods on that node, not just the demo user's. Keep the drain instructor-only, on a disposable or clearly-safe node; the PDB-block message can be shown safely via the eviction API (exercise 5) without draining anything.

Exercise 5's raised CPU limit was *2* until 2026-07-28, when it was found to exceed the `{user}-dev` `limits.cpu` quota (three replicas plus the surge pod ask 7300m against a cap of 6) — the ReplicaSet could never create a pod, and the capacity sampler's flat `available=3/3` made the wedged roll read as a success. Lowering the limit to *1* brings the peak to 5300m; that arithmetic was confirmed against the live quota, and the cold-start re-measured as *23/25/33 s* at 500m versus *14–15 s* at `limits.cpu: 1` (six pods) on OpenShift 4.21.22 / Kubernetes 1.35.
The fix (`schema-management=none` + a decoupled seed-at-deploy Job + the raised CPU limit, alongside the kept `maxUnavailable: 0` and PDB) ships in this module's entry-state solve rendering; the attendee applies each field in the lab.
Graceful `SIGTERM` draining (`quarkus.shutdown.timeout`) is already in the image and was *not* the cause.
