== Demo arc — Dedicated nodes and a zero-downtime roll in ten minutes (10 min)

[NOTE]
.Before you present
====
Run `ws prep deployment-targets-scheduling --user {user}` a few minutes ahead, and set `NS={user}-dev` in your terminal.
This demo runs from the *entry* state (default scheduling, batch worker unpinned), *not* from `ws solve`.
Keep the terminal font large and `oc get pods -o wide` handy; node placement is the whole visual.

*Check the taint before you promise beat 1.* Bootstrap only applies the batch-pool *taint* on a worker
pool of 3 or more nodes (below that floor it labels the node but withholds the taint — tainting one of
only two workers once starved a platform component of capacity for 4h+, so bootstrap will not repeat
that). Run this first:
+
[source,sh,role=execute]
----
oc get nodes -l workshop.redhat.com/pool=batch -o jsonpath='{.items[0].spec.taints}{"\n"}'
----
+
*If that prints a `NoSchedule` taint*, beat 1 runs exactly as scripted below — the money moment is the
batch pod stuck *Pending* on the untolerated taint, then *snapping* onto the batch node the instant you
add the toleration.
*If it prints nothing*, this cluster is below the floor: the `nodeSelector`-only patch will schedule
the pod *immediately*, not go `Pending`. Don't stage the refusal — reframe the Say line to "the
toleration is what you'd need if this node repelled you; on a bigger cluster it does" and skip straight
to applying both fields together. Never hand-taint the node to force the original beat — that recreates
the outage.
====

[demo-block]
[TIME 3m]
Say:: "Parasol's monthly-statement *batch* job is running on the same nodes as the live claims API — fighting it for CPU. We have a *dedicated* pool of nodes for batch work. Watch me move it there — and watch it refuse, first, for a reason worth understanding."
Show:: `statement-batch` on a general node; the batch pool node (labelled + tainted); then the pod going *Pending* on `nodeSelector` alone, and *scheduling* once the toleration is added.
Do:: Pin the batch worker onto its pool:
+
[source,sh,role=execute,subs="attributes"]
----
NS={user}-dev
oc get pods -n $NS -l app=statement-batch -o wide
oc get nodes -l workshop.redhat.com/pool=batch
# nodeSelector ALONE — the pod is attracted but not permitted (the taint blocks it)
oc patch deploy statement-batch -n $NS --type=merge -p '{"spec":{"template":{"spec":{"nodeSelector":{"workshop.redhat.com/pool":"batch"}}}}}'
sleep 10
oc get pods -n $NS -l app=statement-batch
oc get events -n $NS --field-selector reason=FailedScheduling | tail -1
----
+
"'Untolerated taint' — the selector *sent* it to the batch node, but the node *repels* it. A selector attracts; it doesn't permit."

[demo-block]
[TIME 2m]
Say:: "One toleration — 'this pod is allowed on the batch node' — and it snaps into place. Selector to *send* it, toleration to *permit* it. You need both."
Show:: The toleration added; the pod now *Running* on the batch pool node.
Do:: Add the toleration and confirm the pin:
+
[source,sh,role=execute]
----
oc patch deploy statement-batch -n $NS --type=merge -p '{"spec":{"template":{"spec":{"tolerations":[{"key":"workshop.redhat.com/pool","operator":"Equal","value":"batch","effect":"NoSchedule"}]}}}}'
oc rollout status deploy/statement-batch -n $NS --timeout=60s
oc get pods -n $NS -l app=statement-batch -o wide
----
+
"On its own nodes now — the API never has to share a CPU with a statement run again."

[demo-block]
[TIME 3m]
Say:: "Now the claims API. Every time a new pod boots it *reseeds the shared database* — silently discarding every claim filed since the last deploy. That's the real reason a naive rollout loses data, and no shutdown tuning fixes it. I'll stop the reseed, hold capacity flat, and redeploy under live traffic — the claim I plant first will still be there afterward."
Show:: The schema strategy flipped to `none`, `maxUnavailable: 0` and a raised CPU limit applied; a value written before the roll still present after it; `availableReplicas` holding flat at 3 through the rollout restart.
Do:: Stop the boot-time reseed, harden the roll, then redeploy under load:
+
[source,sh,role=execute]
----
oc set env deployment/parasol-claims QUARKUS_HIBERNATE_ORM_SCHEMA_MANAGEMENT_STRATEGY=none -n $NS
oc patch deploy parasol-claims -n $NS --type=strategic -p '{"spec":{"strategy":{"type":"RollingUpdate","rollingUpdate":{"maxSurge":1,"maxUnavailable":0}},"template":{"spec":{"containers":[{"name":"parasol-claims","resources":{"requests":{"cpu":"200m","memory":"256Mi"},"limits":{"cpu":"1","memory":"512Mi"}}}]}}}}'
oc rollout status deploy/parasol-claims -n $NS --timeout=180s
# plant a claim state the seed doesn't carry, then redeploy under live traffic
oc exec deploy/claims-load -n $NS -- curl -s -X PUT http://parasol-claims:8080/api/claims/CLM-1001/status -H 'Content-Type: application/json' -d '{"status":"Approved"}' -o /dev/null
oc rollout restart deploy/parasol-claims -n $NS
for i in $(seq 1 10); do oc get deploy parasol-claims -n $NS -o jsonpath='available={.status.availableReplicas}/{.spec.replicas}{"\n"}'; sleep 4; done
oc exec deploy/claims-load -n $NS -- curl -s http://parasol-claims:8080/api/claims/CLM-1001 | grep -o '"status":"[^"]*"'
----
+
"``available=3/3`` the whole way through — and `CLM-1001` is *still* `Approved` after the roll, because the pods no longer reseed the database on boot. A mid-day redeploy the customers never felt."

[demo-block]
[TIME 2m]
Say:: "Last piece: protect it during a *drain*. A disruption budget says 'never take me below one healthy pod.' An admin draining nodes has to *wait its turn* instead of evicting my last replica."
Show:: The PDB created; an eviction *allowed*, then — with the budget exhausted — *denied* with the exact message a node drain hits.
Do:: Show the budget in force:
+
[source,sh,role=execute]
----
oc apply -n $NS -f - <<'EOF'
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: {name: parasol-claims}
spec: {minAvailable: 1, selector: {matchLabels: {app: parasol-claims}}}
EOF
oc get pdb parasol-claims -n $NS
# budget has headroom — this eviction is ALLOWED
POD=$(oc get pods -n $NS -l app=parasol-claims -o jsonpath='{.items[0].metadata.name}')
echo '{"apiVersion":"policy/v1","kind":"Eviction","metadata":{"name":"'"$POD"'"}}' | oc create --raw /api/v1/namespaces/$NS/pods/$POD/eviction -f -
sleep 8
# now exhaust the budget — the next eviction is DENIED
oc patch pdb parasol-claims -n $NS --type=merge -p '{"spec":{"minAvailable":3}}'
sleep 3
POD=$(oc get pods -n $NS -l app=parasol-claims -o jsonpath='{.items[0].metadata.name}')
echo '{"apiVersion":"policy/v1","kind":"Eviction","metadata":{"name":"'"$POD"'"}}' | oc create --raw /api/v1/namespaces/$NS/pods/$POD/eviction -f - || true
oc patch pdb parasol-claims -n $NS --type=merge -p '{"spec":{"minAvailable":1}}'
----
+
"'Cannot evict pod as it would violate the pod's disruption budget' — that's a node patch politely waiting instead of taking the service down."

Run it before a second demo so beat 1 lands clean.

[NOTE]
.Why the taint line can be empty — and what that does and doesn't tell you
====
The platform only applies the `NoSchedule` taint once the worker pool has *3 or more* nodes; below that floor it deliberately withholds it, because tainting one of only *two* workers once starved a platform component of capacity for 4+ hours on a live cluster.
If your taint line came back empty, `NoSchedule` isn't in effect here: nothing is stopping an ordinary pod from landing on `worker-1` — if none of your app's pods happen to be there right now, that's *chance placement*, not a taint repelling them.
If you *did* get a taint, then `NoSchedule` means "no pod lands here unless it explicitly tolerates the `workshop.redhat.com/pool=batch` taint" — and that genuinely is why none of your app's pods are on `worker-1`.
Exercise 4 checks this again and walks you through exactly what it means for the break-and-fix ahead.
====

== 2. Direct the API with pod anti-affinity
⏱ *~8 min* · force the replicas apart, read a scheduler refusal, watch a reschedule

Your two `parasol-claims` replicas *happen* to be on different nodes — but that's the scheduler's *soft preference*, not a guarantee.
On a busy cluster both could land on one node, and one node failure would take the whole API down.
Turn "prefers apart" into *required* apart with `podAntiAffinity` on `kubernetes.io/hostname` (no two claims pods on the same node):

// Verified live OCP 4.22.5, 2026-07-26: parasol-claims's detail page carries a YAML tab directly
// (Details · Metrics · YAML · ReplicaSets · Pods · Environment · Events · Security) — no need to go via
// Actions. It renders the COMPLETE resource, so spec.template.spec.affinity is exposed there by construction.
[tabs]
====
Console::
+
--
Open *Workloads* → *Deployments* → `parasol-claims` → *Actions* → *Edit Deployment* (YAML).
Under `spec.template.spec`, add an `affinity.podAntiAffinity` with a `requiredDuringSchedulingIgnoredDuringExecution` rule matching `app: parasol-claims` on `topologyKey: kubernetes.io/hostname`, then *Save* — the same object the CLI tab patches.

image::deployment-targets-scheduling/deployment-targets-scheduling-02-edit-deployment-affinity.png["The parasol-claims Deployment on its YAML tab. The console folds managedFields into a single line, so the whole workload spec fits in one view: replicas 3, the container resources and both probes, and then at lines 235 to 241 the block this exercise adds — affinity, podAntiAffinity, requiredDuringSchedulingIgnoredDuringExecution, a labelSelector matching app parasol-claims, and topologyKey kubernetes.io/hostname. Finally, see what happens when the scheduler *can't* satisfy the rule.
A claims pod can only land on a node *outside* the batch pool *if that pool is actually tainted* — count the eligible nodes for *your* cluster, then ask for one *more* replica than that, so the extra pod has nowhere to go.
The count of "eligible" nodes depends on whether the batch pool's taint is in effect (exercise 4 checks this properly; here's the short version so the count is right):

[source,sh,role=execute]
----
BTAINT=$(oc get nodes -l workshop.redhat.com/pool=batch -o jsonpath="{.items[0].spec.taints[?(@.key=='workshop.redhat.com/pool')].effect}")
if [ "$BTAINT" = "NoSchedule" ]; then
  ELIGIBLE=$(oc get nodes -l 'workshop.redhat.com/pool!=batch' --no-headers | wc -l)
  echo "eligible nodes: $ELIGIBLE (batch pool is tainted, so it's excluded)"
else
  ELIGIBLE=$(oc get nodes --no-headers | wc -l)
  echo "eligible nodes: $ELIGIBLE (batch pool is NOT tainted on this cluster, so it's schedulable too and counts)"
fi
oc scale deploy/parasol-claims -n $NS --replicas=$((ELIGIBLE + 1))
sleep 12
oc get pods -n $NS -l app=parasol-claims -o wide | grep -E 'NAME|Pending|Running' | head -12
----

== 3. Spread evenly with topology spread constraints
⏱ *~5 min* · even distribution across a domain — nodes, and (the knob) zones

Anti-affinity says "never two on a node." `topologySpreadConstraints` says the stronger thing — "keep them *evenly* spread across a domain."

[IMPORTANT]
.`ScheduleAnyway` is a preference, not a guarantee — this is why the layout above can skew
====
That output is a genuine capture, not a mistake: measured twice on a live cluster, this same patch settled as `a:1 b:2 c:0` — one zone holding two replicas, another holding none — even with `maxSkew: 1` set.

Here's why.
`whenUnsatisfiable: ScheduleAnyway` scores each pod placement *once*, at the moment the scheduler admits it, against the zone counts visible *right then* — it never revisits or rebalances a pod once it is running.
During a rolling update the constraint's `labelSelector` (`app: parasol-claims`) matches pods from *both* the outgoing and incoming ReplicaSet, so each new replica gets scored against a zone count that still includes an old pod about to be removed.
By the time the last old pod terminates, the skew that justified each placement no longer describes the pods left standing — and `ScheduleAnyway` has no mechanism to go back and correct it.
That is the whole meaning of "preference": the scheduler tries, does not enforce, and never rebalances after the fact.

If you need the *"one replica per zone"* guarantee this might imply, the field for it is `whenUnsatisfiable: DoNotSchedule` — it turns the identical skew check into a hard admission-time stop: a placement that would push a zone's skew past `maxSkew` is refused outright, so whatever layout the Deployment settles into really is bounded.
The trade-off is real: with `DoNotSchedule`, if the zone that needs the next replica genuinely has no room for it — capacity, a taint, another constraint — that pod goes `Pending` and the *rollout stalls* instead of finishing with a slightly uneven spread.
`ScheduleAnyway` trades the guarantee away specifically so a rollout can never get stuck on it.
You'll test the blocking behavior of `DoNotSchedule` yourself in this module's Challenge, below.
====

[NOTE]
.These zones are synthetic — real ones ride the provider
====
This bare-metal cluster has no real failure zones, so the workshop *synthesized* `workshop.redhat.com/zone={a,b,c}` on the nodes to make the spread visible.
On a cloud cluster you'd point `topologyKey` at the provider's real `topology.kubernetes.io/zone`, and the same constraint would score placement across those zones the same way — reducing, but (per the IMPORTANT box above) not *guaranteeing*, the chance a single zone outage takes out more than one replica.
The `kubernetes.io/hostname` spread, by contrast, is *always* true — every node carries that label on every cluster — so put the topology key back to hostname for the rest of the lab:

== 5. Make the rollout zero-downtime

*Step 2 — harden the roll (pin the capacity floor, and speed the cold-start).*
`maxSurge: 1`/`maxUnavailable: 0` brings a new pod up *before* retiring an old one, and raising the container's CPU *limit* gives the JVM cold-start more headroom to burn — so a fresh pod reaches `Ready` in about *15 s* instead of ~27 s.

[IMPORTANT]
.The default is a *percentage* — it protects you at three replicas and quietly stops at four
====
You did not lose capacity in the probe above, and that is not luck.
The `RollingUpdate` default is `maxSurge: 25%` / `maxUnavailable: 25%`, and Kubernetes resolves those against your replica count — rounding *surge up* and *unavailable down*.
At *3* replicas that is `25% of 3 = 0.75` → surge *1*, unavailable *0*: numerically identical to what you are about to set by hand.
At *4* it is `25% of 4 = 1` → unavailable *1*, and the floor drops.
Measured on this cluster (2026-07-29, same deployment, default strategy, sampled every 3–4 s through a full roll): at three replicas *18 of 18* samples read `3/3`; at four replicas *16 of 16* read `3/4`.
So the point of setting it explicitly is not to fix today's roll — it is to make the floor *independent of how many replicas you happen to be running*, so scaling up never silently re-introduces a dip.
====

[IMPORTANT]
.Use a *strategic* patch for the container change
====
The *resources* edit reaches inside a named container, and `--type=merge` (JSON merge) *replaces* the whole `containers` list — dropping the image and failing with `spec.containers[0].image: Required value`.
`--type=strategic` understands the container `name` as a merge key, so it edits *into* the existing container.
Reach for strategic merge (or an `oc set resources`/`oc set env` helper, which do it for you) whenever you patch a single field inside a named list element.
====

.Why a drop or two survives — and why this is still the win
====
`maxUnavailable: 0` guarantees *capacity*, not that every in-flight request lands.
When a pod is retired, its removal from the Service's endpoints propagates through the network layer asynchronously, so for a fraction of a second a request can still be routed to a pod that is already shutting down.
Four measured runs on this cluster: *1* and *3* drops out of ~285 with the reseed removed, *3* and *4* with the reseed still in place — against ~*15* before any of this exercise's changes.
Read the shape, not the digit: the cause you removed was structural (every new pod re-seeded the shared database on boot), and what is left is the ordinary, bounded cost of retiring a pod.
