=== Brief

image::deployment-targets-scheduling/deployment-targets-scheduling-01-scheduler-pipeline.svg["The scheduler pipeline: a Pending pod carrying its CPU and memory requests, tolerations and selectors enters kube-scheduler, which first filters to the nodes that can run it — enough free requests, taints tolerated, nodeSelector and affinity matched — then scores the survivors on free room, spread and anti-affinity and binds the winner; a dotted branch leaves the filter for the case where no node survives, ending in the pod staying Pending with a FailedScheduling event."]

*Nothing chose these nodes*

Parasol's claims API, its database and a monthly-statement batch job all landed wherever the scheduler found room. The batch job takes CPU from live traffic, replicas of the API can sit on one node together, and every mid-day rollout quietly drops requests. None of that needs a bigger cluster to fix — it needs the placement decisions to be made deliberately.

*The scheduler in one mental model, and who seeks versus who repels*

Every pod goes through the same two steps: *filter* to the nodes that can run it, *score* the survivors, bind the winner. The currency in the filter is the pod's *requests*, not its usage. When no node survives, the pod stays `Pending` and the scheduler writes a `FailedScheduling` event naming the reason node by node.

The two ways to influence that are opposites, and confusing them is the most common scheduling mistake there is. *Affinity is the pod reaching toward a node* — `nodeSelector` and `nodeAffinity` attract, `podAntiAffinity` keeps replicas apart. *A taint is the node pushing pods away*, and a matching *toleration* only permits — it never attracts. Reserving a pool for batch, GPU or licensed workloads therefore takes all three: the label, the selector, and the toleration.

*Two different enemies of a zero-downtime rollout*

The first is a capacity dip while pods are replaced, and `maxUnavailable: 0` closes it: a new pod must pass readiness before an old one is retired. The second is invisible to that setting — an application that rebuilds shared state every time it boots. OpenShift keeps the pod count honest; the fix for the second one is to stop doing deploy-time work in the startup path.

*In this demo*

. A batch worker sent to its dedicated pool by a node selector, and refused by the node's taint
. The toleration that permits it, and the pod landing on the pool
. A redeploy under live traffic that holds capacity flat and stops discarding data on every boot
. A disruption budget that makes a node drain wait its turn

=== 1 · A selector sends the pod; the node refuses it — 3 min

Parasol's monthly-statement batch job is running on the same nodes as the live claims API, competing with it for CPU. The cluster has a pool of nodes set aside for batch work, and a `nodeSelector` is the obvious way to move the job onto it — one patch, and the pod does not start.

image::deployment-targets-scheduling/deployment-targets-scheduling-03-batch-pending.png["The web console pod detail page for a statement-batch pod in the user's dev project, with a Pending badge beside the name and the Events tab active. Two identical scheduler events, both generated from default-scheduler, read: 0/6 nodes are available: 1 node(s) had untolerated taint(s), 5 node(s) didn't match Pod's node affinity/selector — the one node the selector targets repels the pod, and the other five were never candidates."]

*Why it matters*

A node bought for one purpose — a GPU box, a node licensed for a commercial database, a batch pool — only earns its premium if the workload it was bought for lands on it and nothing else does. When that goes wrong the pod simply never starts, and the scheduler's own event is where the answer is: it gives a reason for every node in the cluster, which settles almost every "why will this not schedule".

[source,sh,role=execute,subs="attributes+"]
----
NS={user}-dev
oc get pods -n $NS -l app=statement-batch -o wide
oc get nodes -l workshop.redhat.com/pool=batch
# nodeSelector ALONE — the pod is attracted but not permitted (the taint blocks it)
oc patch deploy statement-batch -n $NS --type=merge -p '{"spec":{"template":{"spec":{"nodeSelector":{"workshop.redhat.com/pool":"batch"}}}}}'
sleep 10
oc get pods -n $NS -l app=statement-batch
oc get events -n $NS --field-selector reason=FailedScheduling | tail -1
----

*What just happened*

`untolerated taint` — the selector sent the pod at the batch node, and the node pushed it back. A selector attracts; it does not permit.

=== 2 · One toleration, and it lands — 2 min

The pod is being sent to the right node and refused by it. A toleration is the pod's permission to be there, and with the selector still in place the pod schedules onto the batch pool within seconds.

image::deployment-targets-scheduling/deployment-targets-scheduling-02-seek-vs-repel.svg["Two contrasted rows. In the upper row, affinity: a pod carrying a nodeSelector or nodeAffinity rule pulls toward a node with the matching label. In the lower row, a taint: the node pushes away a pod with no toleration, while a pod that carries the matching toleration is permitted onto it — permitted, the label notes, but not attracted."]

*Why it matters*

Affinity and taints are often described as two ways of doing the same thing. They are opposites, and both are needed here: the selector chooses the node, the toleration gets the pod past the node's guard. The mirror-image mistake is a toleration with no selector — the pod is then allowed on the premium node and just as likely to land anywhere else.

[source,sh,role=execute,subs="attributes+"]
----
NS={user}-dev
oc patch deploy statement-batch -n $NS --type=merge -p '{"spec":{"template":{"spec":{"tolerations":[{"key":"workshop.redhat.com/pool","operator":"Equal","value":"batch","effect":"NoSchedule"}]}}}}'
oc rollout status deploy/statement-batch -n $NS --timeout=60s
oc get pods -n $NS -l app=statement-batch -o wide
----

*What just happened*

The batch worker is on its own nodes. A statement run no longer takes CPU from the live claims API, and nothing without explicit permission can drift onto the pool that was set aside for it. The listing may still show the old pod as `Terminating` on its previous node for up to 30 seconds; the `Running` pod on the batch node is the new one.

=== 3 · A redeploy under live traffic that keeps its data — 3 min

The claims API is redeployed in the middle of the day, with the load generator still driving traffic at it. Two things have to hold: the number of ready pods never dips, and a claim filed before the rollout is still there after it.

image::deployment-targets-scheduling/deployment-targets-scheduling-04-reseed-on-boot.svg["A rolling update over one shared database: a client files a claim, the old pod that is still serving commits the insert into the single PostgreSQL, and the new pod booting alongside it runs Hibernate drop-and-create against that same database, dropping and reseeding the schema — the newly filed claim is discarded with no error returned to the client."]

*Why it matters*

"The deploy dropped requests again" is usually blamed on shutdown, and here that would be the wrong place to look. Every new pod boots with Hibernate set to drop-and-create and reseeds the *shared* database, discarding rows the pods still serving wrote minutes earlier — with no error, because the reseed commits cleanly. `maxUnavailable: 0` guarantees capacity and cannot see this at all. Setting the schema strategy to `none` moves seeding to deploy time, where it belongs, and a higher CPU limit shortens the JVM cold start each new pod makes the rollout wait for.

[source,sh,role=execute,subs="attributes+"]
----
NS={user}-dev
oc set env deployment/parasol-claims QUARKUS_HIBERNATE_ORM_SCHEMA_MANAGEMENT_STRATEGY=none -n $NS
oc patch deploy parasol-claims -n $NS --type=strategic -p '{"spec":{"strategy":{"type":"RollingUpdate","rollingUpdate":{"maxSurge":1,"maxUnavailable":0}},"template":{"spec":{"containers":[{"name":"parasol-claims","resources":{"requests":{"cpu":"200m","memory":"256Mi"},"limits":{"cpu":"1","memory":"512Mi"}}}]}}}}'
oc rollout status deploy/parasol-claims -n $NS --timeout=180s
for i in $(seq 1 45); do [ "$(oc get pods -n $NS -l app=parasol-claims -o name | wc -l)" -eq 2 ] && break; sleep 2; done
# plant a claim state the seed doesn't carry, then redeploy under live traffic
oc exec deploy/claims-load -n $NS -- curl -s -X PUT http://parasol-claims:8080/api/claims/CLM-1001/status -H 'Content-Type: application/json' -d '{"status":"Approved"}' -o /dev/null -w 'planted: HTTP %\{http_code}\n'
oc rollout restart deploy/parasol-claims -n $NS
for i in $(seq 1 10); do oc get deploy parasol-claims -n $NS -o jsonpath='available={.status.availableReplicas}/{.spec.replicas}{"\n"}'; sleep 4; done
oc rollout status deploy/parasol-claims -n $NS --timeout=180s
for i in $(seq 1 45); do [ "$(oc get pods -n $NS -l app=parasol-claims -o name | wc -l)" -eq 2 ] && break; sleep 2; done
oc exec deploy/claims-load -n $NS -- curl -s http://parasol-claims:8080/api/claims/CLM-1001 | grep -o '"status":"[^"]*"'
----

*What just happened*

`available=2/2` the whole way through — the floor never dips below the desired count — and `CLM-1001` is still `Approved` after the roll, because a booting pod no longer rebuilds the database underneath the pods that are serving.

=== 4 · A disruption budget makes a drain wait — 2 min

Nodes get drained for patching and upgrades, and a drain evicts whatever it finds. A PodDisruptionBudget puts a floor under that: the eviction API checks the budget first, and refuses the eviction that would breach it.

image::deployment-targets-scheduling/deployment-targets-scheduling-04-pdb-allowed-disruptions.png["The PodDisruptionBudgets list for the project with a single row, parasol-claims: selector app=parasol-claims, availability Min available 1, and Allowed disruptions reading 2 — three healthy replicas minus the one the budget insists on keeping."]

*Why it matters*

Hardware failures cannot be budgeted. Voluntary disruptions can, and they are most of what actually takes a service down during a maintenance window. The budget does not stop the drain; it makes it wait its turn and take pods one at a time. The one trap is setting `minAvailable` equal to the replica count, which leaves no eviction room at all and deadlocks the drain forever.

// attributes+ APPENDS: plain subs="attributes" drops HTML escaping, and the browser swallowed <none> as a tag.
[source,sh,role=execute,subs="attributes+"]
----
NS={user}-dev
oc apply -n $NS -f - <<'EOF'
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: {name: parasol-claims}
spec: {minAvailable: 1, selector: {matchLabels: {app: parasol-claims}}}
EOF
oc wait pdb/parasol-claims -n $NS --for=jsonpath='{.status.disruptionsAllowed}'=1 --timeout=60s
oc get pdb parasol-claims -n $NS
# budget has headroom — this eviction is ALLOWED (oldest pod not already shutting down)
POD=$(oc get pods -n $NS -l app=parasol-claims --sort-by=.metadata.creationTimestamp -o custom-columns=NAME:.metadata.name,DELETING:.metadata.deletionTimestamp --no-headers | awk '$2=="<none>" {print $1; exit}')
echo '{"apiVersion":"policy/v1","kind":"Eviction","metadata":{"name":"'"$POD"'"}}' | oc create --raw /api/v1/namespaces/$NS/pods/$POD/eviction -f - && echo
sleep 8
# now exhaust the budget — the next eviction is DENIED
oc patch pdb parasol-claims -n $NS --type=merge -p '{"spec":{"minAvailable":3}}'
sleep 3
POD=$(oc get pods -n $NS -l app=parasol-claims --sort-by=.metadata.creationTimestamp -o custom-columns=NAME:.metadata.name,DELETING:.metadata.deletionTimestamp --no-headers | awk '$2=="<none>" {print $1; exit}')
echo '{"apiVersion":"policy/v1","kind":"Eviction","metadata":{"name":"'"$POD"'"}}' | oc create --raw /api/v1/namespaces/$NS/pods/$POD/eviction -f - || true
oc patch pdb parasol-claims -n $NS --type=merge -p '{"spec":{"minAvailable":1}}'
----

*What just happened*

The first eviction is allowed, because the budget has headroom. Once the budget is exhausted the API answers `Cannot evict pod as it would violate the pod's disruption budget` — a node patch waiting politely instead of taking the service down with it.

== Frequently asked questions

*A pod is stuck in `Pending`. How do we find out why?*::
Read the scheduler's own event: `oc get events -n <namespace> --field-selector reason=FailedScheduling`. It gives a reason per node — `untolerated taint(s)`, `didn't match Pod's node affinity/selector`, `didn't match pod anti-affinity rules`, `Insufficient cpu/memory` — and the counts add up to the whole cluster, so the line says both what is wrong and how widely.

*We added a `nodeSelector` for our GPU pool and the pod will not schedule. What is missing?*::
The toleration. Those nodes are tainted so that ordinary workloads stay off them, and a selector carries no permission: it attracts, the toleration permits. Pinning to a dedicated pool needs the pair. A toleration on its own is the inverse mistake — the pod may use the premium node but has no reason to prefer it.

*Why does our rollout still drop requests when `maxUnavailable: 0` is set?*::
Because that setting guarantees capacity — the count of ready pods never dips — and the loss is usually in the data plane at pod *startup*, not the connection plane at shutdown. An application that reseeds a schema, rebuilds a cache or runs a migration on every boot damages state the pods still serving are using. Move that work to deploy time and the class of failure disappears; shutdown-side tuning never addressed it. Some in-flight requests can still be lost as endpoints de-register asynchronously, which is what a `preStop` hook closes next.

*A node drain is hanging and evicting nothing. Is the budget broken?*::
One of two things, both budget-related. Either it is exhausted and the drain is correctly waiting for a pod to become ready elsewhere — the feature working — or `minAvailable` was set equal to the replica count, which leaves zero eviction room and deadlocks the drain permanently. `oc get pdb -n <namespace>` tells them apart: `ALLOWED DISRUPTIONS: 0` with `minAvailable` equal to the replicas is the deadlock.

*With required anti-affinity, our rolling updates crawl. Is that normal?*::
Yes, and it is deliberate. Required `podAntiAffinity` makes the roll sequential: with `maxSurge: 1`, each new pod needs a node holding no other replica, so it waits for one to vacate. The real trap is running as many replicas as there are eligible nodes — the surge pod then has nowhere to go and the rollout wedges. Keep the replica count below the number of nodes the workload may use.

[cols="1,2,2",options="header"]
|===
| | `ScheduleAnyway` (this lab) | `DoNotSchedule`

| A placement past `maxSkew`
| scored lower, still allowed
| refused: the pod stays `Pending`

| After a rolling update
| can settle skewed, never rebalanced
| stays bounded by `maxSkew`

| The risk you take
| an uneven spread
| a stalled rollout when the zone that needs the pod has no room

.`ScheduleAnyway` is a preference, not a guarantee — this is why the layout can skew
[%collapsible]
====
The spread varies from run to run. Some runs settle one replica per zone; others skew, like the sample above (`a:1 b:2 c:0`) — one zone holding two replicas, another none — even with `maxSkew: 1` set. Both are correct behaviour.

Here's why.
`whenUnsatisfiable: ScheduleAnyway` scores each pod placement *once*, at the moment the scheduler admits it, against the zone counts visible *right then* — it never revisits or rebalances a pod once it is running.
During a rolling update the constraint's `labelSelector` (`app: parasol-claims`) matches pods from *both* the outgoing and incoming ReplicaSet, so each new replica gets scored against a zone count that still includes an old pod about to be removed.
By the time the last old pod terminates, the skew that justified each placement no longer describes the pods left standing — and `ScheduleAnyway` has no mechanism to go back and correct it.
That is the whole meaning of "preference": the scheduler tries, does not enforce, and never rebalances after the fact.

If you need the *"one replica per zone"* guarantee this might imply, the field for it is `whenUnsatisfiable: DoNotSchedule` — it turns the identical skew check into a hard admission-time stop: a placement that would push a zone's skew past `maxSkew` is refused outright, so whatever layout the Deployment settles into really is bounded.
The trade-off is real: with `DoNotSchedule`, if the zone that needs the next replica genuinely has no room for it — capacity, a taint, another constraint — that pod goes `Pending` and the *rollout stalls* instead of finishing with a slightly uneven spread.
`ScheduleAnyway` trades the guarantee away specifically so a rollout can never get stuck on it.
You'll test the blocking behavior of `DoNotSchedule` yourself in this module's Challenge, below.
====

*Step 2 — harden the roll (pin the capacity floor, and speed the cold-start).*
`maxSurge: 1`/`maxUnavailable: 0` brings a new pod up *before* retiring an old one. A higher CPU *limit* gives the cold start headroom on a busy node (~27 s to `Ready` became ~15 s; on a quiet one both measured 12–14 s).
The default `25%` already gave `maxUnavailable: 0` at three replicas, but not at four; explicit values hold at *any* count.

.The default is a *percentage* — it protects you at three replicas and quietly stops at four
[%collapsible]
====
[cols="1,1,1,2",options="header"]
|===
| Replicas | `maxSurge: 25%` | `maxUnavailable: 25%` | Measured through a full roll

| 3 | 0.75 → *1* | 0.75 → *0* | 18 of 18 samples `3/3`: no dip
| 4 | 1 → *1* | 1 → *1* | 16 of 16 samples `3/4`: the floor drops
|===

You did not lose capacity in the probe above, and that is not luck.
The `RollingUpdate` default is `maxSurge: 25%` / `maxUnavailable: 25%`, and Kubernetes resolves those against your replica count — rounding *surge up* and *unavailable down*.
At *3* replicas that is `25% of 3 = 0.75` → surge *1*, unavailable *0*: numerically identical to what you are about to set by hand.
At *4* it is `25% of 4 = 1` → unavailable *1*, and the floor drops.
Measured on this cluster (2026-07-29, same deployment, default strategy, sampled every 3–4 s through a full roll): at three replicas *18 of 18* samples read `3/3`; at four replicas *16 of 16* read `3/4`.
So the point of setting it explicitly is not to fix today's roll — it is to make the floor *independent of how many replicas you happen to be running*, so scaling up never silently re-introduces a dip.

⏱ *~7 min* · read the node agents and the batch pool; evict your own pods the way a drain does

*What just happened:* every agent and pool is built from primitives you used:

[cols="2,2,3",options="header"]
|===
| Object | What it does | What you read

| DaemonSet
| one agent pod on every node
| the CNI (`ovnkube-node`), `node-exporter`, `machine-config-daemon`: `DESIRED` equals your node count

| DaemonSet + `nodeSelector`
| an agent on a subset of nodes
| `machine-config-server`: control-plane nodes only, selected by the legacy control-plane role label the platform still sets

| MachineSet
| how many nodes of one shape
| a stub here (bare metal); on a cloud, the replica count a team scales to grow a pool, sized by a *MachineAutoscaler*

| Node label + taint
| makes a pool dedicated
| `pool=batch` is what your `nodeSelector` matched; `NoSchedule` is what your toleration answered
|===

.More on agents and pools
[%collapsible]
====
Before the workshop, the install built your batch pool with two commands: `oc label node <worker> workshop.redhat.com/pool=batch`, then `oc adm taint nodes <worker> workshop.redhat.com/pool=batch:NoSchedule`. Both change a node, so they are cluster-wide and not yours to run.

Drop the `grep` from the DaemonSet block to see every agent that runs on all nodes; some target only a *subset* of nodes using the very `nodeSelector` + `tolerations` you learned.
On a cloud cluster the MachineSet would carry the replica count a platform team scales to grow a pool, with a *MachineAutoscaler* sizing it to demand.
Here it's a stub — the nodes are bare metal — but the *shape* is the same: this is the object platform teams edit to create the batch and GPU pools your workloads pin onto.
====

`oc adm drain <node>` cordons a node, then evicts every pod on it through the *Eviction API*, which checks your budget; refused, the drain retries every 5 seconds.
You can't drain a node, but you can call that API on your own three replicas, as three parallel drains would.

*Predict, then run:* three healthy replicas, `minAvailable: 1`, three evictions. How many succeed?

// Captured live as user2 on OCP 4.22.22, 2026-11-12, at the exercise-5 end state (3 Ready replicas,
// PDB minAvailable 1). The same command also ran from the cockpit terminal's oc 4.21.8 (the server, not
// the client, answered). The success body is a Status with no trailing newline — hence `&& echo`.
[source,sh,role=execute]
----
for POD in $(oc get pods -n $NS -l app=parasol-claims -o jsonpath='{.items[*].metadata.name}'); do
  echo "evict $POD:"
  echo '{"apiVersion":"policy/v1","kind":"Eviction","metadata":{"name":"'"$POD"'"}}' | oc create --raw /api/v1/namespaces/$NS/pods/$POD/eviction -f - && echo
done
oc get pdb parasol-claims -n $NS
----

.Expected output (your pod names differ)
[source,texinfo]

{"kind":"Status","apiVersion":"v1","metadata":{},"status":"Success","code":201}

*What just happened:* two accepted (`201`), the third refused (`429 TooManyRequests`): with two pods leaving, one is left, exactly `minAvailable: 1`.

A drain retries; do the same. The block reads the refused pod's name back (the oldest not already shutting down), so it works in a fresh shell:

[source,sh,role=execute]
----
POD=$(oc get pods -n $NS -l app=parasol-claims --sort-by=.metadata.creationTimestamp -o custom-columns=NAME:.metadata.name,DELETING:.metadata.deletionTimestamp --no-headers | awk '$2=="<none>" {print $1; exit}')
echo "refused pod: ${POD:-NONE — run the first block of this exercise, then the eviction loop above}"
for i in $(seq 1 12); do
  [ -n "$POD" ] || break
  OUT=$(echo '{"apiVersion":"policy/v1","kind":"Eviction","metadata":{"name":"'"$POD"'"}}' | oc create --raw /api/v1/namespaces/$NS/pods/$POD/eviction -f - 2>&1) && { echo "$(date +%T) evicted $POD"; break; }
  echo "$(date +%T) $OUT (retry in 5s)"
  sleep 5
done
oc get pods -n $NS -l app=parasol-claims -o wide
----

.A fourth row, `Terminating` or `Error`?
[%collapsible]
====
A fourth row may show for a few seconds — the pod you just evicted, as `1/1 Terminating` while it shuts down, or as `0/1 Error` once it has stopped:

[source,texinfo]
----
parasol-claims-5ffbccb8b5-twxjz   1/1     Terminating         control-plane-3
parasol-claims-57b86c4d4f-8fzsq   0/1     Error               control-plane-1
----

The eviction sent the JVM a SIGTERM; it stops cleanly but exits with code 143, which Kubernetes reports as `Error`. The row disappears once the deletion completes.
====

*What just happened:* that is a drain, node by node: the budget doesn't block maintenance, it paces it. For a few seconds one pod carried all traffic, so size the floor for load, not `1` by habit.
