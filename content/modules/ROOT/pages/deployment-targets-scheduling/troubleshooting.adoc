== A pod is `Pending` after I added a `nodeSelector` for a pool

Symptom:: You set a `nodeSelector` to target a dedicated pool and the pod won't schedule — it sits `Pending`.
Cause:: The pool node is *tainted*, and a `nodeSelector` only *attracts* — it doesn't grant *permission* to land on a tainted node. The selector sends the pod at the pool node, the taint repels it, and no other node matches the selector.
Fix:: Add the matching *toleration* so the pod is permitted on the tainted node (keep the selector — you need both):
+
[source,sh,role=execute]
----
oc get events -n $NS --field-selector reason=FailedScheduling -o jsonpath='{range .items[*]}{.message}{"\n"}{end}' | tail -1
# "... 1 node(s) had untolerated taint(s), 5 node(s) didn't match Pod's node affinity/selector"
oc patch deploy statement-batch -n $NS --type=merge -p '{"spec":{"template":{"spec":{"tolerations":[{"key":"workshop.redhat.com/pool","operator":"Equal","value":"batch","effect":"NoSchedule"}]}}}}'
oc rollout status deploy/statement-batch -n $NS --timeout=60s
----
+
Selector attracts, toleration permits. A selector alone is exactly this `Pending`.

== The batch pod schedules *somewhere else*, not on the pool

Symptom:: You added a *toleration* for the batch taint, but the pod landed on a general node, not the dedicated pool.
Cause:: The inverse of the previous entry. A toleration only *permits* the tainted node; it doesn't *send* the pod there. Without a `nodeSelector`, the scheduler is free to place the (now taint-tolerant) pod anywhere.
Fix:: Add the `nodeSelector` so the pod is actually *directed* at the pool:
+
[source,sh,role=execute]
----
oc patch deploy statement-batch -n $NS --type=merge -p '{"spec":{"template":{"spec":{"nodeSelector":{"workshop.redhat.com/pool":"batch"}}}}}'
oc get pods -n $NS -l app=statement-batch -o wide     # now on the pool node
----
+
Pinning a workload to a pool always needs the *pair*: toleration (permit) + nodeSelector (attract).

== The selector-alone patch scheduled straight away — and `ws verify` prints a `➖` line for the taint

Symptom:: The `nodeSelector`-without-toleration step was supposed to leave the pod `Pending`, but it scheduled onto the pool node at once — so the first entry on this page never happens to you.
`ws verify {module-id}` then reports the batch-pool taint on a line beginning `➖` rather than ✅ or ❌, and its closing banner still makes the plain green claim — `all … checks passed` — with `(1 not applicable to this cluster)` appended.
Cause:: This cluster has fewer than *three* dedicated worker nodes, and the workshop installer deliberately *withholds* the batch taint below that floor — tainting one of only two workers once starved a platform component for hours.
With no taint there is nothing to repel the pod, so the selector alone is enough and the `Pending` half of the lesson cannot be demonstrated here.
This is the designed behaviour on a small cluster, not a broken pool: the concept page says the lab will tell you honestly which case you are in, and that `➖` line is it telling you.
Fix:: Nothing to fix — and *do not hand-taint the node* to turn the line green, because that recreates the outage the floor exists to prevent.
Confirm which case you are in:
+
[source,sh,role=execute]
----
oc get nodes -l 'node-role.kubernetes.io/worker,!node-role.kubernetes.io/control-plane'
oc get nodes -l workshop.redhat.com/pool=batch -o custom-columns='NODE:.metadata.name,TAINTS:.spec.taints[*].key'
----
+
Read the banner literally, because `➖` and `⚠` are *different* outcomes.
`➖ … not applicable on this cluster (not a failure)` means the condition that check grades genuinely does not exist here — a known, correct result, nothing missing — so the run is *complete*, keeps the plain green claim, and exits `0`.
`⚠ … SKIPPED (not graded)` is the other one: something *could not be evaluated*, and a run carrying one ends `this run did NOT fully verify the lab`.
A run whose only ungraded lines are `➖` graded everything there was to grade.
The `nodeSelector` half of the pool lesson is still checked normally — only the toleration half waits on a third worker joining the cluster.

== A replica is `Pending` after I required anti-affinity

Symptom:: With required `podAntiAffinity` on `kubernetes.io/hostname`, one or more replicas stay `Pending` — usually after scaling up.
Cause:: Required anti-affinity means *no two replicas share a node*, so you can never have more running replicas than eligible nodes. If replicas exceed the eligible-node count (remember the tainted pool node is excluded), the extra pods have nowhere legal to go.
Fix:: Read the event to confirm, then scale within the node budget (or relax to `preferred`):
+
[source,sh,role=execute]
----
oc get events -n $NS --field-selector reason=FailedScheduling -o jsonpath='{range .items[*]}{.message}{"\n"}{end}' | tail -1
# "0/6 nodes are available: 1 node(s) had untolerated taint(s), 5 node(s) didn't match pod anti-affinity rules"
oc scale deploy/parasol-claims -n $NS --replicas=3
----
+
"Didn't match pod anti-affinity rules" on every non-tainted node means "they all already hold one of me." Scale to at most the eligible-node count.

== The rolling update is crawling — or seems stuck

Symptom:: A `parasol-claims` roll takes far longer than a normal Deployment — one replica at a time, with long pauses.
Cause:: This is *expected* with required anti-affinity. With `maxSurge: 1`, the surge pod must find a node that has *no* other claims pod, so it waits for an old pod to vacate before each step — the roll goes serial, not parallel.
Fix:: Nothing to fix if it's progressing — watch it advance:
+
[source,sh,role=execute]
----
oc rollout status deploy/parasol-claims -n $NS --timeout=180s
----
+
It genuinely *wedges* only if replicas equal the eligible-node count (the surge pod can't place at all). Keep replicas below the number of schedulable non-pool nodes so there's always a free node to surge onto.

== `oc patch` fails with `spec.containers[0].image: Required value`

Symptom:: Patching a container field (raising a CPU limit, setting an env var) with `--type=merge` errors: `The Deployment "parasol-claims" is invalid: spec.template.spec.containers[0].image: Required value`.
Cause:: A JSON *merge* patch (`--type=merge`) treats `containers` as a whole-list *replace* — your patch, which named only the container and the new field, wiped the image and everything else.
Fix:: Use a *strategic* merge patch, which understands the container `name` as a merge key and edits *into* the existing container (or an `oc set` helper, which does it for you):
+
[source,sh,role=execute]
----
oc patch deploy parasol-claims -n $NS --type=strategic -p '{"spec":{"template":{"spec":{"containers":[{"name":"parasol-claims","resources":{"requests":{"cpu":"200m","memory":"256Mi"},"limits":{"cpu":"1","memory":"512Mi"}}}]}}}}'
# or the helper that sidesteps the footgun entirely:
oc set resources deploy/parasol-claims -n $NS --limits=cpu=1,memory=512Mi --requests=cpu=200m,memory=256Mi
----
+
Rule of thumb: patching a single field inside a *named list element* (a container, a volume) → `--type=strategic`, not `merge`.

== A node drain hangs, or an eviction is refused

Symptom:: `oc adm drain` won't finish, or an eviction returns `Cannot evict pod as it would violate the pod's disruption budget`.
Cause:: A `PodDisruptionBudget` is doing its job — evicting the pod would drop below `minAvailable`. Either the budget is legitimately exhausted (the drain is *waiting*, which is correct), or `minAvailable` was set *equal to* the replica count, which leaves zero room and *deadlocks* the drain forever.
Fix:: Check the budget math; if `ALLOWED DISRUPTIONS` is `0` because `minAvailable == replicas`, lower it:
+
[source,sh,role=execute]
----
oc get pdb parasol-claims -n $NS
oc get pdb parasol-claims -n $NS -o jsonpath='minAvailable={.spec.minAvailable} healthy={.status.currentHealthy} allowed={.status.disruptionsAllowed}{"\n"}'
oc patch pdb parasol-claims -n $NS --type=merge -p '{"spec":{"minAvailable":1}}'
----
+
`minAvailable` must be *strictly less* than the replica count (`1` of `3`) so a disruption can proceed while the service stays up.

== The rollout never starts — "0 out of N new replicas have been updated"

Symptom:: `oc rollout status` sits at `Waiting for deployment "parasol-claims" rollout to finish: 0 out of 3 new replicas have been updated...` until it times out, and `oc get deploy` still shows the *old* generation. Meanwhile the capacity sampler from exercise 5 prints a reassuring `available=3/3` for the whole window.
Cause:: The new ReplicaSet cannot create its pods — *not one of them*. The usual reason in this lab is the `{user}-dev` `workshop-quota`, which caps `limits.cpu` at *8*: the namespace's other workloads hold *1300m*, so three claims replicas plus the `maxSurge: 1` pod fit at `limits.cpu: 1` (*5300m*) and are refused outright at `4`, where the very first surge pod would take the namespace to *8300m*. The second reason is scheduling — no node has room for the surge pod. `maxUnavailable: 0` keeps the *old* pods serving throughout, which is why the capacity number stays flat and *proves nothing about the roll*.
Fix:: Read the ReplicaSet, which names the cause exactly, then bring the request back inside the cap:
+
[source,sh,role=execute]
----
NEWRS=$(oc get rs -n $NS -l app=parasol-claims --sort-by=.metadata.creationTimestamp -o jsonpath='{.items[-1].metadata.name}')
oc describe rs $NEWRS -n $NS | sed -n '/Conditions/,$p'
oc describe quota workshop-quota -n $NS
----
+
.A quota refusal looks like this
[source,texinfo]
----
Conditions:
  Type             Status  Reason
  ----             ------  ------
  ReplicaFailure   True    FailedCreate
Events:
  Type     Reason        Age   From                   Message
  ----     ------        ----  ----                   -------
  Warning  FailedCreate  86s   replicaset-controller  Error creating: pods "parasol-claims-b49959c69-qcsr6" is forbidden: exceeded quota: workshop-quota, requested: limits.cpu=4, used: limits.cpu=4300m, limited: limits.cpu=8
----
+
`ReplicaFailure=True` with `FailedCreate` and `exceeded quota` means *no pod object was ever created* — this is an admission refusal, not a slow rollout. Lower the container's `limits.cpu` back to `1` (`oc set resources deploy/parasol-claims -n $NS --limits=cpu=1,memory=512Mi --requests=cpu=200m,memory=256Mi`) and the roll proceeds. Do *not* raise the quota: it is a shared workshop-wide object, and every other module's resource lesson depends on it.
+
If instead the ReplicaSet has *no* `ReplicaFailure` and the new pod exists but sits `Pending`, the pod was admitted and the problem is *placement*, not quota — read `oc get events -n $NS --field-selector reason=FailedScheduling` and expect `Insufficient cpu`/`Insufficient memory`. That is a cluster-headroom problem for whoever provisioned the cluster, not something to fix from inside the namespace.
+
Either way, the lesson for the sampler is the same: `available=N/N` tells you the *floor held*, never that the roll *landed*. Confirm with `oc rollout status` before you believe it.

== The rollout gets *partway* and stops — some pods on the new limit, some on the old

Symptom:: `oc rollout status` sits at `2 out of 3 new replicas have been updated...` and times out, and `oc get pods` shows a *mixture*: two pods carrying your new CPU limit and one still on the old one. The ReplicaSet has `ReplicaFailure=True`, but the event says `used` is *higher* than the number in the `describe quota` you read before you started.
Cause:: The same quota ceiling as above, hit *mid-roll* rather than at the first pod. A surge roll admits its new pods one at a time, retiring an old pod between each, so the namespace total walks upward as it goes: at `limits.cpu: 2` from a `4300m` baseline it goes `6300m` (first new pod in), `5300m` (first old pod out), `7300m` (second new pod in), `6300m` (second old pod out) — and the third new pod would need `8300m`, which the `8` cap refuses. The roll is stuck holding two generations at once.
Fix:: Read the `used` figure out of the *event*, not out of your earlier `describe quota` — mid-roll it is the only number that describes the moment the refusal happened:
+
[source,sh,role=execute]
----
NEWRS=$(oc get rs -n $NS -l app=parasol-claims --sort-by=.metadata.creationTimestamp -o jsonpath='{.items[-1].metadata.name}')
oc describe rs $NEWRS -n $NS | grep 'exceeded quota' | tail -1
oc get pods -n $NS -l app=parasol-claims -o custom-columns='NAME:.metadata.name,STATUS:.status.phase,CPULIM:.spec.containers[0].resources.limits.cpu'
----
+
.The partial-wedge signature — one `used` value per rung of the walk
[source,texinfo]
----
(combined from similar events): Error creating: pods "parasol-claims-7cd998dfcc-cww5t" is forbidden: exceeded quota: workshop-quota, requested: limits.cpu=2, used: limits.cpu=6300m, limited: limits.cpu=8

NAME                              STATUS    CPULIM
parasol-claims-7cd998dfcc-6546l   Running   2
parasol-claims-7cd998dfcc-c8qsx   Running   2
parasol-claims-846bc8d48f-gp7lv   Running   1
----
+
The fix is the same one — `oc set resources deploy/parasol-claims -n $NS --limits=cpu=1,memory=512Mi --requests=cpu=200m,memory=256Mi` — and it is *safe from here*: lowering the limit shrinks every pod the next roll creates, so the walk fits and the mixed generations converge. Do not "unstick" it by deleting the old pod: that drops you below the floor `maxUnavailable: 0` exists to hold, and the replacement is refused for the same reason.

== A rollout drops requests even with `maxUnavailable: 0`

Symptom:: You set `maxUnavailable: 0`, capacity holds flat at the desired replica count through the roll, and the API *still* returns 5xx/000 during a rollout — often a burst of them, not a stray one or two.
Cause:: The disruption is in the *data plane, at pod startup*, not the connection plane at shutdown. The `parasol-claims` image boots with Hibernate `schema-management.strategy=drop-and-create`, so *every* pod, on *every* boot, drops and reseeds the *shared* `claims-db`. During a rolling update each new pod's boot wipes the tables out from under the old pods still serving — which is why the shutdown-side knobs (`maxUnavailable`, `preStop`, `terminationGracePeriodSeconds`) can never reach zero. The *deterministic* tell: a value written to the database *reverts to its seed* after a single pod restart.
Fix:: Confirm the signature, then stop pods rebuilding shared state on boot (`schema-management=none`; seed the DB once at deploy from a migration Job instead of from every app pod):
+
[source,sh,role=execute]
----
# signature: write a non-seed status, restart ONE pod, watch it revert (CLM-1001 seeds as UnderReview)
oc exec deploy/claims-load -n $NS -- curl -s -X PUT http://parasol-claims:8080/api/claims/CLM-1001/status \
  -H 'Content-Type: application/json' -d '{"status":"Approved"}' -o /dev/null -w 'wrote %{http_code}\n'
oc delete pod -n $NS "$(oc get pods -n $NS -l app=parasol-claims -o jsonpath='{.items[0].metadata.name}')"
sleep 3; oc wait --for=condition=Ready pod -l app=parasol-claims -n $NS --timeout=180s
oc exec deploy/claims-load -n $NS -- curl -s http://parasol-claims:8080/api/claims/CLM-1001 | grep -o '"status":"[^"]*"'
# reverted to "UnderReview" ⇒ the boot-time reseed is the cause. The primary fix:
oc set env deployment/parasol-claims QUARKUS_HIBERNATE_ORM_SCHEMA_MANAGEMENT_STRATEGY=none -n $NS
----
+
After `schema-management=none` the same write *survives* a restart and a re-run of the drop probe falls to single digits (1 and 3 out of ~285, measured 2026-07-29 — not zero: endpoint removal propagates asynchronously, so a request can still reach a pod that is already shutting down). Graceful `SIGTERM` draining (`quarkus.shutdown.timeout`) is a separate concern this image already handles — it was not the fault this exercise diagnoses, though a `preStop` hook is what you would add to chase the residual few.

== The zone-spread step shows empty zones

Symptom:: The `topologySpreadConstraints` zone-knob step runs, but every pod prints `zone=` (empty).
Cause:: The synthetic `workshop.redhat.com/zone` labels aren't on this cluster's nodes. Those are lab topology, added at bootstrap; the *hostname* spread is the always-true story and needs no node labels.
Fix:: Confirm whether the zone labels exist; if not, use the hostname spread (the real lesson) and treat zones as the "on a cloud, point at the provider's zone" narrative:
+
[source,sh,role=execute]
----
oc get nodes -L workshop.redhat.com/zone
oc patch deploy parasol-claims -n $NS --type=merge -p '{"spec":{"template":{"spec":{"topologySpreadConstraints":[{"maxSkew":1,"topologyKey":"kubernetes.io/hostname","whenUnsatisfiable":"ScheduleAnyway","labelSelector":{"matchLabels":{"app":"parasol-claims"}}}]}}}}'
----
+
On a cloud cluster the same constraint on `topology.kubernetes.io/zone` spreads across *real* failure zones.
