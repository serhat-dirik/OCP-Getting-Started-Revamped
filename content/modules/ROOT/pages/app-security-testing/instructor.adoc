== Timing (measured)

*Read this before you schedule the module.* Total hands-on is *~85–105 min*, not one hour. With the
concept and wrap-up, budget *~115–135 min* — a genuine double slot with no slack in it.

The lab is *pipeline-bound*: from Exercise 3 onward, most of each exercise is *waiting for a re-run*,
not doing the work. Nothing is cached between runs, so every re-run pays the full unit-test and image
build again.

Measured per stage on OCP 4.22.6, from *two complete green capstone runs plus one seeded (red)
run* on the same cluster on 2026-07-31 — a record of what this measurement ran on, not a requirement for
yours. Ranges are the observed spread across those runs — treat them as typical, not as guarantees; a
busier cluster or a cold Maven mirror pushes the long stages up.

[cols="3,1,4",options="header"]
|===
| Stage | Time | Notes

| `fetch-source` | ~20 s | git clone of the fork
| `sast-sonar` | ~2.5 min | SonarQube analysis + quality-gate poll; same cost pass or fail
| `sca-trivy` | ~20 s | Trivy filesystem scan
| `unit-test` | *~5.5 min* | Maven test — no dependency cache survives a run, so this is paid *every* time
| `build-image` | *~4 min* | buildah; the second long pole
| `image-scan` / `sign-check` / `image-report` | ~40 s | run in parallel after the build
| `deployment-check` | ~10 s | roxctl deployment check
| `deploy` | ~45 s | applies the manifest, creates the Route
| `dast-zap` | ~2.5 min | ZAP baseline against the running Service
| `perf-k6` | ~40 s | k6 load test
| *A complete run* | *~17–18 min* | measured 17m01s and 17m33s
|===

What that means for pacing — *how long a re-run takes to reach each gate*:

[cols="3,1,4",options="header"]
|===
| Segment | Time | Notes

| Concept (five pillars, shift-left/right, defense-in-depth, reporting) | ~15 min | ≤15-min read; slides carry it
| 1. Meet the seeded app + start the capstone | ~6–8 min | Read five flaws, start the run; it fails at SAST after *~3 min*
| 2. SAST gate — externalize the credential | ~8–10 min | Read SonarQube, fix, commit; the re-run reaches the SCA gate in *~3–4 min*
| 3. SCA gate — drop the vulnerable dep | *~15–18 min* | *The step-change.* This re-run is the first to build: fetch + SAST + SCA + unit-test + build + image-scan = *~13 min of pipeline* before it fails
| 4. Image scan — log4shell + defense-in-depth | *~16–19 min* | The key beat; another full rebuild to reach `deployment-check` (*~13 min*)
| 5. Config check — harden the manifest | *~18–21 min* | Full rebuild *plus* deploy and DAST — *~16.5–17 min* of pipeline before it fails at `dast-zap`
| 6. DAST — add the security headers | *~19–22 min* | The final run goes the whole way: *~17–18 min*
| 7. Read the whole green run — *instructor-led* | ~5–8 min | You drive this one (see below)
| Wrap-up + org mapping | ~15 min | Reporting, break-glass, pin-vs-float discussion
|===

[NOTE]
.How this timing was measured
====
Re-measured 2026-07-31 on cluster 2 as attendee slot `user5`, replacing an earlier table that was wrong by a wide margin (it claimed ~60 min hands-on and a ~7 min Exercise 3, both roughly half of reality).
The numbers above come from *three* real runs, not one: two complete green capstone runs on clean `main` (17m01s and 17m33s wall) and one seeded red run on `seed-appsec` (2m50s to the SAST failure).

Per-stage spread across the two green runs was under ~5%, which is why the *stage* table gives single ~figures while the *exercise* table gives ranges — the exercise numbers add the genuinely variable human reading/fix/commit time on top of the pipeline cost.
Do not replace these with fresh point estimates from a single sample.

The dominant, non-negotiable costs are `unit-test` (~5.5 min) and `build-image` (~4 min), paid on *every* re-run because no dependency cache survives a run — each PipelineRun claims a fresh workspace PVC.
====

*Running this in the time you actually have.* The six re-runs are ~66 min of pipeline on their own and
that floor cannot be negotiated down. Options, in order of preference:

* *Pre-warm.* The concept page now opens with a `ws prep app-security-testing` box, so the environment
  builds while the room reads it — there is nothing to ask for at the top of the lab any more, and the
  lab page only *confirms* it. Bank that: send them to the concept page first, then have them clone and
  start their first pipeline run *before* you deliver the concept talk. The SAST failure is then waiting
  for them, which removes Exercise 1's wait entirely. Order matters — the fork and the Pipeline come from
  the entry state, so the run has nothing to clone until prep has converged.
* *Teach into the wait.* Exercises 3–6 each leave 13–18 idle minutes. That is where the concept material
  on defense in depth, the org-mapping discussion, and the wrap-up questions belong — not bolted on at
  the end. Do not let the room watch a progress bar.
* *Run the demo flavor instead.* One narrated red-to-green pass, ~15 min of *room* time. If you have a
  single 60-minute slot this is still the honest choice — the hands-on lab does not fit, and compressing
  it means attendees abandon it half-finished. Its *preparation* is not free, though: the arc tours six
  already-finished PipelineRuns, which is a full lab pass beforehand (see *Demo-mode notes*). Stage it
  the day before, not on the morning.

Measured `ws` lifecycle (admin/builder context, OCP 4.22.6, 2026-07-31):

[cols="2,1,3",options="header"]
|===
| Command | Time | What it does

| `ws verify app-security-testing --user <u> --entry-only` | ~15–17 s | 11/11 entry checks
| `ws verify app-security-testing --user <u>` | ~15–18 s | 13/13 (11 entry + 2 end) once a capstone run has Succeeded
| `ws smoke app-security-testing <u>` | ~55 s | 11/11 attendee-cockpit gate (ws-on-PATH, identity, isolation, prep convergence)
| `ws reset app-security-testing --user <u>` | ~2 min | purge `<u>-cicd` + re-materialize entry (Argo sync)
| `ws solve app-security-testing --user <u>` | *~17–19 min* | runs the capstone on clean `main` (every gate passes) — blocks while it runs
|===

`ws smoke` needs the entry state materialized first; if the attendee-`ws prep` convergence check fails,
run `ws reset app-security-testing --user <u>` (or `ws git-refresh --restart-terminals --user <u>` for a
stale cockpit) and re-smoke.

`ws solve` is *slow by design*: it runs the real capstone to completion so the green end state genuinely
exists. It wraps the same ~17–18 min pipeline measured above, so start it *at least 25 minutes* before a
demo — not five.

== Demo-mode notes (beyond Say/Show/Do)

* *Stage the whole ladder before the room — six finished runs, not two.* The demo arc is a *tour of already-finished PipelineRuns*: its five beats point at six different rungs, each stopping one gate later than the one before, so two warm runs do not cover it — beats 2, 3 and 4 each need their own. The prep is therefore *one full pass through this module's own lab* (Exercises 1–6) in the presenter's project, which is the *~66 min of pipeline* floor named in *Running this in the time you actually have* above, inside a *~85–105 min* hands-on pass. Do it days ahead, once: nothing prunes a finished PipelineRun, so all six survive in the project and one staging serves every customer. The lab's demo-flavor prep block carries the same rung-by-rung table, a one-command ladder check, and the fallback below.
* *`ws solve` is the fallback, not the prep.* It creates exactly *one* PipelineRun, on clean `main` — `gitops/entry-states/app-security-testing/templates/solve-endstate.yaml` renders a single PostSync Job with `backoffLimit: 0` precisely so a retry cannot launch a second. It gives you beat 5's green graph and nothing at all for beats 2–4, and it *blocks for ~17–19 min*, so start it *at least 25 minutes* ahead — see Timing. Pair it with one seeded `seed-appsec` run (~3 min, red at `sast-sonar`) for beat 1 and describe the three middle rungs off the green run's stage list rather than pretending to show them.
* *Sign in to RHACS before the room, not during beat 3.* Central has its own login and rejects OpenShift tokens outright (see Watchouts), so it is the one console attendees never see — but *you* need it open and signed in on Violations before beat 3's log4shell reveal, or the beat stalls on a login screen. This warning is also carried in the lab's demo-flavor prep block: it is the one line that saves a demo, and a presenter mid-arc should not have to leave the page they are presenting from to find it.
* *Open all four consoles in a fixed tab order that matches the beats.* Pipelines console (every beat), SonarQube (beat 1), RHACS (beat 3), a terminal in `{user}-cicd` (throughout) — arrange them once so you are never hunting for the right tab mid-sentence.
* *Let beat 5's tour of green land before Q&A.* The close — SonarQube passed, RHACS clean, Tekton Results green, the Route open — is what makes "green now means safe" concrete. Do not rush from it straight into questions.
* *Nothing in the arc runs live, so "the pipeline is slow" is no longer the failure mode — "the console is signed out" is.* The arc closes with a recovery block that prints any gate's finding from any rung's TaskRun log, scoped by `tekton.dev/pipelineRun` and tail-limited. It is the same verdict the console shows and the same path attendees use, so it covers a dead RHACS session, a slow SonarQube, and a missing rung. Rehearse it once so you can reach it without reading.

== Top 5 questions attendees ask

*1. "Trivy found log4shell too, didn't it? Why is the image scan a separate failure?"*

No — and that is the whole defense-in-depth point. In this lab, log4shell is *not* a declared dependency in `pom.xml`; the seeded `Containerfile` bakes the `log4j-core` 2.14.1 jar into the image at build time. Trivy scans the *source tree*, so it has nothing to find — its scan is genuinely clean of log4shell. RHACS scans the *assembled image* and catches it. If you *had* declared log4shell in `pom.xml`, Trivy *would* catch it at the SCA stage — try it and see. The lesson is that *where* you scan decides *what* you can catch.

*2. "Why a custom SonarQube quality gate instead of the default?"*

SonarQube's built-in "Sonar way" gate is Clean-as-You-Code: every condition is "on *new* code", and a project's *first* analysis has no new-code baseline — so a brand-new per-user project passes even *with* a hard-coded credential. The workshop installs a *Parasol AppSec Gate* keyed on *overall* `vulnerabilities > 0`, which fails on the first scan and passes when the vulnerability is gone. In your own SonarQube you'd typically keep the CAYC gate *and* seed a baseline analysis; we chose the simpler, deterministic gate for a first-run lab.

*3. "The pipeline creates the Route — do I still need `oc expose`?"*

No. The `deploy` stage runs `oc create route edge parasol-claims --insecure-policy=Allow` for you (edge-terminated so it is browser-reachable over HTTPS). Attendees never run `oc expose`; the Route appears automatically after the deploy stage passes.

*4. "Each fix means a full rebuild — can't I skip ahead?"*

The re-runs are sequential by design: each gate must pass before the next runs, so you can't reach the image gate without fixing SAST and SCA first. That is the *point* — security is layered. If time is short, run the demo flavor (one narrated pass) rather than six attendee rebuilds, or split the double slot so the slow re-runs overlap the discussion.

*5. "Is this the same as Trusted Software Supply Chain?"*

Complementary. Trusted Software Supply Chain proves the image is *provably yours*: signed, attested, SBOM-verified, admission-controlled. Application Security Testing proves the image is *free of known flaws*: scanned at five layers. You want *both* — a scanned-clean image that isn't signed could be swapped; a signed image full of CVEs is authentically vulnerable.

== Watchouts

* *SonarQube first-analysis behavior (the #1 gotcha).* If the default gate is "Sonar way", the seeded credential *passes* on a fresh project (no new-code baseline). Verify pre-flight step 5 — the default must be *Parasol AppSec Gate*. This surprised the build itself: the credential fires the S2068 rule (`vulnerabilities=1`) but the CAYC gate reports empty conditions on the first run.
* *Per-user Sonar project keys are mandatory.* Community Build has no branch analysis, so every attendee must scan into `parasol-claims-<user>` (set in the Start form / PipelineRun param). A shared key means user A's fix greens the project while user B still has the credential — confusing everyone. The `ws solve` PipelineRun already sets the per-user key.
* *The cluster-resolver task cache.* The pipeline references tasks by cluster resolver, which caches resolved Tasks briefly. If you *update* a curated task (e.g. `roxctl-deployment-check`), a run started within the cache TTL may still use the old body. Re-run after a minute, or bump nothing mid-session.
* *`git push` prompts once.* The lab's fixes push to the attendee's fork; the first push prompts for their Gitea login. The lab sets `git config --global credential.helper store` so subsequent pushes are silent. If a push errors with "could not read Username", that helper line is the fix (also in Troubleshooting).
* *ZAP gate is `FAIL_ON_WARN=true`.* The pipeline promotes missing-header *warnings* to build failures so the DAST gate bites. That means the *clean* app must set its headers or `ws solve` (clean `main`) would also fail DAST — the hardened `application.properties` on `main` carries them. If you fork the app, keep the headers.
* *Build-bound lab.* Every re-run pays unit-test (~5.5 min) *and* the image build (~4 min) again — no cache survives a run. See the timing section: hands-on is ~85–105 min, not 60. Pre-warm the first run and teach into the waits, or run the demo flavor.

* *Six re-runs, one PVC quota, per attendee.* Every PipelineRun claims a fresh workspace PVC from its `volumeClaimTemplate`, and that PVC lives exactly as long as the run does — nothing in the flow deletes a finished run behind the attendee. The module's fix loop is six sequential re-runs per attendee, and across a full cohort that can walk the room straight into the per-namespace PVC quota. If a run never starts a pod and `oc describe pipelinerun` shows `exceeded quota … persistentvolumeclaims`, have the attendee prune their oldest *finished* runs first (each frees its PVC through the ownerReference) — the ceiling itself is workshop-tunable in `gitops/workshop-config/templates/per-user-limits.yaml` (Troubleshooting entry included).

* *"My fix didn't take" is almost always an unlanded push, not a wrong fix.* When a re-run fails at the *same* gate with the *same* finding, the usual cause is one of three: the commit was never pushed (`git push` never ran), it pushed to `main` instead of `seed-appsec` (the pipeline only ever builds `seed-appsec`), or the re-run started before the push landed. Have the attendee confirm the top commit on `origin/seed-appsec` matches their fix before troubleshooting the gate itself (Troubleshooting entry included).

* *A shrinking `WARN-NEW` count is progress, even while DAST stays red.* `FAIL_ON_WARN=true` means *one* remaining header warning is enough to keep the gate shut, and ZAP's header ruleset is not fixed — it ships with ZAP and can grow, so a header list that was complete when this module was written can miss a rule added later. Read the *name* of the remaining `WARN-NEW` line and set exactly that header; do not assume the lab's list is exhaustive, and do not assume the attendee did something wrong (Troubleshooting entry included).

* *You drive Exercise 7, and it needs your RHACS login.* Exercise 7 is an *instructor-led walkthrough*, not a hands-on exercise. Have the four surfaces open before you start it: SonarQube (`parasol-claims-<user>`, passed), the Pipelines console on a green run, the *RHACS console* on Violations, and an attendee's PipelineRun list. Only the RHACS tab needs a login attendees do not have — see the next watchout.

* *Attendees cannot sign in to RHACS Central, by design of the product, not an oversight in the setup.* Central keeps its own user database; its sign-in page offers only a username-and-password form, and it *rejects OpenShift bearer tokens outright* (verified: presenting even a cluster-admin OpenShift token to Central returns "token validation failed"). The `advanced-cluster-security` OpenShift console plugin is not a workaround — it proxies the same OpenShift token to the same Central. So *every* RHACS screen in this module is yours to show. The lab says so plainly and routes attendees to the `image-scan` / `deployment-check` TaskRun logs, which carry the identical verdict. If an attendee asks to see the console, show it on the shared display; do not hand out Central credentials.

* *The ZAP, k6 and SBOM report files are not retrievable, and the lab no longer pretends otherwise.* Each is written into a pipeline workspace — a scratch volume on the stage's own pod — and once the stage finishes there is no running container to copy it out of (`oc exec` into a completed pod is refused, PVC-backed or `emptyDir`, attendee or admin). Expect the question; the honest answer is that publishing artifacts durably is a real platform decision this teaching pipeline deliberately skips, and it is raised as an org-mapping prompt in the wrap-up. Do not improvise a `oc debug` workaround in front of the room — it will not work for the `emptyDir` workspaces at all.

* *Tekton Results is present and attendees can read it — do not tell them otherwise.* The `tekton-results-api`, `-watcher` and `-postgres` pods run on this cluster and archive every PipelineRun, including the failed ones, so the red-to-green history genuinely persists. Attendee identities are authorized for their own namespace (verified: an attendee identity reads its own namespace's results and is denied another attendee's). One caveat still worth knowing: the API runs with `LOGS_API=false`, so run *metadata* is archived but TaskRun *logs* are not — report that to the platform owner rather than working around it. The `tekton-results-api` Route itself is fixed (reencrypt termination) on clusters where the workshop installed Pipelines — verify with `oc get route tekton-results-api -n openshift-pipelines -o jsonpath='{.spec.tls.termination}'` before relying on the public URL in front of the room; on a cluster that already had Pipelines installed before the workshop arrived (adopted, not ours), that config may not have applied, so check first and fall back to the OpenShift console's own service proxy, which always works regardless.
