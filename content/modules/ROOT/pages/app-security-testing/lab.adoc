You are a Parasol platform engineer, and the `parasol-claims` build is *green* — it compiles, its tests pass, it deploys.
It is also *insecure*: a colleague's `seed-appsec` branch has shipped five security regressions, and the old pipeline waved every one of them through.
Your job is to run the *DevSecOps capstone* — an eleven-stage pipeline with a security gate at every layer — and drive it from *red to green*, fixing each finding *and reading it in its own console* along the way.

[TIP]
.How this lab is driven — console for the pipeline, terminal for the fixes
=====
You *start the pipeline* from the *OpenShift Pipelines console* (a real button, with a `tkn`/`oc` alternative beside it). You *read each finding* in its native console — the *SonarQube dashboard*, the *TaskRun logs* — with a command-line alternative every time. And you *fix* each finding with a *real commit* to your `seed-appsec` branch from the terminal. Five gates, five fixes, one green run.

One console is the exception: *RHACS Central* has its own user database and the workshop does not issue
you an account there, so the RHACS screens are *shown by your instructor*. Everything RHACS finds is in
your `image-scan` and `deployment-check` TaskRun logs, which you read yourself.
=====

[IMPORTANT]
.This lab is build-bound — budget ~85–105 minutes of hands-on time
====
Every fix means a *re-run*, and every re-run rebuilds the application from scratch: the unit-test stage
and the image build together account for roughly *nine of the seventeen minutes* a full run takes, and
nothing is cached between runs. The later exercises are therefore *dominated by waiting for the
pipeline*, not by the work you do — the fix itself is usually one command block. Each exercise's timing
chip below is a *measured range* covering both the reading and the re-run.

Use the wait. While a run is in flight, read the next section, or open the previous gate's report in its
console. Do not sit and watch the progress bar.
====

The finding is exact: a password *compiled into the source*. The fix is the one Config, Secrets & Multi-Environment teaches — *externalize it to configuration*, so the value comes from a Secret or environment variable, never a literal. Apply the fix and commit it to `seed-appsec`:

[source,sh,role=execute]
----
cd ~/parasol-claims
cat > src/main/java/com/parasol/claims/PartnerGateway.java <<'EOF'
package com.parasol.claims;

import org.eclipse.microprofile.config.inject.ConfigProperty;
import jakarta.enterprise.context.ApplicationScoped;

/** The partner API credential is read from configuration (a Secret / env var in production),
 *  never hard-coded — the config-externalization pattern from the Config, Secrets & Multi-Environment module. */
@ApplicationScoped
public class PartnerGateway {

    @ConfigProperty(name = "partner.api.password", defaultValue = "")
    String partnerApiPassword;

    private final String partnerEndpoint = "https://partners.example.com/claims";

    public String endpoint() { return partnerEndpoint; }
    public String credential() { return partnerApiPassword; }
}
EOF
git commit -am "fix(SAST): externalize the partner API credential (@ConfigProperty)"
git push origin seed-appsec
----

== 3. Gate 2 — SCA: the vulnerable dependency
⏱ *~15–18 min* · read the Trivy finding, drop the dependency, re-run — *this is the long one*

SCA (Software Composition Analysis) checks the *dependencies you pulled in*. Read the Trivy finding from the TaskRun log:

[source,sh,role=execute]
----
oc get taskrun -n $NS -l tekton.dev/pipelineTask=sca-trivy --sort-by=.metadata.creationTimestamp \
  -o name | tail -1 | cut -d/ -f2 | xargs -I{} tkn taskrun logs -n $NS {} | grep -iE "commons-collections|CVE-2015|CRITICAL|HIGH|SCA scan FAILED"
----

.Expected output (Trivy flags a critical RCE in a transitive-era library)
[source,texinfo]
----
Total: 2 (HIGH: 1, CRITICAL: 1)
│ commons-collections:commons-collections │ CVE-2015-7501 │ CRITICAL │ ... 3.2.1 → 3.2.2 │ InvokerTransformer ...
│                                         │ CVE-2015-6420 │ HIGH     │ ...               │ Insecure Deserialization ...
❌ SCA scan FAILED — a HIGH,CRITICAL dependency CVE was found.
----

`commons-collections` 3.2.1 carries *CVE-2015-7501* — the infamous *InvokerTransformer* deserialization *RCE* (Remote Code Execution) gadget. Your code never calls it; it's a landmine you inherited by declaring the dependency. The fix is to *remove it*. Trivy also wrote a *CycloneDX SBOM* (`trivy-sbom.json`) into the run's workspace — the full bill of materials for the build. Drop the dependency and commit:

[source,sh,role=execute]
----
cd ~/parasol-claims
# remove the seeded commons-collections block from pom.xml
awk '/app-security-testing SCA seed/{skip=1} skip&&/<\/dependency>/{skip=0;next} skip{next} {print}' pom.xml > pom.xml.new && mv pom.xml.new pom.xml
grep -q commons-collections pom.xml && echo "STILL PRESENT" || echo "commons-collections removed"
git commit -am "fix(SCA): remove vulnerable commons-collections 3.2.1 (CVE-2015-7501)"
git push origin seed-appsec
----

*Re-run* the pipeline. SCA is now clean, the build proceeds — and fails at the *next* gate, `image-scan`.

== 6. Gate 5 — DAST: the missing security headers
⏱ *~19–22 min* · read the ZAP finding, add the headers, and watch the whole run go green (a complete run is ~17–18 min)

DAST (Dynamic Application Security Testing) exercises the *running* app — something you can only do *after* deploy. The `zap-baseline` stage ran a ZAP (Zed Attack Proxy) scan against the live service and found it never sets its HTTP security headers, so a browser is free to MIME-sniff it, frame it, and leak its URLs. Read the finding:

[source,sh,role=execute]
----
oc get taskrun -n $NS -l tekton.dev/pipelineTask=dast-zap --sort-by=.metadata.creationTimestamp \
  -o name | tail -1 | cut -d/ -f2 | xargs -I{} tkn taskrun logs -n $NS {} | grep -iE "WARN-NEW|FAIL-NEW|DAST FAILED"
----

.Expected output (ZAP flags missing headers on the RUNNING app — a check only possible post-deploy. Unlike the CVEs in the earlier gates, *which rules fire and the exact counts move with ZAP's shipped ruleset* — read the rule names in your own output, not these)
[source,texinfo]
----
WARN-NEW: Content Security Policy (CSP) Header Not Set [10038] x 3
WARN-NEW: Permissions Policy Header Not Set [10063] x 3
WARN-NEW: X-Content-Type-Options Header Missing [10021] x 3
WARN-NEW: Cross-Origin-Resource-Policy Header Missing or Invalid [90004] x 1
FAIL-NEW: 0   WARN-NEW: 4   INFO: 0   IGNORE: 0   PASS: 62
❌ DAST FAILED — ZAP reported a gating alert on the running app.
----

The `dast-zap` stage runs with `FAIL_ON_WARN=true`, so *warnings* fail the build — and because it is `FAIL_ON_WARN`, **a single remaining warning keeps the gate shut**, no matter how many you have cleared. Every one of these is a missing HTTP response header. The fix is to *set them* in Quarkus configuration — one line per header, applied to every response. Append them to `application.properties` and commit:

// media-pass: screenshot app-security-testing-06-zap-baseline-summary.png — the dast-zap TaskRun
// ZAP baseline WARN/FAIL summary against the running Route: the missing security headers
// (Content-Security-Policy, X-Content-Type-Options, anti-clickjacking). Notice DAST only sees this
// once the app is deployed and answering requests. See media-manifest.md.

[source,sh,role=execute]
----
cd ~/parasol-claims
cat >> src/main/resources/application.properties <<'EOF'

# HTTP security response headers (app-security-testing DAST fix)
quarkus.http.header."X-Content-Type-Options".value=nosniff
quarkus.http.header."Content-Security-Policy".value=default-src 'self'; frame-ancestors 'none'
quarkus.http.header."X-Frame-Options".value=DENY
quarkus.http.header."Referrer-Policy".value=no-referrer
quarkus.http.header."Permissions-Policy".value=geolocation=(), camera=(), microphone=()
quarkus.http.header."Strict-Transport-Security".value=max-age=31536000; includeSubDomains
quarkus.http.header."Cache-Control".value=no-store
quarkus.http.header."Cross-Origin-Resource-Policy".value=same-origin
EOF
git commit -am "fix(DAST): add HTTP security response headers"
git push origin seed-appsec
----

TIP: That last push is the one that prompts. Enter your Gitea username (`{user}`) and the workshop password when git asks — `credential.helper store` from exercise 1 means it only asks once.

*Re-run one final time.* The rebuilt app sets its headers, ZAP finds nothing to warn about, and — for the first time — *every gate is green*: SAST, SCA, unit test, build, image scan, sign, config check, deploy, DAST. The scanned, signed image is deployed with its Route.

The graph doesn't stop at `dast-zap`, though: one more stage runs after it, `perf-k6`.
It isn't a security check — it's a *performance* gate, a short k6 load test (10 virtual users for 30 seconds) against the same running Service, exercising `/api/claims` and the health endpoint and failing the build if p95 latency exceeds 800ms or the error rate exceeds 1%.
It sits alongside the security gates because the same discipline applies to speed as to safety: a change can pass every security check and still make the app too slow or too flaky under load, and this gate catches that before it ships.
The seeded app has no performance regression, so `perf-k6` passes without a fix — watch for it going green after `dast-zap`, and read the p95 and error-rate numbers in its *TaskRun log*, which is where the summary is printed.

[NOTE]
.Where the HTML reports go — and why you read the logs instead
====
The ZAP and k6 stages each write a self-contained *HTML report*, and the SCA stage writes a *CycloneDX
SBOM*, into their pipeline *workspaces*. Those workspaces live and die with the run: they are scratch
volumes attached to the stage's pod, and once a stage finishes, its pod has *stopped* — there is no
running container left to copy a file out of. Treat the reports as artifacts a *real* pipeline would
publish somewhere durable (an artifact repository, an S3 bucket, a Tekton Results log store) and that
this teaching pipeline deliberately does not.

Everything the gates decide on is printed in the *TaskRun logs*, which persist for the life of the
PipelineRun and are what you read throughout this lab. Publishing the reports durably is a good exercise
for your own platform — see the wrap-up.
