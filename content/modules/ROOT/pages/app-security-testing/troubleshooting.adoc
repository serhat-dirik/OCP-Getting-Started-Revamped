// Troubleshooting for Application Security Testing. Every entry is a real failure mode seen (or deliberately induced) while
// performing this module live on OCP 4.21.22 against the appsec + trust stacks on 2026-07-15 — a frozen
// provenance literal, not {ocp_version} (would silently re-date on every versions.yaml bump).
// symptom -> cause -> fix. Environment values via attributes only.

Each entry is symptom → cause → fix. All were seen while performing this module on OpenShift 4.21.22 with OpenShift Pipelines 1.23.1, RHACS 4.11.2, SonarQube Community Build 26.5.0, and Trivy 0.67.0.

== The run fails at `fetch-source`, not at `sast-sonar`

*Symptom:* You start `parasol-claims-devsecops` against `seed-appsec` and the very first task, `fetch-source`, turns red within seconds — the run never gets far enough to reach the SAST gate at all. On the CLI, `tkn pipelinerun logs -f -n $NS --last` shows the clone step failing.

*Cause:* One of the `git-url` or `sonar-project-key` parameters still names a placeholder instead of your real workshop username — most often from starting the CLI-tab manifest before its `{user}` placeholders were replaced, or from mistyping the username by hand in the Console-tab *Start Pipeline* form. `fetch-source` clones whatever `git-url` literally says; a path that isn't `{user}/parasol-claims` doesn't exist in Gitea, so the clone fails before the pipeline ever reaches SonarQube.

*Fix:* Delete the failed run and start again, double-checking both parameters name your own attendee username: `git-url` should read `.../{user}/parasol-claims.git` and `sonar-project-key` should read `parasol-claims-{user}`.

[source,sh,role=execute]
----
oc get pipelinerun -n $NS --sort-by=.metadata.creationTimestamp
oc delete pipelinerun <the-failed-run> -n $NS
----

In the Console tab, re-open *Actions* → *Start* and retype the two parameter fields. In the CLI tab, the manifest in the lab page already substitutes your real username for you — if you pasted from an old capture or typed it from memory, copy it fresh from the lab page instead.

== My workshop username and password won't log me into SonarQube

*Symptom:* You open the SonarQube dashboard, sign in with `<u>` / the workshop password, and it is rejected.

*Cause:* First, the good news: *you do not need to sign in at all.* The dashboard is readable anonymously, and everything this module asks you to look at — the quality gate, the failing condition, the S2068 issue — is visible without an account. So a rejected login never blocks the exercise.

If you *do* want an account, the workshop seeds one SonarQube user per attendee. A rejected login means yours was not seeded — the `sonarqube-user-seed` Job has not run yet, or it failed.

*Fix:* Either carry on without signing in, or have your instructor check the seed Job, which prints one line per attendee:

[source,sh]
----
oc logs job/sonarqube-user-seed -n sonarqube --tail=20
----

It is an Argo CD *Sync hook*, so re-syncing the `workshop-config` Application re-runs it and seeds anyone missing. Note that your SonarQube login is a *local SonarQube user* that merely shares your workshop username and password — the two systems keep separate user databases, so changing your password in one does not change it in the other. The pipeline is separate again: it authenticates with the `sonar-auth` CI token, never with an attendee account.

== The SAST gate PASSES even though the credential is still there

*Symptom:* The `seed-appsec` branch still has the hard-coded `partnerApiPassword`, but `sast-sonar` is *green* and the pipeline sails past it.

*Cause:* The SonarQube project's quality gate is the built-in *"Sonar way"* gate, not *Parasol AppSec Gate*. "Sonar way" is Clean-as-You-Code — every condition is "on *new* code" — and a project's *first* analysis has no new-code baseline, so *all* conditions report empty and the gate passes regardless of issues. The credential *is* detected (rule S2068, `vulnerabilities=1`), but the default gate never evaluates it.

*Fix:* Make *Parasol AppSec Gate* the default. It is created by the `sonar-bootstrap` Job; if it is missing or not default, re-run that Job (or set it in the SonarQube UI: *Quality Gates* → *Parasol AppSec Gate* → *Set as Default*). Confirm with the instructor pre-flight check. The gate's condition is `vulnerabilities` is greater than `0` — an *overall* metric, so it fires on the first scan.

== The pipeline fails at `sast-sonar` with "sonar-auth" errors

*Symptom:* `sast-sonar` fails early; the log mentions a missing `sonar-auth` secret or an unauthorized call to SonarQube.

*Cause:* The per-user hook did not copy the shared CI token into `{user}-cicd`. That hook reads `sonarqube/sonar-ci-token` (minted by the appsec stack) and writes `{user}-cicd/sonar-auth`. If the appsec stack isn't installed, or the token wasn't minted, there is nothing to copy.

*Fix:* Confirm the source token exists (`oc get secret sonar-ci-token -n sonarqube`), then `ws reset app-security-testing --user <u>` to re-run the copy hook. After reset, `oc get secret sonar-auth -n <u>-cicd` should exist (two keys: `sonar-token`, `sonar-host-url`; values never printed).

== My fix didn't take — the same gate fails on the re-run

*Symptom:* You edited a file, but the re-run fails at the *same* gate with the *same* finding.

*Cause:* One of three things: (a) you didn't `git push` (the commit is local only), (b) you pushed to the wrong branch (the pipeline builds `seed-appsec`, not `main`), or (c) the re-run started before the push landed.

*Fix:* Confirm the push reached `seed-appsec`: `git -C ~/parasol-claims log --oneline -1 origin/seed-appsec`. The top commit should be your fix. Then start a *fresh* run (not a cached one). The pipeline's `git-revision` param must be `seed-appsec`.

== `git push` fails with "could not read Username"

*Symptom:* `git push origin seed-appsec` fails with `fatal: could not read Username for 'https://...'` or an `askpass` error.

*Cause:* The terminal has no way to prompt for your Gitea credentials, and none are stored.

*Fix:* Run `git config --global credential.helper store` (the lab does this in exercise 1), then push again and enter your workshop username (`{user}`) and password once — it is stored for the rest of the lab. If a push still hangs, set the remote to the HTTPS route explicitly: `git remote set-url origin {gitea_url}/{user}/parasol-claims.git`.

== The image scan is GREEN but you expected log4shell

*Symptom:* `image-scan` passes on the seeded branch, when it should fail on log4shell.

*Cause:* Either the seeded `Containerfile` step was already removed (check `grep log4j-core:2.14.1 Containerfile`), or the build stage could not resolve the `log4j-core` artifact from the Maven repository (the `mvn dependency:copy` step needs registry access), so nothing was baked into the image.

*Fix:* Confirm the seed is present on `seed-appsec` (`git checkout seed-appsec -- Containerfile; grep log4j-core:2.14.1 Containerfile`). If the build log shows a Maven resolution error on `org.apache.logging.log4j:log4j-core:2.14.1`, the builder can't reach the artifact — the same repository the normal build uses. Re-run once the registry is reachable. (`ws reset app-security-testing --user <u>` re-asserts the seed.)

== `roxctl deployment check` reports violations but the gate seemed to pass before

*Symptom:* You recall an earlier version where the config check "passed" despite an insecure manifest.

*Cause:* `roxctl deployment check` only sets a *non-zero exit code* when a violated policy has *deploy enforcement* — and enabling deploy enforcement would engage the cluster admission controller (which we deliberately don't do, to avoid blocking real workloads). So the raw command exits `0` even on violations.

*Fix:* Nothing to fix — this is by design. The `roxctl-deployment-check` task reads roxctl's *violation summary* and fails the build when the manifest trips any policy at or above `FAIL_SEVERITY` (default MEDIUM). The hardened manifest trips *zero*; the seeded one trips five MEDIUM policies. If you want stricter/looser gating, set the task's `FAIL_SEVERITY` param.

== The SCA scan lists a copyleft license but doesn't fail on it

*Symptom:* Trivy's output shows a restricted/forbidden license (e.g. an AGPL dependency), but the SCA gate doesn't fail because of it.

*Cause:* Trivy's `--exit-code` is driven by *vulnerabilities*, not licenses, and a source-only filesystem scan cannot reliably classify a Maven dependency's license without the built jars. The license scanner still *runs* and its findings appear in the SBOM/report — but the hard *gate* here is the CVE gate.

*Fix:* This is expected. The SCA gate fails on *HIGH/CRITICAL dependency CVEs* (the seeded `commons-collections` 3.2.1 is CVE-2015-7501, CRITICAL). Treat the license output as *review material* in the CycloneDX SBOM. Enforcing a copyleft-license *gate* is an organization decision you'd apply against built artifacts or a dedicated license service.

== The DAST gate passes on an app with no headers

*Symptom:* `dast-zap` is green even though the app doesn't set security headers.

*Cause:* The `dast-zap` stage isn't running with `FAIL_ON_WARN=true`. By default the ZAP baseline treats missing headers as *warnings*, which don't gate. The Application Security Testing pipeline sets `FAIL_ON_WARN=true` on the `dast-zap` stage so warnings become failures.

*Fix:* Confirm the pipeline's `dast-zap` task params include `FAIL_ON_WARN: "true"` (`oc get pipeline parasol-claims-devsecops -n <u>-cicd -o yaml | grep -A2 FAIL_ON_WARN`). If you re-authored the pipeline, add it back — otherwise the header gate never bites.

== The DAST gate still fails after I added every header the lab lists

*Symptom:* You appended the security headers from exercise 6, pushed, re-ran — and `dast-zap` still fails, with a *single* remaining warning naming a header you were never asked to set. For example:

[source,texinfo]
----
WARN-NEW: Cross-Origin-Resource-Policy Header Missing or Invalid [90004] x 1
FAIL-NEW: 0   WARN-NEW: 1   INFO: 0   IGNORE: 0   PASS: 64
❌ DAST FAILED — ZAP reported a gating alert on the running app.
----

*Cause:* `FAIL_ON_WARN=true` means *one* warning is enough to keep the gate shut — clearing seven of eight is still red. And the list of header rules ZAP checks is not fixed: it ships with ZAP and grows as new ones are added to the baseline ruleset. So a header list that was complete when this module was written can become incomplete later, without anything in the lab changing.

*Fix:* Read the rule name in the WARN line and set that header, exactly as you did for the others. The pattern is always the same — one line in `src/main/resources/application.properties`, then commit, push and re-run:

[source,properties]
----
quarkus.http.header."<Header-Name>".value=<value>
----

For the example above, `quarkus.http.header."Cross-Origin-Resource-Policy".value=same-origin` clears it (measured 2026-08-02: adding exactly that line took the run from this failure to all twelve stages green).

This is not a detour from the lesson — it *is* the lesson. A scanner's ruleset moves, the gate holds you to the current one, and the fix is to read what it actually reported rather than re-running and hoping. Treat a shrinking `WARN-NEW` count as progress even while the gate stays red.

== The whole run is slow / a re-run seems stuck

*Symptom:* A re-run takes ten minutes or more; the graph sits on `unit-test`, then on `build-image`, for a few minutes each.

*Cause:* Not stuck — *pipeline-bound*. A complete run is *~10.5–11.5 minutes*. Two stages dominate: `unit-test` (*~2.5–3 min*) and `build-image` (*~2–3 min*), and *both are paid on every re-run* because each PipelineRun claims a fresh workspace, so no Maven or layer cache survives from the previous one. `sast-sonar` and `dast-zap` add ~1.5 min each. This is normal.

If you only need to reach a *particular* gate, the run stops there — so an early re-run is much quicker than a late one: ~2.5 min to the SAST gate, ~2–2.5 min to SCA, but ~8 min to the image-scan gate and ~10–11 min to the DAST gate.

*Fix:* Nothing — wait it out, or watch progress with `tkn pipelinerun logs -f -n <u>-cicd --last`. For a faster classroom, use the *demo* flavor (one narrated red-to-green) instead of six attendee rebuilds, or pre-warm the first run before the concept discussion.

== The RHACS console asks for a username and password I was never given

*Symptom:* You open the RHACS console link and land on a sign-in form asking for a username and password. Your workshop credentials are rejected, and there is no "Log in with OpenShift" button.

*Cause:* This is expected, not a broken setup. RHACS Central keeps its *own* user database, entirely separate from OpenShift, and the workshop does not create an account for you in it. Central will not accept an OpenShift session token either — it rejects them outright, no matter whose token it is.

*Fix:* Nothing to fix; read the finding in the TaskRun log instead. The `image-scan` and `deployment-check` stages run RHACS's own `roxctl` and print the *identical* policy verdict — the policy name, the CVE, the severity, the component — into their logs, which is the path the lab uses. Your instructor shows the RHACS console screens on the shared display.

== I can't open the ZAP HTML report, the k6 report, or `trivy-sbom.json`

*Symptom:* A stage says it wrote a report "to the workspace", but there is no way to open it. `oc exec` or `oc cp` against the stage's pod fails with `cannot exec into a container in a completed pod`.

*Cause:* Also expected. Those files are written into pipeline *workspaces* — scratch volumes attached to the stage's own pod. Once the stage finishes, its container has stopped, so there is nothing left to copy a file out of; and the ZAP and k6 workspaces are `emptyDir` volumes, whose contents are not recoverable at all once the pod ends. This teaching pipeline deliberately does not publish artifacts to durable storage.

*Fix:* Read the *TaskRun logs*, which persist for the life of the PipelineRun and carry every number the gates decide on — the ZAP WARN/FAIL summary, k6's p95 and error rate, and Trivy's CVE table. Making artifacts durable (an artifact repository, an object store, a vulnerability-management dashboard) is a real platform decision, and it is one of the wrap-up's org-mapping questions.

== A later re-run refuses to start: `exceeded quota … persistentvolumeclaims`

*Symptom:* A PipelineRun — often the final, everything-green payoff run — never starts a pod; `oc describe pipelinerun <name> -n <u>-cicd` (or the console) shows `exceeded quota: workshop-quota, requested: persistentvolumeclaims=1`.

*Cause:* Every PipelineRun materializes a *fresh* workspace PVC from its `volumeClaimTemplate`, and that PVC is owned by — and lives exactly as long as — its PipelineRun. The module's designed fix loop is six sequential runs, Tekton's pruner only sweeps daily, and nothing in the flow cleans up behind you, so a single sitting can walk into the per-namespace PVC quota.

*Fix:* Delete the oldest *finished* runs — each frees its PVC through the ownerReference: `oc get pipelinerun -n <u>-cicd --sort-by=.metadata.creationTimestamp`, then `oc delete pipelinerun <old-run> -n <u>-cicd`. The quota ceiling itself is workshop-tunable in `gitops/workshop-config/templates/per-user-limits.yaml`.
