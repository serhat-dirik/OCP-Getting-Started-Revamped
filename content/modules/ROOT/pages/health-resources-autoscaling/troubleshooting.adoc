Every entry below is a failure mode the lab produces on purpose, or one that came up while building the exercises it is made from.

== I broke the readiness probe but the Route stayed `200`

Symptom:: After `oc set probe … --readiness --get-url=http://:8080/q/health/typo`, a new pod sits at `0/1`, the old one keeps running, and the Route still answers `200`.
Cause:: Nothing is wrong. The probe change started a rolling update, and the rollout is gated by readiness: the new pod never becomes ready, so it never replaces the old one.
Fix:: To see the `503`, every pod has to carry the broken probe — scale to zero and back, as the lab does:
+
[source,sh,role=execute]
----
oc scale deploy/parasol-claims --replicas=0
for i in $(seq 1 30); do [ "$(oc get pods -l app=parasol-claims -o name | wc -l)" -eq 0 ] && break; sleep 2; done
oc scale deploy/parasol-claims --replicas=1
sleep 40
oc get endpoints parasol-claims
----
+
Deleting a pod does not do it: the old ReplicaSet recreates a ready one.

== The Route returns `503`, or the router's error page, right after a probe or resource change

Symptom:: `oc rollout status` says `successfully rolled out`, but the next `curl` returns `503` or an HTML error page.
Cause:: The old pod is still shutting down, and the router refreshes its list of backends only every few seconds, so a request can still be routed to the address that just left.
Fix:: Wait for one pod and a few seconds, then retry — the lab's blocks already do:
+
[source,sh,role=execute]
----
for i in $(seq 1 45); do [ "$(oc get pods -l app=parasol-claims -o name | wc -l)" -eq 1 ] && break; sleep 2; done
sleep 10
curl -sf --retry 30 --retry-all-errors --retry-delay 2 -o /dev/null -w "Route: %{http_code}\n" \
  "http://$(oc get route parasol-claims -o jsonpath='{.spec.host}')/api/claims"
----

== The claims pod keeps restarting, and its logs show nothing wrong

Symptom:: `RESTARTS` climbs every half minute or so; `oc logs` shows a normal startup each time.
Cause:: A liveness probe on a path the app does not serve — exercise 2's typo `/q/health/alive`, left in place.
The kubelet reads three `404` responses as "wedged" and restarts a healthy container.
`oc describe pod -l app=parasol-claims` shows `Liveness probe failed: HTTP probe failed with statuscode: 404` and `failed liveness probe, will be restarted`.
Fix:: Point liveness at the real endpoint:
+
[source,sh,role=execute]
----
oc set probe deploy/parasol-claims --liveness --get-url=http://:8080/q/health/live --period-seconds=10 --failure-threshold=3
oc rollout status deploy/parasol-claims
----

== A new pod shows `OOMKilled` or `CrashLoopBackOff` after I changed resources

Symptom:: After `oc set resources`, the new pod never becomes ready; its `STATUS` alternates between `OOMKilled` and `CrashLoopBackOff`, and `oc logs --previous` ends mid-startup with no error.
Cause:: The memory limit is below what the Java runtime needs to start, so the kernel kills the container (exit code `137`).
That is exercise 3's deliberate break; outside it, a limit typed as `128M` instead of `512Mi` does the same.
Confirm it:
+
[source,sh,role=execute]
----
BAD=$(oc get pods -l app=parasol-claims --sort-by=.metadata.creationTimestamp -o jsonpath='{.items[-1:].metadata.name}')
oc get pod "$BAD" -o jsonpath='{.status.containerStatuses[0].lastState.terminated.reason} {.status.containerStatuses[0].lastState.terminated.exitCode}{"\n"}'
----
Fix:: Put the memory back to what the app needs:
+
[source,sh,role=execute]
----
oc set resources deploy/parasol-claims --requests=memory=256Mi --limits=memory=512Mi
oc rollout status deploy/parasol-claims
----

== The claims API returns `500` while the `OOMKilled` pod is crash-looping

Symptom:: During exercise 3's break, the old pod is still `1/1`, but `curl …/api/claims` sometimes returns `500`.
Cause:: The claims service recreates and re-seeds its database schema every time it starts, and every replica shares the one `claims-db`.
A start attempt that is killed partway through that step can leave the tables missing until the next start completes it.
Fix:: Restore the memory limit (previous entry). The rollout's new pod finishes the schema and seed on start, and the `500` responses stop.

== `must be less than or equal to memory limit`

Symptom:: `oc set resources` fails with `Invalid value: "256Mi": must be less than or equal to memory limit`.
Cause:: A request may never exceed its limit. Lowering only `--limits=memory=128Mi` leaves the `256Mi` request above it.
Fix:: Set both together, as the lab does: `--requests=memory=128Mi --limits=memory=128Mi`.

== My HPA shows `<unknown>/60%` and is not scaling

Symptom:: Just after `oc autoscale`, `oc get hpa` shows `TARGETS` as `<unknown>/60%` and `REPLICAS 0`.
Cause:: The HPA has no CPU reading from the cluster's metrics API yet.
For a new HPA that is normal for about a minute; if it lasts longer, the metrics API is not answering.
(A container with no CPU request is the other textbook cause, but it cannot happen here: the namespace's LimitRange gives every container a request.)
Fix:: Wait a minute and re-check.
If it stays `<unknown>`, ask the metrics API directly, and read the HPA's own explanation:
+
[source,sh,role=execute]
----
oc adm top pod -l app=parasol-claims
oc describe hpa parasol-claims | grep -A4 'Conditions:'
----
+
A CPU and memory figure per pod means the metrics are flowing and the HPA catches up on its next sample.
An error from `oc adm top` (or a `ScalingActive False` condition naming `FailedGetResourceMetric`) means the cluster's metrics API is down — a platform fault, so tell your instructor.

== The burst is running but `REPLICAS` is still 2

Symptom:: `claims-burst` is `Running`, but `oc get hpa` still shows `REPLICAS 2` after a minute.
Cause:: Almost always, not enough time yet.
In five measured runs `REPLICAS` reached 4 between *42 and 115 seconds* after the burst started: CPU has to be sampled before the HPA sees it over target (*24–40 s*), and the climb often steps 2 → 3 → 4.
Fix:: Watch rather than re-run — `oc get hpa parasol-claims -w` — and give it two minutes.
If `TARGETS` is still at its idle reading after that, check that the burst is actually sending traffic:
+
[source,sh,role=execute]
----
oc get pod claims-burst
oc adm top pod claims-burst
----
+
A working burst reads hundreds of millicores. Single digits means it is not driving load: delete it and run the lab's `oc run` block again by clicking it rather than retyping it.

== `claims-burst` is stuck in `ImagePullBackOff`

Symptom:: `claims-burst` never starts; `oc get pods` shows `ErrImagePull` or `ImagePullBackOff`.
Cause:: The burst pulls its image from `registry.redhat.io`, which needs the cluster's pull secret — or the image reference was cut short when copied by hand.
Fix:: Check the `claims-load` generator, which runs the very same image:
+
[source,sh,role=execute]
----
oc get pods -l app=claims-load
----
+
If `claims-load` is `Running`, the image is fine: delete the burst (`oc delete pod claims-burst`) and run the lab's block again by clicking it.
If `claims-load` is also stuck pulling, the cluster's pull secret is the problem — tell your instructor.

== The HPA will not scale back down after I stop the load

Symptom:: `TARGETS` fell below 60%, but `REPLICAS` stays at 4 for minutes.
Cause:: The default *5-minute scale-down stabilization window*, which keeps a brief lull from shrinking the service just before the next burst.
Fix:: Nothing — this is correct. It steps back toward the floor of 2 after about five minutes.
