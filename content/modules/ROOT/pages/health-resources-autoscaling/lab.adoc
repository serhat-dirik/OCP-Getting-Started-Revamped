=== Brief

image::health-resources-autoscaling/health-resources-autoscaling-01-readiness-gate.svg["The readiness gate: a Route and Service above two pods. A solid traffic arrow reaches the pod whose readiness is passing, shown in green and in the Service endpoints; a dashed no-endpoint arrow stops short of the pod whose readiness is failing, shown in red, removed from endpoints with traffic held and the Route returning 503."]

*Running is not the same as ready*

A pod can be up and still unable to serve: loading, waiting on a dependency, or wedged.
The platform cannot tell unless the application says so, through three probes: startup holds the others off while the application boots, liveness restarts a wedged container, and readiness removes a pod that cannot serve from the Service.

*Requests, limits and the kernel*

A container's *request* is what the scheduler reserves for it, and what the autoscaler measures against.
Its *limit* is a ceiling: over the CPU limit it is slowed down, over the memory limit the kernel kills it.

*Scaling without a ticket*

A HorizontalPodAutoscaler (HPA) samples CPU against the request and changes the replica count to hold a target, so capacity follows demand rather than a guess made weeks ago.

*In this demo*

. The claims service with three probes, explicit resources and an autoscaler
. Readiness deliberately broken: every pod runs, none is ready, and the Route returns 503
. The probe restored, and the pods put straight back into rotation
. A memory limit too small for the JVM, and the `OOMKilled` it produces
. Load arrives, and the HPA adds pods on its own

=== 2 · Break readiness and the Route returns 503 — 3 min

Point readiness at a URL that does not exist, then replace every pod, so all of them run perfectly well and none can ever answer yes to the platform's question.

image::health-resources-autoscaling/health-resources-autoscaling-02-readiness-503.png["The Pods list for the dev project, two rows: claims-db Running with Ready 1/1, and directly below it parasol-claims also Running with zero restarts but Ready 0/1 — a container that started fine and never passes its readiness probe."]

*Why it matters*

The container is up and the process is fine; what fails is the question "can you serve?".
No ready pod means no endpoints, so the Route returns 503 rather than sending a request into a pod that would break it.
The column that tells the story is READY, not STATUS.

// UNVERIFIED until Part B: scaling to 0 and back to 2 with the solve-state HPA present (the HPA
// pauses at 0 replicas and resumes at 2; both new pods carry the broken probe).
[source,sh,role=execute,subs="attributes+"]
----
oc -n {user}-dev set probe deploy/parasol-claims --readiness --get-url=http://:8080/q/health/typo
# scale to 0 and back, so every pod that comes up carries the broken readiness check
oc -n {user}-dev scale deploy/parasol-claims --replicas=0
for i in $(seq 1 20); do [ "$(oc -n {user}-dev get pods -l app=parasol-claims --no-headers 2>/dev/null | wc -l | tr -d ' ')" = 0 ] && break; sleep 2; done
oc -n {user}-dev scale deploy/parasol-claims --replicas=2
sleep 40
oc -n {user}-dev get pods -l app=parasol-claims
CLAIMS=$(oc -n {user}-dev get route parasol-claims -o jsonpath='{.spec.host}')
curl -s -o /dev/null -w "Route: %\{http_code}\n" http://$CLAIMS/api/claims
----

*What just happened*

Both pods are `Running` at `0/1`, the Service has no endpoints, and the Route answers 503.
The platform is holding the request rather than delivering it to a pod that cannot serve it.

=== 3 · Restore the probe and the pods return to rotation — 2 min

Point readiness back at the endpoint that exists. The same gate that drained the pods puts them back the moment they answer.

....

*Why it matters*

Drain, hold, recover is one continuous decision the platform makes from the application's own answer: nothing was reconfigured by hand, and no user reached a broken pod in between.

`Route: 200`. The recovery took no more action than the failure did.

=== 4 · Too little memory: the kernel stops the container — 2 min

Lower the memory limit below what the Java runtime needs just to start, and read why the new pod never comes up.

[mermaid]
....
include::example$diagrams/health-resources-autoscaling/08-oomkilled.mmd[]
....

*Why it matters*

A memory limit is enforced by the kernel, not by the application, so the evidence is not in the logs: the process is killed mid-start with no exception.
It is in the pod's last termination state, which reads `OOMKilled`.
Readiness holds the rollout, so the old pods keep serving while you find out.

// UNVERIFIED until Part B: the 128Mi value on the cluster image. Measured only as a local proxy
// (2026-11-14, same app build under a Temurin 21 JVM with a podman memory limit): 128Mi and 160Mi
// were OOMKilled (exit 137) within ~4 s of start; 192Mi started at ~173 MB.
[source,sh,role=execute,subs="attributes+"]
----
oc -n {user}-dev set resources deploy/parasol-claims --requests=memory=128Mi --limits=memory=128Mi
# wait until the newest pod has been killed and restarted at least once
for i in $(seq 1 30); do R=$(oc -n {user}-dev get pods -l app=parasol-claims --sort-by=.metadata.creationTimestamp -o jsonpath='{.items[-1:].status.containerStatuses[0].lastState.terminated.reason}'); [ -n "$R" ] && break; sleep 2; done
oc -n {user}-dev get pods -l app=parasol-claims
echo "last termination of the newest pod: $R"
----

Put the limit back before moving on:

[source,sh,role=execute,subs="attributes+"]
----
oc -n {user}-dev set resources deploy/parasol-claims --requests=memory=256Mi --limits=memory=512Mi
oc -n {user}-dev rollout status deploy/parasol-claims
----

*What just happened*

The new pod crash-looped with `OOMKilled` while the two old pods kept serving; restoring the limit rolled out healthy pods.

=== 5 · Load arrives, and the HPA adds pods — 3 min

Start a short burst of concurrent traffic and watch the autoscaler react: CPU climbs past the 60% target and the replica count follows, with no person involved.

image::health-resources-autoscaling/health-resources-autoscaling-05-topology-hpa-scale.png["OpenShift Topology view for the user's dev project with the Resources side panel open for the parasol-claims Deployment. *Why it matters*

Capacity follows demand: the service runs at 2 pods when quiet and grows to 4 under load, and it shrinks back after a deliberate 5-minute wait so a short lull does not cause a flap.

*On screen* — web console → *Topology* in `{user}-dev` → click `parasol-claims` → *Resources*: the *Pods* list grows from 2 to 4 within one to two minutes.

== Frequently asked questions

*Why did the Route not return 503 the moment the probe broke?*::
A probe change triggers a rolling update, and the rollout is itself gated by readiness: the new pod never becomes ready, so the old, healthy pods keep serving.
That is the platform protecting users from a bad change.
A 503 appears only when no pod is ready at all, which is why the demo scales to zero and back.

*Why is there no error in the logs of the OOMKilled pod?*::
Because the application never saw one.
The kernel enforces the memory limit and stops the process outright when it crosses it, so the log simply ends.
The evidence is the pod's last termination state: reason `OOMKilled`, exit code `137`.

*Why does the autoscaler take a minute or two, not a few seconds?*::
Its decision is instant; the wait is the measurement.
CPU has to be sampled and reported before the HPA sees it over target, and the climb often goes 2 → 3 → 4 with a fresh sample before each step.

*Should the liveness probe check the database?*::
No.
If the database blips, every pod fails liveness at once and the platform restarts all of them, turning a short outage into a restart storm.
Readiness may reflect a dependency; liveness should only ask whether this process is healthy.

*Why does scale-down take five minutes?*::
The HPA holds the higher count through a 5-minute stabilization window by default, so a brief lull does not shrink the service just before the next burst.

.Liveness is the probe that can hurt you
[%collapsible]
====
A failing readiness probe only takes a pod out of rotation; a failing liveness probe *kills* it.
That makes liveness the one to point at the narrowest possible question — "is this process able to make progress?" — and never at something outside the process.
If liveness checked the database, a database blip would fail every pod at once and the platform would restart all of them together, turning a short outage into a restart storm.
After several restarts in a row, the kubelet also starts waiting longer between them, and the pod shows `CrashLoopBackOff`.
====

for i in $(seq 1 45); do [ "$(oc get pods -l app=parasol-claims -o name | wc -l)" -eq 1 ] && break; sleep 2; done
----
--
====

*What just happened:* until `/q/health/started` answers, the platform runs neither readiness nor liveness, so a slow boot is never mistaken for a wedged process.
This one allows up to 3 seconds × 30 = *90 seconds* to boot; once it passes, the other two take over.

.Why not just give liveness a long initial delay?
[%collapsible]
====
A long `initialDelaySeconds` on liveness delays *every* check by the slowest boot you ever expect, so a container that wedges five seconds after a fast start goes unnoticed for minutes.
A startup probe gives the boot as much time as it needs and then hands over immediately, so liveness can stay strict for the rest of the container's life.
====

.The three QoS classes, and why they matter
[%collapsible]
====
[cols="1,2,2",options="header"]
|===
| Class | When | Under node memory pressure

| *Guaranteed* | every container's requests equal its limits, for CPU and memory | evicted last
| *Burstable* | requests set, but not equal to limits (this app) | evicted after BestEffort, starting with pods using most over their request
| *BestEffort* | no requests or limits at all | evicted first
|===

You cannot produce BestEffort in this namespace: the LimitRange gives every container defaults.
Guaranteed is the right choice for a latency-critical service whose memory use is well known; Burstable suits most applications, whose use varies.
====

Now the third break.
A Java application needs memory beyond its heap — class metadata, compiled code, threads — before it serves anything.

*What just happened:* the container crossed `128Mi` while starting, and the kernel killed it outright — exit code `137` is 128 + 9, signal 9 being `SIGKILL`.
The new pod never became ready, so readiness held the rollout and the old pod kept serving.

.Why the logs do not help here
[%collapsible]
====
`oc logs --previous` on that pod shows a startup that simply *stops* — no exception, no stack trace — because a `SIGKILL` gives the process no chance to write one.
That is the signature of an out-of-memory kill: when a pod restarts with nothing in its logs, read `lastState.terminated.reason` first.
In the console, the pod's details page shows the same reason under its container's last state.
====

.Work *with* the namespace guardrails
[%collapsible]
====

Right-sizing requests is what keeps you inside it: a request is a reservation, and asking for more than you use wastes the namespace's headroom.
Authoring that quota, and seeing what happens when a workload asks for more than its share, is xref:multi-tenancy-workload-security/lab.adoc[Multi-Tenancy & Workload Security].
