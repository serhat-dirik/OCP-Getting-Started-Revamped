This module is three "read the evidence, then fix it" breaks and one live scale-out.
The two ideas that must land are *"readiness holds traffic away from a pod that cannot serve"* and *"the request is what the scheduler and the HPA read; the limit is what the kernel enforces."*
The breaks are the spine: a readiness probe on a `404` path (a held rollout, then a `503`), a liveness probe with a typo (a healthy container restarted), and a memory limit too small to start in (`OOMKilled`, exit `137`).
The closer, the HorizontalPodAutoscaler (HPA) growing the service from 2 to 4 pods, is *reliable but not quick*: in the measured runs it took 42 seconds to just under two minutes.

== Demo-mode notes

Beyond the steps on the Demo page:

* *Solve first, always.* `adm solve health-resources-autoscaling` a few minutes ahead, then confirm `ready=2`; the HPA reads `<unknown>` for its first minute, which is fine.
* *The readiness break needs the scale-to-zero step.*
Break readiness alone and the old pods keep serving — a held rollout, which is a fine point to make, but not the `503`.
With the HPA present, scale to `0` and back to `2`: the HPA pauses at zero replicas and resumes at two.
* *Say why the OOMKilled pod's logs are empty* before anyone asks: the kernel killed the process, so it had no chance to log.
The evidence is `lastState.terminated.reason`.
* *Fill the HPA wait.* The scale-out takes one to two minutes; narrate the measurement path (sample → compare → scale) while the watch runs, and point at the *Resources* panel's *Pods* list, not the Topology ring, which looks the same at 2 and 4.
* *Delete the burst pod* before the next run — a forgotten `claims-burst` pins the HPA at 4.

== Top questions attendees ask

*1. "I broke readiness and the Route still says 200 — did it not work?"*::
It worked: the probe change started a rolling update, and the new pod never became ready, so the rollout is *held* and the old pod keeps serving.
That is the platform refusing to ship a broken change.
The `503` only appears once no pod is ready at all, which is why the lab scales to zero and back.

*2. "Why did the platform restart my perfectly healthy app?"*::
Because the liveness probe asked the wrong question — the typo'd path answers `404`, and three failures in a row read as "wedged".
A wrong liveness probe is worse than none, which is the point of exercise 2.
The same reasoning is why liveness must never check a database: one blip, every pod restarted.

*3. "The OOMKilled pod's logs show nothing — where is the error?"*::
There is none in the logs: the kernel stopped the process with `SIGKILL` (exit code `137` = 128 + 9) the moment it crossed its memory limit.
Read `oc get pod <name> -o jsonpath='{.status.containerStatuses[0].lastState.terminated.reason}'` — it says `OOMKilled`.

*4. "My HPA says `<unknown>` — is it broken?"*::
For the first minute, no: it has no CPU sample yet.
If it stays `<unknown>`, the container has no CPU request to compute a percentage against — exercise 3 sets `200m`; check it is still there.

*5. "Why is the scale-out so slow, and why won't it scale back down?"*::
Up: the autoscaler decides instantly, but CPU has to be sampled first (*24–40 s* before it first read over target in the measured runs), and the climb often steps 2 → 3 → 4.
Down: a deliberate *5-minute stabilization window*, so a short lull does not cause a shrink-then-grow flap.

== Watchouts

* *Exercise 3 leaves a crash-looping pod until the attendee restores the limit.*
An attendee who stops after the `OOMKilled` step has a held rollout and a pod in `CrashLoopBackOff`; `ws verify` then fails the readiness check with a hint to restore the limit.
Point them at the restore block.
* *The `128Mi` value depends on the Java runtime.*
It was chosen from a local measurement with a wide margin (the JVM needed ~173 MB to start); a future image that starts smaller could survive it.
If an attendee's new pod comes up `1/1` at `128Mi`, have them try `64Mi`, and report it.
* *Rapid `oc set probe` / `oc set resources` mean several quick rollouts.*
Between rollouts the Route can briefly answer `503` even after `rollout status` succeeds, because the router refreshes its backend list every few seconds.
The lab's blocks wait for one pod, sleep and retry; a hand-typed `curl` mid-rollout may see a transient `503` — have them re-run it.
* *Clean up burst pods.*
A `claims-burst` left running keeps CPU high, pins the HPA at 4, and skews the next run: `oc delete pod claims-burst -n {user}-dev`.
* *The optional challenge scales the database to zero.*
The app keeps erroring after the database returns until the claims pods restart (`oc rollout restart deploy/parasol-claims`) — that step is in the challenge's answer.
