In this lab you take the developer inner loop into the cluster.
You open Parasol's claims service in a browser IDE that starts in under two minutes, run it in Quarkus dev mode against the *real* in-cluster database, change a live endpoint and watch it hot-reload, extend the workspace definition with a Valkey cache, push your change to Git, step through a running request in a debugger, and reach past the workspace to port-forward the database and ship your change as a running Deployment.
Everything happens in your own projects — `{user}-devspaces` for the workspace, `{user}-dev` for the app and database — so nothing you do can affect another attendee.

This lab uses two different terminals:

* The *workspace terminal* — inside the browser IDE (Red Hat OpenShift Dev Spaces, "Dev Spaces" from here on).
*Almost every command runs here.*
These blocks are copy-enabled; paste them into the IDE terminal.
* The *Showroom terminal* — the terminal tab beside these instructions, logged in as `{user}`.
Only steps explicitly labelled *Showroom terminal* run here (they use `oc` to look at the cluster from the outside).

== One click to a running, editable service · 9 min

A developer with nothing installed opens Parasol's claims service in a browser IDE, changes a live endpoint against the real in-cluster database, and hands the change on with one push.

[IMPORTANT]
.Prep — run before the session
====
Stage the module from the cockpit terminal:

[source,sh,role=execute]
----
ws prep devspaces-inner-loop
----

That declares a *parasol-claims* workspace on the Dev Spaces dashboard and leaves it waiting; it does not start it.

*Open that workspace once after staging, and leave it open.* The first start pulls the universal developer image onto a node and takes about *85 seconds*; once the image is on that node a start takes about *20 seconds*. Warming it is what keeps step 1 inside its two minutes.

Have two browser tabs signed in as `{user}`: the web console on *Topology* in `{user}-dev`, and the {devspaces_url}[Dev Spaces dashboard^].

While the workspace is open, make the push in step 4 work without an interruption: run `git config --global credential.helper store` in the workspace terminal and push once. The first push from a fresh workspace asks for the Git username and password in an input box at the *top of the editor* rather than on the terminal line, and the terminal looks frozen until it is answered.

NOTE: The workspace is started from the Dev Spaces dashboard, with the *Open* link beside *parasol-claims*. This console version has no "edit source code" link on the Topology node, so Topology is not a way into the IDE.

CAUTION: If the workspace has not opened within about twenty seconds, switch to the workspace opened during preparation rather than waiting out a cold image pull. The subject of the demo is the loop, not the start time.

=== Brief

image::devspaces-inner-loop/devspaces-inner-loop-01-inner-outer-loop.svg["Two loops side by side: a red inner loop of edit, build, run in dev mode and observe, measured in seconds, handing off with a git push to a grey outer loop of pipeline, image, GitOps promotion and running in production, measured in minutes to hours."]

*Two loops, two currencies*

Every change travels through two loops. The *inner loop* — edit, build, run, observe — runs dozens of times an hour while a feature is being written, and its currency is seconds. If it is slow, the whole day is slow.

The *outer loop* — commit, build, scan, promote — starts once the change is good. Its currency is minutes to hours, and it exists for safety and repeatability rather than speed. Optimizing both the same way makes both worse.

*Why the IDE moves into the cluster*

A laptop development environment is a checklist: the right JDK, the right Maven, a local database, container tooling, credentials, VPN. It takes hours to days, and it rots between hires. A workspace in the cluster is a link instead — click it, and a correct environment materializes in under two minutes.

It also closes two gaps the laptop opens. The workspace is built from a pinned image and a `devfile.yaml` in the repository, so the toolchain is reviewed like code rather than drifting machine by machine. And source, credentials and data stay in the cluster under the same RBAC as everything else, so a lost laptop stops being a breach question.

Red Hat OpenShift Dev Spaces is that environment, and this demo stays entirely inside the inner loop it makes fast.

*In this demo*

. A running claims service, and its source opened in a browser IDE from one link
. The devfile deciding the toolchain — the same Java version for every developer and for the pipeline
. A live endpoint changed and hot-reloaded in seconds against the real in-cluster database
. One push, handing the change from the inner loop to the outer loop

=== 1 · From a running service to its source — 2 min

Parasol's claims service and its database are already running in `{user}-dev`. Getting from that running workload to an editable copy of its source is one link away, with no JDK, Maven or local database on anyone's machine.

image::devspaces-inner-loop/devspaces-inner-loop-04-topology-open-in-devspaces.png["The web console Topology view in the user's dev project: the parasol-claims deployment beside its claims-db database, with the side panel listing a running Pod, the Service on port 8080, and the application's Route."]

*Why it matters*

"How long until a new engineer ships their first change?" is a measured cost. Where the environment is a link rather than a checklist, the answer is minutes — and there is no laptop-setup page to keep accurate.

*On screen* — web console → *Topology* in `{user}-dev`: `parasol-claims` and `claims-db`, both running. Then the Dev Spaces dashboard, and the *Open* link beside the waiting *parasol-claims* workspace.

*What just happened*

Opening the workspace clones the fork and builds the environment from the `devfile.yaml` in that repository. Nothing was installed or configured by hand.

=== 2 · The devfile decides the toolchain — 3 min

The workspace opens into che-code — VS Code in a browser tab — with the claims project loaded. What is inside it was decided by a file in the repository, not by whoever set up the machine.

image::devspaces-inner-loop/devspaces-inner-loop-01-workspace-loaded.png["The che-code editor in a browser tab: the parasol-claims project in the Explorer with devfile.yaml among its files, and an integrated terminal where java -version reports openjdk 21."]

*Why it matters*

The universal developer image ships several JDKs and defaults to 17; this project targets 21, so the devfile pins it. "Move everyone to Java 21" is therefore a one-line pull request that every developer and the pipeline pick up together, instead of a machine-by-machine chase.

*On screen* — `devfile.yaml` open in the editor, then a workspace terminal (*Terminal → New Terminal*):

[source,sh]
----
java -version
----

It reports `openjdk 21`, from the devfile.

=== 3 · Change a live endpoint and watch it reload — 3 min

Dev mode runs the service inside the workspace, wired by ordinary in-cluster DNS to the same PostgreSQL the deployed application uses. A saved edit is live on the next request.

image::devspaces-inner-loop/devspaces-inner-loop-02-workspace-gateway-services.svg["The workspace inside the cluster: the browser IDE reaching che-gateway over HTTPS, the gateway fronting a tools container running Quarkus dev mode on port 8080 with debug on 5005, and that container reaching the claims-db PostgreSQL in the app project over cross-namespace DNS."]

*Why it matters*

Nothing here is a stand-in. The development instance is a first-class citizen of the cluster network, reaching the real database the way one microservice reaches another — so the integration being exercised in the loop is the one that ships.

In the workspace terminal, point the datasource at the in-cluster database and start dev mode:

[source,sh,subs="attributes"]
----
cd /projects/parasol-claims
export QUARKUS_DATASOURCE_JDBC_URL=jdbc:postgresql://claims-db.{user}-dev.svc:5432/parasol
export QUARKUS_DATASOURCE_USERNAME=parasol
export QUARKUS_DATASOURCE_PASSWORD=parasol
export QUARKUS_HIBERNATE_ORM_SCHEMA_MANAGEMENT_STRATEGY=update
./mvnw quarkus:dev
----

*On screen* — add a `/ping` endpoint to `ClaimResource.java` and save it, then call it from a second terminal tab:

[source,sh]
----
curl http://localhost:8080/api/claims/ping
----

*What just happened*

Quarkus recompiled only what changed and reloaded it in place: the dev-mode terminal prints a `Live reload total time` of about two seconds, and the endpoint that did not exist a moment ago answers. No image was built and no Pod was replaced.

=== 4 · One push hands it to the outer loop — 1 min

The change exists only in the workspace until it is committed and pushed to the fork. That push is the seam between the two loops.

image::devspaces-inner-loop/devspaces-inner-loop-04-what-you-built.svg["What the workspace ties together: the developer's parasol-claims fork with its devfile opening a Dev Spaces workspace running che-code and Quarkus dev mode, that workspace reaching claims-db over cross-namespace DNS and hot-reloading in about two seconds, git push returning to the fork, and a dotted arrow onward from the fork to pipeline and GitOps."]

*Why it matters*

Everything before the push is seconds long and private to one developer. Everything after it — builds, scanning, policy, GitOps promotion — belongs to the platform and is what the following modules cover. Same code, one command between them.

In the workspace terminal:

[source,sh]
----
cd /projects/parasol-claims
git add -A
git commit -m "Add /api/claims/ping endpoint"
git push origin main
----

*On screen* — the fork in the Git server, with the new commit at the top of `main`.

== Frequently asked questions

*Where does the workspace actually run, and is any of our code on the laptop?*::
It runs as a Pod in the cluster, in the developer's own project. The browser is a thin client to the editor through the che-gateway, over HTTPS and authenticated per user. The repository is cloned onto a volume in the cluster and never onto the laptop, so code and data stay under the same RBAC as everything else on the platform.

*Why not let the framework start its own throwaway database in dev mode?*::
A workspace has no container runtime inside it, so it cannot — and that turns out to be the better answer. A development instance iterating against the real in-cluster database over ordinary service DNS is exercising the integration it will ship, not a substitute for it.

*Is a workspace where the application runs in production?*::
No. It is a development environment, not a runtime: it stops itself when idle, it is capped per user, and dev mode is for iterating. Production comes from the outer loop the push feeds — builds, policy, and GitOps.

*How long does a workspace take to start?*::
About twenty seconds once the developer image is on the node, and up to about ninety seconds the first time, while that image is pulled. Where many people start their first workspace at once, the image puller pre-pulls it onto every node and removes the cold start entirely.

*What stops workspaces from consuming the cluster?*::
An administrator sets the limits: how many workspaces a person may define, how many may run at once, how much CPU and memory each gets, and how long an idle one lives before it stops itself. Files survive that stop, because they live on a persistent volume rather than in the container.

== 2. Wire dev mode to the in-cluster database
⏱ *~7 min* · the deliberate break-and-fix — a dev instance needs a real database

Quarkus *dev mode* (`./mvnw quarkus:dev`) runs the app with live reload.
Start it the naive way first, in the *workspace terminal*, and watch it fail on purpose:

[source,sh]
----
cd /projects/parasol-claims
./mvnw quarkus:dev
----

After the dependencies download, it stops with an error:

.Expected output (the deliberate failure)
[%collapsible]
=====
[source,texinfo]
----
ERROR [...DockerClientProviderStrategy] Could not find a valid Docker environment. ...
WARN  [...DevServicesDatasourceProcessor] Please configure the datasource URL for
      default datasource or ensure the Docker daemon is up and running.
ERROR [io.quarkus.runtime.Application] Failed to start application:
  Datasource '<default>' was deactivated automatically because its URL is not set.
  To activate the datasource, set configuration property 'quarkus.datasource.jdbc.url'.
----
=====

Read what happened, because it is the whole lesson.
The claims app needs a database.
With no database configured, Quarkus tried to *start one for you* (a throwaway container, called a Dev Service) — but a workspace has no container runtime inside it, so that failed, and the app refused to start without a datasource URL.

You do not want a throwaway database anyway.
You want the *real* `claims-db` that is already running in your `{user}-dev` project — the same one the deployed claims app uses.
Your workspace can reach it by ordinary in-cluster DNS, across namespaces: `claims-db.{user}-dev.svc`.

Press *Ctrl+C* to stop the failed attempt, then wire the datasource with environment variables and start dev mode again:

[source,sh,subs="attributes"]
----
export QUARKUS_DATASOURCE_JDBC_URL=jdbc:postgresql://claims-db.{user}-dev.svc:5432/parasol
export QUARKUS_DATASOURCE_USERNAME=parasol
export QUARKUS_DATASOURCE_PASSWORD=parasol
export QUARKUS_HIBERNATE_ORM_SCHEMA_MANAGEMENT_STRATEGY=update
./mvnw quarkus:dev
----

This time it starts.
Watch for these lines:

.Expected output
[source,texinfo,subs="attributes"]
----
INFO  [io.quarkus] parasol-claims 1.0.0 on JVM (powered by Quarkus {quarkus_version}) started in 6.6s. Listening on: http://0.0.0.0:8080
INFO  [io.quarkus] Profile dev activated. Live Coding activated.
INFO  [io.quarkus] Installed features: [..., hibernate-orm, jdbc-postgresql, ...]
----

[NOTE]
.Why environment variables, not an edit to the code
====
The claims service reads its database URL, username, and password from environment variables, so the *same image* runs in dev, stage, and prod with only configuration changing.
You just used that: you pointed a dev instance at the cluster database without touching a line of code.
The schema strategy `update` tells your dev instance to *use* the existing tables, not drop and reseed them — so you never clobber the shared database.
Externalizing configuration like this is the subject of a later module (Config, Secrets & Multi-Environment — a separate module).
====

With dev mode running, confirm your workspace instance is talking to the in-cluster database.
In the workspace terminal, in a *second* IDE terminal tab (leave dev mode running in the first):

[source,sh]
----
curl -s http://localhost:8080/api/claims | head -c 200
----

You should see real claims — `CLM-1001`, `CLM-1002`, … — the 30 seeded rows served from `claims-db`.

[.checkpoint]
****
✔ *Verify:* Dev mode logs `Profile dev activated. Live Coding activated`, and `curl http://localhost:8080/api/claims` returns seeded claims.
If you get `Connection refused`, dev mode has not finished starting — wait for the `Listening on` line.
If the app fails with a datasource error, re-check the `export` lines (host `claims-db.{user}-dev.svc`).
****

== 3. Change a live endpoint and watch it hot-reload
⏱ *~6 min* · the inner loop at full speed

Now the payoff: change the running service without rebuilding or restarting it.
Leave dev mode running.

In the IDE Explorer, open `src/main/java/com/parasol/claims/ClaimResource.java`.
Add a small new endpoint just before the final closing brace of the class:

[source,java]
----
    @GET
    @Path("/ping")
    @Produces(MediaType.TEXT_PLAIN)
    public String ping() {
        return "parasol-claims dev mode: hot reload works";
    }
----

Save the file (*Ctrl+S*).
You did *not* restart anything.
Now hit the new endpoint from your second terminal tab:

[source,sh]
----
curl http://localhost:8080/api/claims/ping
----

The first request triggers Quarkus to recompile just what changed and reload it in place — you will see it in the dev-mode terminal:

.Expected output (in the dev-mode terminal)
[source,texinfo]
----
INFO  [io.quarkus.deployment.dev.RuntimeUpdatesProcessor] Restarting quarkus due to changes in ClaimResource$NewClaim.class, ClaimResource.class, ClaimResource$StatusUpdate.class.
INFO  [io.quarkus.deployment.dev.RuntimeUpdatesProcessor] Live reload total time: 2.2s
----

— and `curl` prints `parasol-claims dev mode: hot reload works`.
That endpoint did not exist a moment ago.
No image was built, no Pod was replaced; the loop was *seconds*.

Prove it is the *same shared database* as the deployed app.
Create a claim through your dev instance, then read it back through the *deployed* app's public Route — from the *Showroom terminal* this time:

[source,sh]
----
# workspace terminal: create a claim via your dev instance
curl -s -X POST http://localhost:8080/api/claims \
  -H 'Content-Type: application/json' \
  -d '{"claimant":"Dev Mode Demo","type":"auto","amount":500.00}'
----

[source,sh,role=execute,subs="attributes"]
----
# Showroom terminal: read it back through the DEPLOYED app's Route
CLAIMS_HOST=$(oc -n {user}-dev get route parasol-claims -o jsonpath='{.spec.host}')
curl -s "http://$CLAIMS_HOST/api/claims" | tr ',' '\n' | grep -A1 "Dev Mode Demo"
----

Your new claim, written by the workspace dev instance, is visible through the separately-deployed app — because both point at the one `claims-db`.

[.checkpoint]
****
✔ *Verify:* `curl .../api/claims/ping` returns your string, the dev-mode terminal shows a `Live reload` line, and the claim you POSTed appears through the deployed Route.

== 4. Extend the workspace: add a Valkey cache to the devfile
⏱ *~7 min* · the devfile is yours to change — restart the workspace from it

A workspace is not fixed — it is whatever its devfile says.
Add a second container (a Valkey cache the app could use) and a command to talk to it, then restart the workspace *from the devfile* so the new container appears.

[NOTE]
.Why Valkey, not Redis
====
*Valkey* is the Linux Foundation's BSD-licensed continuation of Redis, created after Redis changed its license.
Red Hat ships a supported *Valkey* image and it is a drop-in for the same in-memory cache role — the wire protocol and the client commands (`PING`, `SET`, `GET`, …) are unchanged, so what you learn here transfers directly.
====

Stop dev mode (*Ctrl+C*).
In the IDE Explorer, open `devfile.yaml` at the repository root.
Under `components:`, add a `cache` component, and under `commands:`, add a `cache-ping` command:

[source,yaml]
----
  # add under components:
  - name: cache
    container:
      # pinned by digest: tags move, digests don't — a devfile exists to be reproducible
      image: registry.redhat.io/rhel9/valkey-8@sha256:21f04dd3590cbb3561af0ced8e0e1e8cc1039023d808adcbb0c1cf10dca5b6fa
      memoryLimit: 256Mi
      endpoints:
        - name: valkey
          targetPort: 6379
          exposure: internal
----

[source,yaml]
----
  # add under commands:
  - id: cache-ping
    exec:
      label: Ping the Valkey cache
      component: cache
      commandLine: valkey-cli ping
----

Save the file.
Now restart the workspace so Dev Spaces rebuilds it from the updated devfile:

. Open the *Command Palette*: menu *View → Command Palette…* (keyboard: kbd:[Cmd+Shift+P] on a Mac, kbd:[Ctrl+Shift+P] on Windows/Linux).
. Type `Restart Workspace` and choose *Dev Spaces: Restart Workspace from Local Devfile*.

When the workspace comes back, the `cache` container is part of it.
Confirm it by running the devfile command you just declared — this one is a *task*, not a command, so it lives in a different menu: *Terminal → Run Task…* → *devfile: Ping the Valkey cache*.
It executes `valkey-cli ping` *inside the `cache` container* (the `valkey-cli` binary lives there, not in your `tools` terminal).

.Expected output
[source,texinfo]
----
PONG
----

The two containers share the workspace Pod's network, so your app — and your terminal — can reach Valkey at `localhost:6379`.
Prove it from the *workspace terminal* without any Valkey tooling, using bash's built-in TCP support:

[source,sh]
----
exec 3<>/dev/tcp/localhost/6379 && printf 'PING\r\n' >&3 && head -c 7 <&3
----

.Expected output
[source,texinfo]
----
+PONG
----

No service, no route — just a sidecar you declared in Git.

[.checkpoint]
****
✔ *Verify:* After the restart, the *devfile: Ping the Valkey cache* task returns `PONG`, and the workspace now runs a `cache` container (the terminal TCP probe answers `+PONG` too).
If the restart fails, your devfile has a YAML error — check the indentation of the two blocks you added (see xref:devspaces-inner-loop/troubleshooting.adoc[troubleshooting]).
****

== 5. Push your change and ship it as a running Deployment
⏱ *~10 min* · the hand-off from inner loop to outer loop, all the way to a running container

Your `/ping` change lives only in the workspace.
Commit it, push it to your fork, and then let the platform build and run it — this is the moment the inner loop hands off to the outer loop that the rest of the workshop builds (pipelines, GitOps).

In the workspace terminal, first tell git who you are — a fresh workspace container has no git identity yet (set it once per workspace; the values only label your commits):

[source,sh,subs="attributes"]
----
git config --global user.email "{user}@parasol.example.com"
git config --global user.name "{user}"
----

Your workspace can *read* your fork, but it has no credentials to *write* to it yet.
Tell git to remember what you type, so you are asked once and never again:

[source,sh]
----
git config --global credential.helper store
----

Now commit and push:

[source,sh]
----
cd /projects/parasol-claims
git add -A
git commit -m "Add /api/claims/ping endpoint"
git push origin main
----

[IMPORTANT]
.The password prompt appears ABOVE the terminal, not in it
====
On the push, che-code asks for your Git credentials in an *input box at the top of the editor* — not on the terminal line.
The terminal looks frozen until you answer it, so if nothing seems to happen, look up.

Enter your workshop username (`{user}`) and password — the same ones you signed in with.
`credential.helper store` saves them, so later pushes go straight through.
====

The push succeeds:

.Expected output
[source,texinfo,subs="attributes"]
----
To https://.../{user}/parasol-claims.git
   3bf5a39..c270dc8  main -> main
----

[TIP]
.The IDE has a Git UI too

You do not have to use the terminal.
The che-code *Source Control* panel (the branch icon in the left rail) stages, commits, and pushes with buttons, and it asks for your username and password in the same input box the first time you push.
Use whichever you prefer; the result is the same commit on your fork.

****
✔ *Verify:* `git push` reports your commit was written to `main`.
Open your fork in the {gitea_url}[Git server^] (browse to `{user}/parasol-claims`) and confirm the latest commit is your `/ping` change.

=== Now ship it: turn the pushed commit into a running Deployment

Dev mode is for iterating; it is not where the app runs for real.
The `/api/claims/ping` endpoint you just pushed is only source right now — turn it into a running container the platform builds, runs, and heals.
`oc new-app` does the whole source-to-Deployment step from your fork in one command (the same on-ramp the *Ways to Build & Deliver Apps* module covers in depth).

These steps talk to the cluster rather than to the workspace, so run them in the *Showroom terminal* — the tab beside these instructions:

[source,sh,role=execute,subs="attributes"]
----
oc -n {user}-dev new-app java-21~{gitea_url}/{user}/parasol-claims.git --name=parasol-claims-mine
----

That creates a BuildConfig, an ImageStream, a Deployment, and a Service — all named `parasol-claims-mine`, so they sit *beside* the pre-staged `parasol-claims`, not on top of it.
Wire it to the shared database (the same Secret the pre-staged app uses) and wait for the build and rollout:

[source,sh,role=execute,subs="attributes"]
----
oc -n {user}-dev set env deploy/parasol-claims-mine \
  --from=secret/claims-db \
  POSTGRESQL_HOST=claims-db \
  QUARKUS_HIBERNATE_ORM_SCHEMA_MANAGEMENT_STRATEGY=update
oc -n {user}-dev logs -f buildconfig/parasol-claims-mine
oc -n {user}-dev rollout status deploy/parasol-claims-mine
----

The S2I build takes a few minutes the first time — Maven resolves dependencies and compiles your fork.
The `update` schema strategy is the same one you used in dev mode: your new instance *uses* the existing tables instead of dropping and reseeding the shared database.
When `rollout status` reports the Deployment available, give it a browser-reachable Route (edge TLS) and call *your* endpoint on the running container:

[source,sh,role=execute,subs="attributes"]
----
oc -n {user}-dev create route edge parasol-claims-mine \
  --service=parasol-claims-mine --insecure-policy=Redirect
MINE=$(oc -n {user}-dev get route parasol-claims-mine -o jsonpath='{.spec.host}')
curl -s https://$MINE/api/claims/ping; echo
----

.Expected output
[source,texinfo]
----
parasol-claims dev mode: hot reload works
----

The exact string you wrote in dev mode is now served by a container the platform runs — replicated, health-checked, restarted for you if it dies.
That is the outer loop taking your change: from here a pipeline and GitOps would build and promote it (later modules), instead of you running `oc new-app` by hand.

[.checkpoint]
****
✔ *Verify:* `oc -n {user}-dev get deploy parasol-claims-mine` shows the Deployment available, and `curl https://$MINE/api/claims/ping` returns your `/ping` string from the *deployed* container (not dev mode).
****

== 6. Take-home: the same loop, locally
⏱ *~5 min* · read

In-cluster workspaces are one end of a spectrum.
When you want the inner loop entirely on your own machine — on a plane, air-gapped, or just offline — two Red Hat tools give you the same shape (both free for development, on macOS, Windows, and Linux):

* https://developers.redhat.com/products/podman-desktop[Podman Desktop^] — build and run containers (and small Kubernetes/Pod setups) locally; the natural home for the container half of the inner loop without a cluster.
* https://developers.redhat.com/products/openshift-local[Red Hat OpenShift Local^] — a single-node OpenShift on your laptop, for when you need the *platform* (Routes, operators, the console) and not just containers.

Both run the same images and, in OpenShift Local's case, the same objects you have been using all along — the skills transfer directly.
When you are done for the day, your Dev Spaces workspace idles automatically after 30 minutes of inactivity to free cluster resources, and resumes where you left off.

== Optional: Debug a live request
[.optional-lab]

⏱ *~6 min* · attach a debugger to the running service

Quarkus dev mode opens a Java debug port (5005) automatically, so you can attach a debugger to the *running* dev instance and step through a real request — the JVM is genuinely listening for one.

[IMPORTANT]
.Your workspace already has the Java extensions

The breakpoint-and-step (GUI) half of this exercise needs *Language Support for Java* and *Debugger for Java*, and they are already installed — your fork carries a `.vscode/extensions.json` that asks for them, and che-code installs what a project recommends when the workspace starts.

If the IDE offers to *update* an extension, dismiss it — you do not need a newer one for this.

It needs no extension and proves the same thing.

export QUARKUS_DATASOURCE_JDBC_URL=jdbc:postgresql://claims-db.{user}-dev.svc:5432/parasol
export QUARKUS_DATASOURCE_USERNAME=parasol
export QUARKUS_DATASOURCE_PASSWORD=parasol
export QUARKUS_HIBERNATE_ORM_SCHEMA_MANAGEMENT_STRATEGY=update

=== Prefer the terminal? Attach `jdb` instead

This path needs no IDE extension — it uses the JDK's own command-line debugger (`jdb`, shipped with the JDK) to prove 5005 is a real, attachable debug port.
In a *second* workspace terminal tab (leave dev mode running in the first):

[source,sh]
----

----

It connects to the running JVM.
At the `>` prompt, list the live threads, set a breakpoint on the list method, and continue:

[source,text]
----
> threads
> stop in com.parasol.claims.ClaimResource.list

== Optional: Beyond dev mode — reach the database directly
[.optional-lab]
_Not needed to finish the module — take it if you are curious how the workspace reaches the rest of the cluster._
⏱ *~5 min* · port-forward an internal service straight into your workspace

Dev mode is the fast heart of the inner loop, but two everyday developer moves live just past it: reaching a cluster service directly with your own tools, and turning a change into a running Deployment the platform manages.
Both are the bridge from the inner loop to the outer loop.

[IMPORTANT]
.Which terminal? The workspace one — it is you
====
`oc` in the *workspace* terminal is signed in as *you*, not as a service account: run `oc whoami` there and it prints `{user}`.
It has the same rights in `{user}-dev` as the Showroom terminal does.

That matters for the next step: a port-forward only exists on the machine that runs it.
Forward a port from the *workspace* terminal and the workspace — including the IDE and its debugger — can reach it on `localhost`.
Forward it from the Showroom terminal and only the Showroom terminal can.
====

=== Port-forward the database to your localhost

The `claims-db` PostgreSQL database has *no Route* — it is internal-only, reachable inside the cluster by DNS (that is the `claims-db.{user}-dev.svc` name your dev instance used).
To reach it from a database tool on your own machine — `psql`, a GUI client, or your IDE's database panel — bridge it to a local port with `oc port-forward`.
In the *workspace terminal* (so the forwarded port lands where your IDE and tools are):

[source,sh,subs="attributes"]
----
oc -n {user}-dev port-forward svc/claims-db 5432:5432
----

.Expected output (it keeps running — leave it)
[source,texinfo]
----
Forwarding from 127.0.0.1:5432 -> 5432
Forwarding from [::1]:5432 -> 5432
----

`localhost:5432` in your environment is now the in-cluster database: point any PostgreSQL client at it and you are querying the real `claims-db`, through a temporary tunnel that closes when you press *Ctrl+C*.

[TIP]
.Prove the tunnel carries PostgreSQL (optional)
====
The workspace ships no `psql`, but bash can speak enough of the wire protocol to prove what is on the other end — the same TCP trick you used for the cache.
In a second terminal tab, send a PostgreSQL SSL-negotiation request and read the one-byte reply:

[source,sh]
----
exec 3<>/dev/tcp/localhost/5432
printf '\x00\x00\x00\x08\x04\xd2\x16\x2f' >&3
read -t 3 -n1 reply <&3 && echo "claims-db answered on localhost:5432 with: $reply"
----

A reply of `N` (SSL off) or `S` (SSL on) is PostgreSQL's own answer — you have reached the database through the tunnel.
Press *Ctrl+C* on the port-forward when you are done.
====

[.checkpoint]
****
✔ *Verify:* `oc port-forward` prints `Forwarding from 127.0.0.1:5432 -> 5432` and holds the terminal — the internal database is now on your `localhost:5432`.
****

=== Going further: debug and hot-reload the running container

You attached a debugger to dev mode in the *Debug a live request* exercise; the same attach works against a *deployed* container once you open its debug port.
Turn JDWP on for your Deployment, then forward its debug port *from the workspace terminal* — the IDE that will attach runs inside the workspace, so the port has to land on the workspace's `localhost`, not the Showroom terminal's:

[source,sh,subs="attributes"]
----
oc -n {user}-dev set env deploy/parasol-claims-mine \
  JAVA_TOOL_OPTIONS='-agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005'
oc -n {user}-dev rollout status deploy/parasol-claims-mine
oc -n {user}-dev port-forward deploy/parasol-claims-mine 5005:5005
----

// VERIFIABLE, contrary to what this comment used to claim. It read "[UNVERIFIABLE-PERMANENT] …
// requires a graphical IDE running on a host that can reach the forwarded port — a human's own
// machine". That was wrong, and it is why the WRONG TERMINAL went unnoticed here: the IDE is IN the
// workspace, so a workspace-side port-forward is reachable by it, and the attach can be exercised
// the same way exercise "Debug a live request" is. The old instruction forwarded 5005 from the
// Showroom terminal, which binds a DIFFERENT pod's localhost — the attach could never have worked.
// Measured 2026-08-17: `oc whoami` in the workspace returns the attendee, and
// `oc port-forward -n {user}-dev` succeeds from there.
With `5005` forwarded inside the workspace, attach to `localhost:5005` the same way you did in the debugger exercise — the *Attach to Quarkus (5005)* configuration, or `jdb -attach localhost:5005` in a second workspace terminal — and you are stepping through the *deployed* container instead of dev mode.

For a live *edit-and-see* loop against a running Pod (not just local dev mode), Quarkus offers *remote development mode*: you run a mutable build in the cluster with `QUARKUS_LAUNCH_DEVMODE=true` and connect to it with `./mvnw quarkus:remote-dev`, so a saved file hot-reloads straight into the Pod.
It is an advanced pattern — the Quarkus link in the wrap-up has the details.
