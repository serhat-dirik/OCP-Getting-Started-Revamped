== One click to a running, editable service · 9 min

A developer with nothing installed opens Parasol's claims service in a browser IDE, changes a live endpoint against the real in-cluster database, and hands the change on with one push.

[IMPORTANT]
.Prep — run before the session
====
Stage the module from the cockpit terminal:

[source,sh,role=execute]
----
ws prep devspaces-inner-loop
----

That declares a *parasol-claims* workspace on the Dev Spaces dashboard and leaves it waiting; it does not start it.

*Open that workspace once after staging, and leave it open.* A start takes about *40 seconds*: the workshop installer pre-pulls the developer images onto every node.

Have two browser tabs signed in as `{user}`: the web console on *Topology* in `{user}-dev`, and the {devspaces_url}[Dev Spaces dashboard^].

While the workspace is open, make the push in step 4 work without an interruption: run `git config --global credential.helper store` in the workspace terminal and push once. The first push from a fresh workspace asks for the Git username and password in an input box at the *top of the editor* rather than on the terminal line, and the terminal looks frozen until it is answered.

NOTE: The workspace is started from the Dev Spaces dashboard, with the *Open* link beside *parasol-claims*. This console version has no "edit source code" link on the Topology node, so Topology is not a way into the IDE.

CAUTION: If the workspace has not opened within about forty seconds, switch to the workspace opened during preparation rather than waiting it out. The subject of the demo is the loop, not the start time.

=== Brief

image::devspaces-inner-loop/devspaces-inner-loop-01-inner-outer-loop.svg["Two loops side by side: a red inner loop of edit, build, run in dev mode and observe, measured in seconds, handing off with a git push to a grey outer loop of pipeline, image, GitOps promotion and running in production, measured in minutes to hours."]

*Two loops, two currencies*

Every change travels through two loops. The *inner loop* — edit, build, run, observe — runs dozens of times an hour while a feature is being written, and its currency is seconds. If it is slow, the whole day is slow.

The *outer loop* — commit, build, scan, promote — starts once the change is good. Its currency is minutes to hours, and it exists for safety and repeatability rather than speed. Optimizing both the same way makes both worse.

*Why the IDE moves into the cluster*

A laptop development environment is a checklist: the right JDK, the right Maven, a local database, container tooling, credentials, VPN. It takes hours to days, and it rots between hires. A workspace in the cluster is a link instead — click it, and a correct environment materializes in under two minutes.

It also closes two gaps the laptop opens. The workspace is built from a pinned image and a `devfile.yaml` in the repository, so the toolchain is reviewed like code rather than drifting machine by machine. And source, credentials and data stay in the cluster under the same RBAC as everything else, so a lost laptop stops being a breach question.

Red Hat OpenShift Dev Spaces is that environment, and this demo stays entirely inside the inner loop it makes fast.

*In this demo*

. A running claims service, and its source opened in a browser IDE from one link
. The devfile deciding the toolchain — the same Java version for every developer and for the pipeline
. A live endpoint changed and hot-reloaded in seconds against the real in-cluster database
. One push, handing the change from the inner loop to the outer loop

=== 1 · From a running service to its source — 2 min

Parasol's claims service and its database are already running in `{user}-dev`. Getting from that running workload to an editable copy of its source is one link away, with no JDK, Maven or local database on anyone's machine.

image::devspaces-inner-loop/devspaces-inner-loop-04-topology-open-in-devspaces.png["The web console Topology view in the user's dev project: the parasol-claims deployment beside its claims-db database, with the side panel listing a running Pod, the Service on port 8080, and the application's Route."]

*Why it matters*

"How long until a new engineer ships their first change?" is a measured cost. Where the environment is a link rather than a checklist, the answer is minutes — and there is no laptop-setup page to keep accurate.

*On screen* — web console → *Topology* in `{user}-dev`: `parasol-claims` and `claims-db`, both running. Then the Dev Spaces dashboard, and the *Open* link beside the waiting *parasol-claims* workspace.

*What just happened*

Opening the workspace clones the fork and builds the environment from the `devfile.yaml` in that repository. Nothing was installed or configured by hand.

=== 2 · The devfile decides the toolchain — 3 min

The workspace opens into che-code — VS Code in a browser tab — with the claims project loaded. What is inside it was decided by a file in the repository, not by whoever set up the machine.

image::devspaces-inner-loop/devspaces-inner-loop-01-workspace-loaded.png["The che-code editor in a browser tab: the parasol-claims project in the Explorer with devfile.yaml among its files, and an integrated terminal where java -version reports openjdk 21."]

*Why it matters*

The universal developer image ships several JDKs and defaults to 17; this project targets 21, so the devfile pins it. "Move everyone to Java 21" is therefore a one-line pull request that every developer and the pipeline pick up together, instead of a machine-by-machine chase.

*On screen* — `devfile.yaml` open in the editor, then a workspace terminal (*Terminal → New Terminal*):

[source,sh]
----

----

It reports `openjdk 21`, from the devfile.

=== 3 · Change a live endpoint and watch it reload — 3 min

Dev mode runs the service inside the workspace, wired by ordinary in-cluster DNS to the same PostgreSQL the deployed application uses. A saved edit is live on the next request.

image::devspaces-inner-loop/devspaces-inner-loop-02-workspace-gateway-services.svg["The workspace inside the cluster: the browser IDE reaching che-gateway over HTTPS, the gateway fronting a tools container running Quarkus dev mode on port 8080 with debug on 5005, and that container reaching the claims-db PostgreSQL in the app project over cross-namespace DNS."]

*Why it matters*

Nothing here is a stand-in. The development instance is a first-class citizen of the cluster network, reaching the real database the way one microservice reaches another — so the integration being exercised in the loop is the one that ships.

In the workspace terminal, point the datasource at the in-cluster database and start dev mode:

[source,sh,subs="attributes+"]
----
cd /projects/parasol-claims
export QUARKUS_DATASOURCE_JDBC_URL=jdbc:postgresql://claims-db.{user}-dev.svc:5432/parasol
export QUARKUS_DATASOURCE_USERNAME=parasol
export QUARKUS_DATASOURCE_PASSWORD=parasol
export QUARKUS_HIBERNATE_ORM_SCHEMA_MANAGEMENT_STRATEGY=update
./mvnw quarkus:dev
----

*On screen* — add a `/ping` endpoint to `ClaimResource.java` and save it, then call it from a second terminal tab:

[source,sh]
----
curl http://localhost:8080/api/claims/ping
----

*What just happened*

Quarkus recompiled only what changed and reloaded it in place: the dev-mode terminal prints a `Live reload total time` of about two seconds, and the endpoint that did not exist a moment ago answers. No image was built and no Pod was replaced.

=== 4 · One push hands it to the outer loop — 1 min

The change exists only in the workspace until it is committed and pushed to the fork. That push is the seam between the two loops.

image::devspaces-inner-loop/devspaces-inner-loop-04-what-you-built.svg["What the workspace ties together: the developer's parasol-claims fork with its devfile opening a Dev Spaces workspace running che-code and Quarkus dev mode, that workspace reaching claims-db over cross-namespace DNS and hot-reloading in about two seconds, git push returning to the fork, and a dotted arrow onward from the fork to pipeline and GitOps."]

*Why it matters*

Everything before the push is seconds long and private to one developer. Everything after it — builds, scanning, policy, GitOps promotion — belongs to the platform and is what the following modules cover. Same code, one command between them.

In the workspace terminal:

[source,sh]
----
cd /projects/parasol-claims
git add -A
git commit -m "Add /api/claims/ping endpoint"
git push origin main
----

*On screen* — the fork in the Git server, with the new commit at the top of `main`.

== Frequently asked questions

*Where does the workspace actually run, and is any of our code on the laptop?*::
It runs as a Pod in the cluster, in the developer's own project. The browser is a thin client to the editor through the che-gateway, over HTTPS and authenticated per user. The repository is cloned onto a volume in the cluster and never onto the laptop, so code and data stay under the same RBAC as everything else on the platform.

*Why not let the framework start its own throwaway database in dev mode?*::
A workspace has no container runtime inside it, so it cannot — and that turns out to be the better answer. A development instance iterating against the real in-cluster database over ordinary service DNS is exercising the integration it will ship, not a substitute for it.

*Is a workspace where the application runs in production?*::
No. It is a development environment, not a runtime: it stops itself when idle, it is capped per user, and dev mode is for iterating. Production comes from the outer loop the push feeds — builds, policy, and GitOps.

*How long does a workspace take to start?*::
About forty seconds here, because the developer images are pre-pulled onto every node. A node that has never pulled them takes closer to two minutes, which is why a platform team pre-pulls them before many people start workspaces at once.

*What stops workspaces from consuming the cluster?*::
An administrator sets the limits: how many workspaces a person may define, how many may run at once, how much CPU and memory each gets, and how long an idle one lives before it stops itself. Files survive that stop, because they live on a persistent volume rather than in the container.

[source,sh]

cd /projects/parasol-claims

.Expected output (the deliberate failure)

== 4. Extend the workspace: add a Valkey cache to the devfile
⏱ *~7 min* · the devfile is yours to change — restart the workspace from it

The claims team wants to try a cache; in a workspace that is a devfile edit, not a ticket.

*You'll end with:* a second workspace container, `cache` (Valkey), that your terminal reaches on `localhost:6379`.

[mermaid]
....
include::example$diagrams/devspaces-inner-loop/08-workspace-sidecar.mmd[]
....

.Why Valkey, not Redis
[%collapsible]
====
*Valkey* is the Linux Foundation's BSD-licensed continuation of Redis, created after Redis changed its license.
Red Hat ships a supported *Valkey* image and it is a drop-in for the same in-memory cache role — the wire protocol and the client commands (`PING`, `SET`, `GET`, …) are unchanged, so what you learn here transfers directly.
====

Stop dev mode (*Ctrl+C*). In `devfile.yaml` at the repository root, add a `cache` component under `components:` and a `cache-ping` command under `commands:`:

[source,yaml]
----
  # add under components:
  - name: cache
    container:
      # pinned by digest: tags move, digests don't — a devfile exists to be reproducible
      image: registry.redhat.io/rhel9/valkey-8@sha256:21f04dd3590cbb3561af0ced8e0e1e8cc1039023d808adcbb0c1cf10dca5b6fa
      memoryLimit: 256Mi
      endpoints:
        - name: valkey
          targetPort: 6379
          exposure: internal
----

[source,yaml]
----
  # add under commands:
  - id: cache-ping
    exec:
      label: Ping the Valkey cache
      component: cache
      commandLine: valkey-cli ping
----

Save, then restart the workspace from the updated devfile:

. Open the *Command Palette*: *View → Command Palette…* (kbd:[Cmd+Shift+P] on a Mac, kbd:[Ctrl+Shift+P] on Windows/Linux).
. Type `Restart Workspace` and choose *Dev Spaces: Restart Workspace from Local Devfile*.
. When it is back, run *Terminal → Run Task…* → *devfile: Ping the Valkey cache*.
A devfile command is a *task*, and this one runs `valkey-cli ping` inside the `cache` container, where the binary lives.

.Expected output
[source,texinfo]
----
PONG
----

TIP: *Predict, then run:* your `tools` container has no `valkey-cli`. Can its terminal still reach Valkey?

Try with bash's built-in TCP support:

[source,sh]
----
exec 3<>/dev/tcp/localhost/6379 && printf 'PING\r\n' >&3 && head -c 7 <&3
----

.Expected output
[source,texinfo]
----
+PONG
----

*What just happened:* yes. Both containers share the workspace Pod's network, so your app and your terminal reach Valkey at `localhost:6379`.
No Service, no Route: a sidecar you declared in Git.

[.checkpoint]
****
✔ *Verify:* After the restart, the *devfile: Ping the Valkey cache* task returns `PONG`, and the workspace now runs a `cache` container (the terminal TCP probe answers `+PONG` too).
Restart failed? Your devfile has a YAML error: check the indentation of the two blocks you added (see xref:devspaces-inner-loop/troubleshooting.adoc[troubleshooting]).

=== Now ship it: turn the pushed commit into a running Deployment

Dev mode is for iterating, not for running.
Build your fork into a container the platform runs, from the *Showroom terminal* (these steps talk to the cluster):

[source,sh,role=execute,subs="attributes+"]
----
oc -n {user}-dev new-app java-21~{gitea_url}/{user}/parasol-claims.git --name=parasol-claims-mine
----

Wire it to the shared database Secret, then follow the build (a few minutes the first time) and the rollout:

[source,sh,role=execute,subs="attributes+"]
----
oc -n {user}-dev set env deploy/parasol-claims-mine \
  --from=secret/claims-db \
  POSTGRESQL_HOST=claims-db \
  QUARKUS_HIBERNATE_ORM_SCHEMA_MANAGEMENT_STRATEGY=update
oc -n {user}-dev logs -f buildconfig/parasol-claims-mine
oc -n {user}-dev rollout status deploy/parasol-claims-mine
----

Once the rollout completes, publish it with an edge Route and call *your* endpoint:

[source,sh,role=execute,subs="attributes+"]
----
oc -n {user}-dev create route edge parasol-claims-mine \
  --service=parasol-claims-mine --insecure-policy=Redirect
MINE=$(oc -n {user}-dev get route parasol-claims-mine -o jsonpath='{.spec.host}')
curl -s https://$MINE/api/claims/ping; echo
----

.Expected output
[source,texinfo]
----
parasol-claims dev mode: hot reload works
----

*What just happened:* the string you wrote in dev mode now comes from a container the platform runs, health-checks, and restarts if it dies.
In later modules a pipeline and GitOps take over this step from your `oc new-app`.

.What `oc new-app` created, and why `update`
[%collapsible]
====
`oc new-app` does the whole source-to-Deployment step from your fork in one command — the same on-ramp the *Ways to Build & Deliver Apps* module covers in depth.
It created a BuildConfig, an ImageStream, a Deployment, and a Service, all named `parasol-claims-mine`, so they sit *beside* the pre-staged `parasol-claims`, not on top of it.
The first S2I build takes a few minutes because Maven resolves dependencies and compiles your fork.

`set env` hands it the same `claims-db` Secret the pre-staged app uses.
The `update` schema strategy is the same one you used in dev mode: your new instance *uses* the existing tables instead of dropping and reseeding the shared database.
Like any Deployment, it can be scaled to more replicas and is restarted if it dies.
====

== Optional: Debug a live request
[.optional-lab]
_Not needed to finish the module — take it if you want to see the debugger._
⏱ *~6 min* · attach a debugger to the running service

*You'll end with:* a live `/api/claims` request paused on your breakpoint, in the IDE or in `jdb`, through the Java debug port (5005) dev mode opens automatically.

The *Language Support for Java* and *Debugger for Java* extensions are already installed; if the IDE offers to *update* one, dismiss it.

.Why the Java extensions are already there
[%collapsible]
====
Your fork carries a `.vscode/extensions.json` that asks for them, and che-code installs what a project recommends when the workspace starts.
That file is worth knowing about: it is how a team makes every workspace on a repo arrive with the same tooling, the same way the devfile does for the container.
You do not need a newer extension for this exercise.
Rather not use the GUI? The `jdb` path below needs no extension and proves the same thing.
====

Start dev mode again, wired to the database as in exercise 2 (a restart clears the environment variables):

[source,sh,subs="attributes+"]
----
cd /projects/parasol-claims
export QUARKUS_DATASOURCE_JDBC_URL=jdbc:postgresql://claims-db.{user}-dev.svc:5432/parasol
export QUARKUS_DATASOURCE_USERNAME=parasol
export QUARKUS_DATASOURCE_PASSWORD=parasol
export QUARKUS_HIBERNATE_ORM_SCHEMA_MANAGEMENT_STRATEGY=update
./mvnw quarkus:dev
----

Dev mode prints the live debug port:

[source,texinfo]
----
Listening for transport dt_socket at address: 5005
----

=== Attach the IDE debugger

. Open `ClaimResource.java` and click the left margin beside the first line of `list(...)` (`PanacheQuery<Claim> query = Claim.findAll(...)`) to set a *breakpoint* (a red dot).
. Open *Run and Debug* (the play-with-bug icon in the left rail) and start *Attach to Quarkus (5005)*, which your fork ships in `.vscode/launch.json`.
Missing from the dropdown? Wait for the Java extension to finish loading (status bar), then reopen the view.
. Trigger the breakpoint from your second terminal tab:
+
[source,sh]
----
curl http://localhost:8080/api/claims
----
. Execution pauses on your breakpoint: inspect variables, step over a few lines, resume.

//  reaching this state needs a manual extension install first" — was FALSE and is corrected:

=== Prefer the terminal? Attach `jdb` instead

`jdb`, the JDK's command-line debugger, needs no extension.
In a *second* workspace terminal tab (dev mode keeps running in the first):

[source,sh]
----
jdb -attach localhost:5005
----

At the `>` prompt, list threads, break on the list method, and continue:

[source,text]
----
> threads
> stop in com.parasol.claims.ClaimResource.list
> cont
----

`threads` shows the Quarkus main and vert.x event-loop threads: the real, running service, not a copy.
Trigger the endpoint from a *third* tab:

[source,sh]
----
curl http://localhost:8080/api/claims
----

*What just happened:* `jdb` halted at the method: a debugger on a live in-cluster request, with nothing installed.
`locals` prints its variables and `where` the call stack; `cont` resumes, `exit` detaches.

== Optional: Beyond dev mode — reach the database directly
[.optional-lab]
_Not needed to finish the module — take it if you are curious how the workspace reaches the rest of the cluster._
⏱ *~5 min* · port-forward an internal service straight into your workspace

Just past dev mode: reach a cluster service with your own tools, then debug the Deployment you shipped in exercise 5.

*You'll end with:* the internal `claims-db` on your workspace's `localhost:5432`.

[mermaid]
....
include::example$diagrams/devspaces-inner-loop/11-port-forward.mmd[]
....

[IMPORTANT]
.Which terminal? The workspace one — it is you
====
`oc` in the *workspace* terminal is *you*, not a service account (`oc whoami` prints `{user}`), with your usual rights in `{user}-dev`.
A port-forward exists only where it runs: forward from the workspace, and the IDE and its debugger reach it on `localhost`.
====

=== Port-forward the database to your localhost

`claims-db` has *no Route*; it is reachable only by in-cluster DNS (`claims-db.{user}-dev.svc`).
Bridge it to a local port for `psql`, a GUI client, or your IDE's database panel, in the *workspace terminal*:

[source,sh,subs="attributes+"]
----
oc -n {user}-dev port-forward svc/claims-db 5432:5432
----

.Expected output (it keeps running — leave it)
[source,texinfo]
----
Forwarding from 127.0.0.1:5432 -> 5432
Forwarding from [::1]:5432 -> 5432
----

*What just happened:* `localhost:5432` in your workspace is now the real `claims-db`, for any PostgreSQL client, through a tunnel that closes when you press *Ctrl+C*.

.Prove the tunnel carries PostgreSQL (optional)
[%collapsible]
====
The workspace ships no `psql`, but bash can speak enough of the wire protocol to prove what is on the other end — the same TCP trick you used for the cache.
In a second terminal tab, send a PostgreSQL SSL-negotiation request and read the one-byte reply:

[source,sh]
----
exec 3<>/dev/tcp/localhost/5432
printf '\x00\x00\x00\x08\x04\xd2\x16\x2f' >&3
read -t 3 -n1 reply <&3 && echo "claims-db answered on localhost:5432 with: $reply"
----

A reply of `N` (SSL off) or `S` (SSL on) is PostgreSQL's own answer — you have reached the database through the tunnel.
Press *Ctrl+C* on the port-forward when you are done.
====

[.checkpoint]
****
✔ *Verify:* `oc port-forward` prints `Forwarding from 127.0.0.1:5432 -> 5432` and holds the terminal — the internal database is now on your `localhost:5432`.
****

=== Going further: debug and hot-reload the running container

The debugger attach also works on the *deployed* container.
Turn JDWP on for it, and forward its debug port *from the workspace terminal*, where the attaching IDE runs:

[source,sh,subs="attributes+"]
----
oc -n {user}-dev set env deploy/parasol-claims-mine \
  JAVA_TOOL_OPTIONS='-agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005'
oc -n {user}-dev rollout status deploy/parasol-claims-mine
oc -n {user}-dev port-forward deploy/parasol-claims-mine 5005:5005
----

// VERIFIABLE, contrary to what this comment used to claim. It read "[UNVERIFIABLE-PERMANENT] …
// requires a graphical IDE running on a host that can reach the forwarded port — a human's own
// machine". That was wrong, and it is why the WRONG TERMINAL went unnoticed here: the IDE is IN the
// workspace, so a workspace-side port-forward is reachable by it, and the attach can be exercised
// the same way exercise "Debug a live request" is. The old instruction forwarded 5005 from the
// Showroom terminal, which binds a DIFFERENT pod's localhost — the attach could never have worked.
// Measured 2026-08-17: `oc whoami` in the workspace returns the attendee, and
// `oc port-forward -n {user}-dev` succeeds from there.
Then attach to `localhost:5005` as before (*Attach to Quarkus (5005)*, or `jdb -attach localhost:5005` in a second workspace terminal): you are stepping through the *deployed* container, not dev mode.

.Hot reload into a running Pod: remote development mode
[%collapsible]
====
For a live *edit-and-see* loop against a running Pod (not just local dev mode), Quarkus offers *remote development mode*: you run a mutable build in the cluster with `QUARKUS_LAUNCH_DEVMODE=true` and connect to it with `./mvnw quarkus:remote-dev`, so a saved file hot-reloads straight into the Pod.
It is an advanced pattern — the Quarkus link in the wrap-up has the details.
====
