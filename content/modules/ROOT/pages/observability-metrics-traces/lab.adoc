.Counts, rates, and why port 9092
[%collapsible]
=====
The console's query engine is user-workload monitoring's Thanos.
`curl /q/metrics` gives you an instantaneous *count*; turning counts into *rates* over a time window (`rate(...[5m])`), or summing across replicas, is what a query engine does.
The console's *Observe → Metrics* is one door to that engine.
The terminal has another: the in-cluster *tenancy* port of `thanos-querier`, which answers with your own token, scoped to your namespace.
Port `9092` has no Route, so this works only from the cockpit terminal; the `thanos-querier` Route needs a cluster-monitoring role you do not have.
=====

+
[source,yaml,subs="attributes+"]
----
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: parasol-claims-alerts
  namespace: {user}-dev
  labels:
    app: parasol-claims
spec:
  groups:
    - name: parasol-claims.rules
      rules:
        - alert: ParasolClaimsErrorRateHigh
          expr: sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m])) > 0.1
          for: 2m
          labels:
            severity: warning
          annotations:
            summary: "parasol-claims is returning server errors"
            description: "The claims API 5xx rate has exceeded 0.1/s for 2m."
----

.Read your rule in the *project-scoped* view — the cluster-wide Alerting page is empty for you

The cluster-wide *Observe* → *Alerting* page lists *0 - 0 of 0* rules for you; use the project-scoped {ocp_console_url}/dev-monitoring/ns/{user}-dev/alertrules?alert-source=user[*Alerting rules* view for `{user}-dev`^].

.Why the cluster-wide page is empty, and what the project view shows
[%collapsible]
====
The masthead's cluster-wide *Observe* → *Alerting* page queries a *cluster-scoped* monitoring API that a project-level identity is not granted — it answers `Forbidden (verb=get, resource=prometheuses, subresource=api)` — so it lists *0 - 0 of 0* rules for you.
Your rule is missing from it no matter how you filter, and the page has no *Project* selector to point at your namespace.
The project-scoped link above is the surface that queries *per-namespace* monitoring with your identity, and it finds the rule.
It carries a *Project* selector (set to `{user}-dev`) and the tabs *Events* | *Alerting rules* | *Alerts* | *Dashboards* | *Metrics* | *Silences*.
One filter to watch on it: *Source* defaults to *Platform*, which matches nothing you authored.
The link already pins *Source* to *User*; if the list ever looks empty, that filter is the first thing to check.
====

.Creating the rule was denied?
[%collapsible]
====
If either path returns `Forbidden ... cannot create resource "prometheusrules"`, your namespace is missing the user-workload-monitoring editor role.
That is a one-line platform grant, not a mistake on your part — see xref:observability-metrics-traces/troubleshooting.adoc[the troubleshooting page].

== 3. Build the claims dashboard as code
⏱ *~7 min* · four panels in a YAML file, applied like any other object, then changed and re-applied

*Observe → Metrics* answers one question at a time, and the answer is gone when you close the tab.
The on-call engineer wants the same four answers side by side every time, on every cluster the claims service runs on.
So write the dashboard as code: a file you can review, diff and re-apply.

Write the dashboard to a file and apply it.
Each panel is a name, a chart type and one PromQL query:

[source,sh,role=execute]
----
cat > ~/parasol-claims-dashboard.yaml <<'EOF'
apiVersion: perses.dev/v1alpha2
kind: PersesDashboard
metadata:
  name: parasol-claims
spec:
  config:
    display:
      name: Parasol claims
    duration: 15m
    refreshInterval: 15s
    panels:
      requests:
        kind: Panel
        spec:
          display: {name: Requests per second}
          plugin: {kind: TimeSeriesChart, spec: {}}
          queries:
            - kind: TimeSeriesQuery
              spec:
                plugin:
                  kind: PrometheusTimeSeriesQuery
                  spec:
                    datasource: {kind: PrometheusDatasource, name: thanos-tenancy}
                    query: 'sum(rate(http_server_requests_seconds_count[1m]))'
      errors:
        kind: Panel
        spec:
          display: {name: Server errors (5xx) per second}
          plugin: {kind: TimeSeriesChart, spec: {}}
          queries:
            - kind: TimeSeriesQuery
              spec:
                plugin:
                  kind: PrometheusTimeSeriesQuery
                  spec:
                    datasource: {kind: PrometheusDatasource, name: thanos-tenancy}
                    query: 'sum(rate(http_server_requests_seconds_count{status=~"5.."}[1m])) or vector(0)'
      latency:
        kind: Panel
        spec:
          display: {name: Average latency by endpoint (seconds)}
          plugin: {kind: TimeSeriesChart, spec: {}}
          queries:
            - kind: TimeSeriesQuery
              spec:
                plugin:
                  kind: PrometheusTimeSeriesQuery
                  spec:
                    datasource: {kind: PrometheusDatasource, name: thanos-tenancy}
                    query: 'sum by (uri) (rate(http_server_requests_seconds_sum[1m])) / sum by (uri) (rate(http_server_requests_seconds_count[1m]))'
      cpu:
        kind: Panel
        spec:
          display: {name: CPU per pod (cores)}
          plugin: {kind: TimeSeriesChart, spec: {}}
          queries:
            - kind: TimeSeriesQuery
              spec:
                plugin:
                  kind: PrometheusTimeSeriesQuery

[%collapsible]

Turning on histogram buckets is an application setting; once the app publishes them, the panel's query becomes a p95 and nothing else in the dashboard changes.

[%collapsible]

Until the first 5xx, the app has no 5xx series at all, so the query matches nothing and the panel would read *No data*: indistinguishable from a broken query.
`or vector(0)` draws an honest zero instead, and the line climbs off it the moment a server error is counted.

.Why twenty workers, and why a 10-second scrape
[%collapsible]
====
The claims API returns server-errors only inside a *short window*, and threading that window is the whole subtlety of this step.
For the first ~30 seconds the database is still draining, so requests still succeed (*200*).
Once it is truly gone the API fails (*500*) — until, about a minute in, three failed `/q/health/ready` checks (ten seconds apart) trip the readiness probe and the *router* pulls the pod from rotation, after which every request gets a *503* straight from the router and nothing more reaches the app to record a 5xx.
So the entire 5xx signal is banked in a roughly *30-second* window, and two things must line up for the alert to catch it:
you have to bank *enough* server-errors to clear `0.1/s` with margin, and the scrape has to *sample the rising counter more than once* before the pod leaves rotation.
A *concurrent burst* of twenty workers handles the first — hundreds of 5xx, not a couple of dozen — and the ServiceMonitor's *10-second* scrape handles the second: a 30-second window spans three scrapes, so `rate()` reliably sees the counter climb.
(At a 30-second scrape it might sample that window only once, at its frozen final value, so `rate()` reads zero and the alert never fires even though the app plainly failed — which is exactly why the scrape is 10s.)
That last `503` is the probe doing its job: the platform stops sending traffic to a pod that says it is not ready.

.Measured: how long until it fires — and why the scrape interval is the real lesson
[%collapsible]
====
With the concurrent burst, the 5xx rate cleared `0.1/s` within about *50 seconds* and peaked around *1.1/s* — comfortably over the line — then held there through the `for: 2m` window.
`ParasolClaimsErrorRateHigh` reached *Pending* about *50 seconds* after the database went down and *Firing* about two minutes later — close to *3 minutes* end to end.
Plot the counter itself in *Observe → Metrics* (`http_server_requests_seconds_count{status=~"5.."}`) and you can watch the mechanism: it climbs across several 10-second scrapes — a rising series like `3 → 9 → 112 → 298` — and then *freezes*, because once the readiness probe pulls the pod from the router the burst gets `503` s and nothing more reaches the app to increment it.
The alert fires off that captured climb: `rate(...[5m])` sees the rising counter, crosses the line, and stays over it through the `for:` window.
The freeze is the observability lesson twice over.
First, a failing pod stops producing the signal *exactly* when you most want it — so the alert fires off the *last climb* and then *lingers* in Firing while that count ages out of the 5-minute window (the same reason recovery isn't instant, below).
Second — and this is why the scrape is *10 seconds*, not 30 — the whole 5xx climb happens inside a ~30-second window.
A 10-second scrape samples that window three or four times, so `rate()` sees the rise; a 30-second scrape might sample it *once*, at the frozen value, and `rate()` would read a flat *zero* — the alert would never fire even though the app plainly failed.
The scrape interval bounds the shortest fault your alert can catch; the two-minute `for:` window is deliberate on top of that, so a brief blip never pages anyone.

NOTE: Use that project-scoped link, not the cluster-wide *Observe → Alerting* page. The cluster-wide page reads a cluster-monitoring API a workshop account is not granted, so it renders *0 - 0 of 0*, and its *Source* filter defaults to *Platform* — the link above pins it to *User*.

CAUTION: The burst in step 2 has one window. About thirty seconds after the database is scaled away the readiness probe pulls the failing pod out of the router, and from then on the load gets router ``503``s that never reach the application — its own counter freezes, so a second burst cannot re-arm the alert. Recovering from a missed window means a full cycle: recover, wait for the service to answer `200`, then break and burst again, which costs another three minutes. A rehearsal run of the break-and-burst block against a test account is what makes the live window land cleanly.

NOTE: A row that reads *Pending* rather than *Firing* is not a failure — the climb is already banked and the rule's two-minute `for:` window is counting down. Re-running the burst to help it along only adds noise, because the application's counter has already frozen.

CAUTION: The staging command above is idempotent — re-running it restores the end state, with the database back to one replica and the alert rule and dashboard in place.

=== Brief

image::observability-metrics-traces/observability-metrics-traces-01-three-signals.svg["The three signals: a claims request fanning out to metrics, logs and traces, with the question each answers best — metrics for how much, how fast and how bad, logs for what exactly happened in one event, traces for where the time went across services."]

*The three signals, in five minutes*

Observability rests on three kinds of telemetry, and each answers a question the others answer badly. *Metrics* are cheap numbers over time — request rate, error rate, latency, CPU. They are always on, they aggregate across every replica, and they are what you alert on. A metric will say the 5xx rate just tripled; it will not say which claim failed.

*Logs* are individual events with full detail — the stack trace, the offending claim number. They answer "what exactly happened" for one occurrence, but at scale they are a firehose nobody reads live. *Traces* follow one request across every service and database call it touched, and show where the time went. The discipline is: metrics to notice and alert, traces to locate, logs to confirm the detail.

None of that is a separate purchase. OpenShift ships user-workload monitoring built in, and getting an application into it is one small object — a *ServiceMonitor* saying "scrape this Service's `/q/metrics` every ten seconds". Tempo and OpenTelemetry install as operators under the same subscription. Teams that treat "add monitoring" as a procurement project are usually re-buying what they already own.

*In this demo*

. The three signals for a live service, read in the console and at the source
. The database taken away, and what each signal says about a fault in progress
. The same fault on a dashboard kept as code
. The alert firing, and a recovery that takes two steps rather than one

=== 1 · Three signals in one place — 2 min

The claims service is already instrumented and already being scraped. Read its golden signals and a custom business metric in the console, then show the same numbers coming straight out of the application.

image::observability-metrics-traces/observability-metrics-traces-01-observe-metrics.png["Observe Metrics view scoped to the user's project: the PromQL query sum(rate(http_server_requests_seconds_count{uri=\"/api/claims\"}[5m])) in the query box, a steady plotted line just above 0.5 across a thirty-minute window, and the current value 0.503 in the result table below it."]

*Why it matters*

Nothing here was built for this demo. The platform was already collecting; the only integration is a small object pointing at the Service. "Is the claims service healthy" stops being someone tailing logs and becomes a query.

*On screen* — *Observe → Metrics* in `{user}-dev`: plot `sum(rate(http_server_requests_seconds_count[5m]))` for traffic, then `claims_created_total`, the business metric the application team added. A steady line, and a counter climbing.

The same numbers at the source:

[source,sh,role=execute,subs="attributes+"]
----
curl -s http://parasol-claims-{user}-dev.{cluster_domain}/q/metrics \
  | grep -E '^claims_created_total|status="404"' | head
----

*What just happened*

Two places, one set of numbers. The ServiceMonitor is the bridge between them: it tells user-workload monitoring to scrape `/q/metrics` every ten seconds, and both the graph and the alert in the next step ride on that one object.

=== 2 · Take the database away, and read the signals — 4 min

Scale the database to zero, drive a concurrent burst of failing load, and use the three minutes the alert needs to arm to show what metrics, logs and traces each say about a fault that is happening right now.

image::observability-metrics-traces/observability-metrics-traces-05-observe-alerting-inactive.png["Project-scoped Alerting rules view for the user's namespace: ParasolClaimsErrorRateHigh listed with severity Warning and source User, and an empty State column because nothing is wrong yet — the before picture for the firing row later in the demo."]

*Why it matters*

The rule is loaded and watching before anything is wrong, which is the state a production alert spends almost all of its life in. The delay before it fires is a feature, not lag: `for: 2m` on a five-minute rate is what stops a thirty-second blip from waking anybody.

*On screen* — the project-scoped *Alerting rules* view: one row, `ParasolClaimsErrorRateHigh`, severity *Warning*, source *User*, *State* empty.

Then break it. Twenty concurrent workers bank hundreds of 5xx into the roughly thirty-second window before the readiness probe pulls the pod from the router — a serial trickle banks too few for `rate()` to see the climb. Note the time; the alert fires about three minutes from here:

[source,sh,role=execute,subs="attributes+"]
----
oc scale deploy/claims-db -n {user}-dev --replicas=0
# 20 workers pound the now-failing API for ~90s, backgrounded so the terminal stays free:
end=$(( $(date +%s) + 90 )); for w in $(seq 1 20); do \
  ( while [ "$(date +%s)" -lt "$end" ]; do curl -s -o /dev/null http://parasol-claims-{user}-dev.{cluster_domain}/api/claims; done ) & \
done
----

*On screen* — while the rule arms, walk the three signals against the live fault:

* *Observe → Metrics* with `sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))` — the error rate climbing off zero. The metric noticed.
* *Observe → Traces*, filtered to the `parasol-claims` service — open a request and read its route and status. The trace located it.
* The application's own logs — a stack trace ending in `Connection refused` from the database driver:

[source,sh,role=execute,subs="attributes+"]
----
oc logs deploy/parasol-claims -n {user}-dev --tail=20
----

*What just happened*

This is the argument for observability in one screen. The metric noticed, the trace located, and the logs explained. The cause was in the logs all along, but nothing read them until the metric moved. Logs confirm the detail once you know where to look; they do not notice, count or page.

=== 3 · The same fault, on a dashboard kept as code — 2 min

While the rule's two-minute window counts down, switch to the *Parasol claims* dashboard. Four panels, one file, applied like any other object.

// UNVERIFIED until Part B: this beat was written offline from the exercise 3 / exercise 4 runs
// (2026-11-14, user13: the 5xx panel read back near 6/s during the outage, every panel query answered 200
// through thanos-tenancy). Re-time it on a cluster; the 2 min is an estimate, not a measurement.

*Why it matters*

A dashboard that lives in a file is reviewed, versioned and re-applied to the next cluster in seconds, instead of being clicked together again by whoever is on call. It also answers the room's first question during an incident — "what are users seeing right now?" — without anyone typing a query.

*On screen* — *Observe → Dashboards (Perses)* → *Parasol claims*: *Server errors (5xx) per second* climbing off its flat zero line, *Requests per second* split by endpoint, *Average latency by endpoint* and *CPU per pod* beside it.

*What just happened*

The panels are four PromQL queries in a `PersesDashboard` object; the console draws them with the viewer's own token through the project's `thanos-tenancy` datasource, so the room sees only `{user}-dev`. The error panel moves within seconds, well before the alert's two-minute window finishes — the dashboard is how you watch a fault, the alert is how nobody has to.

=== 4 · It pages, and the fix takes two steps — 2 min

The rule crosses its threshold and moves to *Firing*. Recovery is two commands rather than one, because a healthy database does not on its own heal an application still holding dead connections to the old one.

image::observability-metrics-traces/observability-metrics-traces-04-alert-firing.png["Project-scoped Alerting rules view for the user's namespace: ParasolClaimsErrorRateHigh now reads 1 Firing with a Warning severity badge, while claims-db is scaled to zero — the same row that showed an empty State at the healthy baseline."]

*Why it matters*

This is where the platform stops needing a human to notice. In production the same transition reaches the on-call rotation, before a customer calls. The two-step recovery is the honest part of the story: the pool of dead connections is a real failure mode, and it is the restart, not the database, that clears it.

*On screen* — the same *Alerting rules* view. `ParasolClaimsErrorRateHigh` has moved off an empty *State*: *Pending* while the two-minute `for:` window counts down, then *Firing*. The *Alerts* tab, empty at the healthy baseline, now carries it.

Then recover:

[source,sh,role=execute,subs="attributes+"]
----
oc scale deploy/claims-db -n {user}-dev --replicas=1
oc rollout restart deploy/parasol-claims -n {user}-dev
----

*What just happened*

Measured on this content: the 5xx rate cleared the rule's `0.1/s` threshold about fifty seconds after the database went away, and the row reached *Firing* about two minutes after that. Going the other way, the rule lingers in *Firing* for roughly five more minutes after recovery, while the burst's 5xx age out of the five-minute rate window — that is the window decaying, not a failed fix.

== Frequently asked questions

*How long does an alert take to fire, and is that tunable?*::
This one took about three minutes: roughly fifty seconds for the five-minute error rate to climb past `0.1/s`, then the rule's `for: 2m` window on top. Both halves are yours to set. The delay is deliberate — it is what stops a two-second blip from paging anybody — and the practical floor is the scrape interval, because an alert can only react to what a scrape captured.

*Why did recovery take two steps rather than one?*::
Bringing the database back does not heal the application's connection pool, which is still full of dead connections pointing at the terminated database pod. The rollout restart is what actually fixes it. That is a real production failure mode rather than a quirk of the demo, and it is the kind of thing a trace makes obvious and a dashboard does not.

*Do developers need cluster-wide access to see their own metrics and alerts?*::
No, and they should not have it. Developers hold project-scoped monitoring rights: *Observe → Metrics* for PromQL and the project-scoped alert-rules view both query with the developer's own identity, restricted to their own namespaces. The cluster-wide alerting page needs a cluster-monitoring grant and is for the platform team. Same data, two audiences, one RBAC model.

*Why does the trace show one span rather than every database query?*::
This build emits the HTTP request span; per-query database spans need a build-time flag on the image. The distinction matters in practice: the trace tells you *which* endpoint is the outlier, and how much of its time is its own rather than a dependency's. Going a level deeper into individual queries is a configuration change, not a re-instrumentation project.
