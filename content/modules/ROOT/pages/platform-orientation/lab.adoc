=== Brief

image::platform-orientation/platform-orientation-03-what-you-built.svg["What the demo builds: a registry image becomes a Deployment whose ReplicaSet keeps three self-healing Pods running behind a Service, published over HTTPS by a Route."]

*From servers to a platform*

A traditional application runs on a server that someone named, patched, and restarted by hand when it failed. A platform changes that contract. You declare what you want — run three copies of this image, reachable at this address — and the platform makes reality match the declaration and keeps it matching, without a person in the loop.

*Desired state and the reconcile loop*

OpenShift is built on Kubernetes. You never operate a running process directly: you describe the application you want, and controllers continuously compare that desired state against what is actually running and close any gap they find. A failed instance is not an incident to page someone about; it is a routine event the platform absorbs.

*What OpenShift adds*

On top of that engine, OpenShift provides what an organisation needs from day one: one console for developers and administrators, built-in HTTPS routing, containers that run without root by default, and an assistant that knows the platform.

*In this demo*

. A developer with only a container image and an empty project
. The image deployed as a running, routed application — no Dockerfile, no build
. Scaled to three replicas by changing one number
. A replica deliberately removed, and replaced without anyone acting
. OpenShift Lightspeed diagnosing a failing pod in plain language

=== 1 · Nothing but a container image — 2 min

Open the web console on an empty project and orient the audience: the single navigation, the Quick create menu, Topology, and the Lightspeed assistant. Nothing is deployed yet.

image::platform-orientation/platform-orientation-04-unified-console-landmarks.png["Unified console landmarks: the Project selector, the masthead Quick create menu, Topology under Workloads, and the Lightspeed chat bubble at the bottom-right."]

*Why it matters*

One console, one navigation. Application and administrative views live in the same place, so there is no perspective to switch and no second tool to learn. The starting point is a developer with a container image and nothing else.

*On screen* — the console at `{user}-dev`, *Topology*, empty.

=== 2 · Deploy from an image — 3 min

Deploy the Parasol web front end straight from a container image in the cluster registry using the console's deploy form, and watch it start in Topology.

image::platform-orientation/platform-orientation-02-deploy-image-dialog.png["The Deploy from container image form: the image reference validated, the name filled in automatically, and Create a route selected under Advanced options."]

*Why it matters*

A container image is the only input. OpenShift derives the Deployment, the Service, and the Route from it — no Dockerfile, no build pipeline, no server request.

*On screen* — masthead *+* → *Container images*, paste the reference below, wait for the green *Validated*, keep *Create a route* selected, and choose *Create*. Switch to Topology as the ring darkens.

[source,text]
----
image-registry.openshift-image-registry.svc:5000/ogsr-parasol-images/parasol-web:1.0
----

*What just happened*

The platform pulled the image, started the container, and health-checked it. The single-command equivalent is `oc new-app --image=<image above> --name=parasol-web`.

=== 3 · Scale to three — 2 min

Scale the running application from one replica to three in Topology, and watch the Pod ring fill.

image::platform-orientation/platform-orientation-01-topology-3pods.png["Topology view: the parasol-web node with a Pod ring showing three of three Pods running."]

*Why it matters*

Scaling is not starting three servers. It is changing one number — the desired replica count — and letting the platform make reality match it.

*On screen* — select the `parasol-web` node and use the up arrow on the Pod ring to reach *3*.

=== 4 · Remove a Pod — 2 min

Delete one of the three running Pods from the terminal while Topology is visible, and watch the platform replace it on its own.

image::platform-orientation/platform-orientation-01-desired-state.svg["Desired state versus actual state: a controller comparing the two and acting on the difference until they agree."]

*Why it matters*

This is the reconcile loop, and it is why the platform can be trusted with production. The desired count is three. When the actual count drops below it, the controller acts — without a person, and without an alert to answer.

[source,sh,role=execute,subs="attributes+"]
----
oc delete "$(oc get pod -l deployment=parasol-web -o name -n {user}-dev | head -1)" -n {user}-dev
----

*What just happened*

One segment left the ring, and a replacement was already starting before the command finished. The Service kept serving throughout.

=== 5 · The cluster has an assistant — 3 min

Ask OpenShift Lightspeed, from inside the console, why a pod keeps restarting, and walk through the diagnosis it returns.

image::platform-orientation/platform-orientation-03-lightspeed-answer.png["OpenShift Lightspeed chat panel showing a diagnosis: an oc top pod command, a step to verify liveness and readiness probes, and a follow-up question."]

*Why it matters*

Diagnosis is where much of operations time goes. Lightspeed sits in the console, understands OpenShift, and answers with the commands to run rather than a link to documentation.

*On screen* — the *Lightspeed* chat bubble at the bottom-right. Ask *"Why is my pod restarting?"* and go through the first two causes it returns.

TIP: If Lightspeed is not installed, the chat bubble is absent. The same information is available from `oc get events` and `oc logs`; Lightspeed's value is interpreting it for you.

== Frequently asked questions

*What is the difference between Kubernetes and OpenShift?*::
Kubernetes is the engine — the object model and the reconcile loop. OpenShift is Kubernetes plus what an organisation needs on day one: a console for developers and administrators, built-in routing, containers that run without root by default, integrated builds, pipelines and GitOps, and Red Hat support.

*Why does a container run as a user ID such as 1001010000?*::
Because it does not run as root. OpenShift assigns a random user ID per project, so an image that assumes root access fails here — and that same image would be a privilege-escalation risk anywhere else.

*Should we use Routes or Ingress?*::
Both work. A Route is OpenShift's own resource and handles TLS termination in a single field; Ingress is the portable Kubernetes resource. The console creates Routes.

*What is an operator?*::
A controller that encodes how to run a piece of software — install, upgrade, recover — as code, so the platform performs those tasks instead of a runbook.

*Does Lightspeed send cluster data outside the cluster?*::
It sends the question, and any context attached to it, to the model endpoint it is configured to use. Whether that model is hosted or runs on the cluster is a deployment choice.

=== What the Deployment decided: update strategy and resources

`oc new-app` made two more choices for you.
First, how Pods are replaced when you ship a change:

[source,sh,role=execute]
----
oc get deployment parasol-web -o jsonpath='{.spec.strategy}{"\n"}'
----

.Expected output
[source,texinfo]
----
{"rollingUpdate":{"maxSurge":"25%","maxUnavailable":"25%"},"type":"RollingUpdate"}
----

*What just happened:* `RollingUpdate` swaps Pods a few at a time, so the Service keeps answering during a change.

.`RollingUpdate` or `Recreate`?
[%collapsible]
====
[cols="2,4,3"]
|===
|Strategy |When the Pod template changes |Right for

|`RollingUpdate` (this app)
|New Pods come up while old ones retire a few at a time — here up to 25% extra, at most 25% unavailable — so the Service keeps answering throughout
|A web front end like this one

|`Recreate`
|Every old Pod stops first, then the new ones start: a short outage, in exchange for never running two versions at once
|An app holding an exclusive lock, or running a one-shot schema migration
|===
====

.Why not just keep the defaults?
[%collapsible]
====
The LimitRange default keeps a forgotten container from running unbounded, but real apps declare their own values, sized to what they use — and this one needs far less headroom than the namespace hands it by default.
You feel *why* these limits matter in *Config, Secrets & Multi-Environment*, where a tight limit and a health probe combine to crash a Pod on purpose.

== 4. Publish the app with a Route
⏱ *~3 min* · make the claims portal reachable from a browser

Adjusters use a browser, but your Service answers only *inside* the cluster.
Publish the portal.

*You'll end with:* the claims portal open in your browser over HTTPS.

[mermaid]
....
include::example$diagrams/platform-orientation/07-route-path.mmd[]
....

[tabs]
====
Console::
+
--
. Open *Networking* → *Routes* and click *Create Route*.
. Name it `parasol-web`, select the `parasol-web` *Service*, and set *Target port* to *8080*.
. Check *Secure Route*, set *TLS termination* to *Edge* and *Insecure traffic* to *Allow*, then click *Create*.
. In *Topology*, click the `parasol-web` node, then the *Open URL* arrow at its top-right.

.No *Create Route* action on the Topology node?
[%collapsible]
=====
In this console version you create a Route from *Networking → Routes* — there is no *Actions → Create Route* item on the Topology node, and a workload with no Route shows "No Routes found for this resource." in its side-panel *Resources* tab.
=====
--
CLI::
+
--
Create an *edge* Route — the router terminates HTTPS and forwards to port 8080:

// `adm start` does NOT clear a leftover Route from a prior pass on this same cluster (only `ws
// reset`/`ws prep` do) — clear it first, safe even on a first run (no-op if absent):
[source,sh,role=execute]
----
oc delete route parasol-web --ignore-not-found=true
oc create route edge parasol-web --service=parasol-web --port=8080 --insecure-policy=Allow
----

[source,sh,role=execute]
----
oc get route parasol-web
----

.Expected output
[source,texinfo,subs="attributes+"]
----
NAME          HOST/PORT                                 PATH   SERVICES      PORT   TERMINATION   WILDCARD
parasol-web   parasol-web-{user}-dev.{cluster_domain}          parasol-web   8080   edge/Allow    None
----

.Why an edge Route (and `--port=8080`)
[%collapsible]
=====
Browsers reach anything on `*.apps` over HTTPS, so a plain HTTP Route lands on the router's "Application is not available" page.
An *edge* Route terminates TLS at the router with the cluster's wildcard certificate, so `https://…` just works; `--insecure-policy=Allow` also answers plain `http://` (instead of redirecting), which keeps the `curl` below simple.
The Service exposes two ports (8080 for HTTP, 8443 for HTTPS), so `--port=8080` picks the HTTP port the router forwards to.
The Route's host is built from the Route name and your project — `parasol-web-{user}-dev.{cluster_domain}` — so it is unique to you; no two attendees collide.
=====
--
====

Open https://parasol-web-{user}-dev.{cluster_domain}/[the claims portal^]: you should see the *Parasol Insurance — Claims Portal* page.
Its seeded claims are served at `/api/claims`:

[source,sh,role=execute,subs="attributes+"]
----
curl -s http://parasol-web-{user}-dev.{cluster_domain}/api/claims | head -c 300
----

.Expected output
[source,texinfo]
----
[{"id":"CLM-1001","policyholder":"Alice Nguyen","type":"Auto","status":"Under Review","amount":4200.0,...}]
----

*What just happened:* the Route told the cluster's router to accept your host name, terminate TLS, and forward to your Service, which spreads requests across the three Pods.

A 503? Wait a few seconds and refresh — the router is still picking up the new Route.

== 7. Ask the cluster: OpenShift Lightspeed
⏱ *~4 min* · get an answer without leaving the console

At 2 a.m., getting from "something is wrong" to "here is the command to run" should take one question, asked where you fix things.

*You'll end with:* an OpenShift-specific answer that names the `oc` commands to run.

.OpenShift Lightspeed answering an operational question
image::platform-orientation/platform-orientation-03-lightspeed-answer.png[alt="OpenShift Lightspeed chat panel scrolled to the tail of its answer: an oc top pod command, the final bulleted item (Verify Liveness/Readiness Probes), a follow-up question offering to investigate further, and one of five source citations"]

*OpenShift Lightspeed* is the console's built-in assistant (not *Developer Lightspeed for Red Hat Developer Hub* or *Developer Lightspeed for the Migration Toolkit for Applications*, which later modules cover).

. Open the *Lightspeed* chat bubble at the bottom-right of the console.
. Ask:
+
[.copy]
`Why is my pod restarting?`
. Expect the usual causes — `CrashLoopBackOff`, `OOMKilled`, a failing liveness probe, `ImagePullBackOff`, node pressure — plus the commands to investigate (`oc get events`, `oc logs`, `oc describe pod`) and links to documentation.
. Ask about *your* app:
+
[.copy]
`How do I see the logs for a deployment called parasol-web?`

*What just happened:* the commands you would otherwise look up came to you, in the console.
Later modules point the same idea at Parasol's *own* applications.

.If Lightspeed is missing or won't answer
[%collapsible]
====
OpenShift Lightspeed is an add-on and may not be installed on every cluster.
If the chat bubble is absent, you get the same answers from the CLI — `oc get events`, `oc logs`, and `oc describe pod <name>` are exactly what the assistant reads on your behalf.
If Lightspeed answers with a permissions error, your user has not been granted query access — ask your instructor (the workshop setup grants it to all attendees automatically).
Nothing else in this workshop depends on Lightspeed being present.
====
