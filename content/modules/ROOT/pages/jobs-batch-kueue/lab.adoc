== When five teams submit at once · 10 min

Parasol's batch tier runs work that finishes, and an admission layer decides whose month-end run starts now, evicts a low-priority job when an urgent one arrives, and treats an AI inference job as exactly the same object.

[IMPORTANT]
.Prep — run before the session
====
This demo runs from the module's *entry* state — a claims dataset in a ConfigMap and an empty queue — not from a finished lab state. Stage it from the cockpit terminal a few minutes ahead:

[source,sh,role=execute]
----
ws prep jobs-batch-kueue
----

*The queue has to be empty at the start.* Your ClusterQueue `cq-{user}` carries `500m` CPU and `512Mi` — room for exactly *two* of the jobs step 2 submits, which is the only reason "two admitted, three pending" is true. Those jobs `sleep 600`, so an earlier run inside the last ten minutes is still holding the whole quota: step 2 would then show *nothing* admitted, and step 3 would have nothing to evict. Check it:

[source,sh,role=execute,subs="attributes+"]
----
oc -n {user}-batch get workloads
----

`No resources found` means the queue is empty and steps 2–3 behave as written. Anything listed is an earlier run still occupying the quota. Clear it, then re-run the read until the Workloads are gone — quota is freed when the Workload object goes, not when the delete is issued:

[source,sh,role=execute,subs="attributes+"]
----
oc -n {user}-batch delete jobs -l kueue.x-k8s.io/queue-name=user-queue
oc -n {user}-batch get workloads
----

*Step 4 calls a model, and that path is per-cluster.* The entry state validates the Models-as-a-Service credential at sync time and writes the verdict down, so read it now rather than discovering it mid-demo:

[source,sh,role=execute,subs="attributes+"]
----
oc -n {user}-batch get cm maas-config -o jsonpath='ai={.data.aiPathAvailable} reason={.data.aiPathReason} model={.data.model}{"\n"}'
----

With `ai=true`, step 4 runs as written: four claims come back `low` / `medium` / `high`.

With `ai=false` or `ai=unverified`, step 4 still works and the difference is worth naming before it lands rather than after. The Job is admitted by the same ClusterQueue and still completes; only the model call fails, so every line prints `fraud-risk: unknown` in place of a verdict — and that is a usable outcome, because the verdict column is the model's job while the point of the step is that the platform never had to care: same object, same label, same admission, same preemption rules. One timing caveat applies to `ai=unverified` specifically, where the endpoint is unreachable from the cluster: each of the four `curl` calls burns its full `--max-time 40`, so the `oc wait` can run most of its 180 seconds. Trim the Job to one claim beforehand if that wait is too long. Do not paste an API key into the Job to rescue the verdicts — the per-user key is model-scoped, and this step does not need it.

CAUTION: Never raise the `nominalQuota` on `cq-{user}` to get more jobs admitted. A *full* queue is the entire lesson: a bigger one means no pending Workloads and no preemption, so raising it deletes the demo in order to save it. The ClusterQueue is also cluster-scoped and shared with the workshop's per-user isolation, so the edit does not stay in one account.

NOTE: To run the demo again, `ws prep jobs-batch-kueue` clears every Job and requeues a clean world (self-service — it wipes and re-prepares your own environment). Deleting the demo jobs with `oc -n $NS delete jobs --all` is enough on its own.
====

=== Brief

image::jobs-batch-kueue/jobs-batch-kueue-02-kueue-admission.svg["Kueue admission in two rows. Top: a Job labelled with a queue name and a priority class is suspended by a webhook, becomes a Workload on the LocalQueue in its own namespace, and reaches the cluster-scoped ClusterQueue holding 500m CPU and 512Mi of quota, which asks whether there is enough room. Bottom: the three answers — admitted and its Pods run, pending and it waits in the queue, or, for a high-priority Job, admitted by preempting a lower-priority Workload, which is evicted and requeued."]

*A Job runs to completion, then stops*

Parasol answers a customer in milliseconds, and separately grinds through every open claim overnight: statements, fraud scoring, actuarial rollups. That second tier is *batch* — a bounded pile of work that runs start to finish and then stops. Nobody waits on a socket; what matters is that it finishes correctly and inside its window.

A Deployment is the wrong object for it, because a Deployment is designed never to end. A *Job* starts one or more Pods, waits until a set number of them succeed, and stops. A *CronJob* starts one on a schedule.

*Why batch needs a referee: admission control*

Plain Jobs share a cluster badly. Nothing arbitrates between them: every Job the scheduler can place, it runs. A namespace quota caps one team's total, but it cannot say "the actuarial month-end run may use spare capacity, and if the fraud team submits something urgent, that goes first". Left alone, the greediest batch wins and everyone else waits — the starvation problem, which at organization scale is a recurring incident rather than a hypothetical.

*Red Hat build of Kueue* is the referee. It sits above the Job controller as an admission layer: a Job opts in with a label, and Kueue holds it suspended until a queue has quota, admits it in priority order, and preempts lower-priority work to make room for urgent work. The same machinery is what stops teams fighting over scarce GPUs, which is why AI batch ends up on it.

*In this demo*

. An overnight statement run as a plain Job — parallel Pods in waves, then it stops
. Five month-end jobs submitted at once, of which the queue admits two and holds three
. An urgent job evicting a running one and taking its slot, with nothing dropped
. An AI inference job going through the same queue as the same kind of object

=== 1 · The overnight statement run — 2 min

Parasol's monthly statement run is an ordinary Job: six segments of the claims dataset, three Pods at a time, and then it is over.

image::jobs-batch-kueue/jobs-batch-kueue-01-async-spectrum.svg["The async spectrum as three linked stages: request-driven work where a Deployment behind a Service holds a waiting caller at low latency, event-driven work where a handler reacts per message in seconds, and — highlighted as this module's subject — batch, where a Job or CronJob runs to completion and then stops."]

*Why it matters*

Every platform conversation starts with request traffic, and most of the compute bill is not request traffic. Giving batch its own object is what makes the overnight tier something the platform can schedule, bound and account for, instead of a server someone remembers to turn off.

[source,sh,role=execute,subs="attributes+"]
----
NS={user}-batch
oc -n $NS apply -f - <<'EOF'
apiVersion: batch/v1
kind: Job
metadata: {name: monthly-statement}
spec:
  parallelism: 3
  completions: 6
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: s
          image: registry.access.redhat.com/ubi9/ubi-minimal:latest
          resources: {requests: {cpu: 100m, memory: 128Mi}}
          command: ["/bin/sh","-c","wc -l < /data/claims.csv; sleep 12"]
          volumeMounts: [{name: data, mountPath: /data}]
      volumes: [{name: data, configMap: {name: claims-data}}]
EOF
oc -n $NS get job monthly-statement -w
----

*What just happened*

`completions: 6` with `parallelism: 3` ran three Pods, waited for them, then ran three more — two waves, `6/6` in about a minute, and the Job stopped there rather than being kept alive.

=== 2 · Five teams submit at once — 2 min

Five month-end jobs arrive at the same instant, each labelled for the queue. Admission control, not the scheduler, decides how many of them actually start.

image::jobs-batch-kueue/jobs-batch-kueue-01-workloads-admitted.png["The Workloads list for the batch project: five rows, one per submitted low-priority Job, all on the queue named user-queue. The first two carry a ClusterQueue name in the Reserved in column and True in the Admitted column; the other three show a dash in both. Nothing has failed and nothing was rejected — there is quota for two, five were asked for, and three are held."]

*Why it matters*

The three held jobs are not errors and nobody had to negotiate for them. The quota is a platform-owned object, so "how much of the cluster may the batch tier use, and who goes first" is answered once, in code, instead of every month in a chat thread.

[source,sh,role=execute,subs="attributes+"]
----
NS={user}-batch
for i in 1 2 3 4 5; do
oc -n $NS apply -f - <<EOF
apiVersion: batch/v1
kind: Job
metadata: {name: batch-low-$i, labels: {kueue.x-k8s.io/queue-name: user-queue, kueue.x-k8s.io/priority-class: batch-low}}
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - {name: w, image: registry.access.redhat.com/ubi9/ubi-minimal:latest, resources: {requests: {cpu: 200m, memory: 256Mi}, limits: {cpu: 200m, memory: 256Mi}}, command: ["/bin/sh","-c","sleep 600"]}
EOF
done
sleep 8
oc -n $NS get workloads -o custom-columns='WORKLOAD:.metadata.name,ADMITTED:.status.conditions[?(@.type=="Admitted")].status'
----

*What just happened*

Two admitted, three pending. The label at *creation* is what put these Jobs under Kueue: a mutating webhook suspended each one and created a Workload for it, and the ClusterQueue then un-suspended as many as its `500m` / `512Mi` would hold. Nobody's month-end run can take the whole cluster.

=== 3 · An urgent job takes a running one's slot — 3 min

The fraud team submits an urgent scoring job into a queue that is already full. Instead of waiting behind the three pending jobs, it evicts a running low-priority one.

image::jobs-batch-kueue/jobs-batch-kueue-02-preempted-conditions.png["The detail page of the low-priority Workload that lost its slot: Reserved in shows a dash and Admitted is False, and the conditions table reads Quota Reserved False (Pending, insufficient unused quota for cpu and memory), Evicted True (Preempted), Admitted False (No Reservation), Preempted True (In Cluster Queue) and Requeued True (Preempted) — the messages saying it was preempted to accommodate another workload due to prioritization in the ClusterQueue, an eviction back into the queue rather than a failure."]

*Why it matters*

This is the part a namespace quota cannot do. Urgent work gets in without an administrator intervening, the displaced work is put back in line rather than dropped, and the policy that decided it is a priority class in a manifest — reviewable, and the same for every team.

[source,sh,role=execute,subs="attributes+"]
----
NS={user}-batch
oc -n $NS apply -f - <<EOF
apiVersion: batch/v1
kind: Job
metadata: {name: batch-high-1, labels: {kueue.x-k8s.io/queue-name: user-queue, kueue.x-k8s.io/priority-class: batch-high}}
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - {name: w, image: registry.access.redhat.com/ubi9/ubi-minimal:latest, resources: {requests: {cpu: 200m, memory: 256Mi}, limits: {cpu: 200m, memory: 256Mi}}, command: ["/bin/sh","-c","sleep 600"]}
EOF
sleep 12
oc -n $NS get workloads -o custom-columns='WORKLOAD:.metadata.name,PRIORITY:.spec.priority,ADMITTED:.status.conditions[?(@.type=="Admitted")].status,PREEMPTED:.status.conditions[?(@.type=="Preempted")].status'
----

*What just happened*

The high-priority Workload is admitted; one low-priority Workload is now `Preempted` and requeued, and Kueue re-admits it as soon as quota frees. A blank `PREEMPTED` column means the read came too early — the condition is written once the eviction has happened, not when the high-priority Job is created. Re-running the same `oc get workloads` line costs nothing; it is a read.

=== 4 · AI batch is the same object — 3 min

A fraud-scoring inference Job carries the same `queue-name` label as the statement run, becomes the same kind of Workload, and is admitted by the same ClusterQueue.

image::jobs-batch-kueue/jobs-batch-kueue-04-what-you-built.svg["What the batch layer ties together: a Job or CronJob with its completions, parallelism, Indexed mode and schedule reaching a LocalQueue through the queue-name label, that LocalQueue pointing at the ClusterQueue that holds quota, priority and preemption, and the queue fanning out to two admitted, three pending and one preempted-then-requeued Workload — with an AI batch-inference job entering the same LocalQueue through the same label."]

*Why it matters*

Everyone asks where AI workloads fit, expecting a separate stack. An inference or evaluation job reads input, calls a model, writes output and stops: it is a Job. The quota, priority and preemption that keep a claims batch fair are what will keep teams from fighting over GPUs — a ResourceFlavor can describe GPU nodes and a ClusterQueue can hold GPU quota, and nothing else about this picture changes.

[source,sh,role=execute,subs="attributes+"]
----
NS={user}-batch
oc -n $NS delete jobs -l kueue.x-k8s.io/queue-name=user-queue --wait=false
oc -n $NS apply -f - <<'EOF'
apiVersion: batch/v1
kind: Job
metadata: {name: fraud-inference, labels: {kueue.x-k8s.io/queue-name: user-queue, kueue.x-k8s.io/priority-class: batch-high}}
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: infer
          image: registry.access.redhat.com/ubi9/ubi:latest
          resources: {requests: {cpu: 200m, memory: 256Mi}, limits: {cpu: 200m, memory: 256Mi}}
          env:
            - {name: TOKEN, valueFrom: {secretKeyRef: {name: maas-credentials, key: GENAI_API_KEY}}}
            - {name: BASE,  valueFrom: {configMapKeyRef: {name: maas-config, key: endpoint}}}
            - {name: MODEL, valueFrom: {configMapKeyRef: {name: maas-config, key: model}}}
          command: ["/bin/sh","-c"]
          args:
            - |
              tail -n +2 /data/claims.csv | head -4 | while IFS=, read -r id c type region amount status; do
                P="/no_think Reply one word (low/medium/high) fraud risk: type=$type amount=$amount status=$status."
                b=$(curl -s --max-time 40 -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
                  -d "{\"model\":\"$MODEL\",\"temperature\":0,\"max_tokens\":24,\"messages\":[{\"role\":\"user\",\"content\":\"$P\"}]}" "$BASE/chat/completions")
                r=$(echo "$b" | sed -n 's/.*"content":"\([^"]*\)".*/\1/p' | grep -oiE 'low|medium|high' | head -1)
                echo "$id -> fraud-risk: ${r:-unknown}"
              done
          volumeMounts: [{name: data, mountPath: /data}]
      volumes: [{name: data, configMap: {name: claims-data}}]
EOF
oc -n $NS wait --for=condition=complete job/fraud-inference --timeout=180s
oc -n $NS logs -l job-name=fraud-inference --prefix=false | grep fraud-risk
----

*What just happened*

Same label, same LocalQueue, same ClusterQueue, same admission and the same preemption rules — one risk verdict per claim, and then the Job stopped. *AI batch is just batch.*

== Frequently asked questions

*Why Kueue at all — isn't a ResourceQuota enough?*::
A `ResourceQuota` caps one namespace: this team may use at most X. It cannot arbitrate between teams or express priority — there is no way to say "hold this job until there is room, and if an urgent job arrives, evict a lower-priority one". Kueue adds exactly that. You want both: quotas stop one team over-committing, Kueue makes many teams share fairly under contention.

*Why exactly two admitted, and not three?*::
Arithmetic against the ClusterQueue quota of `500m` CPU and `512Mi` memory. Each of these Jobs requests `200m` and `256Mi`, so two fit and a third would need `600m` and `768Mi` — over on both, with memory the tighter bound. Change the requests and the admitted count changes; that is the knob a platform team turns.

*The preempted job — did it lose its work?*::
The Workload is not lost: it is evicted, requeued, and re-admitted when quota frees. The Pod is killed, though, and starts from scratch on re-admission. That is the honest constraint on preemptible batch — it has to be idempotent and restartable, with checkpoints for long work. Preemption trades a restart for fairness.

*Does every Job get queued, or does a team opt in?*::
Opt in, twice over, and both are deliberate. The namespace carries `kueue.openshift.io/managed`, so the admission webhooks only touch projects the platform team enrolled; and the Job carries the `kueue.x-k8s.io/queue-name` label at creation, because Kueue suspends it through a creation webhook. Adding the label to a Job that is already running does nothing.

*This inference job is a shell script calling curl — where is the ML infrastructure?*::
That is the point. A batch-inference or evaluation job is an ordinary Job: it reads input, calls a model, writes output, and stops. OpenShift AI's distributed-workloads stack adds richer integrations — RayJob, PyTorchJob, JobSet — and GPU-aware ResourceFlavors, but the admission layer is identical: the same ClusterQueue, priorities and preemption used here. The control plane is what transfers, and it is the one that governs GPUs.

Create a Job that reads the wrong input file:

[source,sh,role=execute]

        - name: statement
          image: registry.access.redhat.com/ubi9/ubi-minimal:latest
          resources: {requests: {cpu: 100m, memory: 128Mi}, limits: {cpu: 300m, memory: 256Mi}}
          command: ["/bin/sh","-c"]

Read the events and the Pods:

A *CronJob* creates a Job on a cron schedule. Three fields keep it safe:

[cols="2,1,3"]
|===
|Field |Here |Prevents

Submit the inference Job, two Indexed workers at `temperature 0`; its `kueue.x-k8s.io/queue-name` label sends it through *the same LocalQueue as everything else*:

[source,sh,role=execute]
----
oc -n $NS apply -f - <<'EOF'
apiVersion: batch/v1
kind: Job
metadata:
  name: fraud-inference
  labels:
    kueue.x-k8s.io/queue-name: user-queue        # admission-controlled, same as any batch
    kueue.x-k8s.io/priority-class: batch-high
spec:
  completionMode: Indexed
  completions: 2
  parallelism: 2
  backoffLimit: 2
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: infer
          image: registry.access.redhat.com/ubi9/ubi:latest
          resources: {requests: {cpu: 200m, memory: 256Mi}, limits: {cpu: 200m, memory: 256Mi}}
          env:
            - {name: TOKEN, valueFrom: {secretKeyRef: {name: maas-credentials, key: GENAI_API_KEY}}}
            - {name: BASE,  valueFrom: {configMapKeyRef: {name: maas-config, key: endpoint}}}
            - {name: MODEL, valueFrom: {configMapKeyRef: {name: maas-config, key: model}}}
          command: ["/bin/sh","-c"]
          args:
            - |
              set -eu
              DATA=/data/claims.csv
              IDX="${JOB_COMPLETION_INDEX}"
              tail -n +2 "$DATA" | awk -v idx="$IDX" 'NR%2==idx' | head -3 | while IFS=, read -r id claimant type region amount status; do
                P="/no_think You are a fraud-triage assistant. Reply with exactly one word (low, medium, or high) for the fraud risk of this claim: type=${type} region=${region} amount=${amount} status=${status}."
                body=$(curl -s --max-time 40 -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
                  -d "{\"model\":\"$MODEL\",\"temperature\":0,\"max_tokens\":24,\"messages\":[{\"role\":\"user\",\"content\":\"$P\"}]}" \
                  "$BASE/chat/completions") || body=""
                risk=$(echo "$body" | sed -n 's/.*"content":"\([^"]*\)".*/\1/p' | grep -oiE 'low|medium|high' | head -1)
                echo "${id} (${type}/${amount}) -> fraud-risk: ${risk:-unknown}"
              done
              echo "worker ${IDX} done"
          volumeMounts: [{name: data, mountPath: /data}]
      volumes:
        - name: data
          configMap: {name: claims-data}
EOF
# 180s, not 120s: a worker's model-call budget is 3 claims x 40s --max-time — on a dead endpoint
# it can legitimately spend ~120s before finishing, and the wait must outlast that worst case.
oc -n $NS wait --for=condition=complete job/fraud-inference --timeout=180s

.What `temperature 0` does, and does not, promise
[%collapsible]
====
`temperature 0` makes the model take the highest-probability token every time, and so removes the *deliberate* randomness.
Treat that as reducing variation, not eliminating it: `temperature 0` is not a guarantee of identical output, and this workshop has measured the same prompt return different results at that setting.
Here it is enough: you are watching how Kueue admits and runs the work, not grading what the model says.
====

It finishes in well under a minute when the model answers.
Read the verdicts:

[source,sh,role=execute]
----
oc -n $NS logs -l job-name=fraud-inference --prefix=false | grep fraud-risk | sort
----

.Every row reads `fraud-risk: unknown`?
[%collapsible]
====
The *model endpoint* failed: an expired or mis-scoped key returns `401`, or the call timed out (only a dead endpoint pushes the Job toward its timeout).
The Job still runs to *Complete* by design, because a worker degrades to `unknown` rather than crashing.
A green `oc wait` therefore proves the *scheduling*, not the model: see the `401` entry on xref:jobs-batch-kueue/troubleshooting.adoc[the troubleshooting page] for the fix.
====

.Every claim came back `medium`?
[%collapsible]
====
A small instruct model at `temperature: 0`, given this deliberately terse prompt, tends to return the same cautious `medium` for every claim; that uniformity is *expected, not a bug*.
This module's point is not verdict nuance: it is that the inference Job was *admitted and governed by Kueue exactly like every other batch*, which you confirm next.
Sharper, differentiated risk tiers would need a richer prompt or a stronger model, orthogonal to the scheduling lesson here.
