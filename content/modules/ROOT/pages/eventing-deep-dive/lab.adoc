A claim event is dropped into a broker, filters decide which consumers receive it, and a consumer that fails every delivery ends with the event kept rather than lost.

=== Brief

image::eventing-deep-dive/eventing-deep-dive-01-eventing-model.svg["The four Knative Eventing primitives on one path: a producer POSTing a CloudEvent and a seeded PingSource both feeding an in-memory Broker, three Triggers filtering it independently — a catch-all, one on event type, one on claim priority — and two sinks, the claims-consumer that displays each event and the claims-dlq dead-letter sink."]

*A direct call welds the caller to the callee*

When Parasol's claims service accepts a claim, four things must react: fraud scoring, an audit record, a customer notification, an investigations referral. Calling each of them directly means the claims service knows all four — their addresses, their APIs, their health — and waits on every one. A slow fraud service makes claim submission slow, and a fifth listener is a code change and a redeployment of the producer.

*The producer states a fact instead*

An event inverts that. The claims service states what happened — `com.parasol.claim.submitted`, with the claim attached — into a *broker*, and returns. Consumers *subscribe*: each declares, through a *trigger*, which events it wants, matched on the attributes of the CloudEvents envelope rather than on anything inside the payload. A new consumer is a new trigger, with no change to the producer.

*Four primitives, all ordinary Kubernetes objects*

A *source* emits events; a *broker* receives them and holds them for routing; a *trigger* is a subscription with a filter that names its sink; a *sink* is anything addressable — here Knative Services that scale up from zero when an event arrives. Red Hat OpenShift Serverless provides all four, so the routing of events is configuration rather than code.

*In this demo*

. One CloudEvent posted to the broker, routed by a trigger, and a consumer waking from zero to display the envelope
. Two events and two filters, showing that routing is decided in the trigger rather than in anyone's code
. A consumer that fails every delivery, its retries, and the dead-letter sink that keeps the event together with the reason it died

=== 1 · One POST, and a consumer wakes — 4 min

Parasol's claim events land in a broker rather than at a consumer's door. Send one CloudEvent to the broker's address and watch a trigger route it to `claims-consumer`, which is scaled to zero until the event arrives.

image::eventing-deep-dive/eventing-deep-dive-01-event-display-envelope.png["The claims-consumer event-display page in a browser: under Collected CloudEvents, one event card showing id direct-1, source /demo/direct, type com.parasol.claim.submitted, content type application/json, and the claim data claimId CLM-9001, amount 7300 and fraudScore 0.91."]

*Why it matters*

The producer addresses the broker and nothing else. It never learns that a consumer exists, how many there are, or whether any of them is running — which is what makes the fifth consumer free to add, and what keeps a slow consumer out of the claim-submission path.

[source,sh,role=execute,subs="attributes+"]
----
NS={user}-dev
BROKER=$(oc get broker default -n $NS -o jsonpath='{.status.address.url}')
oc exec deploy/demo-client -n $NS -- sh -c 'curl -s -k -m 30 -o /dev/null -w "claim -> broker: HTTP %\{http_code} in %\{time_total}s\n" \
  -X POST -H "Ce-Id: claim-9001" -H "Ce-Specversion: 1.0" -H "Ce-Type: com.parasol.claim.submitted" \
  -H "Ce-Source: /demo/claims" -H "Content-Type: application/json" \
  -d "{\"claimId\":\"CLM-9001\",\"amount\":7300,\"fraudScore\":0.91}" "'$BROKER'"'
----

*On screen* — the `claims-consumer` event-display page: a new `☁️ cloudevents.Event` card carrying the event's `type`, `source` and the claim `Data`.

*What just happened*

`202` is the broker accepting the event. The default in-memory broker delivers synchronously, so that `202` comes back only once the trigger has completed delivery — which is why a POST to a consumer sitting at zero replicas takes about fourteen seconds the first time, and well under a second once the consumer is up.

=== 2 · Filters decide which consumers see an event — 4 min

Two events go into the same broker: a `claim.submitted` and an unrelated `claim.rejected`. The catch-all trigger takes both; the fraud-review trigger filters on `type`, so only one of them is its concern. The delivery count in the consumer's log is that filter at work.

*Why it matters*

Routing lives in the trigger, which is a small Kubernetes object. Sending fraud scoring a new class of event, or adding an analytics consumer that only wants high-value claims, is an edit to that object — no producer change, no consumer change, nothing redeployed.

[source,sh,role=execute,subs="attributes+"]
----
NS={user}-dev
BROKER=$(oc get broker default -n $NS -o jsonpath='{.status.address.url}')
# the staged fraud-review Trigger filters on the seeded PingSource's own type; align it to the
# CloudEvent type this step sends — the same filter exercise 4 builds by hand:
oc patch trigger claims-fraud-review -n $NS --type=merge -p '{"spec":{"filter":{"attributes":{"type":"com.parasol.claim.submitted"}}}}'
kn trigger list -n $NS
for kind in "cnt-submitted:com.parasol.claim.submitted" "cnt-rejected:com.parasol.claim.rejected"; do
  id=${kind%%:*}; typ=${kind#*:}
  oc exec deploy/demo-client -n $NS -- sh -c "curl -s -k -m 20 -o /dev/null -w '$id: HTTP %\{http_code}\n' \
    -X POST -H 'Ce-Id: $id' -H 'Ce-Specversion: 1.0' -H 'Ce-Type: $typ' \
    -H 'Ce-Source: /demo/claims' -H 'Content-Type: application/json' -d '{\"claimId\":\"$id\"}' '$BROKER'"
done
sleep 5
for id in cnt-submitted cnt-rejected; do
  echo "$id displayed: $(oc logs deploy/claims-consumer-v1-deployment -c showcase -n $NS --tail=200 | grep -c "id: $id")x"
done
----

*What just happened*

Both events were accepted with a `202` — the broker takes everything. `cnt-submitted` is displayed twice, once by the catch-all trigger and once by fraud-review; `cnt-rejected` once, by the catch-all alone. The extra delivery is fraud-review's filter matching, and the delivery that is missing is a non-matching event being dropped by that trigger — not an error, simply not its concern.

=== 3 · A failing consumer: retry, then dead-letter — 4 min

Point the fraud-review trigger at a path the consumer does not serve, so every delivery attempt comes back `404`. Knative retries with exponential backoff, and when the retries are exhausted it dead-letters the event to a separate sink instead of dropping it.

image::eventing-deep-dive/eventing-deep-dive-02-dead-letter-event.png["A terminal: the POST of a failing claim event returns HTTP 202 after 35 seconds, and the claims-dlq log below it prints the dead event — id dead-99, type com.parasol.claim.submitted — with the extension attributes knativeerrorcode 404, knativeerrordest naming the /process path on claims-consumer, and knativearrivaltime, followed by the original claim data intact."]

*Why it matters*

Consumers fail. The question a platform has to answer is what happens to the event when one does, and the answer here is written on the trigger rather than in the producer: retry a few times, then hand the event to a sink that records it. Nothing is silently lost, and the record says why.

// attributes+ APPENDS: plain subs="attributes" drops HTML escaping, and the browser swallowed <EOF as a tag.
[source,sh,role=execute,subs="attributes+"]
----
NS={user}-dev
BROKER=$(oc get broker default -n $NS -o jsonpath='{.status.address.url}')
# repoint fraud-review's delivery at a path the consumer 404s, keeping retries + the dead-letter sink:
oc apply -n $NS -f - <<EOF
apiVersion: eventing.knative.dev/v1
kind: Trigger
metadata:
  name: claims-fraud-review
spec:
  broker: default
  filter: { attributes: { type: com.parasol.claim.submitted } }
  subscriber: { uri: http://claims-consumer.$NS.svc.cluster.local/process }
  delivery:
    retry: 3
    backoffPolicy: exponential
    backoffDelay: PT1S
    deadLetterSink: { ref: { apiVersion: serving.knative.dev/v1, kind: Service, name: claims-dlq } }
EOF
oc exec deploy/demo-client -n $NS -- sh -c 'curl -s -k -m 90 -o /dev/null -w "fails -> retries -> DLQ: HTTP %\{http_code} in %\{time_total}s\n" \
  -X POST -H "Ce-Id: dead-99" -H "Ce-Specversion: 1.0" -H "Ce-Type: com.parasol.claim.submitted" \
  -H "Ce-Source: /demo/claims" -H "Content-Type: application/json" -d "{\"claimId\":\"CLM-DEAD-99\"}" "'$BROKER'"'
oc logs deploy/claims-dlq-v1-deployment -c showcase -n $NS --tail=200 | grep -iE 'id:|knativeerror'
----

*On screen* — the `claims-dlq` event-display page now holds the dead event, alongside the healthy ones on the consumer's page.

*What just happened*

The elapsed time is one attempt plus three retries, backing off one, two and four seconds — around eight seconds against a warm consumer, longer if it had to wake up first. Every attempt failed, so the event was delivered to `claims-dlq` and stamped with `knativeerrorcode: 404` and the destination that kept failing. The original claim is intact beneath those attributes, which is what makes a dead-letter sink a diagnosable record rather than a black hole.

== Frequently asked questions

*The first POST took about fourteen seconds — is the broker slow?*::
That is the consumer's cold start, and it sits on the delivery path. The default in-memory broker delivers synchronously, so the `202` returns only once the trigger has finished delivering, and a consumer scaled to zero has to start first. Warm, the same POST is sub-second. A Kafka-backed broker removes even that, by buffering the event so the producer never waits on the consumer.

*An event returned `202` but never reached one of the consumers — did it fail?*::
No. `202` means the broker accepted it. Whether a particular trigger delivers it depends on that trigger's filter, and a non-matching event is dropped by that trigger by design. Only a trigger with no filter, or one whose filter matches, delivers — so an event reaching one consumer and not another is the routing working, not a delivery failure.

*Where do `knativeerrorcode` and `knativeerrordest` come from?*::
Knative stamps them onto a dead-lettered event: the last status the subscriber returned, the destination that kept failing, and any error body it sent. That is the whole difference between a dead-letter sink and dropping the event — what arrives is diagnosable. Here the `404` is deliberate; in production it is more often a `503` from an overwhelmed service.

*Why is the retry and dead-letter trigger written as YAML rather than with the `kn` CLI?*::
`kn trigger create` covers filters and sinks, but not the `delivery` spec, where retries, backoff and the dead-letter sink live. Those are set as YAML through `oc apply` or in the web console's trigger editor. The filtering triggers need none of that and are ordinary `kn`.

*Is this real eventing, or a toy — the source is a ping?*::
The source is deliberately a seeded `PingSource`, because the claims application does not emit CloudEvents yet; giving it an emit handler is application work rather than platform work. Everything downstream is real: the broker, the attribute-filtered triggers, a consumer that validates and displays each envelope, the retries, and a dead-letter sink with real error attributes. Making the application emit `com.parasol.claim.submitted` and repointing the triggers at it is the one remaining step, and nothing else changes.

.Why the wait varies, and what `1` means
[%collapsible]
====

.Why the in-memory broker is synchronous, and why the Kafka broker exists
[%collapsible]
====
The default `MTChannelBasedBroker` is backed by an *in-memory channel*, and it delivers *synchronously*: your POST's `202` comes back only after the trigger *completes* delivery. When the consumer is scaled to zero, that means waiting for its cold start (~10-23 s or more here) — the same JVM cold start from Serverless, now paid on the delivery path. Warm, it's sub-second.

== 5. Survive a failing consumer — retries and a dead-letter sink
⏱ *~9 min* · add delivery guarantees, break the consumer, and catch the dead events

Fraud scoring will fail one day, and Parasol cannot afford to lose a claim event when it does.

*You'll end with:* a failed claim event caught in `claims-dlq`, stamped with why it died.

image::eventing-deep-dive/eventing-deep-dive-02-dead-letter-event.png["The terminal showing the failing claim POST returning HTTP 202 after 35 seconds, then the claims-dlq log for the dead event: id dead-99, source /demo/fraud, type com.parasol.claim.submitted, an Extensions block carrying knativeerrorcode 404 and knativeerrordest pointing at the /process path that kept failing, and the claim Data. Notice the error code and destination — the event was not dropped, it was dead-lettered with a record of why."]

By default a failed delivery is *retried a few times and then dropped*. Give `claims-fraud-review` a `delivery` spec instead: *retry three times* with exponential backoff, then *dead-letter* to `claims-dlq`.
Delivery guarantees aren't a `kn trigger` flag, so the trigger is applied as YAML, deleted and recreated first.

.Why delete and recreate the trigger?
[%collapsible]
====
`kn trigger create` set the subscriber as a `ref`, and this YAML uses a `uri`. A subscriber is `ref` *or* `uri`, never both, and `oc apply` would *merge* the two forms (the webhook then rejects it). Deleting and recreating the trigger switches it cleanly.
====

[tabs]
====
Console::
+
--
In *Serverless → Eventing → Triggers*, edit `claims-fraud-review` (or the masthead *Quick create* (+) menu → *Import YAML*) and set its `spec.delivery`: `retry: 3`, `backoffPolicy: exponential`, `backoffDelay: PT1S`, and a `deadLetterSink` referencing the `claims-dlq` service — the manifest is in the *CLI* tab.

// media-pass: screenshot eventing-deep-dive-04-trigger-filter-edit.png — Console -> Serverless ->
// Eventing -> Trigger editor (or masthead + (Quick create) -> Import YAML) showing a Trigger's
// filter.attributes and a delivery block with deadLetterSink. Circle: the deadLetterSink + retry
// fields. See media-manifest.md.
--
CLI::
+
--
[source,sh,role=execute]
----
# The kn-created trigger set subscriber.ref; recreating it lets this YAML use a single subscriber.uri
# (oc apply over the existing ref would keep BOTH forms -> "Absolute URI is not allowed when Ref is present"):
oc delete trigger claims-fraud-review -n $NS
oc apply -n $NS -f - <<EOF
apiVersion: eventing.knative.dev/v1
kind: Trigger
metadata:
  name: claims-fraud-review
spec:
  broker: default
  filter:
    attributes:
      type: com.parasol.claim.submitted
  subscriber:
    uri: http://claims-consumer.$NS.svc.cluster.local     # the working consumer
  delivery:
    retry: 3                       # try 3 more times before giving up
    backoffPolicy: exponential     # 1s, 2s, 4s between tries
    backoffDelay: PT1S
    deadLetterSink:                # where exhausted events go instead of being dropped
      ref:
        apiVersion: serving.knative.dev/v1
        kind: Service
        name: claims-dlq
EOF
----

Parasol's architects now ask the production questions: which primitive, which broker backing, and does a claims approval need a conductor?

*You'll end with:* a scheduled tick seen arriving on its own, and a decision for each of the three choices. This exercise is *reading and one observation*, with no new graded wiring.

*What just happened:* that is the *whole loop* running unattended: a scheduled source → the broker → a filtered trigger → the consumer displaying the event.

.Every tick is displayed twice — that is exercise 4's lesson again
[%collapsible]
====
Since exercise 4, each `claim-ticker` tick matches *two* triggers: the catch-all `claims-events`, and `claims-audit`, because the tick carries `claimpriority: high`. The consumer displays an event once per matching trigger, so the log holds every tick twice, with the same `knativearrivaltime`.
That is why the read ends in `tail -11`: it keeps only the *newest* ping-typed event, however many ticks and duplicates the log holds.
The `knativearrivaltime` says when it arrived, and the `note` says who sent it — the seeded ticker's reads `seeded claim event …`, the self-ping below reads `self-sent ping-shaped event`.
====

[IMPORTANT]
.If the log is empty, do NOT just wait — waiting is what loses it
====
`claims-consumer` scales to zero roughly 60-90 seconds after it goes idle, and *the pod holding the log goes with it*.
A tick is readable for under 90 seconds out of every 300, so by the time the next tick wakes the consumer, it wakes a *brand-new pod with an empty log*, and the tick you were waiting for is gone for good.
Re-sending an event to wake it does not help either: it is a new pod (measured: send, let it scale to zero, re-send, and only the second event is in the log).
You have two honest options.

*Send a ping-shaped event yourself* — deterministic and immediate, and it exercises exactly the same trigger route the real ticker uses:

Now the decisions you take back to your own systems:

[cols="2,3,3,3",options="header"]
|===
| Decision | What this lab used | The alternative | Reach for the alternative when
| *Broker vs Channel* | *Broker + Triggers*: fan-out, with a filter per subscriber | *Channel + Subscriptions*: a linear pipe, no per-subscriber filter | You need an *ordered processing pipeline*, not fan-out
| *In-memory vs Kafka* `[ADD-ON]` | *In-memory* broker: free with Serverless, synchronous, *not durable* | *Kafka-backed* broker: durable, replayable, ordered; a *separate subscription* | You *cannot lose* the event
| *Choreography vs orchestration* `[ADD-ON]` | *Choreography*: each consumer reacts on its own, no conductor | *Orchestration*: a SonataFlow *workflow* conducts the process | A process has branches, retries across steps, and timeouts
|===

.Broker vs Channel, and in-memory vs Kafka, in more detail
[%collapsible]
====
*Broker vs Channel.* You used a *Broker + Triggers* — the right tool for *distributing events to many consumers with filtering*. Knative's other primitive, a *Channel + Subscriptions*, is a *linear pipe* with no per-subscriber filter — reach for it for an *ordered processing pipeline*, not fan-out. A broker is built *on* a channel, so this is a choice of the abstraction you program against.

*In-memory vs Kafka `[ADD-ON]`.* Your broker is *in-memory*: free with Serverless, synchronous, and *not durable* (events are lost if the broker restarts) — perfect for dev and best-effort internal events. For events you *cannot lose*, the *Kafka-backed broker* (from *Streams for Apache Kafka* {streams_kafka_version}, a *separate subscription*) adds durability, replay, and ordering.

[cols="1,2,2",options="header"]
|===
| | *In-memory broker* (this lab) | *Kafka broker* `[ADD-ON]`
| Durability | None — lost on restart | Persistent — survives restarts
| Replay | No | Yes
| Reach for it when | Dev, demos, best-effort events | Events you can't lose; replay/audit; high throughput
|===
====

.`[ADD-ON]` — the Kafka path (only if you own a Streams subscription)
[%collapsible]
====
Swapping to a Kafka broker is a broker-class change, not an app change: create a `KnativeKafka` custom resource (enabling the Kafka broker), then create a broker with the Kafka broker class instead of the in-memory default. Your *triggers, filters, and consumers are unchanged* — that's the point of the broker abstraction. The durable, replayable Kafka path adds a topic per broker, a `Topic` custom resource for direct produce/consume, and lag-based autoscaling (KEDA) for consumers. It requires the Streams subscription, so it's entirely optional and never on the default path.
====

.Choreography vs orchestration — workflows with SonataFlow `[ADD-ON]`
[%collapsible]
====
Everything you built is *choreography*: each consumer reacts to events on its own, with no conductor. That's beautifully decoupled and *hard to reason about* once a business process has branches, retries across steps, and timeouts. *Orchestration* adds a conductor: *OpenShift Serverless Logic* {serverless_logic_version} (a *SonataFlow* runtime on Knative) runs a declarative *workflow* — a Parasol claims-approval flow would auto-approve below a threshold, route the rest to review, and take a *timeout* branch if review is slow — with a queryable instance per claim.
====

.Why SonataFlow is a concept here, not a graded step
[%collapsible]
====

// OpenShift Serverless 1.33)". Removed 2026-07-31 for consistency with concept.adoc (same
// removal made there the same day): versions.yaml, this project's single source of truth for

OpenShift Serverless Logic ships with a console, a `kn-workflow` CLI, and a VS Code extension. It's presented here as a *concept and `[ADD-ON]`* for one honest reason: a per-user SonataFlow platform (the workflow runtime *plus its own state database*) is significant footprint for every seat, and the graded core of this module is the *eventing* substrate. The decision is what matters and travels with you: *choreography* (triggers) for decoupled fan-out; *orchestration* (SonataFlow) when a *process* needs a conductor that can branch, call services, and time out. The wrap-up's decision guide places it against Pipelines (Pipelines Fundamentals) and Jobs (Jobs, Batch & Queued Workloads).

== Challenge (optional)
⏱ *no hand-holding*

You have the mechanics. Try these on your own:

* *Route to two different sinks.* Repoint `claims-audit` at `claims-dlq` (as a stand-in "audit sink") instead of `claims-consumer`, send a high-priority and a normal claim, and confirm *only* the high-priority one reaches the audit sink — real fan-out to *distinct* consumers.
* *Tune the retry policy.* Change the `delivery` policy on `claims-fraud-review` to `retry: 5` with `backoffDelay: PT0.5S`, break the consumer again, and reason about the total time before dead-letter from the backoff series — then decide what retry budget a real fraud path should have.
* *Make the drop visible.* Delete the catch-all `claims-events` trigger, send a `claim.rejected` event, and confirm the consumer *never* sees it (no trigger matches) — then recreate `claims-events` so your world matches the module's end state.
* *Argue the broker backing.* In two sentences, decide in-memory vs Kafka for (a) a "claim viewed" analytics event and (b) a "payment authorized" event — and defend each on durability.

When you are done, run `ws verify {module-id}` in the Terminal — or run `ws prep {module-id} --yes` to return your world to the entry state (the baseline Trigger only, no filtered or dead-letter Triggers).
