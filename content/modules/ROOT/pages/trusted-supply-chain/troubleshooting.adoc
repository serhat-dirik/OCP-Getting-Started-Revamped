== `verify-conforma` fails: no signature or attestation found

Symptom:: The run stops at `verify-conforma`, and its log reads `No Chains attestation after …s; Conforma reports what is missing.`, then `✕ [Violation] builtin.image.signature_check` (`Image signature check failed: no signatures found`), `✕ [Violation] builtin.attestation.signature_check` (`no matching attestations`) and `CONFORMA POLICY VIOLATED: … must not be deployed`; `deploy` never runs.
Cause:: Tekton Chains did not sign the image, or signed it as an identity the check does not expect. Chains signs from outside the pipeline, a few seconds after `build-image` finishes; if it is down, or cannot get its SPIFFE token or a Fulcio certificate, nothing is signed.
Fix:: Check whether Chains marked the build:
+
[source,sh,role=execute]
----
PR=$(oc get pipelinerun -n $NS --sort-by=.metadata.creationTimestamp -o name | tail -1 | cut -d/ -f2)
oc get taskrun -n $NS -l tekton.dev/pipelineRun=$PR,tekton.dev/pipelineTask=build-image \
  -o jsonpath='{.items[0].metadata.annotations.chains\.tekton\.dev/signed}{"\n"}'
----
+
`true` means Chains signed: read the rest of the `verify-conforma` log for which rule failed (next entry). Empty or `failed` means Chains did not: tell your instructor, who reads the controller's log (`oc logs -n openshift-pipelines deploy/tekton-chains-controller --since=10m | grep -iE 'error|fulcio|spiffe'`) and checks `oc get tektonconfig config -o jsonpath='{.spec.chain}'`. Once Chains is healthy, start the pipeline again.

== `verify-conforma` fails on a policy rule

Symptom:: The signatures verify, but `ec` reports a violation: `parasol.built_by_expected_task` ("No Tekton Chains provenance from task build-image of pipeline parasol-claims-trusted-build") or `parasol.image_pinned_by_digest` ("Image reference is not pinned by digest").
Cause::
* *Built by the expected pipeline:* the provenance must name `build-image` of `parasol-claims-trusted-build`. A copy of the pipeline under another name, or a renamed task, fails it on purpose.
* *Pinned by digest:* the image must be checked as `…@sha256:…`, never by tag.
Fix:: Run the pipeline as shipped (`ws prep {module-id} --yes` restores it). When you run `ec validate image` by hand, pass the image *with* its digest, as the lab's `$IMG` does.

== `verify-conforma` times out waiting for Chains

Symptom:: `verify-conforma` waits, then fails with a timeout while the `build-image` TaskRun is still not annotated `chains.tekton.dev/signed`.
Cause:: Chains signs asynchronously; under load, or right after a controller restart, it can lag behind the run.
Fix:: Wait for the annotation to appear (command above), then start the pipeline again.

== The SBOM's hash does not match the signed provenance

Symptom:: In exercise 3, the sha256 of `~/sbom.json` differs from the `SBOM_SHA256` read from the provenance.
Cause:: ConfigMap `parasol-claims-sbom` holds the SBOM of the *last* run, and `sbom` runs beside `scan`, so even a failed run (the challenge's vulnerable branch) replaces it. The running image's provenance still names its own SBOM.
Fix:: Check which image the stored SBOM belongs to, then start the pipeline on `main` again and repeat the check:
+
[source,sh,role=execute]
----
oc get configmap parasol-claims-sbom -n $NS -o jsonpath='{.metadata.annotations.workshop\.redhat\.com/image-digest}{"\n"}'
----

== The admission webhook refuses the pipeline's own image

Symptom:: The `deploy` step, or `oc run` with the pipeline's digest, is denied: `admission webhook "policy.rhtas.com" denied the request: validation failed: failed policy: ogsr-parasol-claims-keyless: …`, although Conforma passed.
Cause:: The policy controller could not confirm Chains' signature for that digest: it could not read the image's signature from the internal registry, its trust root (from TUF) is out of date, or the policy's expected identity or issuer differs from what Chains signed with.
Fix:: Compare what the image carries with what the policy expects:
+
[source,sh,role=execute]
----
cosign verify --certificate-identity "$SIGNER" --certificate-oidc-issuer "$ISSUER" \
  --allow-insecure-registry "$IMG" 2>&1 | tail -1
oc get clusterimagepolicies.policy.sigstore.dev -o yaml | grep -E 'subject|issuer'
----
+
If `cosign verify` succeeds and the policy names the same subject and issuer, the policy controller cannot reach the registry or its trust root: tell your instructor (`oc get pods -A | grep policy-controller`, then that pod's log).

== The out-of-chain image is admitted

Symptom:: In exercise 4, `oc run claims-unsigned` creates a pod instead of being refused.
Cause:: The webhook does not enforce on your project, or the policy does not name the image. It enforces only in namespaces labelled `policy.rhtas.com/include=true`, and only for images a `ClusterImagePolicy` names (here, the `parasol-claims-secure` repository); everything else is admitted (`no-match-policy=allow`).
Fix:: Check both:
+
[source,sh,role=execute]
----
oc get namespace $NS -o jsonpath='{.metadata.labels.policy\.rhtas\.com/include}{"\n"}'
oc get pod claims-unsigned -n $NS -o jsonpath='{.spec.containers[0].image}{"\n"}'
----
+
Expect `true`, and an image in `…/{user}-cicd/parasol-claims-secure`. If the label is missing, `ws prep {module-id} --yes` restores it; if the image is elsewhere, you tagged it into another repository.

== `oc get clusterimagepolicy` shows a different policy

Symptom:: `oc get clusterimagepolicy` lists `ogsr-signed-parasol-claims` or nothing, not the policy the lab describes.
Cause:: Two kinds share the name: `ClusterImagePolicy` in `config.openshift.io` (a node-level pull policy) and in `policy.sigstore.dev` (the policy controller's). A bare name picks one of them.
Fix:: Name the group: `oc get clusterimagepolicies.policy.sigstore.dev`.

== `cosign verify` says `signature not found in transparency log`

Symptom:: `cosign verify` on the pipeline's image fails with `no matching signatures: signature not found in transparency log`.
Cause:: cosign looked the signature up in the public Rekor, not this cluster's: the command lost its `--rekor-url`, or `$REKOR` is empty after a reconnect.
Fix:: `source ~/m12.env`, then run the lab's command as written, with `--rekor-url "$REKOR"`.

== `oc new-build` prints `--> Failed` with an ImageStreamTag error

Symptom:: The out-of-chain build prints `error: ImageStreamTag.image.openshift.io "parasol-claims-secure:unsigned" is invalid: … not allowed by whitelist …` and `--> Failed`.
Cause:: Without `--to-docker`, `oc new-build` tries to create an ImageStreamTag in the image stream the pipeline already pushed to.
Fix:: Use the lab's command, `--to-docker --to=$REPO:unsigned`; it prints `--> Success`. If a BuildConfig `claims-out-of-chain` already exists, `oc delete bc claims-out-of-chain -n $NS` first.

== Two runs at once sit in `Pending`

Symptom:: With two runs going (the demo's Prep and step 1, or a run started twice), tasks wait in `Pending` and the runs take much longer than three minutes.
Cause:: The project's `limits.cpu` quota is full: a task pod waits until another finishes (`ExceededResourceQuota` in the TaskRun's conditions).
Fix:: Let the earlier run finish, or cancel it: `tkn pipelinerun cancel <name> -n $NS`.

== The scan cannot reach RHACS

Symptom:: `scan` fails at once with `image check COULD NOT RUN`, or an error about `rox-api-token`, an empty endpoint, or authentication — not a policy violation.
Cause:: The scan Task reads Central's address and a CI token from the `rox-api-token` Secret in your project; the Secret is missing, or RHACS is not ready.
Fix:: Check the Secret, and re-materialize the entry state if it is missing:
+
[source,sh,role=execute,subs="attributes+"]
----
oc get secret rox-api-token -n $NS -o name 2>/dev/null || ws prep {module-id} --yes
----
+
If the Secret exists and the log says RHACS is not ready, tell your instructor (`oc get pods -n stackrox | grep -E 'central|scanner'`), then start the pipeline again.

== The vulnerable branch passes the scan

Symptom:: In the challenge, the `seed-vulnerable` run passes `scan` — no `Block Log4Shell` violation — although `log4j-core` 2.14.1 is in it.
Cause:: The RHACS vulnerability store is not warm yet: on a freshly installed cluster Scanner V4 needs about an hour to download its data, and until then `roxctl image check` finds no CVEs.
Fix:: Wait, then run it again. Your instructor's pre-flight checks this.

== Console: `scan` shows *Task does not exist*

Symptom:: On the Pipeline's *Details* graph, `scan` carries a warning icon, *Task does not exist*.
Cause:: The console looks for Tasks only in your project and in `openshift-pipelines`; `acs-image-check` lives in the shared `ogsr-parasol-tasks` library.
Fix:: Nothing to fix: every run fetches the Task through the cluster resolver.

== After a page reload: `Forbidden … in the namespace "-o"`, or an empty `$IMG`

Symptom:: Commands that worked a minute ago fail: `oc` reports `Error from server (Forbidden): … in the namespace "-o"`, or `cosign` complains about an empty image reference.
Cause:: A reload or reconnect opens a fresh shell, and the shortcuts are gone, so `-n $NS` collapses to `-n`.
Fix:: `source ~/m12.env`, then run the first block of the exercise you are in again (it sets `$IMG`, `$PR` and the like).

== `cosign: command not found`, or `gzip: stdin: not in gzip format`

Symptom:: `cosign`, `ec` or `rekor-cli` is not found, or the download prints `gzip: stdin: not in gzip format`.
Cause:: The terminal does not ship the sigstore clients; exercise 3 downloads them to `~/bin` from the cluster's Trusted Artifact Signer client server. The gzip error means the server answered with an error page.
Fix:: Check what the server returns, then run exercise 3's download block again; tell your instructor if it is not `200`:
+
[source,sh,role=execute]
----
curl -ksI $CLI/clients/linux/cosign-amd64.gz | head -1
----

== `cosign verify` fails with `UNAUTHORIZED: authentication required`

Symptom:: `cosign verify` errors with `GET https://image-registry…: UNAUTHORIZED: authentication required`.
Cause:: cosign reads the signature from the internal registry and has no credential.
Fix:: Log in to a path you own; `~/m12.env` already points `DOCKER_CONFIG` there:
+
[source,sh,role=execute]
----
oc registry login --to="$HOME/.docker/config.json" --skip-check
----

== `cosign initialize` prints a `root-checksum` warning

Symptom:: `cosign initialize --mirror=$TUF --root=$TUF/root.json` prints `WARNING: Fetching initial root from URL without providing its checksum is deprecated`.
Cause:: cosign prefers a `--root-checksum` alongside the root URL.
Fix:: Ignore it: initialization completes. A hardened setup pins the root checksum.

== `ec validate image` cannot reach the registry

Symptom:: `ec validate image` fails with a TLS error (`x509: certificate signed by unknown authority`) for `image-registry.openshift-image-registry.svc:5000`.
Cause:: The internal registry serves a certificate from the cluster's service CA, which the terminal does not trust by default.
Fix:: Run it with the service CA added to the system CAs, as the lab's block does (`SSL_CERT_FILE=~/ca-bundle.crt`); the block's `oc get configmap openshift-service-ca.crt … | cat /etc/pki/tls/certs/ca-bundle.crt - > ~/ca-bundle.crt` line builds that file.

== A harmless warning in the scan log

Symptom:: The `scan` step logs `warning: unsuccessful cred copy: ".docker" from "/tekton/creds" to "/": … permission denied`.
Cause:: `roxctl` probes for a docker credential directory it cannot create; it does not need one.
Fix:: Ignore it: `roxctl` authenticates to Central with the token from `rox-api-token`.
