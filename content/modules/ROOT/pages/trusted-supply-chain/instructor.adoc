// This module was rebalanced on 2026-07-18 (owner review): scanning is one beat on a PRE-SCANNED image,
// and the trust story (cosign verify → attestation → keyless/Rekor → admission) is the spine.
// 2026-11-12 (owner rule: no instructor-only exercise): admission is attendee-run against the install's
// ClusterImagePolicy; re-measured as user11 on cluster-5vqxc (OCP 4.22.22, RHTAS 1.5.1).

This module has four facts to plan around.
First, *the signed image is built once, at install*: the workshop layer runs this module's pipeline on the clean `main` branch in `ogsr-supply-chain`, and every prep copies the resulting *scanned-green, Chains-signed* image (with its `.sig` and `.att`) into the attendee's `{user}-cicd` as `parasol-claims-trusted:latest` in about a second. Measured on cluster-5vqxc on 2026-11-12, `ws prep trusted-supply-chain` for user11 took *2m25s* fresh and *2m59s* as a re-prep (purge included), against *5m12s* when every prep ran its own build; the whole trust spine runs against the copy with no waiting.
Second, *there is exactly one attendee build* — the seeded branch, to a throwaway `:candidate` tag — and it is the single memorable beat: the build *succeeds*, then the scan turns the run *red* on a CVSS-10 vulnerability.
Third, *the scan gate depends on the RHACS vulnerability store being warm*: on a freshly installed cluster the scanner needs *~1 hour* to populate before the Log4Shell policy will fire — pre-warm before any session (see pre-flight).
Fourth, *admission is install-applied, attendee-tested*: the install applies one `ClusterImagePolicy`, `ogsr-signed-parasol-claims`, scoped to every attendee's `{user}-cicd/parasol-claims-trusted`. Attendees read it and run one signed and one unsigned pod against it; nobody creates a policy during the session (see watchouts for why).

== Timing

Total hands-on: *~40 min* (add ~12–15 min of concept up front).
This is *shorter* than the pre-rebalance module (~80 min) — the second full build (fix-and-re-run to green) is gone; its place is taken by reading the pre-scanned clean verdict and by the deeper trust beats.

| # | Exercise group | Attendee time | Measured core (as user3, 4.21.22, warm cluster)

| 1 | The scan gate — one refused, one cleared | ~11 min | seeded `:candidate` run `Failed` at `acs-scan` in *2m39s* and *2m31s* (user11, 2026-11-12, Maven mirror warm; *7m11s* before the mirror) — build *Succeeded*, scan blocked on Log4Shell CVSS 10; reading the pre-scanned `scan-passed=true` is instant; `mvn ...:makeBom` *~45s* warm, 240 components (239 on 2026-07-18) — done *during* the build

[NOTE]
.How this timing was measured
====
Every exercise was performed as `user3` on the build cluster (OCP 4.21.22, RHACS 4.11.1, RHTAS 1.4.2, Tekton Chains) on 2026-07-18 and timed.

* *Warm clean build (prep)* — the `main` branch built, scanned green (`scan-passed=true`), and was Chains-signed in *~8 min* (cold node longer); this is the image the trust spine reads — today built once at install in `ogsr-supply-chain` and copied in as `parasol-claims-trusted:latest`.
* *Seeded run (exercise 1)* — `Failed` at `acs-scan` in *7m11s* (2026-07-18) and *2m39s* (user11, 2026-11-12, in-cluster Maven mirror warm); the build *Succeeded* and was even signed before the scan refused the `:candidate` image.
* *Maven resolves from the in-cluster mirror*, which the installer warms, so the first seeded build no longer pays a cold dependency download.
* *Chains signing latency* — the `chains.tekton.dev/signed=true` annotation appears a *few seconds after* the build TaskRun completes, not instantly.
====

== Pre-flight checklist

Run these *before the session* (as cluster admin unless noted).

. *A sample user's entry state materializes and verifies (including the copied signed image).*
+
[source,sh,role=execute]
----
oc get pipelinerun -n ogsr-supply-chain        # the install-time build: expect Succeeded
adm start trusted-supply-chain --user user1     # about three minutes: copies the signed image in
ws verify trusted-supply-chain --user user1 --entry-only
----
+
Expect all checks green: the `user1-cicd` namespace + entry marker, the `parasol-claims-supply-chain` Pipeline, the copied `rox-api-token` Secret and `chains-cosign-pub` ConfigMap, the Gitea fork + its `seed-vulnerable` branch carrying the seeded `log4j-core`, the curated `acs-image-check` task, *the pre-scanned trust artifact* — a Chains-signed `parasol-claims-trusted:latest` with its `.sig`/`.att` tags and a run that passed the scan gate — *and the signature policy* naming `user1-cicd/parasol-claims-trusted`.

. *The shared trust stack is up — RHACS and RHTAS.*
+
[source,sh,role=execute]
----
oc get central -n stackrox -o jsonpath='RHACS: {.items[0].status.conditions[?(@.type=="Deployed")].status}{"\n"}'
oc get securesign -n trusted-artifact-signer -o jsonpath='RHTAS Ready: {.items[0].status.conditions[?(@.type=="Ready")].status}{"\n"}'
oc get route -n trusted-artifact-signer | grep -E 'cli-server|rekor-server|tuf'
oc get task acs-image-check -n ogsr-parasol-tasks -o name
----
+
Expect RHACS `Deployed=True`, `RHTAS Ready: True`, the `cli-server`/`rekor-server`/`tuf` routes serving, and the `acs-image-check` task.
If RHTAS Ready is not `True`, exercises 2–4 cannot run (no cli-server to fetch cosign, no Rekor to record to) — re-sync the trust stack (`pp-trust` + `trust-signing`; these are workshop-layer, not per-user).

. *The cli-server actually serves the clients.*
+
[source,sh,role=execute]
----
CLI=https://$(oc get route -n trusted-artifact-signer -l app.kubernetes.io/component=client-server -o jsonpath='{.items[0].spec.host}' 2>/dev/null || oc get route cli-server -n trusted-artifact-signer -o jsonpath='{.spec.host}')
curl -ksI $CLI/clients/linux/cosign-amd64.gz  | head -1
curl -ksI $CLI/clients/linux/rekor-cli-amd64.gz | head -1
----
+
Expect `HTTP/1.1 200` for both — the attendee downloads `cosign` and `rekor-cli` from here (the Showroom terminal ships neither).
RHTAS 1.5 no longer deploys this client server itself; the workshop install serves it on the same host. A `503` here means that install component is missing, and exercises 2–4 cannot start.

. *The signature policy is in place and the nodes have finished applying it.*
+
[source,sh,role=execute]
----
oc get clusterimagepolicy ogsr-signed-parasol-claims -o jsonpath='{range .spec.scopes[*]}{@}{"\n"}{end}' | wc -l
oc get mcp
----
+
Expect one scope per attendee (13 on cluster-5vqxc) and every pool `UPDATED=True`.
The install applies the policy once; creating or changing it rolls a new MachineConfig across every node (~70 s, a CRI-O reload — no drain, no reboot). A pool still `UPDATING` means the nodes are mid-roll, and exercise 5's unsigned pod may still run.

. *Pre-warm the scanner AND prove the gate fires (do this ~1 h before).*
Run the seeded pipeline once on a sample user to a `:candidate` tag — it both warms the Maven cache and confirms the RHACS vulnerability store is populated enough for the Log4Shell policy to fire:
+
[source,sh,role=execute]
----
NS=user1-cicd
oc create -n $NS -f - <<'EOF'
apiVersion: tekton.dev/v1
kind: PipelineRun
metadata: {generateName: preflight-vuln-}
spec:
  pipelineRef: {name: parasol-claims-supply-chain}
  params:
    - {name: git-revision, value: seed-vulnerable}
    - {name: image, value: "image-registry.openshift-image-registry.svc:5000/$(context.pipelineRun.namespace)/parasol-claims:candidate"}
  taskRunTemplate: {serviceAccountName: pipeline}
  workspaces:
    - name: shared-workspace
      volumeClaimTemplate: {spec: {accessModes: [ReadWriteOnce], resources: {requests: {storage: 1Gi}}}}
  taskRunSpecs:
    - {pipelineTaskName: sbom-report, computeResources: {requests: {memory: 1Gi}, limits: {memory: 1536Mi}}}
    - {pipelineTaskName: build-image, computeResources: {requests: {memory: 1536Mi}, limits: {memory: 2Gi}}}
EOF
tkn pipelinerun logs --last -f -n $NS | grep -iE 'Block Log4Shell|image check'
----
+
[IMPORTANT]
.The scanner needs ~1 hour of warm-up on a fresh cluster
=====
RHACS Scanner V4 downloads its vulnerability data after install; until it is populated, `roxctl image check` finds *no* CVEs and the gate *passes even on the seeded branch* — the lab's first beat silently fails.
On a cluster up for an hour this is a non-issue.
On a *freshly provisioned* cluster, run the pre-flight above and confirm it prints `Block Log4Shell (CVE-2021-44228) at build` before you trust the gate.
=====

. *`adm smoke` passes for a sample attendee — the only pre-flight check that runs as the attendee, in the real cockpit terminal.*
+
[source,sh,role=execute]
----
adm smoke trusted-supply-chain user1
----
+
Every module declares `smokeCommands` in `ws-meta.yaml`; unlike the checks above (run from an admin context), `adm smoke` execs into the attendee's own Showroom terminal as `user1` and proves the representative commands work under their real identity, PATH, and namespace isolation — not just that the objects exist.

[NOTE]
.What "done" looks like
====
You do not need a separate rubric for when the room is ready to move on: each exercise in the lab ends on its own ✔ *Verify:* line, which is the per-exercise move-on signal — when an attendee's output matches it, that exercise is done. For a whole-module self-check, attendees can run `ws verify trusted-supply-chain` themselves at any point in the Showroom terminal; it is the same script pre-flight step 1 above runs for you (with `--entry-only`).

== Demo-mode notes

Beyond the Say/Show/Do arc in the demo flavor:

* *Pre-solve before the room.*
`adm solve trusted-supply-chain --user {user}` lands on the same end state as prep (the scanned, signed `parasol-claims-trusted:latest`, copied in) and returns in about three minutes.
It leaves your "good outcome" ready.

* *cosign is now attendee-hands-on — no verification pod needed.*
Since RHTAS recovered, `cosign` and `rekor-cli` are fetched from the cli-server (exercise 2), so verification is *hands-on for everyone* — the old "instructor runs cosign in a pod" workaround is retired.
If you present on a machine without them, run the same two `curl … | gunzip` lines from the lab.

* *Talk through the one build, never at it.*
Even warm, the seeded run is ~7 minutes.
Start it, then narrate the threat-model / three-artifacts story while it builds — the payoff is the *red scan* and then the trust beats, not a progress bar.

* *Admission is hands-on — nothing to apply from the instructor seat.*
The install applied one `ClusterImagePolicy`, `ogsr-signed-parasol-claims`, with one scope per attendee (`userN-cicd/parasol-claims-trusted`). Demo step 4 and lab exercise 5 tag an unsigned UBI image into that repository and run it; the node refuses the pull with `SignatureValidationFailed`. Run step 4 once before a demo so `demo-unsigned` is not a surprise; `ws prep` deletes it with the rest of `{user}-cicd`.

* *Rekor may be empty on a fresh install.*
`rekor-cli loginfo` printed `Tree Size: 0` on cluster-5vqxc (RHTAS 1.5.1, reinstalled the day before) — nobody had signed keylessly yet. Run lab exercise 4 once before a demo so step 4 shows a live, growing log.

== Top questions attendees ask

*1. "The build succeeded but the run failed — is that a bug?"*::
No, it is the design.
The scan runs *after* the build (`acs-scan` has `runAfter: build-image`) because you cannot scan an image you have not built.
So the image _is_ built (and even signed), and then the scan refuses the `:candidate` — the run is `Failed` with `build-image: Succeeded, acs-scan: Failed`.

*2. "Where did the clean `latest` image come from — I only built `:candidate`?"*::
The platform built it once, at install: the same pipeline ran on the clean `main` branch (no log4j) in `ogsr-supply-chain`, and the entry state copied the scanned-green, Chains-signed image into their project as `parasol-claims-trusted:latest`, signature and attestation included.
That is deliberate — the owner's rebalance makes the attendee *read* the clean verdict and *verify* the clean image, instead of waiting through a second build. Their own seeded build goes to `parasol-claims:candidate`, a separate repository, so it never touches the trusted image.

*3. "What's the difference between the signature, the attestation, and the SBOM?"*::
Three different facts.
The *signature* proves the image is intact and came from us (a signature over the digest).
The *attestation* is *signed provenance* — how the image was built (builder, source, steps, timestamps), as a SLSA statement.
The *SBOM* is what is *inside* — every component and version.
Chains produces the signature and attestation automatically; the build produces the SBOM.

*4. "Key-based versus keyless — and why did we sign the SBOM, not the image, keylessly?"*::
The lab verifies the Chains *key-based* signature (deterministic, no per-build identity) in exercise 2, then demonstrates *keyless* (Fulcio short-lived cert + a Rekor transparency-log entry) in exercise 4.
We sign the *SBOM file* (`sign-blob`) rather than push a keyless *image* signature because the OpenShift internal registry rejects cosign's keyless image-signature manifest (`UNKNOWN` on the manifest PUT) — the Rekor entry is written first regardless, but the image push fails.
In production, keyless *image* signatures go to an external registry (Quay). The SBOM `sign-blob` keeps the transparency-log beat self-contained and clean.

*5. "How does the transparency log actually help?"*::
It makes signing *auditable*.
A key-based signature proves "signed with a key we hold." A keyless signature in Rekor proves "signed by _this identity_ at _this time_, on a public, append-only log nobody — not even us — can quietly alter."
When an auditor asks "prove the image in production came from your pipeline," the Rekor entry is a receipt they can read without contacting you.

*6. "Chains signed my `:candidate` — why is it refused in the trusted repository?"*::
Because the policy trusts one *builder*, not any signature made with the key.
A signature names the repository the image was built in; the policy's `ExactRepository` accepts only `ogsr-supply-chain/parasol-claims`, where the platform's scanned build ran.
Your `:candidate` was signed as `<you>-cicd/parasol-claims`, so the node finds the signature and rejects its identity: `Signature for identity "…" is not accepted`.

*7. "How does this module relate to the Application Security Testing module?"*::
Complementary halves of DevSecOps.
*This* module (trust) proves the image is *provably yours* — signed, attested, transparency-logged, and admission-controlled.
*Application Security Testing* (scanning) proves the image is *free of known flaws* — SAST, SCA, DAST, config, and image-risk gates.
They overlap on one mechanic: both drive an RHACS build-time image check that blocks Log4Shell. Here that scan is *one beat of context*; there it is the subject.

== Watchouts

* *The scanner vulnerability store must be warm.*
On a freshly installed cluster, RHACS Scanner V4 needs *~1 hour* to populate before the Log4Shell policy fires; until then the gate *passes on the seeded branch* and the lab's first beat silently no-ops.
Always run the pre-flight seeded pipeline and confirm it prints `Block Log4Shell` before a session.
* *Prep copies; it does not build.*
`adm start`/`ws prep`/`adm solve` copy the install-time signed image in and return in about three minutes (2m25s–2m59s for user11, purge included). The one exception is right after install: if the shared build in `ogsr-supply-chain` is still running, prep waits for it (ws-meta `waitSeconds: 1500` covers it). Check `oc get pipelinerun -n ogsr-supply-chain` shows it `Succeeded` before the room preps.
* *RHTAS must be Ready for exercises 2–4.*
`cosign`/`rekor-cli` come from the RHTAS cli-server, and the keyless beat records to Rekor. If Securesign is not `Ready`, those exercises cannot run — confirm the routes serve in pre-flight.
* *Never create an `ImagePolicy` or `ClusterImagePolicy` during a session.*
Each create, change or delete rolls a new MachineConfig across every node (~70 s per policy, measured on cluster-5vqxc). One policy per attendee would keep the pools updating for the whole session, which is why the install applies one `ClusterImagePolicy` up front. Attendees can read signature policies (`platform-observer`) but cannot create them (`oc auth can-i create clusterimagepolicies --as=user11` = `no`).
* *The policy accepts only the install's build — by repository identity.*
The trusted image is built and Chains-signed once in `ogsr-supply-chain` and copied into each `{user}-cicd/parasol-claims-trusted`, so its signature claims `ogsr-supply-chain/parasol-claims`. The policy's `signedIdentity` is `ExactRepository` on that name; `MatchRepository` would compare it with the pulled `userN-cicd` repository and refuse the signed image too. A consequence the lab's Challenge shows: an attendee's own `:candidate`, Chains-signed as `userN-cicd/parasol-claims`, is refused even with its signature beside it (`Signature for identity … is not accepted`).
* *Only `parasol-claims-trusted` is guarded.*
`userN-cicd/parasol-claims` stays out of scope because Pipelines Fundamentals and App Security Testing build and deploy their own Chains-signed `:latest` there. An unsigned image tested anywhere else simply runs.
* *cosign v3 sources Fulcio/Rekor from the TUF signing config.*
On cosign v3.0.4, passing `--fulcio-url`/`--rekor-url` to `sign` after `cosign initialize` errors with "cannot specify service URLs and use signing config" — let the signing config (from `cosign initialize`) supply them. The lab commands already do.
* *Chains signs every build — including the seeded one.*
`signed=true` appears on the build TaskRun of the _failed_ `:candidate` run too; that is correct (signing answers "who built it," a different question from "is it clean"). Do not let attendees read "signed" as "passed the scan."
* *The `scan-passed` result is empty on a failed run.*
A failed `acs-scan` task does not propagate the `scan-passed` result, so it is blank (not `false`) on the seeded run; it reads `true` on the install-time clean run in `ogsr-supply-chain`.
* *Benign roxctl warning.*
The `acs-scan` logs a `warning: unsuccessful cred copy: ".docker" ... permission denied` line — harmless; `roxctl` authenticates with the token from `rox-api-token`.
* *`ws reset`/`ws prep` restores the vulnerable seed and the signed image.*
The fork job re-injects `log4j-core` on `seed-vulnerable` idempotently, and the copy hook puts the signed `parasol-claims-trusted:latest` back — a reset returns the attendee to a fresh start.
