This module has four facts to plan around.
First, *every attendee runs the pipeline themselves*: `parasol-claims-trusted-build` in `{user}-cicd` builds into `parasol-claims-secure`, scans, makes the SBOM, checks with Conforma and deploys Deployment `parasol-claims` by digest, and every later exercise reads that run. Nothing depends on a run the attendee never saw. A run takes about 2m20s–2m40s with the defaults.
Second, *Tekton Chains signs keyless, as its own SPIFFE identity* (`spiffe://<cluster-domain>/ns/openshift-pipelines/sa/tekton-chains-controller`), through Trusted Artifact Signer in this cluster. If Chains does not sign, `verify-conforma` fails and nothing deploys, so the Chains and identity checks in the pre-flight come first.
Third, *admission is the RHTAS policy controller*, an admission webhook, enforcing on each `{user}-cicd` (label `policy.rhtas.com/include=true`) for the one repository its `ClusterImagePolicy` names, `{user}-cicd/parasol-claims-secure`. Attendees read the rule; nobody changes it during a session.
Fourth, *the scan gate depends on the RHACS vulnerability store being warm*, but only for the optional vulnerable-branch challenge: the main run passes either way.

== Demo-mode notes

* *Stage before the room.* `adm solve trusted-supply-chain` lands on the finished run in about six minutes (368 s measured); the demo's Prep block then starts the out-of-chain build (about 1½ minutes) and the vulnerable run (about 3 minutes).
* *Let the live run play in the background.* Step 1 starts a fresh run and reads the finished one; by step 3 the fresh run has usually finished, and the room can see it green.
* *Confirm the vulnerable run stopped at `scan`.* If the scanner is cold, it passes the scan — then show step 4 from the challenge's diagram and say so.

== Top questions attendees ask

*1. "Who signed this image?"*::
Tekton Chains, the build platform, as its SPIFFE identity `spiffe://…/ns/openshift-pipelines/sa/tekton-chains-controller`, seconds after `build-image` finished.
The certificate in the signature names that identity, Rekor holds the record, and the provenance names the pipeline run and task that built the image.
No pipeline step signs, and none could: `cosign verify` pinned to the pipeline's own service account is refused (lab exercise 3).

*2. "Why keyless — what was wrong with a key?"*::
A stored key has to be guarded, rotated and revoked, and anyone who copies it can sign as you, silently.
Keyless replaces it with an identity SPIRE attests on the node, a certificate that lives ten minutes, and a public log entry for every signature, so a signature cannot be made quietly.
The cost is operational: the identity plane and the log become production services. For an isolated build system, a well-managed key can be the simpler choice.

*3. "Why both Conforma and admission?"*::
They guard different doors.
Conforma runs in the pipeline: it fails the release with a reason before anything deploys.
Admission runs at the cluster, for every pod, whoever creates it: the backstop for everything that never went through the pipeline (an image built by hand, copied in, or typed into a Deployment).
Only Conforma, and anyone with deploy rights can skip it; only admission, and a bad release is found when a pod is refused.

*4. "Chains signed the vulnerable image too — so is it trusted?"*::
It is *signed*: the signature says who built it, not that it passed.
The scan stopped the run before Conforma and the deploy, so it never ran here. Admission alone would admit it, because the policy only requires Chains' signature; requiring a passed scan as well means attesting the scan result and adding that rule to the policy.

*5. "Where is the SBOM, and is it signed?"*::
In ConfigMap `parasol-claims-sbom` in the attendee's project: storage only.
Its sha256 is the run's `SBOM_SHA256` result, so it is inside the run's provenance that Chains signs; exercise 3 compares the two, and the signature is what makes the stored copy trustworthy.

*6. "Why does `oc get clusterimagepolicy` show something else?"*::
OpenShift has a second kind with the same name in `config.openshift.io`, a node-level pull policy. The policy controller's kind is `clusterimagepolicies.policy.sigstore.dev`; name the group.

*7. "How does this relate to Application Security Testing?"*::
Complementary halves of DevSecOps. This module proves an image is *provably yours*: signed, attested, logged, checked and admission-controlled. Application Security Testing proves it is *free of known flaws* with SAST, SCA, DAST and image-risk gates. Here the scan is one gate in the run; there it is the subject.

== Watchouts

* *Chains must sign within the Conforma wait.* `verify-conforma` waits up to 180 seconds (its `WAIT_SECONDS`) for Chains' signature and provenance; a Chains controller that is down or misconfigured fails every run at that step. Check the TaskRun annotation `chains.tekton.dev/signed` first (troubleshooting has the entry).
* *Never change the ClusterImagePolicy or the namespace label during a session.* Every attendee's admission depends on them.
* *The policy names one repository, but the webhook sees every pod.* Only `*/parasol-claims-secure` images need Chains' signature; `no-match-policy=allow` admits the rest unsigned. In a labelled namespace the webhook still resolves *every* image tag to a digest: it rewrites `tag` to `tag@digest`, and it refuses a tag it cannot resolve with the pod's pull secrets (a `registry.redhat.io` tag, for example: "must be an image digest"). That is why every image this module runs is digest-pinned, and why an Argo CD-managed tag image there would read OutOfSync forever.
* *Two kinds called ClusterImagePolicy.* The node-level `ogsr-signed-parasol-claims` (`config.openshift.io`) is left over from the previous design and scopes `parasol-claims-trusted`, which nothing uses now; the lab reads `ogsr-parasol-claims-keyless` (`policy.sigstore.dev`).
* *The admission label is per module.* This module's entry state labels `{user}-cicd` `policy.rhtas.com/include=true`; an attendee's own reset cannot remove it, so Pipelines Fundamentals and Application Security Testing, which share `{user}-cicd`, remove it in their own PreSync hook when they take the project over. A new module that uses `{user}-cicd` needs the same hook.
* *The vulnerable run overwrites the tag and the SBOM, not the Deployment.* Every run pushes `parasol-claims-secure:latest`, and `sbom` runs beside `scan`, so a failed vulnerable run still replaces ConfigMap `parasol-claims-sbom`. The Deployment is pinned by digest and keeps running; exercise 3's hash check then no longer matches until the next clean run. Do the challenge last.
* *`ws prep` returns the entry state.* It removes runs, images and test pods and re-creates the pipeline, the trust settings and the fork with its vulnerable branch.
