== Block the bad image, prove the good one · 13 min

A pipeline refuses an image carrying a critical vulnerability, and the image that passed arrives with a signature, machine-readable provenance, and a public receipt anyone can check.

[IMPORTANT]
.Prep — run before the session
====
This demo starts from the finished lab state. Stage it before the session:

[source,sh,role=execute]

=== Brief

image::trusted-supply-chain/trusted-supply-chain-01-trust-triangle.svg["The supply-chain pipeline: a build step producing a CycloneDX SBOM and feeding a scan gate that fails the build when it finds a CVE, with Tekton Chains storing a signature and SLSA provenance beside the image. Below it, the registry holding the image with its .sig and .att artifacts, and an ImagePolicy admission check that lets a signed image run and refuses the pull of an unsigned one."]

*You ship your dependencies*

The code a team writes is a small fraction of what it deploys. The claims image is mostly other people's code — the runtime, its transitive libraries, the base operating-system layers — pulled in at build time. That is normal, and it is also the attack surface.

So when a flaw like Log4Shell lands, the hard questions are not about the code the team wrote. They are: what is inside this image, who built it, and can anyone prove the image running in production is the one the pipeline produced. A pipeline that only builds and deploys cannot answer any of the three.

*Three artifacts, three questions*

A *signature* says the image is intact and came from us. An *attestation* — signed SLSA provenance — says how it was built: the builder, the build type, the timestamps. An *SBOM* says what is inside, component by component. They are different facts and they reinforce each other: the attestation is signed, the SBOM can be attested, and the signature is what an admission gate checks.

On OpenShift those artifacts are produced by the pipeline rather than by anyone remembering to make them. Tekton Chains signs every image the pipeline builds and attaches its provenance with no per-build wiring, Red Hat Trusted Artifact Signer records signatures in a public transparency log, and a native `ClusterImagePolicy` makes the cluster verify a signature before it will pull an image.

*In this demo*

. The delivery pipeline with trust controls added, and the signed image it has already produced
. A build carrying a known-critical dependency, refused by the scan gate before it can ship
. The signature and SLSA provenance stored beside the image that passed, verified with `cosign`
. The public record of that signature, and the cluster refusing to pull anything unsigned

=== 1 · Three questions the pipeline could not answer — 3 min

Parasol's pipeline builds and deploys reliably, but a supplier audit asked three questions it could not answer: what is inside this image, who built it, and can you prove it. This is the same pipeline with trust controls added — and it has already produced a signed image.

image::trusted-supply-chain/trusted-supply-chain-06-pipelinerun-clean-check-succeeded.png["The OpenShift console PipelineRun details page for a clean supply-chain run, status Succeeded, its graph showing four nodes — fetch-source, sbom-report, build-image and acs-scan — each with a green checkmark and a 1/1 badge."]

*Why it matters*

The controls are pipeline steps, not a separate security programme. The same run that produces the image produces the bill of materials, the signature and the provenance, so every build is auditable by default rather than when someone remembers.

[source,sh,role=execute,subs="attributes+"]
----
NS={user}-cicd
CLI=https://cli-server-trusted-artifact-signer.{cluster_domain}
REKOR=https://rekor-server-trusted-artifact-signer.{cluster_domain}
TUF=https://tuf-trusted-artifact-signer.{cluster_domain}
tkn pipeline describe parasol-claims-supply-chain -n $NS | sed -n '/^Tasks/,$p' | head -n 7
----

*What just happened*

Four tasks, in order: clone, SBOM, build-and-sign, scan. The same shape as any delivery pipeline, except that it now produces trust artifacts alongside the image — and the scan can stop it.

=== 2 · The gate refuses a vulnerable build — 4 min

Build a branch that carries the Log4Shell library from 2021 to a throwaway tag, and let the scan gate refuse it. The build itself succeeds — the scan runs after it, because an image has to exist before it can be scanned — and then the gate fails the run.

image::trusted-supply-chain/trusted-supply-chain-02-pipelinerun-scan-failed.png["The same PipelineRun graph for the seeded build, status Failed: fetch-source, sbom-report and build-image each green with a 1/1 badge, and acs-scan marked with a red exclamation icon and a 0/1 badge."]

*Why it matters*

A known-critical dependency is caught in the developer's own pipeline run, minutes after the commit, rather than in production months later. The image exists but never becomes a trusted tag, so nothing downstream can deploy it by accident.

[source,sh,role=execute,subs="attributes+"]
----
NS={user}-cicd
oc create -n $NS -f - <<'EOF'
apiVersion: tekton.dev/v1
kind: PipelineRun
metadata: {generateName: demo-vuln-}
spec:
  pipelineRef: {name: parasol-claims-supply-chain}
  params:
    - {name: git-revision, value: seed-vulnerable}
    - {name: image, value: "image-registry.openshift-image-registry.svc:5000/$(context.pipelineRun.namespace)/parasol-claims:candidate"}
  taskRunTemplate: {serviceAccountName: pipeline}
  workspaces:
    - name: shared-workspace
      volumeClaimTemplate:
        spec: {accessModes: [ReadWriteOnce], resources: {requests: {storage: 1Gi}}}
  taskRunSpecs:
    - {pipelineTaskName: sbom-report, computeResources: {requests: {memory: 1Gi}, limits: {memory: 1536Mi}}}
    - {pipelineTaskName: build-image, computeResources: {requests: {memory: 1536Mi}, limits: {memory: 2Gi}}}
EOF
----

That is about three minutes of Maven and buildah on a warm cluster, longer on a cold one. Track it on one line rather than on a log stream — `SUCCEEDED` reads `Unknown` while it works and `False` once the gate refuses it:

[source,sh,role=execute]
----
oc get pipelinerun -n $NS --sort-by=.metadata.creationTimestamp --no-headers \
  -o custom-columns='RUN:.metadata.name,SUCCEEDED:.status.conditions[?(@.type=="Succeeded")].status' | tail -1
----

Steps 3 and 4 do not depend on this run. When the line flips, read the gate's verdict:

[source,sh,role=execute]
----
oc get taskrun -n $NS -l tekton.dev/pipelineTask=acs-scan --sort-by=.metadata.creationTimestamp \
  -o name | tail -1 | cut -d/ -f2 | xargs -I{} tkn taskrun logs -n $NS {} | grep -iE "TOTAL:|log4|CVE-2021-44228|Block Log4Shell|image check FAILED"
----

*What just happened*

`Block Log4Shell (CVE-2021-44228)`, CVSS 10, in `log4j-core` 2.14.1. The build succeeded and the run failed: the `:candidate` tag exists but never becomes a trusted image.

=== 3 · The image that passed carries a signature — 3 min

The gate says something is wrong with one image. The other half of the story is what makes the good one trustworthy: the clean build was signed automatically, with its provenance stored beside it, and any laptop with `cosign` can check that.

image::trusted-supply-chain/trusted-supply-chain-03-imagestream-tags.png["The console ImageStream details page for parasol-claims-trusted: an image count of 3 and a Tags table listing parasol-claims-trusted:latest plus two tags derived from that image's digest, one ending .att and one ending .sig, each with its own sha256 identifier."]

*Why it matters*

Nobody wired signing into this pipeline. Tekton Chains observes completed builds and signs what they produced, so signing cannot be forgotten under deadline pressure — and verification needs nothing but the public key, anywhere, offline.

[source,sh,role=execute,subs="attributes+"]
----
NS={user}-cicd
CLI=https://cli-server-trusted-artifact-signer.{cluster_domain}
mkdir -p ~/bin && curl -ksL $CLI/clients/linux/cosign-amd64.gz | gunzip > ~/bin/cosign && chmod +x ~/bin/cosign
curl -ksL $CLI/clients/linux/rekor-cli-amd64.gz | gunzip > ~/bin/rekor-cli && chmod +x ~/bin/rekor-cli
export PATH="$HOME/bin:$PATH"
oc registry login --to="$HOME/.docker/config.json" --skip-check && export DOCKER_CONFIG="$HOME/.docker"
oc get istag -n $NS | grep parasol-claims
oc get cm chains-cosign-pub -n $NS -o jsonpath='{.data.cosign\.pub}' > ~/cosign.pub
IMG=$(oc get istag parasol-claims-trusted:latest -n $NS -o jsonpath='{.image.dockerImageReference}')
cosign verify --key ~/cosign.pub --allow-insecure-registry --insecure-ignore-tlog "$IMG"
----

*What just happened*

The `.sig` and `.att` tags beside the image are the signature and the SLSA provenance, stored in the registry with it. `cosign` confirms the signature is intact and was made with our key. Sign in the pipeline; verify anywhere.

=== 4 · A public record, and a cluster that checks — 3 min

A signature made with a key we hold proves the image is ours. Two things harden that: a public, append-only transparency log so no signature can be quietly backdated or hidden, and an admission rule so the cluster verifies the signature before it will pull the image.

image::trusted-supply-chain/trusted-supply-chain-04-rekor-entry.png["The Rekor Search UI, branded Red Hat Trusted Artifact Signer, showing one matching entry for a searched sha256 hash: the entry UUID, type hashedrekord, log index and integrated timestamp, followed by the signature and the decoded public-key certificate."]

*Why it matters*

Signing without enforcement is a policy on a wiki. Admission is what turns "we sign our images" into "this cluster will not run an unsigned one", and the transparency log is what turns a signature into a receipt an auditor can read without contacting you.

[source,sh,role=execute,subs="attributes+"]
----
NS={user}-cicd
REKOR=https://rekor-server-trusted-artifact-signer.{cluster_domain}
rekor-cli loginfo --rekor_server "$REKOR" | grep 'Tree Size'
----

The cluster's signature policy guards the repository the signed image lives in. Put an unsigned image there and ask a node to run it:

[source,sh,role=execute]
----
oc tag --source=docker registry.access.redhat.com/ubi9/ubi-minimal:latest \
  parasol-claims-trusted:unsigned --reference-policy=local -n $NS
oc run demo-unsigned -n $NS --image=image-registry.openshift-image-registry.svc:5000/$NS/parasol-claims-trusted:unsigned \
  --image-pull-policy=Always --command -- sleep infinity
sleep 10
oc get pod demo-unsigned -n $NS \
  -o jsonpath='{.status.containerStatuses[0].state.waiting.reason}{"\n"}{.status.containerStatuses[0].state.waiting.message}' \
  | grep -oE 'SignatureValidationFailed|Source image rejected: [^;]*' | sort -u
----

*What just happened*

That tree size is the live Rekor log run by Red Hat Trusted Artifact Signer: every keyless signature lands there permanently. The `ClusterImagePolicy` the platform applied at install made the node look for a signature before pulling, and it refused the unsigned image: `SignatureValidationFailed`, "A signature was required, but no signature exists". A bad image cannot be built, an unsigned image cannot run, and every signature is on the record.

== Frequently asked questions

*The build succeeded but the run failed — is that a bug?*::
No, that is the design. The scan runs after the build, because an image has to exist before it can be scanned. So the image is built — and even signed, since signing answers "who built it", not "is it clean" — and then the gate refuses the `:candidate` tag and fails the run.

*What is the difference between the signature, the attestation and the SBOM?*::
Three different facts. The signature proves the image is intact and came from you. The attestation is signed provenance: the builder, the build type, the build tool, the timestamps, as a SLSA statement. The SBOM is what is inside — every component and version. Tekton Chains produces the first two automatically; the build produces the SBOM.

*Key-based or keyless signing — which should we use?*::
Key-based signing is deterministic and needs no per-build identity, which makes it the simpler, sufficient choice for a controlled build system like this one; the private key lives in the cluster and anyone verifies with the public key, offline. Keyless removes the long-lived key: Trusted Artifact Signer issues a short-lived certificate bound to an identity the signer proves, and records the signature in the transparency log. On OpenShift that identity can be a workload identity: the Zero Trust Workload Identity Manager gives a pod a SPIFFE ID naming its namespace and service account, attested on the node, so the certificate names the workload that signed and no secret changes hands. Reach for keyless when you need public verifiability or per-identity signing.

*How does the transparency log actually help?*::
It makes signing auditable by someone outside your organization. A key-based signature proves "signed with a key we hold". An entry in the log proves "signed by this identity, at this time, on an append-only record that nobody — including us — can quietly alter". That is what "prove it" usually means in an audit.

*How does this relate to vulnerability scanning?*::
They are complementary halves of DevSecOps in the same pipeline. Trust proves the image is provably yours — signed, attested, logged and admission-controlled. Scanning proves it is free of known flaws, with SAST, SCA, DAST and image-risk gates; that is the subject of the Application Security Testing module. A scanned-clean image that is not signed can still be swapped; a signed image full of CVEs is authentically vulnerable.

== 4. Keyless signing with a workload identity, and the transparency log
⏱ *~12 min* · give a pod a SPIFFE identity, sign the SBOM with it, and find your own entry in Rekor

The key behind your signature lives in the cluster: it can leak, and it leaves no public trace.
Parasol wants *keyless* signing: no long-lived key to steal, and a public record nobody can quietly backdate or hide.

*You'll end with:* your SBOM signed by a pod in `{user}-cicd`, and a public *Rekor* entry whose certificate names that workload's SPIFFE ID.

.Keyless signing, SPIFFE and SPIRE in more depth
[%collapsible]
====
The signature you verified in exercise 2 uses a *cosign key pair*; the private key lives in the cluster.
In *keyless* signing, *Red Hat Trusted Artifact Signer* issues a *short-lived certificate* (via *Fulcio*) to a signer that proves an identity, and records every signature in a public, append-only *transparency log* (*Rekor*).

A keyless signature is only as good as the identity behind it, and here that identity belongs to a *workload*, not a person.
*SPIFFE* (Secure Production Identity Framework for Everyone) names a workload `spiffe://<trust domain>/ns/<namespace>/sa/<service account>`.
On this cluster the *Zero Trust Workload Identity Manager* runs *SPIRE* (the SPIFFE Runtime Environment) on every node, and SPIRE hands that name to a pod only after checking, on the node, which namespace and service account the pod really runs as.
Fulcio trusts SPIRE as an identity issuer, so the certificate that signs your SBOM carries your workload's SPIFFE ID — and nobody handed your pod a key or a password to make that happen.
====

*Set up.* Point cosign at the RHTAS trust root; read the issuer Fulcio trusts and the SPIFFE *trust domain* from the cluster:

[source,sh,role=execute,subs="attributes+"]
----
export PATH="$HOME/bin:$PATH"
NS={user}-cicd
REKOR=https://rekor-server-trusted-artifact-signer.{cluster_domain}
TUF=https://tuf-trusted-artifact-signer.{cluster_domain}
ISSUER=$(oc get spireoidcdiscoveryprovider cluster -o jsonpath='{.spec.jwtIssuer}')
TD=$(oc get zerotrustworkloadidentitymanager cluster -o jsonpath='{.spec.trustDomain}')
cosign initialize --mirror=$TUF --root=$TUF/root.json
echo "issuer: $ISSUER"
echo "trust domain: $TD"
----

.Expected output
[source,texinfo]
----
WARNING: Fetching initial root from URL without providing its checksum is deprecated and will be disallowed in a future Cosign release. Please provide the initial root checksum via the --root-checksum argument.
issuer: https://oidc-discovery.<cluster-domain>
trust domain: <cluster-domain>
----

The trust domain is this cluster's apps domain. The checksum `WARNING` is harmless (xref:trusted-supply-chain/troubleshooting.adoc[troubleshooting]).

*Give a workload an identity.* Create a pod that runs as the `pipeline` service account and mounts the SPIFFE CSI volume (`csi.spiffe.io`), SPIRE's socket:

[source,sh,role=execute]

        readOnly: true

.Expected output
[source,texinfo]
----
pod/sbom-signer created

----

*What just happened:* the manifest holds no credential, yet the pod can only ever receive `…/ns/{user}-cicd/sa/pipeline`: SPIRE checks its namespace and service account on the node.

.What gave this pod its identity, and what keeps it yours
[%collapsible]
====
Nothing in that manifest is a credential.
The operator registers *every* pod that mounts the `csi.spiffe.io` volume, so any pod can ask SPIRE for an identity; the `workshop.redhat.com/spiffe-signer` label only matches the workshop's own, explicit registration of signer pods.
What a pod *cannot* choose is *which* identity it gets: SPIRE attests the namespace and service account on the node, so this pod only ever receives `…/ns/{user}-cicd/sa/pipeline`.
To hold a neighbour's identity you would have to run a pod in their namespace, and RBAC does not let you.

The pod's image is the one SPIRE's own agent runs, read from the cluster, because it carries the `spire-agent` client you ask for a token with.
====

*Fetch the identity token and sign, in one block.* The token lives *five minutes*; if you get distracted, rerun the whole block. A `no identity issued yet — retry 1` line is normal.

[source,sh,role=execute]
----
TOKEN=""
for i in $(seq 1 12); do
  TOKEN=$(oc exec sbom-signer -n $NS -- /spire-agent api fetch jwt -audience sigstore \
    -socketPath /spiffe-workload-api/spire-agent.sock -output json 2>/dev/null | jq -r '.[0].svids[0].svid // empty')
  [ -n "$TOKEN" ] && break
  echo "no identity issued yet — retry $i"; sleep 5
done
echo "$TOKEN" | jq -R 'split(".")[1] | @base64d | fromjson | {sub, aud, exp}'

cosign sign-blob -y --identity-token="${TOKEN:?no identity token - see troubleshooting}" --bundle ~/sbom.bundle target/parasol-claims-sbom.json > /dev/null \
  && echo "signed; bundle written to ~/sbom.bundle"
----

.Expected output (your `exp` differs; the retry line may be missing, or appear twice)

*What just happened:* `sub` is your workload's SPIFFE ID. cosign traded the token for a Fulcio certificate, signed, uploaded the record to Rekor, and wrote a *bundle* (certificate + signature + log proof) to `~/sbom.bundle`.

.Reading the token, and why fetch and sign share one block
[%collapsible]
====
The `jq` line decodes the token so you can read whom it names: `sub` is your namespace and your `pipeline` service account.
`aud` is `sigstore`, the audience Fulcio accepts, and `exp` is five minutes after the token was minted — by then the signature is long done.
Because the token lives only five minutes, the fetch and the signature stay together: rerunning the block fetches a fresh one.
SPIRE takes about five seconds to register a new pod, so the loop keeps asking for up to a minute.
====

*Find your entry.* Everyone writes to the same log, so fetch yours by the *log index* in your bundle, then read the identity in its certificate:

  | grep -aoE 'spiffe://[a-z0-9.-]+/ns/[a-z0-9-]+/sa/[a-z]+' | sort -u
rekor-cli loginfo --rekor_server $REKOR | grep -E 'Tree Size'
----

*What just happened:* the SPIFFE ID line is the certificate's *Subject Alternative Name*, copied by Fulcio from your token.
Your entry is a permanent, tamper-evident record anyone can audit without contacting you: *this artifact was signed by this workload, at this time.*

.The `No previous log state stored` line, the `// "0"`, and searching the log
[%collapsible]
====
One SBOM looks much like another, so searching the shared log for "an SBOM" would find everyone's; the log index in your own bundle names exactly your entry.

The `No previous log state stored` line appears the first time you run `loginfo` and not on later runs: `rekor-cli` remembers the tree it saw, to prove the log only ever grew.
The `// "0"` matters once per log: the bundle leaves the index out when it is zero, which happens only to the very first entry a fresh log records.

.Why sign the SBOM, and not push the keyless signature onto the image
[%collapsible]
