*You ship your dependencies*

The code a team writes is a small fraction of what it deploys. The claims image is mostly other people's code — the runtime, its libraries, the base operating-system layers — pulled in at build time. That is normal, and it is also the attack surface.

When a flaw like Log4Shell lands, the hard questions are: what is inside this image, who built it, and can anyone prove the image running in production is the one the pipeline produced?

*How OpenShift answers them*

OpenShift Pipelines runs the build. *Tekton Chains*, part of OpenShift Pipelines, signs every image a pipeline builds, with its SLSA provenance, outside the pipeline itself, so no pipeline step holds a key or can sign for it. It signs *keyless* through Red Hat Trusted Artifact Signer: a ten-minute certificate for the Chains controller's workload identity, and an entry in a transparency log. Conforma checks that signature and provenance before the pipeline deploys, and the Trusted Artifact Signer policy controller checks it again at admission, for every pod, whoever deploys it.

*In this demo*

. One pipeline run: build, scan, SBOM, the Conforma check, and a deploy pinned by digest
. Who signed the image, checked with public material only
. An image built outside the pipeline, refused at admission
. A vulnerable build, stopped at the scan before anything checks or deploys it

=== 2 · Who signed it — 4 min

No pipeline step signs. Tekton Chains watched the build finish and signed the image as its own workload identity, with a certificate that lived ten minutes and a permanent entry in the transparency log.

[mermaid]
....
include::example$diagrams/trusted-supply-chain/11-keyless-steps.mmd[]
....

*Why it matters*

There is no signing key to steal, rotate or leak. Anyone can verify the signature with public material only: the trust root and the identity they expect.

[source,sh,role=execute]
----
source ~/m12.env
mkdir -p ~/bin && curl -ksL $CLI/clients/linux/cosign-amd64.gz | gunzip > ~/bin/cosign && chmod +x ~/bin/cosign
oc registry login --to="$HOME/.docker/config.json" --skip-check
cosign initialize --mirror=$TUF --root=$TUF/root.json 2>/dev/null
IMG=$(oc get deployment parasol-claims -n $NS -o jsonpath='{.spec.template.spec.containers[0].image}')
cosign verify --certificate-identity "$SIGNER" --certificate-oidc-issuer "$ISSUER" --rekor-url "$REKOR" \
  --allow-insecure-registry "$IMG" 2>&1 >/dev/null | grep -E '^  -'
----

*What just happened*

cosign lists the three checks it made: "The cosign claims were validated", "Existence of the claims in the transparency log was verified offline", and "The code-signing certificate was verified using trusted certificate authority certificates".
The signature verifies only for Chains' identity, `spiffe://…/ns/openshift-pipelines/sa/tekton-chains-controller`, and its Rekor entry proves it was made while the ten-minute certificate was valid.

*What just happened*

The out-of-chain image carries no signature from Chains, so the policy controller refused it before a pod existed. The pipeline's digest was admitted, deployed by hand: the webhook judges how the image was built, not who deploys it.

The prep step also ran the pipeline on a branch carrying the Log4Shell library from 2021.

[mermaid]

*Why it matters*

A known-critical dependency is caught in the developer's own pipeline run, minutes after the commit. The vulnerable image never reaches the Conforma check or the deploy, and the running Deployment keeps its earlier digest.

[source,sh,role=execute]

The build succeeded and Chains signed it — a signature says who built an image, not that it is clean — and the scan failed the run before anything checked or deployed it.

== Frequently asked questions

*Where is the signing step?*::
There is none. Tekton Chains, a controller that ships with OpenShift Pipelines, watches every TaskRun and signs the image a build reports when it finishes. No pipeline step holds a key or can sign for it, which is what the SLSA framework asks of a build platform.

*What does keyless mean, and what proves the signature later?*::
No stored private key. Chains gets a ten-minute certificate for its workload identity from Trusted Artifact Signer, signs with a key that exists for one signature, and records the signature in the Rekor transparency log. The log entry's time proves the signature was made while the certificate was valid, so it verifies long after the certificate expired.

*Why check in the pipeline and again at admission?*::
Conforma, in the pipeline, stops a release with a clear reason before anything deploys. Admission is the backstop for everything that never went through the pipeline: an image built by hand, a copy from another registry, a typo in a Deployment. One protects the release, the other protects the cluster.

*Does admission also refuse the vulnerable image?*::
Not by itself: that image was built by the pipeline, so Chains signed it. The scan stopped the run before it was deployed. To make admission require a passed scan as well, the pipeline would record the scan result as a signed attestation and the policy would require it — the same mechanism, one more rule.

*Does any of this call the public Sigstore services?*::
No. SPIRE, Fulcio, Rekor, the certificate-transparency log and TUF all run in this cluster.

.Where each Task is defined, and how to read one yourself
[%collapsible]

A step either *points to* a Task stored in the cluster, or *contains* its Task.

* `fetch-source`, `build-image`, `scan` and `verify-conforma` are `taskRef` entries with `resolver: cluster`: a name and a namespace.

.Keyless signing by Chains, in more depth
[%collapsible]
====
*The identity.* The *Zero Trust Workload Identity Manager* runs SPIRE on every node. SPIRE gives the Chains controller a short-lived token naming its SPIFFE ID, `spiffe://{cluster_domain}/ns/openshift-pipelines/sa/tekton-chains-controller`, after checking on the node which namespace and service account it really runs as. Nobody handed Chains a key or a password.

*The certificate.* *Fulcio*, Trusted Artifact Signer's certificate authority, checks that token against the keys SPIRE publishes and issues a certificate valid for ten minutes with the SPIFFE ID in it. The certificate-transparency log records every certificate Fulcio issues.

*The signature.* Chains signs the image digest and the provenance with a key made for this one signature, pushes both next to the image, and discards the key. *Rekor*, the transparency log, records both with their time.

*Why it still verifies tomorrow.* The certificate expired minutes later; the Rekor entry proves the signature was made while it was valid. A verifier needs only public material: the trust roots from *TUF*, and the identity it expects. Exercise 3 does exactly that.

.Why `clusterimagepolicies.policy.sigstore.dev`, not `clusterimagepolicy`
[%collapsible]
====
OpenShift has a second kind with the same name, `ClusterImagePolicy` in `config.openshift.io`: a *node-level* signature policy that the container runtime checks when it pulls an image.
The policy controller's kind lives in `policy.sigstore.dev`. A bare `oc get clusterimagepolicy` picks one of the two, so name the group.
====

*What just happened:* the out-of-chain image was refused before a pod existed: policy `ogsr-parasol-claims-keyless` names it, and its one authority, `tekton-chains-keyless`, found no signature for its digest.
Note how the webhook first resolved the tag `:unsigned` to a digest: it checks the exact image the pod would run.
The pipeline's digest was admitted, though you deployed it by hand: the webhook judges *how the image was built*, not who deploys it.

.Why admission, if Conforma already checked?
[%collapsible]
====
They guard different doors.
Conforma runs *inside* the pipeline: it stops a release with a clear reason before the pipeline deploys anything.
Admission runs *at the cluster*, for every pod: it is the backstop for everything that never went through the pipeline — an image built by hand, copied from another registry, or typed into a Deployment.
Run only Conforma, and anyone with deploy rights can skip it; run only admission, and a bad release is found when a pod fails to start instead of in the pipeline.
====
