This module is console-heavy and its drama is *live*, not narrated: an alert that goes red while the room watches, and a pod ring that grows under load.
The signature beat is exercise 3 — *break the database, watch the alert fire* — and the closer is exercise 5, the HorizontalPodAutoscaler (HPA) scaling from 2 to 4 pods on its own.
That closer is *reliable but not quick*: measured over five runs it reached the ceiling of 4 every time, between *42 seconds and just under two minutes* after the burst starts (this page said "under half a minute" until 2026-08-14 — it was wrong, and a presenter who believes it will be standing in silence).
Two seams need your attention before you teach: attendees must have the *user-workload-monitoring editor* role in their `-dev` namespace or exercise 2 is a wall (pre-flight item 2), and the alert fires in *~3 minutes* — reliably now that the entry state scrapes every 10s, but only when attendees drive the *concurrent burst* the lab specifies (the 5xx window is only ~30s wide, so a gentle trickle or an edited-down serial loop banks too few 5xx to cross the threshold; see Q2 and the troubleshooting page), so coach them to run it as written and read the other signals while it cooks.

== Timing

Total hands-on: *~40 minutes*.
The two long poles are the alert's fire delay (mostly waiting, filled with the logs/metrics reading) and the trace exploration.

[cols="1,4,1,2",options="header"]
|===
| # | Exercise group | Attendee time | Measured core (as user2, 4.21.22)

| 1 | Read the golden signals + custom metric | ~9 min | `curl /q/metrics` instant; *Observe → Metrics* queries return immediately; the ServiceMonitor scrape interval is *10s* (load-bearing for Ex3), so a just-changed value shows up within ~10s
| 2 | Alert on what matters | ~5 min | `oc apply` the PrometheusRule instant; the thanos-ruler reports it `inactive` within *~40s*, and it appears in the attendee's *project-scoped* Observe view (`/dev-monitoring/ns/<user>-dev/alertrules?alert-source=user`) with an empty *State* column — the cluster-wide *Observe → Alerting* page shows them nothing (see Q1)
| 3 | Break it, watch the alert catch it | ~6 min | DB scale-to-0 *plus a 20-worker concurrent burst* → 5-min 5xx rate peaks ~*1.1/s* → alert *Pending* at *~50s*, *Firing* at *~170s* (~3 min total); deterministic with the *10s* scrape (the ~30s 5xx window spans ≥3 scrapes, so `rate()` sees a rising counter) — a gentle trickle or an edited-down serial loop banks too few 5xx to cross the line; recovery needs DB back *plus* an app restart (poisoned connection pool)
| 4 | Follow a request with a trace | ~7 min | traces present in *Observe → Traces* within seconds of a request; steady-state request durations are single-digit ms (the N+1 cost is structural, not wall-clock — see Q4)
| 5 | Autoscale under load with an HPA | ~7 min | burst drove CPU past *100%* every run (peaks *132–250%*); HPA reached the ceiling of *4* in *5 of 5* runs but took *42–115s* from `oc run` (42/47/70/83/115), often stepping *2 → 3 → 4*; the burst image does *not* pull — every node already has it, so the container is up *3–4s* — and the wait is the metrics path, *24–40s* before CPU first reads over 60% (re-measured 2026-08-14 as user5 on 4.22.8); settles *62–81%* at 4 replicas; scale-down held for the *5-min* stabilization window
| 6 | Survive a node drain with a PodDisruptionBudget (PDB) | ~6 min | PDB create instant; `ALLOWED DISRUPTIONS` reflects `healthy − minAvailable`; the drain itself is your demo
|===

[NOTE]
.How this timing was measured
====
Every core number above was captured performing the lab, not estimated — the alert-beat numbers re-measured against the 10s-scrape entry state on 2026-07-19, the *entire autoscaling row* re-measured as `user5` on OCP 4.22.8 on 2026-08-14 (five runs, each from a settled 2-replica floor), the rest as `user2` on 2026-07-11.
The alert fire timing is real: with the database scaled to zero *and the 20-worker concurrent burst*, the 5-minute 5xx rate climbed off zero to a peak around *1.1/s* and the rule went *inactive → pending (T+50s) → firing (T+170s)* (the ruler's own state names — the console's *State* column shows an empty `-` for the inactive baseline).
What makes it *deterministic* is the *10s* scrape: when the database dies the app returns 5xx only for the ~30-second window before its readiness probe pulls the pod from the router, and a 10s scrape samples that window three or four times, so `rate()` always sees the counter climb (a rising series like `3 → 9 → 112 → 298`) and the rule fires.
At the old *30s* scrape that same window was barely one scrape — the counter could be sampled just once, at its frozen final value, so `rate()` read zero and the alert never fired (the G3 flake: byte-identical runs fired on one attendee and froze at zero on another).
The concurrency is still required for *volume*: a serial one-at-a-time loop or the load generator's trickle alone banks too few 5xx to clear the line.
Budget the room a full 4 minutes for exercise 3 to land, and use the wait to walk the three-signals reading.
====

== How to know the room can move on

Two instruments tell you this without guessing, and neither is the clock. Each exercise ends on a `[.checkpoint]` block with a *✔ Verify:* line in the lab — that is the move-on signal, written for attendees to confirm before continuing. For the whole module, `ws verify observability-health-scale --user <u>` is the same self-check the attendee can run any time; a room reporting all checks green is actually done, not just out of time.

== Demo-mode notes

* Run `adm solve observability-health-scale --user {user}` first so the alert rule, HPA and PDB already exist — the demo *drives* the end state, it does not build it.
* *Start the database break first* (beat 2 of the arc) and let the ~3-minute fire timer run while you narrate the three signals — do not stand and wait for it.
* *Park the alerting tab on the project-scoped view* — `{ocp_console_url}/dev-monitoring/ns/{user}-dev/alertrules?alert-source=user`.
Demoing from the cluster-wide *Observe → Alerting* page shows an empty list when you present as an attendee identity, and switching pages mid-beat costs you the reveal.
* The HPA closer is the crowd-pleaser, but show it in the right place: the *Resources* side panel's *Pods* list grows from 2 to 4.
The Topology status *ring* does NOT subdivide by pod count — it is pixel-identical at 2 and at 4 replicas (grounded 2026-07-31), so pointing at the ring and saying "watch it grow" shows the room nothing.
Have a terminal with `oc get hpa parasol-claims -w` on a second screen so the room sees CPU spike past 60% and replicas climb in real time.
* Clean up the burst pod between runs (`oc delete pod claims-burst -n {user}-dev`) — a forgotten burst keeps CPU high and the HPA pinned at 4.

== Top questions attendees ask

*1. "Why do I get `Forbidden` — and why is *Observe → Alerting* empty when my rule clearly exists?"*::
Both are the same wall: attendees hold *project*-scoped monitoring rights, not cluster-scoped ones.
`curl`-ing PromQL against the `thanos-querier` route fails because that route enforces a cluster-monitoring view permission attendees do not have (and this cluster exposes only that route, not the namespaced tenancy port).
The console's *cluster-scoped* alerting page (`/monitoring/alertrules`) fails the same way — the call behind it returns `Forbidden (verb=get, resource=prometheuses, subresource=api)`, so the page renders *0 - 0 of 0* and offers no *Project* selector.
The supported developer surfaces are the *project-scoped* ones: *Observe → Metrics* for PromQL, and `/dev-monitoring/ns/<user>-dev/alertrules?alert-source=user` for the attendee's own alert rules — both query with the attendee's identity, scoped to their namespace.
Treat `curl /q/metrics` as the raw-truth surface and those project-scoped console views as the query surface — that split is intentional in the lab, not a workaround.

*2. "My alert took forever to fire — is it broken?"*::
No — it is `for: 2m` on a `rate(...[5m])`.
The 5-minute rate has to climb past the 0.1/s threshold (about a minute of sustained 5xx), *then* stay above it for the 2-minute `for:` window before it fires.
With the concurrent burst, that was ~50s to *Pending* and ~170s to *Firing*.
The delay is a feature: it stops a two-second blip from paging anyone.
(If it *never* fires, the load step wasn't the concurrent burst — a gentle trickle or an edited-down serial loop banks too few 5xx in the ~30s window to cross the line; see the troubleshooting page.)

*3. "Does the database come back on its own — and why does the app keep erroring after I bring it back?"*::
Two things.
First, *no* — the entry app runs with Argo self-heal *off* (an attendee's edits to the lab workloads are the whole point of the lab, so Argo does not revert them), so `claims-db` stays at zero until someone scales it back up.
Recovery is a deliberate two-step: scale the database back *and* `oc rollout restart deploy/parasol-claims`.
Second, the app keeps erroring *after* the database returns because its connection pool is full of dead connections pointing at the terminated database pod; a healthy database does not heal a poisoned pool, so the restart is what actually fixes it.
Both steps are real and worth naming out loud.

*4. "The trace doesn't show the N+1 database queries — I just see one span."*::
Correct, and expected.
The claims image emits the *HTTP request* span today; per-query *database* spans need a build-time flag on the image that is tracked as an enhancement.
The N+1 is real in the code (one `SELECT` per event), but at a warm in-cluster database it costs only a few milliseconds, so it does not stand out in steady-state timing.
Teach it as "the trace tells you *which* endpoint is the outlier; the code tells you *why*," and point at the go-deeper note.
Do not promise a database-span staircase this image cannot render.

*5. "Why won't the HPA scale back down after I stop the load?"*::
The default *5-minute scale-down stabilization window*.
The HPA deliberately holds the higher replica count for five minutes after utilization drops, so a brief lull does not trigger a shrink-then-grow flap.
You will see `TARGETS` fall below 60% while `REPLICAS` stays at 4 — that is correct.
Scale-*up* has no equivalent stabilization window — but it is not instant either, and the room will notice.
Measured over five runs, `REPLICAS` reached 4 between *42 and 115 seconds* after `oc run`, often stepping *2 → 3 → 4* rather than jumping.
The image is not why: the burst container is up *3–4s* and pulls nothing at all.
The wait is the *metrics* path — *24–40s* before CPU first reads above the 60% target, and then another sample for each step of the climb.
What genuinely has no delay is the autoscaler's *decision*: in every instrumented run `desiredReplicas` moved in the very same sampling interval that first showed CPU over target.
Tell the room they are waiting on a scrape, or the pause reads as a broken exercise.

== Watchouts

* *Attendees must read their alert rule in the PROJECT-scoped Observe view.*
The cluster-wide *Observe → Alerting* page in the masthead reads a cluster-scoped monitoring API attendees are not granted: it renders *0 - 0 of 0* for them, filters make no difference, and it has no *Project* selector.
Everyone who wanders there concludes their rule failed to load.
The lab links `/dev-monitoring/ns/<user>-dev/alertrules?alert-source=user` directly — point at the link, not at the nav.
Two traps on that page even when they land right: *Source* defaults to *Platform* (zero rows for an attendee — the lab's link pins it to *User*), and at the healthy baseline the *State* column reads `-`, not the word *Inactive*.
Say the dash out loud before anyone reports it as a bug.
* *The monitoring-edit RBAC grant is the single most likely session-killer.*
If it is missing, exercise 2 fails for *everyone* and so does attendee-run `ws verify observability-health-scale` (it reads the ServiceMonitor and the rule).
Confirm pre-flight item 2 prints `yes` for a real attendee id before you start.
* *Tempo runs a monolithic in-memory backend on the shared cluster.*
Traces are *recent-only* — there is no long retention.
If exercise 4 shows an empty trace list, drive a request first (the load generator does this continuously) and refresh; do not go hunting for hours-old traces.
* *`parasol-web` is not OpenTelemetry-instrumented*, so there is no web → claims → db distributed trace yet — the real trace is claims → db, and the objectives' "through web→claims→db" is a future enhancement.
Do not demo a front-end hop that does not exist.
* *The break-fix leaves the app needing a restart.*
If an attendee scales the database back but skips the `rollout restart`, their claims API keeps 500-ing and they think they are stuck.
That *is* the lesson — but be ready to point at it during the exercise.
* *Clean up burst pods.*
A `claims-burst` pod left running keeps CPU high, pins the HPA at 4, and skews the next attendee's baseline.
`oc delete pod claims-burst -n {user}-dev`.
* *The alert needs a _concurrent_ burst of failing load to fire.*
The claims API returns 5xx only for a *short window* — roughly *30 seconds*, from the database going away to the readiness probe pulling the pod from the router — so to clear the `0.1/s` threshold you have to bank *hundreds* of 5xx into it. The load generator's gentle trickle, or a *serial* one-at-a-time loop, banks only a couple of dozen: not enough, and the rule never leaves its idle state (an empty *State* column).
The lab's load step is a 20-worker concurrent burst for exactly this reason: it supplies the volume (5-minute rate peaking ~1.1/s), and the entry state's *10s* scrape samples the ~30s window several times so `rate()` sees the counter climb and the rule fires *deterministically* (at the old 30s scrape the same window was barely one sample — the G3 flake).
If someone edits it down to a single `curl` loop — or only scales the database to zero and waits — their alert will not fire.
Coach them to run the burst as written, and give the fire timer the full ~3 minutes.
