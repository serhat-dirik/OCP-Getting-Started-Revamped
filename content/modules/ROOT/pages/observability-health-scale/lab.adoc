Your claims service is already *instrumented and running under a steady trickle of traffic* — a load generator continuously lists claims, reads a claim's history, files a new claim, and looks up a claim that does not exist.
That traffic is what lights up every signal you are about to read.
You will consume the three signals, alert on the service, break it on purpose to watch the alert fire, trace a request, then make the service *autoscale* and *survive a node drain*.

[NOTE]

====
Keep two things open: a *terminal* logged in as `{user}` (the CLI tab of each step runs there), and the {ocp_console_url}[OpenShift web console^] (the Console tab).

== 1. Read the golden signals and your custom metric
⏱ *~9 min* · find request rate, errors and latency — and the business metric the team added

The claims service exposes Prometheus metrics at `/q/metrics`, and a *ServiceMonitor* (shipped with your environment) already tells user-workload monitoring to scrape them.
So the same numbers exist in two places: raw at the app, and aggregated-and-queryable in the platform's monitoring.
You will look at both — that gap *is* the ServiceMonitor's job.

Start at the source.
The raw endpoint is the ground truth every other view is built from.

Running ad-hoc PromQL from the terminal needs a cluster-monitoring view role most attendees do not have, so treat the console as the PromQL surface and `curl /q/metrics` as the raw-truth surface.

== 2. Alert on what matters
⏱ *~5 min* · turn "the 5xx rate is too high" into a rule that pages you

A dashboard only helps when someone is looking at it.
An *alert* watches a metric for you and fires when it crosses a line.
You author it as a *PrometheusRule* in your own namespace — user-workload monitoring scopes it to `{user}-dev`, so it is *your* alert, invisible to other tenants.

The rule below fires when the claims API's *server-error* (5xx) rate stays above 0.1/s for two minutes.
At the healthy baseline the load generator produces only 404s (client errors), so the rule loads *armed but inactive* — exactly what you want.

[source,yaml,subs="attributes"]
----
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: parasol-claims-alerts
  namespace: {user}-dev
  labels:
    app: parasol-claims
spec:
  groups:
    - name: parasol-claims.rules
      rules:
        - alert: ParasolClaimsErrorRateHigh
          expr: sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m])) > 0.1
          for: 2m
          labels:
            severity: warning
          annotations:
            summary: "parasol-claims is returning server errors"
            description: "The claims API 5xx rate has exceeded 0.1/s for 2m."

== 3. Break it, and watch the alert catch it
⏱ *~6 min* · take the database away, read all three signals, then recover

Now earn the alert.
The claims service depends on its database; take the database away and the API starts returning 500s.
You will watch the alert climb out of that idle `-` — through *Pending* to *Firing* — and see how each of the three signals reads during a real fault.

The database is gone — but the claims API returns server-errors only inside a *short window*, and threading that window is the whole subtlety of this step.
For the first ~30 seconds the database is still draining, so requests still succeed (*200*).
Once it is truly gone the API fails (*500*) — until, about a minute in, three failed `/q/health/ready` checks (ten seconds apart) trip the readiness probe and the *router* pulls the pod from rotation, after which every request gets a *503* straight from the router and nothing more reaches the app to record a 5xx.
So the entire 5xx signal is banked in a roughly *30-second* window, and two things must line up for the alert to catch it:
you have to bank *enough* server-errors to clear `0.1/s` with margin, and the scrape has to *sample the rising counter more than once* before the pod leaves rotation.
A *concurrent burst* of twenty workers handles the first — hundreds of 5xx, not a couple of dozen — and the ServiceMonitor's *10-second* scrape handles the second: a 30-second window spans three scrapes, so `rate()` reliably sees the counter climb.
(At a 30-second scrape it might sample that window only once, at its frozen final value, so `rate()` reads zero and the alert never fires even though the app plainly failed — which is exactly why the scrape is 10s.)
Run it from the terminal (it works whichever lane you picked) and watch the sampled status walk through the three stages — *200* while the database drains, *500* once it is gone, then *503* once the readiness probe pulls the pod (that last `503` is the probe doing its job — the platform stops sending traffic to a pod that says it is not ready):

[source,sh,role=execute]
----
# 20 workers bank hundreds of 5xx in the ~30s window between "DB gone" and the
# readiness probe (~1 min in) pulling the pod from the router — enough, and sampled
# often enough by the 10s scrape, to push rate(...[5m]) past 0.1/s:
end=$(( $(date +%s) + 90 ))
for w in $(seq 1 20); do
  ( while [ "$(date +%s)" -lt "$end" ]; do curl -s -o /dev/null "$CLAIMS/api/claims"; done ) &
done
# meanwhile, sample the status once a second so you can watch 200 -> 500:
while [ "$(date +%s)" -lt "$end" ]; do
  curl -s -o /dev/null -w 'GET /api/claims -> HTTP %{http_code}\n' "$CLAIMS/api/claims"
  sleep 1
done
wait
----

While it climbs, read the *three signals* on the same fault — this is the whole module in ninety seconds:

* *Metrics* say *what*: in *Observe → Metrics*, `sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))` rises off zero and keeps climbing.

[NOTE]
.Measured: how long until it fires — and why the scrape interval is the real lesson
====
With the concurrent burst, the 5xx rate cleared `0.1/s` within about *50 seconds* and peaked around *1.1/s* — comfortably over the line — then held there through the `for: 2m` window.
`ParasolClaimsErrorRateHigh` reached *Pending* about *50 seconds* after the database went down and *Firing* about two minutes later — close to *3 minutes* end to end.
Plot the counter itself in *Observe → Metrics* (`http_server_requests_seconds_count{status=~"5.."}`) and you can watch the mechanism: it climbs across several 10-second scrapes — a rising series like `3 → 9 → 112 → 298` — and then *freezes*, because once the readiness probe pulls the pod from the router the burst gets `503` s and nothing more reaches the app to increment it.
The alert fires off that captured climb: `rate(...[5m])` sees the rising counter, crosses the line, and stays over it through the `for:` window.
The freeze is the observability lesson twice over.
First, a failing pod stops producing the signal *exactly* when you most want it — so the alert fires off the *last climb* and then *lingers* in Firing while that count ages out of the 5-minute window (the same reason recovery isn't instant, below).
Second — and this is why the scrape is *10 seconds*, not 30 — the whole 5xx climb happens inside a ~30-second window.
A 10-second scrape samples that window three or four times, so `rate()` sees the rise; a 30-second scrape might sample it *once*, at the frozen value, and `rate()` would read a flat *zero* — the alert would never fire even though the app plainly failed.
The scrape interval bounds the shortest fault your alert can catch; the two-minute `for:` window is deliberate on top of that, so a brief blip never pages anyone.
====

== 6. Survive a node drain with a PodDisruptionBudget
⏱ *~6 min* · guarantee a minimum of healthy pods through voluntary disruption

Autoscaling handles load.
Node *maintenance* is the other thing that moves your pods: every patch cycle, nodes are cordoned and drained.
A *PodDisruptionBudget (PDB)* is the contract that stops a drain from taking your service down — "you may evict my pods, but never leave me fewer than one healthy."

Create the budget:

[tabs]
====
Console::
+
--
Use *+* (*Import YAML*), paste the budget, set the namespace to `{user}-dev`, and *Create*:

[source,yaml,subs="attributes"]
----
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: parasol-claims
  namespace: {user}-dev
spec:
  minAvailable: 1
  selector:
    matchLabels:
      app: parasol-claims
----
--
CLI::
+
--
// `ws start` does NOT clear a leftover PodDisruptionBudget from a prior pass on this same cluster
// (only `ws reset`/`ws prep` do) — clear it first, safe even on a first run (no-op if absent):
[source,sh,role=execute]
----
oc delete pdb parasol-claims -n $NS --ignore-not-found=true
oc create pdb parasol-claims --selector=app=parasol-claims --min-available=1 -n $NS
oc get pdb parasol-claims -n $NS
----

.Expected output (ALLOWED DISRUPTIONS = current healthy − minAvailable, so it tracks the live replica count)
[%collapsible]
=====
[source,texinfo]
----
poddisruptionbudget.policy/parasol-claims created
NAME             MIN AVAILABLE   MAX UNAVAILABLE   ALLOWED DISRUPTIONS   AGE
parasol-claims   1               N/A               3                     1s
----
=====
--
====

`ALLOWED DISRUPTIONS` is the whole story, and it tracks your *current* healthy pod count.
The HorizontalPodAutoscaler from the previous exercise is likely still holding *four* replicas (the 5-minute scale-down window), so with `minAvailable: 1` the platform will let *three* be evicted at a time — never the last one.
As the HPA settles back to the floor of *two*, that number falls to *one*: the budget is a live promise, not a fixed count.

[IMPORTANT]
.The node drain is an instructor-run demonstration
====
Draining a real node moves *every* tenant's pods on it, so it is run once by the instructor against the shared cluster — do not drain a node yourself.
Watch what happens to *your* service while they do: `oc get pods -n {user}-dev -w`.
As the node drains, one `parasol-claims` pod is evicted and a replacement schedules elsewhere, but a second pod is *held* until the first replacement is healthy — the budget paces the drain so your claims API never drops below one serving pod.
The mechanism is the eviction API refusing the disruptive request: on the build run, evicting past the budget returned `Cannot evict pod as it would violate the pod's disruption budget`.
====
