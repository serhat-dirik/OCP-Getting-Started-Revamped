.Counts, rates, and why port 9092
[%collapsible]
=====
The console's query engine is user-workload monitoring's Thanos.
`curl /q/metrics` gives you an instantaneous *count*; turning counts into *rates* over a time window (`rate(...[5m])`), or summing across replicas, is what a query engine does.
The console's *Observe → Metrics* is one door to that engine.
The terminal has another: the in-cluster *tenancy* port of `thanos-querier`, which answers with your own token, scoped to your namespace.
Port `9092` has no Route, so this works only from the cockpit terminal; the `thanos-querier` Route needs a cluster-monitoring role you do not have.

.Why the cluster-wide page is empty, and what the project view shows
[%collapsible]
====
The masthead's cluster-wide *Observe* → *Alerting* page queries a *cluster-scoped* monitoring API that a project-level identity is not granted — it answers `Forbidden (verb=get, resource=prometheuses, subresource=api)` — so it lists *0 - 0 of 0* rules for you.
Your rule is missing from it no matter how you filter, and the page has no *Project* selector to point at your namespace.
The project-scoped link above is the surface that queries *per-namespace* monitoring with your identity, and it finds the rule.
It carries a *Project* selector (set to `{user}-dev`) and the tabs *Events* | *Alerting rules* | *Alerts* | *Dashboards* | *Metrics* | *Silences*.
One filter to watch on it: *Source* defaults to *Platform*, which matches nothing you authored.
The link already pins *Source* to *User*; if the list ever looks empty, that filter is the first thing to check.
====

.Creating the rule was denied?
[%collapsible]
====
If either path returns `Forbidden ... cannot create resource "prometheusrules"`, your namespace is missing the user-workload-monitoring editor role.
That is a one-line platform grant, not a mistake on your part — see xref:observability-health-scale/troubleshooting.adoc[the troubleshooting page].

TIP: *Predict, then run:* the database is gone. What status will the first sampled request return?

From the terminal (either lane), hit the API with twenty workers for 90 seconds while sampling the status once a second:

[source,sh,role=execute]
----
# 20 workers bank hundreds of 5xx in the ~30s window between "DB gone" and the
# readiness probe (~1 min in) pulling the pod from the router — enough, and sampled
# often enough by the 10s scrape, to push rate(...[5m]) past 0.1/s:
end=$(( $(date +%s) + 90 ))
for w in $(seq 1 20); do
  ( while [ "$(date +%s)" -lt "$end" ]; do curl -s -o /dev/null "${CLAIMS:?is empty - run the first block of this exercise again}/api/claims"; done ) &
done
# meanwhile, sample the status once a second so you can watch 200 -> 500:
while [ "$(date +%s)" -lt "$end" ]; do
  curl -s -o /dev/null -w 'GET /api/claims -> HTTP %{http_code}\n' "${CLAIMS:?is empty - run the first block of this exercise again}/api/claims"
  sleep 1
done

.Why twenty workers, and why a 10-second scrape
[%collapsible]
====
The claims API returns server-errors only inside a *short window*, and threading that window is the whole subtlety of this step.
For the first ~30 seconds the database is still draining, so requests still succeed (*200*).
Once it is truly gone the API fails (*500*) — until, about a minute in, three failed `/q/health/ready` checks (ten seconds apart) trip the readiness probe and the *router* pulls the pod from rotation, after which every request gets a *503* straight from the router and nothing more reaches the app to record a 5xx.
So the entire 5xx signal is banked in a roughly *30-second* window, and two things must line up for the alert to catch it:
you have to bank *enough* server-errors to clear `0.1/s` with margin, and the scrape has to *sample the rising counter more than once* before the pod leaves rotation.
A *concurrent burst* of twenty workers handles the first — hundreds of 5xx, not a couple of dozen — and the ServiceMonitor's *10-second* scrape handles the second: a 30-second window spans three scrapes, so `rate()` reliably sees the counter climb.
(At a 30-second scrape it might sample that window only once, at its frozen final value, so `rate()` reads zero and the alert never fires even though the app plainly failed — which is exactly why the scrape is 10s.)
That last `503` is the probe doing its job: the platform stops sending traffic to a pod that says it is not ready.

.Measured: how long until it fires — and why the scrape interval is the real lesson
[%collapsible]

With the concurrent burst, the 5xx rate cleared `0.1/s` within about *50 seconds* and peaked around *1.1/s* — comfortably over the line — then held there through the `for: 2m` window.

The freeze is the observability lesson twice over.
First, a failing pod stops producing the signal *exactly* when you most want it — so the alert fires off the *last climb* and then *lingers* in Firing while that count ages out of the 5-minute window (the same reason recovery isn't instant, below).
Second — and this is why the scrape is *10 seconds*, not 30 — the whole 5xx climb happens inside a ~30-second window.

The scrape interval bounds the shortest fault your alert can catch; the two-minute `for:` window is deliberate on top of that, so a brief blip never pages anyone.

Two things stretch it, and neither is the image: the container is up *3–4 seconds* after `oc run`, and the kubelet reports it *already present on machine* and pulls nothing at all.
First the *metrics* path — CPU has to be scraped and handed to the autoscaler, which took *10–33 seconds* before `TARGETS` moved off its idle reading at all, and *24–40 seconds* before it first read above 60%, so `REPLICAS` sits at 2 (and `TARGETS` may even dip) for a while.
Second, the climb is often a *staircase*: three of the five runs went 2 → 3 → 4 rather than straight to the ceiling, and every step waits on another CPU sample — which is what puts the slowest run near two minutes.
The autoscaler's *decision* is the fast part: in every instrumented run `desiredReplicas` moved in the very same sampling interval that first showed CPU over target.
What you wait on is the measurement, and then the pods.

== 6. Survive a node drain with a PodDisruptionBudget

*You'll end with:* a *PodDisruptionBudget (PDB)* that let a drain evict every pod but the last, and the last only once a replacement was Ready.

.Why not drain a real node?

TIP: *Predict, then run:* four replicas, `minAvailable: 1`. How many of four back-to-back evictions will the API admit?

The block defines an `evict` helper (one `Eviction`, the request `oc adm drain` sends), then evicts every `parasol-claims` pod back to back: the worst case, as if all of them sat on the drained node.

[source,sh,role=execute]

REFUSED=""
for P in $(oc get pod -n $NS -l app=parasol-claims -o jsonpath='{.items[*].metadata.name}'); do
  echo "── evict $P"; evict $P || REFUSED=$P
done
oc get pdb parasol-claims -n $NS
----

=== Brief

image::observability-health-scale/observability-health-scale-01-three-signals.svg["The three signals: a claims request fanning out to metrics, logs and traces, with the question each answers best — metrics for how much, how fast and how bad, logs for what exactly happened in one event, traces for where the time went across services."]

*The three signals, in five minutes*

Observability rests on three kinds of telemetry, and each answers a question the others answer badly. *Metrics* are cheap numbers over time — request rate, error rate, latency, CPU. They are always on, they aggregate across every replica, and they are what you alert on. A metric will say the 5xx rate just tripled; it will not say which claim failed.

*Logs* are individual events with full detail — the stack trace, the offending claim number. They answer "what exactly happened" for one occurrence, but at scale they are a firehose nobody reads live. *Traces* follow one request across every service and database call it touched, and show where the time went. The discipline is: metrics to notice and alert, traces to locate, logs to confirm the detail.

None of that is a separate purchase. OpenShift ships user-workload monitoring built in, and getting an application into it is one small object — a *ServiceMonitor* saying "scrape this Service's `/q/metrics` every ten seconds". Tempo and OpenTelemetry install as operators under the same subscription. Teams that treat "add monitoring" as a procurement project are usually re-buying what they already own.

*Scaling is a decision, not a reflex*

"It's slow — add replicas" is only sometimes the right answer. A *HorizontalPodAutoscaler* adds replicas when CPU or memory climbs with traffic, and it is the workhorse. Serverless scales to zero for services that are idle for long stretches, KEDA scales on queue depth rather than CPU, and a VerticalPodAutoscaler right-sizes one pod instead of adding more.

Autoscaling handles load. The other half of staying up is *voluntary disruption* — the node reboots and drains that happen every week for patching. A *PodDisruptionBudget* is the application's contract with the platform: take my pods for maintenance, but never leave me fewer than N.

*In this demo*

. The alert firing, and a recovery that takes two steps rather than one
. The autoscaler absorbing a traffic spike with no human and no ticket
. A disruption budget that keeps routine node maintenance from becoming an outage

== Frequently asked questions

*How long does an alert take to fire, and is that tunable?*::
This one took about three minutes: roughly fifty seconds for the five-minute error rate to climb past `0.1/s`, then the rule's `for: 2m` window on top. Both halves are yours to set. The delay is deliberate — it is what stops a two-second blip from paging anybody — and the practical floor is the scrape interval, because an alert can only react to what a scrape captured.

*Why did recovery take two steps rather than one?*::
Bringing the database back does not heal the application's connection pool, which is still full of dead connections pointing at the terminated database pod. The rollout restart is what actually fixes it. That is a real production failure mode rather than a quirk of the demo, and it is the kind of thing a trace makes obvious and a dashboard does not.

*Do developers need cluster-wide access to see their own metrics and alerts?*::
No, and they should not have it. Developers hold project-scoped monitoring rights: *Observe → Metrics* for PromQL and the project-scoped alert-rules view both query with the developer's own identity, restricted to their own namespaces. The cluster-wide alerting page needs a cluster-monitoring grant and is for the platform team. Same data, two audiences, one RBAC model.

*Why does the trace show one span rather than every database query?*::
This build emits the HTTP request span; per-query database spans need a build-time flag on the image. The distinction matters in practice: the trace tells you *which* endpoint is the outlier, and how much of its time is its own rather than a dependency's. Going a level deeper into individual queries is a configuration change, not a re-instrumentation project.

*Why does the autoscaler hold the extra replicas after the load stops?*::
A five-minute scale-down stabilization window, on by default. `TARGETS` falls below the 60% target while `REPLICAS` stays at 4 — that is correct behaviour, and it is what stops a brief lull from triggering a shrink-then-grow flap. Scale-up has no equivalent window, but it is not instant either: the wait is the metrics path, 24–40 seconds before CPU first reads above target.
