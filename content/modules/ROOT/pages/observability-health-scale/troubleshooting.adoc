== Creating the PrometheusRule is denied: `Forbidden ... cannot create resource "prometheusrules"`

Symptom:: In exercise 2, `oc apply` (or console *Import YAML*) of the alert rule returns `prometheusrules.monitoring.coreos.com is forbidden: User "<user>" cannot create resource "prometheusrules" in ... namespace "<user>-dev"`.
Cause:: The project `admin` role does not include the `monitoring.coreos.com` API group.
Authoring a `PrometheusRule` (or reading a `ServiceMonitor`) needs the `monitoring-edit` ClusterRole bound in your namespace — a *platform* grant, not something you did wrong.
Fix:: This is a workshop-layer RoleBinding your platform team applies per attendee; it is not self-service.
Flag it to your instructor.
For reference, the binding is:
+
[source,yaml]
----
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: monitoring-edit
  namespace: <user>-dev
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: monitoring-edit
subjects:
  - apiGroup: rbac.authorization.k8s.io
    kind: User
    name: <user>
----
Once it is in place, `oc auth can-i create prometheusrules -n <user>-dev` prints `yes` and the rule applies.
The same grant is what lets `ws verify observability-health-scale` read your ServiceMonitor and rule.

== *Observe → Alerting* shows no rules at all — my rule is not there

Symptom:: You created the `PrometheusRule` successfully, but the console's *Observe* → *Alerting* → *Alerting rules* page lists *0 - 0 of 0*.
Filtering for `ParasolClaimsErrorRateHigh` changes nothing, and there is no *Project* selector to point at your namespace.
Cause:: That is the *cluster-scoped* alerting page (`/monitoring/alertrules`).
It reads a cluster-wide monitoring API that a project-level identity is not granted — behind the empty list, the call returns `Forbidden (verb=get, resource=prometheuses, subresource=api)`.
Your rule exists and is being evaluated; you are just looking at a surface that cannot show it to you.
Fix:: Use the *project-scoped* Observe view for your namespace instead — the {ocp_console_url}/dev-monitoring/ns/{user}-dev/alertrules?alert-source=user[*Alerting rules* view for `{user}-dev`^], which the lab links directly (`/dev-monitoring/ns/<user>-dev/alertrules?alert-source=user`).
It renders a *Project* selector set to your namespace, the tabs *Events* | *Alerting rules* | *Alerts* | *Dashboards* | *Metrics* | *Silences*, and lists `ParasolClaimsErrorRateHigh` with severity *Warning* and source *User*.
+
Two follow-on traps on that page:
+
* *Source* defaults to *Platform*, which matches nothing an attendee authored — a *Platform*-filtered list is empty even in the right view. The lab's link pins *Source* to *User*; if you navigated another way, switch the filter to *User* or clear the filters.
* At the healthy baseline the *State* column reads `-`, not the word *Inactive*. That dash is the expected "loaded and watching, nothing active" state, not a sign the rule failed to load. A brand-new rule needs about a minute to appear at all. From the terminal, exercise 2's rules query prints the engine's own state: `ParasolClaimsErrorRateHigh  inactive  ok`.

== My alert never fires even though the app is clearly failing

Symptom:: You scaled the database to zero and the claims API is failing, but `ParasolClaimsErrorRateHigh` never reaches *Firing* — its *State* stays at `-` (or flips briefly to *Pending* and falls back).
Cause:: The load step you ran was not the *concurrent burst* the lab specifies.
The claims API returns 5xx only for a short window — roughly *30 seconds*, between the database going away and the readiness probe pulling the pod from the router (after which every request gets a `503` from the router and nothing reaches the app to record another 5xx).
To trip a `rate(...[5m]) > 0.1` rule off that short window you have to bank *hundreds* of 5xx into it, not a couple of dozen.
Just scaling the database to zero (leaving only the load generator's gentle trickle), or editing the burst down to a *serial* one-request-at-a-time loop, banks too few — the 5-minute rate hovers at or below the `0.1/s` line and the `for: 2m` timer never completes.
Fix:: Run the load step as written — a *concurrent* burst of twenty workers — so you bank hundreds of 5xx into the ~30-second window, which the ServiceMonitor's 10-second scrape samples several times so `rate()` sees the climb:
+
[source,sh,role=execute]
----
end=$(( $(date +%s) + 90 ))
for w in $(seq 1 20); do
  ( while [ "$(date +%s)" -lt "$end" ]; do curl -s -o /dev/null "$CLAIMS/api/claims"; done ) &
done
wait
----
+
With the burst the 5-minute 5xx rate peaks around ~1.1/s and the rule reaches *Pending* at ~50s and *Firing* at ~170s (about 3 minutes).
The `for: 2m` window over a `rate(...[5m])` is deliberately slow so a brief blip does not page anyone — confirm the rule loaded (exercise 2's rules query prints its `state`, not just the object) and give it the full window.

== My PromQL query returns nothing, but the metric obviously exists

Symptom:: The alert says it is *Firing*, or the counter clearly has hundreds of samples, yet a PromQL query you run by hand for `http_server_requests_seconds_count` comes back *completely empty* — not a low number, literally zero series. Nothing errors; the answer is just blank.
Cause:: You queried the *wrong Prometheus*. This cluster runs *two independent* monitoring stacks, and they do not share data:
+
* *Platform monitoring* (`prometheus-k8s`, in `openshift-monitoring`) scrapes the cluster's own components. It never scrapes ServiceMonitors in your project, so it has *no knowledge whatsoever* of your application's metrics.
* *User-workload monitoring* (`prometheus-user-workload`, in `openshift-user-workload-monitoring`) is the one that scrapes your `ServiceMonitor`. `thanos-querier` federates both and is what the console's *Observe* pages query.
+
Measured on this cluster, same metric, same instant — platform returned *0* series, user-workload returned *4*.
This is a silent trap rather than an error, because an empty result is a perfectly valid PromQL answer. It is worth knowing beyond this lab: it is one of the most common ways a working alert looks broken on OpenShift.
Fix:: Query through `thanos-querier` (what the console uses) or the user-workload Prometheus directly — never `prometheus-k8s` — for anything your own application emits. The console's *Observe → Metrics* page in your project already does the right thing, so if the console shows data and your terminal does not, this is why.

== I brought the database back, but the claims API still returns 500

Symptom:: You ran `oc scale deploy/claims-db --replicas=1`, the database pod is `Running`, but `curl $CLAIMS/api/claims` keeps returning `HTTP 500`.
Cause:: The claims application is still holding *dead connections* in its Agroal connection pool — they point at the old database pod that no longer exists.
A healthy database does not heal a poisoned pool.
Fix:: Restart the app so it rebuilds the pool against the current database:
+
[source,sh,role=execute]
----
oc rollout restart deploy/parasol-claims -n <user>-dev
oc rollout status deploy/parasol-claims -n <user>-dev
----
Then `curl $CLAIMS/api/claims` returns `HTTP 200`.
This "recovery needs a restart" step is a real operational lesson — a dependency coming back does not always heal the caller.

== `curl`-ing PromQL against thanos-querier returns `Forbidden`

Symptom:: Following a generic monitoring how-to, you try `curl -H "Authorization: Bearer $(oc whoami -t)" https://thanos-querier.../api/v1/query ...` and get `Forbidden (user=<user>, verb=get, resource=prometheuses, subresource=api)`.
Cause:: The `thanos-querier` Route enforces a cluster-monitoring view permission attendees do not have.
It is the same wall as the empty *Observe → Alerting* page above — one grant, two symptoms.
Fix:: Query the in-cluster *tenancy* port instead: `https://thanos-querier.openshift-monitoring.svc:9092/api/v1/query`, with `namespace=<user>-dev` as a parameter.
It authorizes against your own namespace, so your token is enough.
Exercise 1 has the exact command; port `9093` serves `/api/v1/rules` the same way.
The tenancy ports have no Route, so run it from the cockpit terminal.
In the console, *Observe → Metrics* queries with your identity too.

== A dashboard panel says *No data*

Symptom:: In exercise 3, one or more panels of *Parasol claims* draw nothing, while the dashboard itself loads.
Cause:: The query ran and matched no series, for one of three usual reasons.
*No traffic yet:* right after `ws prep`, the claims metrics take a couple of minutes to reach the query engine (measured 2026-11-14: about two and a half minutes between `ws prep` returning and the first claims sample answering a query); the CPU panel comes from the platform, not the app, so it fills first.
*A typo in the query:* a misspelled metric or label matches nothing, and the panel cannot tell that apart from no traffic.
*A window shorter than the scrape:* container CPU arrives about every 30 seconds, so a `[1m]` window on the CPU panel draws a line with gaps; the lab uses `[2m]` for that panel.
Fix:: Run the panel's query by itself, in *Observe → Metrics* or from the terminal (exercise 1 has the command for port `9092`).
If it returns a value there, compare it with the file character by character; if it returns nothing there either, wait for traffic and refresh.
The *Server errors* panel ends in `or vector(0)` precisely so it draws a zero line, not *No data*, while the service is healthy.

== Every dashboard panel shows an error

Symptom:: The dashboard loads, but every panel shows an error instead of a line, while the same queries work from the terminal.
Cause:: Either the panels name a datasource that does not exist in your project, or the platform grant that lets the datasource send queries is missing.
Asked for a datasource that is not there, Perses answers `404` with `datasource doesn't exist`; the only one in your project is `thanos-tenancy`.
Perses sends every query as `POST`, and the tenancy port needs one extra grant for `POST` that plain `GET` from `curl` does not, so a missing grant fails only the dashboard.
// CAPTURE-VERIFY: the 404 text is the Perses datasource proxy's API answer, measured as user13 on
// 2026-11-14 (POST /proxy/projects/<ns>/datasources/thanos/... -> 404 "datasource doesn't exist").
// How the console panel renders that error was not captured; the media pass confirms it.
Fix:: Check the name first, and correct the file if it differs:
+
[source,sh,role=execute]
----
oc get persesdatasource -n <user>-dev
grep 'name: thanos' ~/parasol-claims-dashboard.yaml
----
+
If the name is `thanos-tenancy` everywhere and the panels still error, the grant is missing: `oc get rolebinding <user>-pod-metrics-reader -n <user>-dev` returns `NotFound`.
That binding is a workshop-layer grant; flag it to your instructor.

== My dashboard is not in the Dashboards (Perses) list

Symptom:: *Observe → Dashboards (Perses)* does not list *Parasol claims*.
Cause:: The list is filtered by project, or the dashboard was applied somewhere else.
Fix:: Set the project selector to `<user>-dev`, then confirm the object exists and was accepted:
+
[source,sh,role=execute]
----
oc get persesdashboard -n <user>-dev
oc get persesdashboard parasol-claims -n <user>-dev -o jsonpath='{.status.conditions[?(@.type=="Available")].message}{"\n"}'
----
+
`Dashboard (parasol-claims) created successfully` means Perses has it; an empty list means the `oc apply` ran without `-n <user>-dev` or failed, so re-run the exercise 3 block.

== Observe → Traces is empty

Symptom:: You open *Observe → Traces*, run `{ resource.service.name = "parasol-claims" }`, and get no results.
Cause:: Usually one of: no recent request has been traced (Tempo runs an in-memory backend on the shared cluster and keeps only *recent* traces), the time range is too narrow, or the shared collector is down.
Fix:: Drive a request and widen the range.
The load generator produces traffic continuously, so a request within the last few minutes should appear — hit the app yourself to be sure:
+
[source,sh,role=execute]
----
curl -s -o /dev/null "$CLAIMS/api/claims/CLM-1001/history"
----
+
Then refresh with a *Last 15 minutes* range.
If it is still empty, the collector may be down — that is a shared-stack issue for your instructor (`oc get pods -n ogsr-observability-workshop`), not something in your namespace.

== The trace only shows one span — where are the database queries?

Symptom:: You open a `parasol-claims` trace expecting to see the N+1 database queries, but there is a single HTTP request span and no `SELECT` children.
Cause:: The claims image emits the *HTTP request* span but not per-query *database* spans — database-span instrumentation is a build-time flag on the image, tracked as an enhancement.
The N+1 is real in the code, but invisible in the trace today.
Fix:: There is nothing to fix in your namespace.
Use the trace to identify *which* endpoint is the latency outlier (rank by duration), and read the code to see *why* (`GET /api/claims/\{claimNumber}/history` issues one query per event).
The database-span "staircase" appears once the image ships that flag.

== `claims-burst` is stuck `ImagePullBackOff` and the HPA never climbs

Symptom:: Right after `oc run claims-burst --image=registry.redhat.io/openshift4/ose-cli-rhel9:v4.22@sha256:… ...`, `oc get pods -n <user>-dev` shows `claims-burst` stuck in `ErrImagePull`/`ImagePullBackOff` instead of driving load, and `oc get hpa` never moves off its resting utilization.
Cause:: `claims-burst` is the only step in this module — indeed the only *unmediated* image pull an attendee makes anywhere in the workshop — that pulls straight from `registry.redhat.io` rather than the in-cluster registry or a pre-seeded entry-state image. That pull needs a valid Red Hat entitlement in the cluster's *global* pull secret (`pull-secret` in `openshift-config`), which every node shares. If that entitlement is missing, expired, or was never wired up on this cluster, this is the first place in the course it surfaces.
Fix:: You have a free control before you go anywhere near the pull secret: the burst uses the *same digest-pinned reference* as the `claims-load` Deployment your entry state already runs in this namespace.
+
[source,sh,role=execute]
----
oc get pods -n <user>-dev -l app=claims-load
----
+
If `claims-load` is `Running`, that exact image already pulled in this namespace and the cluster's entitlement is almost certainly fine — the likely cause is then a mangled image reference, so re-issue the burst by *clicking* the lab's command block rather than hand-copying it (the reference sits on a continuation line and is easy to truncate).
If `claims-load` is *also* stuck pulling, the problem is cluster-wide. Confirm it, then flag it — this is a platform-level credential, not something scoped to your namespace:
+
[source,sh,role=execute]
----
oc describe pod claims-burst -n <user>-dev | sed -n '/Events:/,$p'
----
+
An `unauthorized`/`pull access denied` reason in the events confirms the cluster's entitlement, not your namespace, is the problem — flag it to your instructor rather than retrying the same command.
Once the platform team fixes the pull secret, clean up and re-run:
+
[source,sh,role=execute]
----
oc delete pod claims-burst -n <user>-dev --ignore-not-found
----
+
then re-issue the `oc run` from the lab.

== My HPA shows `<unknown>/60%` and is not scaling

Symptom:: Just after `oc autoscale`, `oc get hpa` shows `TARGETS` as `<unknown>/60%` and the app is not scaling.
Cause:: Two possibilities: the metrics pipeline has not reported CPU for the new HorizontalPodAutoscaler (HPA) yet (it takes a short interval after creation), or the target container has no CPU *request*, so utilization cannot be computed.
The entry-state app *does* set a 200m CPU request, so on this lab it is almost always the former.
Fix:: Wait ~30 seconds and re-check — `TARGETS` resolves to a real percentage once the first CPU sample lands.
At an idle floor that reading is low: measured across five settled floors on 2026-08-14 it was 4%, 4%, 5%, 9% and 13% against the 60% target.
If it stays `<unknown>`, confirm the request is present: `oc get deploy parasol-claims -n <user>-dev -o jsonpath='{.spec.template.spec.containers[0].resources.requests.cpu}{"\n"}'` should print `200m`.

== The burst is running but `REPLICAS` is still 2

Symptom:: `claims-burst` is `Running`, but `oc get hpa` still shows `REPLICAS 2` — sometimes with `TARGETS` sitting below 60%, sometimes already above it — and it has been like that for a minute.

Cause:: Almost always *nothing is wrong and you have not waited long enough*.
Measured over five runs on 2026-08-14, `REPLICAS` reached the ceiling of 4 between *42 and 115 seconds* after the burst started — every run got there, but the slowest took nearly two minutes.
Two delays stack up. CPU has to be scraped and handed to the autoscaler, which took *24–40 seconds* before `TARGETS` first read above 60% at all; then the climb is often a *staircase* (2 → 3 → 4, three of the five runs), and each step waits for another CPU sample before the autoscaler will take it.

Fix:: Watch it rather than re-running it — `oc get hpa parasol-claims -n <user>-dev -w` — and give it a full *two minutes* before concluding anything.
Re-issuing the burst does not help and starting a *second* one skews the reading.
If you are past two minutes with `TARGETS` still stuck at its idle percentage, check that the burst is actually generating traffic:
+
[source,sh,role=execute]
----
oc get pod claims-burst -n <user>-dev
oc adm top pod claims-burst -n <user>-dev
----
+
A healthy burst reads *hundreds of millicores* — it was measured pegged near *1500m*.
A burst showing single-digit `m` is not driving load: delete it and re-issue the `oc run` from the lab, taking the command from the lab's block rather than hand-copying it.

== The HPA will not scale back down after I stop the load

Symptom:: You stopped the burst, `TARGETS` fell below 60%, but `REPLICAS` stays at 4 for minutes.
Cause:: The default *5-minute scale-down stabilization window*.
The HPA holds the higher count so a brief lull does not cause a shrink-then-grow flap.
Fix:: Nothing — this is correct.
Wait ~5 minutes and it steps back toward the floor of 2.
(Scale-*up* has no equivalent hold, but it is not instant either — measured 2026-08-14, reaching 4 replicas took *42–115 seconds* from starting the burst, often stepping 2 → 3 → 4.)
