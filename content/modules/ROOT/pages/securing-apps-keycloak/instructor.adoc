Each attendee administers their own realm in the *Keycloak admin console*, and the drama is watching HTTP status codes change: an open API that starts returning *401*, a valid login that gets *403*, the same user flipping to *200* when the role is granted in the realm, and a token exchange that Keycloak flatly *refuses*.
App steps are *configuration* changes (`oc set env` / the console Environment tab) on an image that already carries the OpenID Connect (OIDC) library, and realm steps are clicks in the admin console (or its REST API in the CLI lane) — there is no build, so steps are fast and the room stays together.
Two things need your attention before you teach: exercise 4 contains a *deliberate break* (an `http` `redirect_uri` that Keycloak rejects) that every attendee is meant to hit and fix, so do not let them "fix" it early; and the whole module depends on the *workshop* Keycloak (`sso-workshop`) and each attendee's seeded realm being up — confirm pre-flight items 2 and 3 before the session.

== Timing

Total hands-on: *~48 minutes*.
There are no long waits — the pacing is set by the ~15-second rollouts after each config change, by the admin-console tour, and by reading tokens.

[cols="1,4,1,2",options="header"]
|===
| # | Exercise group | Attendee time | Measured core (as user6, 4.22.22)

| 1 | Admin-console sign-in, realm tour, first token | ~8 min | token get/decode *instant*; the admin-console tour and *Evaluate* are reading time (estimated — not timed in a browser)
| 2 | Protect the claims API (bearer) | ~5 min | `oc set env` → rollout *15s*; 401/200 immediately after
| 3 | Enforce a role, then grant and revoke it in the realm | ~10 min | second rollout *14s*; adjuster 200 / viewer 403; the grant → 200 and revoke → 403 are instant (no rollout)
| 4 | Protect the web frontend (break-fix) | ~5 min | two rollouts *14s* each; the `http`→400 break and the proxy-forwarding fix are the time sink (reading + understanding)
| 5 | Machine identity (client credentials) | ~5 min | one `curl` to the token endpoint; instant
| 6 | Debug tokens like an adult | ~5 min | pure decode/inspection; no cluster change
| 7 | [ADVANCED] token exchange (RFC 8693) | ~6 min | fraud rollout *14s*, then *~30s* before the new Route answers (503 until then); exchange + refusal instant
| 8 | Which front door did you come in through? (view-only) | ~3 min | two read-only `oc get` calls; discussion
|===

[NOTE]
.How this timing was measured
====
Every terminal number was captured performing the lab as `user6` on 2026-11-12 (first measured as `user1` on 2026-07-11), not estimated.
An `oc set env` + `oc rollout status` cycle took *14-15 seconds*; a token round-trip (`get_token` → `decode`) is well under a second.
The admin-console minutes are an estimate: the console steps were validated through the admin REST calls the console makes, not timed in a browser.
There is no multi-minute wait anywhere in this module, so the attendee-time figures are dominated by *reading and understanding*, not by the cluster — budget generously for exercises 3, 4, and 7 where the concept load is highest.
====

== How to know the room can move on

Two instruments tell you this without guessing, and neither is the clock. Each exercise ends on a `[.checkpoint]` block with a *✔ Verify:* line in the lab — that is the move-on signal, written for attendees to confirm before continuing. For the whole module, `ws verify securing-apps-keycloak --user <u>` is the same self-check the attendee can run any time; a room reporting all checks green is actually done, not just out of time.

== Pre-flight checklist

Run these before the session.
A sample user (`user1`) is used here; substitute any assigned attendee id.

`ws prep securing-apps-keycloak` waits up to *5 minutes* for the entry state to converge (no module-specific `waitSeconds` is declared, so this is the engine default). It normally returns well inside that — the ceiling is a timeout, not a duration. Attendees start it themselves from the top of the *concept* page, so deliver the concept at its normal pace and it converges under you.

. *A sample user's entry state materializes and verifies.*
+
[source,sh,role=execute]
----
adm start securing-apps-keycloak --user user1
ws verify securing-apps-keycloak --user user1 --entry-only
----
+
Expect `✅ all 9 checks passed`: `user1-dev` with `parasol-web` + `parasol-claims` + an ephemeral `claims-db`, *all unprotected* (`GET /api/claims` is 200 with no token), and *no `parasol-fraud` yet* (deploying it is exercise 7).

. *The workshop Keycloak is up — and it is NOT the cluster login IdP.*
*(REQUIRED — the whole module depends on it.)*
+
[source,sh,role=execute]
----
oc get keycloak -A
----
+
[IMPORTANT]
.There are two Keycloaks; the module uses the workshop one
=====
Expect *two* rows: `keycloak/keycloak` (the *cluster login* IdP — leave it alone) and `sso-workshop/sso-workshop` (the *workshop* instance this module uses).
[source,texinfo]
----
NAMESPACE      NAME           AGE
keycloak       keycloak       3d
sso-workshop   sso-workshop   95m
----
If `sso-workshop` is missing, the auth stack was not installed — the environment needs the `auth` profile/stack (`--stacks auth`, or `auth: true` in `bootstrap/vars.yaml`).
Nothing in the module works without it.
=====

. *The sample user's realm is seeded and issues tokens.*
*(REQUIRED — exercises 1-7 all get tokens from it.)*
+
[source,sh,role=execute]
----
oc get keycloakrealmimport realm-user1 -n sso-workshop -o jsonpath='{.status.conditions[?(@.type=="Done")].status}{"\n"}'
REALM=$(oc get cm ws-entry-securing-apps-keycloak -n user1-dev -o jsonpath='{.data.authServerUrl}')
curl -ks "$REALM/protocol/openid-connect/token" -d grant_type=password -d client_id=parasol-web \
  -d username=adjuster -d password=parasol -d scope=openid | jq -r 'if .access_token then "token OK" else .error end'
----
+
Expect `True` (the realm import completed) then `token OK`.
If the import status is not `True`, the realm was not seeded — realm imports are *import-once* and survive `ws reset`, so a missing realm is a workshop-layer gap (`gitops/workshop-config`), not something a reset fixes.

. *The sample user administers their realm, and holds nothing extra.*
*(REQUIRED — exercise 1 signs in to the admin console.)*
+
Open https://keycloak-sso-workshop.{cluster_domain}/admin/realm-user1/console/ in a private window and sign in as `user1` with the workshop password: the console opens on `realm-user1`.
Then, still as `user1`, open *Users* → `viewer` → *Role mapping*: it should read *No roles for this user*.
A `viewer` holding `claims-adjuster` is left over from a rehearsal — the realm is not reset by `ws prep` — and breaks exercise 3's *403*.

. *Attendees can read the cluster's identity providers.*
*(Exercise 8.)*
+
[source,sh,role=execute]
----
oc get oauth cluster --as=user1 --as-group=workshop-attendees --as-group=system:authenticated \
  -o jsonpath='{range .spec.identityProviders[*]}{.name}{"\t"}{.type}{"\n"}{end}'
----
+
Expect one row per provider, including `workshop-users` of type `HTPasswd`.
`Forbidden` means the install's attendee read grant on `oauth/cluster` is missing; exercise 8 then falls back to its expected output.

. *The end state solves — as a reference for grading, not as demo prep.*
+
[source,sh,role=execute]
----
adm solve securing-apps-keycloak --user user1
ws verify securing-apps-keycloak --user user1
----
+
Expect `✅ all 13 checks passed`: the entry checks *plus* the API protected (401 without a token, 200 with an `adjuster` token, 403 with a `viewer` token), the web frontend redirecting an unauthenticated request (302), and the two token-exchange checks.
`adm solve` also deploys `parasol-fraud` (the exchange target), which is what turns those last two on.
Those two protected-state expectations are the same reason `adm solve` must not be used as demo prep — see *Demo-mode notes*.
Reset with `ws prep securing-apps-keycloak --user user1 --yes` when done; if you are presenting, that reset is mandatory, not tidy-up.

. *A representative attendee command actually works — from the cockpit, as the attendee.*
+
[source,sh,role=execute]
----
adm smoke securing-apps-keycloak user1     # proves curl + jq are on PATH and parasol-web has an addressable Route, as the attendee, in the live cockpit
----
+
This is the only pre-flight instrument that runs *as the attendee*, in the real cockpit terminal — everything above runs as cluster-admin. This module is a curl-and-jq lab end to end (seventeen `jq` invocations decoding tokens by hand); expect all checks to pass.

== Demo-mode notes

* The arc *starts unprotected* and flips live — do *not* `adm solve` first, and the reason is worth knowing precisely, because the chart looks innocent if you read the wrong file.
`solve` is a single chart-wide flag, not a single object: `templates/solve-endstate.yaml` adds `parasol-fraud`, but the *same* flag also gates the OIDC blocks in `templates/parasol-claims.yaml` and `templates/parasol-web.yaml`, which is what flips both apps from unprotected to protected.
So a pre-solved namespace answers beat 1 with *401* instead of the open *200*, and beat 2's `oc set env` writes exactly the values the chart already applied — the opening beat and the signature beat both go away.
Run `ws prep securing-apps-keycloak --user {user} --yes` so the API is open, and define the lab's shell vars/helpers in your terminal first.
* The signature moment is beat 2: one `oc set env` and the same `curl` goes 200 → 401/200/403.
Have the three-line matrix (`no token` / `adjuster` / `viewer`) ready to paste the instant the rollout finishes.
* The `parasol-fraud` service the encore calls is *not* in the entry state, and `adm solve` is the wrong way to get it (see above).
Deploy it live from the exercise-7 manifest, which adds fraud alone and leaves the two apps untouched — the demo arc's *Before you present* block carries that manifest inline so you never have to leave the page you are presenting from.
The cleanest live arc is: `ws prep` (open) → flip claims live (beat 2) → deploy fraud during beat 4's narration, which changes nothing on the cluster and gives the pod a full beat to become ready → exchange (beat 5).
If you are *forced* to present from a solved namespace, do not run beats 1 and 2 as written: open on the protected state instead and *show* the 401/200/403 matrix rather than promising a flip the room will not see.
* Token lifetime is 30 minutes — long enough that a token you grabbed at the start of the demo is still valid at the encore, but if a beat 401s unexpectedly, `get_token adjuster` again.

== Top questions attendees ask

*1. "I required the `claims-adjuster` role but never set a role-claim-path — why did it just work?"*::
Because the Parasol image ships `quarkus.oidc.roles.role-claim-path=realm_access/roles` baked in.
Keycloak puts *realm* roles under `realm_access.roles`, not the top-level `roles` claim, so a framework has to be told where to look — and this image already is.
Make the teaching point explicit: on an app that does *not* set it, a user who has the role still gets *403*, and it is the single most common Keycloak-with-Quarkus bug.
Have them `decode` a token to see exactly where the role lives.

*2. "My web login fails with 'Invalid parameter: redirect_uri' — did I do it wrong?"*::
No — that is *exercise 4's deliberate break*, and every attendee should hit it.
The app is behind the edge Route (HTTPS terminated, HTTP forwarded to the pod), so it built an `http://` `redirect_uri` that the realm — which only trusts the `https://` callback — rejects.
The fix is `QUARKUS_HTTP_PROXY_PROXY_ADDRESS_FORWARDING=true`.
If someone's login fails *after* that, check they did not typo the client id (`parasol-web`) or the realm URL.

*3. "Can I break someone else's realm from the admin console?"*::
No.
Each attendee signs in as `{user}`, who holds `realm-admin` in `realm-{user}` only: the admin API answers *403* for any other realm and for `master`.
Inside their own realm they can change anything, and nothing resets it — `ws prep` restores the apps, not the realm.
The one change the lab makes, granting `claims-adjuster` to `viewer`, is undone in the same exercise; `ws verify` fails its `viewer` check if it was not.

*4. "The token-exchange escalation attempt returns 'Requested audience not available' — is that an error in the lab?"*::
That *is* the lesson — the exchange toward `parasol-batch` is *supposed* to fail.
The `parasol-claims` client is configured to mint tokens only for the `parasol-fraud` audience (via an audience mapper), so Keycloak refuses any other target.
That refusal is the proof that exchange can re-audience/downscope but never escalate.
The *successful* exchange in the same exercise is toward `parasol-fraud` (returns a token); the *refused* one is toward `parasol-batch` (returns the error).

*5. "Is this the same Keycloak that logs me in to the OpenShift console?"*::
No — deliberately.
The cluster login runs on a *separate* Keycloak (`keycloak/keycloak`); this module uses a *workshop* instance (`sso-workshop/sso-workshop`) with a throwaway realm per attendee, so nobody can lock themselves (or the room) out of the cluster by experimenting.
Exercise 8 has attendees read the cluster's identity providers and find the one they signed in through, which is the bridge to the multi-tenancy module — but the two instances are intentionally distinct.

== Watchouts

* *The workshop Keycloak (`sso-workshop`) is the single point of failure for the whole module.*
If it is down, *nothing* works — no tokens, no logins, no exchange.
It is separate from the cluster login IdP, so a healthy console login does *not* prove the workshop Keycloak is up.
Confirm pre-flight item 2 explicitly.
* *Never touch `keycloak/keycloak` or `oauth/cluster`.*
That instance backs live cluster logins.
The module only reads `oauth cluster` (exercise 8) and only ever writes to the `sso-workshop` realms via seeded imports.
Reconfiguring the login IdP can lock the room out of OpenShift.
* *Realms survive `ws reset` — including what attendees changed in them.*
`ws prep`/`reset` restores the *apps* in `{user}-dev`; it does *not* re-seed the realm (the realm is workshop-layer state, seeded once).
Attendees are realm administrators, so a role grant they forgot to remove, or a client they edited, outlives the reset.
The common one is `viewer` still holding `claims-adjuster`: exercise 3 then shows *200* where it promises *403*, and `ws verify` fails its `viewer` check. Remove the role in the admin console.
A realm broken beyond that is not fixed by a reset — escalate it as a platform-layer issue.
* *The break in exercise 4 is intentional — coach, don't pre-empt.*
Attendees are meant to configure the web app, watch the login fail with the `redirect_uri` error, and fix it.
If you warn them off it, you remove the lesson.
Let them hit it; be ready to explain the edge-Route/`X-Forwarded` mechanism when they do.
* *Client secrets in the lab are seeded demo values.*
`parasol-claims-secret` and `parasol-batch-secret` are workshop fixtures shown in the clear on purpose.
Name that out loud: in production these are generated, stored in a Secret, and never printed — this is a teaching shortcut, not a pattern to copy.
* *`viewer` getting 403 is success, not a bug.*
Some attendees read the `viewer` 403 as "my token is broken."
It is the whole point of exercise 3 — authenticated, not authorized.
Reinforce the 401-vs-403 distinction when it comes up.

== Provenance

Built fresh for this workshop; no content was ported from stale material, and no legacy SSO product branding is used — this is Red Hat build of Keycloak throughout.
Every command, output, and timing on these pages was produced performing the lab as `user1` on OpenShift 4.21.22 against the workshop Red Hat build of Keycloak 26.6 (instance `sso-workshop`, realm `realm-user1`) on 2026-07-11 — the open API at 200, the bearer matrix (401 no token / 200 adjuster / 403 viewer / 401 bad token), the web-app `http`→400 break and the proxy-forwarding fix (`https` 302 with `response_type=code` + PKCE `S256`), the `parasol-batch` client-credentials token, and the RFC 8693 exchange to `aud=parasol-fraud` (200) with the `parasol-batch` escalation Keycloak refused.
