== From an open API to single sign-on · 15 min

Parasol's claims API answers anyone who can reach it, and over fifteen minutes it gains bearer authentication with a role check, a browser login, a machine identity for the nightly batch job and a delegated call to a second service — without a line of authentication code being written.

[IMPORTANT]
.Prep — run before the session
====
This demo runs from the *entry* state, in which both Parasol applications are unprotected, and applies the protection live. Return `{user}-dev` to that state from the cockpit terminal:

[source,sh,role=execute]
----
ws prep securing-apps-keycloak
----

*Then run both of the command blocks that follow this Prep block, in the terminal you use for the demo.* They define `NS`, `CLAIMS`, `WEB`, `FRAUD` and `REALM` and the `get_token` and `decode` helpers, which the steps below read. With any of them unset, `curl` is handed an empty URL and answers `000` — the same number a dead service reports. They are the same two blocks the attendee lab opens with, rendered here from one source, so the two pages cannot drift apart.

*Do not stage the finished state.* `adm solve securing-apps-keycloak` sets the entry chart's `solve` flag, and that one flag does two things rather than one: it deploys `parasol-fraud` *and* it switches `parasol-claims` and `parasol-web` into their OIDC-protected form. On a solved namespace step 1 answers `401` instead of the open `200` the whole demo is built on, and step 2 writes exactly the values the chart has already applied. Deploy `parasol-fraud` from the manifest below instead — it adds the fraud service alone and touches neither application.

*Confirm the shell is ready.* This reports whether those two setup blocks have been run in this terminal; it reads nothing on the cluster, so it can never be answered by a namespace problem:

[source,sh,role=execute]
----
MISSING=""
[ -n "${NS:-}" ]     || MISSING="$MISSING NS"
[ -n "${CLAIMS:-}" ] || MISSING="$MISSING CLAIMS"
[ -n "${FRAUD:-}" ]  || MISSING="$MISSING FRAUD"
[ -n "${REALM:-}" ]  || MISSING="$MISSING REALM"
command -v get_token >/dev/null 2>&1 || MISSING="$MISSING get_token()"
command -v decode    >/dev/null 2>&1 || MISSING="$MISSING decode()"
if [ -n "$MISSING" ]; then
  echo "shell  -> not set in this shell:$MISSING"
  echo "shell  -> run the two setup blocks that follow this block, then run this again"
else
  echo "shell  -> ready"
fi
----

A fresh terminal tab, or a machine other than the one a rehearsal ran on, reports `not set in this shell`. That is a property of the terminal and of nothing else: re-preparing the module would destroy a working namespace and leave the shell exactly as it was.

*Confirm the opening state.* This one reads the namespace directly rather than through those variables, so it answers the same way whatever the terminal holds:

[source,sh,role=execute,subs="attributes"]
----
curl -ks -o /dev/null -w 'claims, no token -> %\{http_code}\n' https://parasol-claims-{user}-dev.{cluster_domain}/api/claims
curl -ks "$(oc get cm ws-entry-securing-apps-keycloak -n {user}-dev -o jsonpath='{.data.authServerUrl}')/protocol/openid-connect/token" \
  -d grant_type=password -d client_id=parasol-web -d username=adjuster -d password=parasol -d scope=openid \
  | jq -r 'if .access_token then "realm            -> token OK" else "realm            -> \(.error // "no answer from Keycloak")" end'
oc get deploy parasol-fraud -n {user}-dev --ignore-not-found -o name
----

Read the three lines together:

*`200`, `token OK`, and no `parasol-fraud` line* — this is the entry state, and the demo runs as written.

*`401` on the claims line*, usually with a `parasol-fraud` line under it — the namespace is already protected, either by a solve or by an earlier run of this demo. Run `ws prep securing-apps-keycloak` again and check again: against a `401`, step 1's `jq` prints nothing at all.

*`000` on the claims line* — nothing answered at the route. Look before acting:

[source,sh,role=execute,subs="attributes"]
----
oc get route,deploy -n {user}-dev
----

No `parasol-claims` route or deployment at all means the entry state was never materialized, and `ws prep securing-apps-keycloak` is the right move. A route that exists but does not answer is a routing or pod problem that re-preparing will not fix.

*Anything but `token OK` on the realm line* — the workshop Keycloak (`sso-workshop`) or the realm is down, and nothing on this page works without it. An OpenShift console login does not prove it is up: the cluster login runs on a different Keycloak.

*Deploy `parasol-fraud` before step 5.* It is not part of the entry state. Step 4 changes nothing on the cluster and the rollout takes 20–30 seconds on a cached image, so applying this during step 4 leaves a warm service for step 5:

[source,sh,role=execute,subs="attributes"]
----
cat <<EOF | oc apply -n {user}-dev -f -
apiVersion: apps/v1
kind: Deployment
metadata: { name: parasol-fraud, labels: { app: parasol-fraud } }
spec:
  replicas: 1
  selector: { matchLabels: { app: parasol-fraud } }
  template:
    metadata: { labels: { app: parasol-fraud } }
    spec:
      containers:
        - name: parasol-fraud
          image: image-registry.openshift-image-registry.svc:5000/ogsr-parasol-images/parasol-fraud:1.0
          ports: [{ name: http, containerPort: 8080 }]
          env:
            - { name: QUARKUS_OIDC_TENANT_ENABLED, value: "true" }
            - { name: QUARKUS_OIDC_AUTH_SERVER_URL, value: "$(oc get cm ws-entry-securing-apps-keycloak -n {user}-dev -o jsonpath='{.data.authServerUrl}')" }
            - { name: QUARKUS_OIDC_APPLICATION_TYPE, value: "service" }
            - { name: QUARKUS_OIDC_TOKEN_AUDIENCE, value: "parasol-fraud" }

Keep the terminal beside a browser signed in as `{user}`, and open the {ocp_console_url}[OpenShift web console^] on the `parasol-claims` deployment in `{user}-dev` for step 2.

CAUTION: Open the Parasol frontend in a *private browser window*. Step 3 shows the redirect to the Keycloak login page, and the frontend deliberately keeps its session cookie readable across restarts — that is what `QUARKUS_OIDC_TOKEN_STATE_MANAGER_ENCRYPTION_REQUIRED=false` in step 3's command is for — so a browser that logged in during a rehearsal restores that session instead of redirecting. If the ordinary window is already open, open a private one and reload.

CAUTION: If step 5 answers `401` twice, the second call went out as a literal `Bearer null`: `XCHG` is read with `jq -r .access_token`, which prints `null` when Keycloak answers with an error instead of a token. Rather than running the step again, repeat its exchange call with `jq '{error, error_description}'` in place of `jq -r .access_token` and read the error the pipeline swallowed. `invalid_grant` means the token in `$ADJ` aged out — they live 30 minutes, so `ADJ=$(get_token adjuster)` and step 5 runs clean. An error naming the client or the audience is a realm-seeding problem that cannot be fixed from here; the case is complete after step 4, and the exchange is covered in the hands-on lab.

CAUTION: If the fraud calls answer `000`, or return the router's error page rather than a status line, check `echo "$FRAUD"` before concluding anything. An empty line means this shell never ran the setup blocks and `curl` is requesting an empty URL — run them, and deploy nothing. If `$FRAUD` is a real URL, then `parasol-fraud` is not there: preparing the module deletes it, so a reset between a rehearsal and the session takes it too. Re-apply the manifest above.

NOTE: `ws prep securing-apps-keycloak` returns `{user}-dev` to the clean unprotected entry state — it removes the OIDC settings from both applications and deletes the fraud service — so run it after every rehearsal and then confirm the opening state again. Do not reach for `adm solve` to bring `parasol-fraud` back: the same flag that deploys it also protects both applications. Re-apply the manifest above instead.

[source,sh,role=execute]
----
# get_token <username>  -> prints an access token from your realm (demo password: parasol)
get_token() { curl -ks "$REALM/protocol/openid-connect/token" \
  -d grant_type=password -d client_id=parasol-web \
  -d username="$1" -d password=parasol -d scope=openid | jq -r .access_token; }

# decode  -> reads a token on stdin, prints its payload claims as JSON
decode() { jq -Rr 'split(".")[1] | gsub("-";"+") | gsub("_";"/")
  | . + ("=" * ((4 - (length % 4)) % 4)) | @base64d | fromjson'; }

== 2. Protect the claims API with bearer tokens
⏱ *~5 min* · turn the open API into one that demands a valid token

Confirm the starting point — the API is wide open, no token required:

[source,sh,role=execute]
----
curl -ks -o /dev/null -w 'GET /api/claims (no token) -> HTTP %{http_code}\n' "$CLAIMS/api/claims"
----

It returns `HTTP 200`.
That is the problem you are here to fix.
Now turn on the OIDC tenant and require an *authenticated* caller on `/api/claims`.
This is a *configuration* change — the Parasol image already carries the OIDC library; you are switching it on and pointing it at your realm, no rebuild.

== 3. Enforce a role — authentication is not authorization
⏱ *~10 min* · require the `claims-adjuster` role, watch a valid login get turned away, then grant and revoke it in the realm

Right now *any* valid token opens the API — including `viewer`, who is a real user but has no business listing claims.
Prove that gap first, then close it.

[source,sh,role=execute]
----
VIEW=$(get_token viewer)
curl -ks -o /dev/null -w 'viewer (authenticated, no role) -> HTTP %{http_code}\n' -H "Authorization: Bearer $VIEW" "$CLAIMS/api/claims"
----

`viewer` gets `HTTP 200` — authenticated is not the same as authorized.

== 4. Protect the web frontend — and hit the redirect trap on purpose
⏱ *~5 min* · a browser login with auth-code + PKCE, and the misconfiguration everyone hits once

The API takes tokens; the *web frontend* has to *get a human logged in* to obtain one.
That is the *authorization-code + Proof Key for Code Exchange (PKCE)* flow: an unauthenticated visitor is bounced to Keycloak, logs in there, and comes back authenticated — the app never sees the password.

Turn on OIDC for the web app as a `web-app` client.
*Do this exactly as written* — it contains the mistake nearly everyone makes the first time, and finding it is the lesson:

[tabs]
====
Console::
+
--
. On *Deployments* → `parasol-web` → *Environment*, add:
+
[cols="2,3",options="header"]
|===
| Name | Value
| `QUARKUS_OIDC_TENANT_ENABLED` | `true`
| `QUARKUS_OIDC_AUTH_SERVER_URL` | _your realm URL (`echo $REALM`)_
| `QUARKUS_OIDC_CLIENT_ID` | `parasol-web`
| `QUARKUS_OIDC_APPLICATION_TYPE` | `web-app`
| `QUARKUS_OIDC_AUTHENTICATION_PKCE_REQUIRED` | `true`
| `QUARKUS_OIDC_TOKEN_STATE_MANAGER_ENCRYPTION_REQUIRED` | `false`
| `QUARKUS_HTTP_AUTH_PERMISSION_PUBLIC_PATHS` | `/q/*`
| `QUARKUS_HTTP_AUTH_PERMISSION_PUBLIC_POLICY` | `permit`
| `QUARKUS_HTTP_AUTH_PERMISSION_WEB_PATHS` | `/*`
| `QUARKUS_HTTP_AUTH_PERMISSION_WEB_POLICY` | `authenticated`
|===
+
*Save*, and wait for the rollout. (Note the `/q/*` = `permit` rule: same "protect the app, not the health probes" split as the API.)

Visit the frontend and follow where it sends an unauthenticated visitor:

[source,sh,role=execute]
----

The app *does* redirect to Keycloak (`HTTP 302`) — but look at the `redirect_uri` it built: it starts with `http://`, not `https://`.
Follow that redirect the way a browser would, and Keycloak rejects it:

[source,sh,role=execute]
----
LOC=$(curl -ks -D - -o /dev/null "$WEB/" | sed -n 's/^location: //Ip' | tr -d '\r')

.Expected output — the break
[%collapsible]
====
[source,texinfo]
----
Keycloak with the http redirect_uri -> HTTP 400
----
The Keycloak page reads *"We are sorry... Invalid parameter: redirect_uri"*.
====

*What happened.* Your app sits behind the OpenShift *edge Route*, which terminates HTTPS and forwards plain HTTP to the pod.
The app, seeing an HTTP request, built an `http://` `redirect_uri` — but the realm only trusts the `https://` callback it was registered with, so Keycloak refuses it.
See the rule Keycloak applied:

[tabs]
====
Console::
+
--
In your admin console, *Clients* → `parasol-web` → *Settings* → *Access settings* → *Valid redirect URIs* holds one pattern, `https://parasol-web-{user}-dev.{cluster_domain}/*`.

CLI::
+
--
[source,sh,role=execute]
----

----

It prints one pattern, `https://parasol-web-<user>-dev.<cluster-domain>/*`.
--
====

The fix is to tell the app to honor the `X-Forwarded-*` headers the Route sets, so it knows the *original* request was HTTPS:

[source,sh,role=execute]
----
oc set env deployment/parasol-web QUARKUS_HTTP_PROXY_PROXY_ADDRESS_FORWARDING=true
oc rollout status deployment/parasol-web
----

Confirm the redirect is now HTTPS and carries the auth-code + PKCE parameters:

[source,sh,role=execute]
----
curl -ks -D - -o /dev/null "$WEB/" | sed -n 's/^location: //Ip' | tr -d '\r' \
  | grep -oE 'response_type=[^&]*|redirect_uri=https[^&]*|code_challenge_method=[^&]*'
----

.Expected output — the fix
[%collapsible]
====
[source,texinfo]
----
response_type=code
redirect_uri=https%3A%2F%2Fparasol-web-<user>-dev.<cluster-domain>%2F
code_challenge_method=S256
----
====

[NOTE]
====
If that command prints nothing, run it again. `oc rollout status` returns as soon as the new Pod is
ready, but the Service can still send one request to the old Pod that is on its way out — and the old
Pod still answers with the `http` redirect. A second attempt lands on the new Pod.
====

That is the auth-code + PKCE flow, correct at last: `response_type=code` (bring back a code, not a token), an `https` `redirect_uri` the realm trusts, and `code_challenge_method=S256` — the PKCE proof that makes an intercepted code worthless.
Open `$WEB/` in a browser and you will land on the Keycloak login page; sign in as `adjuster` / `parasol` and you are in.

== 6. Debug tokens like an adult
⏱ *~5 min* · decode, check expiry, read the audience — stop guessing

When a call is rejected, the answer is *in the token* — you just have to read it.
Three habits cover almost every "why is this 401/403?" you will ever hit.

*Is the signature even valid?* A garbage token is a clean 401:

[source,sh,role=execute]
----
curl -ks -o /dev/null -w 'bogus token -> HTTP %{http_code}\n' -H "Authorization: Bearer not-a-real-token" "$CLAIMS/api/claims"
----

It returns `HTTP 401` — the API could not validate it, so it does not know who you are.

*Has it expired?* The `exp` claim is a Unix timestamp; compare it to now:

[source,sh,role=execute]
----
get_token adjuster | decode | jq '{exp, seconds_left: (.exp - now | floor)}'
----

.Expected output (this realm issues 30-minute tokens; a negative `seconds_left` means expired → 401)
[%collapsible]
====
[source,json]
----
{
  "exp": 1783789453,
  "seconds_left": 1782
}
----
====

An expired token is the single most common "it worked five minutes ago" bug.
Clock skew is its cousin: if the API's clock and Keycloak's clock disagree, a *just-issued* token can look not-yet-valid or already-expired — which is why realms keep token lifetimes comfortably longer than any expected skew.

*Is it even for this service?* The `aud` (audience) claim names who a token is *for*.
Your `adjuster` token is stamped `aud: parasol-claims`:

[source,sh,role=execute]
----
get_token adjuster | decode | jq -c '{aud}'
----

.Expected output
[%collapsible]
====
[source,texinfo]
----
{"aud":"parasol-claims"}
----
====

The stamp comes from your realm, from an audience mapper on the `parasol-web` client:

[tabs]
====
Console::
+
--
*Clients* → `parasol-web` → *Client scopes* → `parasol-web-dedicated` → *Mappers* → `claims-audience`: its *Included Client Audience* is `parasol-claims`.

Alt: "Keycloak mapper details for claims-audience, an audience mapper adding parasol-claims to access tokens issued to parasol-web."
--
CLI::
+

[source,sh,role=execute]

It prints `{"name":"claims-audience","protocolMapper":"oidc-audience-mapper","audience":"parasol-claims"}`.

That single claim is why the same token that opens the claims API will be *refused* by the fraud service: a token minted for `parasol-claims` is not valid at `parasol-fraud`.

Now do the exchange.
The `parasol-claims` client (a confidential client, so it authenticates with its secret) hands Keycloak the user's token and asks for the `parasol-fraud` audience:

[source,sh,role=execute]

  -d grant_type=urn:ietf:params:oauth:grant-type:token-exchange \
  -d client_id=parasol-claims -d client_secret=parasol-claims-secret \

  -d subject_token_type=urn:ietf:params:oauth:token-type:access_token \

----

Read what changed and what did not: `aud` is now `parasol-fraud` (it will be accepted), `azp` (authorized party) is now `parasol-claims` (claims made this call), and `preferred_username` is *still `adjuster`* — the call is made *on the user's behalf*, not as a robot.

----

Now the property that makes exchange *safe*: it can narrow, but it *cannot* grant something the caller was never allowed.
Try to exchange the user's token toward `parasol-batch` — an audience the `parasol-claims` client has *no* permission to mint for:

[source,sh,role=execute]
----
ADJ=$(get_token adjuster)

.Expected output (Keycloak refuses the escalation)
[%collapsible]

  "error": "invalid_request",
  "error_description": "Requested audience not available: parasol-batch"
}

====

That refusal is the lesson.
Token exchange is *re-audience and downscope, never escalate*: a service can pass a user's identity to a *narrower* downstream call, but it cannot manufacture reach it was never granted.
That is what makes a chain of services auditable — each hop provably sees only what it should.

=== Brief

image::securing-apps-keycloak/securing-apps-keycloak-01-four-flows.svg["The four OAuth and OpenID Connect flows this demo uses, in two groups. With a human present: authorization code with PKCE, where the browser logs in at Keycloak and the application never sees the password, and bearer tokens, where the caller presents a token the API validates before checking a role. With no human: client credentials, where a service authenticates as itself, and token exchange, where one service re-audiences a user's token to call another on that user's behalf. Arrows follow one user's token from the browser login into the API and on into the exchange."]

*Authentication is not authorization*

Two questions hide inside every "is this allowed?", and confusing them is the most common security bug there is. *Authentication* asks who you are, and a login, a token or a certificate answers it. *Authorization* asks what you may do, and a role, a group or an ownership rule answers it.

A valid token answers only the first question. Parasol's `viewer` user logs in perfectly — correct password, valid token — and still must not list claims, because listing claims needs the `claims-adjuster` role. The platform reports the difference as two status codes: *401 Unauthorized* is "I do not know who you are", *403 Forbidden* is "I know exactly who you are, and the answer is no".

*Four flows cover an enterprise application*

OAuth 2.0 and OpenID Connect define a family of flows — scripted conversations for getting a token — and four of them cover almost everything a business application needs:

* *Authorization code + PKCE* protects a browser frontend. The browser is redirected to Keycloak, the person logs in there, and the application receives a short-lived code it swaps for tokens. PKCE adds a one-time secret per login, so a stolen code is useless.
* *Bearer tokens* protect an API. The caller attaches a token, the API validates its signature, issuer, expiry and audience, then reads its roles to decide. No redirect and no session: every request stands alone.
* *Client credentials* is for machines. A batch job has no human and no browser, so it authenticates as itself and gets a token that represents the service.
* *Token exchange (RFC 8693)* is for one service calling another on a user's behalf. The token is re-audienced for the second service — same user, narrower scope.

*Identity is a platform capability, not a project*

Authentication is a solved problem, and getting it slightly wrong is the whole breach. Red Hat build of Keycloak provides password policies, multi-factor authentication, lockout, federation, token issuance and an audit trail, and it is included with the OpenShift subscription — the same product backs the OpenShift console login. What is left is describing who may do what, and pointing the applications at it.

*In this demo*

. The claims API returning real claim records to an anonymous caller
. Bearer authentication and a role check turned on live — 401, 200 and 403 from the same endpoint
. A browser login for the frontend, which never sees the password
. A machine identity for the nightly batch job
. A token re-audienced for a second service, and the escalation Keycloak refuses

=== 1 · The open API — 2 min

Everything built in the earlier modules — the deployment, the configuration, the database, the pipeline — has been open by default. The claims API holds customer names, amounts and adjusters, and reading all of it takes no login and no token.

*Why it matters*

This is the shape of most internal breaches: something reached the network, and everything on the network trusted it. "On the network" was a boundary when it meant a locked server room; it is not one when the network is a shared cluster, a partner integration and a mobile app.

Three real claim records came back to a caller who presented no credential of any kind.

=== 2 · Bearer tokens and a role check — 4 min

One configuration change turns on OpenID Connect and points the claims service at Keycloak. The API then demands a valid token, and checks a role before it answers.

image::securing-apps-keycloak/securing-apps-keycloak-05-claims-env.png["The Environment tab of the parasol-claims deployment in the OpenShift web console, listing the settings this step applies: QUARKUS_OIDC_TENANT_ENABLED set to true, QUARKUS_OIDC_AUTH_SERVER_URL pointing at the user's Keycloak realm, QUARKUS_OIDC_APPLICATION_TYPE set to service, and the two QUARKUS_HTTP_AUTH_PERMISSION_CLAIMS entries restricting /api/claims to callers holding the adjuster policy."]

*Why it matters*

No authentication code was written. The runtime validates the token's signature, issuer and expiry against the realm, then reads `realm_access.roles` to decide — so authentication and authorization arrive as configuration and show up as two different status codes.

[source,sh,role=execute,subs="attributes"]
----
oc set env deployment/parasol-claims -n {user}-dev \
  QUARKUS_OIDC_TENANT_ENABLED=true \
  QUARKUS_OIDC_AUTH_SERVER_URL=$(oc get cm ws-entry-securing-apps-keycloak -n {user}-dev -o jsonpath='{.data.authServerUrl}') \
  QUARKUS_OIDC_APPLICATION_TYPE=service \
  QUARKUS_HTTP_AUTH_PERMISSION_CLAIMS_PATHS='/api/claims,/api/claims/*' \
  QUARKUS_HTTP_AUTH_PERMISSION_CLAIMS_POLICY=adjuster \
  QUARKUS_HTTP_AUTH_POLICY_ADJUSTER_ROLES_ALLOWED=claims-adjuster
oc rollout status deployment/parasol-claims -n {user}-dev
----

The rollout takes about twenty seconds. Then call the same endpoint three times — with no token, as `adjuster`, and as `viewer`:

[source,sh,role=execute]
----
curl -ks -o /dev/null -w 'no token -> %{http_code}\n' "$CLAIMS/api/claims"
curl -ks -o /dev/null -w 'adjuster -> %{http_code}\n' -H "Authorization: Bearer $(get_token adjuster)" "$CLAIMS/api/claims"
curl -ks -o /dev/null -w 'viewer   -> %{http_code}\n' -H "Authorization: Bearer $(get_token viewer)" "$CLAIMS/api/claims"

*What just happened*

`401` with no token. `200` for the adjuster. And `403` for `viewer` — a real user, logged in correctly, and told no. That is the difference between who you are and what you are allowed to do.

=== 3 · The browser login — 3 min

The API takes tokens; the frontend has to get a person logged in. The same realm handles that with the authorization-code flow, and the application never sees the password.

image::securing-apps-keycloak/securing-apps-keycloak-06-keycloak-login.png["The Red Hat build of Keycloak login page for the user's realm, headed PARASOL INSURANCE, reached by opening the protected parasol-web frontend without a session: a Sign in to your account card with an empty username or email field, an empty password field, and a Sign In button."]

*Why it matters*

The login page, the password policy, lockout, multi-factor authentication and the session all belong to Keycloak, which ships with OpenShift. Adding login to an application becomes a configuration change rather than a project, and every application in the estate gets the same one.

=== 4 · A machine identity for the batch job — 2 min

Not every caller is a person. The nightly statement run has no human and no browser, so it authenticates as itself with a client id and secret and receives a token that represents the service.

image::securing-apps-keycloak/securing-apps-keycloak-02-realm-model.svg["The realm model: one realm holding clients, roles and users. *Why it matters*

A machine principal can be audited, rotated and revoked without paging a person, and no engineer is tempted to run the job under a personal login. When someone leaves, nothing scheduled breaks with them.

[source,sh,role=execute]

*What just happened*

The decoded token names `service-account-parasol-batch` — an identity in its own right, with no person behind it. The client secret is a seeded workshop value shown here in the clear; in production it is generated, kept in a Secret and never printed.

=== 5 · Token exchange — 4 min

The claims service needs to call the fraud service as the adjuster, but the adjuster's token is addressed to claims. Token exchange re-audiences it — and it can narrow what the token reaches, never widen it.

image::securing-apps-keycloak/securing-apps-keycloak-07-what-you-built.svg["What this demo leaves in place: the adjuster reaching parasol-web through authorization code with PKCE and parasol-claims with a bearer token that answers 401, 200 or 403; parasol-claims re-audiencing that token to call parasol-fraud, which enforces its audience; the batch job authenticating with client credentials; and Red Hat build of Keycloak, holding the user's realm, behind all three applications."]

*Why it matters*

This is delegation without impersonation. A chain of services can each see only what they need, and the refusal at the end is the proof: escalation is not merely discouraged, it is unavailable.

[source,sh,role=execute]
----
ADJ=$(get_token adjuster)
curl -ks -o /dev/null -w 'user token -> fraud -> %{http_code}\n' -H "Authorization: Bearer $ADJ" "$FRAUD/api/fraud/score/CLM-1001"
XCHG=$(curl -ks "$REALM/protocol/openid-connect/token" \
  -d grant_type=urn:ietf:params:oauth:grant-type:token-exchange \
  -d client_id=parasol-claims -d client_secret=parasol-claims-secret \
  -d subject_token="$ADJ" -d subject_token_type=urn:ietf:params:oauth:token-type:access_token \
  -d audience=parasol-fraud | jq -r .access_token)
curl -ks -o /dev/null -w 'exchanged  -> fraud -> %{http_code}\n' -H "Authorization: Bearer $XCHG" "$FRAUD/api/fraud/score/CLM-1001"
curl -ks "$REALM/protocol/openid-connect/token" \
  -d grant_type=urn:ietf:params:oauth:grant-type:token-exchange \
  -d client_id=parasol-claims -d client_secret=parasol-claims-secret \
  -d subject_token="$ADJ" -d subject_token_type=urn:ietf:params:oauth:token-type:access_token \
  -d audience=parasol-batch | jq -r '.error_description'
----

*What just happened*

`401` for the wrong audience. `200` once the token is re-audienced, still as the adjuster. And a refusal when the exchange aims at a service the claims application has no business reaching: `parasol-claims` may mint tokens for `parasol-fraud` alone, so Keycloak answers `Requested audience not available`.

== Frequently asked questions

*We required a role and never configured where roles live in the token — why did that work?*::
The Parasol image ships `quarkus.oidc.roles.role-claim-path=realm_access/roles`. Keycloak puts realm roles under `realm_access.roles` rather than a top-level `roles` claim, so a framework has to be told where to look. On an application that does not set it, a user who genuinely holds the role still gets `403` — it is the most common Keycloak-with-Quarkus mistake, and decoding one token shows exactly where the role sits.

*Our logins fail with "Invalid parameter: redirect_uri" behind the load balancer — is that a Keycloak bug?*::
No, it is the classic edge-termination trap. TLS ends at the Route and plain HTTP is forwarded to the pod, so the application builds an `http://` callback URL while the realm trusts only the `https://` one. Telling the runtime to honour the forwarded headers — `QUARKUS_HTTP_PROXY_PROXY_ADDRESS_FORWARDING=true` in step 3 — fixes it. If a login still fails afterwards, check the client id and the realm URL.

*The escalation attempt returns "Requested audience not available" — is that a misconfiguration?*::
That refusal is the point. The `parasol-claims` client is configured to mint tokens only for the `parasol-fraud` audience, so Keycloak declines every other target. It is what makes a service chain provably safe: exchange can re-audience and downscope, and there is no path by which it escalates.

*Is this the same Keycloak that signs us in to the OpenShift console?*::
The same product, a deliberately separate instance. The cluster login runs on its own Keycloak; this module uses a workshop instance with a throwaway realm per user, so experiments cannot lock anyone out of the cluster. In a real estate the split is the same decision: one instance for platform access, one for applications, both the identity provider that comes with the subscription.
