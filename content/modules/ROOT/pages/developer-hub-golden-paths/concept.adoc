A new engineer joins Parasol's claims team and needs a quote service in production this sprint, built, scanned, signed, verified and released the way the auditors expect.
Every one of those practices exists on the platform today, but each is a separate set of files, conventions and credentials to get right, and the new engineer would spend the sprint assembling them.
In this module one form in *Red Hat Developer Hub* creates the whole project, with every practice of this workshop already wired in, and the developer's only job left is the code.

== What you'll learn

* Why a platform team packages its practices into a *golden path*: a *Software Template* in a *developer portal*, Red Hat Developer Hub, instead of documentation and copied repositories.
* What one golden template can carry: a *Pipelines-as-Code* build pipeline with test and scan gates, a *software bill of materials* (SBOM), *keyless signing* and a *Conforma* policy check, *GitOps* promotion of the same image digest to dev, stage and prod, and a *canary* release with an automated analysis.
* Where the line falls between *what the template generates* for one service and *what the platform team wires once* for a whole team.
* How the *software catalog* turns those generated files into a component page with *CI*, *CD* and *Topology* views, so the developer watches the whole path in one place.
* When a golden template is worth its upkeep, and when it is not.

== The problem: every practice is another thing to assemble

By this point in the workshop you have seen the delivery practices one at a time.
A pipeline that runs on every push.
Gates that test the code and check the image for known vulnerabilities.
An SBOM that records what is inside the image, a signature that proves who built it, and a policy check that refuses an image whose signature or provenance does not verify.
GitOps repositories that decide what runs in each environment, promotion by Git commit, and canary releases that roll back on their own.

Each practice is sound, and each one is *more files, more conventions and more credentials* for a developer to get right before the first line of business logic.
Multiply that by every new service and the cost is not the tools, it is the *cognitive load*.
The tenth service is created by copying the ninth, including whatever was wrong with it; the pipeline drifts from the standard; the canary is left out because nobody had the afternoon to wire it.
Standards that live in a wiki are standards that drift.

The fix is to make the practices the *default*: the platform team encodes them once, in a template, and every new service starts with all of them.

== The front door: Red Hat Developer Hub

An *Internal Developer Platform* (IDP) is the set of tools and paths a platform team offers to the developers it serves.
Its front door is a *developer portal*.
*Red Hat Developer Hub* (RHDH) is Red Hat's build of the open-source Backstage project: a portal assembled from plugins, which you enable through configuration rather than a custom build.

It gives an organization two things.
A *software catalog* answers "what do we run, and who owns it?"
*Golden paths* answer "how do I start something new, correctly, without asking anyone?"

=== The catalog: the organization's map

The catalog is a live inventory of what the organization runs, modelled as *entities* with typed relationships:

Component:: A thing you build and run: a service, a website, a library.
API:: A contract a Component provides or consumes.
System:: A group of Components and APIs that work together, such as `parasol-insurance`.
Group:: The team that *owns* entities.

Each entity is described by a small `catalog-info.yaml` file that lives *in the service's own repository*, next to the code, so ownership is reviewed like code instead of kept in a spreadsheet that rots.

The same file switches on the views a component page shows.
Three annotations matter in this module:

|===
|Annotation in `catalog-info.yaml` |What the component page shows

|`backstage.io/kubernetes-id`

|`tekton.dev/cicd`

|`argocd/app-selector`
|*CD*: the Argo CD Applications that deploy the service, with their sync and health
|===

== The golden template: one form, the whole project

A golden path is a *Software Template*: a short form plus a list of steps.
The developer names the service and picks their team's Git organization; the template generates everything else, publishes it, and registers it in the catalog.

In this module the template is *Parasol service, build to production*, and one form submission creates:

* an *app repository*, `parasol-quote-{user}`: the service's source, its `Containerfile`, a `devfile.yaml` for Dev Spaces, its `catalog-info.yaml`, and a `.tekton/` folder that says *when* pipelines run;
* a *GitOps repository*, `parasol-quote-{user}-gitops`: `ci/` with the Pipelines-as-Code `Repository` and the two pipelines, and `overlays/` for dev, stage and prod;
* a *catalog Component* whose CI, CD and Topology tabs read the pipeline runs, the Argo CD Applications and the running pods.

=== What the template generates, and what the platform team wires once

A template creates *one service*.
Some things belong to the *team*, not the service, and a platform team sets those up once per team so that every service the team creates later works the same way.
In this workshop each attendee is a team, and `ws prep` performs that one-time setup for yours:

[cols="2,3",options="header"]
|===
|Set up once per team (platform) |Why it is not in the template

|Your Git organization, `{user}-svcs`, with two *organization webhooks*: one to Pipelines-as-Code, one to Argo CD
|Every repo created in the org is connected from its first push, with no per-repo step and no webhook credentials in the portal

|A CI credential, the Secret `golden-pac-secret` in `{user}-cicd`
|Pipelines-as-Code reports each run back to the commit with it, and the pipelines commit promotions with it; it is the team's, not the service's

|An Argo CD *ApplicationSet* with an *SCM-provider generator* over your org
|It turns every `*-gitops` repo in the org into four Applications, `ci`, `dev`, `stage` and `prod`, inside your own Argo CD project; the portal never holds a credential that can create Applications

|Pull rights from `{user}-cicd` for dev, stage and prod, and read access to stage for the release pipeline
|Permissions are the platform's to grant; generated files only use them
|===

The split is deliberate.
The template is the part a developer reads and changes: it should hold every decision about *how the service is built and released*.
The platform wiring is the part a developer should never have to think about: credentials, webhooks and the rule that turns a repository into running Applications.

Because the generated files are only text in two repositories, the paved road stays editable.
A team that needs one more step in its pipeline commits it to `ci/` in its GitOps repo, and Argo CD applies it like any other change.

== From commit to production

The two pipelines split the path at the point where a release is a decision.

[mermaid]
....
include::example$diagrams/developer-hub-golden-paths/10-commit-to-production.mmd[]
....

*A push to `main`* runs the build pipeline in `{user}-cicd`:

. It runs the unit tests and builds the image in parallel; the image is pushed tagged with the commit.
. Red Hat Advanced Cluster Security checks the image against the cluster's build-time policies, and the pipeline records an SBOM.
. *Tekton Chains*, a controller beside the pipeline rather than a step in it, signs the image and its SLSA provenance *keyless*, through Red Hat Trusted Artifact Signer.
. *Conforma* verifies that signature and provenance, checks that this pipeline's build task made the image, and checks that it is referenced by digest.
Any failure stops the run, and nothing reaches an environment.
. Only then does the pipeline write the verified digest into `overlays/dev/release.yaml` and push.
Argo CD sees the commit and deploys it to `{user}-dev`.
The pipeline never touches the dev namespace itself.

*A tag such as `v1.0.0`* runs the release pipeline, which *builds nothing*:

. It finds the image the build pipeline made from the tagged commit.
A commit that never passed the build pipeline has no image, so it cannot be released.
. Conforma checks that same digest again, because a release is the moment trust is asserted, not assumed.
. It commits the digest to `overlays/stage`, waits until stage runs it, then commits it to `overlays/prod`.
. In prod the service is an Argo Rollouts *canary*: half the pods take the new release, an automated analysis checks them, and only a passing analysis promotes it to all of them. (The very first release has no stable version to compare against, so it goes straight to all pods.)
A failing analysis rolls back on its own.

The *same digest* moves from dev to stage to prod.
Nothing is rebuilt between environments, so what was tested and verified is exactly what runs in production.

=== Where the images live

Each service's images go to the cluster's internal registry, in the team's CI namespace (`{user}-cicd/parasol-quote-{user}`), and every environment refers to them by digest.
The gate for this template is Conforma *inside both pipelines*: only a digest that passed it is ever written to Git, and Git is the only way into an environment.
A platform team can add a second line of defense at admission, a cluster policy that refuses unsigned images in chosen namespaces, as the Trusted Software Supply Chain module shows; the template does not depend on it.

== A paved road, not a cage

A cage forces one way and punishes deviation.
A paved road makes the right thing the easy thing, and leaves you free to drive off it when you have a reason.

[cols="2,3,3",options="header"]
|===
| |A cage |A paved road

|The standard way |The *only* way |The *easy* way
|Leaving it |Blocked or punished |Allowed, with a reason
|Who owns the result |The platform team, as a black box |Your team, from the first commit
|What teams do |Route around it |Use it, because it is quicker
|===

The generated project is plain files in *your* repositories.
You own them from the moment they exist: change the code, add a gate, adjust the canary steps.
The template gave you a correct starting line and got out of the way.

[NOTE]
.Standards by construction, not by audit
====
Without a golden path, a service is created some ad-hoc way and audited *later*: someone finds the missing scan, the unsigned image, the environment deployed by hand, and files a ticket.
With one, the service starts *already* scanned, signed, verified and promoted through Git.
Compliance is the default state at creation, and auditing becomes "confirm the road was used."
====

== Keeping the template right is platform engineering's job

A template is a product with users.
Its value is that every service created from it inherits the platform team's current best answer, so the template has to *stay* current:

* *Change it once, and every new service inherits the change.* A new gate, a newer base image or a stricter policy is one commit to the template, not a migration project across fifty repositories.
* *Existing services do not change on their own.* A template generates files once; services created last year keep last year's files.
A platform team decides, per practice, whether to keep it in the generated files (each team can adapt it) or to move it to a shared definition every service references (one fix reaches everyone, and teams adapt less).
This template keeps the pipelines in each service's GitOps repo and takes its *tasks* from the shared task library: the steps are shared, the order is the team's.
* *Measure whether the road is used.* Templates nobody chooses are a signal that the road is slower than the shortcut.

== How this shows up in real orgs

* *"How do I start a new service?" gets one answer.*
The tenth service is created from the template the platform team owns, so it starts with the current pipeline, the current gates and an owner already recorded.
* *Security and release practices stop depending on who set the service up.*
Signing, verification, SBOMs and canary releases arrive with the first commit, so they are present in the team that never heard of them as much as in the team that pioneered them.
* *The catalog answers "what is running, where, and did it pass?" in one place.*
The component page shows the pipeline runs, the Argo CD Applications per environment and the running pods side by side, without access to five consoles.
* *The platform team's leverage compounds.*
Improve the template once, and every service created after inherits it.
