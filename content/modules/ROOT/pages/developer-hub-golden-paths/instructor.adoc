The module's signature beat: one form in Developer Hub creates a service that already carries *every practice of the workshop* (Pipelines-as-Code, test and image-scan gates, SBOM, keyless signing, Conforma, GitOps promotion by digest, a canary with analysis), and the attendee watches a push and two tags take it to production.
The closing message is the module: every practice can live in a template, and keeping that template right is platform engineering's job.

What makes it work is split in two, and attendees will ask which is which:

* *The template* (`parasol/parasol-golden-path` in Gitea, *Parasol service, build to production* in Self-service) writes two repositories per service: the code with its `.tekton/` triggers, and `-gitops` with `ci/` (the PaC `Repository` and both pipelines) and the dev/stage/prod overlays.
* *The platform wiring*, laid by `ws prep` per attendee: `golden-pac-secret` (a Gitea token and webhook secret) in `{user}-cicd`, two org webhooks on `{user}-svcs` (to Pipelines-as-Code and to the attendees' Argo CD), and the ApplicationSet `golden-path-{user}` in the attendees' Argo CD, whose SCM-provider generator turns every `*-gitops` repo in the org into four Applications: `ci`, `dev`, `stage`, `prod`.

== Demo-mode notes

* *Stage with `adm solve` the evening before.* It creates the project and releases `v1.0.0`, so the demo opens on a component page with history in *CI*, four applications in *CD*, and pods in three environments.
* *Start the build early.* Step 2's build takes about 2.5 minutes; talk through its task table while it runs. Do not tag in step 3 until the build has Succeeded, or the release is refused (that refusal is the lab's break-and-fix, and makes a fine extra beat if you mean it).
* *Each demo run needs a new tag.* Solve released `v1.0.0`; use `v1.1.0`, then `v1.2.0` on a rehearsal, and so on.

== Top questions attendees ask

*1. "Who created the Argo CD applications and the webhooks? I only filled a form."*::
The platform team's per-team wiring, which `ws prep` lays for each attendee: an ApplicationSet in the attendees' Argo CD watches the `{user}-svcs` organization and makes four applications for every `-gitops` repository in it, and two org-level webhooks send every push to Pipelines-as-Code and to Argo CD. The template only writes files; nothing in Developer Hub holds a credential that can deploy.

*2. "Why is the pipeline in the GitOps repository, not in my app repo?"*::
The app repo's `.tekton/` files say *when* to run; the pipeline (*what* runs) is a cluster object applied by Argo CD from `ci/`, so changing it is a reviewed commit like any other configuration, and Conforma can check that a named pipeline built the image. A shared, versioned pipeline in a task library is the other common choice; the wrap-up compares them.

*3. "Why did my first release go straight to prod, but the second was a canary?"*::
A canary compares a new version with a running stable one. The first release has nothing to compare against, so Argo Rollouts creates production with it; every later release is a canary with the analysis.

*4. "Where is the signing step?"*::
There is none: Tekton Chains watches the build task and signs the image and its provenance, keyless, as its own workload identity, seconds after the task ends. The pipeline only verifies the result, with Conforma, before dev and again before stage.

*5. "Can I use my own service name?"*::
Yes, but the declared Dev Spaces workspace clones `parasol-quote-{user}`, and the catalog is shared, so a name must be unique in the room; keep the username in it.

== Watchouts

* *`{user}-cicd` is shared with the pipeline modules.* Starting this module evicts pipelines-fundamentals, app-security-testing and trusted-supply-chain for that attendee and purges `{user}-cicd` (and the reverse). Switching either way is clean.
* *A reset of a finished lab takes a few minutes.* `ws prep` deletes the four Applications, and the `ci` one waits for Kubernetes to delete the Pipelines-as-Code `Repository` (foreground deletion; about two minutes measured) before the purge goes on.
* *The first Dev Spaces start on a node pulls the developer image* (about two minutes). Have the room open the workspace at the start of exercise 3 and read the pipeline table while it starts.
* *The Git password prompt appears at the top of the editor*, not in the terminal; attendees think the push hung.
* *A tag pushed before its build passed is refused* (exercise 5's break-and-fix). If an attendee deletes and re-pushes a tag instead of using the next version, Pipelines-as-Code also runs the release for the deletion; both runs promote the same digest, so the result is the same, but the run list shows two.
* *Developer Hub restarts when its Argo CD access changes.* The workshop layer's `devhub-argocd-access` hook rewrites the portal's plugin Secret and restarts the pod only when the Secret's content changes (the first install, or a changed workshop password); the portal is unavailable for about three minutes while the dynamic plugins reinstall.
* *Links inside Developer Hub that point at Gitea* resolve to its in-cluster address (`gitea.ogsr-gitea.svc:3000`) and do not open in a browser; use the Gitea route ({gitea_url}).
