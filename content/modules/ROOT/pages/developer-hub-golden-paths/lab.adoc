In this lab you step into the shoes of a new Parasol engineer.
You tour the *software catalog* to learn what the org already runs and who owns it, then use a *golden-path template* to scaffold a brand-new, standards-compliant Parasol service into your *own* Git organization — repo published, catalog entry registered, paved-road wiring already in place.
You inspect what the template pre-wired, then build and run the scaffolded service in `{user}-dev` and watch its health and metrics endpoints answer — observability you never had to set up.

[NOTE]
.One terminal, plus two browser tabs
====
Terminal commands run in the *Terminal* tab beside these instructions, logged in as `{user}`.
They act on *your own* namespace (`{user}-dev`) and your own Git organization (`{user}-svcs`).
Two tabs in the browser carry the portal work:

* *Red Hat Developer Hub* — the shared portal: {rhdh_url}[the Developer Hub portal^].
Sign in with *Enter* (guest) — one click, no password (real deployments wire single sign-on instead).
This is where you *browse the catalog* and *run the golden-path template*.
* *Gitea* — your Git server, where your scaffolded repo lands: {gitea_url}[Gitea^].
Sign in with your workshop username `{user}` and password.

Open both now.
====

[WARNING]
.The Developer Hub portal is shared with the whole room
====
There is *one* Red Hat Developer Hub in this workshop, and everyone signs in to it as the same *Guest*.
There is no per-attendee identity inside the portal — a deliberate trade (real deployments wire single sign-on and scoped permissions; this build trades that for a one-click start).

Two consequences, both better met here than by surprise:

* *You will see other people's work.* The catalog holds every attendee's scaffolded service, so alongside your own `parasol-policy-{user}` you will find entries like `parasol-policy-user3`. That is expected, not a bug.
* *Guest is not read-only — you could change or delete theirs.* Touch only the entries named after *your own* user: `parasol-policy-{user}` and the `{user}-svcs` organization. Everything else on that portal belongs to someone who is mid-exercise.

Your Gitea organization (`{user}-svcs`) and your namespace (`{user}-dev`) *are* yours alone.
The sharing stops at the portal.

== Demo arc — Modules 2 through 10, packaged into one button (11 min)

[NOTE]
.Before you present
====
Two prep steps, both *before the room*:

. Run `ws solve developer-hub-golden-paths --user {user}`.
It materializes a demo-ready *already-scaffolded* service (`{user}-svcs/parasol-golden`) in your scaffold org so you have a concrete post-scaffold repo to fall back on, and confirms the portal + catalog + template are serving.
. Sign in to the {rhdh_url}[Developer Hub portal^] with *Enter* (guest), open the *Catalog*, and filter to the `parasol-claims` Component so the org map is your opening visual.

The money moment is beat 2: a short form produces a complete, catalog-registered Parasol service in your own Git org in *under a minute*.

*One pre-flight, and it is the difference between a live scaffold and a red banner.* The template
publishes to `{user}-svcs/parasol-demo-{user}`, and publishing into a name that already exists is
*refused*: the scaffolder's *Publish to Gitea* step fails with
`409 Conflict … The repository with the same name already exists`, and *Register in the software
catalog* is greyed out and never runs.
A rehearsal is therefore the one thing guaranteed to break beat 2. List the org — this is beat 2's
own command:

[source,sh,role=execute,subs="attributes"]
----
curl -sk "{gitea_url}/api/v1/orgs/{user}-svcs/repos" \
  | python3 -c 'import sys,json;[print("repo:",r["full_name"]) for r in json.load(sys.stdin)]'
----
*If you see `parasol-golden` and no `parasol-demo-{user}`*, you are clean: solve staged your fallback,
and the name beat 2 needs is free.
*If `parasol-demo-{user}` is already listed*, re-run `ws solve developer-hub-golden-paths --user {user}`
before the room — it applies the entry state first, which empties the scaffold org *and* deregisters
its catalog Location on the shared portal, then re-creates `parasol-golden`.
Do not just delete the repo in Gitea and retry: emptying Gitea does not remove the catalog entry (it
is a catalog object, not a Gitea repo), so you would clear the *Publish* conflict and leave the stale
registration standing in front of the *Register* step. If you only find out on stage, see the note
after beat 2.
====

=== Beat 1 — The catalog: what we run and who owns it

[demo-block]
[TIME 3m]
Say:: "This is Parasol's developer portal. Everything the company runs is in one catalog — the claims service, the APIs it exposes, the team that owns it. When an engineer asks 'what do we run and who owns it,' this is the answer, and it is generated from files that live next to the code."
Show:: The Developer Hub *Catalog*: the `parasol-claims` Component; open it and trace *owner* (`parasol` group), *System* (`parasol-insurance`), and the *API* it provides (`parasol-claims-api`) — click the API and show the OpenAPI definition rendering.
Do:: In the terminal, prove the catalog is an API, not just a screen:
+
[source,sh,role=execute,subs="attributes"]
----
TOKEN=$(curl -sk {rhdh_url}/api/auth/guest/refresh | python3 -c 'import sys,json;print(json.load(sys.stdin)["backstageIdentity"]["token"])')
curl -sk -H "Authorization: Bearer $TOKEN" \
  "{rhdh_url}/api/catalog/entities/by-name/component/default/parasol-claims" \
  | python3 -c 'import sys,json;d=json.load(sys.stdin);s=d["spec"];print("owner:",s["owner"],"| system:",s["system"],"| provides:",s.get("providesApis"))'
----
+
"Owner, system, the API it provides — the map is queryable."
+
The *portal* is the visual here and you already have it open; the `curl` is the garnish. A
`KeyError` traceback out of that one-liner is what an unreachable portal or an unregistered entity
looks like from the terminal — do not debug it on stage. Say the line, point at the Catalog page,
and move on.

=== Beat 2 — A form instead of a week of plumbing

[demo-block]
[TIME 5m]
Say:: "Now the payoff of this whole workshop. A new engineer needs a service — one that builds the trusted way, has probes and metrics and tracing, and is ready for GitOps. Instead of a week of plumbing, they fill in a form."
Show:: *Catalog → Self-service* → the *New Parasol microservice* template → the form: *Name* `parasol-demo-{user}`, *Your Gitea organization* `{user}-svcs`, *Owner* `parasol` → *Create*. Watch the three steps run: fetch the skeleton, publish to Gitea, register in the catalog. (The name carries your username because the Developer Hub portal is shared — a per-user name keeps every registered service distinct on the one catalog.)
Do:: While the task runs, narrate the steps; when it finishes, follow the *Open in the software catalog* link to the new Component, then show the repo it created:
+
[source,sh,role=execute,subs="attributes"]
----
curl -sk "{gitea_url}/api/v1/orgs/{user}-svcs/repos" \
  | python3 -c 'import sys,json;[print("repo:",r["full_name"]) for r in json.load(sys.stdin)]'
----
+
"A form became a real Git repository and a registered service in under a minute — carrying the base image, the probes, the metrics, the tracing, the GitOps wiring you built by hand across the last nine modules. The platform team packaged all of it into one button."

[NOTE]
.If the scaffolder task goes red
====
The named failure is *Publish to Gitea* returning
`409 Conflict … The repository with the same name already exists` — a rehearsal, or a second run of
the arc. The task page tells you exactly that:
*Fetch* green, *Publish* red, *Register* greyed out and never run.
Never sit on a failed task page re-reading the stack trace. Two escapes, in order of preference:

. *Change the Name in the form and press Create again.* `parasol-demo2-{user}` publishes and registers
cleanly, the whole beat lands as written, and it costs one field.
. *Switch to the pre-staged service.* `ws solve` already put `{user}-svcs/parasol-golden` in your org,
produced by this same template. Say "here is one this template made earlier", and run beat 3 against
it instead:
+
[source,sh,role=execute,subs="attributes"]
----
curl -sk "{gitea_url}/{user}-svcs/parasol-golden/raw/branch/main/catalog-info.yaml" | grep -E 'kind:|owner:'
----

Be honest about what that fallback repo is: solve materializes the golden-path *outcome* — the repo
and its registered `catalog-info.yaml` — not the full skeleton. So show the catalog entry rather than
promising `pom.xml`, the `Containerfile` and the devfile on screen; for those, browse `parasol-claims`
in the catalog, which beat 1 already has open.
====

=== Beat 3 — A paved road, not a cage

[demo-block]
[TIME 3m]
Say:: "And it is a paved road, not a cage — plain, standard code in the engineer's own repo, theirs to change."
Show:: The repo you just scaffolded in Gitea (`{user}-svcs/parasol-demo-{user}`): `pom.xml` (Quarkus, Java 21), `src/.../InfoResource.java`, `application.properties` (health, metrics, OpenTelemetry), the UBI9 `Containerfile`, `catalog-info.yaml`, `devfile.yaml`.
Do:: Point at the wiring that is already there:
+
[source,sh,role=execute,subs="attributes"]
----

----
+
"Nobody hand-wrote any of this. The golden path made the correct decisions once, and the new service inherits them — then the engineer owns it and drives wherever they need to."

[NOTE]
.Resetting between runs
====
`ws prep developer-hub-golden-paths --user {user} --yes` returns everything to the entry state: it empties your `{user}-svcs` scaffold org, deregisters its catalog entry from the shared portal, and purges `{user}-dev`, so the next run starts from a clean slate.
The scaffold is fast (seconds), so the create-a-service beat lands live with no waiting.
====

== 4. Deploy your scaffolded service into {user}-dev

[source,sh,role=execute]

for i in $(seq 1 90); do

    Complete) echo "  ✔ image built and pushed to the internal registry"; break;;
    Failed|Error|Cancelled) echo "  ✖ build $P — see: oc logs build/$B -n $DEV"; break;;
  esac
  sleep 12
done
