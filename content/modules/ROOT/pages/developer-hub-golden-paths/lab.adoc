== A new service that starts compliant · 11 min

Parasol's developer portal answers what the organization runs and who owns it, and turns a week of plumbing into a short form that produces a real, standards-compliant service — in the team's own Git organization, registered in the catalog — in under a minute.

[IMPORTANT]
.Prep — run before the session
====
This demo starts from the finished lab state. Stage it before the session from your own terminal, signed in with a cluster-admin account:

[source,sh,subs="attributes"]
----
adm solve developer-hub-golden-paths --user {user}
----

It empties the `{user}-svcs` scaffold organization and leaves one already-scaffolded service in it, `{user}-svcs/parasol-golden`, as a ready-made example of what the template produces; it takes about a minute.

Then sign in to the {rhdh_url}[Developer Hub portal^] as a guest — one click on *Enter*, no password — and open the *Catalog* filtered to the `parasol-claims` Component: that page is the opening view for step 1. Keep the cockpit terminal beside it, signed in as `{user}`, for the terminal blocks in the steps.

Step 2 publishes to `{user}-svcs/parasol-demo-{user}`, and publishing into a name the organization already holds is refused: *Publish to Gitea* fails with `409 Conflict … The repository with the same name already exists`, and *Register in the software catalog* is greyed out and never runs. A rehearsal is what leaves that name taken, so list the organization first — this is step 2's own command:

[source,sh,role=execute,subs="attributes"]
----
curl -sk "{gitea_url}/api/v1/orgs/{user}-svcs/repos" \
  | python3 -c 'import sys,json;[print("repo:",r["full_name"]) for r in json.load(sys.stdin)]'
----

`parasol-golden` and no `parasol-demo-{user}` is the clean state: staging left the fallback service and the name step 2 needs is free. If `parasol-demo-{user}` is already listed, run the staging command above again — it applies the entry state first, which empties the scaffold organization *and* deregisters its catalog Location on the shared portal, then re-creates `parasol-golden`. Deleting the repository in Gitea by hand is not equivalent: the catalog entry is a separate object, so that clears the *Publish* conflict and leaves a stale registration standing in front of the *Register* step.

NOTE: Inside the portal, *Open the new repository* and the catalog's *View Source* link resolve to Gitea's in-cluster address (`gitea.ogsr-gitea.svc:3000`) and will not open in a browser. Reach a repository through the Gitea route instead — {gitea_url}/{user}-svcs/parasol-demo-{user}. *Open in the software catalog* stays inside the portal and works normally.

NOTE: The catalog query in step 1 is a garnish beside the portal page, which carries the step on its own. A `KeyError` traceback from that one-liner is what an unreachable portal or an unregistered entity looks like from the terminal.

CAUTION: If a live scaffold fails, the staged `{user}-svcs/parasol-golden` service shows the same result — it came from this same template. Either change the *Name* field to `parasol-demo2-{user}` and create again, which costs one field and lands step 2 as written, or run step 3 against `parasol-golden` instead. Staging materializes the golden-path *outcome* — the repository and its registered `catalog-info.yaml` — not the full skeleton, so show that catalog entry rather than a `pom.xml`; the paved-road file list is on `parasol-claims`, which step 1 already has open.

CAUTION: `ws prep developer-hub-golden-paths` returns the entry state and empties the `{user}-svcs` scaffold organization — it also deregisters the catalog entry from the shared portal and purges `{user}-dev`. Run the staging command above again after it.

=== Brief

image::developer-hub-golden-paths/developer-hub-golden-paths-02-golden-path-flow.svg["A new engineer fills a short form, which runs the New Parasol microservice software template. The template branches into three steps: scaffold a Quarkus skeleton with probes, metrics and OpenTelemetry; publish it to the engineer's own Git organization; and register it in the catalog with ownership and System. The first two arrive at a new service repository carrying paved-road wiring, the third at the software catalog, where the service appears with an owner."]

*The problem: cognitive load, and standards nobody follows*

A platform accumulates capabilities: a container image built the trusted way, a pipeline that ships it, signing and verification, GitOps delivery, safe scaling. Each one is also another tool, another repository layout, another set of conventions an engineer has to learn before writing a line of business logic.

The cost is not the tools; it is the cognitive load. The tenth engineer to create a service reverse-engineers how the last nine did it, copies a repository that was already subtly wrong, or asks the platform team to do it by hand. Standards that live in a wiki are standards that drift — the probes get forgotten, the base image goes stale, the pipeline is copied from a service that did it differently. The platform is powerful, and nobody can find the on-ramp.

*The golden path: a paved road, not a cage*

A developer portal fixes the on-ramp with two things. A *software catalog* answers "what do we run and who owns it": Components, the APIs they provide, the Systems they belong to, and the Groups that own them — each described by a small file next to the code, so the map is as current as the last commit. A *golden path* answers "how do I start something new, correctly, without asking anyone": a form plus a template that scaffolds a complete service with health, metrics and tracing already wired, a trusted base image, a build recipe and a catalog entry.

The phrase that matters is paved road, not cage. What the template produces is plain, standard source in the team's own repository, theirs to change from the moment it exists. The platform team makes the correct decisions once and gets out of the way — which moves compliance from something audited into a service later to the default state at creation.

Red Hat Developer Hub, Red Hat's supported build of the open-source Backstage project, is that portal.

*In this demo*

. The software catalog as the organization's live map — what runs, who owns it, and the API it provides
. A short form producing a complete, standards-compliant service in the team's own Git organization, registered in the catalog
. The scaffolded repository — plain, editable code carrying every decision the platform team made once

=== 1 · The catalog: what we run and who owns it — 3 min

Everything Parasol runs is in one catalog: the claims service, the APIs it exposes, the team that owns it. The entries are not maintained by hand — they are generated from files that live next to the code.

image::developer-hub-golden-paths/developer-hub-golden-paths-01-catalog-components.png["The Developer Hub catalog page, Kind filtered to Component, listing all three Parasol Components — parasol-claims, parasol-notifications and parasol-web — with columns for Name, System, Owner, Type, Lifecycle and Description. All three share the parasol-insurance System, the parasol owner and the production lifecycle, while their types differ between service and website. A Self-service button sits above the table."]

*Why it matters*

"Who owns claims, what depends on its API, which System is it part of" becomes a query rather than an archaeology project across wikis and chat histories. Because each entry comes from a `catalog-info.yaml` in the service's own repository, ownership and structure are reviewed in pull requests like everything else — so the map an incident responder opens is current, not a diagram three reorganizations out of date.

*On screen* — the Developer Hub *Catalog*: open the `parasol-claims` Component and trace its *owner* (the `parasol` group), its *System* (`parasol-insurance`) and the *API* it provides (`parasol-claims-api`); open that API and its OpenAPI definition renders in the portal.

The same map answers from the terminal, because the catalog is an API and not only a screen:

[source,sh,role=execute,subs="attributes"]
----
TOKEN=$(curl -sk {rhdh_url}/api/auth/guest/refresh | python3 -c 'import sys,json;print(json.load(sys.stdin)["backstageIdentity"]["token"])')
curl -sk -H "Authorization: Bearer $TOKEN" \
  "{rhdh_url}/api/catalog/entities/by-name/component/default/parasol-claims" \
  | python3 -c 'import sys,json;d=json.load(sys.stdin);s=d["spec"];print("owner:",s["owner"],"| system:",s["system"],"| provides:",s.get("providesApis"))'
----

*What just happened*

Owner, System and provided API came back as data. Because the relationships are typed and queryable, the same catalog feeds scorecards, access reviews and incident tooling instead of being one more page someone has to remember to update.

=== 2 · A form instead of a week of plumbing — 5 min

A new engineer needs a service: one that builds the trusted way, carries probes, metrics and tracing, and is ready for GitOps. Instead of a week of plumbing, they fill in three fields.

*Why it matters*

Everything the earlier modules assembled by hand — the trusted base image, the probes and metrics, the repository layout, the catalog entry — is a decision the platform team makes once and encodes in the template. The new service inherits all of it, so it starts compliant rather than being audited into compliance later. And the leverage compounds: improve the template once, and every service created afterwards inherits that too.

A form became a real Git repository and a registered, owned service in under a minute — carrying the base image, the probes, the metrics, the tracing and the GitOps wiring that the preceding modules built one command at a time.

=== 3 · A paved road, not a cage — 3 min

What the template produced is ordinary code in the engineer's own repository, not a locked black box handed back by a platform team.

image::developer-hub-golden-paths/developer-hub-golden-paths-05-what-you-built.svg["What the golden path produced: a short form naming a service and an organization runs the golden-path template, which creates both a new repository holding Quarkus with paved-road wiring and a catalog registration that records the owner and the System. From that repository, an in-cluster UBI9 build produces the image that runs in the engineer's namespace with health and metrics answering."]

*Why it matters*

A cage forces one way and punishes deviation; a paved road makes the right thing the easy thing and leaves the team free to drive off it when they have a real reason. Ownership transfers at creation — the code, the dependencies and the build recipe are all in the team's repository from the first commit — which is what keeps a golden path from becoming the next thing engineers work around.

*On screen* — the scaffolded repository in Gitea, at {gitea_url}/{user}-svcs/parasol-demo-{user}: `pom.xml` (Quarkus, Java 21), `src/.../InfoResource.java`, an `application.properties` with health, metrics and OpenTelemetry, a non-root UBI9 `Containerfile`, `catalog-info.yaml` and `devfile.yaml`. Then the wiring that arrived with it:

[source,sh,role=execute,subs="attributes"]
----
curl -sk "{gitea_url}/{user}-svcs/parasol-demo-{user}/raw/branch/main/catalog-info.yaml" | grep -E 'kind:|owner:'
----

*What just happened*

Nobody hand-wrote any of that. The ownership and System that make the service findable came from the same scaffold as the code, so the service is on the organization's map from the moment it exists — and the engineer owns it from that moment too.

== Frequently asked questions

*Everyone signs in with one click as a guest — how would this work with real identities?*::
Guest sign-in is a teaching simplification: one click, no credentials, one shared identity in the portal. A real deployment wires single sign-on, so the catalog and the templates run under each engineer's own identity with role-based access, and every scaffold is attributable to the person who ran it. Isolation here comes from each person scaffolding into their own Git organization instead.

*The template did not create a pipeline or a GitOps application — where is the rest?*::
This golden path scaffolds three things: the service skeleton with probes, metrics, tracing, a trusted image and a build recipe; the published repository; and the catalog registration. A pipeline and GitOps delivery are the paved road's next layer — exactly the kind of thing a platform team adds to the template so every future service inherits it. The pattern is the point: standards encoded once, applied on every click.

*Can two teams scaffold the same service name?*::
Not into the same place. A Git server refuses a second repository with a name it already holds, so the publish step fails with a `409 Conflict` that names the exact conflict rather than half-completing the scaffold; and a catalog keyed by name needs distinct entries, which is why the name here carries the username. In a real deployment the naming convention lives in the template, so the collision is prevented at the form rather than discovered at the push.

*The scaffold took seconds — how long until that service is actually running?*::
The first in-cluster build of a new service pulls the Java builder image and runs a full Maven build, about eight to nine minutes; a later build can land on any worker node, so it is not reliably faster. That part is ordinary work the platform already does the same way for every service. Scaffolding is the part that used to take a week.

== 4. Deploy your scaffolded service into {user}-dev
⏱ *~6 min* · collect the build and run the new service

The build you started in exercise 3 has been running on the cluster while you toured the repo.
Collect it — poll until it reports `Complete`. How long that takes depends almost entirely on whether the node already holds the UBI9 Java 21 builder image: measured *8–9 minutes* on a genuinely cold node, and *3m57s* on a warm one (2026-08-02). Either is normal:

[source,sh,role=execute]
----
for i in $(seq 1 90); do
  B=$(oc get build -n $DEV -l buildconfig=$SVC --sort-by=.metadata.creationTimestamp -o jsonpath='{.items[-1:].metadata.name}' 2>/dev/null)
  P=$(oc get build "$B" -n $DEV -o jsonpath='{.status.phase}' 2>/dev/null)
  echo "  $(date +%T)  ${B:-build}: ${P:-Pending}"
  case "$P" in
    Complete) echo "  ✔ image built and pushed to the internal registry"; break;;
    Failed|Error|Cancelled) echo "  ✖ build $P — see: oc logs build/$B -n $DEV"; break;;
  esac
  sleep 12
done
----
