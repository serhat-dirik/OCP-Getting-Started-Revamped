Parasol's platform team packages its whole delivery practice, from pipeline gates to a canary in production, into one Developer Hub template, so a new service ships the way the auditors expect from its first commit, and the developer's work is the code.

*The problem: every practice is another thing to assemble*

A platform collects good practices: a pipeline on every push, tests and an image scan as gates, a software bill of materials, a signature that proves who built the image, a policy check before deploy, GitOps promotion, canary releases.
Each one is sound, and each one is more files, conventions and credentials a developer must get right before writing business logic.
The tenth service gets them by copying the ninth, with whatever was wrong with it.

*The golden path: the platform team's practice, as a product*

Red Hat Developer Hub, Red Hat's build of the open-source Backstage project, puts a *software template* behind a form.
This template creates two repositories: the service, and its GitOps and CI configuration.
The platform team's one-time wiring for the team, two webhooks and an Argo CD ApplicationSet, turns them into running pipelines and environments within a minute.
Keeping that template right, for every team at once, is the platform engineering team's job.

*In this demo*

. One page for the whole service: code, pipelines, deployments and what is running
. A push that becomes a tested, scanned, signed and verified deploy, with nobody writing a pipeline
. A tag that promotes the same digest to stage and then to a canary in production

*Why it matters*

What runs in production is exactly what was tested, by digest, and the GitOps history shows who released what and when.

== Frequently asked questions

*Where does the pipeline live, and who can change it?*::
In the service's GitOps repository, `ci/pipeline-build.yaml`, applied by Argo CD. The team can change it with a commit; the platform team improves it for new services by changing the template, and many organizations move it into a shared, versioned pipeline instead so one change reaches every service.

*What happens if a test fails or the image has a critical vulnerability?*::
The run stops at that task, nothing is committed to the GitOps repository, the environments keep running the last image that passed, and that commit can never be released.

*Why is the image not checked again at deploy time?*::
It is checked twice before Git ever names it: by Conforma in the build pipeline and again by the release pipeline before stage. A cluster admission policy can add a third check at deploy time; this workshop applies one to the trusted supply chain module's image only.

*Does the developer need to know Tekton or Argo CD?*::
No. They push code and tag releases; the template and the platform's wiring do the rest, and Developer Hub shows what happened.

== 5. Release again: a canary in production
⏱ *~12 min* · the second release meets a stable version, so prod runs it as a canary

The first release had nothing to compare against, so Argo Rollouts put it straight into production.
A second release meets the stable one: half the pods move to it, an automated analysis checks them, and only then does it take over.

. In Dev Spaces, change the `quote` value in `InfoResource.java` to `"golden-path-2"`, then commit and push:
+
[source,sh]
----
git commit -am "Second quote release"
git push origin main
----

=== Break and fix: tag before the build is done

. *Right away*, without waiting for the build, tag the new commit and push the tag:
+
[source,sh]
----
git tag v1.1.0
git push origin v1.1.0
----

*Predict:* the release pipeline promotes the image built from the tagged commit. That build is still running. What does the release find?

In Developer Hub's *CI* tab, the new release run turns *Failed* within about ten seconds, while the build run beside it is still *Running*. Read why:

[source,sh,role=execute]
----
tkn pipelinerun logs -n $CICD $(tkn pipelinerun list -n $CICD -o name | grep -m1 release | cut -d/ -f2) -t resolve-image
----

.Expected output (your commit differs)
[source,texinfo,subs="attributes+"]
----
task resolve-image has failed: "step-resolve" exited with code 1: Error
[resolve-image : resolve] Commit 689d91cdc990d76744cdf02dcf98af92552624ba has no image that passed the build pipeline.
[resolve-image : resolve] Only a commit that passed every gate can be released. Wait until its
[resolve-image : resolve] parasol-quote-{user}-build run Succeeded, then tag it with the next version.
...
Tasks Completed: 1 (Failed: 1, Cancelled 0), Skipped: 2

The release refused, and stage and prod still run `v1.0.0`: only a commit that passed every gate of the build pipeline can be released, however it is tagged.

*Fix:* wait until the new build run reads *Succeeded* in the *CI* tab (about 2.5 minutes after your push), or from the terminal:

[source,sh,role=execute]

tkn pipelinerun list -n $CICD --limit 3
----

[source,sh]

----
