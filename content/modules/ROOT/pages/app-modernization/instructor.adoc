== Timing (measured)

Total hands-on: *~40 min*. Exercise timings from a live run; MTA analysis and the `ws` lifecycle were measured against MTA 8.1.2 on OpenShift 4.21.22 on 2026-07-13. Those versions are a *record of the measurement*, not a requirement — the MTA operator follows the catalog's default channel by design, so your Hub will very likely be a different release (two clusters in use today carry 8.0.1 and 8.2.0). Confirm yours with `oc get csv -n openshift-mta` if a number in the report table looks off.

| Segment | Time | Notes

== How to know the room can move on

Two instruments tell you this without guessing, and neither is the clock. Each exercise ends on a `[.checkpoint]` block with a *✔ Verify:* line in the lab — that is the move-on signal, written for attendees to confirm before continuing. For the whole module, `ws verify app-modernization --user <u>` is the same self-check the attendee can run any time; a room reporting all checks green is actually done, not just out of time.

== Pre-flight checklist

Run these from an admin context *before* the session. Each shows the captured expected output (domains shown as placeholders).

*1. The environment materializes.* A fresh cluster (or a user who has never run this module) needs the entry state built before any check below will go green:

[source,sh,role=execute]
----
adm start app-modernization --user user2
----

This is the same path `ws prep app-modernization` runs — attendees trigger it themselves from the top of the *concept* page. `ws prep app-modernization` waits up to *5 minutes* for the entry state to converge (no module-specific `waitSeconds` is declared, so this is the engine default); it normally returns well inside that — the measured figures in the `ws` lifecycle table below (`adm solve` ~76 s, `ws reset` ~2 min) are the realistic ones to expect, and the ceiling is a timeout, not a duration. Deliver the concept at its normal pace and it converges under you.

*2. MTA Hub is healthy.*

[source,sh,role=execute]
----
oc get pods -n openshift-mta
----

[source,texinfo]
----
NAME                            READY   STATUS    RESTARTS   AGE
mta-hub-...                     1/1     Running   0          ...
mta-operator-...                1/1     Running   0          ...
mta-ui-...                      1/1     Running   0          ...
rhbk-operator-...               1/1     Running   0          ...
----

*3. The MTA console route answers (this is the URL attendees use).*

[source,sh,role=execute]
----
oc get route mta -n openshift-mta -o jsonpath='{.spec.host}{"\n"}'
# -> mta-openshift-mta.apps.<cluster-domain>   (edge/Redirect, HTTP 200)
----

*4. Each attendee's entry state is clean.* For a sample user:

[source,sh,role=execute]
----
ws verify app-modernization --user user2 --entry-only
----

[source,texinfo]
----
✅ namespace user2-modernize exists
✅ entry marker ws-entry-app-modernization present
✅ MaaS config present (endpoint + model)
✅ legacy fork parasol-legacy-claims reachable in Gitea
▶ [ADS] maas-credentials present — Developer Lightspeed for MTA is wired ...
✅ no modernized service deployed yet (attendee builds it)

✅ all 5 checks passed
----

*5. The AI wiring works `[ADS]`.* Confirm the model is the one this cluster's key is scoped to, and that a real completion returns. For a sample user:

[source,sh,role=execute]
----
oc get cm maas-config -n user2-modernize -o jsonpath='{.data.model}{"\n"}'
# -> the model your cluster's MaaS key is scoped to (e.g. the cluster-specific model)
----

Then *run Exercise 4's API block once yourself*, in a terminal for that user. Do not read the ConfigMap and assume: the key is scoped to exactly one model, and asking for any other returns `HTTP 401` with `key not allowed to access model` (verified live 2026-07-31). A wired endpoint ends the block with:

[source,texinfo]
----
reasoning trace: none - this model answers directly
--- the model answer ---
dataSource.setUrl(System.getenv("CLAIMS_DB_URL"));

reads the URL from the environment: YES - System.getenv("CLAIMS_DB_URL") is present
----

The first line is the one to note before you present. `reasoning trace: none` means the model answers directly; a character count there means it thinks first, which is normal and already handled — but it makes the block slower, so budget a few extra seconds in the demo. Only the final `YES` is a pass/fail signal; the answer text between them is the model's own and will not match this capture word for word.

[NOTE]
.The per-cluster model is sourced on-cluster — a fixed defect
====
The Application Modernization entry state *sources the model and endpoint from the platform Lightspeed secret* (`openshift-lightspeed/credentials` keys `model`/`endpoint`) at sync time, falling back to the chart default when those keys are absent. This is why a cluster whose MaaS key is scoped to a *different* model still gets the *right* model in `maas-config` and in the workspace's `GENAI_MODEL` — without a code change. If `maas-config` shows the wrong model, the platform Lightspeed secret is missing its `model` key; fix the secret, then `ws reset app-modernization --user <u>`.
====

*6. The attendee-facing repo URL clones over HTTPS.* MTA analyzes the HTTPS Gitea *route* (recorded in the entry marker), which clones cleanly with the Hub's secure default — no `git.insecure` change needed. If you instead drive the Hub API directly against the *internal* `http` Gitea service address, you will hit `http URL used with git.insecure.enabled = FALSE` — use the HTTPS route.

== Demo-mode notes (beyond Say/Show/Do)

* *Stage three finished analyses the day before — not one.* A live analysis is *~3–5 min*, too long to narrate, so every report the arc shows has to exist before you start. *Three* of them, and the reason is a property of the product rather than a preference: the MTA console keeps *one current report per application*, so producing the after-the-fix report by re-analysing `parasol-legacy-claims-demo` in place *overwrites the baseline beat 1 opens on*. One application per report is the only way to put a before and an after on screen together — `parasol-legacy-claims-demo` (the untouched seed; the baseline, beat 1), `parasol-legacy-claims-fixed-demo` (the same app with beat 2's fix already applied, from a `demo-fixed` branch you push to your own fork; beat 3, the money moment), and `parasol-claims-demo` (the modernized Quarkus service; beat 3's side-by-side). Run all three in *Source code* mode against the *same* five targets, or the totals are not comparable to one another. The repo/branch table and the exact `git` commands for `demo-fixed` live in the lab's demo-flavor *Before you present* block — stage from there, so there is one recipe and not two.
* *What the staging costs you — and it sits outside every measured number on this page.* Three analyses at *~3–5 min* each is *~10–15 min of Hub time*, and they can overlap, because the Hub runs each analysis as its own task pod. On top of that sit the console clicks to create three applications and the one `git push` that makes the `demo-fixed` branch; *this module measures neither*, and the Timing table above is *hands-on lab* time, not demo prep. Do it the evening before, not in the half hour before the room fills.
* *Keep the `-demo` suffix on all three.* Never stage under `parasol-legacy-claims-{user}` or the bare repo name: the Hub's portfolio is shared and flat, so an application carrying an attendee's username is the one *they* are asked to create in the lab's exercise 2 — a finished analysis sitting there hands them the answer and leaves exercise 5 with no baseline to drop from. If you want to show a progress-to-complete transition live, kick that run off under a *fourth*, throwaway `-demo` name; re-running any of the three replaces the report a later beat still needs.
* *Warm the Dev Spaces workspace.* First workspace start pulls the universal developer image and can take 2–3 minutes. Start it before the demo so the MTA extension view is already open.
* *Beat 3 is a two-report side-by-side — have both open.* `parasol-legacy-claims-fixed-demo` (the *Hardcoded IP address* row gone, the effort total below the baseline) beside `parasol-claims-demo` (the modernized service). The *24 → 1* gap between the untouched legacy app and its Quarkus counterpart is the strongest single visual in the module, and it only lands if the two reports are one *click* apart rather than one *re-analysis* apart. Read your own totals off the screen first: those two figures are captures from one Hub release and yours move with its shipped rule sets, so narrate the drop and the ratio rather than promising the room a number.
* *Rehearse the AI beat once — on the cluster you will present from.* `temperature 0` does *not* make the output fixed: 12 identical requests to one model returned the same Java line, but one of them wrapped it in a Markdown code fence and eleven did not (measured 2026-07-31). And the model itself differs per cluster, because the MaaS key is scoped to exactly one model. Rehearse so you can narrate the *shape* of the change — literal out, environment lookup in — rather than promising the room a sentence.

== Top 5 questions attendees ask

. *"Is this the AI that auto-migrates my app?"* +
No. Developer Lightspeed for MTA proposes a *per-issue diff* that you review and accept. It compresses the typing, not the judgement. The Hub also has a separate agentic component (the Kai solution server) that is *not* configured in this workshop — the AI you use here is the *VS Code / Dev Spaces extension* feature.

. *"Why not just wrap the WAR in a container and ship it?"* +
Because the config is compiled in (a hardcoded DB IP and password), the app writes to a host filesystem path a container can't provide, and it expects a servlet container that isn't there. MTA finds each of these *before* they become a 2 a.m. incident. Lift-and-shift (rehost) buys time but pays no modernization debt down.

. *"What do the effort story points actually mean?"* +
A *relative* estimate of the work to fix an issue, summed across the app. Use them to *rank* apps and *track a burn-down* (the number drops as you fix), not to promise hours to management. `parasol-legacy-claims` scores 24; the modern Quarkus equivalent scores 1.

. *"Do all thirty attendees hammer the same Hub?"* +
Yes — the MTA Hub is *shared*, with a per-user Application in the portfolio. Each analysis runs as its own task pod; a small source app is ~3–5 min, so staggered starts are fine. There is no per-user MTA instance (that would be heavy); portfolio isolation is by Application, not by RBAC.

. *"What if my cluster doesn't have the Advanced Developer Suite?"* +
The AI section is `[ADS]` and *degrades gracefully*: you make the same config-externalization fix by hand, and the analyze → fix → re-analyze loop is identical. The `[OCP]` MTA core (assess / analyze / replatform) is fully functional without `[ADS]`.

== Watchouts

* *LLM nondeterminism, and the model is not the same everywhere.* The demo issue (hardcoded IP → `System.getenv`) yields a *substantively* stable suggestion, but not a stable string: the packaging varies between identical `temperature 0` calls, and your cluster's model is whichever one its MaaS key is scoped to. Stick to the rehearsed issue for the demo; in the lab, the *review-the-diff* discipline covers any variation. Never diff the model's text against the page.
* *Reasoning models change what "success" looks like.* If your cluster serves a model that emits a thinking trace, Exercise 4's API block spends part of its budget on that trace before answering. The block is written for both kinds — `max_tokens: 1024` plus a strip of `reasoning_content` / inline `<think>` — and reports a verdict line rather than a quotable answer. If someone trims that budget "for speed", the block returns `finish_reason=length` and *no answer*, which is what a stale, smaller budget did to this module before 2026-07-31. Do not add a model-specific thinking switch either: the gateway returns `HTTP 200` for unknown request fields and ignores them, so a green call proves nothing about whether the switch applied.
* *Dev Spaces first-start latency.* The universal developer image pull dominates the AI section's clock. Pre-warm.
* *Shared-Hub portfolio hygiene — and it is genuinely shared.* One MTA Hub serves the whole room, with *no* per-user view and *no* login on this build: MTA's roles (`tackle-admin`/`architect`/`migrator`) are personas, not tenants, so every user would see the whole inventory even with authentication switched on. That is why the lab has each attendee name their Application `parasol-legacy-claims-{user}` — the bare repo name would give you eight indistinguishable rows. Anyone can therefore edit or delete anyone's entry, so say so if your cohort isn't a trusted group. Portfolio state lives in the Hub DB, not in `{user}-modernize`, so the namespace purge cannot see it — which is why `ws reset` (`ws prep`) reaches the Hub separately and deletes *exactly one* row, `parasol-legacy-claims-<the user who ran it>`, declared by name in `gitops/entry-states/app-modernization/ws-meta.yaml` and matched exactly, never by prefix. That narrowness is deliberate on a shared, unauthenticated Hub: a wider sweep would delete a colleague's work. So attendee rows clear themselves, and *nothing* touches your three `-demo` staging rows — which is what you want between runs, and means they are yours to delete by hand when the *event* ends. (On a cluster torn down afterwards the Hub goes with it and this is moot.)
* *The Kai solution server shows "not ready."* On a stock install the Hub's `KaiSolutionServerReady` condition is `False` (no Kai secret). That is expected and *out of scope* — do not send attendees into the Hub's not-ready AI feature; the AI beat is the *extension* in Dev Spaces.
* *Analysis returns zero issues?* The target *labels* matter. In the console the friendly targets (*Containerization*, *OpenShift*, *OpenJDK*) map to rule labels `cloud-readiness`/`linux`/`openjdk`/`jakarta-ee`/`jws`; if a run reports nothing, the target selection didn't resolve to any ruleset — re-select the targets.
* *The modernized pod runs but never becomes Ready.* This is the exercise-6 probe break, done on purpose — after deploying `parasol-claims-modernized` the pod sits `Running` but `0/1`, because the readiness probe still points at `/health`, which the Quarkus service returns `404` for. The fix *is* the exercise: point the probe at `/q/health/ready` (Quarkus health lives under `/q/health/...`); `oc rollout status deploy/parasol-claims-modernized` confirms `1/1` once patched.

== Provenance

Application Modernization is a *reworked* module: the `parasol-legacy-claims` migration target — its Spring-on-Tomcat WAR structure, the hardcoded-configuration anti-patterns, and the assess → analyze → refactor → deploy arc — is re-themed from Konveyor's `customers-tomcat-legacy` sample (via the Red Hat Modern Application Development workshop, `rh-mad-workshop`; credited in the README) onto the Parasol claims domain. The AI-assisted fix and the workshop delivery built around it are net-new.

Everything on this page was *performed*, not estimated: the portfolio analysis of the seeded `parasol-legacy-claims` fork (analyzer add-on, source mode, targets `cloud-readiness`/`linux`/`openjdk`/`jakarta-ee`/`jws`) against a live MTA 8.1.2 Hub on OpenShift 4.21.22 on 2026-07-13 returned *24* story points across 6 mandatory + 1 potential issue + 15 technology tags; the modern Quarkus counterpart analyzed identically returned *1*; and a real Developer Lightspeed for MTA completion rewrote the hardcoded JDBC URL to `System.getenv("CLAIMS_DB_URL")`. The `ws` lifecycle figures in pre-flight and the Timing section (`ws verify --entry-only` ~8 s, `adm smoke` ~41 s, `adm solve` ~76 s, `ws reset` ~2 min) are from the same session.

The AI pre-flight capture and the nondeterminism/reasoning-model Watchouts were *re-verified* against a live Models-as-a-Service endpoint on 2026-07-31 — including the `reasoning trace: none` / `System.getenv` capture quoted in pre-flight item 5, and the finding that twelve identical `temperature 0` requests to the same model returned the same Java line but varied in Markdown formatting. The two version literals in this page's header comment (OCP 4.21.22 / MTA 8.1.2) are frozen provenance recording what was measured, on what, when — not a requirement; see the Timing section above for why your Hub will very likely differ. The Kai solution server's `KaiSolutionServerReady: False` on a stock install, and the fully shared (no per-user view, no login) MTA Hub portfolio, are both real, observed properties of this build, not assumptions.

Two claims in Demo-mode notes and Watchouts are *derived* rather than measured, and are marked as such here so nobody quotes them as timings. The *~10–15 min* demo-staging figure is arithmetic on the measured single-analysis time (three runs at ~3–5 min), not a stopwatch on three; the console clicks and the `demo-fixed` `git push` are unmeasured by design. And the statement that `ws reset`/`ws prep` deletes the attendee's own Hub row — exactly one, `parasol-legacy-claims-<user>`, by exact name — is read from the shipped `ws` CLI and `gitops/entry-states/app-modernization/ws-meta.yaml` (`purgeMtaApps`), not re-measured against a Hub. It replaced an older claim on this page that `ws reset` left portfolio state alone, which the CLI has not done since it learned to reach the Hub.
