Each entry is symptom → cause → fix. All were seen (or deliberately induced) while performing this module on OpenShift 4.21.22 with Migration Toolkit for Applications (MTA) 8.1.2.

== The analysis finishes instantly and reports zero issues

*Symptom:* The analysis task completes in a second or two and the report is empty — no issues, effort 0.

*Cause:* No ruleset was selected — the analysis ran with an empty rule set. This happens when the *Set targets* step is skipped or the chosen tiles don't cover the app's technology (each console tile resolves to shipped rule labels).

*Fix:* Re-run the analysis and select the five tiles *Containerization* / *Linux* / *OpenJDK* / *Jakarta EE 9* / *JBoss Web Server 6* (they resolve to `cloud-readiness`, `linux`, `openjdk`, `jakarta-ee`, `jws`). A real run on this app takes a few minutes (~3 min measured) and returns *6 mandatory* issues; an instant, empty result means the rules never loaded.

== Analysis fails: "http URL used with git.insecure.enabled = FALSE"

*Symptom:* The analysis task fails almost immediately; the task error reads `http URL used with git.insecure.enabled = FALSE`.

*Cause:* The application's repository was configured with an insecure `http` Git URL (for example the internal `gitea` service address on port 3000 rather than the HTTPS route), and the Hub refuses insecure Git by default.

*Fix:* Use the *HTTPS* Gitea *route* URL — the one recorded in your entry marker (`{gitea_url}/{user}/parasol-legacy-claims`). It clones cleanly with the Hub's secure default. (Only an operator maintaining the Hub would instead flip `git.insecure.enabled`; attendees should just use the HTTPS route.)

== Re-running the module: the Application from my last attempt is still in the MTA portfolio

*Symptom:* You are doing the module a second time, and the *Create new application* drawer refuses `parasol-legacy-claims-{user}` — or the *Application inventory* already lists it, holding the analysis results from your previous run.

*Cause:* MTA's portfolio lives in the *Hub's own database*, in a namespace shared with the whole class — not in your `{user}-modernize` project. Purging your namespace therefore cannot see it, which is why a re-run used to inherit the old entry.

*Fix:* Nothing by hand — `ws prep app-modernization` clears *your* application from the Hub as part of preparing the module, so the "add app" beat starts clean. (It deletes only the exact name this module declares for your user, never a prefix or wildcard match: the Hub is shared, and a loose match would delete a classmate's work.)

Prep will say so if it *could not* do it, and those lines are the ones to act on — `MTA Hub route not found …` or `MTA Hub did not answer — skipping portfolio cleanup`. Both mean the Hub was unreachable at that moment, not that your environment is broken; nothing else in the prep is affected. Re-run `ws prep app-modernization`, or delete the application yourself in the MTA console (*Application inventory* → your row → *Delete*) before re-adding it.

== The MTA console shows an AI feature that says "not ready"

*Symptom:* Somewhere in the Hub UI there's an AI/solution-server feature that appears disabled or reports "not ready."

*Cause:* That is the Hub-level *Kai solution server*, which needs its own configuration (a Kai secret) that this workshop does not install — its readiness condition is `False` by design.

*Fix:* Ignore it — it is *out of scope*. The AI-assisted refactoring in this module is *Developer Lightspeed for MTA*, which lives in the *MTA extension for VS Code / Dev Spaces*, not in the Hub. Do your AI fix there.

== `maas-config` shows the wrong model (or the AI path is "not wired")

*Symptom:* The pre-flight check prints a model name you didn't expect, or the lab's `[ADS]` check reports "Manual path" even though the cluster is entitled.

*Cause:* The entry state *sources* the model, endpoint, and key from the platform Lightspeed secret (`openshift-lightspeed/credentials`) at sync time. If that secret is missing its `model`/`endpoint` keys, the chart *falls back* to its default model; if the whole secret is unreadable, no `maas-credentials` Secret is created (graceful degradation).

*Fix:* Confirm the platform secret carries `apitoken` + `model` + `endpoint`, then `ws reset app-modernization --user <u>` to re-run the copy. After reset, `oc get cm maas-config -n <u>-modernize -o jsonpath='{.data.model}'` shows the effective model, and `oc get secret maas-credentials -n <u>-modernize` exists with `GENAI_API_KEY`/`GENAI_MODEL`/`GENAI_ENDPOINT`.

== The AI section is unavailable ("Manual path")

*Symptom:* The lab's entitlement check reports the *Manual path*; there is no `maas-credentials` Secret.

*Cause:* The cluster has no readable Models-as-a-Service credential — typically because the *Advanced Developer Suite* `[ADS]` entitlement (and its key) isn't present. This is *expected* on an `[OCP]`-only cluster.

*Fix:* Follow the *Manual path* — make the same config-externalization edit by hand. The `[OCP]` MTA analyze → fix → re-analyze loop is unaffected; only the typing assistant is absent.

== The "prove the AI wiring" block prints a reasoning trace, or no answer at all

*Symptom:* The API block in Exercise 4 returns `HTTP 200` but no Java line — either a wall of the model thinking aloud (often between `<think>` and `</think>`), or nothing usable and `finish_reason=length`.

*Cause:* The cluster's model is a *reasoning* model. It spends tokens on a thinking trace before it answers, and a `max_tokens` budget sized for the one-line answer is consumed entirely by the trace — so the reply is truncated before the answer is ever emitted. This is a property of the model your MaaS key is scoped to, not of the lab: the same block on a directly-answering model returns in ~17 tokens.

*Fix:* The shipped block already handles both — it budgets `max_tokens: 1024` and strips the trace from either `reasoning_content` or an inline `<think>` block, then reports whether the answer reads `CLAIMS_DB_URL` through `System.getenv`. If you edited the block down to a smaller budget, restore it. If it still says `finish_reason=length`, raise `max_tokens` further — a longer trace needs more room, and on a directly-answering model raising the ceiling costs nothing because `max_tokens` caps the reply rather than padding it.

Two things *not* to do. Do not "fix" it by pinning the prompt or the expected output to one model's phrasing — the two clusters this workshop runs on are scoped to *different* models, and even one model at `temperature 0` varies its packaging between calls. And do not add a model-specific thinking switch (for example a `chat_template_kwargs` flag) and assume it took effect: the gateway accepts unknown request fields with `HTTP 200` and silently ignores them, so a successful call is *not* evidence the switch did anything.

== Developer Lightspeed proposes a fix that's wrong (or won't compile)

*Symptom:* The AI's suggested diff changes behavior unexpectedly, references something that doesn't exist, or wouldn't compile.

*Cause:* The output is a *probabilistic model's suggestion*, not a verified change. Models are sometimes wrong — occasionally confidently so.

*Fix:* This is the lesson, not a bug — *read every diff before accepting it*. Reject a bad proposal, refine the issue context, or fix it by hand. Then *re-analyze*: a correct fix removes the issue and drops the effort; if the issue is still there, the fix didn't land. The analysis is your test.

== The modernized pod runs but never becomes Ready

*Symptom:* After deploying `parasol-claims-modernized`, the pod is `Running` but `0/1` ready; `oc get pods` shows it never passes readiness.

*Cause:* The readiness probe points at the wrong path. The lab deliberately starts with `/health`, which the Quarkus service returns `404` for.

*Fix:* Point the readiness probe at the real endpoint, `/q/health/ready` (Quarkus health lives under `/q/health/...`). After the patch, `oc rollout status deploy/parasol-claims-modernized` reports available and the pod turns `1/1`.

== The modernized pod is ImagePullBackOff

*Symptom:* `parasol-claims-modernized` won't start; events show `ImagePullBackOff` on the `parasol-claims` image.

*Cause:* The modernized image isn't present in the cluster's internal registry (`ogsr-parasol-images`) yet — it's populated by the workshop image-load step, and on a fresh cluster it may not be loaded.

*Fix:* This is an environment provisioning gap, not a lab error — tell your instructor.

Expect `ws verify app-modernization` to go *red* while this lasts, and that red is correct. The end-state check asserts the modernized Deployment is *Ready* (`readyReplicas >= 1`), not merely present — a deliberate hardening, because the earlier present-only check passed on a pod that was crash-looping and told nobody. A pod that cannot pull its image is not a finished lab. The script's hint discriminates the two causes for you: *absent* means the lab simply has not been done yet (the expected state on a fresh entry, not a fault), while *present but not Ready* means something is actually broken — this case, or a crash-loop needing `QUARKUS_DATASOURCE_ACTIVE=false`.

Give that check time to answer, and do not read a pause as a hang. Readiness assertions no longer judge on the first look: they *poll*, for up to *45 seconds*, before deciding. A Deployment you have only just rolled out therefore gets a chance to converge instead of collecting a red ❌ for being seconds old — so a `ws verify` run right after a deploy can sit quietly for the better part of a minute and that is the check working, not stalling. A healthy workload answers on the first poll and costs nothing; the wait is only ever spent on a workload that was not ready yet. The upshot for this entry: a ❌ that arrives *after* that wait is a real one, so start reading the pull events rather than re-running the command.

== Dev Spaces takes minutes to open the workspace

*Symptom:* The Dev Spaces workspace spins for 2–3 minutes on first start.

*Cause:* First start pulls the universal developer image (with the JDK, Maven, and the MTA extension). It's a one-time cost per workspace.

*Fix:* Wait it out; subsequent starts are fast. Instructors: pre-warm a workspace before a demo so the MTA extension view is already open.

== `ws smoke` fails only on "cockpit clone HEAD matches the mirror"

*Symptom:* `ws smoke app-modernization <u>` reports 11/12, failing only the freshness check ("pod serves ..., mirror ...").

*Cause:* The attendee's cockpit pod holds a Git clone from *before* the latest content push — a stale cockpit, not a module defect.

*Fix:* `ws git-refresh --restart-terminals --user <u>` re-clones the cockpit to the mirror HEAD; re-run `ws smoke` for 12/12. (Every other check — identity, isolation, `ws prep`/`verify`, the smoke command — passes independently of this one.)
