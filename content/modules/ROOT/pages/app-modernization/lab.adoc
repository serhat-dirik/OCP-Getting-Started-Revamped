The *deploy* step at the end is genuine dual-path: a `Console::` tab (the OpenShift web console) and a `CLI::` tab (`oc`) — pick either.

== 1. Meet the migration target
⏱ *~5 min* · read the legacy code and find the anti-patterns MTA will flag

Before you analyze the app, look at what makes it *legacy*. Clone your fork into the terminal and read the three files that carry the worst offenders.

[source,sh,role=execute]
----
git clone $REPO /tmp/legacy 2>/dev/null || (cd /tmp/legacy && git pull)
sed -n '6,11p' /tmp/legacy/src/main/resources/persistence.properties
grep -n "AUDIT_LOG_PATH\|System.out" /tmp/legacy/src/main/java/com/parasol/claims/legacy/config/ApplicationConfiguration.java
grep -n "java.version\|ojdbc\|tomcat-servlet" /tmp/legacy/pom.xml
----

.Expected output (abridged — one representative line per file; config baked into the build, the exact things a container can't tolerate)
[source,texinfo]
----
jdbc.driverClassName=oracle.jdbc.driver.OracleDriver
jdbc.url=jdbc:oracle:thin:@10.14.221.9:1521/CLAIMSDB
jdbc.user=claims
jdbc.password=claims
hibernate.hbm2ddl.auto=create-drop
hibernate.dialect=org.hibernate.dialect.OracleDialect
19:    private static final String AUDIT_LOG_PATH = "/opt/parasol/logs/claims-audit.log";
...
19:    <java.version>1.8</java.version>
----

You are looking at the whole modernization story: a *hardcoded database IP* and *plaintext password*, a *hardcoded filesystem path* the container can't write, `create-drop` that would *wipe the schema on every start*, a *proprietary Oracle* driver, and a pin to *Java 8*. MTA is about to find every one of these — and *score* them.

== 4. Fix an issue with Developer Lightspeed for MTA `[ADS]`
⏱ *~8 min* · let the AI propose the config-externalization fix — then review it critically

You'll fix the *Hardcoded IP address* issue — the cheap, high-value win. *Red Hat Developer Lightspeed for MTA* — an AI feature of the *MTA extension for VS Code / Dev Spaces* — proposes a concrete diff for a selected issue.

[IMPORTANT]
.This section is `[ADS]` — and degrades gracefully
====
Developer Lightspeed for MTA is part of the *Red Hat Advanced Developer Suite* `[ADS]`. If your cluster has it, follow the *AI path*. If it doesn't, follow the *Manual path* — you fix the *same* issue by hand and the rest of the lab is identical. Check which applies — the command below asks the model endpoint for a real (1-token) completion with your cluster's key, so it reports the AI path only when the wiring *actually answers* (a ConfigMap and Secret can be present with an expired or mis-scoped key; only an `HTTP 200` proves the path works):

[source,sh,role=execute]
----
code=$(curl -sk -o /dev/null -w '%{http_code}' --max-time 20 \
  "$(oc get cm maas-config -n $NS -o jsonpath='{.data.endpoint}' 2>/dev/null)/chat/completions" \
  -H "Authorization: Bearer $(oc get secret maas-credentials -n $NS -o jsonpath='{.data.GENAI_API_KEY}' 2>/dev/null | base64 -d)" \
  -H 'Content-Type: application/json' \
  -d '{"model":"'"$(oc get cm maas-config -n $NS -o jsonpath='{.data.model}' 2>/dev/null)"'","max_tokens":1,"messages":[{"role":"user","content":"ping"}]}' \
  2>/dev/null)

  200)     echo "AI path: Developer Lightspeed is wired (the model answered HTTP 200)." ;;
  401|403) echo "Manual path: the MaaS key is missing, expired, or not scoped to this model (HTTP $code) — fix by hand (graceful degradation)." ;;
  *)       echo "Manual path: the model endpoint did not answer (HTTP ${code:-000}) — fix by hand (graceful degradation)." ;;

The model returns a diff. For this issue, a real captured proposal replaces the compiled-in URL in `PersistenceConfig.java` with a runtime lookup:

[source,java]
----
// before:  dataSource.setUrl(config.getProperty("jdbc.url"));   // resolves the hardcoded jdbc:oracle:thin:@10.14.221.9:...
// after (Developer Lightspeed proposal):
dataSource.setUrl(System.getenv("CLAIMS_DB_URL"));
----

Your model may word it differently — a different variable name, a fallback default, an added comment. What must be true is the *shape*: the URL stops being a compile-time literal and becomes a runtime lookup.

*Read the diff before accepting it.* This one is correct — it moves the value out of the build and into the environment, exactly the containerization fix — but you only *know* that because you read it. Accept it, then provide the value the way a container should, as an environment variable, not a literal.

    print("--- the model answer ---"); print(ans if ans else "(nothing left after the trace)")
    ok="System.getenv" in ans and "CLAIMS_DB_URL" in ans
    if ch.get("finish_reason")=="length" and not ok: print("\nfinish_reason=length: the model used the whole max_tokens budget and never reached its answer. Raise max_tokens and re-run.")
    print("\nreads the URL from the environment: "+("YES - System.getenv(\"CLAIMS_DB_URL\") is present" if ok else "NO - re-read the answer above"))'
----

*What to look for* — not a sentence to match, a *property* to check. The last line prints `reads the URL from the environment: YES` when the returned Java reads `CLAIMS_DB_URL` through `System.getenv`. That is the only part of the answer that is fixed. Everything else is the model's own prose and *will* differ: your cluster's model is whichever one its MaaS key is scoped to, and even one model at `temperature 0` varies its packaging — the same request returned the line bare on one call and wrapped in a Markdown code fence on the next. Judge the *substance*; never diff the text.

Two lines in that pipeline are doing real work.

*`max_tokens` is a budget a thinking model can exhaust.* Some models answer immediately; others first emit a *reasoning trace* — several hundred tokens of thinking-aloud — and only then the answer. A budget sized for the answer alone is spent entirely on the trace, and the reply comes back truncated with `finish_reason: "length"` and *no answer at all*. `1024` is generous enough for a trace plus the one-line answer. It costs a direct-answering model nothing: `max_tokens` is a ceiling, not a target — measured, the same model spent 17 tokens whether the ceiling was 120 or 1024, with identical output.

*The trace is stripped, wherever it arrives.* A reasoning model returns its thinking either in a separate `reasoning_content` field or inline between `<think>` and `</think>`; the `re.search` handles both, and also the unterminated case where the budget ran out mid-thought. On a model that does not reason, there is nothing to match and the strip is a no-op — which is why this works on either kind of endpoint without you knowing in advance which one you have.

That `sed` is not decoration either. When the key is rejected, the model gateway can echo it *back in full* inside its own error body — and the failure branch prints that body, so without the redaction the failure path would print your key into your terminal. It replaces the value by *name* (the gateway's `Received=` field) and by *shape* (anything `sk-…` or JWT-shaped), which is why the rest of the message survives: you can still read which of the three key faults you hit, and the `sk-`/`eyJ` prefix is kept so "a JWT was staged where an API key was expected" is still diagnosable.

// ==== silently CLOSES the outer block instead of opening a nested one (the build stays green and
// the page renders wrong).
[WARNING]
.Never trim output to hide a credential
=====
It is tempting to cut the body to a fixed number of characters instead. Don't — this repo shipped exactly that, and measured the echoed key starting at character *201* behind a `cut -c1-200`. It was safe by ten characters, and any reword upstream would have printed it. Truncation makes a leak *look* fixed while leaving it one message-format change away. Redact the thing by name or by shape; a character count is not a control.
=====

Whichever model your cluster serves, a wired endpoint ends this block with `reads the URL from the environment: YES`. That is the wiring the module depends on: the MaaS key is *scoped to one model*, and both the key and the model name are sourced on-cluster — so the same content works against a cluster scoped to a different model with no edit. Ask for a model the key is not scoped to and the gateway is explicit about it: `key not allowed to access model`, `HTTP 401`.

*Manual path (graceful degradation).* No `[ADS]` entitlement? The point of the lesson — *externalize the config* — is identical; only the typing assistant differs.

*The accessor is only half of it — and the other half is the half MTA measures.*
The `hardcoded-ip-address` rule never fires on `PersistenceConfig.java`. It fires on the *literal*
`10.14.221.9` sitting at line 7 of `src/main/resources/persistence.properties`. Change the accessor
alone and the issue comes back in the next report unchanged, because the string the rule matched never
moved. Externalizing configuration means the value *leaves the build* — not merely that the code stops
reading it:
