== 1. Meet the migration target
⏱ *~5 min* · read the legacy code and find the anti-patterns MTA will flag

Before you analyze the app, look at what makes it *legacy*. Clone your fork into the terminal and read the three files that carry the worst offenders.

[source,sh,role=execute]
----
git clone $REPO /tmp/legacy 2>/dev/null || (cd /tmp/legacy && git pull)
sed -n '6,11p' /tmp/legacy/src/main/resources/persistence.properties
grep -n "AUDIT_LOG_PATH\|System.out" /tmp/legacy/src/main/java/com/parasol/claims/legacy/config/ApplicationConfiguration.java
grep -n "java.version\|ojdbc\|tomcat-servlet" /tmp/legacy/pom.xml
----

.Expected output (abridged — one representative line per file; config baked into the build, the exact things a container can't tolerate)
[source,texinfo]
----

jdbc.url=jdbc:oracle:thin:@10.14.221.9:1521/CLAIMSDB
jdbc.user=claims

== 3. Read the report like a consultant
⏱ *~6 min* · separate the mandatory blockers from the noise, and group by fix

A raw report is a wall of findings. Your job is to turn it into a *short work list*. Open the application's report and its *Issues* tab, sorted by *Category* then *Effort*.

Here is what `parasol-legacy-claims` actually reports (performed live against MTA {mta_version}):

[cols="2,1,1,3",options="header"]
|===
| Issue | Category | Effort | Fix (and where)

| Version of Spring not compatible with Jakarta EE 9+ | mandatory | 3 | Upgrade Spring / move to an embedded runtime (`pom.xml`)
| Hardcoded IP address | mandatory | 1 | Externalize to an env var (`persistence.properties`)
| File system - Java IO | mandatory | 1 | Log to stdout, not a host path (`ApplicationConfiguration.java`)
| The `javax` package replaced by `jakarta` | mandatory | 1 | Namespace migration (`Claim.java`, initializer)
| `javax.activation` replaced by `jakarta.activation` | mandatory | 1 | Dependency swap (`pom.xml`)
| Tomcat artifact not compatible with JBoss Web Server | mandatory | 1 | Drop the provided servlet API (`pom.xml`)
| `java.io` constructor defaults to UTF-8 (OpenJDK 21) | potential | 1 | Confirm charset assumptions
|===

The report totals *24 story points* — the per-rule efforts above, multiplied by how many places each fires. It also lists *15 technology tags* (Spring MVC, Spring DI, Spring Web, Spring Data JPA, Java Servlet): MTA doesn't just flag problems, it *inventories* what the app uses, which is gold for planning.

The consultant's read:

* *Start with mandatory.* Six of these are the whole job (the one *potential* finding is a check, not a blocker); the technology tags are context, not work.
* *Group by fix, not by finding.* Three of the mandatory issues (`javax` package, `javax.activation`, the Spring/Jakarta incompatibility) are *one migration* — the `javax`→`jakarta` move. The hardcoded IP and the filesystem write are the *externalize-config* theme. Grouped, "six issues" becomes "three pieces of work."
* *Effort is relative.* The Spring/Jakarta issue (effort 3) is the heaviest; the config externalizations (effort 1) are the cheap, high-value wins you do first.

== 4. Fix an issue with Developer Lightspeed for MTA `[ADS]`
⏱ *~8 min* · let the AI propose the config-externalization fix — then review it critically

You'll fix the *Hardcoded IP address* issue — the cheap, high-value win. *Red Hat Developer Lightspeed for MTA* — an AI feature of the *MTA extension for VS Code / Dev Spaces* — proposes a concrete diff for a selected issue.

[IMPORTANT]
.This section is `[ADS]` — and degrades gracefully
====
Developer Lightspeed for MTA is part of the *Red Hat Advanced Developer Suite* `[ADS]`. If your cluster has it, follow the *AI path*. If it doesn't, follow the *Manual path* — you fix the *same* issue by hand and the rest of the lab is identical. Check which applies — the command below asks the model endpoint for a real (1-token) completion with your cluster's key, so it reports the AI path only when the wiring *actually answers* (a ConfigMap and Secret can be present with an expired or mis-scoped key; only an `HTTP 200` proves the path works):

[source,sh,role=execute]
----
code=$(curl -sk -o /dev/null -w '%{http_code}' --max-time 20 \
  "$(oc get cm maas-config -n $NS -o jsonpath='{.data.endpoint}' 2>/dev/null)/chat/completions" \
  -H "Authorization: Bearer $(oc get secret maas-credentials -n $NS -o jsonpath='{.data.GENAI_API_KEY}' 2>/dev/null | base64 -d)" \
  -H 'Content-Type: application/json' \
  -d '{"model":"'"$(oc get cm maas-config -n $NS -o jsonpath='{.data.model}' 2>/dev/null)"'","max_tokens":1,"messages":[{"role":"user","content":"ping"}]}' \
  2>/dev/null)
case "$code" in
  200)     echo "AI path: Developer Lightspeed is wired (the model answered HTTP 200)." ;;
  401|403) echo "Manual path: the MaaS key is missing, expired, or not scoped to this model (HTTP $code) — fix by hand (graceful degradation)." ;;
  *)       echo "Manual path: the model endpoint did not answer (HTTP ${code:-000}) — fix by hand (graceful degradation)." ;;
esac
----
====

*AI path (Dev Spaces + MTA extension).* Open your fork in {devspaces_url}[Dev Spaces^]. The fork's `.vscode/extensions.json` *recommends* the *MTA extension* (and its `redhat.java` prerequisite) — accept the recommendation prompt when the workspace opens (or install it from the extensions view).
The model wiring is *not* mounted into the workspace automatically: Dev Spaces provisions your workspace in its own `{user}-devspaces` namespace, while the workshop's model credentials live in `{user}-modernize`. You are logged in as yourself in the *workspace terminal*, so export the three values the extension reads — type this in the *workspace* terminal (not the cockpit terminal):

[source,sh,subs="attributes"]
----
export GENAI_API_KEY=$(oc get secret maas-credentials -n {user}-modernize -o jsonpath='{.data.GENAI_API_KEY}' | base64 -d)
export GENAI_ENDPOINT=$(oc get cm maas-config -n {user}-modernize -o jsonpath='{.data.endpoint}')
export GENAI_MODEL=$(oc get cm maas-config -n {user}-modernize -o jsonpath='{.data.model}')
echo "model: $GENAI_MODEL @ $GENAI_ENDPOINT"
----

In the MTA extension view, open the *Hardcoded IP address* issue and choose the Developer Lightspeed *fix* action.
// [CAPTURE-VERIFY] the exact MTA-extension command name / lightbulb action in Dev Spaces {devspaces_version}.

The model returns a diff. For this issue, the real proposal (captured live against `{maas_model}`) replaces the compiled-in URL in `PersistenceConfig.java` with a runtime lookup:

[source,java]
----
// before:  dataSource.setUrl(config.getProperty("jdbc.url"));   // resolves the hardcoded jdbc:oracle:thin:@10.14.221.9:...
// after (Developer Lightspeed proposal):
dataSource.setUrl(System.getenv("CLAIMS_DB_URL"));
----

*Read the diff before accepting it.* It is correct here — it moves the value out of the build and into the environment, exactly the containerization fix — but you only *know* that because you read it. Accept it, then provide the value the way a container should, as an environment variable, not a literal.

[NOTE]
.Prove the AI wiring yourself (the grounded API path)
====
The IDE action above is a product UI, so here is the *same call* the extension makes, which you can run from the terminal to prove the key + model + endpoint work end-to-end:

[source,sh,role=execute]
----
curl -sS -k "$(oc get cm maas-config -n $NS -o jsonpath='{.data.endpoint}')/chat/completions" \
  -H "Authorization: Bearer $(oc get secret maas-credentials -n $NS -o jsonpath='{.data.GENAI_API_KEY}' | base64 -d)" \
  -H 'Content-Type: application/json' \
  -d '{"model":"'"$(oc get cm maas-config -n $NS -o jsonpath='{.data.model}')"'","temperature":0,"max_tokens":120,
       "messages":[{"role":"user","content":"Rewrite this to read the JDBC URL from env var CLAIMS_DB_URL, return only the Java line: dataSource.setUrl(\"jdbc:oracle:thin:@10.14.221.9:1521/CLAIMSDB\");"}]}' \
  | sed -E -e 's#Received=[^,]*#Received=<redacted>#g' \
           -e 's#(sk-|eyJ)[A-Za-z0-9._~+/=-]{8,}#\1<redacted>#g' \
  | python3 -c 'import sys,json
b=sys.stdin.read()
try: print(json.loads(b)["choices"][0]["message"]["content"])
except Exception: print("MaaS did not return a completion (a 401 — your key is not scoped to the model in maas-config — is the usual cause). Response follows, credentials already redacted:\n"+b)'
----

That `sed` is not decoration. When the key is rejected, the model gateway echoes it *back in full* inside its own error body — and the `except` branch prints that body, so without the redaction the failure path would print your key into your terminal. It replaces the value by *name* (the gateway's `Received=` field) and by *shape* (anything `sk-…` or JWT-shaped), which is why the rest of the message survives: you can still read which of the three key faults you hit, and the `sk-`/`eyJ` prefix is kept so "a JWT was staged where an API key was expected" is still diagnosable.

// 5-'=' delimiter: this WARNING is nested inside the enclosing [NOTE] ==== block, and a same-length
// ==== silently CLOSES the outer block instead of opening a nested one (the build stays green and
// the page renders wrong).
[WARNING]
.Never trim output to hide a credential
=====
It is tempting to cut the body to a fixed number of characters instead. Don't — this repo shipped exactly that, and measured the echoed key starting at character *201* behind a `cut -c1-200`. It was safe by ten characters, and any reword upstream would have printed it. Truncation makes a leak *look* fixed while leaving it one message-format change away. Redact the thing by name or by shape; a character count is not a control.
=====

Live, this returns `HTTP 200` and the `System.getenv("CLAIMS_DB_URL")` rewrite above. This is *exactly* the wiring the module fixes: the MaaS key is scoped per cluster and the model (`{maas_model}` here) is sourced on-cluster, so the same content targets a cluster whose key is scoped to a different model without a code change.
====

*Manual path (graceful degradation).* No `[ADS]` entitlement? Make the *same* change by hand in `PersistenceConfig.java` — replace the compiled-in `getProperty("jdbc.url")` with `System.getenv("CLAIMS_DB_URL")`. The point of the lesson — *externalize the config* — is identical; only the typing assistant differs.

== 6. Containerize and deploy the modernized service
⏱ *~8 min* · ship the modernized claims service to OpenShift — and fix a deliberate break

The modernized service is a container image (the Quarkus rebuild of the claims service). Deploy it to `{user}-modernize`. This step is *dual-path* — use the *Console* or the *CLI*.

You'll deploy it *with a deliberately wrong health-probe path first*, watch OpenShift catch it, then fix it — because a modernized app that lies about its health is worse than an honest legacy one.

[tabs]
====
Console::
+
--
In the {ocp_console_url}[OpenShift web console^] (project `{user}-modernize`), choose the masthead *Quick create* (+) menu → *Container images*.
Set the image to `image-registry.openshift-image-registry.svc:5000/ogsr-parasol-images/parasol-claims:1.1` and the name to `parasol-claims-modernized`.
