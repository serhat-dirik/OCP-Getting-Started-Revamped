== Source in, a running application out · 11 min

A Git repository with no image and no Dockerfile becomes a running, database-backed claims API, built by the platform out of content it can vouch for.

[IMPORTANT]
.Prep — run before the session
====
This demo starts from the finished lab state. Stage it before the session:

[source,sh,role=execute]
----
adm solve build-deliver
----

It leaves a finished, database-backed `parasol-claims` running in `{user}-dev` beside the `claims-db` PostgreSQL it uses, and returns in roughly *5–10 minutes* — longer on a cluster whose Maven and builder-image caches are still cold, so start it well ahead.

Nothing is deleted during the demo. Step 1 builds a *second* copy of the same source, named `claims-live`, beside the staged application, and step 4 wires that copy to the database the staged one already owns.

A Quarkus S2I build takes about *4–5 minutes* on a warmed node; the first build on a fresh cluster has neither cached Maven artifacts nor a cached builder image and runs considerably longer.

Have two browser tabs signed in as `{user}`: the web console, and the {gitea_url}/{user}/parasol-claims[parasol-claims repository^] whose URL step 1 pastes into the console.

NOTE: The console's *Import from Git* cannot reach the in-cluster Gitea host, so it reports the repository as unreachable and detects no import strategy. That is expected on this cluster: the *Java 21* builder is chosen by hand, and the build itself clones the repository without trouble.

CAUTION: If the live build is still running when step 4 arrives, use the staged `parasol-claims` instead — it is untouched, already wired to its database, and shows the same result. The live build's logs are still there afterwards.
====

=== Brief

image::build-deliver/build-deliver-01-build-spectrum.svg["A decision flow from an application to run: if an image already exists, deploy it with no build; with source and no need to control the base image, Import from Git builds it with Source-to-Image; where the base image and the build steps must be controlled, a Containerfile build with Buildah; and once the build belongs to the team, the same build runs from a pipeline."]

*Source, not an image*

One question comes first, because it can remove the build entirely: is there already an image? If so the platform simply runs it. With source and no image, OpenShift offers two build strategies — alternatives, one per application, not a ladder to climb.

*Source-to-Image is the paved road*

S2I takes a Git repository plus a supported language builder image and produces a runnable image. Nobody writes a `Containerfile`, and nobody owns a base image or its patching. A Containerfile build, run with Buildah, is the answer when something S2I cannot give is genuinely needed: a specific or hardened base image, a system package, an unusual build step.

*A pipeline is not a third strategy*

A pipeline runs whichever of those two was chosen, on every push, with test, scan, sign and promote around it. That is where a build goes once it belongs to the team rather than to one developer — a separate module.

*Where the image comes from*

Every container starts from a base image, and "where did this come from?" is the first question a security review asks. Red Hat's language builders are built on the Universal Base Image, maintained and patched, and already included in the subscription — and the platform team decides which of them developers see.

*In this demo*

. Source in a Git repository, built and deployed by the platform with no Dockerfile
. The software catalog those builder images and the database come from
. Two Red Hat registries, and what their different behaviour proves about provenance
. The built application wired to its database and serving claims on its own URL

=== 1 · Source to a running application — 3 min

Parasol's claims service arrives as source in Git: no image, no `Containerfile`. *Import from Git* hands that repository to a supported Java 21 builder and deploys what comes out, as a second copy named `claims-live` beside the staged application.

image::build-deliver/build-deliver-01-import-from-git.png["The console's Import from Git form showing the repository-is-unreachable and unable-to-detect-the-import-strategy warnings, with Import Strategy set to Builder Image and the row of language builder tiles below it."]

*Why it matters*

There is no Dockerfile to write, review or keep patched, and no build server of the customer's own. The build is an ordinary workload in the developer's own project, bound by that project's quota — not something happening off to the side.

*On screen* — masthead *Quick create* (+) → *Import from Git*. Paste `{gitea_url}/{user}/parasol-claims`; when the unreachable-repository warning appears, choose *Import Strategy → Builder Image* and the *Java 21* tile, set *Name* to `claims-live`, leave *Target port* at `8080`, then *Create*. The console lands in *Topology* with the build already starting.

*What just happened*

Source-to-Image paired the repository with the Java 21 builder image — the same pairing the CLI writes as `java-21~<repo>`. That build runs for the next few minutes, and neither of the two steps after this one waits on it.

=== 2 · Where the builder images and the database come from — 3 min

The software catalog is the platform's front door: the builder images, databases and templates a developer on this cluster can start from, chosen by the platform team rather than found on the internet.

image::build-deliver/build-deliver-02-catalog-postgres-tile.png["The Software Catalog filtered to the Databases category: MariaDB, MySQL and PostgreSQL tiles, each provided by Red Hat, with the Parasol PostgreSQL (ephemeral) tile at the bottom of the frame."]

*Why it matters*

Everything on this page is curated. The language builders are UBI-based — Red Hat's Universal Base Image, maintained and patched — and the subscription already covers a wider road than most people expect: Java, Node.js, Python, .NET, Go, Ruby, PHP, plus JBoss EAP, JBoss Web Server, httpd and nginx. An administrator adds any other Red Hat builder to the same catalog, which is exactly how the Java 21 builder in step 1 got here.

*On screen* — *Ecosystem* → *Software Catalog*: the *Databases* category, where the Parasol PostgreSQL tile that provides `claims-db` lives, then *Type → Builder Images* for the language builders, the Java 21 one among them.

=== 3 · Two registries, two trust models — 2 min

One level deeper on trust: the base images underneath those builders come from two Red Hat registries that behave differently on purpose, and the image this build produces is tagged into an ImageStream in the project itself.

....
include::example$diagrams/build-deliver/04-registry-trust.mmd[]

*Why it matters*

"Which base images are we allowed to use, and can we prove where they came from?" is the whole of software supply chain security, and it starts with content whose origin can be named and whose patches arrive from someone under contract. Inside the cluster the same question has an answer too: the build's output is tagged in an ImageStream in this project, so what is deployed points at a specific image the cluster produced.

[source,sh,role=execute]
----
oc run probe --image=registry.access.redhat.com/ubi9/ubi-minimal --restart=Never --rm -i --command -- curl -sI https://registry.access.redhat.com/v2/ | head -1
----

*What just happened*

`registry.access.redhat.com` served a UBI image to a Pod on this cluster with no credentials at all. The fuller catalog on `registry.redhat.io` refuses the same anonymous request and needs the cluster's pull secret. That difference is provenance made concrete: what is running here is always traceable to a registry someone maintains.

=== 4 · Wire it to the database and serve claims — 3 min

The build has finished and `claims-live` is running, but a freshly built application does not know where its database lives. One command hands it the credentials the catalog database already published as a Secret.

image::build-deliver/build-deliver-03-what-you-built.svg["The finished chain: the parasol-claims source in the developer's Git fork built by the java-21 Source-to-Image builder into an ImageStream tag, deployed as a Deployment that takes the claims-db Secret as environment variables and reaches the PostgreSQL database from the catalog, published through a Service on port 8080 and a Route a claims adjuster reaches over HTTPS."]

*Why it matters*

The image is built once and carries no environment inside it; what it connects to is configuration, handed over at deploy time. That separation is what lets the same image move from dev to production unchanged — the subject of the configuration module.

[source,sh,role=execute,subs="attributes"]
----
oc -n {user}-dev set env deploy/claims-live --from=secret/claims-db
oc -n {user}-dev rollout status deploy/claims-live
----

*On screen* — *Topology* → the `claims-live` node → its *Resources* tab → the completed *Build*; then open the application's Route and call `/api/claims`, which returns the seeded claims as JSON.

*What just happened*

A Git repository became a running, database-backed API on its own URL: the platform built the image from source, one line of configuration wired it to the catalog database, and a Route published it. No Dockerfile, no registry credentials, and nothing installed on anyone's machine.

== Frequently asked questions

*Source-to-Image or a Containerfile — how do we choose?*::
Default to S2I: nothing is written, the platform builds the source with a supported and patched builder image, and no `Containerfile` is owned. Reach for a Containerfile build only for something S2I cannot give — a specific or hardened base image, a system package, an unusual build step. The test is whether there is a reason to own a base image; if not, S2I.

*Why is the builder called `java-21` rather than `java`?*::
Because a platform team pinned it. The stock OpenShift samples ship a `java` stream that trails the current release, so this cluster carries its own Java 21 builder on UBI 9 and every build lands on the same current JDK. Curating that list is precisely what a platform team does, and how such a list is published and kept current is the Developer Hub module.

*Where do the builds run, and what stops them consuming the cluster?*::
Each build runs in a build Pod in the developer's own namespace, under that namespace's ResourceQuota and LimitRange — a first-class, quota-bound workload like any other. The default 1 GiB container limit carries these Quarkus builds; a larger application can need more, set on its BuildConfig.

*The console said the repository was unreachable. Is that a problem?*::
Only for the console's inspection. The console backend on this cluster cannot reach the in-cluster Git host, so it cannot read the repository to detect a strategy — the build itself clones it fine. Where the Git server is reachable the strategy is detected automatically, and choosing the builder by hand is the same choice the CLI's `java-21~<repo>` makes.

*Is that database real, and where does the data go?*::
It is a real PostgreSQL 15, but deliberately ephemeral here: it stores to an `emptyDir`, so restarting the Pod loses everything in it. Giving a database durable, identity-stable storage is the storage module. Nothing anyone cares about should point at an ephemeral database.

The workshop provides a *Java 21* builder (`java-21`) in the shared catalog; because the claims service is a Java 21 application, that builder is the right match.

[TIP]
.Why the first build is slow — and how real orgs speed it up
====
Almost all of that wait is *Maven downloading the dependency tree from the public internet* (`repo1.maven.org`), not compiling — a cold build with an empty cache fetches hundreds of jars.
Two techniques an organization uses to make this fast, neither of which changes your code:

* *An internal artifact repository (Maven mirror).*
A platform team runs a repository manager — Sonatype Nexus or JFrog Artifactory — inside the network and points builds at it.
On the Red Hat Java builder that is one BuildConfig environment variable, `MAVEN_MIRROR_URL` (several mirrors: `MAVEN_MIRRORS` lists prefixes, each with its own `<PREFIX>_MAVEN_MIRROR_URL`); a `settings.xml` `<mirror>` baked into the builder image or mounted from a ConfigMap does the same job.
Dependencies then come from the LAN cache at wire speed, the build stops depending on the public internet — and, the reason platform teams actually do it, the mirror decides which libraries may enter a build at all and caches them for audit.
* *Incremental builds.*
Source-to-Image can *reuse* the previous build's artifacts (the `.m2` repository) instead of downloading them again — set `spec.strategy.sourceStrategy.incremental: true` on the BuildConfig, and the second build onward skips most of the download.

Slow builds read as "the platform is inefficient," but the real cause is dependency egress — and both fixes are platform-team decisions, not app changes.
====

Now look at *how* the platform recorded the build — a first-class object, not a shell script:

[source,sh,role=execute]
----
oc get buildconfig parasol-claims -o jsonpath='{.spec.strategy.type}{"\n"}'
----

[source,sh,role=execute]
----
oc get istag parasol-claims:latest -o jsonpath='pushed image: {.image.dockerImageReference}{"\n"}'
----

The BuildConfig's strategy is `Source` — that is S2I.
The ImageStream now has a `parasol-claims:latest` tag pointing at the image you just built, living in the cluster's internal registry.
The `pushed image:` line prints a *digest* (`…/parasol-claims@sha256:…`), not the `:latest` tag — that digest is the immutable content address S2I pushed, and it is exactly what `:latest` resolves to right now. Referencing an image by digest is what guarantees every replica runs the identical bytes you just built.

[IMPORTANT]
.Your app builds, then can't fully start — that is expected
====
Once the build finishes, the Deployment runs your image — and the Pod goes into `CrashLoopBackOff`.
That is *not* a build failure; the build succeeded.
The claims service needs a *PostgreSQL database* to start (it creates its schema and loads seed data at boot), and there is no database yet.
Confirm what it is complaining about:

[source,sh,role=execute]
----
oc logs deployment/parasol-claims --tail=40 | grep -iE 'UnknownHost|PSQLException|connection attempt|datasource' | head -3
----

.Expected output
[source,texinfo]
----
Caused by: org.postgresql.util.PSQLException: The connection attempt failed.
Caused by: java.net.UnknownHostException: parasol-db
----

`parasol-db` is the datasource host the image falls back to when nothing sets `POSTGRESQL_HOST` — no Service by that name exists in your project yet, so the driver cannot resolve it.
Leave it crash-looping — you will give it a database in exercise 4 and wire it up in exercise 5.
This is a real dependency, and fixing it is the payoff at the end of the lab.
====

== 2. The same app, the Dockerfile way — and why you'd choose it
⏱ *~10 min* · full control, at the cost of owning the build recipe — most of it spent watching a build

S2I built the image *for* you from a builder image you did not write.
Sometimes you need control S2I does not give — a specific base image, a system package, an exact build.
Your `parasol-claims` repo ships a `Dockerfile` — a multi-stage build recipe (a fat build stage, a lean runtime stage) — so you can build the *same source* with the *Docker* strategy and compare the two build strategies side by side.

[NOTE]
.`Dockerfile` or `Containerfile`?
====
The Docker build strategy looks for a file named `Dockerfile` by default, so the command below just works.
`Containerfile` is Red Hat's vendor-neutral name for the very same file, and this repo ships both (identical) so either tool finds a recipe.
If a repo has *only* a `Containerfile`, the Docker strategy will not auto-detect it — you point the build at it explicitly with a BuildConfig `dockerfilePath: Containerfile` (or the console's *Dockerfile path* field).
The xref:build-deliver/troubleshooting.adoc[troubleshooting page] shows that fallback.
====

[tabs]
====
Console::
+
--
. Open the masthead *Quick create* (+) menu → *Import from Git* again.
. Paste the same URL: `{gitea_url}/{user}/parasol-claims`.
The same *unreachable-repository* warning appears — ignore it and choose the strategy yourself, exactly as in exercise 1.
. Under *Import Strategy*, choose *Dockerfile*.
The *Dockerfile path* field defaults to `Dockerfile` — the exact file in the repo, so leave it.
. Set the *Name* to `claims-docker` (so it does not collide with your S2I app), and click *Create*.
--
CLI::
+
--
Because the repo has a `Dockerfile`, `--strategy=docker` finds it and builds — nothing else to specify:

// `adm start` does NOT clear a leftover BuildConfig/ImageStream/Deployment/Service from a prior pass
// on this same cluster (only `ws reset`/`ws prep` do); guarded the same way as the S2I import above,
// rather than deleting build history a re-run doesn't need to touch.
[source,sh,role=execute,subs="attributes"]
----
if oc get bc claims-docker >/dev/null 2>&1; then
  echo "claims-docker already exists — this module already ran in this namespace; skipping oc new-app and reusing the existing build."
else
  oc new-app --strategy=docker {gitea_url}/{user}/parasol-claims.git --name=claims-docker
fi
----

Like the S2I import, this creates a *BuildConfig* (this time `Docker`-strategy), a *Deployment*, and a *Service* — plus *two* ImageStreams, not one: `claims-docker` for your built image, and `openjdk-21-runtime` to track the runtime base image the multi-stage `Containerfile` copies into. The S2I import needed only one because its builder image was already tracked. Both are labelled `app=claims-docker`, so the cleanup at the end of this exercise removes them together.
Follow the multi-stage build (it compiles in the JDK 21 build stage, then copies the artifact into the lean runtime stage):

[source,sh,role=execute]
----
oc logs -f bc/claims-docker
----
--
====

Like your S2I app in exercise 1, the `claims-docker` Deployment will crash-loop until it has a database — expected, and it does not affect the build you came here to compare.

Now compare the two BuildConfigs side by side:

[source,sh,role=execute]
----
oc get bc parasol-claims claims-docker -o custom-columns=NAME:.metadata.name,STRATEGY:.spec.strategy.type
----

.Expected output
[source,texinfo]
----
NAME             STRATEGY
parasol-claims   Source
claims-docker    Docker
----

Same source, two strategies.
The *Source* (S2I) build used the platform's Java 21 builder — you conform to its runtime.
The *Docker* build ran the repo's own multi-stage recipe, which pins its *own* base images (`ubi9/openjdk-21` to build, `ubi9/openjdk-21-runtime` to run) — you control the runtime, and you own that file forever.

[TIP]
.Which did you just prove you'd rather maintain?
====
Both produced a working image.
S2I needed *nothing* from you but the source; the Docker path needed a hand-written, hand-patched build recipe.
For most services, that is the whole argument for S2I — and the wrap-up returns to when the Docker path genuinely earns its keep.
====

You do not need `claims-docker` past this comparison — clean it up so it does not clutter your project:

[source,sh,role=execute]
----
oc delete all -l app=claims-docker
----

[.checkpoint]
****
✔ *Verify:* `oc get bc` showed `parasol-claims` as `Source` and `claims-docker` as `Docker` before you deleted the latter.
You understand the trade-off: S2I = the platform owns the build; Dockerfile = you own the base image and the recipe.

== 5. Wire the claims service to its database
⏱ *~5 min* · the break-and-fix payoff — and a preview of config

The database is running; the claims service is still crash-looping because it does not yet know where the database is.
The claims image reads its datasource from environment variables (`POSTGRESQL_HOST`, `POSTGRESQL_DATABASE`, `POSTGRESQL_USER`, `POSTGRESQL_PASSWORD`) — and the `claims-db` Secret holds exactly those keys.
So wiring them is one command: pull every key from the Secret into the Deployment as environment.

[tabs]
====
Console::
+
--
. In *Topology* (under *Workloads*), click the `parasol-claims` node → *Actions* → *Edit Deployment* (or open the Deployment's *Environment* tab).
. In the *All values from existing ConfigMaps or Secrets (envFrom)* section, add the `claims-db` Secret — this pulls *every* key from it, the same as the CLI's `--from=secret/claims-db`.
. Save.
The Deployment rolls out a new Pod with the database environment; it starts, connects, and goes Ready.
--
CLI::
+
--
[source,sh,role=execute]
----
oc set env deployment/parasol-claims --from=secret/claims-db
----

.Expected output
[source,texinfo]
----
deployment.apps/parasol-claims updated
----

Watch the crash loop turn into a healthy Pod:

[source,sh,role=execute]
----
oc rollout status deployment/parasol-claims
----
--
====

The rollout replaces the crash-looping Pod with one that carries the database environment.
Read its log — the same image that could not resolve `parasol-db` a moment ago now boots cleanly.

Now open *Topology* and make it match the picture in your head.
By default it looks scattered: `claims-db` sits inside an application group named *parasol* (its catalog template stamped the `app.kubernetes.io/part-of=parasol` label), while `parasol-claims` and `parasol-notifications` — which `oc new-app` labelled only with their own names — float as separate, ungrouped nodes, and nothing draws the line from the claims service to the database it depends on.
Two labels fix that, and they are worth knowing because this is exactly how the console decides what to group and what to connect:

[source,sh,role=execute]
----
# group all three under one "parasol" application, and draw claims -> claims-db
oc label deploy/parasol-claims deploy/parasol-notifications svc/parasol-claims svc/parasol-notifications \
  app.kubernetes.io/part-of=parasol --overwrite
oc annotate deploy/parasol-claims app.openshift.io/connects-to='["claims-db"]' --overwrite
----

Refresh *Topology*: one *parasol* application now holds all three workloads, with an arrow from `parasol-claims` to `claims-db`.
The `part-of` label groups; the `connects-to` annotation connects — your topology finally matches your mental model.
